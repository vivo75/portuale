## 1. What real Portage does

Real's built-in `world` set is a `DummyPackageSet` over three nested
sets, in this order (`portage/_sets/__init__.py:97-98`):

```python
parser.set("world", "class", "portage.sets.base.DummyPackageSet")
parser.set("world", "packages", "@profile @selected @system")
```

- `@selected`  = `WorldSelectedSet` (world file + `world_sets`).
- `@system`    = `PackagesSystemSet` (`_sets/profiles.py:41-75`): reads
  **every** profile level's `packages` file
  (`profiles_complex`), stacks them with `stack_lists(incremental=1)`
  (so `-atom` removal spans levels), and keeps only `*`-prefixed lines
  (the `*` stripped).
- `@profile`   = `ProfilePackageSet` (`_sets/profiles.py:13-38`): same
  stacking, but the source list is filtered to profile levels whose
  **repo declares `profile-set`** in `metadata/layout.conf`
  (`if "profile-set" in y.profile_formats`, `:40`), and the kept lines
  are the **unstarred** ones (`if str(x)[:1] != "*"`, `:38`).

`_valid_profile_formats` lists `profile-set`
(`portage/repository/config.py:56-68`). On this host the active profile
lives in the `buildovl` repo, whose `layout.conf` declares
`profile-formats = portage-2 profile-set profile-bashrcs`; its
`profiles/vivo/desktop/packages` file is 100 unstarred lines — that is
the whole missing set (rclone, linux-firmware, virt-manager/weston, …).
Gentoo's own profile levels (repo without `profile-set`) contribute
nothing to `@profile`, only starred `@system` atoms.

Display side: real's world-colour column is computed from
`root.sets["selected"]` (`_emerge/resolver/output_helpers.py:233`), so
`@profile` membership must **not** change the `[W]`/world colouring.

## 2. Portuale today

- `resolve_config` reads every chain level's `packages` into
  `packages_sources`, stacks with `stack_mask_lines`, and keeps only
  `*`-prefixed lines as `config.system_packages`
  (`portage-profile/src/lib.rs:3152-3168`). The unstarred lines are
  deliberately dropped (the fixture comment at
  `fixtures/repo/profiles/base/packages` documents the current model).
- `@world` expands as selected + system only:
  - resolver/display path: `pretend.rs:10093-10110` (with a comment that
    names `@selected ∪ @system ∪ @profile` as real's definition);
  - graph seeding: `pretend.rs:10468-10469`
    (`expand_selected(...)` + `config.system_packages`);
  - `-C`/`--deselect` path: `pretend.rs:3203` expands `@world` to
    `expand_selected` only (a pre-existing wider gap, see §7).
- `@profile` is not an accepted target: it falls through to
  `resolve_custom_set` and errors as "set 'profile' not found".
- `read_world_atoms` (`pretend.rs:2231`, display/`:10749`) is
  intentionally `@selected` and stays that way.

The repo-level gate has partial machinery already: `repo_profile_formats`
(`portage-profile/src/lib.rs:1470-1486`) reads a repo's
`layout.conf` list, and `repo_containing` (`:1488-1497`) maps a profile
dir to its repo (both used today only for the `parent` colon gate at
`resolve_config` `:2283-2295`).

## 3. Design

**S1 — `Config::profile_packages`.** In `resolve_config`, next to the
`system_packages` block, collect only the chain levels whose containing
repo declares `profile-set`, stack those files with the same
`stack_mask_lines`, and keep the **unstarred** lines:

```rust
let mut profile_sources: Vec<Vec<String>> = Vec::new();
for level in &chain {
    let qualifies = repo_containing(level, &all_repos)
        .map(|(_, loc)| {
            repo_profile_formats(&loc)
                .iter()
                .any(|f| f == "profile-set")
        })
        .unwrap_or(false);
    if qualifies {
        profile_sources.push(read_config_lines(&level.join("packages"))?);
    }
}
config.profile_packages = stack_mask_lines(&profile_sources)
    .into_iter()
    .filter(|line| !line.starts_with('*'))
    .collect();
```

Note the asymmetry that must be preserved: `@system` stacks **all**
levels (current code is right), `@profile` only `profile-set` levels.
For a level not inside any configured repo (`repo_containing` → `None`,
e.g. a bare temp profile in unit tests) the `profile-set` gate is false
— matching real's user-config node behaviour closely enough for this
slice, and documented as a narrowing in the field's doc comment.

**S2 — expand `@profile` everywhere `@world` is built.**

- `@world` in the resolve path (`pretend.rs:10093`): append
  `config.profile_packages` **before** the selected atoms and the sorted
  `@system` atoms, mirroring the real set's `@profile @selected @system`
  order. Keep the existing per-arg `sorted(...)` handling for the
  `@system` segment (`depgraph.py:5500`).
- Graph seeding (`pretend.rs:10468`): same three-way union.
- Add `"@profile"` as a first-class target arm next to `@system` in both
  the resolve path and the `-C`/unmerge expansion
  (`pretend.rs:3203-3220`): real exposes `@profile` as a set name, so
  `emerge -p @profile` must resolve to the same atom list.
- Do **not** touch `read_world_atoms` / the display `world_atoms`
  (`pretend.rs:10749`): real colours from `@selected`.

## 5. Tests and pins

Rust (`portage-profile/src/lib.rs` unit tests, modelled on
`system_packages_stack_across_profile_levels_with_atom_removal_and_star_filter`
at `:4561`):

- positive: a repo whose `metadata/layout.conf` declares
  `profile-formats = portage-2 profile-set`, a base level with
  `*dev-libs/a` + `dev-libs/hint`, and a leaf with `-dev-libs/hint` +
  `dev-libs/leafpkg`; assert `profile_packages == ["dev-libs/leafpkg"]`
  and `system_packages == ["dev-libs/a"]`, proving both the star filter
  and the cross-level `-atom` removal.
- negative control: same tree with `profile-formats = portage-2` (the
  committed fixture's value) → `profile_packages` empty and `hint` still
  absent from `@system`.

Python contract (`tests/test_emerge_pretend_contract.py`; the committed
fixture repo declares only `portage-2`, so **every existing pin stays
byte-identical** — that is a required property of this slice):

- negative: `emerge --pretend @world` output on the committed fixture is
  unchanged (`dev-libs/hintonly` remains out of `@world`).
- positive: copy `fixtures/` into `tmp_path` (pattern
  `_reversed_repos_conf` in `tests/test_output_invariants.py`), rewrite
  the copied main repo's `metadata/layout.conf` to add `profile-set`,
  add an unstarred `dev-libs/hintonly`-style atom (or reuse the existing
  hint line), then:
  - `emerge --pretend @world` lists that atom as a target;
  - `emerge --pretend @profile` lists exactly the profile atoms and
    `emerge --pretend @system` does not;
  - an `@world` update (`--update`) proposes the profile atom's upgrade
    path like any other target.
- optional, if cheap: a second copied configroot with an overlay profile
  level (parent chain into `fixtures/overlay`) to prove per-level repo
  gating rather than "all or nothing".

## 7. Non-goals and residue

- The `-C`/`--deselect` `@world` arm (`pretend.rs:3203`) currently
  expands to `@selected` only — it does not even include `@system`.
  Fixing that is a separate parity item (real `emerge -C @world` removes
  `@system` and `@profile` members too); this slice may add `@profile`
  there as a target but must not silently change `-C @world` semantics
  without its own pins. File the residue if not done here.
- `@profile` for non-repo/user-config profile nodes (real's per-node
  `profile_formats` for `PORTAGE_CONFIGROOT/profile`) is approximated by
  the `repo_containing` gate; document, don't over-engineer.
- No change to world-file recording (`saveNomergeFavorites`): a merged
  `@profile` member must not be written to `world` (real keeps it out
  because it is not in `@selected`).

## 8. Risks

- **Seed-order sensitivity:** `pretend.rs:10468` feeds the resolver's
  discovery order; inserting the profile atoms first changes nothing on
  the committed fixture (empty profile set) but must be re-verified on
  the host after S2 (compare the real-vs-portuale diff again against the
  evidence files).
- **Gate source:** do not infer `profile-set` from `portage-2`; the
  fixture proves the two are independent, and Gentoo's own repo
  (`portage-1-compat`) also has neither.
- **EAPI floor:** profile `packages` stacking is EAPI-independent here;
  no EAPI 0–6 branches to consider.
