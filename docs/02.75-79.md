## 2. What each item is, in code

Portuale's Phase D machinery, as shipped (all symbols current on
`9ee5473`):

- `portage-repo/src/lib.rs::resolve_blockers` classifies each blocker row
  and sets `BlockerConflict::satisfied_by`:
  `Some(Replacement { cp, slot })` for the replaced-in-slot arm,
  `Some(Uninstall { cpv })` **only when `!unsolvable && owner_merging`**,
  `None` otherwise.
- `lib.rs::file_blocker_conflicts` files each row on its owner entry and
  appends one `uninstall_entry` (`PretendOutcome::Uninstall`) per
  `satisfied_by: Uninstall` cpv, anchored on the owner.
- `portuale/src/pretend.rs::blocker_row_disposition` maps a row to
  `Inline(index)` / `Trailing` / `Hidden`; `replacement_wait_index` is
  the `Replacement` arm's mechanism predicate;
  `collect_inline_blocker_lines` compiles the `(after, line)` pairs and
  `count_blocker_rows` counts everything that is not `Hidden`.
- The flat loop and `print_tree` both consume
  `collect_inline_blocker_lines`; `print_tree` passes `columns = false`
  unconditionally (the CLI refuses `--tree` + `--columns`).

Against that, the five items are:

- **#75** — `print_tree` uses the flat predicate *and* the flat
  placement. Real's tree mode differs in both: a different serialization
  (which rows exist at all) and a different display list (where they go).
- **#76** — `replacement_wait_index` skips every `DepEdge` with
  `alt.is_some()`, so a wait chain that runs through a `|| ( … )` branch
  reads as "no wait" and the row is `Hidden`.
- **#77** — `resolve_blockers`' nomerge-owner arm leaves `satisfied_by:
  None`, so `file_blocker_conflicts` fabricates no removal entry and the
  row stays in the trailing group.
- **#78** — with `--backtrack=0` real prints an empty merge list where
  portuale upgrades the provider.
- **#79** — portuale's backtracker masks away the blocker-carrying
  candidate real keeps, so a `[blocks B]` + rc 1 becomes a silent rc 0.

### #75 — **confirmed, and under-scoped by half**

Confirmed:

- `tree_mode = "--tree" in self._frozen_config.myopts`
  (`depgraph.py:9680`) and the greedy leaf pop is disabled in tree mode
  (`depgraph.py:9764-9777`, comment *"This optimization destroys --tree
  output, so it's disabled in tree mode"*). So tree mode really can reach
  the stuck-serializer state (`:9998`) that schedules the uninstall
  (`:10190`) and appends the solved blocker (`:10351-10358`) in shapes
  where flat mode does not — exactly what B0's tree p2b captured.
- `depgraph.display()` reverses the list in tree mode:
  `if "--tree" in self._frozen_config.myopts: mylist = tuple(reversed(mylist))`
  (`depgraph.py:10618-10619`).
- Portuale applies the flat predicate and flat placement in tree mode
  (`pretend.rs::print_tree` calls `collect_inline_blocker_lines(entries,
  root, quiet, false, color)` and prints each line after entry `i`,
  the same as the flat loop).

**Correction — the backlog says closing this "needs a tree-mode port of
the serializer's leaf selection, a `merge_order.rs` item". That is only
one of the two halves.** The other half is the display list itself:
`output.py:585-586` routes tree mode through
`output_helpers.py::_tree_display` (`:341-407`; layout `:434-495`,
pruning `:497+`), which before laying out
anything **rewrites the graph's blocker edges**: it substitutes the
`Uninstall` node for the installed "nomerge" node, expands
`Package -> Uninstall` into `Package -> Blocker -> Uninstall`
(`:381-390`), and — the case that matters here — when the uninstall task
was *not* executed because of an upgrade, adds
`upgrade_node -> blocker` edges so the blocker is shown against the
**replacement** (`:392-398`). Then `_ordered_tree_display`
(`:434-495`) / `_unordered_tree_display` (`:410-431`) lay it out and
`_prune_tree_display` trims it.

That is why B0b's p2c-t capture shows the `b` row *before*
`blocked-2.0`, with the tree's two-space bracket width: it is a child of
the upgrade node in a reversed list, not a line appended after a package
line. So #75 splits cleanly into a cheap display half and an expensive
scheduling half — §4 C slices it that way, so the cheap half ships even
if the expensive half stops.

### #76 — **confirmed, and the proposed fix is the wrong shape**

Confirmed: `replacement_wait_index` opens its edge loop with
`if edge.alt.is_some() || edge.priority.optional ||
edge.priority.runtime_post { continue; }`, so no `|| ( … )` member is
ever traversed.

**Correction — the backlog says real "resolves one `||` branch through
`dep_zapdeps`, so [we] need a real capture of such a shape before
widening".** The capture is still needed (it is B0), but the inference
that follows from it is wrong. `dep_zapdeps` runs during **graph
construction**; the wait predicate models the **serializer**, which runs
over `self._dynamic_config.digraph` *after* the `||` has already
collapsed to one concrete child edge. So the predicate must not "follow
`||` branches" (plural) at all — it must follow **the one branch this
run actually selected**, exactly like every other edge.

Portuale already computes that selection: `merge_order.rs::build_digraph`
derives `alt_suppressed` (one kept branch per `(group, branch)` via
`DepEdge::alt`, ranked the way `dep_zapdeps`' `choice_bins` ranks:
all-in-graph, then all-installed, then first) and this is the same seam
backlog #53 corrected. So the fix is "reuse `build_digraph`'s kept-branch
set in `replacement_wait_index`", not "port `dep_zapdeps` into
`pretend.rs`" — a far smaller change, and one whose regression guard
(#53's `mopodman` pins) already exists.

### #77 — **confirmed, and much smaller than filed**

Confirmed, line by line, in `_validate_blockers`' `blocked_final` loop:

- `if parent.operation == "nomerge" and pkg.operation == "nomerge":
  continue` (`depgraph.py:9192-9195`) — the blocked instance must be
  merging for this arm to be reachable.
- `elif parent.operation == "nomerge": depends_on_order.add((parent,
  pkg))` (`depgraph.py:9204-9206`) — the **owner** (`parent`) is the
  first element, i.e. the uninstall target; `pkg` (the merging blocked
  instance) is only the ordering anchor.
- The guard that can still make it unresolved: *"Make sure we don't
  unmerge any package that have been pulled into the graph"* —
  `digraph.contains(inst_pkg) and digraph.parent_nodes(inst_pkg)` →
  `unresolved_blocks = True` (`depgraph.py:9216-9224`).
- The task itself: `Package(..., cpv=inst_pkg.cpv, operation="uninstall",
  ...)` built from `inst_pkg`, i.e. from the owner, then
  `digraph.addnode(uninst_task, inst_task, priority=BlockerDepPriority.instance)`
  (`depgraph.py:9226-9242`).

**Correction — "not modelled" overstates it.** #73 already shipped
exactly this arm's *classification*: `resolve_blockers`' nomerge branch
computes `merge_bound_match && (graph_has_parent(owner…) ||
owner_set_parent(…))` as its `unsolvable`, which is portuale's port of
`:9204-9206` plus the `:9216-9224` guard. What is missing is one line:
the arm sets `satisfied_by: None` because the tagging condition is
`if !unsolvable && owner_merging`. Tag the nomerge arm with
`Uninstall { cpv: <owner cpv> }` and the already-shipped B3/B4 machinery
(`file_blocker_conflicts` → `uninstall_entry` → `blocker_row_disposition`
→ `collect_inline_blocker_lines`) produces and places the row with no
further changes.

One genuine design question survives, and it is A1's stop rule:
`file_blocker_conflicts` anchors the removal entry on the owner entry and
`uninstall_entry` sets `required_by = owners`. For this arm the owner
**is** the removal target, so the entry would list itself as its own
puller. Real's digraph says otherwise: the uninstall's parent is
`inst_task`, i.e. the *merging blocked instance* (`:9240-9242`). A1 must
anchor `required_by` on that instance, not on the owner, and the A0
capture's `--tree` cell is what proves it.

### #78 — **the observation is right; the diagnosis is wrong**

Confirmed:

- `--backtrack=0` really does disable the whole cascade:
  `max_retries = 0 if nodeps else myopts.get("--backtrack", 20)` and
  `allow_backtracking = max_retries > 0` (`depgraph.py:12188-12190`),
  and the cascade's entry point is gated on it —
  `if self._dynamic_config._allow_backtracking:
  self._slot_operator_trigger_reinstalls()` (`depgraph.py:2131-2132`).
- `FakeVartree._apply_dynamic_deps` does preserve the built `:=` atoms:
  it collects `find_built_slot_operator_atoms(pkg)` and appends them to
  the live ebuild metadata before `aux_update` (`FakeVartree.py:164-182`).
  So real's *resting* graph reads the installed consumer's recorded
  `provpkg:0/1=`, which the installed provider satisfies — hence the
  empty merge list.

**Correction — "portuale does not model [`_apply_dynamic_deps`]" is
false (T13).** Portuale implements it:
`lib.rs::installed_dep_string` appends
`built_slot_operator_atoms(&raw, &use_flags)` to the live ebuild value,
`built_slot_operator_atoms` is a documented port of
`portage/dep/_slot_operator.py:24-38` (including the "`:2=` without a
sub-slot is *not* built" rule), and
`installed_dep_string_appends_only_vdb_built_slot_operator_atoms` pins
it.

The append is **gated off by default**, behind
`PORTUALE_DYNAMIC_DEPS_APPEND` (`lib.rs`: `DYNAMIC_DEPS_APPEND`,
`set_dynamic_deps_append`, `dynamic_deps_append_enabled`). Its own doc
comment says why: two #24 oracle pins (`slotchange-case4`,
`slotundo-cascade`) prove the resolver cannot yet reconcile a vdb-built
`:S/SS=` atom walking alongside the ebuild's unbound `:=` for the same
cp; real reconciles that pair through the slot-operator rebuild probe and
portuale drops the cascade's second consumer.

This reshapes #78 completely:

- It is **not** a `--backtrack=0`-only artifact. With backtracking on,
  real's `_slot_operator_trigger_reinstalls` converges on the same answer
  by a second route, which *masks* the model difference; `--backtrack=0`
  merely removes the mask. The divergence is latent in every run.
- The fix is not "model dynamic deps"; it is "make the resolver able to
  walk the appended atom, then flip the gate's default". That is the #24
  probe-ordering work the gate's comment already names.
- And there is a five-minute decisive experiment nobody ran: re-run the
  #78 probe with `PORTUALE_DYNAMIC_DEPS_APPEND=1`. If real's empty merge
  list appears, the whole item is the gate; if it does not, the item is
  something else and E0's stop rule fires. §4 E0 makes that the first
  thing to do.

### #79 — **the observation is right; two corrections to the diagnosis**

Confirmed: the divergence, the trace evidence and the general shape
(portuale masks a version through backtracker feedback and settles on the
installed one) all stand as `TEST/findings/l0.md` "#74 S2b" records them.

**Correction 1 (T14) — "the only producer of `!=cat/pkg-<ver>` masks is
`collect_feedback`'s slot-conflict feedback" is false.** `MaskReason` has
two variants, `SlotConflict` and `MissingDependency`, and
`BacktrackFeedback` has three arms (`Config`, `SlotConflict`,
`MissingDep`). A `MissingDep` feedback produces the same `!=` negative
shape. D0 must re-run the trace and say **which** arm fired, not assume.
There is a third candidate the finding did not consider at all:
`collect_feedback`'s *solvable* pre-check, which — when one version
satisfies every recorded want-atom — returns `BacktrackFeedback::Config`
with a `slot_constraints` entry instead of a mask. In the gtk-doc-am
shape the want-atoms plausibly include `>=dev-build/gtk-doc-am-1.3` and
(from the installed `gtk-doc-1.34.0`'s own `BDEPEND`)
`~dev-build/gtk-doc-am-1.34.0`, whose only common solution is `1.34.0` —
i.e. the *solvable* branch would produce portuale's wrong answer without
ever writing a mask. D0 decides between the three; do not start D2
before it has.

**Correction 2 — the real-side attribution is incomplete.** The backlog
says real's `_eliminate_rebuilds` / `_solve_non_slot_operator_slot_conflicts`
"treat the installed node as replaced by the in-slot merge". Real has
**three** gates before any of that matters, and naming them changes where
portuale's fix belongs:

1. `PackageTracker.conflicts()` iterates only `self._multi_pkgs` /
   `self._cp_pkg_map` — packages added by `add_pkg`, i.e. graph nodes
   (`package_tracker.py:260-288`). An installed package that is only in
   the vdb enters through `add_installed_pkg` into `_cp_vdb_pkg_map` and
   is recorded in `_replacing` / `_replaced_by` (`:107-147`, `:157-174`).
   It is **never** a conflict. That is the literal "replacement, not
   conflict" bookkeeping the backlog was reaching for.
2. Even when both *are* graph nodes, `_process_slot_conflict` only
   escalates when some package fails to match **all** parent atoms:
   it builds `slot_parent_atoms`, tests `atom.match(pkg…)` per parent,
   sets `all_match = False` on a miss, and only then appends to
   `conflict_pkgs` (`depgraph.py:2173-2185`); the backtracking call is
   `if conflict_pkgs and self._dynamic_config._allow_backtracking and not
   self._accept_blocker_conflicts()` (`:2188-2191`). A parent atom that
   matches both instances escalates nothing.
3. `_solve_non_slot_operator_slot_conflicts` then resolves what is left
   in favour of the merge: `is_arg_parent = inst_pkg is not None and not
   self._want_installed_pkg(inst_pkg)` (`:1888-1891`) and the match test
   `if atom.match(…) and not (is_arg_parent and pkg.installed)`
   (`:1913-1917`) drop the installed instance from `matched`, so the
   merge is forced and the installed node is removed with `_remove_pkg`
   (`:2059-2065`) — no mask, no restart. (`_want_installed_pkg` is
   `depgraph.py:7280-7302`.)

So the portuale-side question is not "how do I recognise a replacement
and exempt it from the mask" but **"why was this recorded as a conflict
at all"**. Portuale records per-atom during the walk, at two sites in
`resolve_pretend_graph`: the `resolved_slots` site (the current atom
rejects an already-resolved *merge* version) and the `installed_slots`
site (the current atom rejects an *installed* version, #57 direction 2,
`InstalledSide::Existing`) — both via `record_slot_conflict` /
`build_slot_conflict`. Real's per-atom collection is `conflict_atoms`;
real's *escalation* is a set-level test over all parents. Portuale has no
set-level gate; `collect_feedback` is where it would go, because that is
the first place that sees the whole `pass.slot_want` set for the cp.

This also gives the discriminator the backlog asked for and could not
name. #57's pinned shapes (`othermod`/`needer`: `>=paired-2.0` vs
`<paired-2.0`) have **no** version satisfying every want-atom, so real's
`all_match` genuinely fails on both sides and real reports the block. The
#79 shape has a want-atom set every candidate-relevant parent matches (or
whose only common solution real still rejects in favour of the merge via
gate 3). A gate built on real's own `all_match` / `is_arg_parent` rules
therefore leaves #57 and #68 D's cells untouched *by construction*, not
by tuning — which is what makes D2 safe to attempt at all.
