## 1. What real Portage does (the four-layer model)

Write this down once, in S0, and every later slice is mechanical.

**The layer stack.** `USE_ORDER` defaults to
`env:pkg:conf:defaults:pkginternal:features:repo:env.d`
(`config.py:1031-1035`). `lookuplist` is the **reversed** `configlist`,
so for a **scalar** the winner is, highest first:

```
env   (the calling process environment)      <- highest
pkg   (what _grab_pkg_env read from package.env)
conf  (make.conf)
defaults / pkginternal / features / repo / env.d
```

**So a `package.env` scalar LOSES to the calling environment.** This is
the single fact #101 exists to restore.

**Incrementals are folded, not overridden.** `regenerate()`
(`config.py:2735`, and `:2778-2825` for the `FEATURES` case) folds the
ordered list `[lower layers, pkg, backupenv]` — the calling environment
is folded **last**, so a `-tok` in the calling env prunes a token a
`package.env` file added. The result is `" ".join(sorted(myflags))`
after `-*` / `-tok` pruning.

**`FEATURES` is an incremental** and reaches `settings.features`, every
`feature_enabled`-style consumer, and the exported
`FEATURES`/`PORTAGE_FEATURES` (#98).

**`PORTAGE_TMPDIR` is accepted from an env file** — it is not in
`env_blacklist`, `environ_filter`, `global_only_vars` or the
profile-only set — and `doebuild_environment` reads the **resolved**
value for `PORTAGE_TMPDIR`, `BUILD_PREFIX` and `PORTAGE_BUILDDIR`
(`doebuild.py:435-458`, `:504-506`), failing with

```
The directory specified in your PORTAGE_TMPDIR variable, '...', does not exist.
```

when it is absent (#99).

**Standalone `ebuild <file> <phase>` exports the whole resolved config
env**, i.e. `config.environ()` — not a curated subset (#100).

## 2. Portuale today (the seam map)

| Seam | File / symbol | Role |
|---|---|---|
| run-wide phase env | `portage-profile` `phase_environ(config, None)` | step 1 config scalars, **step 2 calling environment on top**, then folded incrementals |
| acceptance gate | `portage-profile` `phase_environ::{ENVIRON_FILTER, ENV_BLACKLIST, PORTUALE_COMPUTED}` | `exportable()`; **`FEATURES` and `PORTAGE_TMPDIR` are both in `PORTUALE_COMPUTED`** — that is the drop |
| package.env match | `portuale` `ebuild_phases::match_package_env_vars` | reads the matching `/etc/portage/env/` files for a cpv |
| incremental fold | `portuale` `ebuild_phases::fold_package_env_incremental(base, overlay)` | applies the **overlay last** — the inverted order |
| merge path per-entry env | `portuale` `emerge_build::entry_build_env` | `options.build_env` (already carries the calling env), **then** `entry_package_env_vars` on top — inverted |
| standalone path base | `portuale` `ebuild_phases::phase_standalone_base_env` | builds from `pretend::build_config_env` = `BUILD_VARS` only — narrow |
| builddir computation | `portuale` `ebuild_phases::compute_environment` | computes `PORTAGE_BUILDDIR` from the CLI/process `PORTAGE_TMPDIR` **before** any package.env lookup |
| merge FEATURES consumers | `ebuild_merge::MergeOptions::features` + `ebuild_merge::feature_enabled` + `pretend::feature_enabled` | all read the **run-wide** string |

## 3. Slices

### 3.0 — Why S1 must precede S2

S1 (#101) makes a `package.env` scalar lose to the calling environment.
S2 (#100) replaces the standalone path's narrow base with
`phase_environ(config, None)` — whose **step 2 is the calling
environment**. Today the standalone path carries no calling env at all,
so the inversion is merge-path-only. Land S2 first and the standalone
path inherits the inversion S1 exists to remove: one bug becomes two,
in two places, and S1's blast radius doubles.

### S1 (#101) — a `package.env` scalar loses to the calling environment

**Moves output. Corpus bless allowed, in pmtest's commit, after review.**

1. **Merge path.** In `emerge_build::entry_build_env`, the
   `entry_package_env_vars` extension currently lands **after**
   `options.build_env`. Make a package.env **scalar** drop when the
   calling environment carries the same key. The calling environment is
   `portage_profile::config_env_all()` — the same source
   `phase_environ`'s step 2 uses; compare against *that*, not against
   `options.build_env` as a whole (which also contains config scalars
   that a package.env value legitimately outranks).
2. **Incrementals.** `fold_package_env_incremental(base, overlay)` must
   fold in real's order `[base-lower, pkg, calling-env]`, so a `-tok` in
   the calling env prunes a package.env token (S0 cell B). This is a
   three-argument fold now, not two — change the signature rather than
   pre-mixing the arguments at the call site.
3. **The pinned test that asserts the bug.**
   `test_emerge_atom_source_build_package_env_overrides_the_build_flags`
   in pmtest pins the inverted precedence (its docstring already admits
   it). Update the expectation **and** the docstring, citing S0 cell A.
   Add the negative twin: the same fixture with the process variable
   unset still sees the package.env value.

**Do not** touch the standalone path in this slice — it carries no
calling environment yet. That is S2's job.

**Tests.** The updated pin + its twin, plus a Rust unit test for the
three-argument fold (`-tok` in the calling-env layer prunes a pkg-layer
token; a pkg-layer `-tok` does **not** prune a calling-env token).

**Commit subject:** `#101: package.env loses to the calling environment, like real`.

### S3 (#99) — per-package `PORTAGE_TMPDIR` reaches the build directory

1. Remove the reason the key is dropped: `PORTAGE_TMPDIR` is in
   `PORTUALE_COMPUTED` because portuale computes `PORTAGE_BUILDDIR` from
   it. The fix is **not** to delete it from the list (that would let a
   stale value through as a plain pair) but to **recompute**: after the
   package.env match resolves for an entry, re-derive
   `Environment::portage_builddir` (and `PORTAGE_TMPDIR`,
   `BUILD_PREFIX`) from the *matched* value in
   `ebuild_phases::compute_environment`, then export both computed keys
   as today.
2. Both paths: the merge scheduler (via `entry_build_env`) and the
   standalone path. After S2 there is one base seam, so this should be
   one recompute site — if you find yourself writing it twice, stop and
   re-read S2.
3. **Precedence still applies** (S1): a process `PORTAGE_TMPDIR` beats
   the env file's.
4. **The missing-directory failure (S0 cell E) is part of this slice.**
   Real fails with an exact message; portuale must produce the same text
   and the same exit code. Pin it.

**Tests.** S0 cells D and E as pins, plus a Rust unit test that
`compute_environment` given a matched `PORTAGE_TMPDIR` yields a
`PORTAGE_BUILDDIR` under it.

**Trap:** the builddir is used to *create directories*. A test that
points it at a path the test process cannot write will fail for the
wrong reason. Use the pytest tmp path, and if you see cascading
`OSError`s across the suite, check `df -i /tmp` before assuming a
regression — `/tmp` inode exhaustion from old `pytest-of-vivo/` trees is
a known false alarm in this repo.

**Commit subject:** `#99: per-package PORTAGE_TMPDIR feeds the build directory`.

### S4 (#98) — per-package `FEATURES` reaches all three consumers

`FEATURES` is an **incremental**, so a flat `extra_env` pair would
*replace* the run-wide folded list (last-wins). It must fold.

1. Thread the per-entry folded `FEATURES` list (produced by S1's
   three-argument fold) through the `MergeOptions` construction, so
   `MergeOptions::features` carries the per-entry value for that entry.
   `MergeOptions` already has `set_resolved_features` — use it rather
   than adding a parallel field.
2. All **three** consumers must see it:
   `ebuild_merge::feature_enabled`, `pretend::feature_enabled`, and the
   exported `FEATURES`/`PORTAGE_FEATURES` in the phase env. Name each
   one in the commit body with what you changed.
3. The standalone `build_config_env` base (S2) gets the same treatment.

**Open owner decision O2 (see the index §2):** does this apply to
**binary** merges as well as source builds? Real folds in `regenerate()`
regardless of merge type, so the plan's answer is yes — but the first
*binary*-merge pin that moves is an owner call, not yours. Report it.

**Test.** S0 cells B and C as pins: a `FEATURES="splitdebug"` env file
produces a `.debug` tree for that package and not for its neighbour in
the same run — a per-package assertion, not a run-wide one. That
neighbour is the whole point: it proves the value is per-entry, not a
run-wide clobber.

**Commit subject:** `#98: per-package FEATURES folds into the merge and phase gates`.

## 4. What not to do

- Do not delete `FEATURES` or `PORTAGE_TMPDIR` from `PORTUALE_COMPUTED`
  as a shortcut. Both are computed for a reason; the fix is to recompute
  after the match, not to let a raw pair through.
- Do not "fix" the precedence by reordering `entry_build_env`'s two
  `extend` calls wholesale. `options.build_env` mixes config scalars
  (which package.env outranks) with the calling environment (which
  outranks package.env). Only the calling-environment keys win.
- Do not fold S3 and S4 into one slice because they touch neighbouring
  code. They have different oracles and different failure modes.
- Do not update a pinned expectation to whatever the new portuale prints.
  Every moved pin is re-derived from a real capture.
