## 1. The bug, already fully diagnosed — do not re-derive it

Reproduce first (one line, both revisions):

```sh
brush -c 'var=CC; prog=( gcc ); export ${var}="${prog[*]}"; echo "CC=[${CC}]"'
# brush:  CC=[]     (exit 0 -- a silent no-op)
# bash:   CC=[gcc]
```

Confirmed unfixed on the embedded pin `b9524ad5` **and** on upstream
`reubeno/brush` main `6bada559` (built and run 2026-09-20), and still
unfixed on the 2026-09-20 re-pin `4edb1f43`. No compat test covers it.

**Mechanism.** brush's parser only recognises an assignment word when
the name is a **literal** identifier (`brush-parser/src/word.rs`,
`assigned_scalar_name`), so `export ${var}=…` is a plain word. After
expansion the builtin receives `CommandArg::String("CC=gcc")`, and
`export.rs`'s `String` branch only marks an *existing* variable exported
— a silent no-op. `declare` / `local` are worse in a different way: they
print `not a valid variable name` (`declare.rs`).

bash performs the assignment **after** expansion for declaration
builtins (`export` / `declare` / `local` / `readonly` / `typeset`;
POSIX XCU 2.9.1).

**Why it matters to portuale.** `toolchain-funcs.eclass`'s `_tc-getPROG`
ends with `export ${var}="${prog[*]}"; echo "${!var}"`, reached whenever
`CC`/`BUILD_CC`/… is unset — the normal emerge environment. So
`tc-getCC` echoes **empty**, status 0. `_tc-has-openmp` then runs
` -fopenmp test.c -o test`, the empty expansion leaves `-fopenmp` as
argv[0], `command not found`, and `tc-check-openmp` `eerror`s and
`die`s. Live:

```
portuale emerge --shell brush media-gfx/gimp-3.2.6
 * Your current compiler does not support OpenMP!
error: command not found: -E        (x2, from tc-get-compiler-type)
die "Active compiler does not have required support for OpenMP"
```

The default `--shell bash` path is unaffected.

## 2. Slices

### S1 — the fix, on the fork

Work in `3rdparty/brush`, branch `fix/declaration-assignment-expansion`,
**one commit on current upstream `main`** (the house style for all five
existing fixes).

Two candidate implementations; pick one and say why in the commit body:

- **(i)** split `CommandArg::String` on the first `=` inside the
  declaration builtins (`export`, `declare`, `local`, `readonly`,
  `typeset`), treating the left side as the name; or
- **(ii)** defer assignment detection for declaration *commands* so the
  word is re-examined after expansion.

(ii) is closer to bash's actual model and closer to what upstream #1280
attempts; (i) is smaller and lands entirely inside the builtins. **Read
#1280 first** — if it is close to merging, align your shape with it so
the fork's commit rebases cleanly rather than conflicting.

**Correctness cases the implementation must get right**, all of which
belong in the compat test (S2): the name is only the part before the
**first** `=`; `export ${var}+=v` appends; `export "${var}=v"` (quoted)
behaves the same; `export ${var}` with no `=` still just marks exported;
a name that expands to something that is not a valid identifier must
produce bash's diagnostic, not a silent no-op; and `local`/`declare`
inside a function must scope like bash.

### S2 — the brush compat case

Add a `brush-shell/tests/cases/compat/builtins/` YAML case (follow
`dot.yaml`'s shape, as fix 04 did) covering the matrix:

```
forms:   literal | ${var} | "${var}" | append (+=) | no-value
builtins: export | declare | local | readonly
```

The compat harness diffs brush against real bash, so the expected output
is bash's — do not hand-write it.
