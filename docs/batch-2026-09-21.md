## 0. The agent runbook (follow literally, every slice)

1. **Read** this file §1/§3, then your cluster file's §0 and your slice.
2. **Branch** — `git checkout -b <branch>` in **both** repos
   (`portuale` here and `../pmtest`), same name, before touching
   anything. A branch that exists in only one repo is already drifted.
3. **Oracle before code.** Your slice names an oracle: real Portage
   source under `3rdparty/portage`, this host's real `/usr/bin/emerge`
   or `/usr/bin/ebuild`, or an upstream `ResolverPlayground` case. Run
   it and record the capture *before* writing product code. If the
   capture contradicts the slice's stated expectation, **STOP and
   report** — do not reinterpret the slice.
4. **Write the failing test first** (pmtest pin and/or Rust unit test),
   confirm it fails for the stated reason, then implement.
5. **Fixtures** go in `../pmtest/fixtures/` (the `fixtures/` symlink
   here points there). Every new ebuild needs a real-md5
   `metadata/md5-cache/` entry, a collision check against existing
   fixture names, and `git add` **before** any `git clean`.
6. **Verify** — from the workspace root here: `cargo fmt --check`,
   `cargo clippy --release --all-targets` (zero warnings),
   `cargo test --release`; then in `../pmtest`:
   `python3 -m pytest pytests-contract-suite -q`. Diff failures against
   a clean-`main` baseline **by test name, never by count** (the suite
   has a known order-dependent isolation bug worth ~22 scattered
   failures on a dirty tree; `git clean -fdq fixtures/` first).
   **And if your slice touches resolver code, or adds a line to a bed
   atomlist, re-run that bed before close-out and quote the numbers.**
   `differential-test-bed/atomlists/l0-fixture-oracle.txt` is the
   *default* list — a cell added there runs on every later bed run, so a
   cell whose portuale side is knowingly short does not stay your
   slice's business: it becomes an unexplained finding in everyone
   else's baseline. Phase 3b's S7 is the model (both beds, numbers in
   the finding). Phase 3c skipped it and cost the fixture-oracle bed a
   red cell that this review had to find — see #141 in §1.
7. **Corpus drift** is a STOP, not a bless, unless your slice's §
   explicitly says the slice moves output. When it does, review the
   drift line by line, then accept with `PORTUALE_CORPUS_BLESS=1` in
   **pmtest's** commit only.
8. **Merge-path safety gate** — if your slice's header says it applies,
   a successful test merge of `sys-libs/glibc` **and** `app-shells/bash`
   is mandatory before the slice is done (`agent-context.md`,
   "Merge-path safety gate"). No exceptions, no "it's only a read".
9. **Report, do not commit.** Commits and pushes are **never
   pre-authorised** by this plan. Finish the slice, run step 6, then
   report what changed and wait to be asked. When asked: one slice =
   one commit, pmtest first so this repo's message can quote its sha.

### Stop conditions (all slices)

Stop and report instead of improvising when any of these happens:

- the oracle capture disagrees with the slice text (step 3);
- a test outside your slice's named blast radius changes;
- you cannot reproduce the divergence the slice is built on;
- the fix you find is larger than the slice describes;
- you are about to edit the differential bed, `known-divergences*.yaml`
  or a pinned expectation **to make portuale pass**. A red is fixed in
  the product; an accepted divergence is an owner decision.

- **O3 (Phase 3b, #132) — now live, and the reason Phase 3b exists.**
  #111's S0 answered the "if": real's abort *is* correct and portuale
  *is* under-resolving. `enqueue_dependencies` never evaluates an
  installed parent's conditional use-deps, so every `[flag=]`/`[flag?]`
  dependency of every installed package is vacuously satisfied on every
  `--deep` run. Fixing it takes `emerge -puD --getbinpkg net-libs/rest`
  and `sys-devel/gcc` from rc 0 to rc 1 on the live tree, matching real.
  The ruling to make: **land it**, land it behind a default-off gate, or
  record the divergence and leave portuale under-resolving. The phase's
  S0–S3 exist to put that question in front of the owner with a measured
  moved-pin inventory attached; no product code is committed before it
  is answered. Detail and the exact wording:
  [`02.132-installed-parent-use-dep-conditionals.md`](02.132-installed-parent-use-dep-conditionals.md)
  §4 S3.
- **O4 (Phase 2b, #130) — what O1 deferred.** `PackageOptions` is built
  run-wide (`pretend::package_options_from_env`), so the binpkg-affecting
  `FEATURES` tokens — `binpkg-multi-instance`, `binpkg_compress`,
  `buildpkg-live`, signing — cannot take a per-entry value. Real's
  `EbuildBinpkg` uses the package's own settings, so per-entry is the
  faithful answer; but the first pin that moves a *binary artefact*
  shape (a `BUILD_ID` directory that appears for one package and not its
  neighbour, a package compressed differently from the rest of the run)
  is an owner call, exactly as O1 would have been.
- **O5 (Phase 6b, #126) — the `Option` semantics.** Routing
  `read_installed_slot` through `vdb_entry_slot` turns a missing `SLOT`
  from `None` into `Some("")`, because that is what real `_aux_get`
  returns. That is observable in `ebuild_unmerge`'s `others_in_slot`
  matching: today a `SLOT`-less vdb entry is skipped, after the change
  it matches other `SLOT`-less entries. Whether to take real's
  semantics, or keep the skip and normalise only the non-empty case, is
  a ruling — not a refactor an agent makes on the way past. Ask before
  S1, and re-run the merge-path gate whichever way it goes.
- **O6 (Phase 0b, #137) — what to do with a line that cannot be
  justified** (added 2026-09-22). Re-harvesting the corpus *is* editing
  a pinned expectation, which §0's stop conditions call an owner
  decision. The slice's own rule (§3b) is: every stale line is either
  grounded against real (a bed capture, an upstream case, real's
  source) and re-harvested, or deleted because nothing grounds it.
  A line that is neither — portuale's current output, plausible, but
  with no oracle anyone can produce — is the ruling: accept it as a
  pin, delete the case, or leave the harvest red and keep pinning with
  explicit tests. Do not guess; the whole point of the slice is that
  the next agent can trust what the corpus says.

### H3 — stop the `portage-fetch` stub-script flake (#128)

**Do this before H1/H2 and before every other phase.** `portage-fetch`'s
test helper (`rust/portage-fetch/src/lib.rs`, `mod tests`'s `tempdir()`)

`cargo test --release -p portage-fetch --lib`, and 2 of 3 whole-workspace

   --release -p portage-fetch --lib >/dev/null || echo "FAIL $i"; done`,
   and keep the capture. A flake you have not watched fail is a flake
   you cannot claim to have fixed. This is the slice's oracle: the
   failure itself, not real Portage.
2. **Make the name unique by construction** — a crate-level
   `AtomicUsize` the helper increments (or the test's own name passed
   in), so no two tests can collide whatever the clock resolution is.
   The timestamp may stay; it is the *only* discriminator today, which
   is the bug.

   whether an `ETXTBSY` can still happen inside a single test depends on

   corpus. If anything outside `rust/portage-fetch`'s test module needs
   to change, stop — that is a different finding.

**H3 execution correction (2026-09-21).** The capture found unique
paths in every failure, so the same-tick name collision was not the
mechanism: an `strace -f -tt` run shows a *sibling* test's `Command`
fork copying the still-open `O_WRONLY` fd into its pre-exec child
(`clone3(CLONE_VM|CLONE_VFORK)` landing inside the `fs::write` window),
which pins the inode's write count past the writer's own `close` until
that child execs — hence `ETXTBSY` on a path with no second opener. The
counter from step 2 alone did **not** clear the 30-run loop (5/30
failures); the `SPAWN_SERIAL` mutex held across script writes and
serialized spawns did. Both landed; #128's entry carries the trace and
the verification numbers.
