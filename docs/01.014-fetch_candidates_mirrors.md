## 1. Problem and evidence

The `portage-fetch` module doc used to claim the `layout.conf`
negotiation could be skipped because flat layout is "what the real,
well-known `GENTOO_MIRRORS` entries actually use". That was false for the
stock mirrors:

```
$ curl -s http://distfiles.gentoo.org/distfiles/layout.conf
[structure]
0=filename-hash BLAKE2B 8

$ curl -sI .../distfiles/which-2.23.tar.gz      -> 404   (portuale's flat URL)
$ curl -sI .../distfiles/80/which-2.23.tar.gz   -> 200   (real's filename-hash URL)
```

So every `mirror://gentoo/…` and every dead-upstream download failed
against a stock `GENTOO_MIRRORS`. Two smaller defects sat next to it: a
`mirror://` URI's third-party expansions were attempted twice (real
skips repeats with `tried_locations`), and `/`-rooted `GENTOO_MIRRORS`
entries were handed to `wget` as URLs instead of being treated as local
mirrors (`fsmirrors`).

## 2. What real does (the shipped ground truth)

All citations are real Portage 3.0.82.2 `lib/portage/package/ebuild/fetch.py`:

- `async_mirror_url` resolves a mirror root through that mirror's own
  `distfiles/layout.conf`, cached in `${DISTDIR}/.mirror-cache.json` as
  `{url: [ts, [layout-args…]]}` with a 86400 s TTL; a `/`-rooted root
  reads `<dir>/layout.conf` directly. On any failure it falls back to
  flat and writes nothing. Resolution is lazy (only when a candidate is
  reached) and `ftp`/`http`/`https` paths are `urlquote`d.
- `assemble_candidates` order: local mirrors (incl. `custommirrors`
  local `/` dirs) → public `GENTOO_MIRRORS` → the file's `mirror://`
  expansions in `thirdpartymirrors` order → the literal URIs, appended
  (or prepended as a group under `RESTRICT=primaryuri`), with literals
  reversed first and `A`/`AA` deduplicated.
- `tried_locations` de-duplicates **attempts**, not the candidate list.
- Checksum failure: `checksum_failure_count`; the second failure appends
  the reversed primary URIs ("switch to primaryuri mode"); the search
  stops after `PORTAGE_FETCH_CHECKSUM_TRY_MIRRORS` (default 5; bad
  values warned and replaced); the bad file is renamed
  `<file>._checksum_failure_.<random>` and real prints `Refetching...
  File renamed to '…'`.
- `fsmirrors` are copied with a plain file copy before any remote
  candidate; `Local mirror has file: <f>`; digest verification still
  applies.
- `PORTAGE_FETCH_RESUME_MIN_SIZE` gates resume; `RESUMECOMMAND` is the
  default `FETCHCOMMAND` plus `-c`.

## 5. Transport residue (candidate slices; not part of the original F1–F6)

Found while consolidating this plan; **filed as backlog #70** because
they are genuine real behaviours portuale does not model:

1. **`FETCHCOMMAND` / `RESUMECOMMAND` overrides are ignored.**
   `portage_fetch::download_via_wget` hardcodes the `make.globals`
   default wget template; real spawns `mysettings["FETCHCOMMAND"]` and
   consults the protocol-specific `FETCHCOMMAND_HTTP`/`_HTTPS`/`_FTP`/
   `_RSYNC`/`_SFTP`/`_SSH` variants (and the matching `RESUMECOMMAND*`)
   via its own fetch-command selection, with `${DISTDIR}`/`${URI}`
   template substitution. Portuale only lists those names in
   `phase_environ` (so they reach build phases) but never uses them for
   its own downloads.
2. **`PORTAGE_RO_DISTDIRS` is ignored.** Real reads each entry as an
   additional read-only distdir source
   (`fetch.py:1057`, `shlex.split`), useful for shared/NFS distdirs;
   portuale only lists the name in `phase_environ`.
3. **`FEATURES=distlocks` stays a documented cut** — portuale's
   single-invocation-at-a-time CLI assumption, already recorded in
   `what-this-proves.md`; not a slice here.
