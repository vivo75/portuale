## 2. Defects (fix these in the plan before S2)

### D1 — S2 makes `native` the default with a dispatcher that knows only S2's helpers: every build and every binary merge breaks until S6
**Severity: high · Proven (source read)**

S2.3 points `PORTAGE_PYTHON` at the shim, with "Unset or `native` is the
default" (D2). S2.1 implements only `chmod-lite`, `ebuild-ipc`, `ping` and
the locale answer. D1 lists `filter-bash-environment.py`, `gpkg-helper.py`,
`xpak-helper.py`, `doins.py` and `install.py` as dispatcher names, but those
helpers land in S3 to S7. The plan says nothing about what those names do
in between.

What happens from S2 until the helper's own step lands:

- `filter-bash-environment.py` runs at the end of **every** phase
  (`phase-functions.sh:1261`) and in every binary merge's preprocess
  (`:274`). It would fail with `|| die "filter-bash-environment.py failed"`
  (`:206-207`). Every source build and every binpkg merge on the dev host
  dies, including the ones that have Python and the checkout.
- `gpkg-helper.py` and `xpak-helper.py` (`misc-functions.sh:601,622`) and
  `doins.py` (`doins:104-106`) fail the same way.
- So S2's "Done when: V-std green" cannot hold. The e2e tests
  `real_package_*` and the merge tests run real phases.
- **Remote, too.** S2.3 also switches the remote headers (`remote.rs:2520`,
  `:2941`) to `$UNITBIN/portuale-python`. The shim requires
  `${PORTUALE_BIN:?}` (S2.2). Over ssh, `PORTUALE_BIN` is not exported until
  S8.3 (today only `local_client_bash` sets it, `remote.rs:480`). Every
  client hook phase would die from S2 until S8. Remote clients run the
  filter on every hook phase: `remote.rs:2583`, `:2828` and `:2924` write
  `environment.raw`, and `:1261` runs after every phase.

S2 also changes the merge path: binary merges run the filter through the
new `PORTAGE_PYTHON`. It is not marked [gate].

Fix direction:

- In the dispatcher, keep an explicit per-name fallback table: "not ported
  yet → exec the real interpreter with the original argv". Each of S3 to S7
  removes its row. S9 (or Z) asserts the table is empty and that anything
  else is 127.
- Alternatively, keep D2's default at `real` until S6 and flip it in its own
  step.
- Leave the remote headers on `/usr/bin/python` until S8 (move S2.3's
  remote half into S8.3).
- Mark S2 [gate].

### D3 — S8's bed acceptance does not fit the l31 topology
**Severity: high · Proven (bed source read)**

S8: "Bed: `l31-remote-merge.sh` with the client image built like [nopy] and
without portuale … a re-run shows no install." In l31 the client **is the
server's own container**. `layers/l31/consume-remote.sh:1-14`: "a

is the container ROOT (`/`)". The same container mounts the PM bin dir
read-only at `/usr/local/bin` (`run/lib.sh:65`
`PM_MOUNTS=(-v "$PM_BIN_DIR:/usr/local/bin:ro")`). Consequences:

- A "client without portuale" is impossible, because the server binary runs there.
- D5's search would find `/usr/local/bin/portuale`. If that file is the
  server's own binary its SHA matches and nothing is installed, so "first

  read-only mount.
- `/usr/local/bin` is pruned from snapshots (`compare/snapshot.sh:77-83`).
  `/opt/bin` is not, so any install there shows up as an unexplained l31
  diff.

`run/lib.sh:46` defines `MRG_CLIENT_IMAGE=localhost/test-mrg-client:latest`,
but nothing uses it.

Fix direction: add a real two-container cell. The server container
(portuale, repo) reaches a separate client container (bash, coreutils,
sshd, no portuale, no Python, no repo mount) over a podman network.
Snapshot the client and compare against real Portage's consume. Keep the
local-transport e2e for install/reuse/corrupt-copy. File the new cell's
bed work inside S8, or as its own pmtest step before S8.

### D4 — In-process cargo tests would export the libtest harness as `PORTUALE_BIN`
**Severity: high · Likely (source read; not run)**

`phase_env_vars` exports `PORTUALE_BIN=portuale_bin_value()`, which is
`std::env::current_exe()` (`ebuild_phases.rs:3115-3119`, `:3197`). The
in-process unit tests call the phase runner directly, for example
`real_package_with_gpkg_format_…` (`ebuild_package.rs:2732`) calls
`run_package(...)`. There `current_exe()` is
`target/release/deps/portuale-<hash>`, the libtest harness. After S2 the
shims run `"$PORTUALE_BIN" __helper python …/filter-bash-environment.py
"<pattern>"`. libtest reads those positional arguments as test-name
filters, prints `running 0 tests … ok` on stdout and exits 0. That banner
becomes the filtered environment. The failure is silent: tests can pass
while the saved env is garbage. (The existing `portageq-wrapper` already
has this latent problem for any in-process test ebuild that calls
`has_version`.)

Fix direction: S2 must make `portuale_bin_value()` resolve to the real
`portuale` executable under `cfg(test)`, the sibling-of-`deps/` pattern
that `ebuild_phases.rs:5575-5580` already uses. It must also make sure that
binary is built before the tests run. Add a test that fails if
`PORTUALE_BIN` names a libtest binary (for example, run
`$PORTUALE_BIN __helper ping` and expect a fixed token).

### D5 — S2.4's `has_utf8_ctype` method (normalise `LC_ALL`/`LC_CTYPE`/`LANG`) does not reproduce real's answer
**Severity: medium-high · Proven (live probe, Python 3.14.8 on this host)**

Real's answer comes from the interpreter's effective C-library locale,
after PEP 538 C-locale coercion and PEP 540 UTF-8 mode. It also depends on
which locales are **installed**. Probed with
`env -i LANG=<v> /usr/bin/python -c 'import locale; print(locale.getlocale()[1])'`:

| `LANG` | real | `locale.normalize` alone |
|---|---|---|
| unset, `C`, `POSIX` | `UTF-8` | none / `ANSI_X3.4-1968` |
| `en_US` (installed iso88591) | `ISO8859-1` | `ISO8859-1` |
| `en_US.ISO-8859-1` (installed) | `ISO8859-1` | `ISO8859-1` |
| `xx_YY.ISO-8859-1` (**not installed**) | `UTF-8` | `ISO8859-1` |

A normalisation-only port gets three of these rows wrong. Static musl
cannot know what glibc has installed, and musl's `setlocale` accepts any
name. So "byte-identical" (D3) is not a property of the environment
strings alone.

Fix direction: answer from the locale the phase's **bash** actually uses,
which is what `config_impl_decl_check` needs for its `‘` regex. For
example the native helper runs
`bash -c 'printf %s "$(locale charmap 2>/dev/null)"'`, or `setlocale(LC_CTYPE, "")` +
`nl_langinfo(CODESET)` in a dynamically linked build. Then decide and
document the C/POSIX case explicitly (real says UTF-8). The D4 oracle table
must record the host's `locale -a` and Python version, and should include
an uninstalled-locale row.

### D6 — S3 says "the same regexes compiled once". Python bytes-regex semantics differ from Rust `regex`
**Severity: medium · Likely (semantics from source; no differential run)**

`filter-bash-environment.py` iterates `sys.stdin.buffer` lines **with** the
trailing `\n` and uses `bytes` patterns. Two semantic differences matter:

- (a) Python `$` matches before a final newline. `func_end_re = ^\}$`,
  `here_doc_re = .*\s<<[-]?(\w+)$` and the dynamic `b"^" + delim + b"$"`
  (`bin/filter-bash-environment.py:19-21,107`) all rely on that. Rust
  `regex` `$` (no `m` flag) matches only at the haystack end.
- (b) `\w`, `\s`, `\d` and `\W` are ASCII-only for bytes patterns.
  `regex::bytes` is Unicode-aware by default. That changes
  `var_pattern.append(rb".*\W.*")` (`:158`), which filters invalid names,
  for any non-ASCII byte that forms valid UTF-8.

Also: Python `.match` is start-anchored, while Rust `is_match` is
unanchored, and `close_quote_re.search` is unanchored. The user pattern
(argv) is Python regex syntax, so the port must state the subset it
accepts.

Fix direction: S3 prescribes `(?-u)` byte regexes. Either strip a single
trailing `\n` before matching and re-append it on output, or use `\n?\z`
in place of `$`. Anchor explicitly. Add fixture cases with non-ASCII
variable names and a last line without a newline.

### D8 — The S4 / D3 gpkg pointers name the wrong Portage functions and miss writer traits that D3's equality depends on
**Severity: medium · Proven (source read)**

- **Format selection.** D3 and S4 cite "`_get_tar_format` (`gpkg.py:1939`)".
  `_get_tar_format` is at `:1927` and **reads** an existing container.
  `compress` picks formats with `_get_tar_format_from_stats` (`:1948-1986`)
  over `_check_pre_image_files` (`:1988-`), and forces GNU for the container
  when `len(basename) >= 154` (`:1007-1008`). The image tar is USTAR or GNU,
  never PAX. The metadata tar is always USTAR (`:1311,1316`).
- **Tarinfo construction.** "the tarinfo construction at `:1440-1500`
  (uid/gid/uname/gname, numeric owner rules)" is inside `_quickpkg`
  (`:1340-1520`). `compress` does not call it. `compress` uses
  `image_tar.add(root_dir, "image", recursive=True)` (`:1052`), which is
  Python `TarFile.gettarinfo`: `uname`/`gname` from `pwd`/`grp` (empty on
  lookup failure), hardlinks by an inode table, children in **sorted**
  `os.listdir` order, and directory names with a trailing `/`.
- **Metadata member order.** It is `os.walk` (unsorted `scandir`, so
  filesystem-dependent) order, and recursive by basename
  (`_generate_metadata_from_dir`, `:1844-1862`). The port must use raw
  `read_dir` order, not portuale's sorting helpers, or D3's "identical
  member order" fails.
- **Record padding.** Python's `TarFile.close()` pads every archive
  (container, image, metadata) to a 10240-byte record. `tar::Builder::finish`
  writes only two zero blocks, so "identical decompressed payloads" needs
  explicit padding.
- **Header details.** Python writes empty device fields for non-device
  members, `%06o\0 ` checksums, and rounded integer mtimes. These matter
  if "headers" in D3 means bytes. If it means fields, say so.
- **Settings.** Real reads `MAKEOPTS` for `{JOBS}` in the `xz`/`zstd`
  command (`_get_binary_cmd`, `:1883-1885`; `compression_probe.py:38,43`).
  `MAKEOPTS` is missing from S4's list of settings. The compressed bytes,
  and so the image `DATA` Manifest line, depend on it and on the
  compressor version.

Fix direction: rewrite S4's "Read first" with the functions above, and
write the traits into D3 as an explicit checklist. D3 then needs no
reinterpretation.

### D9 — D6's `ebuild-ipc` shim exits 1, which `has_version` reads as "not installed"; and removing the variable in `phase_env_vars` does not stop it leaking
**Severity: medium · Proven (source read)**

- **The exit code.** `phase-helpers.sh:916-922`: `0|1) return ${retval}`.
  Only 2 and others die. A leaked `PORTAGE_IPC_DAEMON` plus a shim exiting 1
  makes `has_version` silently false and `best_version` silently empty.
  That is the opposite of D6's "fails visibly". The die path
  (`isolated-functions.sh:200`) ignores the code anyway.
- **The leak.** `PORTAGE_IPC_DAEMON` is in `ENVIRON_WHITELIST`
  (`ebuild_phases.rs:2599`). The spawns copy whitelisted calling-env vars
  **before** applying `vars` (`ebuild_phases.rs:3808-3813` and
  `:4415-4417`). `phase_env_vars` does not set the variable, so S2.3's
  "`PORTAGE_IPC_DAEMON` removed" in `phase_env_vars` changes nothing.

Fix direction: make the shim exit with a code ≥ 3 (for example 127), so
`has_version` dies with `unexpected ebuild-ipc exit code`. Drop
`PORTAGE_IPC_DAEMON` explicitly at both spawn sites, the same way `LC_ALL`
is dropped there. Add a test with `PORTAGE_IPC_DAEMON=1` in the calling
environment.

### D10 — Remote bundles ship the overlay's absolute symlinks; native mode keeps building the overlay
**Severity: medium · Likely (source read; l31 masks it)**

When a checkout exists, `bin_dir()` returns the overlay
(`ebuild_phases.rs:742-752`). The overlay consists of **absolute symlinks**
into the server's checkout and vendored `bin/` (`build_bin_overlay`,
`:932-945`). `remote_bundle.rs:437-446` copies it with `cp -a`, which does
not dereference, and `tar -cf` (`:474-479`) keeps the links. A client on
another host receives dangling `bin/ebuild.sh` and helpers. l31 cannot see
this because its client is the same container, with the repo mounted at
the same path (`run/lib.sh:70`, `PM_MOUNTS+=(-v "$PM_REPO:$PM_REPO:ro")`).
S2.5 only rewrites `bin_dir()`'s doc comment, so in `native` mode the
overlay is still built and still shipped.

Fix direction: in `native` mode, `bin_dir()` should skip the overlay
entirely, since only `real` needs it. Independently, the bundle should copy
with `cp -aL`, or ship the embedded runtime. The D3 two-container cell
then guards this.

### G2 — S8 misses failure modes and two required doc sections
- **§5.5 ordering.** "nothing on the client changes before stage 4"
  (`remote-merge.md` §5.5). The binary install is a client mutation. It
  must run after stage 3 (resolve and verify) and only when at least one
  unit will ship. `--pretend` and empty plans must never install. S8.4
  must update §5.5, and §9, whose current text says "only the target ROOT
  is writable and only unit files are written". Today S8.4 lists only
  §1/§2/§6.
- **Tool floor.** D5 uses `mv`, `uname` and `sha256sum`. The preflight
  tool list (`remote.rs:1020`, `:1075-1077`) has none of them. S8.4 names
  only `sha256sum`. The §6 doc list (6 tools) is already stale against the
  code (14 tools); reconcile both.
- **Overwrite and ownership.** D5 replaces any `/opt/bin/portuale` or
  `/usr/local/bin/portuale` whose digest differs. That clobbers an
  operator's own install, and two servers with different builds will
  ping-pong the file. Consider a content-addressed name
  (`<dir>/portuale-<sha256[:16]>`). It removes the overwrite, the
  concurrency race and the "re-run reuses" ambiguity in one change.
- **Temp file safety.** `.portuale.tmp.$$` is predictable. With Q1's
  override pointing into a world-writable directory, it is a symlink race
  run as root. Use `mktemp` in the target directory, and refuse
  world-writable non-sticky directories.
- **What to ship.** Q3 checks `uname -m` on both sides. The server binary's
  arch is its ELF `e_machine`, not the server kernel's `uname -m`. A dev
  build is typically dynamically linked against the server's glibc. Q1's
  `--remote-portuale-path` overrides the **client** path, but nothing lets
  the operator pick **which server binary** to ship, for example the static
  musl build. Add a server-side option, or state that the server must run
  a static build.
- **Local transport.** For `--remote-transport=local`, should D5 install
  into the host's own `/opt/bin`, or keep `local_client_bash`'s
  `PORTUALE_BIN=current_exe` (`remote.rs:478-481`)? S8.3 says both. Pick
  one.
- **Every generated script.** All generated scripts need
  `PORTUALE_BIN=<abs>`, not only the merge and old-hook headers:
  `phase_script` (`remote.rs:2567-`), `postinst_regen_script`
  (`:2775-`) and the old-hook driver (`:2900-2950`). Also export
  `PORTAGE_PYM_PATH=/` there: today `phase-functions.sh:1145,1260` run
  `cd ""` on the client and print `cd: null directory`.
- **Install placement vs ROOT.** For a client with `ROOT=/` the installed
  binary lands inside the managed system, and no vdb entry owns it.
  Document it.

### G7 — S6 (`doins`) leaves out parts of the argv contract that the beds exercise
The real option names are `--recursive`, `--preserve_symlinks`,
`--helpers_can_die`, `--strict_option`, `--enable_copy_xattr`,
`--xattr_exclude`, `--distdir`, `--helper`, `--dest`
(`doins.py:457-507`, built by `ebuild-helpers/doins:35-97`). S6 spells

- **Install options.** `-p` (`--preserve-timestamps`) makes mtimes part of

  set (`doins.py:100-133`).
- **Owner names.** `_parse_user`/`_parse_group` use NSS. A static musl

### G8 — S5 (xpak) leaves out real's edge behaviour

`recompose_mem` truncates an existing XPAK segment (`scan()` +
`seek(-xpaksize)`), and when `st_nlink > 1` it breaks hardlinks by copying
and renaming (`xpak.py:342-380`). The fixtures need a re-recompose case
and a hardlinked tbz2 case.

### G9 — The `__helper` entry path must have no side effects; sandbox behaviour changes

`$TMPDIR`, the atexit cleanup registration), load config, or write
anywhere but its outputs. Under `FEATURES=sandbox` those writes can be
denied.

Separately, a static binary is not intercepted by libsandbox's
`LD_PRELOAD`, while the Python helpers were. Native `doins` writing
outside `${D}` would no longer be reported. State this as a known
difference, or add a native write-path assertion.

(`embedded_runtime.rs:207-227`, `ebuild_phases.rs:5506`). An in-process
override races (D16), and `bin_dir()` is cached.

### G11 — The [nopy] sanity check misses versioned interpreters
`! command -v python python3` misses `python3.13` and `python3.14`, which
Gentoo installs as real binaries. Use `compgen -c python` (empty) or a
glob over `/usr/bin/python*`.
