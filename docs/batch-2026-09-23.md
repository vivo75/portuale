The owner's criteria, in priority order: **(1) interdependency of the
fixes, (2) severity of the problem, (3) simplicity of implementation.**

```

Phase 9   blocker fidelity          #143 -> #142                                   06.142-143
Phase 10  slot-conflict merge list  #148                                           02.148
Phase 11  per-entry binpkg artefact #147 (+ its two secondary questions)          01.147
Phase 12  vdb aux_get translations  #115 (probe first, then decide)                02.115
Phase 13  --tree walk sequence      #131                                           02.131
Phase 7b  owner campaign            #52 lib.rs mutation run                        03.30 §B   last, on a clean tree — **moved to [`batch-2026-09-24.md`](batch-2026-09-24.md) P7b**
```

**Hard dependency edges:**

- **Phase 8 → Phase 9, Phase 8 → Phase 13.** #142's second facet is row
  *placement* (real interleaves `[uninstall]`/`[blocks b]` right after
  the blocker owner; portuale defers them past every `[ebuild N]` row),
  and #131 is display-walk sequencing surgery inside the `--tree`
  simulation arms. Both edit `rust/portage-repo/src/merge_order.rs`,
  and today the mutation run (#52, Phase 4 S3) says 233 of that file's
  mutants survive — including `tree_schedule_stuck`,
  `tree_note_selection`, `tree_solved_replacements` (#144) and
  `edge_satisfied_with` / `dep_edge_satisfied_by_installed` (#145). A
  behaviour change landed into a file whose unit coverage cannot see
  whole-body no-ops is reviewed only by the contract suite and the bed.
  Tests first: when #142 or #131 then moves a Phase-8 unit test, that
  move is a visible, intended diff instead of a silent one.
- **#146 → #145 → #144** (soft, inside Phase 8). By size and by
  scaffolding: #146 is predicate-level (synthetic `DepPriority` values,
  no graph); #145 needs a fixture vdb or a `read_vdb_slot`-style seam
  for the installed half; #144 is the largest and carries the timeouts
  (mutants that hang the suite — likely scheduler loops that stop
  terminating). Each builds the helpers the next one reuses.
- **#143 → #142** (soft, inside Phase 9). Both are upstream
  `test_blocker` shapes from the same bulk translation, sharing the
  fixture namespace `dev-libs/blk*` and the same allowlist block. #143
  is a gate (`--buildpkgonly` evaluates only DEPEND/BDEPEND blockers, a
  hard `!!` there aborts, RDEPEND/PDEPEND blockers are not evaluated),
  with a real-source answer and six deterministic cells; #142 depends on
  walk order (the uninstall target varies with argv order) and is the
  harder design. Land the one that settles the blocker-evaluation seam,
  then the one that reorders around it.
- **Phase 7b → the end.** `cargo mutants --in-place` rewrites
  `portage-repo/src/lib.rs` under the working tree for ~3 h. Nothing
  else can run on this checkout while it does, and a run started on a
  dirty tree measures somebody's uncommitted change. Every other phase
  also edits `lib.rs` or its tests, so the measurement is only
  meaningful after them.
- **Phase 7a → nothing, and nothing → Phase 7a.** The `l3-core` run is
  container-side, writes only under `../pmtest/differential-test-bed/logs/`,
  and tests the merge/build pipeline none of Phases 8–13 touch except
  #147 (binpkg artefacts) — see the stop rule in §4 Phase 11. Launch it
  at the start so its multi-hour wall clock overlaps the rest.

**Severity ranking used inside the phases** (highest first):
#143 (portuale resolves rc 0 where real aborts, and schedules uninstalls
real never would, under `--buildpkgonly`) > #142 (the uninstall target
depends on argument order; one order merges a version that violates a
bound) > #148 (a slot-conflict plan one instance short) > #147 (a
per-package setting that may or may not reach the binary artefact —
Rust-tested, never pinned) > #131 (`--tree` display order) > #115
(an unanswered parity question, no captured divergence) >
#144/#145/#146 (test coverage) > #30/#52 (measurement campaigns).

**Deliberate deviation from the criteria: Phase 8 runs before the
higher-severity Phase 9.** That is criterion (1) outranking (2), stated
above, not a preference: the test phase is the dependency. If the owner
wants #143 first anyway it is safe on its own — #143's fix site is the
blocker-evaluation gate under `--buildpkgonly`, not the scheduler — and
#142 alone waits.

**Can run in parallel:** Phase 7a (container only) with anything; Phase
11 and Phase 12 with each other and with Phase 8 (`ebuild_package.rs` /
`emerge_build.rs` and the vdb reader, not `merge_order.rs`). Phases 8, 9,
10 and 13 all touch the resolver or the scheduler and run in sequence.
