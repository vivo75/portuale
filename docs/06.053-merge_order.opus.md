## 1. What was known, and what planning found

The L0 run `TEST/logs/l0-20260915T092215Z` (not present locally; the
same row reproduces in the local `TEST/logs/l0-20260915T073208Z/
invariants.txt`) reports:

    portuale app-containers_podman: merge order: dev-lang/go (#100)
      merges after its owner dev-go/go-md2man (#94)

The backlog attributed it to the `:=` slot-operator bind/rebuild path
(F-A1 family). **Planning disproved that and built an 8-package repro.**

Gentoo metadata of the chain (host tree, same versions as the probe):

| package | relevant deps |
|---|---|
| `dev-lang/go-1.26.4` | `BDEPEND=\|\| ( >=dev-lang/go-1.24.6 >=dev-lang/go-bootstrap-1.24.6 )` |
| `dev-go/go-md2man-2.0.7` | `BDEPEND=>=dev-lang/go-1.24.11:= app-arch/unzip` |
| `app-containers/conmon-2.1.13` | `BDEPEND=dev-go/go-md2man` |
| `app-containers/containers-common-0.64.2` | `BDEPEND=>=dev-go/go-md2man-2.0.3`, `RDEPEND=... containers-storage ...` |
| `app-containers/containers-storage-1.59.1` | `BDEPEND=>=dev-go/go-md2man-2.0.2` |
| `app-containers/podman-5.8.2` | `BDEPEND=... dev-go/go-md2man >=dev-lang/go-1.24.11:= app-arch/unzip`, `DEPEND`/`RDEPEND` `conmon containers-common ...` |

Real's own output on the probe is **not a merge list**: it is the
`--tree` display followed by

    * Error: circular dependencies:
    (dev-lang/go-1.26.4:0/1.26.4::gentoo, ebuild scheduled for merge) depends on
     (dev-lang/go-1.26.4:0/1.26.4::gentoo, ebuild scheduled for merge) (buildtime)

i.e. real resolved go's own `||` to **go itself** (the first branch; go
is already in the graph when its BDEPEND is evaluated — the `dep_zapdeps`
`all_in_graph` bin), and aborts on the self-cycle. Portuale resolves the
same `||` to `go-bootstrap` (L0 finding D, `b5b256f`, "fresh resolve must
pick bootstrap") and prints a merge list. So the resolutions already
differ; the order bug is inside portuale's own list.

Bisection (one change at a time from that baseline; position of md2man
vs go):

| change | md2man | go | bug? |
|---|---|---|---|
| baseline | 3 | 7 | **yes** |
| drop `:=` from md2man's go atom | 3 | 7 | yes — **`:=` is irrelevant** |
| drop `:=` from podman's go atom | 3 | 7 | yes |
| drop podman's go BDEPEND entirely | 3 | 8 | yes |
| drop md2man's unzip BDEPEND | 3 | 7 | yes |
| **go's BDEPEND without the self-branch** (`>=r53goboot-1.24` only) | 4 | 3 | **no** |

A simpler first attempt (podman with only `BDEPEND=go`, `RDEPEND=conmon`)
ordered correctly, so the self-branch alone is not sufficient: a second
consumer chain through md2man is also needed. S0 minimises this further.

**Working hypothesis (H1):** in `merge_order`'s digraph, go's own
deferred `||` group (`split_disjunctive` -> `alt`) is re-resolved against
the graph, where go is merge-bound, so the self-branch wins
(`atoms_all_in_graph`) and adds a **go -> go buildtime self-edge**. go can
then never become a leaf, the serializer's cycle/ladder fallback
(`find_smallest_cycle`, `ignore_priority`) eventually releases it, and
md2man's hard `buildtime_slot_op` edge to go is not respected on the
way. **H2:** the self-branch is correctly skipped, but go's edge to
`goboot` lands in a `_dep_disjunctive_stack`-deferred batch that is
processed after md2man is already selected. S1 decides between them
with a trace. Anchors: `rust/portage-repo/src/merge_order.rs`
`dep_edges_from_metadata` (~250), `split_disjunctive`, the selection loop
(`select_nodes`, the `PORTUALE_MO_SEL` harness), `find_smallest_cycle`;
`rust/portage-repo/src/lib.rs` `atoms_all_in_graph` /
`disjunction_preference`.
