## 1. Portuale today (the seam map, extending Phase 2 §2)

| Seam | File / symbol | Role |
|---|---|---|
| merge scheduler per-entry env | `emerge_build::entry_build_env` | matches package.env via `entry_package_env_vars`, folds `FEATURES` via `entry_resolved_features` — **already wired (#98/#99/#100/#101)** |
| standalone `ebuild <file>` per-entry env | `ebuild_phases::phase_standalone_base_env` | matches package.env via the standalone md5-cache identity — **already wired** |
| **`--buildpkgonly` per-entry env** | `emerge_build::run_buildpkgonly` | built `run_wide_phase_env(config) + entry_phase_env_tail(...)` only — **no package.env match, no FEATURES fold, no PORTAGE_TMPDIR recompute (#129, the gap)** |
| **binpkg-affecting `PackageOptions` fields** | `pretend::package_options_from_env`, `ebuild.rs`'s standalone construction | built once, run-wide, from the calling process's raw `FEATURES` — **no per-entry resolution at either `package_after_install` call site, nor in standalone `ebuild <file> merge`'s gates (#130, the gap)** |
| `package_after_install` call sites | `emerge_build.rs:1286` (source-build path, `buildpkg: Option<&PackageOptions>`), `ebuild_merge.rs:3080` (binary-merge path) | both currently receive the single run-wide `&PackageOptions` |
| standalone merge `FEATURES` | `ebuild.rs`'s `merge_options = MergeOptions::from_env(...)` | never calls `set_resolved_features`; reads the raw process `$FEATURES` only |

**Why #129 needs no `MergeOptions`.** `run_buildpkgonly`'s signature
already carries `config: &portage_profile::Config`, and `Config` itself
carries `package_env_vars` (`Config::package_env_vars`, populated at
config-resolve time — see `portage-profile/src/lib.rs:3360`). The merge
scheduler threads the same table through `MergeOptions::package_env_vars`
only because it doesn't otherwise carry a `Config` reference past
resolution; `run_buildpkgonly` never lost that reference, so it reads
`config.package_env_vars` directly.

## 2. Slices

### S1 (#129) — `--buildpkgonly` matches `package.env`, folds `FEATURES`, recomputes `PORTAGE_TMPDIR`

**No corpus drift.** `--buildpkgonly` is not part of the pinned-output
contract suite (`test_emerge_pretend_contract.py` pins `-p`/`--pretend`
text, not a real-execution build) — its own tests are Rust-only,
fixture-driven end-to-end (`AGENTS.md` §0 step 6, "Real-execution
features get Rust fixture-driven end-to-end tests instead").

1. **Extract the shared halves.** `entry_package_env_vars` and
   `entry_resolved_features` (both `emerge_build.rs`, both tied to
   `&ebuild_merge::MergeOptions`) split into a thin `&MergeOptions`
   wrapper plus a raw-pieces function
   (`matched_package_env_vars`/`resolved_features_for`) that takes
   `package_env_vars`, the `cpv_slot`, and the run-wide base directly —
   the "extract the shared half" fix direction the backlog entry names.
   Both the merge scheduler and `run_buildpkgonly` now call the same raw
   functions; the wrapper functions are behaviour-identical for their
   existing callers (verified: no pinned test in this repo or
   `2pmtest`'s contract suite moved).
2. **Wire `run_buildpkgonly`.** Per entry: build `cpv_slot`
   (`entry_cpv_slot`, already shared with the merge path), match
   `config.package_env_vars` into `build_env` via
   `matched_package_env_vars` (layered after `run_wide`, before
   `entry_phase_env_tail`, mirroring `entry_build_env`'s order), fold a
   matched `FEATURES` via `resolved_features_for` (base = `run_wide`'s
   own `FEATURES` row), and recompute the per-entry `PORTAGE_TMPDIR` via
   the already-generic `ebuild_phases::resolve_entry_portage_tmpdir`
   (needs no change — it already takes raw `package_env_vars`, never a
   `MergeOptions`). The recomputed tmpdir shadows the loop-local
   `portage_tmpdir` for that entry's pre-clean/build/post-clean, exactly
   as `build_one_source_entry`'s `entry_tmpdir` shadow already does on
   the merge-scheduler path. A missing matched directory fails the entry
   with real's exact `_check_temp_dir` message (Phase 2 S0 cell E),
   respecting `--keep-going`.
3. **Tests** (`emerge_build.rs`'s `mod tests`, no new fixture files —
   `package_env_vars` is constructed in-memory, the same pattern
   `per_package_portage_tmpdir_feeds_the_build_directory`
   (`ebuild_phases.rs`) already uses):
   - a `--buildpkgonly` build of the existing `penvbuildpkg` fixture
     (Phase 2's own build-var probe) with an in-memory `package_env_vars`
     entry matching its cpv, asserting the packaged binary's build ran
     under the matched `CFLAGS`/`CC` (Phase 2 S0 cell A/F shape, applied
     to the third path);
   - a `PORTAGE_TMPDIR` cell-E pin: matched value pointing at a
     nonexistent directory fails the entry with real's exact message,
     `--keep-going` collects it instead of aborting the whole run;
   - a `FEATURES` fold pin at the `resolved_features_for`/
     `matched_package_env_vars` level (already covered structurally by
     the extracted functions' own tests) plus one `run_buildpkgonly`-level
     assertion that an unmatched entry keeps the run-wide `build_env`
     byte-identical (regression guard for every existing
     `run_buildpkgonly` test).

**Commit subject:** `#129: --buildpkgonly matches package.env, like the other two build paths`.

### S2 (#130) — per-entry `PackageOptions` at all three `package_after_install` sites, and standalone-merge `FEATURES`

**Merge-path safety gate: does not apply** (§0, corrected during this
slice — there is no separate "binary-merge path" call site; see step 2).
**O4 stands**: this slice lands the mechanism and Rust-level proof; it
does not move a pmtest pin.

1. **`PackageOptions::set_resolved_features`** (`ebuild_package.rs`, new,
   mirrors `MergeOptions::set_resolved_features`'s shape exactly):
   re-derives `buildpkg_live`/`binpkg_multi_instance`/`binpkg_signing`
   from a resolved (already-folded) `FEATURES` list by plain presence —
   a negated token has already been folded away by
   `fold_package_env_incremental`, unlike the raw-process-env
   default-on-unless-negated fallback `PackageOptions::default`'s own
   doc comment describes. `PackageOptions` needed `#[derive(Clone)]`
   added (it had none) so each call site below can clone the shared
   instance per entry.
2. **All three `package_after_install` call sites** (there are three, not
   two — the plan's original "binary-merge path" guess was wrong; both
   `emerge_build.rs:677`-era's serial source-build call and
   `ebuild_merge.rs:3080`'s internal call belong to the *same*
   `ebuild_merge::run_merge` function, used by the serial single-job
   source path, not a separate binary-merge path):
   - `build_one_source_entry` (`emerge_build.rs`, the `-jN` scheduler's
     build function): clone `buildpkg`'s `PackageOptions`, fold this
     entry's `FEATURES` via the already-shared `entry_resolved_features`,
     `set_resolved_features` on the clone, pass `&clone` instead of the
     shared reference.
   - `ebuild_merge::run_merge`'s own internal call (used by the serial
     single-job source path via `emerge_build.rs` and by nothing else —
     `ebuild.rs`'s standalone `merge` always passes `buildpkg: None`):
     `options.features` (the caller's `MergeOptions`) is *already* this
     call's fully resolved value by the time `run_merge` runs (the caller
     cloned `MergeOptions` and called `set_resolved_features` before
     invoking `run_merge`), so clone `package_options` and call
     `.set_resolved_features(&options.features)` unconditionally — no
     `Option` branch needed, since `options.features` is always the
     correct value whether or not anything matched.
   - `run_buildpkgonly`'s own `ebuild_package::run_package` call: reuse
     the `FEATURES` value `buildpkgonly_entry_build_env` (S1) already put
     in `build_env` — no recomputation, just read it back out — clone
     `options` (`PackageOptions`) and `set_resolved_features` from it.
3. **Standalone `ebuild <file> merge`/`qmerge`** (`ebuild.rs`'s CLI
   boundary, shared `merge_options` variable). New
   `ebuild_phases::resolve_standalone_resolved_features`, mirroring
   `resolve_standalone_portage_tmpdir`'s path-parsing exactly — factored
   the shared "ebuild path → pkg_dir/category/pf → resolved `Config` +
   `cpv_slot`" logic out of `resolve_standalone_portage_tmpdir` into a
   new private `standalone_package_env_lookup` so both functions share
   it instead of a second copy. `merge_options.set_resolved_features` is
   called when something matched — the exact gap the backlog text names
   ("`ebuild <file> merge` never calls `set_resolved_features`"). The
   standalone `package` command's own `PackageOptions` (separate
   variable, `ebuild.rs`'s `package_options`) was left untouched — the
   backlog text names "`ebuild <file> merge`", not `package`, and a
   one-shot `ebuild <file> package` run has no "shared across entries"
   problem to fix; noted as a possible residue, not folded in.
4. **Scope boundary — do not widen.** `PackageOptions::binpkg_compress`
   is a scalar config var, not a `FEATURES` token, and is untouched —
   not grounded by this item's text.
5. **Tests.** Rust-level: `set_resolved_features_rederives_the_binpkg_affecting_tokens`
   (`ebuild_package.rs`, direct); a per-entry `binpkg-multi-instance` pin
   (`run_buildpkgonly_resolves_per_entry_binpkg_multi_instance_from_package_env`,
   `emerge_build.rs`: matched package gets real's
   `<pkgdir>/<cat>/<pn>/<pf>-<id>.xpak` multi-instance layout, its
   unmatched neighbour in the same run keeps the single-instance
   default). **No pmtest CASES row, no contract pin** — per O4, that is a
   follow-up with the owner present.

**Commit subject:** `#130: per-entry FEATURES reaches PackageOptions and the standalone merge gates`.
