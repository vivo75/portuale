## What Z found in portuale, and fixed

1. **`doins -r` on a dangling absolute symlink died with
   `FileNotFoundError`** (the first Z leg (a), `porttest/helper-doins`).
   - Root cause: the phase environment did not export
     `PORTAGE_ACTUAL_DISTDIR`. Real `config.environ()`
     (`config.py:3403-3409`) exports it. `ebuild-helpers/doins:80-82`
     passes `--distdir` only when it is set, and without it `doins.py`
     dereferences every absolute symlink. The native doins was right;
     its input was wrong.
   - Fix: `run_commands_async` exports `PORTAGE_ACTUAL_DISTDIR=DISTDIR`
     (`ebuild_phases.rs`).
   - Also, the native doins symlink failure now prints Python's
     two-filename `OSError` form, `b'<target>' -> b'<dest>'`
     (`helpers/doins.rs` `errno_line2`).
   - Tests: `phases_export_portage_actual_distdir_so_doins_keeps_absolute_symlinks`
     (pmtest fixture `dev-libs/actualdistdirpkg`, which failed before
     the fix), `symlink_failure_names_target_and_dest_like_real`, and
     two new D4 oracle cases generated from real `doins`:
     `dangling-abs-kept` (link preserved) and `dangling-abs-nodistdir`
     (real's own rc 1). On regeneration the other 23 cases came out
     byte-identical.
2. **A `--buildpkg` source merge recorded no `BINPKGMD5` in the vdb**
   (leg (a) after fix 1: `push-3.4` and `quoter-4.2`, which are built
   from source and never re-merged from their gpkg).
   - Real `EbuildBuild._record_binpkg_info` (`EbuildBuild.py:502-523`)
     and `doebuild`'s `package` branch (`doebuild.py:1522-1544`) write
     `build-info/BINPKGMD5`, plus `BUILD_ID` when present, after the
     package step. The vdb merge copies them.
   - Fix: `package_after_install` (`ebuild_package.rs`) writes both.
     Test: `package_records_binpkgmd5_and_build_id_in_build_info_like_real`.
     After the fix the leg (a) vdb rows are gone.

Leg (b) ran before fix 2. Its packages are re-merged from their gpkg in
step 2, so the binpkg-merge path writes their `BINPKGMD5` and fix 2
cannot show there. The gate, gate-reinstall and l31b cells ran on the
final binary.

The audit decides by construction. The nopy image has no Python at all,
and neither image has an importable `portage` or any helper `.py` file,
so a green build proves that every helper call went through the
dispatcher. A live `ps` sampler and a log scan corroborate it. During
the close-out I fixed one audit classifier bug: the dispatcher's own
argv `portuale __helper python <script>` was being counted as a real
interpreter call.

## Residues (filed)

- **#330:** no per-package fake distdir. Accounts for the `MY_PATCHES`
  rows.
- **#331:** replacing portuale's binary mid-run breaks later phases. Hit
  once in this close-out, when a `cargo build` landed during the glibc
  postinst; that run was discarded and repeated.
- **#332:** env.d changes from one merge do not reach later builds in
  the same run (real `config.reload()` per task). Accounts for the
  `PT_HELPER_DOINS` rows in gpkg (a).

The glibc `.a` and getconf rows are build nondeterminism, not portuale
behaviour:
- the `.a` digests differ between two real-Portage builds;
- the getconf `.gnu_debuglink` names a different member of the same
  hardlink group (real `POSIX_V7_LP64_OFF64.debug`, portuale
  `POSIX_V6_LP64_OFF64.debug`), the #261 race.
