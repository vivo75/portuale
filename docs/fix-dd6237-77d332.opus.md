## 🔴 CRITICAL

### O1 — `installed_cp_sources` now emits a duplicate on a `move` cycle *(new — not in the first audit)*

`rust/portage-repo/src/lib.rs:813-844`. This is the one place in the
batch where the new code is **not** equivalent to the code it replaced.

The old per-call loop deduped against `out`, which was seeded with the
target:

```rust
let mut out = vec![target.clone()];                 // target is already in `out`
for cmd in global_package_updates() {
    if let UpdateCmd::Move { old, .. } = cmd {
        if apply_updates_to_cp(&old.0, &old.1) == target && !out.contains(old) {
            out.push(old.clone());
        }
    }
}
```

so it could never push `target` a second time. `installed_cp_sources_map`
dedups a bucket against **itself** (`if !bucket.contains(old)`) and never
against the destination, so it files `old` into bucket `old` whenever
`apply_updates_to_cp(old) == old`. `move_chain_map`
(`lib.rs:764-790`) produces exactly that for a **cycle**, because it
declines to insert when the replay returns to the start:

```
move a/x b/x
move b/x a/x
```
→ `apply_updates_to_cp("a","x") == ("a","x")` → `bucket[(a,x)] = [(a,x), (b,x)]`
→ `installed_cp_sources("a","x") == [(a,x), (a,x), (b,x)]`.

**Impact.** `installed_candidates_uncached` (`lib.rs:6045`) iterates
`sources` and scans each category dir, so the same vdb entry is emitted
**twice** — duplicate `(version, slot, sub_slot)` rows into the installed
sets the resolver builds graph nodes from. `vdb_pkg_dir_meta`
(`lib.rs:6915`) also scans the same directory twice.

**Reachability, measured.** I replayed the host tree's
`profiles/updates/` (477 `move` commands, 1Q-2020..today) through the
same chain algorithm: **0 cps whose chain returns to themselves**. So this
is latent on today's Gentoo, and would be armed the first time a package
move is reverted in a later quarter's file — which is an ordinary thing
for a distro to do. It is a strict regression against code that was
cycle-safe by construction, and the fix is one line.

**Why the test does not catch it.**
`installed_cp_sources_map_matches_the_command_loop` (`lib.rs:26953`)
replays the *same* loop over the ambient repos' actual updates — which
contain no cycle — so it is a tautology on the tested input.

**Fix.**
```rust
// in installed_cp_sources_map(), inside the `for cmd` loop:
let dest = apply_updates_to_cp(&old.0, &old.1);
if dest == *old { continue; }   // the target is already out[0]
let bucket = map.entry(dest).or_default();
```
and add a unit test that feeds a synthetic two-command cycle through a
`_with`-style seam — the same testability seam `apply_updates_to_dep_string_with`
already introduced for #119.

### O2 — the USE-context fingerprint is sampled, and it is a memo *key* `[= C1]`

`rust/portage-profile/src/lib.rs:2529` `use_context_base_fingerprint`
digests ~15 ordered fields with `hash_sampled` (length + first + middle +
last), including `package_use`, `package_use_user`, `package_use_mask`
and `package_accept_keywords`. That digest is the identity component of
five memo keys: `EUF_CACHE` (`lib.rs:3414`), `RUMF_CACHE` (`:3755`),
`MKA_CACHE` (`:4555`), `BRU_CACHE` (`:2850`) and `IV_CACHE` (`:4722`, via
`is_visible_base_fingerprint`, which folds the same base in). Two configs
differing only at a non-sampled position are served each other's USE
flags and visibility verdicts.

**I confirm the finding and adopt the severity, with a sharper
justification than "it could collide".** The sampling was justified by
*per-call* cost, and #105 destroyed that justification: the base is now
computed **once**, in `resolve_config` (`portage-profile/src/lib.rs:3731`).
A full content hash there costs microseconds at process start. Sampling in
a memo key that is computed once is not a trade-off any more — it is a
retained hazard with no remaining upside. That is what makes this
🔴 rather than 🟡, not the (currently nil) probability of a hit.

I verified the production single-config invariant actually holds today —
see O6 — so this is latent, not live. The first audit's supporting
argument ("it already failed once in this batch — the MKA accept-list
collision") is about a *missing field*, not a sampled one, so it is
evidence for the general fragility of audit-built keys, not for this
specific collision. The freeze-time cost argument above is the stronger
one.

**Fix.** Make `use_context_base_fingerprint` exact (plain `.hash()` for
every ordered field; keep the existing order-independent xor-fold for the
`HashSet` fields, which is already exact). Leave the `None`-base fallback
exact too — test configs are not hot. This is a same-day change with no
behavioural risk: the digest is process-local and never persisted.

## 🟡 WARNING

### O3 — `local_binpkg_index` keys its memo on a raw `Vec` pointer, and never re-reads `Packages` `[≈ C2, extended]`

`lib.rs:2340-2380`. `scanned_id` is
`(entries.as_ptr() as usize, len, first_CPV, last_CPV)`.

I confirm the ABA analysis. **I disagree with the CRITICAL severity**, and
the reason is checkable: the two `scanned_binpkgs` assignment sites
(`rust/portuale/src/pretend.rs:10874`, `:11301`) cannot both run in one
process — `:10874` is inside the `--info` standalone-action branch, which
returns before the resolve path reaches `:11301`. With exactly one
assignment per process there is no free-and-reallocate, so the ABA is
latent. It should be promoted to 🔴 the moment a second assignment is
added, which is precisely why it should be fixed now rather than
documented.

**A second staleness axis the first audit does not cover.** When
`scanned_binpkgs` is `None`, the key is just
`(pkgdir, None, quickpkg_root)` and the memoised value came from
`read_packages_index(&config.pkgdir)` — a **filesystem read that is now
never repeated for the life of the process**. Before this batch each
`local_binpkg_index` call re-read `<pkgdir>/Packages`. `cached_binary_index`
(`lib.rs:2322`) already documents an "emerge is one-shot" assumption, but
that one guards a *remote binhost* index; this is the local `$PKGDIR`
pool, and portuale does build and merge packages in-process
(`--buildpkg`, `--resume`). A third axis: the `--quickpkg-direct` entries
appended at `:2395` are derived from the source root's **vdb**, which the
key does not cover at all.

Also note the cache is a single `Option` slot, not a map, so two configs
alternating thrash it to a 0 % hit rate.

**Fix (preferred, and it dissolves all three axes).** Stop deriving the
index from `&Config` at the call sites. `ResolveCtx` already holds
`local_binpkg: Arc<BinaryIndex>` (`lib.rs:19546`) — thread that `Arc` to
the three remaining callers (`lib.rs:11453`, `:11472`, `:12559`) instead
of having each rebuild from the config. That removes the 3,056 calls
outright and makes the key question moot.

**Fix (if the memo must stay).** A generation counter bumped by the CLI at
each `scanned_binpkgs` assignment. Note the first audit's suggestion of
`Option<Rc<Vec<…>>>` + `Rc::ptr_eq`: **use `Arc`, not `Rc`** — `Rc` in a
`pub` field of `Config` makes `Config` `!Send` and would block the
`feat/parallel` work this branch exists for (see O18).

### O4 — `BRU_CACHE`'s key omits `ebuild.repo_location` `[= W4, with reachability evidence]`

`lib.rs:2874-2886` hashes the ebuild's
version/slot/sub-slot/repo-name/iuse/keywords/source, but the uncached
body reaches `repo_aux_metadata(&ebuild.repo_location, …)` through
`candidate_iuse_and_use` (`lib.rs:9220`).

I initially dismissed this on the grounds that `repo_name` ⇒
`repo_location` is 1:1 in production. The first audit is right that the
test process breaks that, and I can make the claim concrete: the crate's
test helper `candidate()` (`lib.rs:38619`) hardcodes
`repo_name: "test"` and `repo_location: PathBuf::new()`, and **four**
test sites then overwrite `repo_location` with distinct temp dirs while
leaving `repo_name` at `"test"` (`lib.rs:25164`, `:25294`, `:25375`,
`:25476`) — all at version `1.0`, slot `0/0`, keywords `["amd64"]`,
sharing one thread-local `BRU_CACHE`.

It is **not** currently triggered: I checked all four, and each varies
`candidate.iuse` in lockstep with the md5-cache `IUSE` it writes, so the
hashed `iuse` separates them. It is triggered the moment a test varies
only the md5-cache contents behind two `repo_location`s at identical
candidate `iuse` — which is exactly the shape
`ebuild_at(tag, iuse)` (`lib.rs:25367`) invites. Same class as the #110
review fix, same one-line remedy.

**Fix.** `e.repo_location.hash(&mut h);` — one short path per call.

### O5 — `is_visible` and `binpkg_respect_use_ok` keys are *pure* 64-bit digests *(new)*

`lib.rs:4714` keys on `(u64, u64)` where the second hash already subsumes
the first; `lib.rs:2827` keys on `(u64, bool, bool, bool)`. In both, a
`DefaultHasher` output **is** the key — there is no literal value
component to disambiguate a collision. `EUF_CACHE` and `MKA_CACHE` are
better off: they retain `candidate_str` (and `value_str`) as real key
components, which bounds any collision to same-candidate inputs.

This is independent of O2: fixing the sampled base makes the *config* half
exact, but the *candidate* half of these two keys stays a 64-bit digest of
eleven fields. At the measured cardinalities (1,503 and 1,197 distinct
inputs) the birthday probability is ~10⁻¹³, so this is not a live bug —
but it is a gratuitous hole in exactly the two functions that gate "is
this package installable at all", and the fix is one `String` these
functions already build internally.

**Fix.** Put `candidate_str` (or `candidate.version`) into the tuple
alongside the digest, as `EUF_CACHE` and `MKA_CACHE` already do.

### O6 — the frozen bases are `pub` fields with no enforcement of the invariant they rest on *(new; adjacent to C1's second paragraph)*

`portage-profile/src/lib.rs:566` (`use_context_base`), `:578`
(`is_visible_base`). Five memos now depend on an unwritten rule:
*nothing mutates a USE-context or visibility field after `resolve_config`,
except `autounmask_use`.*

**The invariant holds today — I checked, and this is the check the first
audit did not run.** Enumerating every production assignment to a
`Config` field outside `portage-profile`'s own resolve gives exactly
three: `scanned_binpkgs` (`pretend.rs:10874`, `:11301`),
`autounmask_backtrack` (`pretend.rs:11270`) and `autounmask_use` on a
clone (`lib.rs:23878`). None of the first two is in either base, and the
third is hashed live on top. So the design is sound as shipped.

What is missing is any way to *keep* it sound. The fields are `pub`,
`Clone` carries a stale digest forward silently, and the crate's own tests
exercise the `None` fallback (`Config::default()`), not the frozen path —
so a future `config.package_mask.push(…)` for, say, an autounmask-unmask
feature would poison `IV_CACHE`, `EUF_CACHE`, `RUMF_CACHE`, `MKA_CACHE`
and `BRU_CACHE` with no test failure anywhere.

**Fix (free, and it is the highest value-per-line item in this document).**
```rust
// in use_context_fingerprint / is_visible_fingerprint, on the Some(base) path:
debug_assert_eq!(
    base, portage_profile::use_context_base_fingerprint(config),
    "a USE-context field was mutated after resolve_config froze its digest"
);
```
Zero cost in release; the recompute is code the `None` path already runs.
This turns a silent wrong-answer class into a loud failure the first time
anyone adds such a mutation. Pairs naturally with O2 (once the base is
exact, the assertion is exact too).

### O7 — `binpkg_respect_use_ok` constructs one SipHash hasher per baked-USE flag, per call `[= W2, with a sharper fix]`

`lib.rs:2866-2873`. The order-independent xor-fold builds a fresh
`DefaultHasher` for **every element** of `binary_use`, on every call, hit
or miss — ~200 hasher constructions per call for a real package, ×12,000
calls. Confirmed in source.

The first audit's fix ("fold all elements through a single hasher") does
not work as stated: a single hasher is order-*dependent*, and the set's
iteration order is not stable — which is why the fold exists.

**Better fix, and it removes the fold entirely.** A binary candidate is
already uniquely identified by `(CPV, repo_name, build_id)`:
`Candidate::build_id` (`lib.rs:2027`) is populated from the index entry's
`BUILD_ID` (`lib.rs:2576`) and is precisely what distinguishes two
`binpkg-multi-instance` instances of the same CPV; without multi-instance
two entries with the same CPV cannot coexist in one index. So hashing
`candidate.build_id` in place of the baked-USE fold is both exact and
O(1). Verify that claim against `dedup_binary_instances` before
committing; if it does not hold for the remote/binhost shape, the
fallback is to memoise the set's digest on the `Candidate` when
`binary_use` is built, so it is folded once per candidate instead of once
per call.

### O8 — cache *hit* paths allocate what they are about to discard `[= N3 / ≈ W1, quantified]`

Three sites, all on the hot path, all pure waste:

1. **`installed_candidates` (`lib.rs:6019`)** —
   `CANDIDATES_CACHE.with(|c| c.borrow().get(&key).cloned())` deep-clones

       c.borrow().get(&key)
           .filter(|(old, _)| *old == fps)

   and `fps.push((dir, mtime))` (move, don't `dir.clone()`).
2. **`local_binpkg_index` (`lib.rs:2372`)** — same `.borrow().clone()`

3. **Key construction on hits** — `candidate_str.to_string()` in

### O9 — `resolved_use_mask_or_force`'s key omits `category` and `package` *(new)*

`lib.rs:3736`. The signature takes them; the key (`:3755`) is
`(which, stable, use_context_fingerprint, candidate_str)`. It is sound
only because every current caller builds `candidate_str` as
`"{category}/{package}-{version}:{slot}/{sub}::{repo}"` from those same
two values — I checked all five (`lib.rs:3650`, `:3873`, `:9624`,
`:10213`, plus the test sites). That is correct-by-coincidence, and it is
the same shape as the bug the #110 review fix caught.

**Fix.** Either hash them into the key (two short strings), or drop the
parameters and derive them from `candidate_str` inside the function so
the coupling is structural rather than conventional.

### O10 — invalidation granularity, and two caches covering `SLOT` under different signals `[= W3, confirmed]`

`lib.rs:5995` (`dir_mtime_nanos`), `:6019` (`CANDIDATES_CACHE`), `:6667`
(`AUX_CACHE`). Both findings hold:

- **Granularity.** On a filesystem with coarse mtime (the plan itself
  documents truncated mtimes on livecd squashfs for the analogous
  `aux_cache`), two mutations inside one tick are invisible. Real portage
  has the same hole — which is exactly why it calls `_bump_mtime` on both
  sides of `aux_update`.
- **Cross-cache mismatch.** `CANDIDATES_CACHE` validates on the
  **category**-dir mtime while `AUX_CACHE` validates on the
  **package**-dir mtime, and both serve `SLOT`. A `utime` on a package dir
  (real's `_bump_mtime`) invalidates one and not the other, so the two can
  disagree about the same value.

Portuale's own writers are safe: `write_vdb_entry_from_dir`
(`ebuild_merge.rs:~2330`) does `remove_dir_all` + `rename`, and unmerge
removes the dir — both change the category dir. The exposure is a
concurrent external writer, which is not a supported scenario today.
Keep as a documented robustness limit; if it is ever tightened, a
process-local mutation sequence counter bumped by portuale's own writers
beats adding more stats.

### O11 — the out-of-set vdb-key guard is `debug_assert!` only `[= W6, failure mode corrected]`

`lib.rs:6635-6639`. The guard that a key outside real's 23-field
`_METADATA_FILE_FIELDS` would need an `environment.bz2` search is a
`debug_assert!`. Every current caller was audited and I re-verified it:
extracting every key literal reaching `read_vdb_string`/`vdb_aux_get`/
`read_vdb_flag_set` across `lib.rs`, `merge_order.rs` and
`resolver_trace.rs` yields exactly `{BDEPEND, BUILD_TIME, DEFINED_PHASES,
DEPEND, IDEPEND, IUSE, KEYWORDS, PDEPEND, RDEPEND, SLOT, USE,
repository}` — all in-set.

**Correction to the first audit's failure mode.** It says a future
out-of-set caller "silently gets `""` in release". That is true only when
a *validated snapshot exists*. Otherwise control reaches
`read_vdb_file(&dir.join(key))` (`lib.rs:6720`), which reads the file and
applies `split_whitespace().join(" ")` — so a line-oriented key
(`CONTENTS`, `NEEDED.ELF.2`) comes back **whitespace-collapsed**, i.e.
structurally corrupted, which is worse than empty and much harder to spot.
That strengthens the case for making the guard structural.

**Fix.** A key enum (the `MetadataKey` discriminant #110 introduced is the
precedent), or an `in_metadata_file(key)` early-return that routes a
line-oriented key to a raw, un-normalised read.

### O12 — the fingerprint still does O(n) work inside the loops the batch sped up *(new; overlaps W1)*

`use_context_fingerprint` (`lib.rs:3458`) removed the expensive half but
still hashes `config.autounmask_use` — a `Vec<(String, Vec<String>)>` — in
full on **every** `effective_use_flags` (~20 k), `resolved_use_mask_or_force`
(29,774), `metadata_key_accepted` and `binpkg_respect_use_ok` (12,000)
call. `n` is small today (a few autounmask tiers), so this is not a
regression — but it is O(n) inside the hot loop, and it is the next
obvious thing to remove.

Same shape at `accept_lists_fingerprint` (`lib.rs:4612`):
`package_accept.hash(&mut h)` walks the entire
`package.properties`/`package.accept_restrict` list per
`metadata_key_accepted` call.

**Fix.** Compose the fingerprint once per backtrack pass and thread it,
or cache it on the `Config` behind a mutation counter (which is also O3's
and O6's mechanism — one counter serves all three).

### O13 — the `#109`/`#110` port is faithful; I checked it against real's source

Diffed line-by-line against
`/usr/lib/python3.14/site-packages/portage/dbapi/vartree.py`. All of
these match: the 23-field `_METADATA_FILE_FIELDS` set (`:78-104`), the
`#format=` early abandon before parsing the rest (`:152-160`), the

Two things worth recording because they are easy to get wrong and this
batch got them right:

- **`METADATA_FILE_FIELDS` moving out of `ebuild_merge.rs` into
  `portage-repo` (#109 S2) is the correct call**, not merely tidy — real's
  own module comment says the field set *is part of the format version*
  and that reader/writer drift is the bug.
- **The merge-side stamp ordering is right.**
  `write_consolidated_metadata_file(&tmp_dir)` runs after `CONTENTS` and
  `COUNTER` (`ebuild_merge.rs:2364`) and before the `rename`; renaming a
  directory does not touch that directory's own `mtime`, so the stamp
  survives the move. I confirmed real's two
  `_consolidate_to_metadata_file` call sites (`vartree.py:1153`, `:5231`)
  both take the `delete_individual=False` default, so individual files
  always remain — which is what keeps portuale's remaining direct readers
  working.

### O14 — correcting W5: the `Rc::make_mut` is fine, and the TOCTOU is benign `[≠ W5]`

`lib.rs:6685-6699`. The first audit is right that `Rc::make_mut` would
silently clone if a second strong ref existed, and a comment stating the
uniqueness invariant is worth adding. But the second half of W5 — "a
concurrent external writer replacing the dir between the validity stat
and the snapshot read serves one torn snapshot" — does not happen. Trace
it: the stat yields `M1`; if the dir is replaced, the new snapshot's
`#dir_mtime=M2 ≠ M1`, so `read_metadata_file` **rejects** it and the code
falls through to the individual-file read of the (new) dir. The worst
outcome is an entry cached under a stale `M1`, which the very next call's
stat invalidates. Self-healing, and identical to real's own behaviour. No
retry loop needed.

### O15 — `read_vdb_file` does not port real's `errors="replace"` *(new)*

`lib.rs:6718`. `fs::read_to_string(...).unwrap_or_default()` returns `""`
for a field file containing invalid UTF-8; real returns the text with
U+FFFD substitutions (`vartree.py:1035-1039`,
`encoding="utf-8", errors="replace"`). This is pre-existing — the old
direct read behaved the same — but #109 S1's commit claims
*"normalise `read_vdb_string` like real's `_aux_get`"*, and this is the

`DESCRIPTION`/`HOMEPAGE` carrying a stray Latin-1 byte. (The same pattern
in `read_metadata_file` is harmless: there it just rejects the snapshot.)

### O16 — the single-key vdb scans pay 3 syscalls where they used to pay 1; already tracked

`all_installed_packages_uncached` (`lib.rs:7106`) and
`installed_candidates_uncached` (`:6045`) read exactly **one** key
(`SLOT`) per instance, so `vdb_aux_get` turns one `open(dir/SLOT)` into
`statx(dir)` + `open(dir/metadata)`→ENOENT + `open(dir/SLOT)`. The batch's
own numbers confirm it rather than contradict it: #109 S3 measured
`statx` 294,450 → 466,470 and reported itself a regression; S4's memo took
`openat` 160,351 → 33,685 and `read` 202,281 → 30,041 while `statx` stayed
up at 339,804; #112 then brought `statx` to 211,165. Net for the batch is
strongly positive (4.05 s → 3.48 s at S4, 2.01 s after #112), and the
residual is filed. Recorded here only so the trade is explicit: the win
comes from amortising across the 5 dep keys + `USE` + `IUSE` read later
per instance, which the two single-key scans by definition do not get.

One avoidable remainder: `all_installed_packages_uncached` already holds
the `DirEntry` for the package dir but re-resolves it through
`vdb_pkg_dir_meta`, paying a `statx` on a directory it just enumerated.

### O17 — the direct-`SLOT`-read bypass is already filed as #116

`ebuild_merge::read_installed_slot` and the sites named in backlog #116
(`pretend.rs:5226`, `ebuild_merge.rs:2682`) read `SLOT` with their own
`fs::read_to_string` + `.trim()`, bypassing the new seam and its
real-matching normalisation. Nothing to add — #116 already states the fix
and the glibc+bash gate that applies to it.

### O18 — `Rc` mortgages the branch's own stated goal

`effective_use_flags` and `resolved_use_mask_or_force` now return
`Rc<HashSet<String>>` (`!Send`), and eight thread-local memos
(`EUF`/`RUMF`/`MKA`/`BRU`/`IV`/`AUX`/`CANDIDATES`/`BINPKG`) grow unbounded.
`cleanroom/parallelism.md` §2.0 point 4 documents this explicitly, which
is good hygiene — the trade is deliberate, not accidental. Recording it
anyway because this is branch `feat/parallel`: every new `Rc` raises the
eventual `Rc→Arc` migration cost, and each thread-local memo is N× memory
and N× cold misses under a pool. **Prefer `Arc` for any new memo**, and
see O3 for a concrete place where the first audit's `Rc` suggestion would
have made this worse.

### O19 — `DefaultHasher` (SipHash) on every key `[= N2]`

Confirmed and no action: it is deterministic within a process, which the
passing fingerprint-equality tests rely on, and it is ~2–3× slower than
`foldhash`/`fxhash` for short keys. The right time to change it is
together with O8 (hit-path tax), not before.

### O20 — process commendations `[= N5, endorsed]`

Endorsing all of the first audit's, and adding two: `#118` withdrawing a
fully-implemented change with its measurements rather than shipping a
0.03 s "win" inside the noise floor; and `#119` reporting a **negative**
paired wall delta (+0.017 s mean, 9/15 wins) for a change the profile
said should help. Both are the behaviour that makes the rest of this
batch's numbers trustworthy.
