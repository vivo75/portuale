Status: **proposed 2026-10-04**. No step started.
Design (authoritative): [`feat-157-authoritative-vdb-database.md`](feat-157-authoritative-vdb-database.md).

## 0. Read this first (every agent, every step)

### 0.1 Backlog number

The design calls the feature "#157 (to be filed; re-check before
filing)". Backlog **#157 is taken**: it is the `sys-apps/portage`
keyword item, DONE 2026-09-27. On 2026-10-04 the highest number in

### 0.2 Scope

- **portuale only.** The feature is tested with Rust unit and
  end-to-end tests in this repo. New pmtest contract tests are allowed
  but not required, so no step depends on one.
- `fixtures/` is a symlink into pmtest. **Do not add files under
  `fixtures/`.** Tests build their VDBs in a `tempfile` directory, or
  read the existing fixture VDBs without changing them.
- These steps run pmtest **read-only** for verification: the contract
  suite, the L0 and L1 beds, and the glibc + bash gate. A step that
  must change pmtest says so. Today only S4.6 and S5.6 might.
- **`emerge` output must not change.** Through S8, every existing
  pmtest test, corpus entry and bed result must stay identical. If one
  drifts, the step has a bug. Do not bless the corpus.

### 0.3 Branches and commits

- Branch `backlog/305-vdb-backends`, created in **both** repos by P0.1
  (AGENTS.md "Two repos, one project"). The pmtest branch may end with
  no commits. If so, it is deleted at merge.
- **One step = one commit**, made after the step's "Done when" check
  passes. Use the commit title given in the step. The body explains why
  and cites the design section. Trailer:
  `Co-Authored-By: <actual model name> <noreply@anthropic.com>`.
- A portuale-only commit says in its body: "portuale-only; no pmtest
  counterpart (feat#157 is a portuale-only feature)".
- Never push. Never merge into `main`. Merging is the owner's call
  after Z.2.
- Each code commit builds and leaves `cargo test --release` green. A
  step must not leave the tree half-routed for the next step to finish.

### 0.4 How agents run (lessons from #270–#304)

- **One agent at a time, on the shared branch.** Steps are sequential
  unless their "Depends on" lines say otherwise.
- **The coordinator checks the agent's claims.** An agent's report is
  not evidence. Before committing, the coordinator re-runs the step's
  "Done when" commands. A cheap agent's "verified" has been wrong
  before (#243, #287).
- **Long test suites run in the background** (`cargo test --release`,
  the pmtest suite, the beds). Either the coordinator runs them, or the
  agent starts them in the background and polls. An agent's own shell
  can kill a long run in the middle.
- A **new worktree** needs symlinks for `3rdparty/*`, which is
  gitignored. Add `/3rdparty/*`, `/fixtures` and `/helpers` to the
  worktree's `info/exclude`.
- **Escalation:** if a step fails its "Done when" check twice with the
  suggested model, retry it once with the next model up
  (Haiku → Sonnet → Opus). Do not commit partial work. Revert it.

### 0.5 Difficulty and model

| Grade | Meaning | Cheapest model likely to succeed |
|---|---|---|
| **D1** | Mechanical: run commands, edit docs, small boilerplate | Haiku 4.5 |
| **D2** | Contained code, one file or module, the spec says exactly what to do | Haiku 4.5; Sonnet if the step touches the resolver crate |
| **D3** | Several files, needs judgment, existing tests protect it | Sonnet 5.5 |
| **D4** | Subtle semantics (byte parity, cache validity, transactions, IPC, FUSE), weak test protection | Sonnet 5.5 with a precise brief; Opus 5.5 on the first failure |

`[gate]` = the merge-path safety gate applies: a successful glibc + bash

coordinator runs it.

### 0.6 Standard verification ("V-std")

From `rust/`: `cargo fmt --check`, then
`cargo clippy --release --all-targets` (zero warnings), then
`cargo test --release`. A step that changes code also passes the
default build with no extra features. Once the backend features exist,
it also passes `--features vdb-sqlite,vdb-redb` (and `vdb-fuse` from
S7). Steps that can change `emerge` behaviour additionally run the
pmtest suite (`python3 -m pytest pytests-contract-suite -q` in
`../pmtest`) and compare the results with the P0.2 baseline.

### 0.7 S0 findings that change later steps (added 2026-10-04)

S0 found these facts, and they override the design and the step text
below wherever the two disagree. Evidence:
[`305-s0-vartree-write-order.md`](evidence/305-s0-vartree-write-order.md),
[`305-s0-path-inventory.md`](evidence/305-s0-path-inventory.md) (§5
N1–N16 is the list of interface needs),
[`305-s0-corpus.md`](evidence/305-s0-corpus.md).

- **Merge functions.** `write_vdb_entry_from_dir` does not exist. The
  merge writes the VDB through `create_vdb_tmp`, `populate_vdb_tmp`,
  `write_vdb_tmp_contents`, `write_consolidated_metadata_file` and
  `publish_vdb_tmp` (`ebuild_merge.rs:2682-2865`).
- **Counter allocation.** The counter is allocated in
  `populate_vdb_tmp`, before the payload merge, so `begin_entry` must
  return it (N1). Real's counter is locked and takes
  max(`counter` file, every entry `COUNTER`) + 1. portuale's
  `next_counter` does not. Keep portuale's behaviour in S1. Do not fix
  it silently; file it as a residue.
- **Replace order.** Real and portuale both delete the old entry, then
  rename the new one in (`vartree.py:5219-5238`), not the other way
  round as design §9 says. The files backend keeps that order.
- **Pending entry and late files.** The merge reads the pending
  `-MERGING-` entry while it runs, and adds `CONTENTS` and other files
  after the payload lands (N2, N3). `WriteTxn` needs per-file puts on
  a pending entry.
- **`world` is written separately from the merge**, by `pretend.rs` at
  the end of the run, and by `run_deselect` after unmerge. A
  world-only transaction must be legal, and `world` and `world_sets`
  are set separately (N4, N5).
- **Ebuild phases need a real path to the entry** (`PORTAGE_UPDATE_ENV`
  → `<entry>/environment.bz2`, N9). The files backend gives the path.
  The database backends give a scratch file, then call `replace_file`.
- **`reverse_dependents` needs `portage-dep` and `portage-use-reduce`**,
  which sit above or beside `portage-vdb` (N15). S1.1 decides where the
  reduction runs: the interface returns raw `*DEPEND` + `USE` per
  entry, and `portage-repo` reduces them.
- **mtimes and the stamp.** `_bump_mtime` touches the category
  directory and the VDB root, not the entry directory
  (`vartree.py:578-583`). Any mtime applied after the `metadata` stamp
  invalidates it (nanosecond equality), so a writer sets directory
  mtimes **before** writing the stamp, and touches no entry afterwards.
  This replaces "directory mtimes are applied last" in S2.6 and design
  §11.
- **Stale stamps stay stale** (S2.6, S2.7). A `metadata` file whose
  stamp did not match must still not match after a round trip. Only
  630 of 2,130 host entries have a `metadata` file at all, and a
  converter never adds one.
- **Step scope corrections.** `emerge_getbinpkg.rs`, `emerge_build.rs`,
  `merge_order.rs` and `solver_bridge.rs` have no production VDB sites;
  they only call helpers. `resolver_trace.rs` calls the
  `portage-repo` readers too. The `server:` shadow in `remote.rs` is
  only read today, so S1.7 routes reads only. `unmerge_replaced_same_slot`
  has its own same-cp prefix rule and no package-move remapping;
  routing it must keep the same result set.
- **Baseline `clippy`** already has 4 warnings on `main`
  (`portage-repo`, newer lints). V-std means **no new warnings**;
  record the count.

## 3. Order and parallelism

**Order change (2026-10-05, found in S4.1).** On a sqlite ROOT,
`has_version` / `best_version` inside ebuild phases still go through the
vendored `portageq`, which reads `var/db/pkg` and cannot see the
database. So the glibc + bash gate on sqlite (S4.6) cannot pass before
the native `portageq` exists. The steps after S4.5 run in this order:
S6.1 → S6.2 → S6.4 → **S4.6** → S5.1 … S5.5 → S6.3 → S5.6 → S7 → S8 → Z.
S6.3 (the parent pipe) needs S5.3's `RedbDb`, so it moves after S5.

```
P0.1 → P0.2 → S0.1, S0.2, S0.3 → S1.1 → S1.2 → S1.3 → S1.4 → S1.5 → S1.6 → {S1.7, S1.8} → S1.9 → S1.10
S1.10 → S2.1 → S2.2 → S2.3 → S2.4 → S2.5 → S2.6 → S2.7 → S2.8
S2.8 → S3.1 → S3.2 → S3.3 ; S3.1 → S3.4
S3.2 → S4.1 → S4.2 → S4.3 → S4.4 → S4.5 → S4.6
S2.2 → S5.1 → S5.2 → S5.3 → S5.4 → S5.5
S1.10 → S6.1 → S6.2 → S6.4 ; {S6.2, S5.3} → S6.3 → S5.6
S2.4 → S7.1 → S7.2 → S7.3 → S7.4
S2.5 → S8.1, S8.2, S8.3
→ Z.1 → Z.2
```

All agents share one branch, and §0.4 allows one agent at a time, so
in practice the steps run in the order written. The graph matters when
the owner wants to stop early. Useful stopping points:
**after S4.6** (sqlite usable by `mrg`), **after S6.4** (native
`portageq`, with no dependency on `3rdparty/portage`), or the full
plan.
