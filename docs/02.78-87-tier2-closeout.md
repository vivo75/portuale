## 2. #62 is now in scope for this batch

**Decision (this session): the exit code for a slot-conflict/residual
notice becomes `1`, matching real Portage 3.0.82.2, everywhere portuale
currently treats it as purely informational.** This reverses the #57
standing convention. The reason it was deferred — "changing it touches
every slot-conflict pin in the suite" — is no longer the blocker it was:
see §2a. This is a genuine, if narrow, behaviour change (a script that
today reads `$? == 0` after a slot-conflict notice will see `1`), so it
still needs a `what-this-proves.md` paragraph calling it out explicitly
as a corrected divergence, not a silent tightening.

**Real's actual rule — read this before writing the flag.** Verified
against 3.0.82.2 in `/usr/lib/python3.14/site-packages` on 2026-09-18,
because the obvious formulation ("real prints the notice ⇒ real exits 1")
is **wrong in three cases** and coding it would create new divergences:

- The notice itself is unconditional on the conflict existing:
  `display_problems()` prints it whenever
  `any(_package_tracker.slot_conflicts())` (`depgraph.py:11117-11120`).
  It says nothing about the exit code.
- The exit code comes from `action_build`'s `if not success:
  display_problems(); return 1` (`actions.py:460-462`).
- **Escape 1 — `--autounmask-only` returns 0 first**
  (`actions.py:456-458`), notice printed and all. It precedes the
  `not success` check.
- **Escape 2 — `_accept_blocker_conflicts()`**
  (`depgraph.py:9259-9271`): when backtracking is **disabled** and any of
  `--buildpkgonly`, `--fetchonly`, `--fetch-all-uri`, `--nodeps` is set,
  real *tolerates* the conflict — `_serialize_tasks` does not raise
  (`depgraph.py:10417-10421`), the run succeeds, and
  `display_problems()` prints the notice from the **success** path
  (`actions.py:479`/`:486`) with rc 0.

So the rule to implement is: **a slot conflict makes the run fail
(rc 1) unless `--autounmask-only`, or backtracking is off and one of
those four options is set.** S0b verifies both escapes with real
captures before S1 codes them.

**Where the code lives — and where the check must NOT go.**
`pretend.rs::run` is one function spanning `8243`–`12841`, and it does
the **actual merge** between the notice and its final return:

- The `result.slot_conflicts` render block (`~11812`): its own comment
  says outright *"Purely informational -- v1 neither refuses nor changes
  the exit code."* That comment is the target.
- `--autounmask-only` early `return ExitCode::SUCCESS` (`~12230`) —
  real's escape 1; the new check must sit **after** it so that
  precedence is preserved for free.
- `unsolvable_blockers` → `ExitCode::from(1)` (`~12299`),
  `buildpkgonly_deps_unsatisfied` (`~12512`), circular deps (`~12561`,
  `~12583`): the existing band of "display first, then fail the whole
  action" checks. **This is where the new check belongs** — same class,
  already before any merge dispatch. The blocker path itself is
  unaffected: its `all satisfied` → rc 0 / `unsatisfied` → rc 1 split
  already matches real.
- The merge/`--ask`/build dispatch (`~12594` onwards) and the final
  `ExitCode::SUCCESS` (`12841`). **A flag consulted at the end would
  merge the packages and then report failure** — the opposite of real,
  which returns 1 before the merge list is even offered.

The change is still small (one condition, in an existing band), but it
is not "set a flag, read it at the end". It is not a rewrite of the
blocker/slot-conflict model either — #78–#81 neither block on it nor are
blocked by it (§3).

### 2a. Why the pin-cost objection is weaker now

K1 was filed as "not scheduled" specifically because flipping this rc
touches every slot-conflict/residual fixture pin in the suite, and that
suite lived inside `portuale` itself. Since 2026-09-18
(`335543e`, "Fixtures now live in pmtest only"), **the whole pin surface
— `pytests-contract-suite`, the corpus, the fixture-oracle atomlists,
`what-this-proves.md`'s runnable examples — is a separate, sibling repo
(`pmtest`) that this batch can update freely**, on its own commits, with
no coupling to `portuale`'s own release history. That is exactly the
"large pin-update surface" column in §1's table: still real work (every
existing `rc: 0` expectation for a slot-conflict/residual notice needs
to become `rc: 1`), but no longer entangled with `portuale`'s own commit
boundaries the way it would be if the fixtures still lived here.

This does **not** mean "bless without checking" — see
[[corpus-matcher-same-args-env-collision]] (blessing corpus drift
uncritically once already corrupted the corpus by papering over a real
matcher bug rather than fixing it). Every re-pinned exit code in this
slice must be checked against an actual real-Portage capture (host probe
or container oracle) for that exact shape, not bulk-blessed from
portuale's own new output. The freedom pmtest gives is "cheap and
isolated to update," not "safe to skip verifying."

**And the pins were never the real risk.** `GraphResult::slot_conflicts`
has **two** producers: the walker's own `record_slot_conflict` calls
(`lib.rs:19425`, `:19891`, `:19962`, `:20129`) and the residual pass
(`build_residual_slot_conflicts`, fed at `lib.rs:21811`). The residual
half is portuale's own construct from #54/#57 — it has no 1:1
counterpart in real's `_package_tracker.slot_conflicts()`. So wherever
portuale records a residual conflict real never had, today's divergence
is *display-only* (an extra notice, same rc); after the flip it becomes
an **exit-code** divergence, and a probe that is clean or merely
"explained" today can turn into a bed failure. **That**, not the pin
sweep, is what S0 has to bound before S1 touches the code: inventory
every L0 and fixture-oracle probe whose portuale run has a non-empty
`slot_conflicts` (`--json` exposes it directly) and record real's rc for
each. If that set contains shapes where real exits 0 and no escape from
§2 explains it, the item stops and reports — the divergence is then in
which conflicts portuale records, which is #54/#57/#79 territory, not an
exit-code convention.

### 2b. #81's size, proposed implementation, and performance cost

This was asked for explicitly; answering it in full here rather than
just in the slice plan (§5).

**What "disproportionate" meant when C2 stopped.** Real's
`_serialize_tasks` (`depgraph.py:9457-10420`) is a priority-bucketed
topological scheduler: each iteration it greedily pops every currently
available "leaf" node (a package with no unresolved dependency) it can
find in one pass. Tree mode (`tree_mode`, `:9680`) disables that
multi-leaf greedy pop (`:9764-9777`), so tree mode reaches the *stuck*
branch (`:9998`, "no leaf could be selected") in shapes flat mode never
does. Only in that stuck branch does real forcibly schedule an
`[uninstall]` task for a blocked package (`scheduled_uninstalls.add`,
`:10190`) and append the now-solved blocker row (`:10311-10358`). C2's
own dump (`sys.settrace` on p2b) shows this precisely: flat mode's
retlist has no `Blocker` node and `scheduled_uninstalls == []`; tree
mode's has both.

**What implementing it would take.** Not a tree-only patch — reproducing
this needs a second, tree-mode-aware pass of the *whole* leaf-selection
algorithm real's serializer runs, tracked as live scheduler state
(`scheduled_uninstalls` growing as the walk proceeds), because whether a
node counts as "stuck" depends on the full set of nodes still pending at
that point in the walk, not on any single edge. `merge_order.rs` already
carries a flat-mode port of a good chunk of `_serialize_tasks`
(`SerializeFrontier`, the discovery-order work from the cluster-I effort
— 12 slices, `[[cluster-i-merge-order]]`, to get flat-mode order to
today's parity). A faithful tree-mode leaf-selection port is comparable
in kind, not a small addition on top of it: a new, largely independent
scheduling mode threaded through the same module, with its own oracle
matrix (tree-mode-specific stuck/non-stuck cells, not just the one p2b
row already captured), and real risk of moving *unrelated* already-pinned
tree-mode order — cluster I's #17/#85 class of divergence is exactly
"the wall moves when you touch scheduler order," and tree mode is the
less-tested half of that module.

**What it buys.** Exactly one row class: a satisfied blocker (and its
inline `b`/removal row) becoming visible in `--tree` output, only in the
specific shape where the replacement's merge is gated on the owner's
uninstall and tree mode's disabled greedy pop is what exposes it (C0's
p2b cell, plus u6/multislotparent's sibling-order variant). `--tree` is
an interactive/inspection flag, not the default `-p`/`-pv` path most
tooling scripts against; no `--json` or exit-code consumer is affected.

**Performance impact, if built.** Low and containable *if scoped
correctly*: the new leaf-selection pass only needs to run when
`tree_mode` is requested (`--tree`), so the default `emerge -p`/build
path pays nothing. The risk is not runtime cost, it's correctness
fragility — a second scheduling mode is more surface for the merge-order
work already struggling with #17/#85 to regress silently, and every
existing tree-mode pin becomes a candidate for movement until re-verified.
If, contrary to the design, it turned out to need to run unconditionally
(e.g. to keep flat and tree order derived from one shared pass rather
than diverging further), that would touch the hot path measured in
[[perf-investigation-2026-09-07]] (`emerge -puD`, 4.6s today) — but
nothing in C0's evidence requires that; the gate should be `--tree`-only.

**Recommendation given this, not just a re-ask:** decline it as a
documented cut, same shape as #17's frontier-drain wall and #78's
non-goals. One display row in one flag's output does not justify adding
a second, largely-duplicate scheduling model to the highest-blast-radius
module in the codebase. §5's #81 slice plan still puts this to the
owner explicitly as a stop-and-ask (not a foregone conclusion baked into
the plan on the model's own authority), but leads with this
recommendation instead of an open question.

### 2c. #89 — the confirmation run (reported, then verified)

Filed from a VM-bed `INVALID` run (`MERGE_RC=2`): the stock cloud image
ships `/etc/portage/package.use/releng/no-filecaps` (`*/* -filecaps`);
real honours it and merges the htop binpkg, portuale ignores the
fragment, computes `filecaps` from the IUSE default, sees a binpkg USE
mismatch and rebuilds from source. The same probe in the container bed
(which has no `releng/` fragment) has both PMs agree — that contrast is
what isolates it from plumbing.

**Verified host-side on 2026-09-18**, one copied configroot, both PMs,
same `PORTAGE_CONFIGROOT`:

| fragment staged under `package.use/` | real `config()['USE']` | portuale `emerge --info` |
|---|---|---|
| `zz-flat-control` → `*/* flattestflag` | PRESENT | PRESENT |
| `releng/no-filecaps` → `*/* nestedtestflag` | **PRESENT** | **absent** |
| `zz-flat-control~` → `*/* backupflag` | absent | **PRESENT** |
| `.hidden-frag` → `*/* dotflag` | absent | **PRESENT** |
| `.git/frag` → `*/* vcsflag` | absent | absent (only because it does not recurse yet) |

So there are **three** divergences, not one, and two of them point in
opposite directions:

1. **No recursion.** Real: `grabfile_package(..., recursive=1)` →
   `_recursive_file_list` (`portage/util/__init__.py`), arbitrary depth.
   Portuale: `read_config_lines`
   (`portage-profile/src/lib.rs:~2044`) does one `read_dir` with
   `.filter(|p| p.is_file())` — a subdirectory is silently dropped.
2. **No name filters.** Real skips `VCS_DIRS`
   (`CVS RCS SCCS .bzr .git .hg .svn`, `const.py:278`), dot-prefixed
   names and `~`-suffixed backups (`_recursive_basename_filter`), at
   every level *including the root path itself*. Portuale reads every
   regular file — so an editor backup left in `package.use/` is live
   config in portuale and inert in real.
3. **Traversal order.** Real yields one merged ascending sort over files
   *and* directories, each directory expanded **in place** — verified:
   `00-first, aa/inner, mm/inner, nn-mid, zz/inner, zz-last`. A naive
   "files first, then recurse" port gives a different order, and these
   files are incremental (last wins), so the order is load-bearing.

**The two defects must land together.** Adding recursion without the
filters turns `.git/` and `*~` backups under `package.use/` into live
configuration — strictly worse than today.

**Blast radius, and why it is still small.** One function
(`read_config_lines`) feeds every
`/etc/portage/package.{use,env,license,mask,unmask,accept_keywords,properties,accept_restrict}`,
`binrepos.conf`, and the profile/repo-side `package.*` / `use.*` /
`arch.list` reads. A **second, independent copy** of the same one-level
logic sits in `portage-repo/src/lib.rs:~1143` for `repos.conf`, which
real also reads recursively (`repository/config.py:943-950`). Two
functions, not twenty call sites. No committed fixture uses the
directory form at all today — which is why nothing caught this, and also
why the fix is behaviour-neutral for the existing suite.
