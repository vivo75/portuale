## 1. What real does (3.0.82.2, `3rdparty/portage/lib/portage/gpkg.py`)

**Writer** — `gpkg._add_metadata`: one `TarInfo("metadata/<KEY>")` per key,
regular files only, USTAR, **no directory entries, no links**. So no
archive real produces can be affected by a regular-file-only check.

**Populate/read** — `unpack_metadata(dest_dir=None)` (via `get_metadata`):
reads the inner tar fully into memory, then for **every** member
`metadata.extractfile(k).read()` keyed by `_strip_metadata_prefix(k.name)`.
Python `tarfile.extractfile` (host `tarfile.py` `extractfile` /
`_find_link_target`): a regular member (or an unknown type) -> bytes; a
symlink -> looks up `dirname(name)/linkname` (normalized) in the **whole**
archive; a hardlink -> looks up `linkname` among members **before** it;
either link recurses into `extractfile(target)`; not found -> `KeyError`;
directory/FIFO/device -> `None` (so `.read()` -> `AttributeError`).
`_getmember` returns the **last** member with a given name.

| inner member | real result |
|---|---|
| regular `metadata/KEY` | bytes |
| name not under `metadata/` | `InvalidBinaryPackageFormat` |
| symlink, target inside the archive | the **target member's** bytes |
| symlink, target outside (`/etc/hostname`, `../..`) | `KeyError: linkname ... not found` (verified 2026-09-15) |
| hardlink to an earlier archive member | the target's bytes |
| hardlink to a non-member / a later member | `KeyError` |
| directory / FIFO / char / block device | `AttributeError` (`None.read()`) |
| nested `metadata/sub/KEY` | key `sub/KEY` (never produced by the writer) |

No host file is ever read. `bintree._populate_local` (`bintree.py` ~288,
~748) only catches `SignatureException` around `get_metadata()` — whether a
`KeyError` there aborts real `emerge` with a traceback or is caught higher
is **to be confirmed in S0**; it decides what the caller should do.

**Merge** — `unpack_metadata(dest_dir)` -> `tar_safe_extract(metadata,
"metadata").extractall(dest)`: rejects duplicate names, absolute names,
`../` traversal, **device members**, and **hardlinks whose target is not an
earlier member**; **symlinks are extracted as-is** (`fully_trusted_filter`)
into a temp dir and `shutil.move`d into build-info. For an escaping symlink
the preceding populate `get_metadata()` already failed, so real never gets
there for a package from its own pool. S0 confirms both halves.

## 2a. Mechanism: read the inner tar in-process with the `tar` crate

Owner suggestion (2026-09-16): use a Rust tar reader
([`tar`](https://crates.io/crates/tar), `github.com/composefs/tar-rs`,
0.4.46, MIT/Apache-2.0, the de-facto standard crate) instead of
`tar -xf` + a filesystem walk for the **inner metadata tar**.

Why it fits #58 better than #56's post-extraction check:

- **Nothing inner is ever written to disk before it is judged**, so no
  symlink can be followed, no FIFO opened, no device node created — the
  class of bug disappears rather than being checked for afterwards.
- The entries come with their header type and link name
  (`Entry::header().entry_type()`, `link_name()`), so portuale can port
  real's `extractfile` **exactly** (§1 table), including in-archive link
  resolution. The narrowings the first draft of this plan needed (in-archive
  symlink rejected, nested keys rejected) go away.
- The metadata tar is small (a few KiB-MiB) and real itself reads it fully
  into memory; one `Vec<(header, bytes)>` pass is the same shape.
- The decompressor stays a subprocess (`gpkg_compressions()` argv): its
  stdout is piped straight into `tar::Archive::new(stdout)` — no
  `<scratch>/metadata.tar` temp file, no second `tar` process.

Dependency cost, verified 2026-09-16 from the crate's `Cargo.toml`:
`filetime` + `libc` (both **already direct deps** of `portuale`), `xattr`
only behind the default feature. With `default-features = false` the crate
adds **zero new transitive crates**, pure Rust, no C linkage — the
musl-static goal is untouched. It is still a new direct dependency and
`binpkg.rs`'s module doc states the "shell out to `tar`" stance, so it needs
an owner-accepted waiver comment in `Cargo.toml` like `filetime`/`libc`
have (K0).

What stays on GNU `tar` after the owner's K2/K7 answers: **only the actual
unpacking of `image.tar`**, for its ownership/permission/xattr/sparse
semantics (`-xpf`) — and even there the members are validated in-process
first (K2). Everything else in `binpkg.rs`'s gpkg paths — the outer
container walk (K7, S5) and both inner metadata paths — is read through the
crate, so the file ends with one mechanism instead of two.

### S1 — the in-process reader (executor **F**, **F review**)

Executor is frontier here: it is the security-relevant port of tarfile's
link-resolution rules, and the new dependency's API choices (bytes vs
lossy paths, header vs PAX link names) are easy to get subtly wrong.

1. `rust/portuale/Cargo.toml`: `tar = { version = "0.4", default-features
   = false }` with a waiver comment in the file's existing style (why:
   #58, in-process inner metadata read; pure Rust; deps already present;
   `xattr` off). Update `rust/Cargo.lock`. Update the `binpkg.rs` module
   doc paragraph that says it shells out to `tar` (outer + image still do;
   the inner metadata tar does not).
2. New private helper in `binpkg.rs`, e.g.
   `fn read_inner_metadata(gpkg: &Path, member: &Path, comp:
   Option<&[&str]>) -> Result<Vec<(String, Vec<u8>)>, String>`:
   - open the member (already type-checked by #56) or spawn the
     decompressor with `Stdio::piped()` and feed its stdout to
     `tar::Archive::new`; check the child's exit status after the read
     (a decompressor failure is still an error, as today).
   - collect every entry in order as `(name_bytes, entry_type,
     link_name_bytes, data)`; read data only for regular / unknown-type
     entries; cap total bytes read (a bomb guard: e.g. 64 MiB, named
     constant, error if exceeded).
   - resolve per K1/K3/K4/K5: strip `metadata/` (else error), refuse
     absolute/`..`, resolve symlinks (whole archive, last match,
     normalized `dirname/linkname`) and hardlinks (earlier members only),
     recursion depth cap, error on unresolved/dir/FIFO/device.
   - return `(key, bytes)` in archive order with last-wins de-dup, plus a
     flag or a separate check for duplicates so S3 can refuse them.
3. Unit tests for the helper alone: build tars in-memory with
   `tar::Builder` + hand-set headers (no Manifest needed at this level)
   for every S0 cell i1-i12, asserting exactly the S0 real column
   (bytes for i2/i3, error for i1/i3b/i4/i5/i6/i8/i10/i12, `sub/KEY` for
   i7, last-wins for i11); a regular fixture-shaped tar round-trips

4. Workspace-root `cargo build/test/clippy --release`; not yet wired, so
   pytest is unaffected — run `pytest tests/ -k "gpkg or binpkg"` anyway.
5. F review of the diff (a second F pass, not the executor re-reading).

## 7. Done criteria

- No member of a gpkg — outer container, inner metadata, inner image — can
  make portuale read or write a host path, open a FIFO or create a device
  node, on the populate or the merge path. For metadata this holds by
  construction (nothing reaches the filesystem before it is resolved to
  regular bytes); for the image, by real's own `tar_safe_extract` rules
  applied before anything is unpacked.
- `read_gpkg_metadata` returns exactly what real `get_metadata()` returns
  for every S0 cell real accepts, and errors wherever real raises; the
  image pre-scan accepts exactly what real's `decompress()` accepts.
- Every archive real's writer can produce reads, verifies and merges
  byte-identically to before — committed fixture, cell i19 (symlinks,
  sparse, xattr), L2 both directions — and the musl static build still
  passes its smoke test.
- `binpkg.rs` has **one** tar mechanism: the crate reads every container,
  GNU `tar` only unpacks the image. #56's post-extraction helpers are gone
  and its test assertions still hold.
- Every remaining difference from real is named in #58's DONE text, or
  filed as its own backlog item.
