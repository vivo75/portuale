## 🔴 CRITICAL

### C1 — the USE-context fingerprint is lossy, and it is a memo *key*

`portage-profile/src/lib.rs:2529` `use_context_base_fingerprint`
hashes every ordered field with `hash_sampled` — length plus
first/middle/last element only. That digest is the identity
component of **five** memo keys:

- `EUF_CACHE` (`rust/portage-repo/src/lib.rs:3414`, key at `:3416`),
- `RUMF_CACHE` (`:3755`),
- `MKA_CACHE` (`:4555`, via `use_context_fingerprint` at `:3458`),
- `BRU_CACHE` (`:2850`),
- `IV_CACHE` (`:4722`, via `is_visible_base_fingerprint` at
  `portage-profile/src/lib.rs:2635`, which folds the same base in).

**Why it is a problem.** Two configs that differ only in
non-sampled positions — e.g. `package.use` entries differing at
position 50 with identical length/first/middle/last — produce the
*same key* and are served *each other's* USE flags and visibility
verdicts. That is silent wrong-resolution, not a missed memo.
The code's own justification (`lib.rs:3403-3410`: "impossible in
production (one config per process) and not hit by any test") is an
environmental hope, not a structural guarantee — and it already
failed once inside this same batch: the MKA key shipped without
accept-list hashing and collided on the crate's own masking unit
tests (admitted in the `d034557` commit message, fixed by adding
`accept_lists_fingerprint`). The single-config invariant is nowhere
enforced: `Config` fields are `pub`, tests routinely mutate configs
in place (`solver_bridge.rs:1598`), and hand-built configs
(`Config::default()`, struct literals) take the per-call sampled
fallback while sharing process-wide thread-local caches.

**How to fix.** Hash *exactly* at freeze time.
`use_context_base_fingerprint` runs **once** per `resolve_config`
(`portage-profile/src/lib.rs:3731`), so a full content hash there
costs ~zero per call while removing the collision class entirely.
Keep sampling — or go exact too, tests are not hot — only in the
`None`-base fallback. Optional belt-and-braces: a
`#[cfg(debug_assertions)]` exact-hash cross-check on memo hit in
tests.

### C2 — `local_binpkg_index` keys its memo on a raw `Vec` pointer

`rust/portage-repo/src/lib.rs:2340-2370`. `scanned_id` is
`(entries.as_ptr() as usize, len, first_CPV, last_CPV)`.

**Why it is a problem.** (a) **ABA**: `scanned_binpkgs` is a `pub`
field, and `pretend.rs:10874/:11301` already assigns it from two
sites. If it is ever *replaced* mid-process, a new `Vec` can reuse
the freed address with the same length and same first/last CPV but
different middle entries — and be served the stale
`Arc<BinaryIndex>`, i.e. wrong binary candidates. (b) In-place
element edits preserving length/first/last are invisible by
construction. "Correctness preserved by construction" (the `9c40b32`
message) holds only under a never-mutate/never-replace discipline
that nothing enforces.

**How to fix.** Change `Config::scanned_binpkgs` to
`Option<Rc<Vec<…>>>` (or `Arc`) and key on `Rc::ptr_eq` — O(1) and
sound against replacement. For in-place mutation, either freeze
(share `&` after the single set) or add a content version counter.
At minimum, document the freeze contract on the field itself, not
only in a commit message.

## 🟡 WARNING

### W1 — eight thread-local memos grow without bound and allocate on every hit

`EUF`/`RUMF`/`MKA`/`BRU`/`IV`/`AUX`/`CANDIDATES`/`BINPKG_CACHE` are
never cleared, shrunk, or generation-tagged. Fine for one-shot CLI
use; a slow leak for library, test-harness, or multi-resolve use —
MKA alone already cost +8 MB RSS (per the `d034557` message).
Worse, **key construction allocates on every call even on hits**:
`candidate_str.to_string()` (EUF `lib.rs:3422`, RUMF), plus
`value_str.to_string()` and a full accept-list rehash (MKA
`:4565-4571`). Fix: hash borrowed `&str` for lookup and materialise
owned keys only on miss; clear (or generation-tag) the caches
between resolves.

### W2 — `binpkg_respect_use_ok` builds O(n) hashers per call

`lib.rs:2866-2873`: the baked-USE xor-fold constructs a fresh
`DefaultHasher` (SipHash) **per element** of `binary_use`, on every
call, hit or miss — hundreds of hasher constructions per call to
save downstream rebuilds. Net-positive on the two measured
workloads, but it inverts if hit rates drop on other shapes (the
plan's own §4 names workload over-fitting as the standing risk).
Fix: fold all elements through a single hasher, or cache the set's
hash alongside it.

### W3 — `installed_candidates` invalidation is mtime-only, at the wrong granularity

`lib.rs:5995-6043` (`dir_mtime_nanos`, `CANDIDATES_CACHE`). (a)
**Granularity hole**: mutations landing inside one timestamp tick on
coarse filesystems are invisible — the plan itself documents
truncated mtimes on livecd squashfs for the analogous `aux_cache`.
(b) **Cross-cache mismatch**: this cache is validated by the
*category*-dir mtime while `AUX_CACHE` (`:6667`) is validated by the
*package*-dir mtime, and both cover `SLOT`. Utime-ing a package dir
(exactly what real's `_bump_mtime` does around `aux_update`)
invalidates one but not the other, so the two caches can disagree.
Fix: a process-local mutation sequence counter bumped by portuale's
own writers, or validate candidate rows against package-dir mtimes;
at minimum document that no in-place writer may exist.

### W4 — `BRU_CACHE` key omits `ebuild.repo_location`

`lib.rs:2874-2886` hashes the ebuild's
version/slot/sub-slot/repo-name/iuse/keywords/source — but the
uncached body reads `repo_aux_metadata(&ebuild.repo_location, …)`
via `candidate_iuse_and_use` (`:9220`). `repo_name` ⇒ location is
1:1 in production, but hand-built test candidates can share a repo
name with different locations and collide in the shared
thread-local cache. Fix: hash `repo_location` (one short string).

### W5 — `vdb_aux_get` fallback mutation leans on subtle `Rc` uniqueness

`lib.rs:6685-6699`: `drop(map)`, then `Rc::make_mut` through the
cache entry. Sound today — single-threaded, and the `Rc` never
escapes the function — but `make_mut` *silently clones* instead of
mutating if a future refactor holds a second strong ref, and the
insert then lands correctly only by accident of the `&mut` path.
Restructure to `get_mut` plus a plain `HashMap` insert, or comment
the uniqueness invariant. Same function has a stat→read TOCTOU: a
concurrent external writer replacing the dir between the validity
stat and the snapshot read serves one torn snapshot (self-heals on
the next call). Re-stat after the read and retry once on mtime
movement.

### W6 — out-of-set vdb keys fail open in release builds

`lib.rs:6635-6639`: the `environment.bz2` guard ("real would search
the saved environment for this key, which this helper does not
implement") is `debug_assert!` only. Every current caller was
audited (S1), but a future caller passing `CONTENTS`/`NEEDED.*` or
any key outside the 23-set silently gets `""` in release where real
searches. Make it structural: a key enum, or an
`in_metadata_file` early-return that falls back to the individual
file with a logged warning, so the invariant survives the next
contributor.

## 🔵 NOTE

- **N1 — S1 normalisation is intentional, real-grounded drift.**
  Collapsing multi-line vdb fields to `" ".join(split())` changes
  bytes exactly where old portuale diverged from real; pinned
  against real Portage 3.0.82.2 output (`bcc69fd`). No action.
- **N2 — SipHash on hot paths.** Every memo key uses
  `DefaultHasher`. Deterministic within a process (the passing
  fingerprint-equality tests prove it), but ~2–3× slower than
  `foldhash`/`fxhash` for short keys. The next cut if the W1/W2
  hit-path tax is ever trimmed.
- **N3 — candidate hits clone `(fps, out)` wholesale**
  (`lib.rs:6019` `get(&key).cloned()`); the `fps` clone is pure
  waste — compare by reference inside the `with` closure.
- **N4 — `Rc`-shared sets mortgage future parallelism.**
  Already inventoried in-tree (`cleanroom/parallelism.md`, updated
  by `54e265f`) — good hygiene, just noting each new `Rc` cache
  raises the eventual `Rc→Arc` migration cost. Prefer `Arc` for new
  memos.
- **N5 — process commendations.** S3 honestly reporting its own
  regression with `strace` numbers and ordering S4 immediately after
  (`6f158d7`); the `54e265f` final-review catch of the MKA
  `IUSE`/`KEYWORDS` omission (which is also the evidence that
  key-construction-by-audit needs structural backup — see C1);
  second-workload (`sys-devel/gcc`) spot checks against over-fitting;
  merge-path gates on the writer/reader slices.
