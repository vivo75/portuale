### S1 (#102) — cache `installed_candidates` per `(root, cat, pkg)`

**Where.** `portage-repo/src/lib.rs::installed_candidates` (`:5595`)
scans `var/db/pkg/<cat>` with `read_dir_entries` + `e.path().is_dir()`
(one `statx` per entry) and reads `SLOT` per matching dir, then applies
`installed_cp_sources` (`:760`) and `apply_updates_to_slot` (`:806`).
`installed_cp_sources` replays **every** `profiles/updates/` `move`
command through `apply_updates_to_cp` (`:749`) on every call.

**Cost.** 12,684 calls → 906,881 entries stat'ed, ~110 k `SLOT` reads,
6.05 M `apply_updates_to_cp` (each allocating two `String`s for the
`(cat, pkg)` key and cloning the destination). `perf`:
`binary_deps_changed` 10.7 % (the installed chain through
`libc_provider_cps` → `installed_versions` → `installed_candidates` →
`installed_cp_sources` → `apply_updates_to_cp` 5.2 %) plus direct
`installed_candidates` 4.5 % — ~15 % of the run on top of the syscall
side (~1.6 s of the 1.9 s sys).

**Design (recommended).** A process cache keyed by `(root, category,
package)`, validated by the **mtime of the category directories the
lookup scans** (`vdb_fingerprint`'s model, `:6327`, but only the 1–2
dirs `installed_cp_sources` names — not the whole vdb):

- `installed_candidates` computes `sources = installed_cp_sources(cat,
  pkg)`, stats `<vdb>/<src_cat>` for each, and only re-scans on an
  mtime change or a miss; negative results (no installed versions) are
  cached too.
- Every portuale vdb mutation replaces or removes a package dir
  (`ebuild_merge::write_vdb_entry_from_dir` `remove_dir_all` + `rename`,
  `ebuild_merge.rs:2387-2390`; unmerge removes the dir), so the category
  dir mtime catches all of them. An external in-place `SLOT` rewrite
  inside a running process is not caught — the same in-process-cache
  property real's `vardb` dbapi has; document it at the cache.
- Keep the return type `Vec<(String, String, String)>` (the vec is 1–2
  entries); return a clone of the cached vec.

**Cheap complements (same slice, measured separately):**

- `installed_cp_sources`: build the reverse map once
  (`move_chain_map()` already holds the resolved chains; invert it to
  `post-cp → Vec<pre-cp>`) instead of looping all ~477 moves per call.
  That alone removes the 6.05 M `apply_updates_to_cp` even on cache
  misses.
- `e.path().is_dir()` → `e.file_type()?.is_dir()` in the scan: uses the
  readdir `d_type`, no `statx` (falls back to `lstat` only on
  `DT_UNKNOWN`).

**Tests.** Rust unit tests: (a) a second call returns the cached result;
(b) adding/removing/replacing a vdb package dir invalidates (mtime
bump); (c) the move/`slotmove` chain still resolves through the cache
(the existing `apply_updates_to_cp` / `installed_candidates` tests stay
green). The merge-path read sites (`bind_slot_operator`,
`inject_libc_dep`) must be exercised: run the glibc+bash safety gate.
Contract suite must be byte-identical.

**Expected.** ~1.5–1.7 s sys + ~0.5–1.0 s user.

### S2 (#103) — `effective_use_flags` returns `Rc<HashSet<String>>`

**Where.** `effective_use_flags` (`:3178`) already stores
`Rc<HashSet<String>>` in `EUF_CACHE` but returns `hit.as_ref().clone()`
on the hit path (and the same clone after an insert). 71,572 calls /
70,237 hits × ~200 flags ≈ **14 M `String` clones** plus a fresh
hashbrown table each — the `HashSet<String>::clone` 2.46 % flat plus a
large share of the malloc/memmove/SipHash attributed to its callers
(`effective_use_flags`' whole subtree is 25.0 % of the run; the
fingerprint's ~8 % is #105's, the rest is this clone plus the 1,335
uncached builds).

**Design.** Return `Rc<HashSet<String>>` (the same shape
`read_md5_cache` / `list_candidates` already use with `Arc`). Audit the
~31 call sites (~15 production): almost all only read (`contains`,
`use_deps_satisfied(&…)`, iterate, `.clone()`). Where a wrapper needs an
owned set (`candidate_iuse_and_use`, `candidate_effective_use_flags`,
`use_flags_if_conditional`), return the `Rc` too or clone once at the
wrapper — never per EUF call. `Rc` is sound because the cache is
already `thread_local`.

**Tests.** The ~20 existing `effective_use_flags_*` unit tests pin the
semantics; no new fixture. Byte-identical output; re-measure.

**Expected.** ~0.8–1.2 s user.

### S3 (#104) — memoise `resolved_use_mask_or_force`

**Where.** `resolved_use_mask_or_force` (`:3602`), called twice per
`forced_or_masked_flags_unfiltered` (`:3677`): 29,774 calls, each
walking every `config.use_mask_force_levels` entry through
`apply_incremental_iter` (global sets) and `specificity_ordered_flags`
(`:3570`) → `config_entries_matching` (`:3025`) → `candidate_positions`
(`:2939`: `format!` + `Vec` clone + `sort_unstable` **per call**) and
`matches_config_entry`. 826,643 `config_entries_matching` and 658,411
`specificity_ordered_flags` calls; 23 % of the run sits under
`binpkg_respect_use_ok`, whose 9.9 % is `resolved_use_mask_or_force`.

**Design.** Memoise `resolved_use_mask_or_force` keyed by `(which,
stable, candidate_str, config fingerprint)` → `Rc<HashSet<String>>`,
thread-local, next to `EUF_CACHE`. Soundness: `use_mask_force_levels` is
built once at config resolution (`portage-profile/src/lib.rs:3373`) and
the `'backtrack` loop mutates only `autounmask_use`, which this function
never reads — the fingerprint is included for defence in depth (and S4
makes it cheap). Prefer memoising the whole
`forced_or_masked_flags_unfiltered` (13,433 calls) if the audit shows
the Force/Mask pair always used together. `candidate_positions`'s
`format!` can be removed in the same slice (key `by_cp` by
`(String, String)` or use a stack `cat/pkg` buffer) — the `format_inner`
was visible at 0.52 %.

**Tests.** The `effective_use_flags_applies_*` / forced-masked unit
tests; byte-identical output; re-measure.

**Expected.** ~0.5–0.9 s user (`resolved_use_mask_or_force`'s whole
subtree is 11.3 %).

### S4 (#108) — memoise `local_binpkg_index`

**Where.** `portage-repo/src/lib.rs::local_binpkg_index` (`:2272`), 3
callers (`has_local_binary_candidate`, `resolve_info_binary_candidate`,
`resolve_pretend`): 3,056 calls per resolve, 2.45 % of the run. Each
call clones `config.scanned_binpkgs` (or re-reads `config.pkgdir`'s
`Packages` index when `None`), appends any `--quickpkg-direct` entries,
and rebuilds the `by_cp` map in `BinaryIndex::from_entries` (`:2269`).

**Design.** Thread-local cache `Option<(Key, Arc<BinaryIndex>)>` keyed
by `(pkgdir, scanned identity, quickpkg root)`, mirroring
`cp_bucket_index`'s existing `(ptr, len)` + first/last fingerprint
(`:2988`): `scanned_binpkgs` is set once by the CLI layer
(`pretend.rs:10874/:11301`) before resolution and never mutated after,
and `quickpkg_direct_root()` is a set-once process global (`:2317`) —
so the key is stable within a run and any change rebuilds (correctness
preserved by construction). Return `Arc<BinaryIndex>`; audit the 3
callers for ownership needs. The `None` arm should go through the
existing `cached_binary_index(pkgdir)` (`:2254`) instead of re-reading
the file.

**Tests.** Existing binpkg unit tests + contract suite byte-identical; a
unit test that two calls share the `Arc` (ptr_eq) and that a changed
`scanned_binpkgs` rebuilds. Re-measure.

**Expected.** ~0.2 s.

## 3. Risks

- **S1 staleness in the merge path** — the one real risk. Mitigated by
  cat-dir mtimes + the glibc/bash safety gate + a unit test for
  invalidation; the in-place-`SLOT` hole is documented (no portuale
  write does it).
- **S2 API churn** — 31 call sites, mechanical but wide; keep the diff
  to the return type + `Rc::clone`/`unwrap_or_clone` where ownership is
  genuinely needed.
- **S3 key soundness** — the fingerprint covers the level structure; if
  a future config mutation adds a field to `use_mask_force_levels`
  mid-resolve, the memo must be keyed on it. Put the invariant in a doc
  comment on the cache.
- **Over-fitting the benchmark** — every slice re-measures the same
  workload; also spot-check a second shape (`sys-devel/gcc` or the
  `nano` probe from #83) so a memo that only helps one graph is visible.

## 4. What not to do (already measured/decided)

- FxHash for the memo maps: measured ~1 %, not worth it
  (`performances-tuning.md` "Parse cache — remaining options").
- Hand-written atom parser / `Rc<Atom>` parse cache: the regex is <1.5 %
  now.
- Skipping the second `run_pass` to win the benchmark: #107 is a
  **behaviour** question (real reports `backtrack: 0/20` on this
  workload while portuale's feedback loop restarts — the #68-family
  blocker divergence). Do not silence the pass; fix the trigger or leave
  it.
