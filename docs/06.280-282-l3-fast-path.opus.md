## S1 (#282) — tmpfs at `/var/tmp/portage`

The cheapest slice and independent of the others. Do it first.

**Where (all `../pmtest/differential-test-bed/`).** `run/l3-source-parity.sh`
(`run_pm()`, and the `L3_KEEP_TMP=1` doc line at `:17`),
`run/l3-source-parity-vm.sh:78` (the only current `L3_KEEP_TMP` consumer),
`compare/snapshot.sh:50` (already excludes `/var/tmp` — no change needed,
cite it in the report).

**The change.**

1. In `run_pm()`, add the tmpfs mount to the container invocation:
   `--tmpfs /var/tmp/portage:rw,exec,size=${L3_TMPFS_SIZE},mode=0775`.
   The `exec` is load-bearing: podman `--tmpfs` defaults to
   `noexec,nosuid,nodev`, and builds run configure scripts from
   `/var/tmp/portage`, so a bare `--tmpfs` breaks every build.
2. Knobs: `L3_TMPFS=1` (default on; `0` = back to disk) and `L3_TMPFS_SIZE`
   (size passed into the mount). The default for `L3_TMPFS_SIZE` is **not**
   fixed here: this slice must measure the peak `/var/tmp/portage` usage of
   the largest build (gcc) on the core list — an A/B wall-clock run on the
   CURRENT smoke list (disk vs tmpfs) plus one `L3_PM=portuale` core run for
   peak-size data — and set the default from that measurement (peak plus
   margin, recorded in the slice report with the raw peak number), so the
   default is grounded, not guessed. The knob exists because the owner's
   workstation RAM size is unknown.
3. Fix or drop the stale `L3_KEEP_TMP=1` doc line in
   `run/l3-source-parity.sh:17`: only the VM variant passes it on
   (`run/l3-source-parity-vm.sh:78`), and with a tmpfs it cannot work at
   all. Say which (fix or drop) in the slice report.

**Verification.** A/B wall-clock on the current smoke list, disk vs tmpfs
(report both numbers); one `L3_PM=portuale` core run for the peak-size data;
confirm the snapshot still excludes `/var/tmp` (no mount content in the
diff).

**Acceptance.** The tmpfs mount is in `run_pm()`, both knobs work
(`L3_TMPFS=0` reproduces today's disk behaviour), the size default cites the
measured gcc peak, and the `L3_KEEP_TMP` doc line is no longer stale.

**Stop conditions.** If the tmpfs run is not faster than disk, or the
measured peak does not fit a tmpfs this server (125 GB RAM) can hold while
building at `L3_JOBS=28`: **STOP and report** with the numbers — do not
enlarge the scope to lowering `L3_JOBS` (that is #261 territory).

## S2 (#281) — bake portage 3.0.82.2 into the test-bed image

**Where (all `../pmtest/differential-test-bed/`).** `create-container.bash`
(the image recipe), `run/lib.sh:45` (the `localhost/test-portuale:latest`
reference), `layers/l3/build-and-merge.sh` (`PIN`, `SKIP_UPGRADE` — read
only, no change), plus the sibling skip sites verified by grep below.
`vm/pins.sh` (`VM_PORTAGE_PIN`) is out of scope.

**How — recommended: a `buildah run` step before `buildah commit`.** The
recipe today unpacks the stage3 into WORKDIR and commits with `buildah
unshare` + `buildah commit`, running no emerge at build time. Adding one
`buildah run` that emerges the pin inside the working container keeps the
single-image lineage (no second image, no tag bookkeeping, no derived-layer
drift between the two) and matches the existing unpack-then-commit flow.
The alternative — a derived layer via `podman run` + `podman commit` —
splits the lineage and needs its own tagging/GC story; do not take it
without owner sign-off.

The bake command must be the oneshot form, so `@world` (and therefore every
L0 baseline) stays unchanged:

```
FEATURES="-cgroup" ACCEPT_KEYWORDS="~amd64" emerge -q -1 --usepkg=n =sys-apps/portage-3.0.82.2
```

(`scripts/00-install-portage.sh` uses a non-oneshot `emerge -tv` — do NOT
copy that form here.) Record the new image ID in the slice report.

**Caveats, stated up front.** Today in L3 portage is built after the
determinism block edits make.conf; baked, it is built with the image
defaults. That is the same on both sides, so parity is unaffected — but
`installed-before.txt` and the file baselines shift once; the slice report
must record that shift as expected. No layer script change is needed: every
layer already skips its own upgrade when the installed version equals the
pin — verify each by grep before claiming it:

```
layers/l0/in-container.sh:23,73
layers/l1/consume.sh:20,76
layers/l3/build-and-merge.sh  (PIN, SKIP_UPGRADE)
layers/l32/common.sh
layers/l2/build-*.sh
```

**Verification.** (a) The grep check above, recorded. (b) An L0 resolver run
and an L1 run show no change against their latest reports, by row name.
(c) An L3 smoke run logs no "upgrading portage" line.

**Acceptance.** Image contains 3.0.82.2 (no upgrade block fires in any
layer), L0/L1 unchanged by row name, new image ID recorded.

**Stop conditions / fallback.** If the `buildah run` step proves hard (image
build failures outside the existing recipe's shape): **STOP, report, and
hand the rebuild to the owner** — he explicitly offered to do it himself.
Do not redesign the image recipe in this slice.

## Not doing

- **Parallel containers.** The four L3 sides still run serially. Owner chose
  not to now: container-parallelism changes the beds' alone-on-the-bed
  isolation story and is its own design.
- **`emerge --jobs`.** Parallelising inside one emerge is a separate
  Portage-semantics question, not a harness-time lever. Owner chose not to
  now.
- **Cached reference sides.** Reusing a built reference across runs would
  trade the control pair's independence for speed. Owner chose not to now.
- **ccache.** It conflicts with the determinism block's `-ccache`: caching
  compilers would poison exactly the byte-parity the bed exists to check.
  Owner chose not to now.
