## S1 (#113) — read `PORTUALE_SHUFFLE_DIRS` once, not 42,524 times

**Where.** `rust/portage-util/src/lib.rs`, `pub fn shuffle_seed()`, and
its only caller `read_dir_entries` in the same file.

**What is wrong.** `shuffle_seed` does `std::env::var("PORTUALE_SHUFFLE_DIRS")`
on **every** directory read (42,524 per reference run) and allocates a
`String` each time, to parse a value that is test/CI-only and fixed for
the life of the process. It also keeps a live `std::env::var` read in
the hot path, which is the `set_var` race surface
[`cleanroom/parallelism.md`](cleanroom/parallelism.md) §1.6 names as a
blocker for any thread pool.

**What real does.** Nothing — this is portuale-only test scaffolding,
so there is no oracle to capture. This is the one slice in the batch
where "expected output = the pre-slice binary" is legitimate, because
the observable behaviour must not change at all.

**The change.** Cache the parse in a `OnceLock<Option<u64>>` read at
first use. This is the established env-free pattern in this tree —
copy the shape from `ebuild_phases.rs`'s `bin_dir` (`static BIN:
OnceLock<Option<PathBuf>>`), not from scratch:

```rust
pub fn shuffle_seed() -> Option<u64> {
    use std::sync::OnceLock;
    static SEED: OnceLock<Option<u64>> = OnceLock::new();
    *SEED.get_or_init(|| {
        std::env::var("PORTUALE_SHUFFLE_DIRS")
            .ok()?
            .trim()
            .parse()
            .ok()
    })
}
```

**The trap, and the reason this slice has a test.** Freezing the value
at first use means a **test that sets the variable after any directory
read has already happened silently gets the old answer**. Before
writing the code, find every place the variable is set:

```
cd /home/vivo/repo/PORTUALE && grep -rn "PORTUALE_SHUFFLE_DIRS" portuale/rust portuale/scripts pmtest/
```

If any of them sets it *per test* inside a process that has already
read a directory (rather than per subprocess / per CI job), **STOP and
report** — the freeze is then a behaviour change, not a memoisation,
and the owner decides.

**Tests.** One Rust unit test in `portage-util`: two consecutive
`shuffle_seed()` calls return the same value, and `read_dir_entries`
over a fixture directory is still sorted with the variable unset. Do
not add a pmtest pin — nothing observable changes.

**Verify.** Workspace-root `cargo fmt --check`, `cargo clippy --release
--all-targets`, `cargo test --release`; then the pmtest contract suite.

**Commit subject when asked:** `#113: read PORTUALE_SHUFFLE_DIRS once`.

## S2 (#116) — route the last two `SLOT` scans through the `portage-repo` seam

**Merge-path safety gate: YES.**

**Where.** Two production scans still read the file directly:

| File | Function | What it does with the value |
|---|---|---|
| `rust/portuale/src/pretend.rs` | `installed_cp_versions` | `read_to_string(dir.join("SLOT"))`, `.trim()`, `.split('/').next()` — keeps the **main slot only**, defaulting to `"0"` |
| `rust/portuale/src/ebuild_merge.rs` | `blockers_from_flat_deps` | `read_to_string(dir.join("SLOT"))`, `.trim()`, then `split_once('/')` into `(slot, sub_slot)`, sub-slot defaulting to the slot |

**Why it matters.** Both bypass `portage_repo::vdb_aux_get`, so they
(a) miss the consolidated `metadata` snapshot #109 added — each is a
separate `open`+`read` per installed package, 2088 of them on this host
— and (b) do **not** normalise a multi-line value the way real's
`_aux_get` does. `read_vdb_string` collapses a multi-line field to one
space-separated line; a bare `.trim()` does not. A vdb `SLOT` file with
a stray second line therefore parses differently in these two scans than
everywhere else in portuale.

**Do not** touch `rust/portuale/src/emerge_build.rs` or
`rust/portuale/src/emerge_getbinpkg.rs`: their direct reads are **test
assertions** and must stay direct, exactly so they can catch a seam that
lies. Same for the `std::fs::write(...join("SLOT"), ...)` calls — those
are fixture setup.

**The obstacle, and the shape of the fix.** `vdb_aux_get` is private and
takes `(root, category, package, version)`. Both scans have a directory
name (`pf`, e.g. `foo-bar-1.2.3-r1`) and no package name.
`portage-repo`'s own `strip_version_prefix` cannot help — it needs the
package name already. The bare-`pf` splitter that exists is
`pretend.rs`'s `split_pf`, whose own doc comment says it is
approximating a portage-repo helper it cannot reach.

So the slice is three moves, in this order:

1. **Move `split_pf` into `portage-repo` as `pub fn split_pf(dir_name:
   &str) -> Option<(String, String)>`**, with its unit tests. Leave a
   `use` in `pretend.rs` — do not keep a second copy. Verify the moved
   tests still pass before going on.
2. **Add `pub fn vdb_entry_slot(root: &Path, category: &str, pf: &str)
   -> String`** in `portage-repo`, next to `installed_refs`: split `pf`
   with `split_pf`, call `vdb_aux_get(root, category, &package,
   &version, "SLOT")`, return the normalised string **as-is** (the
   `"slot/sub_slot"` form, no splitting). A `pf` that does not split
   returns `String::new()`.
3. **Re-point both call sites at it**, each keeping its *current*
   post-processing verbatim — `pretend.rs` still takes
   `.split('/').next().unwrap_or("0")`, `ebuild_merge.rs` still does
   `split_once('/')` with the slot-as-sub-slot fallback. **This slice
   does not change either caller's defaulting.** Real's
   `aux_get` invalid-`SLOT` → `"0"` translation is a *separate* filed
   residue (#115); do not fold it in here.

**The one behavioural difference to check, not assume.** Going through
`vdb_aux_get` means a multi-line `SLOT` now collapses instead of
`trim`ming. Before you claim the slice is output-preserving, prove which
way that cuts:

```
# is there any such file on this host?
awk 'END{if (NR>1) print FILENAME}' /var/db/pkg/*/*/SLOT 2>/dev/null
```

Empty output means no live instance is affected and the change is
behaviour-preserving on real data. Non-empty output is a finding:
**STOP and report it** with the package names before changing anything.

**Tests.**
- Rust unit test in `portage-repo`: `vdb_entry_slot` on a fixture vdb
  entry returns the same string `vdb_aux_get` does, and a multi-line
  `SLOT` file collapses to one space-separated line (pin the *new*
  behaviour explicitly — it is the only semantic change).
- Rust unit test in `portage-repo`: an unsplittable `pf` returns `""`.
- Rust test for `blockers_from_flat_deps` over a two-entry fixture vdb
  where one entry has a sub-slot: the returned set is unchanged from
  before the slice (copy the expectation from the existing test, do not
  re-derive it).
- No pmtest pin. If a pmtest pin moves, that is the STOP condition.

**Verify.** The full pass, **plus the merge-path gate**: a successful
test merge of `sys-libs/glibc` and `app-shells/bash`. Record both in the
report.

**Commit subject when asked:** `#116: read SLOT through the portage-repo vdb seam`.
