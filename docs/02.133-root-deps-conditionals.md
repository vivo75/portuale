## 1. The defect, stated once

### What is wrong

`rust/portage-repo/src/lib.rs`, `fn root_deps_satisfied_atoms` (`lib.rs:12018`)
and `fn unsatisfied_root_deps_atoms` (`lib.rs:12089`) — the two producers
that split an installed package's `DEPEND`/`BDEPEND`/`IDEPEND` into
"already satisfied by the running root" vs "must be built against the
running root" — flatten the metadata **without evaluating the tokens'
conditional use-deps**, and every consumer compares against those raw-keyed
sets. #132's S5 evaluates each `enqueue_dependencies` token against the
parent's vdb USE but keeps the *raw* form for exactly these two membership
tests (`lib.rs:24882-24922`, with the workaround documented in the comment
at `:24873-24881`), because looking an evaluated token up in a raw-keyed set
silently stops matching. The asymmetry is portuale's, not real's.

### What real does

Real evaluates at every producer, inside `use_reduce` itself. With
`token_class=Atom` each token gets `token.evaluate_conditionals(uselist)`
during the parse loop, **before** any `||` branch selection
(`3rdparty/portage/lib/portage/dep/__init__.py:1045-1046`, inside the token
loop whose `stack[level].append(token)` follows at `:1048`;
`Atom.evaluate_conditionals` at `:2243`, the use-dep fold at `:2262`).
The flatten-atoms cache the walkers read is built the same way
(`3rdparty/portage/lib/_emerge/depgraph.py:2993-3011`: `use_reduce(...,
uselist=use, ..., flat=True, token_class=Atom)` over every `pkg._dep_keys`
entry). Everything downstream — the satisfied/unsatisfied split, the
build-entry resolution, the membership tests — therefore sees evaluated
atoms. There is no raw-keyed set anywhere in real's path.

Portuale's `use_reduce_flat_disjunctive` stays atom-agnostic **by design**
(`rust/portage-use-reduce/src/lib.rs:13,37,530`: no `token_class=Atom`,
no per-token `evaluate_conditionals` — the caller does both as a per-atom
post-pass). #132 added that post-pass to the token loop; the two producers
never got one. The fix is the missing post-pass, in one place (both
producers), plus re-keying each consumer to the evaluated form real holds.

### The three consumer sites (all must agree after S1)

1. The main New/Upgrade/Reinstall walk (`lib.rs:22955-23014`): filters its
   `flat_deps` tokens against both sets (`:23000-23001`) and resolves the
   unsatisfied half against the running root (`:23003-23015`).
2. The `--deep` recursion into an installed package
   (`enqueue_dependencies`, `lib.rs:24787-24922`): the two membership tests
   S5 pointed at `raw` (`:24908`, `:24914`).
3. `resolve_root_deps_build_entries`' own recursion (`lib.rs:12331`): walks
   the unsatisfied set's atoms directly — it inherits whatever keying the
   producer returns, so it needs no edit, only a re-read in review.

Open questions S1 answers before editing (named here so S1 does not guess):

- **Q1.** What keying does the main walk's `flat_deps` carry at `:23000`?
  `enqueue_flat_deps` already populates evaluated + unevaluated queue items
  (#132 §1), but the `:23000` filter runs on the pre-queue token list. If
  that list is raw, the filter must compare evaluated-to-evaluated — i.e.
  evaluate the token at the filter, mirroring S5's loop step — not just
  flip the sets and hope.
- **Q2.** The `||`-preference closures *inside* the two producers receive
  raw branch atoms (`atom_currently_satisfiable` / `running_root_satisfies_atom`
  over unevaluated tokens). Real evaluates before branch selection too
  (§1 above). S0's fixture uses a plain (non-`||`) conditional `BDEPEND`,
  which never consults the closure — so Q2 is out of S1's scope unless S0's
  real capture shows a `||` shape mattering. If it does, file it as a new
  number; do not widen S1.

### Blast radius, stated honestly

`--root-deps` only (plus genuine cross-root builds, which the fixture suite
never exercises): with `root_deps_running_root: None` both producers return
empty sets and every consumer is today's code path unchanged. Expected
direction: the evaluated split converges on real's — a conditional build
dep the running root cannot satisfy stops being silently dropped as
"satisfied" and starts becoming a running-root build entry (or vice versa
for the satisfied half). S0's real capture decides which direction is
toward real; nobody guesses it.

## 4. What this phase deliberately does not do

- It does not touch the `||`-preference closures inside the two producers
  (Q2). Their inputs stay raw unless S0's real capture forces the question,
  in which case that question gets its own number.
- It does not touch `enqueue_flat_deps`' own evaluation or
  `use_deps_satisfied`'s conditional semantics (#132 §5: correct for an
  unevaluated atom; the defect is an unevaluated atom arriving).
- It does not add a default-off gate (the standing position since #132 S3:
  a second resolver path nobody runs is not a fix).
- It does not re-open #132. That phase is `DONE` and live-verified; this
  phase changes the keying its S5 workaround was written against, which is
  exactly what the workaround's own comment said would happen.
