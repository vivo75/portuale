### S0.5 O10 ruling: NO walk-order change

Real produces the same plan in all six orders, and S0.3–S0.4 show
portuale's order-dependence is an emergent composition of three
walk-order-*agnostic* defects, each fixable without touching queue
order (traced with `--pretend --debug`; walk order itself is never
consumed by any of the three fix sites):

1. **Split conflict records.** `record_slot_conflict` merges only
   identical `(cp, slot, existing, current)` triples, so one
   three-version contention lands as two two-instance
   `SlotConflict`s (e.g. b/c/a: `(X-3,X-2)` + `(X-3,X-1)`).
   `direct_solve_slot_conflicts` solves each independently and the
   repoint loop applies both removals to the same row — the second
   finds no entry at its version and is silently dropped. b/c/a
   keeps X-2 (against B's bound) instead of X-1.
2. **Stale-owner blockers.** `resolve_blockers` looks the owner up
   by cp only and never checks the declaring instance is the merged
   one, so a walked-but-unmerged candidate's blocker (X-3's
   `!=Y-3`, X-2's `!=Y-2`) files against the merged entry. The
   uninstall target is whichever stale instance the walk visited,
   which is what varies with argv order.
3. **Placement.** The uninstall/blocks rows sort after every
   `[ebuild]` row instead of interleaving after their owner
   (merge-order scheduling; S0.2 placement rule).

Fixing (1) by joint-solving one merged record per `(cp, slot)`
converges to the uniquely jointly-satisfying version (X-1) from
*any* first-writer state; fixing (2) by gating on
`owner_version == merge_bound_version(owner entry)` drops
non-merged instances' blockers in *any* order. No slice in S1/S2
may reorder the walk or the top-level processing; a slice that
cannot converge without doing so STOPS (batch O10) instead of
reordering quietly. *Cost if wrong:* every multi-atom CASES entry
re-grounded.

## S2 rulings (landed during implementation)

- **R1 (F4 mechanism): `good_uninstalls`-only does not converge —
  port the full scheduling dance.** A bare "uninstalls first among
  ready leaves" rule reproduces both bedded blk0 cells but regresses
  the trusted B4/u6 pin (`blockerpkg` first). Tracing real's
  `_validate_blockers` + `_serialize_tasks` against live playground
  graph dumps shows why: the validation edge
  (`digraph.addnode(uninst_task, inst_task)`) keeps the blocker owner
  out of the leaf set until an empty round admits the removal (edges
  reversed), and only then does `good_uninstalls` fire. Portuale
  virtualizes the dance in `select_nodes` (no graph surgery, the
  frontier never sees an edge change): owners of live unadmitted
  merging-arm removals wait (filtered from every leaf set, the asap
  scan, the rung ladder, the cycle search and the last-resort roots);
  the first stuck round admits the first removal in graph order and
  resets round state; ready admitted removals pop first. The
  admission granularity (first-in-graph-order, not real's
  min-parent_deps) is the one documented approximation; single-
  removal runs are exact. *Cost if wrong:* uninstall rows schedule
  early in multi-blocker runs.
- **R2 (B4 + #91 ebuild orders): re-pin to the dance order,
  provisional pending bed cells.** Real's validation edge (proven in
  its own pre-serialization dumps: `children[blockerpkg] ∋
  uninstall`) makes the old pins' owner-first orders unreachable by
  real's own code — both encoded stale portuale convention (their
  oracles ground only the `b`-inline / `B`-tail / rc properties and
  the row sets, never the full ebuild order). The new orders come
  from the dance, and real's own unsolved playground run
  corroborates the u6 prefix (`partner, weak, gbp, blockerpkg`).
  Close-out adds three bed cells (`blockerpkg graphblockerparent`,
  the no-`FX_WORLD_EXTRA` `#91` shape, plus the four missing pg0
  orders) and any divergence from real there reopens the item
  instead of re-pinning. *Cost if wrong:* two pins assert an order
  real does not print.
- **R3 (keeper walk): blockers-only, no driver re-pass.** Feeding
  the solver's kept version back through the backtrack loop would
  walk the keeper's full deps, but it changes driver semantics at
  `--backtrack=0` for every shape, not just blk. The keeper's
  blockers (the only thing the blk oracle needs) are collected
  post-solve; a keeper merge dep stays the documented non-leaf
  staleness. *Cost if wrong:* a keeper with real merge deps drops
  them (filed as a follow-up if ever observed).
