## 2. Defects (fix these)

### D1 — #69 R2: `forced_or_masked_flags` filters to IUSE; real does not
**Severity: medium · Proven (live probed against real 3.0.82.2)**
**Files:** `rust/portage-repo/src/lib.rs:3678` (the `result.retain(|f|
iuse_names.contains(f))` line), called from `binpkg_respect_use_ok` at
`rust/portage-repo/src/lib.rs:2730-2737` (same-version-ebuild arm) and
`:2753-2760` (no-ebuild arm).

Real passes `forced_flags` to `_reinstall_for_flags` **unfiltered**:
`forced_flags = set(chain(myeb.use.force, myeb.use.mask))`
(`depgraph.py:8264`) or `set(chain(pkgsettings.useforce,
pkgsettings.usemask))` (`:8268-8270`), and `:3151` does
`flags -= forced_flags` over the IUSE symmetric difference.
`myeb.use.force/mask` come from `Package._use_class._init_force_mask`
→ `pkgsettings.useforce/usemask`, i.e. `config.setcpv`'s per-cpv
`getUseForce(cpv_slot)`/`getUseMask(cpv_slot)`
(`portage/package/ebuild/config.py:1973-1980`) — the profile's
`use.force`/`use.mask`/`package.use.force`/`package.use.mask` lists,
**without any intersection with the ebuild's IUSE**.

Portuale's `forced_or_masked_flags` ends with
`result.retain(|f| iuse_names.contains(f))` (`lib.rs:3678`), so a flag
the profile forces/masks but that the **ebuild's IUSE has since
dropped** is not subtracted and wrongly triggers a rebuild.

Corrected divergence shape (implementation follow-up, 2026-09-17):
binary 1.0 baked `USE="foo"` / `IUSE="foo removed"`; same-version ebuild 1.0
`IUSE="foo"` only (flag removed); profile `use.force`/`use.mask`
contains `removed`; `--newuse` (or respect-use) → real's
`_reinstall_for_flags` returns `None` (keeps the binary; probed live:
`depgraph._reinstall_for_flags(ctx,pkg,{"removed"},{"foo"},{"foo",
"removed"},{"foo"},{"foo"})` → `None`), while portuale's filtered set
does not contain `removed`, so the presence diff keeps it and the
binary is rejected → portuale schedules a rebuild real does not.

Correctness boundary: the subtraction only exempts the flag from the
**presence** term. If `removed` was enabled in the binary's baked USE,
real still rejects through `old_iuse ∩ old_use` versus `cur_iuse ∩ cur_use`.
The original report incorrectly described that enabled case as accepted;
the first test failed for precisely this reason. Do not change the
implementation to accept it. The corrected regression test covers the
disabled positive case and the enabled rejection control.

**Fix direction:** stop filtering by the *subtraction input's* IUSE —
either drop the `retain` at `lib.rs:3678` (it exists only to keep the
returned set inside the candidate's IUSE) or add an unfiltered variant
used by the two `binpkg_respect_use_ok` arms. Check other callers of
`forced_or_masked_flags` before changing shared behaviour; prefer the
new-variant route. Add the unit test described in G1.

**Related (likely, needs one bed cell to confirm):** in the no-ebuild
arm portuale uses per-candidate `package.use.force/mask` (it passes a
`cat/pkg-ver:slot::repo` candidate string) where real's `setcpv` uses
per-**cp** matching against the binary's own cpv — same thing — but
`forced_or_masked_flags`'s stability gate (`is_stable`, `lib.rs:3652`)
may drop repo/stable-level entries real's `getUseMask` keeps for the
`_pkg_str` fallback path (`UseManager.py:446-503`). If a cell with a
`>=cat/pkg-2` `package.use.mask` on an installed-only binary
diverges, fix granularity there; if it does not, record the check in
the findings and move on.

### D2 — #73/B2c: `owner_set_parent` consults the retry closure on every pass
**Severity: medium-likely · Source reading; no discriminating oracle**
**Files:** `rust/portage-repo/src/lib.rs:15163` (the nomerge arm ORs
`owner_set_parent(&pb.owner_key, blocker_retry_closure)`),
`lib.rs:14787-14792`, closure built at `lib.rs:17284-17339` from
`config.blocker_retry_seed_atoms` filled on **every** pass
(`pretend.rs:10977`).

Real's structure: `depends_on_order.add((parent, pkg))` is populated
in `_validate_blockers` (`depgraph.py:9204-9224`), and the digraph
parents test for a nomerge owner runs inside that loop — the
complete-mode **retry** (`:10365-10383`) only exists when an uninstall
task was actually selected (`have_uninstall_task and not complete and
not unsolvable_blockers`). Portuale now treats
`blocker_retry_closure.contains(owner)` as a permanent set-parent,
including passes where real would have no uninstall task and no retry.

Concretely: a cell-g shape (`installed owner` + merge-bound blocked
target, no uninstall resolved, owner in `@world`) — real refuses the
nomerge-arm action unless the run actually reaches the retry (real's
S0 cells all *did* select an uninstall or abort with `B`; the plan's
u4 is the retry shape). Portuale's unconditional closure can mark a
row `B`/rc 1 where real (stuck-free, no uninstall selected) would not.
All existing S0/S1 cells pass because their owners *are* in world/
system, so the wider closure changes nothing there; no current cell
discriminates "owner set-reachable but no uninstall happened".

**Fix direction:** gate the `owner_set_parent` term (and arguably the
target-side `blocker_retry_closure.contains(&target_key)` term at
`lib.rs:15141`) on the same condition real retries under — the
blocker resolved via an uninstall task (i.e. the row being classified
is `satisfied_by: Uninstall`-eligible / the run selected a removal).
This needs a real-Portage capture first (per plan §0.3): stage a cell
where a block resolves *without* any uninstall task while the owner is
in `@world`, then decide. If the capture shows real also keeps the row
`B` there, close as no-bug with the capture as evidence.

### D3 — #70 R1: `substitute` falls back to the process environment
**Severity: low (config-path divergence) · Proven by source comparison**
**Files:** `rust/portage-profile/src/lib.rs:1354-1358` (the
`std::env::var` fallback inside `substitute`).

Real's config expansion map is env.d + roots + previously-read files
only — `config.py`'s expand dict is explicitly documented "Notably
absent is 'env'" (`portage/package/ebuild/config.py:438-465`), and
`varexpand` leaves unknown names **literal** in that context
(`portage/util/__init__.py:1004-1005`). A `${HOME}` (or any ambient
env var) in `make.conf`/`make.globals` therefore resolves to the
caller's environment value in portuale and stays literal (or, for
`FETCHCOMMAND`'s varexpand path, expands from the passed dict only)
in real. Low severity because the R1 host matrix pins the six fetch
keys byte-identical (their variables come from the passed dict), but
it is a real parser-fidelity gap inside the function R1 claimed
byte-parity for.

**Fix direction:** remove the process-env fallback (or gate it to the
one call chain that documented needing it, if any exists — grep
`substitute(` callers first). Re-run the R1 capture matrix plus a
`PORTAGE_CONFIGROOT` probe with `${HOME}` in `make.conf` before/after.
