## 2. What is already known (pre-S0 reading, 2026-09-15)

**The backlog's pointer is off by one branch.** The incremental check
the entry cites (`lib.rs:~18268`) is not the slot check. The walker in
`rust/portage-repo/src/lib.rs` has two relevant spots:

1. `let Some(version) = resolved_version else { ... }` (~18213). An
   `AlreadyInstalled` (or `NoVisibleCandidate`) outcome takes this
   early branch, dedups on `state.other_outcomes` (cp only, ~18270),
   optionally walks its deps under `--deep`, and **never looks at
   `state.resolved_slots`**.
2. The slot check itself (~18637-18686): `state.resolved_slots.get(&slot_key)`
   → `match_from_list(current_atom, existing)` → `record_slot_conflict(build_slot_conflict(...))`.
   It runs only for `New`/`Upgrade`/`Downgrade`/`Reinstall`, and
   `resolved_slots` only ever **indexes** those four outcomes (~18880,
   and the `unreachable!` at ~18649 says so).

So an installed instance is invisible to slot tracking on both sides:

- argv `needer othermod`: needer's `>=2.0` → `Upgrade 2.0`, indexed;
  othermod's `<2.0` → `AlreadyInstalled 1.0` → branch 1, no check.
- argv `othermod needer`: othermod's `<2.0` → `AlreadyInstalled 1.0`,
  not indexed; needer's `>=2.0` → `Upgrade 2.0`, finds nothing in
  `resolved_slots`.

Local probe (`portuale emerge --pretend --debug`, fixture env, both argv
orders): the `--debug` digraph dump lists **both**
`(dev-libs/paired-1.0:0/0::testrepo, installed)` and
`(dev-libs/paired-2.0:0/0::testrepo, ebuild scheduled for merge)` as
runtime children, rc 0, no block. Portuale's graph already has two
packages in one slot; it just never records the conflict. (Side note
for S1: the same trace files `Parent Dep: ... required by othermod`
under the **2.0** child, which is wrong. Real would put othermod under
1.0.)

**This is the same gap as bug 614390.** The strict xfail
`test_oracle_slotop_complete` (`tests/test_emerge_pretend_contract.py`)
says: `meta`'s `=socc-1` lands on the already-scheduled slot "through the
already-installed fast path, which never consults `resolved_slots` --
real's `_add_pkg` slot-parent check ... turns that into a slot conflict".
A correct #57 fix may turn that xfail into an XPASS, which fails the
suite because it is `strict=True`. See K3.

**Real's mechanism** (`3rdparty/portage/lib/_emerge/depgraph.py`),
independent of `_complete_graph`:

- `_add_pkg` (~3550) adds every selected package, installed nomerge
  nodes included, to `_package_tracker`. A second package in the same
  `(root, slot_atom)` is a slot collision (~3764: "the notice needs to
  be called later").
- `_process_slot_conflicts` (~2108) → per slot, the parent atoms that
  don't match each instance (~2160-2185) → `conflict_pkgs` → with
  backtracking allowed, `_slot_confict_backtrack` (~2205) records
  `runtime_pkg_mask` choices.
- `_solve_non_slot_operator_slot_conflicts` (~1774) silently resolves
  conflicts where one instance satisfies every parent. **This matters:**
  an unversioned `dev-libs/paired` dep picking installed 1.0 plus a
  `>=2.0` dep elsewhere is a *solvable* collision, and real merges 2.0
  with no block. Portuale already gets that output today by accident
  (no check at all), so a naive check would regress it.
- When backtracking runs out (`backtrack: 4/20` here: the useful mask
  choices are used up well before the budget),
  `_show_slot_collision_notice` (~1712, called ~11120) renders the block,
  and the run exits 1.

**Open question for S0:** is real's final state exactly "the tracker
holds installed 1.0 plus merge 2.0, unsolvable, choices exhausted", or
does one of the 4 backtrack steps change what gets reported (for
example, masking ebuild `paired-1.0` so othermod falls back to the
installed instance)? The installed instance in real's block suggests a
mask happened. The S1 design depends on this answer.

### 3.1 K2/K3 — spiegazione per l'owner (IT)

L'owner non aveva capito le domande K2 e K3 come formulate sopra (in
inglese, con gergo interno). Ecco la stessa cosa in italiano, con
alternative e impatto. **Confermato dall'owner il 2026-09-16**:
alternativa A per entrambe (le stesse proposte originali).

**K2 — quando mostrare il nuovo avviso di conflitto**

Il nuovo controllo (S1) deve rilevare quando un pacchetto già installato
e una nuova versione da installare occupano lo stesso "slot" (posizione)
e sono richiesti da atomi (dipendenze dirette) incompatibili. La
domanda è: in quali casi mostrarlo?

- **Alternativa A (proposta originale)** — mostralo *solo* quando è
  **irrisolvibile**: nessuna delle due versioni (l'installata o quella
  da installare) soddisfa *tutte* le dipendenze dirette che la
  richiedono, in qualunque ordine i pacchetti siano indicati sulla riga
  di comando. Se invece una delle due versioni va bene per tutti (es.
  una dipendenza generica senza numero di versione), non si mostra
  nulla — esattamente come fa Portage reale in quel caso.
  **Impatto:** rischio basso. Copre solo gli scenari già verificati
  contro Portage reale (matrice S0); non introduce differenze mai
  testate.
- **Alternativa B — più ampia**: mostrare l'avviso anche in alcuni casi
  "risolvibili" (dove esiste già una versione che va bene per tutti).
  **Impatto:** nessuna cella dell'oracolo S0 copre questo scenario, per
  cui si rischierebbe di inventare un comportamento mai confrontato con
  Portage reale — cosa che le regole del progetto vietano esplicitamente
  (mai indovinare, sempre verificare).

**K3 — cosa fare del test che oggi "fallisce come previsto" (xfail)**

Esiste un test (`test_oracle_slotop_complete`, per il bug Gentoo
614390) che oggi è marcato come "ci si aspetta che fallisca" (xfail
*strict*: se invece passasse, la suite si romperebbe comunque, perché
un successo inatteso è trattato come un errore). La modifica S1
potrebbe farlo passare. Come gestirlo?

- **Alternativa A (proposta originale)** — se dopo S1 l'intero elenco
  dei pacchetti da installare combacia esattamente con quello di
  Portage reale: si rimuove il marcatore "fallimento atteso" e il test
  diventa una verifica normale, permanente, contro regressioni future.
  **Impatto:** un test in più che protegge il fix.
- **Alternativa B** — se dopo S1 il conflitto viene rilevato ma la
  scelta finale del pacchetto è ancora diversa da Portage reale: si
  aggiorna solo la spiegazione del "fallimento atteso" per descrivere
  il nuovo problema residuo, e il test resta xfail.
  **Impatto:** nessuna regressione nascosta; il gap residuo resta
  documentato e visibile invece di sparire silenziosamente.

La proposta originale sceglie automaticamente A o B **in base al
risultato reale di S1** (non è una scelta a priori). **Confermato
dall'owner 2026-09-16**: questa logica condizionale va bene.

### S1 — installed-instance slot tracking (executor F, commit `#57 S1: ...`)

Design below is the default. Adjust it to S0's answer, and record any
deviation in the commit message and findings.

1. **Index installed graph nodes by slot.** When the walker commits an
   `AlreadyInstalled { version }` for `(cat, pkg)`, record
   `(cat, pkg, slot) -> installed version` (slot from the vdb
   `InstalledRef`) in a new `state` map, or extend `resolved_slots`'
   value type. Keep the `unreachable!` invariant truthful either way:
   prefer a separate `installed_slots` map over a new outcome arm.
   Record the parent atom in `state.slot_pullers` exactly as merge
   outcomes do, so `build_slot_conflict`'s per-instance parents are
   right for both instances (this also fixes the `--debug`
   `Parent Dep` misfiling noted in §2 if the trace reads the same map;
   check, don't assume).
2. **Check both directions.**
   - Branch 1 (`AlreadyInstalled`): before the `other_outcomes` dedup,
     look up `resolved_slots` for the same slot. If a merge version is
     already graphed that does not satisfy `current_atom`, that is a
     collision.
   - The existing check (~18638): also consult `installed_slots`. A
     new merge version whose slot already holds an installed node that
     the new atom rejects is a collision.
3. **Solvable vs unsolvable (K2).** Before recording, apply real's
   `_solve_non_slot_operator_slot_conflicts` rule over the hard parent
   atoms known so far for that slot. If one graphed instance satisfies
   all of them, there is no record (today's silent output stays). Find
   out whether portuale already has this reconciliation for
   merge-vs-merge (`fixture_solvable_slot_conflict_is_reconciled_by_backtracking`)
   and **reuse it**; do not write a second solver. Because the walk is
   incremental, a later atom can make a recorded collision solvable or
   an unrecorded one unsolvable. Decide the collision on the final
   per-slot parent set (end of pass), not at first sight, if the
   existing machinery allows it.
4. **Record and render.** Build the `SlotConflict` with the installed
   instance marked `installed: true` (the renderer in
   `rust/portuale/src/pretend.rs` already prints `installed in '<root>'`
   and gates `(Argument)` parents on an installed other side). Feed it
   to the same backtrack loop as merge-vs-merge conflicts
   (`slot_conflict_mask_choices`) so the mask choices match S0 cell a.
   The final record must be byte-identical to real's block (cell a/c)
   once the comparator's normalisation is applied.
5. **No interplay regressions with #54.** `build_residual_slot_conflicts`
   keeps its reachable-dropped-pin input. If the keeper-reachable
   variant (`test_keeper_reachable_*` on the copied configroot) now
   produces the same `(package, merge version, installed version)`
   triple from both producers, dedup on that key (the residual builder
   already groups by it) so the block appears once, with real's parent
   union (`othermod` **and** keeper, #54 S0 keeper-in-world row).
6. **Pins.**
   - Rename + rewrite `test_needer_othermod_triangle_merges_cleanly_when_the_pin_is_unreachable`
     to `test_needer_othermod_triangle_reports_the_installed_instance_conflict`,
