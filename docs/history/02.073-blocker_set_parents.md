## 1. What real Portage does (source-grounded)

`_validate_blockers`' step 4 (`depgraph.py:9216-9246`): once
`depends_on_order` holds `(inst_pkg, inst_task)` pairs, real refuses to
uninstall any `inst_pkg` that is "a digraph node with parents":

```python
if not unresolved_blocks and depends_on_order:
    for inst_pkg, inst_task in depends_on_order:
        if self._dynamic_config.digraph.contains(inst_pkg) \
                and self._dynamic_config.digraph.parent_nodes(inst_pkg):
            unresolved_blocks = True
            break
```

Otherwise it adds an uninstall task with a hard edge before
`inst_task` (the `:9226-9246` block #72 models).

`_complete_graph` (`depgraph.py:8660-8745`) walks
`_initial_arg_list` plus the required sets appended as `SetArg`s
(`@world`/`@selected`/`@system`, `:8723-8731`), and `_expand_set_args(args,
add_to_digraph=True)` (`:3271-3347`) puts every `SetArg` node into the
digraph. Every installed package selected from those sets therefore has
at least one parent node -- the set arg (or, for a plain atom argument,
its `AtomArg`, which is likewise `dep.parent` of the selected package).

**Cell g** (the open shape): installed `bparent` (a `@world` member,
walked, not replaced), installed `blocked-1.0`, merge-bound `blocked-1.5`
matching `bparent`'s `!<dev-libs/blocked-2.0`. `blocked_initial` =
{blocked-1.0}, `blocked_final` = {blocked-1.5}; the parent operation is
`nomerge`, so real uninstall-orders the **owner**:
`depends_on_order.add((bparent, blocked-1.5))`. `bparent` is a digraph
node with the `@world` set as parent → `unresolved_blocks = True` → `B`,
rc 1.

Cell f (control, already matching): same shape without the merge-bound
match → `depends_on_order` empty → no row, rc 0.

## 2. Portuale today

`resolve_blockers` (`rust/portage-repo/src/lib.rs`, `fn
resolve_blockers`) computes the two parent-operation arms. The
nomerge-owner arm is:

```rust
} else {
    merge_bound_match
        && owner_entry.is_some_and(|e| {
            graph_has_parent(
                &pb.owner_key.0, &pb.owner_key.1,
                &pb.owner_version,
                e.slot.as_deref().unwrap_or_default(),
                e.sub_slot.as_deref().unwrap_or_default(),
                &pb.owner_key,
                entries,
            )
        })
};
```

`graph_has_parent` only scans walked entries' `deps`, so the `@world`
set parent is invisible and cell g stays `unsolvable = false` (no row,
rc 0).

The target arm already handles the mirror case: since #68 S3 it is
`graph_has_parent(target) || installed_closure.contains(&target_key)`
(`ResolveCtx::installed_closure`, computed for every resolve from
`complete_seed_atoms ∪ args ∪ config.system_packages` via
`required_set_reachable_cps`). The **owner** arm never consults it --
that asymmetry is this bug.

## 8. Risks

- **Over-counting parents.** `installed_closure` is a forward closure,
  so an owner merely reachable from a world member counts -- which is
  what real's `_complete_graph` does too, but g3 must confirm it. If g3
  shows no `B`, the predicate must be narrower than plain closure
  membership; stop and re-derive before S1.
- **Cell f flip.** The nomerge arm must keep dropping the
  installed-only match regardless of membership (real's step 1 `parent
  .installed` skip); the unit tests pin both.
- **Argv-order / dedup.** `resolve_blockers` iterates `pending` in
  discovery order; the new predicate must not change which owner the
  conflict is attributed to (one row per owner, as today).
