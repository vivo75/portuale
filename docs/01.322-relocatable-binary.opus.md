# #322 — relocatable binary and a real error for a missing build tree: implementation plan

Status: **proposed 2026-10-07.** Not started. Backlog entry: #322 in
[`backlog-tasks-2026-10.md`](backlog-tasks-2026-10.md) (Tier 1). Filed from
`docs/remote_emerge_examples.md` §3 (the container run that crashed).

## 0. Read this first

### 0.1 Goal

1. A binary run without the tree it was built in must **never abort**. It
   prints one error that says what is missing, why it is needed and what to
   do, and exits non-zero. No panic, no core dump, no backtrace.
2. Then the binary **runs anywhere**: the vendored phase runtime `bin/` is
   embedded in it, so a lone `portuale` file (a container, the `FROM scratch`
   musl image of hard goal 3) can run phases and remote merges.

### 0.2 Facts established 2026-10-07 (checked in the tree)

- The only production use of `env!("CARGO_MANIFEST_DIR")` is `repo_root()`
  (`ebuild_phases.rs:651`). It canonicalises `<manifest>/../../` at run time
  and `.expect()`s. Every other use is in a test.
- `repo_root()` has two callers: `bin_dir()` (`ebuild_phases.rs:703`, the
  vendored `bin/`) and `portage_checkout()` (`:669`, the optional
  `3rdparty/portage`, overridable by `$PORTUALE_PORTAGE_CHECKOUT`).
- **`portage_checkout()` panics too.** With `$PORTUALE_PORTAGE_CHECKOUT`
  unset it falls through to `repo_root()`, so a relocated binary also dies in `emerge --list-sets` / search set names
  (`pretend.rs:7062`), `ebuild … package` (`ebuild_package.rs:1312`) and
  every phase environment (`ebuild_phases.rs:3142`). The backlog entry only
  named `bin_dir()`; S1 covers both.
- `bin_dir()` production call sites: `run_one_phase` (`:3363`),
  `run_depend_phase` (`:3809`), `run_misc_functions` (`:4070`) and
  `remote_bundle::build_bundle` (`remote_bundle.rs:437`, copies it into each
  unit with `cp -a`). The rest are tests. `build_bundle` is reached only after
  the plan is printed and the client is contacted, which is why the crash came
  late.
- `[profile.release] panic = "abort"` (`rust/Cargo.toml:32`): any `expect` on
  this path ends in `Aborted (core dumped)`. S1 must remove the panic, not
  catch it.
- `bin/` is 70 files, 292 KB of content (486 KB on disk), 24 symlinks (all
  relative, same directory: `ewarn -> elog`, `newins`, `prepall`, `chown`), 38
  files with the exec bit. Modes and symlinks matter: `ebuild.sh` runs the
  helpers by name.
- `bin_dir()` today returns `&'static Path` and, when `3rdparty/portage/bin`
  exists, builds a symlink overlay in `$TMPDIR/portuale-bin.<pid>` removed by an
  `atexit` handler (backlog #88). The overlay exists so the non-vendored `.py`
  helpers fall through to the checkout. `ebuild.sh` never `realpath`s
  `PORTAGE_BIN_PATH` (doc comment on `bin_dir()`).
- No `build.rs` exists in `rust/portuale`. `Cargo.lock` has no `include_dir` /
  `rust-embed`; `tar` is a dependency already (`default-features = false`).
- `musl/Containerfile` copies `rust/` into the builder but **not `bin/`**
  (line 29). An embed through `../../bin` would break that build unless the
  Containerfile also copies `bin/`.
- Contract-suite and corpus: no `emerge` output changes in either slice, so no
  corpus bless. A failing contract test means a bug.

### 0.3 Decisions (re-open any of these, do not silently change them)

- **D1 — resolution order**, first hit wins:
  1. `$PORTUALE_BIN_DIR` if set and non-empty. It must contain `ebuild.sh`,
     else the error names the variable and the directory. An override that is
     set but wrong never falls through (a silent fallback hides a typo).
  2. The build tree's `bin/` if `<manifest>/../../bin/ebuild.sh` exists.
     Keeps every developer and bed flow byte-identical to today.
  3. The embedded copy (S2).
  4. Error (S1; after S2 only reachable when the embed is disabled).
  Moving the override from the entry's S2 to S1 is deliberate: S1 needs it to
  be testable end to end (see S1.4), and it is the "way out" the error offers.
- **D2 — the `3rdparty/portage` overlay stays as is.** `portage_checkout()`
  becomes `Option<PathBuf>` (env override, else the build tree's if it
  exists, else `None`). With `None` the `.py` helper phases degrade as they
  already do with no checkout. The embedded runtime does not include
  `lib/portage` (not embeddable: it is the Python package).
- **D3 — embed format:** a `build.rs` in `rust/portuale` walks `../../bin` and
  writes `$OUT_DIR/embedded_bin.rs`, a `static [(&str, Kind)]` table of
  `File { mode, include_bytes!(abs path) }`, `Dir`, `Symlink { target }`. No
  new crate. `cargo:rerun-if-changed=../../bin` (the directory, so a new file
  is seen). Extraction order: directories, files, symlinks.
- **D4 — extraction target:** one directory per process under
  `std::env::temp_dir()`, named `portuale-bin.<pid>` like the existing overlay
  (same `atexit` removal, same stale-sweep behaviour). Modes are set explicitly
  after writing (umask-proof). When the overlay is also needed (a checkout
  exists), it is built over the extracted copy exactly as it is built over
  `<repo>/bin` today.
- **D5 — fail early, not mid-plan.** Resolution runs once, at the gate stage
  of a real run (`run_remote_plan` top, `run_merge_plan` top), before any
  client contact or mutation. `--pretend` keeps working with no runtime unless
  it needs a phase (the `depend` phase on an md5-cache miss resolves lazily and
  reports the same error).

### 0.4 Branches, commits, verification

- Branch `backlog/322` in **both** repos (AGENTS.md "Two repos, one project");

- One step = one commit, titled as given, trailer

- V-std from `rust/`: `cargo fmt --check`, `cargo clippy --release
  --all-targets` (zero warnings), `cargo test --release`; the default build and
  `--features vdb-sqlite,vdb-redb`. The pmtest contract suite
  (`python3 -m pytest pytests-contract-suite -q` in `../pmtest`) compared by

- **`[gate]`** (merge-path safety gate): S2 changes which files the merge

- Container checks use `localhost/test-portuale:latest` with

### S1 — a real error, plus the override (D3)

- **S1.1 Resolver as a pure function.** New in `ebuild_phases.rs`:
  `resolve_bin_dir(override: Option<&str>, build_tree: Option<&Path>) ->
  Result<PathBuf, RuntimeMissing>` where `RuntimeMissing` carries what was
  tried. Pure, so unit tests need no process tricks. `build_tree()` returns
  `Option<PathBuf>`: `<manifest>/../..` canonicalised, `None` if it does not
  exist (no `expect`).
- **S1.2 `bin_dir()` returns `Result<&'static Path, String>`** (a
  `OnceLock<Result<PathBuf, String>>`), built from S1.1. Update the 7
  production call sites to propagate (`run_one_phase`, `run_depend_phase`,
  `run_misc_functions` already return `Result<_, String>` or an exit code;
  check each; `build_bundle` returns `Result<_, String>`). Tests that call
  `bin_dir()` unwrap it.
- **S1.3 `portage_checkout()` returns `Option<PathBuf>`** (D2). *As built
  it stays a `PathBuf`: with `repo_root()` no longer panicking a missing
  checkout is just a nonexistent path (see `evidence/322-s1.md`).* Update its 4
  users (`ebuild_package.rs:1312`, `ebuild_phases.rs:3142` and `:673`'s own
  overlay, `pretend.rs:7062`): `None` is "no checkout", same as a missing
  directory today. No behaviour change when the tree exists.
- **S1.4 The message.** One line to stderr, prefix `portuale:`, no
  backtrace. Proposed text (final wording is the implementer's, the three
  facts are required):
  `portuale: cannot find the phase runtime (bin/ebuild.sh): looked in
  $PORTUALE_BIN_DIR (unset) and <build tree>/bin (not present). Run from the
  tree this binary was built in, or point PORTUALE_BIN_DIR at a copy of the
  repository's bin/ directory.`
  Exit code: the applet's usual failure code (1), never 134.
- **S1.5 Gate (D5).** Call the resolver once at the top of `run_remote_plan`
  and `run_merge_plan` (and the `ebuild` real-phase entry), before the vdb
  shadow load, the ledger gate, any ssh and any write. A remote run must fail
  with the message and with **no** `portuale-remote:` line. *As built: on the
  resolve path the read-only client preflight has already run (it precedes
  the resolve); the gate still precedes every unit and every write.*
- **S1.6 Tests.**
  - Unit: `resolve_bin_dir` — override wins; override set to a directory
    without `ebuild.sh` is an error that names the variable (no fallthrough);
    build tree used when `ebuild.sh` exists; both absent is the error; empty
    override is unset.
  - Binary e2e (`std::process::Command` on the built binary, as the other
    e2e tests do): `PORTUALE_BIN_DIR=/nonexistent mrg --remote-transport=local
    --remote-binpkg=<fixture gpkg> …` exits 1, stderr contains the three facts,
    stdout/stderr contain neither `panicked` nor `stack backtrace`, and the
    local-transport ROOT is untouched (no unit dir, no ledger line).
  - Same for `ebuild … package` and `emerge --list-sets` with
    `PORTUALE_PORTAGE_CHECKOUT=/nonexistent` and no build tree reachable
    through the override: no panic.
- Done when: V-std green, contract suite equals baseline, and the P0 container
  repro now prints the one-line error and exits 1 for both commands, no core
  dump (`echo $?`, `dmesg`/`coredumpctl` quiet). Evidence
  `docs/evidence/322-s1.md`.
- Commit: `phase runtime: a missing bin/ is an error with a way out, not a panic (#322 S1)`

### S2 — embed `bin/` (D4 for the build script and extraction; D3 otherwise)

- **S2.1 `rust/portuale/build.rs`** (D3). Generates `embedded_bin.rs` per D3.
  Reads `../../bin` through `CARGO_MANIFEST_DIR`; prints

  build with a clear message if `bin/ebuild.sh` is missing. Unit-test the

## 2. Risks and what to check, not assume

- **Size and build time.** 292 KB of content embedded is small, but record the
  release size before and after (S2.4) and the incremental build time of
  `build.rs` (it reruns only when `bin/` changes).
- **Reproducible builds.** Sort the table; do not embed mtimes, absolute paths
  (use `include_bytes!` with a path relative to `OUT_DIR` built from
  `CARGO_MANIFEST_DIR` only at compile time, not stored as a string), or the
  build host's umask.
- **Staleness.** The embedded copy is a snapshot of `bin/` at build time. A
  developer editing `bin/*.sh` and re-running a *stale* binary from the tree
  gets the tree's copy (D1 step 2 wins), so the existing flow is unaffected;
  only a relocated binary uses the embed. `rerun-if-changed` keeps `cargo
  build` honest.
- **Two bin dirs in `$TMPDIR`.** The extraction and the `3rdparty/portage`
  overlay both use `portuale-bin.<pid>`. Build the overlay *in* the extracted
  directory's place, not next to it, and keep one `atexit` owner (the comment on `bin_dir()`
  explains why per-call-site removal rots).
- **`TMPDIR` mounted `noexec`.** `ebuild.sh` is run as `bash ebuild.sh` (read,
  not exec'd) but helpers are exec'd by name from `PATH`. A `noexec` temp dir
  would break them (assumed from how the helpers are named in `PATH`, not
  checked). Not solved here; the extraction error message must not hide it.
  Check how `portageq-wrapper` and `ebuild-helpers` are invoked before
  declaring it out of scope, and file a residue if it is real.
- **A set-but-wrong `PORTUALE_BIN_DIR`** is an error, never a fallthrough (D1).
- **Remote client.** The client needs no change: `build_bundle` already `cp
  -a`s whatever directory `bin_dir()` returned into each unit.
