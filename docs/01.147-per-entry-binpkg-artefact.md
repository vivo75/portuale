(a) `FEATURES=binpkg-multi-instance` from `package.env` for one
package. **The artefact PATH does not follow it.** Real allocates
the path once, run-wide: `portage/__init__.py:549-551`
(`create_trees` builds one `bintree` per root from the run-wide
`mysettings`), `dbapi/bintree.py:526-531` (the constructor binds

settings), single (`:2588-2606`, `<pkgdir>/<cpv>.tbz2`/`.gpkg.tar`)

`<pkgdir>/<cp>/<pf>-<build_id>.<suffix>`). The per-package
`setcpv` (`_emerge/EbuildBuild.py:76`) runs later, per task, and
cannot rebind the allocator. What the per-package token DOES do:

package-phase env when the package's own settings carry the token

`__dyn_package`).
(b) `BINPKG_COMPRESS` from `package.env`. **Split by format.**
`doebuild_environment` (`doebuild.py:381`, the function owning
`:697`) reads `binpkg_compression =
mysettings.get("BINPKG_COMPRESS", "bzip2")` from the package's own
`mysettings` (setcpv'd per package) and derives
`PORTAGE_COMPRESSION_COMMAND` from it. The xpak path compresses
through that env var (`bin/misc-functions.sh:593-596`, tar pipe) —
per-package honored. The gpkg path does not: `bin/gpkg-helper.py:49`
builds `portage.gpkg.gpkg(portage.settings, …)` on the global,
run-wide settings (no setcpv), and `gpkg.py:785` reads
`self.settings.get("BINPKG_COMPRESS", None)` from it — run-wide
only. (`config.py:2001-2047`: `setcpv` applies `package.env` via
`_grab_pkg_env`, so the scalar IS in the package's settings; the
gpkg helper just never looks at those settings.)
(c) Standalone `ebuild <file> package` and `package.env`.
**Yes.** `bin/ebuild:358-365` calls `tmpsettings.setcpv(pkg)`
("Apply package.env and repo-level settings… as soon as
possible") before dispatching every phase in `pargs`, `package`
included; the `package` phase then runs `doebuild` on the
setcpv'd settings (tmpfile + `bintree.inject(mycpv,
current_pkg_path=…)` at `doebuild.py:1485-1526`, whose
`getname(cpv, allocate_new=True)` is again the run-wide
allocator).

  `PORTAGE_COMPRESSION_COMMAND` into the entry `build_env`
  (`buildpkgonly_entry_build_env`, plus the merge/scheduler entry
  envs that feed a later `package_after_install` — the layer real

  `phase_compression_command` over the entry env (which already

  `matched_package_env_vars`): matched entry → its compressor,

  `invoke_dyn_package`'s gpkg env exports stay run-wide, and no

  real report zstd). `BINPKG_COMPRESS=""` (real `cat`) and
  unknown-codec behavior ride the existing
  `resolve_compression_command` semantics, pinned.

  at all — portuale's `package_env_key_allowed` rejects
  `ENVIRON_FILTER` keys from `package.env` matching, and
  `BINPKG_COMPRESS` is on that list. Real's `_grab_pkg_env`
  rejects only `protected_keys` ∪ `non_user_variables`
  (PROFILE_ONLY ∪ env_blacklist ∪ CONFIG_PROTECT) — S0's setcpv
  probe proves `BINPKG_COMPRESS='gzip'` lands in the package's
