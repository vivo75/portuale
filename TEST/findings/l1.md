# L1 findings — merge parity backlog

Triage of `TEST/run/l1-merge-from-binpkg.sh` output. Portage builds the
`atomlists/l1-merge.txt` set once; Portage and portuale each merge that
identical `$PKGDIR` into a fresh container; `diff.py` compares the two
`$ROOT` + VDB snapshots. Every unexplained hard finding is a portuale
merge-path bug (or a deliberate, allowlisted deviation).

**None are allowlisted** — they are portuale bugs, to be fixed on
`main`. `known-divergences.yaml` stays empty until a divergence is
adjudicated *not* a bug.

---

## L1-a. `--usepkgonly` (`-K`) doesn't treat an installed dep as satisfied  ·  HIGH · blocks `-K`

`portuale emerge -pK --oneshot app-misc/jq` (against a `$PKGDIR` with
`jq` + `oniguruma` binpkgs, `glibc`/`ncurses` installed but no binpkg):

```
!!! no visible ebuild for dependency "sys-libs/glibc"
!!! no visible ebuild for dependency "sys-libs/ncurses"
[binary  N     ] dev-libs/oniguruma-6.9.10-1
[binary  N     ] app-misc/jq-1.8.2-1
Total: 5 packages (5 new, 5 binaries)
```

The merge list is correct (5 binaries, matches real). But portuale
*also* emits the `!!! no visible ebuild` warnings, and in a **real
merge** (`emerge -K -1 …`, not `-p`) it puts `sys-libs/glibc` on the
resume list and fails: `emerge: sys-libs/glibc: no visible ebuild to
merge`, `merged 0 packages`.

Real portage: `--usepkgonly` restricts what may be *newly merged*, not
what counts as *already satisfied* — an installed dep is satisfied by
the vardb regardless. Real `emerge -pK -1 app-misc/jq` is silent and
merges only oniguruma + jq.

Portuale's `--usepkgonly` dep-satisfaction check consults only the
binpkg index, not the installed (vardb) set. `effective_use_flags` /
the `-p` resolve path already handle installed correctly (L0 firefox
resolved fine), so this is specific to the `--usepkgonly` filter in the
graph walk.

Workaround in L1: `consume.sh` uses `--usepkg` (ebuild fallback) instead
of `-K`, with a post-merge assertion that nothing was actually built
from source.

Next: grep portuale's `usepkgonly` / `--usepkgonly` handling in the
resolver for where a dependency's candidate set is built; it needs the
`AlreadyInstalled` branch to short-circuit before the "must have a
binpkg" filter.

## L1-b. local-`$PKGDIR` binary merge needs `--getbinpkg`  ·  MEDIUM

`portuale emerge -k --oneshot app-text/tree` (a `$PKGDIR` binpkg, no
binhost): resolves `[binary N] app-text/tree` but the merge aborts:

```
emerge: sys-apps/lsb-release-3.3: resolved to a binary package --
  pass `--getbinpkg` for a mixed source+binary merge, or
  `--getbinpkgonly` for binary-only
```

Real portage merges a local `$PKGDIR` binary on `-k` (or `-K`) alone --
`--getbinpkg` is only about *also* consulting a **remote** binhost.
portuale gates binary-merge *execution* on `--getbinpkg`/`--getbinpkgonly`
even for a purely local `$PKGDIR`.

Workaround in L1: both PMs run `-k --getbinpkg` (real portage accepts
the redundant flag -- with no binhost it is a no-op). Fixing this is
cheap: the merge-execution path should treat a resolved `Binary`
candidate whose source is the local `$PKGDIR` as mergeable under `-k`
without `--getbinpkg`.

## L1-c. vdb `environment` not refreshed on a binpkg merge  ·  MEDIUM

The vdb `environment` (decompressed) of every merged package differs
between the two PMs on two points:

1. **`FEATURES` / `PORTAGE_FEATURES`**: portage's stored value is the
   *merge-time* config (`consume.sh` sets `FEATURES="-buildpkg …"`, so
   no `buildpkg`); portuale's is the *binpkg's build-time* value (`…
   buildpkg …`). Real portage refreshes these when it writes the vdb
   entry for a binary merge; portuale stores the binpkg's
   `build-info/environment` verbatim.
2. **a stray `declare -- x=""`** in portuale's environment that
   portage's doesn't have — real `save-ebuild-env.sh` /
   `filter-bash-environment.py` strips such uninteresting locals;
   portuale's filter misses this one.

Normalised away in `normalize.py` (both `FEATURES=` lines dropped, and
this is the reason) so it does not drown the rest of the diff, but the
underlying behaviour should match real.

Next: real `_emerge/Binpkg.py` / `dblink.treewalk`'s environment
handling for a binary merge — which vars it refreshes vs takes from the
binpkg.

## First run — 5-package smoke set (`tree pv lsb-release oniguruma jq`)

2026-09-08, both PMs at portage 3.0.82.2, identical fresh containers,
same `$PKGDIR` (Portage-built). After the methodology + normalisation
fixes (see below): **5 hard findings, all one root cause (L1-c above),
allowlisted; 0 unexplained; 54 non-fatal mtime-only diffs** (different
merge wall-times). So: for this set, portuale's binpkg merge produces a
byte-identical `$ROOT` and a VDB that differs only in the tracked
`environment` refilter (L1-c) and mtimes.

Methodology / normalisation issues found and fixed along the way (not
portuale bugs):

- Both consumer containers must upgrade portage to the pin (with `-1`,
  or `world`/`COUNTER` drift) so the base `/` is identical -- the
  portuale consumer doesn't *use* 3.0.82.2 but its installed state must
  match the portage consumer's.
- `snapshot.sh` must compare `/var/db/pkg` via the `vdb.tar` only, and
  `--vdb-list` it to just the merged packages (else 320 base packages'
  metadata drowns the diff).
- `snapshot.sh --paths` must treat a CONTENTS `dir` line as stat-only
  (`-maxdepth 0`), not a recurse root -- CONTENTS records shared
  parents (`/usr/lib64`).
- `normalize.py`: blank `#dir_mtime=` in the `metadata` file; drop a
  directory's `st_size` (filesystem-internal, drifts with identical
  entries); drop `FEATURES=`/`PORTAGE_FEATURES=` from `environment`
  (merge-env vs build-env -- the standalone `FEATURES` vdb file is
  authoritative).
