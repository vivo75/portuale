## L1-a. `--usepkgonly` (`-K`) doesn't treat an installed dep as satisfied  ·  HIGH · blocks `-K` · FIXED

`portuale emerge -pK --oneshot app-misc/jq` (against a `$PKGDIR` with
`jq` + `oniguruma` binpkgs, `glibc`/`ncurses` installed but no binpkg):

```
!!! no visible ebuild for dependency "sys-libs/glibc"
!!! no visible ebuild for dependency "sys-libs/ncurses"
[binary  N     ] dev-libs/oniguruma-6.9.10-1
[binary  N     ] app-misc/jq-1.8.2-1
```

The merge list was correct (5 binaries), but portuale *also* emitted
the `!!! no visible ebuild` warnings, and in a **real merge**
(`emerge -K -1 …`) put `sys-libs/glibc` on the resume list and failed:
`emerge: sys-libs/glibc: no visible ebuild to merge`, `merged 0
packages`.

Real portage: `--usepkgonly` restricts what may be *newly merged*, not
what counts as *already satisfied* — real
`_select_pkg_highest_available_imp` falls back to
`_iter_match_pkgs(root_config, "installed", atom)` once the merge-
candidate search comes up empty.

**Fixed on `main`:** `resolve_pretend` (both `portage-repo/src/lib.rs`
and the `emerge_pretend_reference.py` mirror), at the point it would
return `NoVisibleCandidate`, now first checks `best_installed_for_atom`
— scoped to `!empty && !is_top_level && (usepkg || usepkgonly)`.
`--usepkgonly` empties the ebuild candidate pool wholesale, so this is
the case that needed it; a top-level atom still reports the missing
candidate, and `--emptytree` still forces the rebuild. New fixtures
`dev-libs/usepkgonlydeppkg` (a binary package RDEPENDing on the
installed-but-binpkg-less `dev-libs/samepkg`); Rust unit test
`usepkgonly_dependency_satisfied_by_an_installed_version_with_no_binpkg`
+ 2 contract CASES.

## L1-b. local-`$PKGDIR` binary merge needs `--getbinpkg`  ·  MEDIUM · FIXED

**Fixed on `main`:** `pretend.rs`'s non-`--pretend` merge dispatch now
routes to `emerge_getbinpkg::run_merge_plan` whenever any resolved entry
is a `Binary` (`getbinpkg || has_binary_entry`), not only under
`--getbinpkg`. `merge_one_binary_entry` prefers the on-disk `$PKGDIR`
file and only consults a binhost when it is absent, so a pure `-k`
local merge stays offline. Test:
`test_emerge_usepkg_merges_a_local_pkgdir_binary_without_getbinpkg`.

---


`portuale emerge -k --oneshot app-text/tree` (a `$PKGDIR` binpkg, no
binhost): resolves `[binary N] app-text/tree` but the merge aborts:

```
emerge: sys-apps/lsb-release-3.3: resolved to a binary package --
  pass `--getbinpkg` for a mixed source+binary merge, or
  `--getbinpkgonly` for binary-only
```

Real portage merges a local `$PKGDIR` binary on `-k` (or `-K`) alone --
`--getbinpkg` is only about *also* consulting a **remote** binhost.
portuale gates binary-merge *execution* on `--getbinpkg`/`--getbinpkgonly`
even for a purely local `$PKGDIR`.

Workaround in L1: both PMs run `-k --getbinpkg` (real portage accepts
the redundant flag -- with no binhost it is a no-op). Fixing this is
cheap: the merge-execution path should treat a resolved `Binary`
candidate whose source is the local `$PKGDIR` as mergeable under `-k`
without `--getbinpkg`.

## L1-d. `--getbinpkg` merge ignores env-var `INSTALL_MASK`  ·  MEDIUM · FIXED

**Fixed on `main`:** `config_install_mask` now prefers a non-empty
process-env `INSTALL_MASK` over the resolved make.conf/profile value
(real portage: `INSTALL_MASK` is `environ_whitelist` + non-incremental,
so the calling env's value overrides make.conf's). Covers both the
non-resume `--getbinpkg` merge and `--resume`. Test:
`test_getbinpkg_merge_honours_env_install_mask`.

---


`emerge INSTALL_MASK="…" -k --getbinpkg <pkg>`: portuale merges the
masked files anyway. Real portage folds `INSTALL_MASK` from the
environment into the config (whitelisted env var) and applies it.

`pretend.rs`'s non-`--resume` `--getbinpkg` merge does
`(merge_options.install_mask, …) = config_install_mask(&config)`
(pretend.rs:~10723), which reads only the resolved make.conf/profile
layer -- overwriting the value `MergeOptions::from_env` had already read
from the process env. Real portage uses both.

Fix: merge the env `INSTALL_MASK` into `config_install_mask`'s result
(or don't overwrite `from_env`'s value, append). `MergeOptions::from_env`
already reads it -- the source-merge and `--resume` paths just need the
config value ORed with it, not replacing it.

Workaround in L1: `consume.sh` writes `INSTALL_MASK` into
`/etc/portage/make.conf` instead of exporting it, so both PMs read it
via the config layer and the `porttest/installmask` fixture actually
exercises the mask logic.

## L1-e. `pkg_pretend` not run on a `-k` / `--getbinpkg` binary merge  ·  MEDIUM · FIXED

**Fixed on `main`:** `ebuild_merge::merge_binpkg` now runs a `pretend`
hook (via the existing `run_hook` -> `run_phase_from_saved_env`,
`DEFINED_PHASES`-gated) before `pkg_setup`, aborting the merge on a
non-zero exit. Matches portuale's own source path, which runs `pretend`
inline before each build. New committed fixture
`fixtures/pkgdir/dev-libs/binpkgpretendpkg-1.0.tbz2` + test
`merge_binpkg_runs_pkg_pretend_before_pkg_setup`; also verified
end-to-end by the L1 `porttest/phases` run (phase.log now byte-identical
to portage's). Allowlist entry `l1-pkg-pretend-skipped-on-binmerge`
removed.

Original finding: `emerge -k --getbinpkg --oneshot porttest/phases` (a
fixture whose every `pkg_*` phase appends a marker to
`/var/lib/porttest/phase.log`) had `setup preinst postinst` where
portage had `pretend setup preinst postinst` (241 vs 322 B). Real
`_emerge/Scheduler.py:_run_pkg_pretend` iterates the **whole**
`_mergelist` and runs `pkg_pretend` for every non-uninstall `Package`
with EAPI ≥ 4 that lists `pretend` in `DEFINED_PHASES`, `x.built` (a
binary package) explicitly supported — only the `SRC_URI` fetch is
guarded by `if not x.built`, and the colour switches to
`PKG_BINARY_MERGE` for the binary case.

## L1-c. vdb `environment` not refreshed on a binpkg merge  ·  MEDIUM · FIXED

The vdb `environment` (decompressed) of every merged package differed
between the two PMs on two points:

1. **`FEATURES` / `PORTAGE_FEATURES`**: portage's stored value is the
   *merge-time* config (`consume.sh` sets `FEATURES="-buildpkg …"`, so
   no `buildpkg`); portuale's was the *binpkg's build-time* value.
2. **a stray `declare -- x=""`** — real `save-ebuild-env.sh` /
   `filter-bash-environment.py` strips such uninteresting locals when it
   regenerates the vdb env; portuale stored the binpkg's
   `build-info/environment.bz2` verbatim and never regenerated it.

Real `vartree.py:5334` sets `PORTAGE_UPDATE_ENV = <dbpkgdir>/
environment.bz2` around the merge's `postinst` `EbuildPhase`;
`bin/phase-functions.sh`'s `prerm|postrm|preinst|postinst|config|info`
case then regenerates that file from the **live** phase environment
(`___save_and_filter_ebuild_env … --filter-path --filter-sandbox
--allow-extra-vars | bzip2 -9 > $PORTAGE_UPDATE_ENV`). Real runs the
`postinst` phase even with no `pkg_postinst`.

**Fixed on `main`** (three coordinated changes):

* `ebuild_merge::merge_binpkg` now runs the `postinst` hook
  **unconditionally** (whenever the binpkg carries `environment.bz2` +
  `<pf>.ebuild`), passing `PORTAGE_UPDATE_ENV = <vdb>/environment.bz2`
  and the resolved merge-time `FEATURES`.
  `run_phase_from_saved_env` gained `(update_env, refresh_features)`;
  `MergeOptions::features` carries the resolved list from the `emerge`
  paths (`from_env` keeps the raw `$FEATURES` fallback).
* `portage-profile`: **`FEATURES` is incremental, not scalar** — a
  process-env `FEATURES="-buildpkg -cgroup …"` now folds onto the
  profile + `make.conf` list (`apply_env_layer` calls
  `note_incremental` for it) so `resolved_incremental("FEATURES")`
  matches real. (A genuine bug independent of L1-c.)
* `bin/phase-functions.sh`: the brush-deadlock wrapper
  `___save_and_filter_ebuild_env` and its locals are renamed to the
  `___`-prefix, which `__filter_readonly_variables`' own `"___.*"`
  filter term strips — so `__save_ebuild_env`'s subshell no longer
  `declare -p`-dumps them.

Result: the vdb `environment` (`FEATURES`, `PORTAGE_FEATURES`, and the
`x` local) now byte-matches real across all 9 `porttest` fixtures. The
`l1-env-binpkg-not-refiltered` allowlist entry is removed; `normalize.py`
no longer drops `FEATURES=` lines.

## L1-f. binpkg phase env inherits the full process env  ·  LOW · FIXED

Surfaced while fixing L1-c: portuale spawned a phase (`run_one_phase_bash`
via `sandbox_wrapped_command`, and the embedded brush shell) with the
full inherited process environment; real `doebuild` builds a curated
`config.environ()` and never inherits wholesale. So `EMERGE_DEFAULT_OPTS`
(an `emerge` CLI option), a portuale-only `PORTAGE_RUNNING_ROOT`, and the
explicitly-exported `O` leaked into the regenerated vdb `environment`
where real's has nothing.

**Fixed on `main`:** `ebuild_phases::ENVIRON_WHITELIST` mirrors real's
`special_env_vars.environ_whitelist` (+ the `^(CCACHE_|DISTCC_)` regex).
`run_one_phase_bash` now `env_clear()`s and re-adds only whitelisted
calling-env vars before `phase_env_vars`; `phase_setup_script` (brush)
emits `unset` for the non-whitelisted ones. `phase_env_vars` also drops
`O` for a binary-merge phase (`MERGE_TYPE=binary`) — real never sets it
there. The vdb `environment` now byte-matches real except the
`LANG`/`LC_*` locale vars, which differ only because the two consumer
containers are invoked with different locale env (a test-harness
artefact) — `normalize.py` `ENV_DROP` still drops just those.

## First run — 5-package smoke set (`tree pv lsb-release oniguruma jq`)

2026-09-08, both PMs at portage 3.0.82.2, identical fresh containers,
same `$PKGDIR` (Portage-built). After the methodology + normalisation
fixes (see below): **5 hard findings, all one root cause (L1-c above),
allowlisted; 0 unexplained; 54 non-fatal mtime-only diffs** (different
merge wall-times). So: for this set, portuale's binpkg merge produces a
byte-identical `$ROOT` and a VDB that differs only in the tracked
`environment` refilter (L1-c) and mtimes.

Methodology / normalisation issues found and fixed along the way (not
portuale bugs):

- Both consumer containers must upgrade portage to the pin (with `-1`,
  or `world`/`COUNTER` drift) so the base `/` is identical -- the
  portuale consumer doesn't *use* 3.0.82.2 but its installed state must
  match the portage consumer's.
- `snapshot.sh` must compare `/var/db/pkg` via the `vdb.tar` only, and
  `--vdb-list` it to just the merged packages (else 320 base packages'
  metadata drowns the diff).
- `snapshot.sh --paths` must treat a CONTENTS `dir` line as stat-only
  (`-maxdepth 0`), not a recurse root -- CONTENTS records shared
  parents (`/usr/lib64`).
- `normalize.py`: blank `#dir_mtime=` in the `metadata` file; drop a
  directory's `st_size` (filesystem-internal, drifts with identical
  entries); drop `FEATURES=`/`PORTAGE_FEATURES=` from `environment`
  (merge-env vs build-env -- the standalone `FEATURES` vdb file is
  authoritative).

## `porttest` synthetic edge-case set (`atomlists/l1-porttest.txt`)

2026-09-08, both PMs at portage 3.0.82.2, identical fresh containers,
same Portage-built `$PKGDIR`. Nine `EAPI=8` fixtures, one merge-path
behaviour each (see `TEST/images/overlay/porttest/README.md`).

**All 9 fixtures byte-identical at the file level** -- 108/108 paths
match on mode (incl. `4711`/`2755`/`1750`/`0600`), owner, xattrs +
filecaps, sha256, symlink target (incl. the `symfarm` dangling +
chained links), unicode/space/metachar filenames, the `splitdebug`
`.debug` + `.build-id` objects, the `installmask` drops, the `emptydirs`
`.keep` markers. VDB `CONTENTS` / consolidated `metadata` / `NEEDED`
match for all 9.

First run: **10 hard findings** -- L1-c (`environment` refilter, ×9) and
the new **L1-e** (`pkg_pretend` not run on a binary merge), surfaced
precisely by the `porttest/phases` phase-marker fixture, which is what
it was built to catch. **After the L1-b/d/e fixes landed on `main`:**
re-run is **9 hard findings, all L1-c, 0 unexplained** -- the
`porttest/phases` phase.log now byte-matches portage's.

Harness fix made here: `snapshot.sh` silently aborted (under `set -o
pipefail`, no stderr, ERR trap in a pipeline subshell so it never fired)
when the walk hit `symfarm`'s dangling symlink -- `getfattr` without
`-h` dereferences and fails ENOENT. Now `getfattr -h` (correct anyway --
we record the link node, not its target) plus `set -e`-safe
`stat`/`readlink`/`getfattr` and a tolerant walk pipeline. This had been
masking the *entire* VDB comparison for the porttest set (files.tsv +
mtimes.tsv were written, but the `.vdb.tar` and `.meta.tsv` were not).
