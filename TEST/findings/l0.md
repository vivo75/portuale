## L. installed dep lacks a `[flag]` use-dep → not autounmasked/reinstalled  ·  HIGH · many probes · **FIXED**

Root cause shared by the `nginx` exit finding, most of E, all of G, and
part of F/`kdecore-meta`/`gnome-shell`. A dependency atom `foo[bar]`
where `foo` is **installed without `bar`**: real portage reinstalls
`foo` with `bar` and, since `bar` needs `package.use`, autounmasks it
(`[ebuild R] … bar*`, exit 1, the `nghttp2`/… that `bar` pulls appear).
portuale treated the installed `foo` as satisfying `foo[bar]` and
returned `AlreadyInstalled` → exit 0, subtree missing.

**Fixed** (`e17c6e9` + follow-up): `resolve_pretend`'s
`candidate_is_installed(best)` branch forces a `Reinstall` (not
`AlreadyInstalled`) when the atom's `[flag]` use-deps aren't satisfied
by the installed **vdb-recorded** USE -- so the graph layer's own
child-flip block routes the entry, records an autounmask change *only*
when the resolved candidate's *effective* USE also can't satisfy it
(`mime-types[nginx]` -> rc 1), and otherwise just reinstalls
(`systemd[policykit]` -- `policykit` is a global flag `systemd`'s ebuild
now defaults on -> `[ebuild R] … policykit*`, rc 0). The first cut
checked the effective USE, which wrongly suppressed the reinstall for
those global-flag cases. Dual-language, fixture
`dev-libs/flipinstconsumer` + 2 contract CASES. Verified in the L0
container: `www-servers/nginx` `rc 0->1`; `sys-auth/polkit` /
`dev-lang/rust` (E) / `net-misc/networkmanager` (G) all now match real
exactly (24/15/67 packages).

The `:=` slot-op turned out not to strip the `[flag]`
(`net-misc/curl:=[http2,ssl]` parses with `use_deps` intact), and the
already-resolved-`other_outcomes` case did not actually apply here --
`curl`/`systemd` are reached first by their own `[flag]` atom.

## I. Merge order  ·  KNOWN-HARD · ~40 probes  ·  **root-caused 2026-09-09**

First-divergence position varies (`#0`–`#5`). Same package **set**, same
USE, same versions — only the merge **order** differs.

**Root cause (traced on `sys-apps/dbus`, 12-pkg tree).** Real
`emerge -p --debug`'s `digraph:` dump shows every installed nomerge node
(pulled in as a build/run dep of a merge-bound package, plus the whole
`@system` set) carries its **full recorded vdb dependency tree**,
recursively. Portuale's `merge_order::build_digraph` gives those same
installed nodes `(no children)` — it truncates them at depth 1.

moment it becomes a leaf (no unmerged children). In real, `x11-libs/
xtrans`'s build deps (`elt-patches`→`gentoo-functions`, `pkgconfig`→

becomes a leaf first and merges first. In portuale both `elt-patches`
and `meson` are `(no children)` → instant leaves → `xtrans` and
`xorg-proto` become leaves together → `_merge_order_bias` orders them by
parent count (`xorg-proto` 9 > `xtrans` 4) → `xorg-proto` first. Real:
`xtrans, xcb-proto, xorg-proto`; portuale: `xorg-proto, xtrans,
xcb-proto`. Positions 3+ already match exactly.

## R3c attempt — satisfied-at-add edge drop: STOPPED (2026-09-15, wave 6)

  merge-bound child. gedit's nghttp2 edge disappears (its merge-list

## R3c revalidation — F-B4 is an aborted re-walk, not "initially satisfied → no edge" (2026-09-15)

**The stop was right, its diagnosis was wrong.** Neither "carry the
insertion instant per entry" nor merging R3c into R3d would fix gedit,
because real's mechanism is different:

1. `nghttp2`'s `>=sys-apps/systemd-209` does resolve to the *installed*
   systemd at add time (`Child: … systemd-260.1-r2-1 … installed`), and
   polkit's `sys-apps/systemd:0=[policykit]` later adds the merge in
   the same slot (`Slot Conflict:`).
2. After `_complete_graph`,
   `_solve_non_slot_operator_slot_conflicts` (`depgraph.py:1774-2100`)
   keeps the merge, `_remove_pkg`s the installed node (which drops
   **all** its in-edges and orphaned children), and pushes
   `broken_packages` (the removed node's parents plus the kept package)
   onto `_dep_stack` for a `_create_graph()` re-walk that re-creates
   each parent's edge, now pointing at the merge node.
3. In gedit that re-walk **returns 0 at `gnome-base/gnome-keyring`**:
   `>=app-crypt/gcr-3.27.90:0=[gtk]` is unsatisfiable (the same
   autounmask problem the probe ends with, rc 1). `_create_graph` stops,
   the solver ignores the return value, and every broken parent still on
   the stack is never re-walked: `nghttp2`, `sys-libs/pam`,
   `sys-apps/shadow`, `sys-auth/pambase` and `virtual/service-manager`
   lose their systemd edge, while the parents walked earlier (`gvfs`,
   `gcr`, `p11-kit`, `dbus`, `util-linux`, `procps`, …) get it back.
   Real's final digraph confirms both halves: `gvfs → systemd (merge)
   (buildtime_slot_op)` present, `nghttp2 → virtual/pkgconfig` only.
   nautilus is the identical shape (same removal, same abort at
   gnome-keyring's `gcr[gtk]`). Which parents survive is the order in
   which `list(set_of_Package)` comes off a LIFO stack, i.e. CPython
   string-hash and set-table order under `PYTHONHASHSEED=0`.
4. When the re-walk completes, real **redirects** the in-edges instead

## #53 S1 — root cause: `alt_suppressed` re-derives the `||` branch instead
of trusting the resolver's own choice (2026-09-15)

**H1 confirmed, H2 ruled out.** `PORTUALE_DEBUG_MERGE_GRAPH=1` on the S0
failing fixture dumps the actual scheduling digraph:

    (dev-lang/mogo-1.26:0/1.26::testrepo, ebuild scheduled for merge) depends on
      (dev-lang/mogo-1.26:0/1.26::testrepo, ebuild scheduled for merge) (buildtime)
      (dev-lang/mogoboot-1.24:0/1.24::testrepo, ebuild scheduled for merge) (runtime)

`mogo` carries a genuine **`mogo -> mogo` buildtime self-edge** (H1's
predicted smoking gun), and its edge to `mogoboot` -- the branch the
*actual resolver* chose (`b5b256f`, L0 finding D: "fresh resolve must
pick bootstrap") -- has been demoted to a weak `runtime` fallback edge
instead of the real `buildtime` one.

**Mechanism**, `rust/portage-repo/src/merge_order.rs` `build_digraph`'s
`alt_suppressed` computation (~1442-1500, pre-fix): for each `||` group
this is a **second, independent** re-derivation of "which branch wins",
run purely for scheduling/edge purposes, using the same `all_graph` >
`all_inst` > `all_any` preference order as real `dep_zapdeps`/
`atoms_all_in_graph` -- but with no knowledge of the resolver's own
`circular_self` exclusion (`b5b256f`, lib.rs's `resolve_pretend`/
`enqueue_dependencies`). For `mogo`'s own BDEPEND `|| ( >=mogo-1.24
>=mogoboot-1.24 )`: branch 0's atom `>=dev-lang/mogo-1.24` resolves via
`cp_indices` straight back to `mogo`'s **own entry** (the only
`dev-lang/mogo` graph node is itself), which trivially counts as
`graph_m = true` -- so branch 0 (written first) wins `all_graph` over
branch 1 (`mogoboot`, also `all_graph`-true, but never reached: `pick`
takes the first `true` by ascending branch number). Branch 1 is
suppressed, dropping the real `mogo -> mogoboot` forward edge; the
`required_by` fallback loop (~1671-1703) re-adds it anyway, but at a
blanket `runtime` priority (that loop has no per-edge key information),
and the suppressed self-branch (edge 0) survives into the "Edges" loop
where the self-edge special case (`depgraph.py:3765-3770`, kept only for
an *unsatisfied build-time* self-dep) keeps it: `sat = satisfied(edge,
Some(mogo))` is `false` (mogo isn't installed), so `i == j &&
!(buildtime && !sat)` is `false` -- the self-edge is **added**, not
dropped.

**Why this misorders instead of erroring**: real's *actual* dependency
resolution (`dep_zapdeps`, run once, feeding both the merge decision and
the scheduling graph) picks the self branch too, and then aborts with
the literal `* Error: circular dependencies:` self-loop shown in the
live #48 evidence -- real never reaches `_serialize_tasks` on this
shape. Portuale's resolver (`resolve_pretend`/`enqueue_dependencies`)
deliberately special-cases exactly this pattern to avoid that abort
(`b5b256f`) and picks bootstrap, producing a *valid* graph -- but
`merge_order.rs`'s `alt_suppressed` never learns which branch that was
and mechanically re-derives its own, inconsistent answer.

**Why `mogo` lands after `md2man`/`moconmon`/`mocommon` specifically**
(`PORTUALE_MO_SEL=1` trace, `select_nodes`):

    MO_SEL iter=1 ... pick=m:app-misc/mounzip-6.0 m:dev-lang/mogoboot-1.24
    MO_SEL iter=3 ... drop_satisfied=1 pick=m:dev-go/momd2man-2.0
    MO_SEL iter=4 ... drop_satisfied=0 pick=m:app-misc/moconmon-2.1 m:app-misc/mocommon-0.64
    MO_SEL iter=6 ... drop_satisfied=1 pick=m:dev-lang/mogo-1.26
    MO_SEL iter=7 ... pick=m:app-misc/mopodman-5.8

`Digraph::is_leaf`/`child_nodes` (merge_order.rs ~522-537) apply the
`ignore_priority` filter uniformly, with **no self-edge exclusion**: a
plain unsatisfied `buildtime` priority is never dropped by any rung
(including the widest `DepPrioritySatisfiedRange.ignore_medium`), so
`mogo` never satisfies `is_leaf` at *any* ignore level and never enters
`find_smallest_cycle`'s `mergeable` set. `md2man`'s edge to `mogo` is
`buildtime_slot_op`, which *is* droppable at the widest rung -- so once
`unzip`/`mogoboot` (true leaves) are gone, `md2man` becomes `mergeable`
and `find_smallest_cycle` releases it (a size-1 `gather_deps` closure,
confirmed by `--debug`: no `runtime cycle digraph` line at all, since
`sub.len() == 1` never triggers that dump); `moconmon`/`mocommon` then
become literal leaves once `md2man` is gone (iter 4, strict rung, no
relaxation needed). By iter 6 only `{mopodman, mogo}` remain and `mogo`
*still* never satisfies `is_leaf` at any level (its self-edge is
permanent) -- so it is picked only by `select_nodes`' absolute last
resort (~2440-2448, `.or_else(|| g.order.iter().copied().find(|&i|
g.alive[i]))`, "fall back to plain bias order when even [the widest
filter] finds nothing"), landing it *after* every package whose edge to
it could legitimately relax.

**Fix (G1(a) chosen, see below)**: `alt_suppressed`'s branch-preference
loop must not let a `||` alternative count as "in graph" via a match
against the **owning entry's own index**, the same `circular_self`
carve-out `b5b256f` already applies to the actual resolve -- so the
independent re-derivation agrees with the resolver's real choice instead
of re-discovering (and losing) it. Minimal, localized: guard the inner
`for &j in idxs` loop in `alt_suppressed` (merge_order.rs ~1469) with
`if j == i && !g.installed[j] { continue; }` (`i` = the owning entry's
own index, added via `.enumerate()`). Does not touch `atoms_all_in_graph`
(lib.rs) or the resolver's own `circular_self` check -- this is a
second, independent occurrence of the same class of bug, in a different
function, not a shared root cause.

**G1 decision**: option (a) (ordering consistency, keep portuale's
bootstrap resolution, fix the merge-list inconsistency) -- not (b) (full
parity, matching real's circular-dependency abort), per the plan's own
default and rationale (reopening finding D's `b5b256f` fix is a
separate, larger change). No blocking question for the owner: the fix
is a straightforward consistency bug, not a design choice.
