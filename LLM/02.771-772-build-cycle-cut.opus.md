## 0. Premise and what grounding found

### 0.1 Where the code is (read)

- Only `mrg --plan-world --sort depend` reaches this code: `plan_world.rs:69` → `World::build_plan` (`crates/portage-world/src/bootstrap.rs:75-87`) → `World::ordered` (`crates/portage-world/src/order.rs:45-69`) → `depend_order` (`order.rs:100-114`). `emerge` never does (02.764 §0.1; inside `portuale` only `plan_world.rs` and `check_world.rs` use `portage-world`, and `check_world.rs` uses no cycle, bootstrap or `Order` API). Consumers of `--sort depend`: pmtest `test_plan_world.py` (`:25`, `:42-54`, `:81`, `:224`, `:358`), `test_health_checker.py:1189`, `:1242`, the l0-health bed (`differential-test-bed/layers/l0-health/in-container.sh:64`, `FAST_world`; `compare/health-report.py` reads `FAST_world.json`, never `FAST_world.stderr`), and 17 Rust call sites (`grep -rn '"--sort", "depend"' crates`).
- `depend_order` loops `runtime_cut` (`order.rs:190-226`), removing one edge per pass, then orders the rest with `unordered` (`order.rs:118-145`), a name-ordered DFS that breaks any remaining cycle at whatever back edge it meets.
- `cycle_cut` (`order.rs:234-249`) returns the first edge of the closed cycle for which `is_cuttable_runtime_edge` holds (`order.rs:179-185`: runtime-only AND its source is not in `build_time_used`, `order.rs:168-175`). With none it returns `None`; `runtime_cut` goes on, and the cycle stays in `working`.
- `build_time_cycles` (`order.rs:255-339`, doc `:251-254`) is a Tarjan SCC over **build-kind edges only** (an edge without a kind counts as build). It is called only from `bootstrap.rs:77` (`build_plan`, into `BuildPlan.cycles`, which `plan_world.rs:70-85` prints as `plan-world: build cycle with no serial order: … (no order satisfies it; disable a USE flag …[; bootstrap with USE="-f" node temporary — …])`) and `bootstrap.rs:201` (`select`, the #753 bootstrap choice). Members come out in Tarjan discovery order (`:288-304` push, `:316-325` pop and reverse), which is **not a path**: `plan_world.rs:71-72` joins them with ` -> ` and closes with the first member. Proven on data by the review: the host line's `dev-lang/python:3.15 -> sys-fs/cryptsetup:0` is not an edge of any kind.
- Edges come from `node_atoms` × `atom_nodes` (`crates/portage-world/src/lib.rs:707-720`): one edge per (slot, target slot) with the OR of the `*DEPEND` bits. `node_atoms` is local to `walk()` (`lib.rs:640`) and dropped after that loop; `SlotSet.atoms` (`reorder.rs:16`) keeps the atoms aimed at a slot and their requesters' cpvs, but neither the `*DEPEND` bits nor the `||` origin, so it does not replace `node_atoms` (review G7, checked).
- **Slotless atoms (review D1, verified; corrects this plan's earlier text).** An atom without a slot is narrowed by `process_atom` → `narrow_slotless` (`lib.rs:832-839`, `:858-889`). `plan_world.rs:35` sets `opts.rebuilds = true`, which becomes `Memos::newest_slot` (`lib.rs:142`, `:593`, `:623`); with it `keep` is empty and `narrow_slotless` keeps **the best slot alone**. Only a check (`newest_slot = false`) keeps the installed visible slots. So in `--plan-world` a slotless atom gives exactly one edge, to the newest visible slot, even when an older installed slot already meets it. The doc of `World::reached` (`lib.rs:509-511`, "an atom without a slot aims at every slot of its package") is stale; S2 corrects it. The two host python members come from slotted atoms (eclass per-target atoms or `||` arms), not from a slotless one.
- `||` groups: `dependency_atoms` (`lib.rs:345-399`) resolves each `||` to **one** arm (`branch_preference`, `lib.rs:287`; plan mode prefers the arm that admits the newest version, `lib.rs:112-116`, `:310`). The literal checker's `_satisfied` (`health_checker.py:413-420`) accepts **any** satisfied arm.
- Build keys are read only for a slot whose version changes, or with `--with-bdeps` (`dependency_keys`, `lib.rs:406-418`); `--plan-world=emptytree` sets `with_bdeps` (`plan_world.rs:37-38`), so there kept slots carry build edges and can be SCC members that are not rows.

### 0.2 #771 (read + 02.764 evidence)

Shape V3 `w764d*` (`db -B-> dt`, `dt -R-> du`, `du -B-> db`): `dt` is build-used, so `(dt,du)` is not cuttable; the cycle has no cuttable edge; `build_time_cycles` sees `db -> dt` and `du -> db` only, no SCC, no line. The walk gives `du, dt, db`; the literal checker fails `du` (BDEPEND `db` merged later), while `dt, db, du` is legal. Pinned exactly: unit `w764_an_uncuttable_runtime_cycle_is_left_to_the_walk` (`order.rs:658-681`), pmtest `test_764_an_uncuttable_runtime_cycle_is_left_to_the_walk` (`test_plan_world.py:393-406`).

Proposed fix (the entry's): when `cycle_cut` finds no cuttable edge, fall back to the first runtime-only edge (`is_runtime_edge`, `order.rs:159-161`) of the cycle; still `None` when the cycle is all build. `after/red.txt` R3 ran `cargo test -p portage-world` and `pytest -k 764` only; **in `portage-world`** it moves exactly two unit tests: V3 (`runtime_cut` = `(dt,du)`; order `dt, db, du`, derived) and `the_virtual_provider_edge_is_the_only_cuttable_edge` (`order.rs:507-563`: first cut becomes `(w751prov, w751base)` instead of `(virtual/w751virt, w751prov)`), plus the V3 pytest pin. The `portuale` crate and the rest of `test_plan_world.py` were not run by R3 (review G1); by hand (review) `a_kept_virtual_with_a_stale_provider_keeps_todays_cut_and_order` (`plan_world.rs:1134`) cuts `(prov,base)` then `(virt,prov)` and keeps `user, prov, base`, and the w749 pair (all-build, no runtime edge) cannot be touched; S0.6/S1 measure it. The `rest` assertion of the virtual-provider test stays: with `(prov,base)` removed, `prov→user→virt→prov` still has the cuttable `(virt,prov)`, which `find` takes before the fallback.

What the fallback guarantees, by construction (review): once every cycle that contains a runtime edge is cut, the DFS postorder honours every build edge outside a pure-build SCC, so it cannot add a literal failure on a modelled build edge outside a build SCC. Inside the bed's 26-member build SCC the walk can still reorder; that is why the owner made the bed measurement a precondition (§1 Q1). What it costs: the cut edge is a build tool's runtime edge, so the tool's direct runtime dependency can land after the tool's consumer (charter-literal legal, PMS 8.1 "usable" not met; the strict model notes it as `cycle-noted` on V3, 02.764 §1): the #764 hole moved to depth 1 for this shape only, in exchange for removing a literal `build-order` failure.

### 0.3 #772 (read; the premise is only half proven)

Backlog #772: the host fast plan prints an 11-member `build cycle with no serial order` line and the bed `FAST_world.stderr` a 26-member one, while the literal checker finds 0 `build-order` on both plans. Suspected cause: `build_time_cycles` counts build edges whose atom an installed package already meets.

- **Proven:** "no order satisfies it" is false for those plans: the printed order satisfies every build atom by the literal checker (`health_checker.py` `check_order`, `:765-785`: a build atom must be matched by a package installed or merged earlier). Property 5 is violated whatever the cause. The ` -> ` chain is not a path either (§0.1).
- **Not proven: the cause.** `hostcycle.py` reads consecutive members of the printed chain as edges (`zip(members, members[1:])`, `:21`); they are SCC members in discovery order, so its per-"edge" lines and its "6 of 11" / "12 of 26 met" counts are on pseudo-edges. Its "installed: True" means "a package of that cp is installed" (any version or slot), not "the atom is met", and it keys plan entries by cp (`:17`), so python:3.14 and :3.15 collapse into one. The backlog's "every member's target is installed" is false on the bed (`dev-libs/icu`, `net-libs/nghttp2`, `sys-devel/binutils:2.47`, `sys-devel/gcc:16` are `new` in `FAST_world.json`) **and on the host** (`dev-lang/python:3.15` is `new`, #7; only `/var/db/pkg/dev-lang/python-3.14.10` exists).
