## D — defects in the plan

### D1 — AUTOCLEAN does not default to "yes"; the auto-clean in the captures is a side effect of global updates (high for S11/Q10 and for every S0 `emerge` cell; proven)

**Where.** Plan §0.4 "Auto-clean", §1 row 351-CLEAN, S11, Q10.

**Portage.** `make.globals:103` is `AUTOCLEAN="no"`. `actions.py:694-704` auto-cleans only when `settings["AUTOCLEAN"] == "yes"`. Two places force it to "yes":
- `run_action` sets it after `_global_updates(...)` returns True (`actions.py:3671-3691`, bug #792195);
- depclean sets it too (`:809-813`).

The #348 capture `LLM/evidence/2026-10-12-348-s0/b/b-env-portage-emerge-binpkg8.stdout` shows `Performing Global Updates` (line 2) and `>>> Auto-cleaning packages...` (line 51) in the same run.

**Divergence in the plan's reasoning.**
- Input: a hermetic configroot where Portage cannot record its updates in `mtimedb`.
- Portage: global updates run on every invocation, which forces AUTOCLEAN=yes, which triggers the auto-clean.
- On a default real system (updates already recorded, AUTOCLEAN unset), Portage prints no auto-clean at all.
- The plan attributes the auto-clean to make.globals. That overstates S11 ("after each merge") and makes Q10's framing wrong. It also contaminates every S0 A/M/L/CL `emerge` capture with two blocks that portuale should *not* reproduce, because 351-UPD is cut.

**Fix direction.**
1. Correct §0.4 and Q10: auto-clean happens only with a user-set `AUTOCLEAN=yes`, or as a consequence of applied global updates.
2. Because 351-UPD is cut, tie 351-CLEAN to the user setting only, and record the global-updates coupling in the cut text.
3. Run all S0 `emerge` cells with `--package-moves=n` on both sides (portuale parses it, `args.rs:823`). That suppresses both blocks at the source. Alternatively, keep one dedicated cell that shows the coupling.

### D2 — S2 has the `package.keywords` merge order reversed (medium; proven by source read)

**Where.** Plan §2 S2 Goal: "both files merged, `package.keywords` second".

**Portage.** `KeywordsManager.py:80-104`:
1. `pkgdict = grabdict_package(package.keywords)` is read **first**;
2. `package.accept_keywords` entries are then `.extend`ed onto it per atom;
3. a bare entry gets the `~arch` default after the merge.

**Divergence.**
- Inputs: `package.keywords` has `cat/p ~amd64`, and `package.accept_keywords` has `cat/p -~amd64`.
- Portage: the tuple is `(~amd64, -~amd64)`. The incremental stack in `getMissingKeywords` cancels the token, so the package stays masked.
- A port that appends `package.keywords` second gives `(-~amd64, ~amd64)`, and the package is accepted.
- The order is also the dict insertion order for each atom key.

**Fix direction.** Read `package.keywords` first and extend with `package.accept_keywords`. Add a K cell with a `-` token across the two files. The warning fires only when `package.keywords` yields at least one valid entry (`if pkgdict and portage._internal_caller`); say so in Q3's pin.

### D3 — S4's file list misses most of the direct-path FEATURES gates that Q4 turns on (medium; likely)

**Where.** Plan S4 "Files". It names `ebuild_merge/options.rs` only at `:110` (DISTDIR) and `sandbox.rs:111`.

**portuale.** These direct-path gates read the raw `$FEATURES`:
- `MergeOptions::from_env`: `collision-protect`, `protect-owned`, `config-protect-if-modified`, `features` (`ebuild_merge/options.rs:90-131`);
- `unmerge_orphans` (`ebuild.rs:393-398`);
- `buildpkg_live`, `binpkg_multi_instance`, `binpkg_signing` (`ebuild.rs:470-480`);
- `features_string` (`ebuild_phases/sandbox.rs:97`);
- `XattrPolicy` (`options.rs:176-179`);
- the gpg policy (`binpkg/gpg.rs:44`).

`from_env` is shared with `emerge`, `--resume`, `--config`, `--info` and `-C` (`merge_setup.rs:63`, `resume.rs:198`, `config_action.rs:134`, `info.rs:721`, `removal/unmerge.rs:520`).

**Divergence risk.** An executor who changes `from_env` itself, the obvious place, alters every emerge caller. Some already override from the config (`merge_setup.rs:74-78`) and some do not (`config_action.rs`, `info.rs`). An executor who changes only the listed lines leaves Q4 half-done: `ebuild … merge` would export the resolved FEATURES but gate `protect-owned` and `unmerge-orphans` on the empty environment. `make.globals:83` has `unmerge-orphans` on, so a real-system `portuale ebuild … merge` would keep orphans that Portage removes.

**Fix direction.** In the direct path, mirror `merge_setup.rs:63-78`: `from_env`, then `set_resolved_features(config_features_string(config))`, `apply_config_protect`, `config_install_mask`, and `resolved_config = Some(...)`. Derive `unmerge_orphans` and the `PackageOptions` booleans by calling `package_options_from_env(.., Some(features), Some(config))` instead of `ebuild.rs:455-485`. Leave `from_env` unchanged except for the DISTDIR default. List these sites in S4.

### D4 — §0.2.3/S8 miss the trailing blank line on every `parser.error` message (medium; proven by host runs)

**Where.** Plan §0.2.3 table, S0 cell C ("capturing **only the last stderr line**"), S8.

**Portage.** Every `parser.error(...)` call in `_emerge/main.py` passes a message that ends in `\n`: `:843-845`, `:904-906`, `:1000-1002`, `:1019`, `:1034`, `:1067-1068`, and others. argparse adds its own newline. A host run of `emerge --jobs=x` ends its stderr with `…parameter: 'x'\n\n`, and `emerge --exclude =a/b-1` ends with `…allowed)\n\n`. Argparse-native errors (`unrecognized arguments`, `invalid choice`) end with a single `\n`.

**portuale.** `cli_atoms.rs:121-124, 145-149` and the `args.rs` sites print one `\n`. So the plan's "same line, no usage" verdict for `--exclude` is incomplete: there is already a divergence there today.

**Fix direction.** S0 cell C should capture the full stderr *tail after the usage block* (everything from the `emerge: error:` line to EOF), not just the last line. The S8 helper should take the message with its trailing `\n` exactly as Portage passes it, so `parser.error`-origin messages get the blank line and argparse-origin ones do not.
