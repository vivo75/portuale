# #682 — merge-order candidate sort: total order, deterministic input

**Status:** done 2026-11-08 (Tasks 1–5, branch `backlog/682-merge-order-sort-total` in both repos; commits to be cited when made). Residue: #685 (the `llvm_targets_XCore` abort, a resolver result, not a sort problem).

**Goal:** `portuale emerge -pvuDN --getbinpkg=n media-video/ffmpeg` never panics
("user-provided comparison function does not correctly implement a total
order") and prints the same plan on every run.

**Spec:** `LLM/backlog-tasks.md` #682. Charter property: a panic or a result
that changes between runs is a wrong result for the user; the expected
behaviour is "deterministic", not "same as Portage" (Portage sorts `cp` then
`vercmp`, it never meets an unparseable version).

## 0. Read this first

The backlog entry's cause is a hypothesis. Task 1 proves or refutes it before
any fix. Two symptoms are reported and may have two causes:

1. the panic (sort closure, `merge_order/cycles.rs:49`);
2. the output differing between runs (an error about
   `~llvm-core/llvm-22.1.8[llvm_targets_XCore=]` on the non-panicking runs).
   The sort fix may not cure this; if it does not, file a new number
   (`grep -nE '^[0-9]+\. \*\*' LLM/backlog-tasks*.md`, next free is 685 today,
   re-check) and keep #682 to the panic.

## Findings from reading the code (2026-11-08)

- `cycles.rs:49`: `vercmp(..).unwrap_or(0).cmp(&0)`. `vercmp` returns `None`
  when either side fails the version regex, so an unparseable version is
  "equal" to everything: not transitive.
- `entry_version(..)` is `None` for `NoVisibleCandidate`; `unwrap_or_default()`
  gives `""`, which does not parse, so such an entry also compares equal to all.
- `cand` comes from `mergeable: HashSet<usize>` when `prefer_asap` is off, so
  the input order of the sort differs per run (`RandomState`).
- Same `unwrap_or(0)` / `unwrap_or(Equal)` shape at
  `merge_order/installed_closure.rs:243` (`max_by`, a fallback; no panic, but
  the winner depends on iteration order) and `merge_order/prelude.rs:89-100`
  (`union.sort_by`, installed first, then version; same panic risk).
- Not a problem: `sort_by_key` sites (`build.rs:330`, `select_nodes.rs:195`,
  `replay.rs:249`, `cycles.rs:228`, `tree_display.rs:174`) use total keys.
