# Review of plan `02.589-575-residues.opus.md`

- **Date:** 2026-10-26
- **Scope:** read-only, pre-execution review of the plan against the current
  portuale source and Portage 3.0.83.
- **Plan range:** `fb940d2fb3c253c84fbb5a89f52c9c46a85173ed` to
  `1f027ff9e7820c86c9a620d98a78ddd19c758cd7`.
- **Method:** independent review followed by targeted verification of the
  findings against the source. No implementation or full test/bed gate was
  run.
- **Verdict:** **ready to execute with fixes**. The plan has strong source
  grounding and useful gates, but the cleanup rule risks data loss, Task 4
  contradicts the live WHIRLPOOL oracle, and Task 9's central mechanism does
  not match Portage's installed-parent flow.

## Strengths

- The dependency migration is sequenced correctly: moving the existing
  hashers to `digest 0.11` before adding `ripemd` and `whirlpool` directly
  supports the single-`digest` requirement. The pre-migration known-answer
  test is a useful safety net.
- The remote-binary `pkg_pretend` work follows Portage's actual flow: fetch,
  verify, unpack metadata, run the pretend phase, and reuse the fetched file.
  The required abort-before-merge behavior targets the real gap.
- The scheduler design can use existing graph information rather than adding
  a parallel dependency representation.
- The execution safeguards are well specified: one writer at a time, frozen
  bed binaries, failure comparison by test name, corpus-drift review, paired
  commits, and no push.

## Issues

### Critical (must fix)

#### 1. The prescribed fixture cleanup can delete uncommitted work

**Plan:** `LLM/02.589-575-residues.opus.md:202-207`

When fixture pollution appears, the manager is told to run:

```sh
git clean -fdq fixtures/
```

New fixtures are expected during slices and may still be untracked when the
manager reviews and tests the change. This command would delete them. The
project's own lessons explicitly require `git add` before any `git clean`
because clean deletes untracked fixtures
(`LLM/lessons-of-backlog-ops-2026-10-03.md:329-333`).

**Minimal correction:** remove the blanket clean instruction. Delete only
named generated paths identified by the failing test. If a broader clean is
unavoidable, inspect `git clean -ndq fixtures/` first and ensure every
intended fixture is already staged or committed.

### Important (should fix)

#### 1. Task 9's central `runtime_pkg_mask` premise does not match Portage's installed-parent paths

**Plan:** `LLM/02.589-575-residues.opus.md:692-694,712-719,735-746`

For installed-parent slot-operator handling, Portage records installed
parents and children in `slot_operator_replace_installed`; only non-installed
binary instances receive `slot_operator_mask_built`:

- `3rdparty/portage/lib/_emerge/depgraph.py:2438-2464`
- `3rdparty/portage/lib/_emerge/depgraph.py:2896-2931`
- `3rdparty/portage/lib/_emerge/resolver/backtracking.py:237-243`

Current Rust already models that distinction in
`crates/portage-repo/src/resolve/feedback/mod.rs:82-105`. A parent mask with
the `missing dependency` reason belongs to the separate missing-dependency
path, not to an unconditional installed-parent update-probe result.

**Minimal correction:** have Task 8 identify the actual
missing-dependency/`dep_zapdeps` path responsible for the remaining
divergence, then replace Task 9's mask-production assertion and
implementation target accordingly. Do not execute Tasks 9-10 with the current
parent-mask requirement.

#### 2. Task 4's WHIRLPOOL oracle and required behavior contradict the reference host

**Plan:** `LLM/02.589-575-residues.opus.md:479-485,503-525`

The plan assumes bundled pure-Python WHIRLPOOL and unconditionally requires
dropping it beside another hash. The plan's own S0 condition makes the filter
conditional on `_whirlpool_unaccelerated`, but the required tests do not
preserve that condition.

The reference host was checked directly and reported:

```text
Portage 3.0.83
origin bundled-c unaccelerated False
filtered ['SHA512', 'WHIRLPOOL', 'size']
```

Portage only drops WHIRLPOOL when `_whirlpool_unaccelerated` is true
(`3rdparty/portage/lib/portage/checksum.py:159-168,294-310`). On this host, a
bad WHIRLPOOL beside a good SHA512 must therefore fail rather than pass.

**Minimal correction:** settle the intended acceleration environment before
implementation and record `get_hash_origin("WHIRLPOOL")`. Against the current
host, replace the unconditional drop test with the mismatch expectation. If
pure-Python behavior is the deliberate target, make that an explicit
owner-approved configuration with separate accelerated and unaccelerated
cases.

#### 3. Task 2 does not cover the `mtimedb` warning for `emerge --info`

**Plan:** `LLM/02.589-575-residues.opus.md:372-412`

S0 explicitly asks which commands print the unknown-key warning, including
`emerge --info`, but the only product file named is `mtimedb.rs`. Portage
constructs `MtimeDB` while loading the general emerge configuration
(`3rdparty/portage/lib/_emerge/actions.py:3378-3391`), so its load warning
also applies to `--info`. Rust's `--info` dispatch never touches mtimedb
(`crates/portuale/src/pretend/standalone_actions.rs:257-293`).

Normalizing only the existing read/write helpers cannot close that observable
gap.

**Minimal correction:** specify the per-command mtimedb load at the same
lifecycle, expand the affected dispatch files, and add black-box tests for
`--info` and duplicate-warning prevention. Alternatively, explicitly narrow
the warning scope with an owner ruling.

#### 4. Task 4 misses the independent digest-name renderer

**Plan:** `LLM/02.589-575-residues.opus.md:492-496,522-526`

`verified_digest_names_filtered` independently hard-codes the old eight
algorithms and applies only `PORTAGE_CHECKSUM_FILTER`
(`crates/portuale/src/emerge_getbinpkg.rs:1982-2003`). It drives local and
remote success output as well as fetch-only output
(`crates/portuale/src/emerge_build/fetchonly.rs:131-143`). Portage displays
the same filtered digest set it verified
(`3rdparty/portage/lib/_emerge/BinpkgVerifier.py:41-46,122-127`).

Changing only verification would make the displayed verification and the
actual verification diverge.

**Minimal correction:** centralize digest selection and filtering for both
verification and rendering. Add success-line tests for RMD160, WHIRLPOOL, and
the applicable acceleration/filter cases.

#### 5. Task 4 changes merge-time acceptance without the mandatory merge-path gate

**Plan:** `LLM/02.589-575-residues.opus.md:119-124,522-527`

The changed verifier is called directly during binary merge and remote
download (`crates/portuale/src/emerge_getbinpkg.rs:1460-1466,2113-2116`), so
it changes which packages are accepted before merge. The governing rule
requires the glibc+bash reinstall for merge-path changes
(`LLM/agent-context.md:398-418`), but Task 4 is absent from the global gate
list and ends with only the ordinary full gate.

**Minimal correction:** add Task 4 to the merge-path gate list and record a
qualifying run containing both `sys-libs/glibc` and `app-shells/bash`.

#### 6. Task 5's per-crate commits violate the full-gate-before-every-commit rule

**Plan:** `LLM/02.589-575-residues.opus.md:111-118` versus `:551-561`

The global constraint requires the complete Rust and pmtest gate before every
commit. Task 5 instead runs only `cargo test -p <crate>` after each crate,
commits each crate, and runs the full gate only after the last one.

**Minimal correction:** either run the complete gate before every per-crate
commit or make the whole Task 5 sweep one commit after the final full gate.

#### 7. Task 6 captures verification failure but has no corresponding acceptance test

**Plan:** `LLM/02.589-575-residues.opus.md:590-610`

S0 case (c) requires a verify failure during the new up-front pass, but the
RED list contains only ordering, pretend failure, and fetch-once cases.
Portage returns immediately when the verifier fails
(`3rdparty/portage/lib/_emerge/Scheduler.py:1206-1212`), before metadata
unpacking or merge. This is a distinct new failure path.

**Minimal correction:** add a RED test grounded in S0(c) that asserts
abort-before-any-merge, no subsequent metadata/pretend processing, and no
second download.

#### 8. The L0 stop condition has no defined target set or target acceptance oracle

**Plan:** `LLM/02.589-575-residues.opus.md:125-126,704-719,747-760`

Tasks 9-10 allow target cells to move while stopping on non-target movement,
but Task 8 never requires an explicit list of those L0 cells or their expected
Portage outcomes. An executor therefore cannot apply the stop condition
mechanically, and a wrong result inside an unnamed target cell could be
accepted.

**Minimal correction:** make Task 8 emit a named target-cell list with
before/after Portage expectations. Compare all cells by name, require targets
to reach their oracle, and stop on every other delta.

#### 9. Task 10's keeper-pin recovery contradicts the global stop condition

**Plan:** `LLM/02.589-575-residues.opus.md:248-253` versus `:761-766`

Globally, a keeper pin still red after one fix round requires stopping and
committing nothing further. Task 10 instead says to revert the removal,
document the gate, file a residue, and continue with later heuristics.

**Minimal correction:** distinguish keeper pins from other Task 8 pins. For a
keeper, restore the working tree to green and stop without further commits.
Reserve keep-and-continue recovery for explicitly permitted non-keeper pins.

#### 10. Close-out requires a commit's contents but never schedules that commit

**Plan:** `LLM/02.589-575-residues.opus.md:781-798`

The backlog, plan status, and final report must change in the close-out
commit, but the next step immediately checks out `main` and fast-forwards. No
close-out commit is instructed. This also conflicts with the same-commit
status requirement in `AGENTS.md` and risks leaving the close-out changes
uncommitted or outside the cited branch tip.

**Minimal correction:** add the final paired close-out commit after the final
gates and before either fast-forward, committing pmtest first when it has a
half.

### Minor (nice to have)

#### 1. One proposed Task 5 RED is already a green guard

**Plan:** `LLM/02.589-575-residues.opus.md:546-550`

`temp_dir_removes_itself_on_drop` already covers the drop-and-check behavior
in `crates/portage-util/src/temp_dir.rs:145-160`.

**Minimal correction:** identify this as an existing green pin and limit the
expected RED to the genuinely new source check for disallowed `.keep()` calls.

#### 2. Task 5's leak-count command is unreliable with an unset `TMPDIR`

**Plan:** `LLM/02.589-575-residues.opus.md:556-558`

The check expands paths through `$TMPDIR`, while `TempDir::new` uses Rust's
actual temporary-directory resolution
(`crates/portage-util/src/temp_dir.rs:26-38`). With unset `TMPDIR`, the shell
check looks in the wrong place. Comparing counts can also hide equal-number
creation and deletion.

**Minimal correction:** assign an isolated temporary root for each per-crate
run and compare exact `portuale-td-*` path sets before and after.

## Recommendations

- Add a plan-wide rule that an S0 result contradicting a task premise stops
  product work and requires an amended plan or owner ruling. This would cover
  both the WHIRLPOOL and `runtime_pkg_mask` contradictions without worker
  improvisation.
- Re-review the amended Tasks 8-10 before Task 0 starts. The resolver phase
  depends on a corrected mechanism and target-cell matrix; discovering either
  only after Phase 1 would needlessly strand the paired branch.

## Declined to judge

- **Digest 0.11 and new-hasher compilation/API compatibility:** no dependency
  build was run; Task 3's S0 appropriately leaves detailed API verification
  for execution.
- **Actual full-gate results, L0/L1 deltas, and feasibility of newly proposed
  bed shapes:** not executed in this read-only review.
- **Third-party mtimedb consumers such as gentoolkit/eix and runtime
  performance effects:** excluded by the owner ruling or not benchmarked.

## Assessment

**Ready to execute? With fixes.**

The plan is not safe or unambiguous as written. Correct the cleanup rule and
reconcile the WHIRLPOOL and resolver requirements with Portage before starting
Task 0; then close the remaining gate, test, and close-out gaps so each phase
can be executed mechanically.
