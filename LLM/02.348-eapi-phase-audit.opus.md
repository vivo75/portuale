## 0. What this plan is, and what the code already tells us

**Goal.** For every EAPI an ebuild in the supported floor can declare (**7 and 8**; floor: ebuilds ≥7, profiles 5 — memory `eapi-floor-7-profiles-5`), portuale runs the phases the way Portage 3.0.82.2 does: same phase sequence and skips, same environment, same helpers available/banned with the same failure text, same install-time behaviour. Divergences found are fixed or recorded as deliberate cuts.

**Non-goals.** EAPIs below 7 for ebuilds (old-EAPI-only divergences are not bugs); the atom grammar and dependency validation (done in #341); the brush-vs-bash interpreter differences that are not EAPI-dependent (separate line of work, `docs/brush-pr/`); PMS conformance beyond what Portage itself does (Portage is the oracle, not PMS).

**Facts established while scoping (2026-10-12), so the plan does not have to re-derive them:**

1. **The bash side is Portage's own.** `bin/` is a vendored copy of upstream Portage's `bin/` (`bin/README.md`; ref pinned in `3rdparty/repos.toml`, `[portage]`), executed by brush. So the **74 `___eapi_*` predicates** of `eapi.sh` (banned/available helpers, `econf` flags, `unpack` formats, `die`/`nonfatal`, `best_version -b/-d/-r`, `failglob`, `ENV_UNSET`, strict `keepdir`, …) and the per-EAPI helper behaviour are inherited, **provided** (a) the vendored copy equals the 3.0.82.2 scripts, and (b) brush evaluates them the way bash does. Only `chmod-lite`, `portuale-python`, `ebuild-ipc` (always exits 127), `portageq-wrapper` and `phase-functions.sh` (one local change) are portuale-owned. A first `diff -rq bin 3rdparty/portage/bin` (2026-10-12) shows exactly those five files differing (`chmod-lite`, `ebuild-ipc`, `phase-functions.sh`, `portageq-wrapper`, plus the added `portuale-python` and `README.md`); the pinned ref is `portage-3.0.82.2`, equal to the host's `portage.VERSION`.
2. **The Python side is portuale's own.** What `doebuild`/`config.environ()` do per EAPI is Rust code in `crates/portuale/src/ebuild_phases/` (`phase_env.rs`, `single_phase.rs`, `run_phase.rs`, `commands.rs`) and the merge engines. Portage's per-EAPI branches there (doebuild.py): `eapi_exports_KV` (`:655`), `eapi_exports_merge_type` (`:1282`), `eapi_exports_replace_vars` (`:1300`, `REPLACING_VERSIONS`/`REPLACED_BY_VERSION`), `eapi_exports_pms_vars` (`:2211`, the unexported-PMS-vars set), skip of `prepare`/`configure` without `src_prepare_src_configure` (`:2388`) and of `pretend` without `pkg_pretend` (`:2393`), `eapi_has_required_use` (`:1943`), and `_eapi_attrs`-driven `IUSE_EFFECTIVE`/slot-operator handling (`:2710-2764`). The `_eapi_attrs` fields that are **not** dependency-grammar (`broot`, `sysroot`, `prefix`, `exports_*`, `path_variables_end_with_trailing_slash`, `posixish_locale`, `symlink_rewrite`, `dosed_dohard`, `pkg_pretend`, `src_prepare_src_configure`, `rdepend_depend`) are **not** in portuale's `EapiAttrs` (#341 S1 ported only the 17 fields atoms and deps need). Today the phase code has scattered, undocumented EAPI conditionals (`phase_env.rs:293` trailing slash "EAPI 6 and below"; `commands.rs:73` `A`/`AA`; `single_phase.rs:267` `REPLACING_VERSIONS`).
3. **IPC is stubbed.** `ebuild-ipc` exits 127 and `portageq-wrapper` replaces the queries. Any EAPI feature that Portage serves over the ebuild IPC (`has_version`/`best_version` with `-b/-d/-r`, `docompress`/`dostrip` accounting, `die`/`nonfatal` hand-off, `elog`) is an audit target, not an assumption.
4. **Unsupported EAPI at phase time.** `depend_phase.rs:138-148` already returns a failure for an unsupported EAPI at metadata time. Whether every other entry point (`ebuild <file> <phase>`, `--buildpkgonly`, binary merge of a package whose EAPI portuale does not know, `pkg_*` of an installed package) refuses with Portage's text has not been checked.
5. **Test infrastructure exists.** pmtest has L2 (`l2-portuale-builder.sh`: both PMs build; archives and cross-install diffed), L3 (`l3-source-parity.sh`: both build+merge from source into two identical containers; installed tree + VDB diffed), L3.2 life-cycle, and the hermetic contract suite with ~930 EAPI-8 and 28 EAPI-7 fixture ebuilds (`pmtest/fixtures/repo`). What is missing is a **purpose-built probe set**: tiny ebuilds that each exercise one EAPI-dependent behaviour and record what the phase saw.

## 1. Method (applies to every task)

- **Probe ebuild = one behaviour.** A hand-written ebuild (real md5-cache entry — memory `md5-cache-validation`; collision-checked name; new fixture names only, existing fixtures untouched) whose phases `einfo`/write to a log the behaviour under test (env dump, helper exit status and message, file listing of `${D}`). One probe ebuild per EAPI per behaviour, `EAPI=7` and `EAPI=8` variants side by side.
- **Capture = both PMs, same configroot, same argv**, via `ebuild <file> <phase>` and via `emerge --oneshot` in the bed (host Portage first for speed; container bed for the final proof). Capture files per cell: `argv`, `rc`, `stdout`, `stderr`, `phase log`, `env dump` (as in `LLM/evidence/2026-10-11-341-s0/portage/`). Evidence directory: `LLM/evidence/<date>-348-s0/`.
- **Verdicts per cell:** `same` / `diverges (fix)` / `diverges (cut, owner decides)` / `not reproducible (why)`. Nothing is guessed: a cell whose Portage output is unstable is stabilised or dropped with a reason.
- **Fix slices follow the repo rhythm** (AGENTS.md steps 4–8): failing contract pin from the capture → implement → green → L0 + L2/L3 smoke where merge/phase code changed (merge-path safety gate: a successful test merge of `sys-libs/glibc` and `app-shells/bash` for any change to the merge path) → `what-this-proves.md` paragraph with a runnable example → commit pair (pmtest first, `git add -f` for fixture files).
- **Gates unchanged from #341:** fmt, clippy (0 warnings), `cargo build --release` before `cargo test --release --no-fail-fast`, pmtest suite (never concurrent with cargo test), the three known baseline failures ignored, no corpus bless without review.

## 4. Risks and open points

- **The probe set is the work.** S0 is large (74 predicates × 2 EAPIs, ~25 helper families × 2 EAPIs, env per 12 phases). Mitigation: scripted capture, one table, and the existing `LLM/tools` capture helpers; partial matrices are acceptable only if the uncovered rows are listed.
- **IPC cut may hide real EAPI-8 failures** (fact 3). If S0.6 shows an EAPI-7/8 helper that needs the IPC daemon, the choice is port-or-cut per helper, owner's call.
- **Prefix and cross-compile (`BROOT`, `SYSROOT`, `ESYSROOT`)** need configroots the bed may not offer; unreproducible rows are recorded, not guessed.
- **Brush vs bash** differences may surface as "EAPI" divergences (a predicate that behaves differently in brush). They are fixed in the brush patch set (`docs/brush-pr/`) or by a vendored-script workaround, and noted as such in the matrix — they are not EAPI semantics.
- **Owner decisions expected from S0.8:** which clusters become slices; per-helper port-or-cut for IPC-only features; whether any divergence confined to a feature no real ebuild in the tree uses (e.g. `PROPERTIES=live`) is worth fixing.
