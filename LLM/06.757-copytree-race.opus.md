# 06.757 — one filtered copy of the fixture tree (the #754 race at four more sites)

Status: proposed

## 0. What this fixes

`fixtures_copytree_ignore()` (`pytests-contract-suite/conftest.py:580`) exists
precisely because a copy of the shared fixture tree can list
`var/db/.pkg.portage_lockfile` a microsecond before its owner deletes it, and
then die with `ENOENT`/`shutil.Error`. Its docstring says so; #754 put the
same filter into the mutant harness. Almost every site uses it. Four do not,
and they are the ones that copy the vdb:

| Site | What it copies |
|---|---|
| `test_emerge_pretend_contract.py:39048` (`test_skipped_update_block_names_every_installed_consumer`) | `<ROOT>/var` |
| `test_emerge_pretend_contract.py:39886` (`_698_root`) | `<ROOT>/var` |
| `test_emerge_pretend_contract.py:40041` (`test_715_the_provider_is_merged_before_the_holders_rebuilt_for_it`) | `<ROOT>/var` |
| `test_health_checker.py:1230` | the whole `<ROOT>` |

Observed, not theorised: `/var/tmp/755-after.log` has
`test_733…[pubgrub]` failing with `shutil.Error` naming that lockfile, and
the #755 bless run had `test_698_a_holder_without_a_route_still_withholds_the_upgrade[portage]`
fail the same way (both pass solo, 2/2). The other ~40 `copytree(...)`
calls in the suite copy `etc/`, `repo/`, `pkgdir` or an overlay — no vdb, no
race, and they stay as they are.

## 1. Decision `[default sicuro]` — fix the class, not the four sites

Adding `ignore=fixtures_copytree_ignore()` at four call sites fixes today's
faults and leaves the same trap for the next helper. Instead: add one
helper in `conftest.py`,

```python
def copy_fixture_tree(src, dst, **kwargs) -> None
```

that always applies `fixtures_copytree_ignore()`, with an explicit
`extra=` argument for the site-specific names (`mtimedb` where a copy must
start record-free) and pass-through `kwargs` (`symlinks=True`,
`dirs_exist_ok=True`). Convert **all** sites that copy the vdb or the whole
ROOT to it — the four above, plus the existing `ignore=fixtures_copytree_ignore()`
calls that copy `var`/ROOT, so there is exactly one way to copy fixture
state. Sites copying `etc/`/`repo/`/`pkgdir` are left alone: they cannot
meet the lock and converting them is churn without a failure mode behind it.

Rationale: the repo's own rule for slices is "prefer changes that remove
code", and a class that returned once (#754 → #757) is the definition of
one that needs a seam, not four patches.

## 2. The pin (this is the half that matters)

A test in `pytests-contract-suite/test_emerge_pretend_contract.py` (or a
small `test_conftest_copy.py` if that reads better):

1. build a scratch source tree containing `var/db/pkg/<cpv>/…` plus
   `var/db/.pkg.portage_lockfile` and `var/lib/portage/.mtimedb.tmp.123`;
2. `copy_fixture_tree(src, dst)`;
3. assert the copy succeeded, `var/db/pkg/…` is present, and **neither
   volatile name travelled** (`lock state is not transferable`, as the
   docstring already says);
4. assert `copy_fixture_tree` refuses nothing else: a second call with
   `extra=("mtimedb",)` drops `var/lib/portage/mtimedb` too.

Red-first: the same test written against a bare `shutil.copytree` fails on
step 3 (the lock name is copied, and with a concurrently-deleted file it
also raises), which is the behaviour being removed.

## 4. STOP rules

- **STOP-0**: a converted site's test starts failing for a *reason other
  than* the volatile names (e.g. it needed the lock to be present) → STOP
  and report; the filter is right, the site's expectation is not.
- **STOP-1**: `pytest-parallel.sh` totals move by anything other than the
  added pin → STOP; a harness change must not silently drop a test.
- **STOP-2**: the helper grows a mode that copies volatile state (`copy
  the lock anyway`) → STOP; that is the bug, not an option.
