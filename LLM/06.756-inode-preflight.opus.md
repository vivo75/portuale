# 06.756 — the space preflight must see inodes, and a basetemp must not land on an inode-poor filesystem

Status: done 2026-11-15 (branch `backlog/756-inode-preflight` in both repos; pmtest `9553305`, merged into `opencode` as portuale `e8efb6da` + pmtest `ce98f0b`; guard + pins + both entry points, gate.sh rc 0)

## 0. What this fixes

`LLM/tools/check-work-space.sh` answers "is there room for a big run?" with
`df -Pk` size fields only. On 2026-11-15 a full `gate.sh` run with its
`--basetemp` under `/tmp` exhausted that filesystem's **inodes** while **63 G
of space were still free**: `/tmp` is a tmpfs with 1 048 576 inodes, the
suite reported **182 errors and 2 failures** (`2 failed, 4776 passed, … 182
errors`), all `OSError: [Errno 28] No space left on device` / `touch: cannot
touch …` — exactly the confusion the preflight exists to prevent. The
identical tree, with the output under `/var/tmp`, was green.

Why it happened although the tooling anticipates it: `gate.sh` defaults `OUT`
to `mktemp -d` under `${TMPDIR:-/var/tmp}` — correct — but nothing stops a
caller passing an `OUT` (or `--basetemp`) on an inode-poor filesystem, and
the preflight has no opinion about inodes, so it said "ok".

## 1. The numbers (measured, not assumed)

From `LLM/evidence/06.756/inode-demand.txt`, all on this host:

| Measurement | Value |
|---|---|
| `df -i /tmp` | 1 048 576 total, 959 944 free when healthy |
| `df -i /var/tmp` | 10 737 418 240 total |
| **a complete suite run's basetemp** (8 workers, 4967 nodes) | **1 804 465 inodes** |
| the aborted `/tmp` run's peak (2 failures, 182 setup errors) | 962 145 |

The 962 145 figure is **not** the demand: it is where the run died, i.e. a
partial tree. A run that finishes needs about **1.8 M** inodes on this
suite, so the guard's floor is **2 500 000** free inodes (≈ 39 % headroom for
test growth), and S0 must re-measure and adjust if the suite has grown.

The generic inode floor in `check-work-space.sh` stays **200 000**: it is a
sanity floor for "this mount is in trouble", not a run-sizing number — today's
`/tmp` (959 944 free) passes it while being unable to hold a run, which is
harmless *only* because the basetemp guard (D2) dominates on both suite entry
points. Say that in the script's comment so the two numbers cannot be
confused for each other.

## 2. Decisions `[default sicuro]`

- **D1 — the preflight reports inodes too, with an absolute floor.** Add an
  inode row per mount (`df -Pi`) and fail when free inodes are below
  `MIN_INODES` (default 200 000). A percentage is meaningless across these
  mounts (50 % of `/tmp` is 524 288 — below one run's need, so a percentage
  would wave through the exact failure). Bytes keep their percentage rule.
  **A filesystem reporting `total=0`** (some FUSE mounts) is a named failure
  with a message, never an arithmetic crash: guard the division.
- **D2 — the basetemp guard is the real fix, and it has an override.**
  `pytest-parallel.sh` and `gate.sh` resolve the filesystem their basetemp
  will use and refuse when it has fewer than `PMTEST_MIN_BASETEMP_INODES` (default
  **2 500 000**) free inodes. The refusal prints the free count, the demand
  measured above, the path and the override name, and exits non-zero
  *before* any destructive or expensive step. An explicit small run
  (`pytest-parallel.sh -k …` on a 1 M-inode mount) is legitimate: setting
  `PMTEST_MIN_BASETEMP_INODES=<n>` lowers the floor, documented next to
  `PMTEST_MIN_FREE_PERCENT` in `pytest-parallel.sh`'s header and in
  `LLM/skills/portuale-tests-harness/SKILL.md` where the space rule already
  lives. No silent bypass: an override is a number a reviewer can see.
  **[review]** The first cut used the name `PMTEST_MIN_FREE_INODES`, which
  `conftest.py` already owns for its own per-tmp-dir guard (default 20 000, and
  it crashes on a non-numeric value). The knob is renamed for that reason, and
  both entry points now refuse a value that is not a positive integer: `-5`
  compares false and `abc` errors inside `[ ]` without tripping `set -e`, so an
  unvalidated knob is a silent bypass — the exact hole this guard exists to
  close.
- **D3 — the two tools keep their contract.** `check-work-space.sh` stays
  read-only, exits 0/1/2 as today, keeps the byte behaviour and its
  `[min_percent]` argument, and prints the inode line unconditionally so a
  human sees both numbers.
- **D4 — placement is part of the fix, not an implementation detail.**
  - `pytest-parallel.sh`: the check runs **after** the basetemp is resolved
    (argv wins over the env default — parse at `:36-45`) and **before** the
    `rm -rf` at `:46`, so a refusal cannot delete the tree it protects, and
    the check judges the path that will actually be used.
  - `gate.sh`: `OUT` comes from `mktemp -d` (`:8-9`); the check runs
    **immediately after that, before the doc checks** (so the `rmdir` is
    guaranteed an empty directory), and removes the directory it created
    before exiting 2 — but only when it created it, never when the caller
    passed `$1`.
  - A basetemp that does not exist yet is judged by its **nearest existing
    ancestor**; nothing is created before a refusal.
- **D5 — scope statement.** The guards cover the two entry points
  (`pytest-parallel.sh`, `gate.sh`) and their `PMTEST_BASETEMP`/`OUT`
  arguments. A raw `pytest --basetemp=/tmp/x` bypasses them — noted in both
  headers, not defended against.
- **D6 — no heuristics in the suite.** Nothing parses pytest output for
  ENOSPC. The preflight refuses before the run; a run that fails anyway stays
  a run that fails.

## 3. The pins

A Python test in `pytests-contract-suite/test_harness_guards.py` (new file),
with a `df` shim on `PATH` (bare `df`/`du` invocations are what the three
scripts use, so the shim controls them). Each case asserts **exit code and
the naming message only** — never the `du` table, which walks the real
mounts and is host-variable — and none of the cases may trigger a `pip
install` (the venv block in `pytest-parallel.sh:9-12` must already be
satisfied in the pin environment; skip with a loud reason if not).

1. `check-work-space.sh`: bytes fine, inodes below the floor → exit 1,
   message names inodes.
2. bytes low, inodes fine → exit 1, message names space (the old behaviour
   must not be lost).
3. both fine → exit 0, and both rows are printed.
4. `df -Pi` reporting `total=0` → exit 1 with a message, **not** a shell
   crash (D1's guard).
5. `pytest-parallel.sh` with a short-inode `--basetemp` → refuses with the
   message, exits non-zero, and **does not create** the basetemp nor delete a
   pre-existing one (D4).
6. `PMTEST_MIN_BASETEMP_INODES=100` on the same short filesystem → proceeds (the
   override is real, D2).
7. `gate.sh` with a short-inode `OUT` → exits 2 with the message, and the
   `OUT` it created is gone (D4).

Red-first: today's `check-work-space.sh` ignores `-Pi` entirely, so (1) and
(4) exit 0; today's scripts have no guard at all, so (5) and (7) run pytest.

## 5. STOP rules

- **STOP-0**: measurement says a complete run needs more than the floor →
  raise `PMTEST_MIN_BASETEMP_INODES` with the number; the generic 200 000 floor
  is not the one that moves.
- **STOP-1**: killing the byte check to make room for the inode check, or
  changing `check-work-space.sh`'s exit codes/argument → STOP; both
  protections must stand.
- **STOP-2**: the guard refuses the *default* path on this host (`/var/tmp`
  has 10.7 G inodes — it cannot) → the numbers are wrong, STOP.
- **STOP-3**: the override becomes a silent bypass (an unset-vs-empty
  confusion, an override that also lowers the byte check) → STOP; the two
  knobs stay separate and both remain visible.
