# 06.756 — the space preflight must see inodes, and a basetemp must not land on a 1M-inode tmpfs

Status: proposed

## 0. What this fixes

`LLM/tools/check-work-space.sh` answers "is there room for a big run?" with
`df -Pk` size fields only. On 2026-11-15 a full `gate.sh` run with its
`--basetemp` under `/tmp` exhausted that filesystem's **inodes** while **63 G
of space were still free**: `/tmp` is a tmpfs with 1 048 576 inodes, the
suite's basetemp held 1 276 per-test directories of copied fixtures
(962 145 files at the peak, measured on the directory tree), and the suite
reported **182 errors and 2 failures** (`2 failed, 4776 passed, … 182 errors`),
all `OSError: [Errno 28] No space left on device` / `touch: cannot touch …`. That
is exactly the confusion the preflight exists to prevent: a full disk that
reads as a product regression. The re-run on the identical tree, with the
output under `/var/tmp` (10.7 G inodes), was green.

Why it happened even though the tooling anticipates it: `gate.sh` defaults its
`OUT` to `mktemp` under `${TMPDIR:-/var/tmp}` — correct — but nothing stops a
caller passing an `OUT` (or `--basetemp`) on a small-inode filesystem, and
`check-work-space.sh` has no opinion about inodes, so the preflight said "ok".

Grounding (all verified on this host):

| Where | What |
|---|---|
| `LLM/tools/check-work-space.sh` | `df -Pk "$d" \| awk 'NR==2 {print $2, $4, $5}'` — size in 1K blocks, no `-i` |
| `pmtest/scripts/pytest-parallel.sh:34` | `basetemp="${PMTEST_BASETEMP:-/var/tmp/pytest-parallel}"` |
| `pmtest/scripts/pytest-parallel.sh:38-43` | accepts `--basetemp <dir>` / `--basetemp=<dir>`, no filesystem check |
| `LLM/tools/gate.sh` | `OUT=${1:-$(mktemp -d "${TMPDIR:-/var/tmp}/gate.XXXXXX")}`, then `--basetemp="$OUT/pytest"` |
| `/tmp` vs `/var/tmp` | 1 048 576 inodes vs 10 737 418 240 (`df -i`); measured demand 962 145 for one full run |

## 1. Decisions `[default sicuro]`

- **D1 — the preflight reports and gates on inodes too, with an absolute
  floor, not a percentage.** A percentage is meaningless across these two
  mounts: 50 % of `/tmp` is 524 288 inodes — far below the ~962 000 one run
  needs — so a percentage rule would say "ok" right before the failure. Add
  an inode row per mount (`df -Pi`) and fail when free inodes are below a
  floor (`MIN_INODES`, default **200 000**), which catches a mount already in
  trouble without pretending to size a suite.
- **D2 — the real guard is on the basetemp: refuse a filesystem that cannot
  hold a run.** `pytest-parallel.sh` and `gate.sh` resolve the filesystem of
  the basetemp/`OUT` they will use and refuse when it has fewer than
  **1 500 000** free inodes (measured demand ~962 000 plus ~55 % headroom),
  printing the number, the default path and the reason. `PMTEST_BASETEMP`
  and an explicit `--basetemp` are both checked. This is the guard that would
  have turned today's 182-error run into one clear sentence.
- **D3 — the two tools keep their contract.** `check-work-space.sh` stays
  read-only, exits 0/1/2 as today, keeps the byte behaviour and its
  `[min_percent]` argument, and prints the inode line unconditionally so a
  human sees both numbers; the new failure is the same exit 1 with a message
  naming inodes.
- **D4 — no heuristics in the suite.** Nothing parses pytest output for
  ENOSPC. The preflight refuses before the run; a run that fails anyway stays
  a run that fails.

## 2. The pin

Shell logic, so the pin is a Python test in
`pytests-contract-suite/test_harness_guards.py` (new file):

1. build a scratch dir with a `df` shim on `PATH` that answers `-Pk` with
   plenty of free space and `-Pi` with `_free_inodes=150` (below the floor);
2. run `sh LLM/tools/check-work-space.sh`, assert exit 1 and that the message
   names inodes;
3. second shim: bytes low, inodes plenty → exit 1, message names **space**
   (the old behaviour must not be lost);
4. third shim: both fine → exit 0 and both rows printed;
5. for D2, a shim `df` that reports the basetemp's filesystem as short of
   inodes → `pytest-parallel.sh` exits non-zero **before** running pytest
   (assert its message, and that no basetemp was created).

Red-first: today's script ignores `-Pi` entirely, so (1) exits 0 — the test
fails. The same for (5).

## 3. Steps

1. S0 — measure, do not guess: on this host, record `df -i /tmp /var/tmp`,
   the inode count of a finished `PMTEST_BASETEMP` from a full run (a fresh
   one if none is around), and the observed 182-error log as the evidence
   that the failure mode is real. `docs/evidence/06.756/`.
2. S1 — `check-work-space.sh`: inode row + floor (D1, D3).
3. S2 — `pytest-parallel.sh` and `gate.sh`: the basetemp filesystem check
   (D2), with the message naming the default and the measured demand.
4. S3 — the pin (§2), red-first per case.
5. S4 — `pytest-parallel.sh` twice (both green), `gate.sh` once, and one
   deliberate misuse (`--basetemp=/tmp/x`) captured showing the refusal.
6. S5 — close: #756 `DONE` with commits and the two runs;
   `LLM/what-this-proves.md` paragraph (the false red, the two numbers, the
   refusal); `LLM/tools/scope/README.md` or the script headers updated where
   they describe the preflight.

## 4. STOP rules

- **STOP-0**: measurement says a full run needs more inodes than the floor
  assumed → raise the floor with the number, never lower the guard.
- **STOP-1**: killing the byte check to make room for the inode check, or
  changing `check-work-space.sh`'s exit codes/argument → STOP; both
  protections must stand.
- **STOP-2**: the basetemp check refuses the *default* path on this host
  (`/var/tmp` has 10.7 G inodes — it cannot) → the numbers are wrong, STOP.
- **STOP-3**: any change that makes a legitimately small basetemp (a caller
  who knows what they are doing) impossible to run → STOP and discuss; the
  guard is about capacity, not policy.
