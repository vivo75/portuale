**Goal:** `portage-dep` parses Portage's full atom grammar (build-ids,
extended/wildcard atoms, every EAPI rule), and each place portuale reads an
atom applies exactly the flags Portage applies there — so a package, a
config line or an argument that Portage rejects is rejected the same way,
with the same message, and nothing Portage accepts is rejected.

**Architecture:** one parser with options instead of one fixed superset.
`portage_dep::eapi` ports `_get_eapi_attrs`; `portage_dep::parse_atom_with(s,
&AtomOptions) -> Result<Atom, AtomError>` ports `Atom.__init__` (its regexes,
its post-parse checks, its error texts); `parse_atom(s)` stays as the
`eapi=None` default every current caller already means. Each *context*
(ebuild/binary deps, installed deps, profile files, user config, command
line, exclude options, sets) then gets its own options and its own failure
behaviour (mask / drop-with-warning / abort), one slice per context.

**Tech Stack:** Rust (`portage-dep`, `portage-profile`, `portage-repo`,
`portuale`), pmtest contract suite + atom harness differential
(`python-harness/atom_harness.py` vs `crates/atom-harness`), container bed.

**Spec:** the backlog entry and the oracle report. Portage = 3.0.82.2 as
installed (vendored copy byte-identical, oracle §"What these citations point to"), **including its native C parser** (`portage.dep._parser`, on by default).

## 0. Read this first

### 0.1 What Portage does (oracle summary — read the report for citations)

1. **Grammar has no EAPI input.** `_get_atom_re`/`_get_usedep_re`/`_get_atom_wildcard_re` ignore `eapi_attrs`; only the slot regex varies (`slot_operator`). EAPI checks run after the parse and **only when `eapi is not None`**: `slot_deps`, `use_deps`, `use_dep_defaults`, `strong_blocks` (category `EAPI.incompatible`), conditional use-dep flags vs `is_valid_flag` (`IUSE.missing`).
2. **`::repo` and build-ids are caller flags.** `eapi=None`: both allowed by default. `eapi` given: `allow_repo` defaults to `repo_deps` = **False for every EAPI 0–9**, `allow_build_id` falsy. Unsupported EAPI string ⇒ the permissive `None` attrs, but `allow_build_id` still off.
3. **Per context** (oracle Q2): ebuild and binary deps parse with `eapi=pkg.eapi`, `is_valid_flag=iuse.is_valid_flag`; any failure masks the package `invalid: <KEY>: Invalid atom (<atom or message>), token <N>` (first bad token per key; `N` = 1-based whitespace token position counting `(`, `)`, `||`, `flag?` — live: `'x? ( a/b ) c/d::x'` → token 5). **Order of reasons:** keys are visited in `_dep_keys` order (`BDEPEND DEPEND IDEPEND PDEPEND RDEPEND`) but each error is filed under its category (`dependency.syntax`, `IUSE.missing`, `EAPI.incompatible`; Package.py:534-557) and the display iterates the categories in first-insertion order (depgraph.py:12560-12563) — so BDEPEND IUSE.missing + DEPEND syntax + RDEPEND IUSE.missing prints BDEPEND, RDEPEND, DEPEND (review I-1, proven). **Categorized** errors (IUSE.missing, EAPI.incompatible) print `<KEY>: <message>` without the `Invalid atom (…), token N` wrapper. Structural errors come from `use_reduce` itself (`expected: dependency string, got: ')', token N`, `missing whitespace around '(' at 'a/b(', token 1` — checked *after* the atom fails, dep:1031-1041 —, `Invalid token '%s', token N`); `^^`/`??` are not operators in dep strings (`^^` → `Invalid atom (^^)`, `??` → IUSE.missing on flag `?`). Unbuilt ebuilds also reject `:slot/sub=` (`Improper context for slot-operator "built" atom syntax: <atom>`, `Package.py:347-356`): only for a key that parsed cleanly, one reason per built atom. Profile files drop bad lines with `--- Invalid atom in <file>: <msg>`; user config the same with looser flags; command line aborts `!!! '<x>' is not a valid package atom.`; `--exclude`-style options abort through `parser.error`; named sets print `<file>: Validation failed at line: N, data X` after the merge list; the world file drops silently.
4. **Installed deps** validate with `eapi=None`, which in this Portage takes the native C `use_reduce` path, and that path **rejects `::repo` and build-ids** (a quirk of the native parser, oracle Q1 "use_reduce() does diverge"); depgraph traversal of installed deps uses `eapi=pkg.eapi` (`depgraph.py:4352-4379`).

### 0.2 What portuale does today (oracle Q4 + this plan's reading)

- `crates/portage-dep/src/lib.rs`: one superset regex (`atom_regex`), no EAPI input, no build-id, `::repo` always accepted, `WildcardAtom` only for `*/*`, `cat/*`, `*/pkg`.
- **Real bugs found by the oracle** (fixed in S2): `=cat/foo-1-2` (and `>=`/`~`, `=…-1-2*`) parses as package `foo-1` version `2` — Portage reads build-id 2 (`eapi=None`) or rejects; `SLOT` rejects a leading `_` that Portage accepts (`dev-libs/foo:_a`); `VER` uses Unicode `\d` (Portage `re.ASCII`; `=dev-libs/foo-١` accepted by portuale).
- The only `invalid:` mask is `invalid_use_conditional_reasons` (`crates/portage-repo/src/masked_deps.rs:296`, IUSE-missing conditionals, Portage text already); `first_invalid_conditional` skips atoms it cannot parse. No `Invalid atom (…), token N`, no `Improper context`.
- `portage-profile` reads every `package.*` line raw (`package_files.rs:10 read_config_lines`), does not read profile `eapi` files, and validates nothing; atoms are matched later via `crates/portage-repo/src/config_match.rs:8 matches_config_entry`.
- EAPI predicates are scattered: `crates/portage-repo/src/md5_dict.rs:20-94` (`eapi_is_supported`, `eapi_has_slot_operator`, `eapi_empty_groups_always_true`, `eapi_has_iuse_effective`, `eapi_has_idepend`) parse digits by hand, with their own normalisation (trim; `""` → false; unsupported `"10"` → idepend/iuse_effective **true**, where Portage's permissive set says false, eapi.py:262/264). Callers: `pass/enqueue_deps.rs:58`, `installed_meta.rs:146-162`, `conflict_use_display.rs:108`.
- `portage-repo::Candidate` already has `build_id: Option<String>` for binaries (candidates.rs:48, binary_index.rs:312) but **no EAPI field**; binary candidates all have an empty `repo_location` (binary_index.rs:296).
- `crates/portage-use-reduce` already ports `use_reduce` flat mode with Portage's structural messages, differentially tested by `use-reduce-harness`; S4 builds on it.
- `use_flags.rs:470-483 atom_specificity` returns −2 for anything `parse_atom` rejects; `CpBucketIndex::build` (config_match.rs:38-52) relies on `parse_atom` *failing* for wildcards to route them to `other` — the default `parse_atom` must keep rejecting extended atoms.
- 189 `parse_atom(` call sites in 72 files outside `portage-dep` (2026-10-11). They keep calling `parse_atom` (= `eapi=None`), which is what Portage's internal re-parses use too (`match_from_list` re-parses with `allow_wildcard=True, allow_repo=True`, oracle Q3). Only the *entry points* of each context change.
