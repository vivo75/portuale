# 04.755 — remove the `resolvo` solver backend (closes #33; the #702 cut becomes moot)

Status: proposed

## 0. Owner ruling (read first)

Owner, 2026-11-14: *"resolvo never worked and carries complexity the project
does not need"* — the value **disappears**, it is not kept behind a
special rejection. After this slice `--solver=resolvo` behaves exactly
like any other unknown value. `--solver=pubgrub` and the default path are
out of scope and must come out of the slice byte-identical.

Two entries ride with it: **#33** (`--solver=resolvo` cycle
linearization — `install_order` cannot order a toolchain-cycle closure)
ceases to have a subject and closes with the reason recorded; **#702**
(already `DONE` as CUT-12, "`--solver=resolvo` runs no perl co-upgrade")
keeps its `DONE` and gains one sentence saying the cut is moot because the
subject is gone. Neither is deleted.

## Decisions (all `[default sicuro]`; no open `[BLOCCA]`)

- **D1 — the removal is total.** No `SolverKind` variant, no importable
  shim, no "this solver was removed" branch. `--solver=resolvo` exits 2 with
  the ordinary unknown-value message naming `portage` and `pubgrub`.
  Rationale: the owner's word is *disappears*; a bespoke refusal would keep
  the value in the CLI contract and in every future reader's head.
- **D2 — the message shape is kept, only its value list shrinks.**
  `emerge: --solver: "sat" is not "portage" or "pubgrub"\n` (the existing
  two-item/three-item grammar decided by the count), and the `--help` line
  reads `portage (default) or pubgrub`. No other wording change.
- **D3 — `3rdparty/` is annotated, never deleted.** One line each in
  `3rdparty/README.md` and `repos.toml` saying the reference checkout's
  `portage-atom-resolvo` is upstream-only and never a build input here.
- **D4 — proof of no collateral damage, by fingerprint.** `--solver=pubgrub`
  and the default path must be byte-identical before/after on: (a) the whole
  contract suite (4960 cases), (b) a fixed set of `--solver=pubgrub`
  `--pretend`/`--json` probes on fixtures plus the L0 pubgrub bed's own
  probe list. Any moved stdout/stderr/rc is a STOP, not a pin to update.
- **D5 — `Cargo.lock` may only lose entries.** Acceptable: the two packages
  and any transitive crate no surviving package uses. A *version change* of
  a surviving crate is a STOP (it would move behaviour for a slice whose
  whole claim is "nothing but resolvo changes").
- **D6 — the recorded reason survives its comment.** The pin-waiver comment
  at `portage-repo/Cargo.toml:41` explains why the two versions were
  exact-pinned; it goes with the deps, and its substance is restated in the
  #755 close-out so the next reader knows the pins were deliberate, not
  incidental.

## STOP rules (not negotiable; S0/S1 enforce them)

- **STOP-0** (S0.1): any live path to `ResolvoResolver` other than the
  `--solver=resolvo` selection → STOP with `NEEDS_CONTEXT`. Remove nothing;
  a backend reached by a second door is a feature, not dead weight.
- **STOP-1** (S1.5/S3): any pubgrub or default-path output differs from its
  S0 fingerprint → STOP and bisect; do not adjust pins.
- **STOP-2** (S1.4): a surviving crate's version moves in `Cargo.lock` →
  STOP.
- **STOP-3** (S1.1): a test or pin depends on `resolvo` beyond the five
  sites listed under Grounding → STOP and report it; the list above is the
  whole inventory and an unlisted dependency means the inventory is wrong.

## Review focus (what an adversarial review should attack)

1. **The inventory's completeness**, not its list: can `ResolvoResolver` be
   reached through a path the grep cannot see (a trait object built by
   name, a match arm on a string elsewhere, a feature flag)?
2. **D5's lock claim**: run the removal and check whether a *shared*
   transitive crate (e.g. `fixedbitset`, `petgraph`, `version-ranges`)
   disappears or moves — pubgrub's behaviour must be untouched, and a
   vanished shared crate is exactly where a silent change would hide.
3. **The three pins**: does updating them hide a behaviour change rather
   than a text change? Compare the binary's `--help` and error output
   before/after, not just the pin.
4. **`#702`'s disposition**: is "moot" honest, or does the cut record a
   real user-visible limitation that exists independently of resolvo?
5. **The claims in the close-out**: every number (suite totals, probe
   fingerprints, lock diff) must be reproducible from the committed tree.
