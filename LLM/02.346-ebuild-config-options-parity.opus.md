### 0.2 #347: command-line options

1. `--getbinpkg-exclude`/`--getbinpkg-include` are parsed (`pretend/args.rs:1035-1040`) and validated (`pretend/cli_atoms.rs:112-153`) and then never read. Portage filters the **remote index at load time**. `bintree.populate` gets them through `actions.py:167-173`/`:436-442`. `_populate_remote` (`bintree.py:1410-1460`) folds the CLI sets into each binrepo's own `getbinpkg-exclude`/`getbinpkg-include` keys and prints conflict warnings. `bintree.py:1825-1846` then skips excluded entries before they reach the dbapi. CLI conflicts are warned and removed at `actions.py:2928-2945`. The per-binrepo keys (`binrepo/config.py:42-75`, with their own `!!! … invalid in getbinpkg-exclude attribute for binrepo [x]` warning) are not parsed by portuale either (`portage-profile/src/binrepo.rs:110-125` knows `sync-uri`, `priority`, `location`, `verify-signature`, `frozen`). Portage supports a `file://` binhost (`bintree.py:1564-1569`), and the pmtest fixture binhost is `file://` (`fixtures/etc/portage/binrepos.conf`), so a hermetic host oracle is possible.
2. Partly-masked/partly-excluded top-level target: `top_level_atom_entirely_excluded` (`portage-repo/src/resolve/pass/top_level_unsatisfied.rs:21-31`) ports only the all-excluded half. The doc comment records the corner as "documented, not pinned".

### 0.3 #349: `ebuild` configuration

Probe: #350 recipe repo, `make.conf` with `DISTDIR`, `PORTAGE_TMPDIR`, `FEATURES` and a `PROBE_OUT` path; `pkg_setup` dumps the variables. `env -u PORTAGE_TMPDIR -u DISTDIR -u FEATURES`, `ebuild p-1.ebuild setup`:

| variable | Portage | portuale |
|---|---|---|

| `PORTAGE_ACTUAL_DISTDIR` | make.conf `DISTDIR` | `/var/cache/distfiles` |
| `PORTAGE_TMPDIR` / `PORTAGE_BUILDDIR` | make.conf value / `<tmp>/portage/t/p-1` | `/var/tmp` / `/var/tmp/portage/t/p-1` (it **wrote into the host's `/var/tmp/portage`**; removed by hand) |
| `PORTAGE_CONFIGROOT` | `<cfg>/` | `<cfg>` |

- The backlog claim "the build directory loses Portage's `/portage/` infix" is **wrong**: both have `<tmp>/portage/<cat>/<pf>`. Only the tmpdir differs. Code: `ebuild.rs:221-251` (`portage_tmpdir_from_env`, plus the `package.env` override only), when `portage_repo::portage_tmpdir_from_config` (`env_roots.rs:29-37`) already exists and is used by `emerge`.
- The backlog claim "`emerge` honours the config" is **wrong for `DISTDIR`**. Every path takes it from the process environment or `/var/cache/distfiles`: `ebuild.rs:255-257`, `pretend/resolve_plan.rs:214-219` (fetch-restrict column), `pretend/env_config.rs:66-68` (`PackageOptions`), `ebuild_merge/options.rs:110`. The beds and the pmtest suite export `DISTDIR`, which is why nothing noticed. Portage takes it from the config (`config.py:3409-3410` sets `PORTAGE_ACTUAL_DISTDIR`; `doebuild.py:487`).
- `FEATURES` in the phase environment is the raw process value (`ebuild_phases/sandbox.rs:111-113`, `phase_features_value`, pushed by `phase_env.rs:194-196`). The direct path only folds a matched `package.env` value (`standalone_config.rs:460-480`). Precedent for reading the resolved config: #335 (`config_features_string(config)` for `emerge -C`). **make.globals:** portuale reads it relative to `config_root` (`scalar_layers.rs:80-84`, "absent under tests"). Portage reads it from its install path (`config.py:466-474`, `const.py:66-68`), whatever `PORTAGE_CONFIGROOT` is. So under `ROOT=/` both see the same file; in a hermetic configroot portuale sees none. That is settled design (#335 and the `--info` work both rely on it). Pins that need make.globals values put a copy at `<cfg>/usr/share/portage/config/make.globals`.
- `ARCH`: Portage filters each `USE_EXPAND_UNPREFIXED` variable to the flags in the package's `USE` (`config.py:2249-2255`). The fixture profile's `ARCH="amd64"` is not in USE, so `ARCH=""`. portuale exports the raw `amd64` (D5, emerge path too).
- `PORTAGE_CONFIGROOT` gets its trailing slash from `LocationsManager.py:80-82`.
- **Not in the backlog:** `PORTAGE_REPO_NAME` is set only by the emerge path (`emerge_build/entry_env.rs:174`). The direct path never sets it, so `die` prints `ERROR: cat/pf:: failed` (`bin/isolated-functions.sh:135, 160-161`). D16's "drops the `::repo` suffix" is this, not an output problem.
- D18 (binary layout): the direct path's `binpkg_multi_instance` reads the process `FEATURES` only (`ebuild.rs:465-480`). The emerge path uses `feature_on` (`pretend/env_config.rs:80-83`). `PackageOptions::binpkg_multi_instance` is documented as "opt-in (default `false` here, a deliberate conservatism)" (`ebuild_package.rs:56-60`), while Portage's make.globals has it on (`make.globals:78`). The multi-instance layout itself is already implemented and Portage-shaped: `<pkgdir>/<cat>/<pn>/<pf>-<bid>.<suffix>` (`ebuild_package.rs:768-775`, matches `bintree.py:2607-2640`). The backlog's `<pf>/<pf>-<build-id>` spelling is inexact.

### 0.4 #351: build-command output

Probe: #350 recipe, `ebuild p-1.ebuild unpack`, `unpack` again, `compile`, `test`, `install`, everything via `2>&1`:

- **portuale prints nothing at all** apart from `Forcing test.` (shipped by #348 S3; that part of #351 is stale) and the two `Final size` lines. Portage prints `* checking ebuild checksums ;-) ...` (`digestcheck.py:49`), `>>> Unpacking source...`/`>>> Source unpacked in …` and the other `__vecho` markers (`phase-functions.sh:378` etc.), `>>> Test phase [not enabled]: t/p-1` (`:630`), `>>> Existing ${T}/environment for 'p-1' will be sourced. Run 'clean' to start with a fresh environment.` (`/usr/lib/python-exec/python3.14/ebuild:375-381`), `>>> WORKDIR is up-to-date, keeping...` (`doebuild.py:1251`; `>>> Not marked as unpacked; recreating WORKDIR...` at `:1208`), and per stamped phase `>>> It appears that '<phase>' has already executed for '<pf>'; skipping.` + `>>> Remove '<builddir>/.<phase>ed' to force <phase>.` (`doebuild.py:2395-2412`; stamp name `f".{mydo.rstrip('e')}ed"`, skipped under `FEATURES=noauto` for `install`).
- **Root cause of the missing markers:** `phase_env.rs:183` hard-codes `PORTAGE_QUIET=1`, and `__vecho` is silent under `__quiet_mode` (`bin/isolated-functions.sh:209-215`). Portage sets it only for `noiselimit < 0` (`doebuild.py:500-501`) and for the Scheduler's digest-prefetch clone (`Scheduler.py:801-805`). `--quiet-build` is a log redirect, not `PORTAGE_QUIET`.
- **Streams:** Portage sends *all* phase output (the bash's stdout and stderr) through the build-log tee to **stdout**. A probe with `2>/dev/null` shows every line above; stderr carries only the config warnings. It also writes `${T}/build.log`. portuale's direct path runs with `log_file: None` (`ebuild.rs:351`), so the bash's stderr (`eerror`, `einfo`, the `die` block) lands on stderr, no `build.log` exists, and `die`'s `The complete build log is located at '…'` line (`isolated-functions.sh:176-184`) never prints. D16 is therefore this tee (stream and `build.log` line) plus `PORTAGE_REPO_NAME` (0.3).
- **The order matters:** after `PORTAGE_QUIET` is dropped, the vendored bash's *own* stamp checks would start printing a different text (`>>> It appears that 'p-1' is already pretended; skipping.`, `phase-functions.sh:340, 354, 502, 538, 570, 602, 655`). Portage never reaches them, because Python returns before `_spawn_phase`. So the Rust-side stamp check (S5) must land **before** the un-quieting (S6).
- `qmerge` listing (D14): Portage's merge prints `* checking N files for package collisions`, `>>> Merging <cpv> to <root>/`, one `---`/`===`/`>>>` line per entry, `>>> Safely unmerging already-installed instance...`, `--- replaced …`/`<<< …` per old entry, `>>> Original instance of package unmerged safely.`, `>>> <cpv> merged.` (capture `LLM/evidence/2026-10-12-348-s0/b/b-phases-t348-b-phases-7-portage-ebuild-qmerge.stdout`). **portuale prints none of this on any merge path**. The only merge-time `>>>`/`<<<` lines are preserve-libs (`ebuild_merge/plib_merge.rs:307`, `plib_unmerge.rs:356`) and backup packages. So this is merge-engine-wide, not `qmerge`-specific.
- Auto-clean: **`AUTOCLEAN="no"` in make.globals (`make.globals:103`).** `action_build` auto-cleans only when `settings["AUTOCLEAN"] == "yes"` (`actions.py:694-704`). Two things force it to yes: `run_action` after `_global_updates(...)` returned True (`actions.py:3671-3691`, bug #792195) and depclean (`:809-813`). The auto-clean seen in the #348 captures (`b-env-portage-emerge-binpkg8.stdout` lines 2 and 51) is a side effect of the hermetic configroot's global updates, not the default; on a real system with recorded updates and no user setting Portage prints none. When it runs, it is a system-wide `unmerge(…, "clean", [], autoclean=1)` after a successful merge. That run prints `>>> No outdated packages were found on your system.` (`unmerge.py:316-319`) or *unmerges* the outdated packages. portuale has the selection already (`pretend/removal/prune_clean.rs`, the `--clean` action, which prints the same line at `:307`).
- Global updates: portuale applies `profiles/updates` moves at read time (`portage-repo/src/updates.rs`) and never rewrites the vdb, binpkgs or `mtimedb`. Portage's `Performing Global Updates` block announces exactly those writes. In the hermetic probes Portage prints it on every run, because it cannot record them.
- News: portuale has the relevance/count code (`--check-news`, `NewsSet`), but `scope-backlog.md` Part 3 lists news items as not in scope and the `.unread` write side is a documented cut. The #348 harness ran with `FEATURES="-news"` and stripped both blocks (b-env-phases.md "Harness").
- Masked aborts: `show_resolution_header` (`pretend/merge_list.rs:763-813`) runs only for non-`--pretend` and is skipped on the top-level all-masked arm. Probe: `emerge --oneshot dev-libs/bareacceptkeywordspkg` prints `Calculating dependencies ... done!` + `Dependency resolution took …` on stdout (rc 1) in Portage, while portuale's stdout is empty. Under `-p`, Portage also prints `These are the packages that would be merged, in order:`. portuale's `--pretend` prints the preamble only on the `gated_abort_partial` arms (`merge_list.rs:419-450`) and never on success, which is a long-standing convention of the pinned `--pretend` output.
