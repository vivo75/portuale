## Execution Protocol (opencode manager + subagents)

The manager is the opencode session's top-level LLM. It does not write
product code; it briefs, reviews, verifies and commits.

**Branch.** `fix/2026-10-25-review`, opened in Task 0 in `portuale` *and*
`../pmtest` from their current `main`. Every slice commits on it. Leave both
`main`s alone.

**Order.** Tasks run in number order, 0 → 21, then the close-out. Task 1
goes first because the defect it removes is already on pushed `main` and
damages hosts that also run Portage. Task 20 (comment sweep) runs after
every code task so it does not conflict with them. Run implementers **one at
a time**, never two writers in parallel (they share `target/` and the pmtest
corpus).

**Per slice, the manager:**
1. Writes the implementer brief: task text verbatim, the files to touch, the
   oracle to use, the exact RED/GREEN commands, and the line *"Do the work
   yourself. Do not start sub-agents or tasks."* (opencode sub-agents run
   inside `opencode serve` and outlive their parent). Dispatch it with
   opencode's own subagent mechanism; check in the subagent's log which
   model actually ran (if the manager instead shells out to `opencode run`,
   pass `--model` explicitly and wrap it in `LLM/tools/scope/oc.sh`). Never
   `pkill`. Space parallel launches ≥60 s (only read-only oracle/analysis
   workers may run in parallel with an implementer).
2. Waits until the worker exits **and** its files stop changing; then
   reviews the diff itself against the task and the Global Constraints
   (oracle cited in the test docstring, real-md5 cache entries for new
   ebuild fixtures, short comments + code-notes, no unrelated churn). Sends
   fix-ups to a fresh worker, not the same files under a live one.
3. Runs the full gate itself (Global Constraints). Failures are compared
   **by test name** against `LLM/evidence/2026-10-25-review/baseline.txt`;
   `git clean -fdq fixtures/` in pmtest if order-dependent fixture
   pollution shows up. Corpus drift is read line by line before any
   `PORTUALE_CORPUS_BLESS=1`; unexplained drift blocks the commit.
4. Commits: pmtest half first (fixtures, pins, bless, bed logs), then
   portuale (code, unit tests, `LLM/` docs, code-notes index), the portuale
   message quoting the pmtest short SHA and the pmtest message naming the
   branch and the backlog item.
5. Updates the docs in the same commit: backlog entry (narrowed, or DONE
   with date, branch and the sibling SHA), one appended
   `LLM/what-this-proves.md` paragraph for any slice that changes
   behaviour.

**Owner gates (any new question).** The owner may not be present. At a gate
the manager writes the analysis plus a crisp question with a recommended
answer to `LLM/evidence/2026-10-25-review/OWNER-QUESTION-<task>.md`,
commits it (docs-only, standalone), and **moves on to the next task** — it
never implements on a guessed ruling. The final report lists every open
gate.

**Bed runs.** Copy the binary first and run frozen so cargo stays usable:
`cp -p target/release/portuale /var/tmp/bedbin/portuale`, then
`PMTEST_PM=portuale-bed PMTEST_NO_BUILD=1 differential-test-bed/run/<runner>.sh`
from `../pmtest`. Fetching runs need
`GENTOO_MIRRORS=http://$(ip -j -4 -o addr show eth0 | jq -r .[0].addr_info[0].local):8080`.

**Stop conditions.** Stop (commit nothing further, report) if: the merge
gate fails; a keeper pin (#54 K3, #222, #223, #35 R4) goes red after one fix
round; corpus drift cannot be explained; a non-target L0 probe moves. Clean
`/var/tmp` of leftovers at the end.

### Task 2: merge-wait queues every gated merge and drains like Portage

**Defects.**
1. `emerge_build/scheduler.rs:946`:
   `if (wait_set.contains(&idx) || hold[idx]) && in_flight > 0 { queue } else { land }`.
   With A and B building under `merge-wait` (on by default,
   `make.globals:80`), A finishes → queued; B finishes with
   `in_flight == 0` → lands **before** A. Portage never lands a gated merge
   directly: `_build_exit` appends it to `_merge_wait_queue`
   (`Scheduler.py:1833-1836`, not under `--buildpkgonly`) and the queue is
   drained FIFO.
2. The drain itself differs. Portage, once no job and no merge runs, moves
   **the whole queue** into the merge task queue in one pass, stopping
   before a system package only when the merge queue is already non-empty
   (`Scheduler.py:2245-2270`). portuale lands **one** queued merge and then
   reschedules (`scheduler.rs:825-830`), so builds freed by that merge can
   start between two queued merges.
