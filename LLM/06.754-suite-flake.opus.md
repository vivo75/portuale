## 2. Hypotheses, ranked

- **H1 (strongest): any concurrent worker holding the vdb lock against
  shared `FIXTURES` flickers `var/db/.pkg.portage_lockfile` between the
  clean copy and the noop copy.** The holders are `fixture_env`-ROOTed
  `emerge` runs (`pretend/mod.rs:272-283` → global updates on every
  `emerge`, even `-p`), not `mrg --check-world`, which is read-only (§0).
  Under `-n8` some worker is almost always inside such an `emerge` against
  `FIXTURES`; the lockfile exists only for the lock hold, so the two
  `copy_tree` calls land on opposite sides of a flicker. Serially the
  window is empty, hence green alone / `-n4`. Already evidenced by the
  02.745 log quoted in §0.
- **H2 (weak): `tmp_path` / `work/op.name` collision across xdist
  workers.** Would need two workers sharing a work dir; `tmp_path` is
  per-test unique, so expect S0 to rule this out by logging the work dir.
- **H3 (STOP rule): `mrg --check-world` persistently mutates the tree it
  checks.** Contradicted by the unlink-on-release code cited in §0, but if
  S0 observes persistence, H1/H2 are wrong and §4 applies instead of §3.

## 4. S1 — the fix, sized to the mechanism

Pick by S0; do not mix.

- **If H1 (flickering lockfile from concurrent runners): harness
  isolation, no product code.** The mutant harness must not see
  lockfiles as tree content. Fix in
  `differential-test-bed/compare/check-world-mutants.py`: `snapshot()`
  (lines 79–87; `changed` starts at line 90) skips volatile lock names
  per the in-tree rule `vdb_rw.rs:44-52` (`is_volatile_name`: `.` prefix
  + `.portage_lockfile` suffix / `.portage_lockfile.hardlock-` /
  `-inode-test`), which ports Portage's `locks.py`
  (`lockfile`/`unlockfile`, `unlinkfile=1`; in-tree pointers
  `portage_lock.rs:2-6,21-22,75-79`, `files_write.rs:324-329`) — plus
  the `tests_consumer_pin_conflict.rs:20` precedent that already filters
  this exact name. One filter, not a copy-on-write rework: `run()`
  already isolates mutants in per-op copies; the leak is the
  *observation*, not the isolation.
  The committed pin is **(a) a hermetic `snapshot()`/`changed()` unit
  test** (pmtest side, e.g. in `test_check_world_mutants.py`): build two
  tiny trees under `tmp_path`, plant `.pkg.portage_lockfile` and a
  `.pkg.portage_lockfile.hardlock-<pid>` sibling in one, assert
  `changed(before, after) == []` — red-first (fails before the
  `snapshot()` filter, green after). **(b)** the S0.2 hammer+probe log
  stays one-off before/after evidence quoted in the commit message, and
  **(c)** the standing `-n8` suite is the gate. Do **not** commit a
  live-`FIXTURES` hammer or any test that writes the shared tree.
- **If H2 (work-dir collision — not expected):** unique-ify `run()`'s
  `work / op.name` (pid/worker id suffix). Same pin shape: deliberate
  parallel run, before/after.
- **If H3 (persistent mutation by the check): STOP.** Do not work around
  it in the harness. Re-scope: the defect is product-side (a check
  writing the tree), belongs in the #754 trace as a re-scoped product
  bug, and any harness change waits for the product fix.

In all cases: no fixture changes (no ebuild/md5-cache involved), no
corpus impact (no `emerge --pretend` output moves; if the run reports
drift, it is unrelated — stop and look).
