## 2. New findings

### Critical

**C-1 (proven). S2 opens a behaviour regression that only S9 closes: `=…-<bid>` atoms match ebuilds.**

- **What S2 changes.** `parse_atom` (default options = Portage `eapi=None`) starts accepting build-ids. Today `=dev-libs/foo-1.0-2` → `None`, and `=dev-libs/foo-1-2` → package `foo-1` version `2`.
- **What is missing.** portuale's `match_from_list` (lib.rs:772-790) has no build-id check, and the plan defers that check to S9.
- **What Portage does.** `=` + build-id never matches a `_pkg_str` whose build_id is None, i.e. any ebuild (dep:2994-3008). Live (`probe_match.py`): `=dev-libs/foo-1.0-2` → only `#2`.
- **The window, S2–S8:**
  - A user `package.mask` / `package.use` / `package.accept_keywords` line `=dev-libs/foo-1.0-2`:
    - Today: inert (`matches_config_entry` → false).
    - After S2: masks / changes **every** `foo-1.0` ebuild and binary.
  - The CLI `emerge -p =dev-libs/foo-1-2`:
    - Portage: `there are no ebuilds to satisfy` (oracle run5).
    - After S2, portuale would resolve `dev-libs/foo-1`.
- **Fix.**
  - Move S9's "an atom with `build_id` matches no candidate without one" rule into S2. In `matches_version`, `Eq` + `atom.build_id.is_some()` should reject any candidate string that carries no build-id; all of them carry none until S9.
  - Pin it with a unit test citing dep:2994-3008 and `probe_match.py`.
  - S9 then only adds the positive match for binary instances.
  - Define explicitly which portuale candidate strings model Portage's "plain string matches regardless". Portage's depgraph always passes `Package`/`_pkg_str`, so the answer should be "none".

**C-2 (proven). S3's example test asserts a result Portage does not produce.**

- **The assertion.** Plan:245 asserts `match_from_list("*/*::x", &c) == vec![c[3]]` with `c = ["dev-libs/foo-1.0", "dev-libs/foo-1.0-r1", "dev-libs/foo-10", "dev-libs/foobar-1.12::x"]`.
- **Portage's rule.** Candidates with no repo pass the repo filter (dep:3190-3203: `repo is not None and repo != _unknown_repo and repo != mydep.repo` → skip).
- **portuale today.** `matches_repo` (lib.rs:483-491) does the same.
- **Live result.** `match_from_list("*/*::x", <those strings>)` returns **all four**, and also all four as `_pkg_str` without a repo.
- **Why the oracle differs.** The oracle's `[foobar]` result used candidates with `repo="gentoo"` (`probe_match.py:3-8`).
- **Risk.** An executor will either "fix" `matches_repo` (breaking parity everywhere) or stall.
- **Fix.** Give the foo candidates `::gentoo`, as the oracle did, and keep `vec![c[3]]`. Or keep the plain strings and expect all four. Cite `probe_match.py` either way.

### Important

**I-1 (proven). S4's validator signature and reason order do not match `_validate_deps`.**

- **(a) Order is grouped by category, not `_dep_keys`.**
  - `_metadata_exception` files each error under its category: `dependency.syntax`, `IUSE.missing` or `EAPI.incompatible` (Package.py:534-557).
  - `_invalid` is a dict of lists.
  - The display iterates `pkg.invalid.values()` (depgraph.py:12560-12563).
  - So reasons come out grouped by category, in first-insertion order. Proven with Portage's own methods on a stub: with BDEPEND=`y? ( a/b )`, DEPEND=`c/d::x`, RDEPEND=`z? ( e/f )`, the output order is **BDEPEND, RDEPEND, DEPEND**.
  - The plan's "keys in `_dep_keys` order" (plan:53, :265) holds only when all reasons share a category. `t341-twokeys` is both `dependency.syntax`, so it would not catch this.
- **(b) Categorized errors drop the wrapper.** A categorized error (IUSE.missing **and EAPI.incompatible**) renders `<KEY>: <InvalidAtom msg>`, with no `Invalid atom (…), token N` wrapper. The plan states this only for IUSE.missing (plan:269).
- **(c) `Improper context` behaviour** (see I4 above): it runs only for keys that parsed cleanly, and produces one reason per built atom. So `validate_dep_string(..., built) -> Result<(), String>` (plan:267) cannot express it.
- **Fix.**
  - Have `validate_dep_string` return `Result<Vec<Atom>, DepError { category, text }>` with no `built` parameter.
  - Let `invalid_dep_reasons` run the `Improper context` loop over the returned atoms for unbuilt candidates, pushing one `(dependency.syntax, …)` per atom.
  - Bucket by category in insertion order.
  - Add an S0 cell mixing categories across keys, e.g. `BDEPEND="y? ( dev-libs/t341-dep )" DEPEND="dev-libs/t341-dep::a"` with `IUSE=""`, and one with two built atoms in one key.

**I-2 (proven). S4 re-implements the `use_reduce` walk instead of reusing the verified port, and misses what `use_reduce` itself raises.**

- **An existing port.** `crates/portage-use-reduce/src/lib.rs` already ports `use_reduce` (flat mode) with Portage's exact structural messages (`expected: dependency string, got: ')', token N`, `no matching '(' for ')'`, `expected: '(', got: …`, `Missing ')' at end of string`, …; lib.rs:36-101). It is differentially tested by `use-reduce-harness`.
- **Errors the plan's walker does not cover** (live, EAPI 8 with `is_valid_flag`):
  - `'|| ( )'` → `expected: dependency string, got: ')', token 2`.
  - `'x? ( )'` → same.
  - `'a/b('` → `missing whitespace around '(' at 'a/b(', token 1`. The check runs *after* the atom fails (dep:1031-1041, def at dep:788-796, and it also checks `||`). Plan:269's "dep:1016-1019 area … runs first" is wrong on both counts.
  - `'y? ( a/b )'` → `USE flag 'y' referenced in conditional 'y?' is not in IUSE`. This is raised by `is_active` at the matching `)` (dep:700-715), so an invalid atom *inside* an invalid conditional group is reported first.
  - `^^` → `Invalid atom (^^), token N`.
  - `??` → IUSE.missing on flag `?` (see I6).
  - Non-`InvalidAtom` exceptions → `Invalid token '%s', token N`.
- **Fix.** Add a token hook to `portage_use_reduce::use_reduce_flat`, plus an `is_valid_flag` variant of `is_active` (Portage builds the IUSE.missing error there instead of the useflag regex). Build `validate_dep_string` on it, and retire `first_invalid_conditional`. Then the structural messages stay harness-verified. Add S0 cells: `RDEPEND="x? ( )"`, `"a/b("`, `"^^ ( a/b )"`, and `"y? ( dev-libs/t341-dep::a )"` with `IUSE=""` (atom-first ordering).

**I-3 (proven). S1 is not a pure refactor as written.**

- Plan:162-163 rewrites the `md5_dict` helpers to `eapi_attrs(Some(e)).<attr>` and claims "identical".
- **Existing tests would fail** (md5_dict.rs:493-520):
  - They assert `eapi_has_slot_operator("") == false` and `eapi_idepend("")…`. `eapi_attrs(Some(""))` is the permissive set (slot_operator **true**).
  - They assert `" 8 "` is true. Portage's `Eapi(" 8 ")` raises `ValueError` (live).
- **Callers outside the floor would change:**
  - The helpers read unsupported `"10"` as idepend/iuse_effective **true**. Portage's permissive set has both **false** (eapi.py:262, :264).
  - Callers: `pass/enqueue_deps.rs:58` (any metadata EAPI), `installed_meta.rs:146-162`, `conflict_use_display.rs:108`.
- **Fix.**
  - Keep each helper's documented normalisation (trim; `""`/unparseable → false), and delegate to `eapi_attrs` only after `eapi_is_supported`.
  - Specify `eapi_attrs` for supported-but-unparseable spellings (`*_pre*`, padded). Portage raises there, so either return `Option<EapiAttrs>` or document a cut citing eapi.py:224-229. Do not split on `_`.
  - Add `3_pre1`, `9-pre1`, `" 8 "`, `""` and `"10"` rows to the S1 test with their live Portage outcome.

**I-4 (likely; supported by the repo's own profile). The S2 cache key forces an allocation on every hit.**

- **The problem.**
  - Plan:39 says the key is `(AtomOptions, &str)`, but plan:220 says `(AtomOptions, String)`.
  - `std::collections::HashMap` cannot look up a tuple key by borrowed parts (no `raw_entry` on stable, and no new deps allowed). So every `parse_atom` hit would allocate a `String` and clone `AtomOptions.eapi: Option<String>`.
  - Today's cache looks up `&str` without allocating (lib.rs:245-247).
  - `docs/performances-tuning.md:643-649` already names "`parse_atom`'s memo-hit clone per token" as the residual hot cost.
- **Fix.**
  - Leave the existing `HashMap<String, Option<Atom>>` cache untouched for the default options.
  - Give non-default options a nested `HashMap<AtomOptions, HashMap<String, Result<Atom, AtomError>>>` looked up with `&str`.
  - Make `AtomOptions: Copy` by storing the EAPI as a small enum (`None | Known(u8) | PreRelease9 | Unsupported`); the unsupported string is needed only for messages, and the caller has it.
  - Measure S2 alone against the perf gate.

**I-5 (proven by source read). The S4 memo key `(repo_location, cpv)` collides, and the candidate EAPI is not available.**

- **Collisions.**
  - Binary candidates all have `repo_location: PathBuf::new()` (binary_index.rs:296). Every multi-instance build of one cpv, with different `binary_deps`, would share one entry.
  - Validity also depends on `implicit_iuse_set(&candidate.iuse, config)` (masked_deps.rs:316). A thread-local memo keyed without config leaks across configs in unit tests; `use_flags.rs:958` exists because of exactly this.
- **Missing EAPI.** `portage-repo::Candidate` has no EAPI field. Ebuilds need it from `repo_aux_metadata`; binaries need the `Packages` `EAPI` field, which `binary_index.rs:291-317` does not retain.
- **Fix.** Add `eapi: String` to `Candidate`, filled in both constructors. Key any memo on `(source, repo_location, cpv, build_id)` plus a config fingerprint. Or drop the memo: `is_visible` is already memoised (visibility.rs:236).

**I-6 (proven). S3 misses two consumers of extended atoms.**

- **(a) Specificity ranking.** `atom_specificity` (portage-repo `use_flags.rs:470-483`) returns −2 for anything `parse_atom` rejects. Portage's `best_match_to_list` ranks extended `=*` 0, slotted −1, plain −2 (dep:2796+, oracle Q3 live). Specificity ranking of `package.use`/`package.env` entries would diverge.
- **(b) Wildcard parse in `match_from_list`.**
  - Portage's `match_from_list` re-parses with `allow_wildcard=True, allow_repo=True` (dep:2901-2906).
  - The S3 test calls `portage_dep::match_from_list` with wildcards, but S3's Files list never says `match_from_list` switches parse mode.
  - `CpBucketIndex::build` (config_match.rs:38-52) relies on `parse_atom` *failing* for wildcards, to route them to `other`. That must stay true: the default `parse_atom` must not accept extended atoms.
- **Fix.** Add `atom_specificity` (with a test from `probe_match.py`'s `best_match_to_list` rows) and `match_from_list`'s parse mode to S3. Add a test that `CpBucketIndex` still routes `dev-libs/fo*` to `other`.
