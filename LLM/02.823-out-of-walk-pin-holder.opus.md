### 0.2 Cause (read; S0.2 measures)

1. `stale_pin_for_consumer` (`crates/portage-repo/src/slot_operator/rebuild_scan.rs:694`) asks
   `held_back` (`:513`, the **recorded** versioned pin) at `:754` [`:751`] **before** `tree_held_back`
   (`:551`, the tree pin, only when `tree_pin_refuses`, i.e. from the pubgrub bridge). On `a10pin` the
   recorded `=…5.42*` refuses first, so the refusal has `tree_pin: false`.
2. `tree_refusal_fix` (`crates/portage-repo/src/solver_bridge.rs:6018`) reads only
   `refusals.iter().filter(|r| r.tree_pin && !r.no_ebuild)` (`:6034`). A recorded refusal is never
   judged, so pubgrub never withholds the provider for it; it upgrades and the NOTE names the consumer.
3. The default solver has no tree-pin refusal at all. On `a10` it holds the provider only because the
   scan schedules a rebuild of `p573virt` whose walked tree pin then conflicts (#790 §0.2); on `a10pin`
   the recorded pin refuses that rebuild, so nothing holds the provider.

So the same consumer, with the same tree, is protected or broken depending on whether its VDB record
carries the pin — and the record carries it whenever the consumer was built from its current tree.
`a10pin` is the normal state; `a10` (record older than the tree's pin) is the odd one. And the `a10`
protection does not survive merging the default solver's own `a10` plan: the `rR p573virt-1` re-records
the tree's dependencies (by PMS `sec:slot-dep` the `:=` is recorded as `:0/5.42=`), which is `a10pin`'s
record, so the next `-uDN @world` breaks the consumer (derived, not merged; #790 §0.3).

### 0.3 What this is not

- Not #790: #790 is the needless `rR` on `a10`; `a10pin` has no rebuild. #790 (B) keeps `a10` stable
  but leaves `a10pin` broken.
- Not #791: #791's rule covers `tree_pin` refusals only (cause 2).
- Not #793: `p573virt` has no `||`; no arm escapes the pin.
- Not #698/#703: those are holders the world reaches (root `r703`: `p573virt` in the world, the
  provider simply stays at 5.42, no message needed).
- Not #704: #704 measured and kept the cost of co-upgrading reached holders that **have a route**, and
  noted that unreached holders were "not protected on any path" on 2026-11-11. #791 (2026-11-27) then
  protected an unreached holder with **no route** when the refusal came from its tree. `a10pin` is an
  unreached holder with no route whose refusal comes from its record. `outpin` (unreached, recorded pin,
  the tree **accepts** the provider, so a rebuild route exists) stays #704/Q-D territory (Q3).

### 0.4 Candidate change (M1, pubgrub only)

In `tree_refusal_fix`, judge recorded refusals too, but give them only the withhold branch:

- filter `!r.no_ebuild` instead of `r.tree_pin && !r.no_ebuild`;
- after computing `follow = tree_follow_atoms(&texts, &use_flags, &provider, &new).filter(|arm| arm.iter().all(mergeable))`:
  `Some(arm)` → `if r.tree_pin { asks.extend(arm); } continue;` (a recorded refusal whose tree can follow
  is the `outpin`/#704 class and is left as today: no arm is asked, because the recorded pin would refuse
  the rebuild again); `None` → the existing withhold path (`plan_requires_move`, the user's own atoms,
  `HeldBackNoRoute`).

Predicted (not measured): `a10pin` on pubgrub prints `a10`'s pubgrub rows and "cannot follow" NOTE;
`prov` (`p569virt-1`: the `~p569core-1.0` arm accepts → `Some`), `outpin` (tree `p569prov:=` → `Some([])`)
and `pull` (`p569pull-2` requires the move) unchanged. Unknown: the reached-holder roots (`r698`, `r703`,
`w774`, `w775`), where `holder_fix` may already have filed a `HeldBackNoRoute` for the same provider
(a second entry would print a duplicate NOTE line). S0.2 measures every root.

The default solver needs a different mechanism (cause 3) and is S5, designed only after S0 and Q2.
