### 0.1 #361 — the entry's diagnosis is wrong: it is an option-presence rule

1. Portage: `create_depgraph_params.py:97-103` sets `myparams["bdeps"] = "auto"` only when `--with-bdeps` is absent **and `"--usepkg" not in myopts`**. This is a *key-presence* test. `main.py:1109-1114` stores `--usepkg=n` as `False`, so the key is present: **an explicit `--usepkg=n` turns bdeps-auto off** exactly like `--usepkg=y`. `actions.py:3710-3723` also inserts `--usepkg=True` for `--getbinpkg=y`, `--getbinpkgonly=y`, `--usepkgonly=y` and `FEATURES=getbinpkg` (unless `--getbinpkg=n`). `--getbinpkg=n` alone stays `False` and inserts nothing. `debug-361-blib-pvuD.txt` shows the result: `myopts` has `'--usepkg': False`, and `myparams` has **no** `bdeps` key. With no `bdeps`, `_add_pkg_deps` sets `ignore_build_time_deps` for a built parent (`depgraph.py:4194-4206`).
2. So "an installed parent that is not merged does not drag its BDEPEND" (backlog text) is false. Without `--usepkg=n`, Portage does upgrade `pg34-btool` (`361-blib-pvuD-noflags`, `-nousepkgflag`). The #34 captures always passed `--getbinpkg=n --usepkg=n` (to dodge the host binhost trap; see memory "getbinpkg ⇒ bdeps off probe trap"), so they never saw this.
3. portuale: `crates/portuale/src/pretend/resolve_plan.rs:97-103` computes `with_bdeps = with_bdeps_auto && !(usepkg || usepkgonly || getbinpkg || getbinpkgonly)` on the **values**. `--usepkg=n` parses to `opts.usepkg = false` (`pretend/args.rs:2097-2120`, field `:105`), so the key-presence information is lost.
4. Stale texts this exposes, all in pmtest: the `CASES` label `"-pvuD: installed, already-built parent plans nothing (pg34-blib, #34 S3)"` (`test_emerge_pretend_contract.py:451`; the argv has no `--usepkg=n`, so Portage plans `U pg34-btool`), and the rationale in the pubgrub docstrings at `:27940-27947`. Also in portuale: the #34 code-notes wording "installed-BDEPEND fold stays cut pending bed evidence".
5. Consequence for `--solver=pubgrub`: with no flags it prints `Total: 0` (`extra/pubgrub-probes.txt`), while Portage prints `U pg34-btool-2`. This is a pubgrub divergence, filed as **#390** (§5), not fixed here.

### 0.2 #362 — Portage's `_want_update_pkg`, not `_ignore_dependency`

1. `debug-362-dtop-pvu.txt`: for the dep `dev-libs/pg34-dlib` Portage lists `ebuild: dlib-2` and `installed: dlib-1`, and picks **the installed child** (`Child: (dev-libs/pg34-dlib-1 … installed …)`). The deciding code is `_wrapped_select_pkg_highest_available_imp` (`depgraph.py:7799`). At `:8445-8458`, if an installed match exists, the dep has a parent, and `not self._want_update_pkg(parent, inst_pkg)`, it returns the installed package before any update or visibility logic, **unless `inst_pkg` is `None`** (a `--newuse` reinstall hides the installed package at `:7860-7864`, see 3). The same predicate at `:7972-7979` keeps a **masked** installed package under `--update` ("Ensure that --deep=<depth> is respected even when the installed package is masked"). That explains `needskeywordmasked`: Portage keeps `keywordmaskedpkg-2.0`, portuale downgrades.
2. `_want_update_pkg` (`depgraph.py:7304-7333`): `False` when the package is `--exclude`d; otherwise `not _complete_mode and (arg_atoms or update) and not _too_deep(depth)`, with `depth = parent.depth + 1`, reset to 0 when the package matches an argument whose `reset_depth` is true (`DependencyArg.py:13-23`; default `True`; `False` only for internal sets, `depgraph.py:5474-5481`, `:8730`). `_too_deep` (`:7359-7375`): `depth > deep`, `deep` defaulting to 0. So **without `--deep`, no non-argument dependency is ever updated, reinstalled for USE or downgraded when an installed package satisfies it.** That covers `dtop`, `withdeps`, `needskeywordmasked`, `toolchainroot`. `needer` still upgrades because the installed `paired-1.0` does not match the atom.
3. **`_ignore_dependency` does fire in `uapp -pvN`/`-pvuN` (D2).** The ebuild db is walked before the vardb (`:809-825`). The `ulib-1` ebuild matches the installed cpv; under `--newuse`, `_reinstall_for_flags` sees the USE drift and sets `reinstall = True` (`:8311-8329`). At the vardb, `want_reinstall` is true and `matched_packages` is non-empty, so the installed db is skipped (`:7860-7864`) and `inst_pkg` is `None` at `:8436-8440`: the `:8445` return cannot fire. The ebuild child is selected, then dropped by `_ignore_dependency` (`:4423-4462`, call `:4583-4603`): the priority is satisfied by the visible installed `ulib-1`, `recurse_satisfied` is false, the child is not installed, and the tracker holds no non-installed package in that slot (`dep.child = None`, `_ignored_deps`). Portage keeps the reinstall when the installed instance is **not visible** (`mypriority.satisfied.visible`). In the other #362 cells (`dtop`, `withdeps`, `needskeywordmasked`, `toolchainroot`) the `:8445` return decides. Rows for `uapp` are identical either way (`N uapp` only), but the mechanism differs: S2 models the drop (a USE-drift reinstall of a non-wanted dependency whose installed instance is visible is discarded, not kept as `AlreadyInstalled`), and S0 (a) covers the masked-installed + `--newuse` variant.
4. portuale models only the `!update` half. `resolve_pretend` (`crates/portage-repo/src/resolve/pretend.rs:374`) has two installed shortcuts: `:468` `if !update && !empty && !is_top_level && excluded.is_empty()` (early, pre-visibility) and `:1101` `if !update && ((!is_top_level && !empty) || selective)`. Both go through `dependency_avoid_update_candidate` (`:35`) and `already_installed_or_reinstall` (`:94`). The second **re-applies `--newuse`/`--changed-use`** (that is how `R ulib USE="x*"` appears under `-pvN`). `resolve_pretend` sees only `is_top_level` (`resolve/pass/resolve_outcome.rs:50`: `is_top_level: depth == 0`), not `depth`, `deep` or "is this package an argument".
5. **Existing pins encode the wrong behaviour.** `test_update_threads_through_dependency_recursion_not_just_top_level` (pmtest `test_emerge_pretend_contract.py:17736-17756`) pins `U upgradepkg-2.0` for `--pretend --update dev-libs/withdeps`, and its docstring claims `--update` "threads uniformly through the whole BFS". The `CASES` entry `"--update threads through dependency recursion, not just top-level"` (`:2569-2572`) carries the same claim. Portage (`362-withdeps-pu`) prints only `N newpkg` + `N withdeps`. ### 0.3 #359 — the default solver has no `_greedy_slots`

1. Portage: `select_files` → under `--update` (`depgraph.py:5385-5427`), for every `AtomArg` it appends `AtomArg(arg=arg.arg, atom=<cp>:<slot>)` for each slot `_greedy_slots` returns (`:5896-5975`). Those are the installed slots of the same cp, minus the slot of the best visible match, each kept only if its own best `pkg < highest_pkg`. Then it repeats with `blocker_lookahead=True`, which discards slot atoms whose package conflicts by blocker with `highest_pkg`. Only `AtomArg` gets this, not set members, and it runs on every backtrack attempt (`select_files` per depgraph).
2. portuale: `graft grep greedy_slots` finds it only in the pubgrub bridge (`crates/portage-repo/src/solver_bridge.rs:1133-1197`, `target_slots`/`root_target_slots`, which has no blocker lookahead, noted there as part of #368) and in `slot_operator/abi_probe.rs:440,494`. The default solver seeds `ctx.atoms` unchanged (`resolve/pass/seed_queue.rs:6-22`; request field `resolve/request.rs:13`). `CASES` already has `"-pvu: greedy slots add the installed-slot upgrade (pg34-gs, #34 S1)"` (`:441`), but it checks the rc only.

### 0.4 #360 — an installed package with no ebuild must be a candidate

1. Portage builds its `dbs` with the vardb as `"installed"` (`depgraph.py:825`), and `_iter_match_pkgs_any` (`:7085`) walks all of them. An installed-only package is therefore an ordinary match, and the dep is satisfied by `pg34-gone-1`. Under `-pvuD` its **vdb** RDEPEND (`pg34-gextra`) is walked, which gives the `N gextra` row. As an argument without `selective` (`-pv`), Portage wants to reinstall it, finds no ebuild, and fails. `_show_unsatisfied_dep` (`:6471`) then prints `"no ebuilds to satisfy"`, with **no** similar-names block, because `cp_exists` is true via the installed db (`:7018-7040`). The ` for <root>` suffix comes from `root != running_root` (`:6502-6503`): Portage's running root is `/` in the container (`roots.txt`), while the contract harness sets `PORTAGE_RUNNING_ROOT=ROOT`, so portuale correctly omits it there.

In `resolve/pass/outcome_fallbacks.rs:77-96` it applies only to dependency edges (`owner.is_some() && depth != 0`), not `buildtime_hard`, not `||`-chosen, not `--emptytree`, and **only for slot / slot-operator atoms** ("bare and version-range atoms stay on the old path"). ### 0.5 #369 — Portage defers `||` choices; portuale chooses at enqueue time
