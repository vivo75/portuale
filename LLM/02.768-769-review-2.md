## D — defects (new, introduced or left by the fold-in)

### N1. `bdout`'s agreement parameter `(set(), set())` is wrong: both resolvers refuse `p569virt` there. Severity: medium. S1's GREEN run fails on it, and STOP-1 fires on a strictly expected root. **Proven** (recorded capture). **Blocking for S1.**

- Plan: Q-A ("`bdout` is pinned in S1 as agreeing (both silent)"), S1.2 ("`bdout` (`set()`,
  `set()`, Q-A (i))"), S1.5 ("`bdout` (Q-A (i): both silent)").
- `bdout` adds `dev-libs/p569prov` to the world (`mkroots.sh:43`), so the fixture's `p569virt-1` is
  stale exactly as on `prov`. `LLM/evidence/02.766/before/compare.txt` `== bdout`:
  - `df` refusals `[('dev-libs/p569virt', '=dev-libs/p569prov-5.42*', 'dev-libs/p569prov-5.44')]`
  - `pg` the same
  - both with reinstalls `[]`
- After S1, the fast side names `p569virt` with the same row (Q-B: visible ebuild, recorded `=5.42*`
  hold-back), and `p698rebuild` stays silent (Q-A (i)).
- `test_766_the_two_plans_agree_on_the_stale_consumers` asserts `{r[0] for r in fast[0]} == consumers`,
  so `set()` fails. It is D2's error again.
- Fix direction:
  - `bdout` → (`{"dev-libs/p569virt"}`, `set()`). With `full_rows`, the row is `_VIRT_RES_766`.
  - Reword Q-A and S1.5 to "`p698rebuild` silent on both sides; `p569virt` refused on both".

### N2. The walk condition "in `world.reached` before Q-C seeding" has no data source, and §0.6 still says `world.reached.contains(node)` is the whole gate. Severity: medium-high (D1's fix and Q-A (i) both rest on it). **Likely** (source read, no root built). **Blocking for S1/S2 design.**

- `analyse` (`lib.rs:575-608`) calls `slot_operator(&world, …)` on the walk of the *current*
  iteration. After Q-C, that walk seeds every `rebuilds` node (`walk`, `:613-630`), so from the second
  iteration on a seeded consumer *is* in `world.reached`. Nothing in `World` records which slots were
  reached from `world_atoms` alone.
- Taken literally, §0.6 (and an executor reading "world.reached" in S2.2) gates on the
  post-seeding set. Concrete shape:
  - Consumer C is outside the world, with recorded `RDEPEND="dev-libs/p:0/1="` and
    `DEPEND="=dev-libs/p-1*"`, and an unpinned tree. The world moves `p` to `0/2`.
  - Iteration 1: C is not reached, so 3 keys are read, nothing is held back, the tree names `p`
    → `Ok(true)` → seeded.
  - Iteration 2: C is reached, so 5 keys are read and the `DEPEND` hold-back hits.
    - If the tree accepts `p-2`, the waiver applies (which Q-D forbids for an out-of-walk consumer).
    - Otherwise `Err`.
  - `rebuilds` never shrinks (`:603`), so C ends with **both** an `R` row and a refusal line. Or it is
    rebuilt through a waiver the resolver would not grant (`outpin` class).
- A related point: a slot reached only through a *seeded* consumer's tree dependencies also becomes
  "walked". Whether that is right (the resolver walks a scheduled rebuild's deps) is an owner
  question the plan does not ask.
- Fix direction:
  - Compute the gate set explicitly inside `walk`: the slots reachable over `edges` from the
    `world_atoms` seeds' `atom_nodes`, excluding the rebuild-seed atoms. Store it as e.g.
    `World::walked`, and use it in Q-A, Q-D and S2.2.
  - Correct §0.6.
  - Add a Rust case to S1.1: "a seeded consumer is judged on the same keys in every iteration (no
    row-plus-refusal)".

### N3. S0.5's expected fast row for `outpin` carries the wrong atom. Severity: medium (S0's oracle check would report a false mismatch on a strictly listed root). **Proven** (source, plus the recorded D1 rows).

- S0.5: `outpin` fast `{(p569virt, …), (p698reinst, "=dev-libs/p569prov-5.42*", null)}`.
- Today's D1 branch refuses with `refuse(installed, first, None)` (`rebuild.rs:366`), where `first` is
  the first entry of `stale`, i.e. the stale `:=` token. Every recorded D1 row shows this, for
  example `bdout`/`prov` `('dev-libs/p569virt', 'dev-libs/p569prov:0/5.42=', None)`.
- Fix direction: `(p698reinst, "dev-libs/p569prov:0/5.42=", null)` before S1; after S1,
  `(p698reinst, "=dev-libs/p569prov-5.42*", "dev-libs/p569prov-5.44")`.

### N4. Q-E's key set contradicts Q-A (i). Severity: low-medium. **Proven** (plan text against plan text).

- Q-A (i) restricts the **tree-side** keys of `tree_names_provider` to the runtime keys for a
  consumer outside the walk (G9).
- Q-E says `TreeVerdict` reads "all five `DEP_KEYS` for both halves", in one read shared with
  `tree_names_provider`.
- For an out-of-walk consumer, the `names` half must read three keys. The `accepts` half is unused
  there (Q-D), so only the walked case reads five.
- Fix direction: Q-E reads "five keys for a walked consumer (N2's set), three otherwise, for both
  halves".

### N5. The waiver stops at the first hold-back hit. Severity: low-medium. **Likely** (source).

- `held_back` (`rebuild.rs:262-304`) returns the *first* failing atom.
- S2.2 makes `judge` waive "the hit" when the tree accepts the moved provider, and then goes on to
  `tree_names_provider`.
- A walked consumer holding back two providers would have only the first judged. For example, it
  records `=a-1*` and `=b-1*`, both move, and the tree accepts `a-2` but pins `=b-1*`. It is then
  rebuilt against `b`'s pin.
- The resolver's route needs a route per (holder, provider) pair (`co_upgrade_request`).
- Fix direction: iterate every hit. Waive one only if the tree accepts *that* hit's provider, and
  refuse on the first one not waived. Add a two-provider Rust case.
