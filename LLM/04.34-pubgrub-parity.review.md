## 3. New findings

### Critical

**N1 — D, proven. A bare target atom becomes a target in every slot. No slice addresses this.**

- **Where:** `solver_bridge.rs:883-893`. When the target names no `:slot`, `provider.packages_for_cpn(&dep.cpn)` returns every slotted node (crate `provider/mod.rs:905-916`), and all of them are pushed as root targets.
- **Portage:** a bare argument selects the slot of the highest visible match. Only under `--update` does it add *installed* slots that are older than that match (`_greedy_slots`, `depgraph.py:5385-5427`, `:5896-5930`). It never adds non-installed sibling slots.
- **Host capture**, same options on both sides (`--getbinpkg=n --usepkg=n --color=n`). Installed: `sys-devel/gcc-16.2.1_p20260926`.
  ```
  emerge -p sys-devel/gcc                       -> [ebuild   R    ] sys-devel/gcc-16.2.1_p20260926
  portuale emerge -p sys-devel/gcc (default)    -> [ebuild   R    ] sys-devel/gcc-16.2.1_p20260926
  portuale emerge -p --solver=pubgrub sys-devel/gcc
      -> [ebuild  NS    ] sys-devel/gcc-14.4.1_p20261001 [16.2.1_p20260926] ...
         [ebuild  NS    ] sys-devel/gcc-13.5.0 ...
         [ebuild  NS    ] sys-devel/gcc-12.5.0 ...
         [ebuild  NS    ] sys-devel/gcc-11.5.0 ...   (no gcc-16 row)
  ```
  So pubgrub shows four extra `NS` rows and no `R` row. Multi-slot corpus targets (gcc, llvm, python, `dev-lang/rust` — likely a large part of §0.1's 114) all hit this, and none of the H-buckets covers it. S3's R rule ("best accepted version == installed") cannot work while the target list is wrong.
- **Fix direction:** a new slice before S3.
  1. For a target without a slot, pick the single slot of the best visible version within the atom's range, using `LazyRepo::load_versions`, which is already visibility-filtered.
  2. When `req.update`, also add each installed slot whose own best version is lower than that pick (Portage's `_greedy_slots`, without `blocker_lookahead` in v1, recorded as a cut).
  3. Tests: a contract pin on a two-slot fixture (one slot installed, a newer slot available) for `-pv` and `-pvu`, with expected output from container captures.
  4. Add the `H-target-all-slots` bucket to S0.

**N2 — D, proven (engine behaviour). The plan maps `--with-bdeps` to an engine switch that does nothing, and installed packages' build deps never enter under `--deep`.**

- **Where:**
  - The only reader of `with_bdeps` is the cross-host branch, `solve.rs:378` (`cross_active && merge_root == Host && with_bdeps`). The setter doc at `provider/mod.rs:884-888` ("false = BDEPEND excluded") contradicts the code at `solve.rs:382-387` (a built package always pulls its BDEPEND).
  - The installed-and-kept branch (`solve.rs:311-341`) never returns DEPEND/BDEPEND.
  - So S4's `provider.set_with_bdeps(req.with_bdeps)` has no effect, and S4's planned `--with-bdeps=y` pin either passes for the wrong reason or cannot be made to pass.
- **Portage:** with the default bdeps=`auto` (`create_depgraph_params.py:97-103`, when `--usepkg` is not set), a built or installed package's DEPEND/BDEPEND is traversed as *optional* priority (`depgraph.py:4196-4206`, `:4274-4289`). `_add_dep` skips an optional dep only when no package can be selected at all (`:3395-3398`). So under `-uD`, installed packages' build deps are updated (`U`) and missing ones are pulled (`N`). The corpus modes `-pvuD` and `-pvuDN` are directly affected (corpus impact is likely).
- **Fix direction:**
  1. In S2's kept-installed facts, when deep is in effect and `req.with_bdeps` is set, fold the installed DEPEND+BDEPEND entries into the **RDEPEND** class handed to `PackageDeps::new`. The crate reads only RDEPEND/PDEPEND/IDEPEND for kept packages, so this is the only route that stays bridge-side.
  2. Leave `raw_deps` untouched, because merge-order edges and blockers read it.
  3. Drop `set_with_bdeps` from S4, or keep it with a comment that it only matters for cross builds.
  4. Write a crate-doc note per §0.4.
  5. Test: a fixture where an installed package's BDEPEND has a newer in-slot version. Capture `-pvuD` and `-pvuD --with-bdeps=n` in the container.

### Important

**N3 — D, proven (source). S1's leaf rule ignores `--emptytree`.**

- **Where:** `-pve` does not set `req.deep`. `resolve_phases.rs:147` sets only `empty: emptytree`, and "empty forces deep" lives inside the walk. S1 keys the rule on `req.deep == NotRequested` with `rebuilding` empty until S4. So from S1 to S4, every installed package under `-pve` is a leaf, and its new deps vanish (`-pve` already hides installed packages; see C3).
- **Fix direction:** `deep_effective = req.deep != Deep::NotRequested || req.empty`. Under `empty`, put every installed cpv into the rebuild set from S1 onwards. `set_rebuild_tree` stays in S4.

**N4 — D, likely. The bridge's closure never expands installed packages, including installed targets, so their slot-map entries are missing.**

- **Where:**
  - `LazyRepo::build` (`solver_bridge.rs:121-128`) builds its queue as `seeds(expand) ++ shallow(no-expand)` and drains it with `Vec::pop` (LIFO). Every installed CPN is therefore inserted into `closure` *unexpanded* before any seed is popped.
  - An installed target's own `(cp, true)` entry then hits `!closure.insert` and is skipped. Every dep reached only through installed packages stays outside `closure`.
  - `all_packages()` returns `closure` (`:750-752`) and feeds `build_slot_map` (crate `provider/mod.rs:365-387`).
- **Effect:** a CPN outside the slot map converts an unslotted dep to `PortagePackage::unslotted(cpn)` (`convert.rs:417-426`). Its versions are registered as `slotted(cpn, slot)`, because the bridge always passes a slot (`solver_bridge.rs:767-771`, crate `mod.rs:465-475`). The dep can therefore never match.
- **Affected slices:** S3 (an R'd installed argument that needs a non-installed dep) and S2/N2 (installed packages' deps under `--deep`).
- **Fix direction:** in S1, pop seeds before shallow entries, or let a seed re-expand a CPN that was inserted shallow. Under deep in effect, expand installed CPNs. Note that resolvo shares `LazyRepo` and iterates `closure_cpns()` (`:955-960`), so a larger closure costs it time; keep the change behind the pubgrub path or measure it.
- **Discriminating test:** an installed target `pg34-arg` with `RDEPEND="dev-libs/pg34-new"`, where `pg34-new` is not installed. Run `-pv --solver=pubgrub`. Portage's expected output (container capture): `R pg34-arg`, `N pg34-new`.

**N5 — D/P, proven. The portage-cli citations point at the wrong mechanism.**

- **Architecture citation:** the Architecture section cites `portage-resolve/src/repo.rs:1255-1375` as how portage-cli feeds installed facts. That span is the `Adapter` fields plus `cede_required_use` (Level-C REQUIRED_USE). `installed_cpvs` and `rebuilding_cpvs` are read only at `repo.rs:1354`. portage-cli has **no** rule that makes installed packages leaves; S1 and S2 are portuale's own design, not a port.
- **S3 citation:** S3 says "Port portage-cli root-target handling (`rebuilding_cpvs` comment `repo.rs:1271-1276`)". portage-cli's R for named arguments is a **post-solve display filter** (`round.rs:578-620`: keep `Favor`, then re-list the selected `(cpn, slot)` when `!selective`). It does not register `Rebuild`. An executor told to "port" this would look in the wrong place.
- **Fix direction:** rewrite the attributions. S1 and S2 are portuale-original, and nothing needs a port comment. S3 cites `round.rs:578-620` as *reference* and states the deliberate difference: `Rebuild`, so the R'd target expands DEPEND/BDEPEND as Portage's ebuild node does, whereas portage-cli's `Favor` gives runtime deps only (`solve.rs:311-341`).
