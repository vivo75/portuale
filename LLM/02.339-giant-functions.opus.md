## Global Constraints

- Limit: **≤ 200 code lines per production function**; target ≤ 150 for every *new* function. "Code line" = what `LLM/tools/fn_lengths.py` counts (blank and comment-only lines excluded).
- Out of scope: the 6 functions under `crates/portage-repo/src/tests/` (owner decision); `graph_result_from_order` (`solver_bridge.rs:337`, 336 lines) is **owned by #34** ([`04.34-pubgrub-parity.opus.md`](04.34-pubgrub-parity.opus.md) Task S6), because #34 rewrites that function's inputs.
- Statements move **verbatim and in order**. No merged branches, no renamed locals, no new abstractions, no clippy-driven rewrites beyond what `extract_block.py` runs (`clippy --fix`, `fmt`). The **only** allowed non-move edits are plumbing, each listed in the commit body: parameter/return lines; a loop label; `ControlFlow` for a host-targeted `continue`/`break`/early `return` (slices 2–3's convention — used only when the range really contains one; a range without host control flow is extracted **without** `--loop`); the hand patterns of §0.4 rules 8–10; `captured_var` → `ctx.captured_var` in a closure turned into a fn (rule 4). Every auto-fix the tool applied (`&`/`&mut` flips, `*x`, `.clone()`→`.to_vec()`, `mem::take`) is reviewed in the per-cut patch (Track R Step 2), not trusted.
- An `Args`/`Ctx` struct whose fields serve two unrelated statement groups means the cut is in the wrong place: split the cut instead (reviewer rule; no fixed field cap — `clippy.toml` and decisions §36 already govern wide signatures).
- No output change anywhere: contract suite with **no corpus drift**, L0 UNEXPLAINED **identical line for line** to the Task 0 baseline. A corpus bless in this plan is a defect.
- Comments: `///` summary on every new function (one line, what it does); context and history go to `LLM/code-notes/<crate>/<path>.md` under `## fn <name>`, moved verbatim from the host's notes; run `python3 LLM/tools/code_notes_index.py` after any notes change; `python3 LLM/tools/fact_coverage.py HEAD <files>` must print nothing.

### 0.4 The method, once (every slice uses it)

1. `python3 LLM/tools/fn_outline.py <file>:<fn line>:<name> --min 8 --nest 60` — list the cut candidates.
2. **Closures and nested items first** (rules 4–5), then re-run the outline (every later line number shifts).
3. For each cut, from the bottom of the function upward (so earlier line numbers stay valid):
   - `python3 LLM/tools/stmt_range.py <file> <first line> [COUNT | --until NEXT] [--indent N]` → the exact `START END`.
   - `python3 LLM/tools/extract_block.py <file> START END <new_fn> <host.rs> --crate <crate> [--loop LABEL --indent N] [--try ERR] [--ret TYPE] [--own A,B] [--doc "<one line>"]` → moves the range, infers the signature from compiler errors, runs `clippy --fix` and `fmt`. **`--crate` is mandatory** (`portage-repo` for Track R; the default `portuale` checks the wrong package and can suggest `use portage_repo::X;` inside portage-repo). `--try`/`--ret` per the host's return type — read the host signature before each slice (R2 and Track M state theirs; only D5, D6-`run`, M2, M3, M4 return `ExitCode`, D6-dispatch has its own pattern). `--loop` only when the range contains a `continue`/`break` aimed at the host loop. Read the leftover-error output; fix by hand only what it prints.
   - Where a `--loop` cut's call site loops either way: `python3 LLM/tools/flatten_flow.py <host.rs> <fn.rs> <new_fn>` (it cannot flatten a call ending in `?`; leave `if f(..)?.is_break() { continue; }` then, as slice 2 did).
   - `cargo build --release` must pass before the next cut; then `git diff > $P/cut-<n>.patch` (`P=LLM/plans/2026-10-11-339/patches/<slice>`) — the per-cut patches are the bisect record and the reviewer's view of every auto-fix.
4. Big **closures** are not statements `extract_block.py` can move; the tool stops with `needs a host-local fn: <name>` on a closure a range calls. Turn each into a private `fn` whose parameters are the captured locals (or one `<Name>Ctx<'a>` struct of borrowed fields when more than 5, for closures that call each other or are always used together) and replace the closure binding with calls. The body text stays identical; only `captured_var` → `ctx.captured_var` renames are allowed, and only when a struct is used. A closure that memoises through a `OnceCell` keeps the cell in the host and takes it by `&`. Every task lists the closures its ranges call.
5. **Nested items** (`fn`/`struct` declared inside a function body) move verbatim to module level first; that is a pure move and usually the cheapest lines.
6. **New functions go in the host file**, right after the host (slice 3's precedent). A new file only when the host already is a `mod.rs` directory module (the only case `extract_block.py` wires a sibling, `:238-240`) — never mid-algorithm for a line-count heuristic.
7. Notes: for each new function, cut the host's `## fn <host>` bullets that describe the moved code into a new `## fn <new>` section of the same notes file; `code_notes_index.py`; `fact_coverage.py HEAD <changed .rs files>` prints nothing. The `///` of a `ControlFlow` function gains one line saying what `Break` means to the caller.
8. **Bare `return;` in a `()` host** inside a non-loop range: the helper returns `ControlFlow<()>` and the host does `if f(..).is_break() { return; }` (slice 3's convention; Task 0 makes the tool do it). Never let a guard `return;` become a return from the helper only.
9. **let-else with `else { return; }`** (R4): the helper returns `ControlFlow<(), T>` and the host does `let ControlFlow::Continue(x) = f(..) else { return; };` (slice 3's `flatten_dep_string`, `enqueue_deps.rs:395-511`). The tool does not detect these outputs; do it by hand.
10. **A range ending in the host's tail expression** (R2): the helper body is the range verbatim returning the host's type; the host's tail becomes `f(..)`. By hand.
11. Check with `python3 LLM/tools/fn_lengths.py` that the host is ≤ 200 and every new function ≤ 150 (a new function over 150 is allowed only when it is one indivisible `match`, named in the task — D1's arms; say so in the commit body).

## Risks and how the plan handles them

- **A move that is not a pure move** (a borrow forces a clone, a `?` changes error type): `extract_block.py` prints leftovers; the reviewer reads each per-cut patch and rejects any edit outside the plumbing list of Global Constraints. Guard: L0 identical + no corpus drift.
- **Silent tool defects** (a lost Copy write-back, a guard `return;` that returns from the helper only, the host written back uncut): all three compile cleanly. Task 0 fixes them with regression checks; until then no slice starts. The reviewer still greps every patch for `return;` and `_out` write-backs.
- **Line numbers drift** between slices: every slice re-runs the outline (Step 1); hints here name statements by their first line text as well as by number.
- **Closures capturing many locals** (D1, D4, R7, R11): rule 4's ctx struct; the reviewer checks the closure body text is unchanged except `ctx.` prefixes.
- **Bed noise**: L0 is deterministic (decisions §34 compared it line for line in slices 2–3); a differing line is a real change until proven otherwise.
