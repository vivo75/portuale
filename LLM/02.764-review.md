## D — defects in the plan (each proven by probe)

**B1 — blocking. The S0.5 "V3: strict as well" expectation is false.**
- Probe: the strict checker on v3 k1 (`du, dt, db`) reports **`cycle-noted`** (non-failure) on `w764du`, reason
  "BDEPEND is only met by a later package of the same cycle". It reports no `build-order` and no "not usable yet" row.
- Cause: the strict `_build_graph` adds RDEPEND edges (`dt -R-> du`), so `du, db, dt` form one SCC and
  `_order_finding` excuses the late `db`. That excuse is exactly the "unserializable cycle" behaviour #749 removed.
- S0.6 says a cell mismatch is STOP-1, "do not adapt", so an executor following the plan halts on its own wrong
  expectation.
- Fix: in S0.5 write "V3: literal exactly 1 `build-order` on `w764du`; strict: 1 `cycle-noted` on `w764du`
  (the strict model's runtime-edge SCC excuses it; this is why the oracle for V3 is the literal checker)".
  `classify.py` must then print strict `cycle-noted` rows that lack "not usable yet" as their own class, and not
  drop them.

**B2 — blocking. `classify.py`'s depth rule has no class for slot-operator binding transitions. On this host
the strict model reports 49 such rows, so the D0/D1 verdict is undefined.**
- Probe: `mrg --plan-world --json --sort depend` on the host (349 rows, sha prefix `ea695c42e792af67`, rc 0),
  then both checkers with `--vdb /var/db/pkg`:
  - literal: 0 `build-order` (1 `runtime-deps`);
  - strict: **49 `build-order`**, every one "…is not usable yet: RDEPEND of X…".
- All 49 unmet atoms are the `dev-libs/openssl` `:0/3=` binding: 26 × `>=…-1.1.1:0/3=`, 11 × `>=…-1.0.1h-r2:0/3=`,
  11 × `dev-libs/openssl:0/3=`, 1 × `>=…-3.0.0:0/3=`. The plan upgrades openssl `3.6.5` (sub-slot 3) to `4.1.0`
  (sub-slot 4) at merge #4.
- The S0.5 rule ("depth 1 when the provider is the package matching the build atom, else depth≥2") classes most
  of them as depth≥2. One example: "BDEPEND >=dev-build/meson-1.2.3 is not usable yet: RDEPEND of
  dev-lang/python-3.14.10". The "avoidable" test then needs the variants to settle each one. That risks a D1
  STOP on rows that are the #737/#749 binding class (the strict `gap` docstring itself calls them a checker
  limitation), not the #764 shape.
- Fix: before the depth split, `classify.py` must set aside as `binding-transition` every strict row whose unmet
  atom carries a sub-slot binding (`:<slot>/<sub>=`) on a cp the plan moves to another sub-slot. Only the rest
  count for D0/D1. With that rule, today's host gives 0 #764-shaped rows.

**B3 — blocking. The S1.3 cargo command is invalid, and its filter is not exact.**
- Probe: `cargo test --release -p portuale plan_world::tests::a_tool_runtime plan_world::tests::an_` exits with
  `Usage: cargo test [OPTIONS] [TESTNAME] [-- [ARGS]...]`: two positional filters are rejected.
- Even after `--`, `plan_world::tests::an_` also matches the existing `an_acyclic_plan_carries_no_bootstrap_key`
  (`:834`) and `an_unknown_plan_mode_is_a_usage_error_naming_the_two` (`:1434`), so the count is 5, not "3 passed".
- Fix: either `cargo test --release -p portuale -- plan_world::tests::a_tool_runtime_dependency
  plan_world::tests::an_unavoidable plan_world::tests::an_uncuttable`, or put `w764` in the three test names and
  filter on it (the same goes for `-k 764` on the pytest side, which already works).
