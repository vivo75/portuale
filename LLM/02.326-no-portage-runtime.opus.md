## 0. Read this first

### 0.1 Goal

1. A lone static `portuale` binary builds, packages (`gpkg` and `xpak`) and
   merges real ebuilds on a host with **no `sys-apps/portage`**, and with **no
   Python at all** whenever the ebuilds themselves do not need it.
2. The same helpers serve **remote merges** (`mrg --remote-*`). The client runs
   them through a `portuale` binary that the server installs and verifies
   (D5), and every client call uses its absolute path, never `$PATH`.
3. Real Portage stays the oracle. Each native helper is checked against the
   real Python helper it replaces, on the same input.

Not goals:

- importing code from `lu-zero/portage-cli` (owner's decision 2026-10-08, see 0.4);
- an IPC daemon (`ebuild-ipc`, D6);
- building ebuilds that themselves need Python (`python-any-r1` and similar)
  on a Python-free host: that is an ebuild requirement, not a Portage one;
- changing any `emerge` output. No corpus bless is expected anywhere in
  this plan.

### 0.2 Trigger (2026-10-08)

The owner ran, in a container without the build tree:

```sh
podman exec server bash -c '
  export BINPKG_FORMAT=gpkg FEATURES="buildpkg -sign" PKGDIR=/var/cache/binpkgs
  portuale emerge -1 -v --buildpkg app-portage/eix'
```

It failed in `app-shells/push-3.4` `clean` with
`phase-functions.sh: line 401: cd: null directory`, then
`PORTAGE_PYM_PATH does not exist: ''`.

- **Cause.** `phase_env_vars` (`rust/portuale/src/ebuild_phases.rs`, the
  `PORTAGE_PYM_PATH` block near `:3299`) only sets the variable when
  `<checkout>/lib/portage` exists. `__dyn_clean` (`bin/phase-functions.sh:401`)
  `cd`s into it unconditionally.
- **A fix is in the working tree, uncommitted, on `backlog/326`.** It falls
  back to `/`, and sets `PORTAGE_PYTHONPATH` (`ebuild_package.rs`,
  `invoke_dyn_package`) only when the checkout exists. S1 finishes and
  commits it.
- That gets past `clean`. The build then stops at the first missing helper.

### 0.3 Facts established 2026-10-08 (checked in the tree, confirmed by the review)

except `filter-bash-environment.py`, which uses only the standard library.
`bin_dir()`'s doc comment (`ebuild_phases.rs:703-730`) says the rest are
served from the checkout through a symlink overlay. I grepped `bin/` for
`PORTAGE_PYTHON`, `.py` and the helper names, and compared with upstream
3.0.82.2 (`3rdparty/portage`, pinned tag `1d95fc2c5`). The review confirmed
the list is complete, and that every call site passes the script path as
the first argument.

- **Already Python-free.** `has_version`/`best_version` go through
  `bin/portageq-wrapper`, which execs `$PORTUALE_BIN portageq` (feat#157 S6).
  `save-ebuild-env.sh:37` only *compares* `PYTHONPATH` with
  `PORTAGE_PYM_PATH`; it runs nothing.
- **Missing from the vendored `bin/`:** `ecompress-file` and `chmod-lite`.
  Neither is Python-only (`ecompress-file` is bash).
  - A missing `ecompress-file` is **fatal**: `ecompress:282-283` calls
    `__helpers_die`.
  - A missing `chmod-lite` is **silent**: `find -exec` prints
    `No such file or directory` and returns 1, nobody checks the status, and
    WORKDIR modes stay un-normalised. The review probed this live.
  - Both happen on a relocated binary even when Portage is installed.
- **The Rust side** spawns `python3` in two places only. Neither is in scope:
  - `emerge --info`'s version probe (`pretend.rs:8479`), which degrades to
    `unavailable`;
  - a test oracle (`portageq.rs:1117`).
- **Remote today.** `remote-merge.md` §1/§2 promise a client with bash and
  POSIX `/bin`, "never Python" and no portuale binary. The code disagrees:
  - `local_client_bash`'s doc comment (`remote.rs:457-467`) says the client's
    `PATH` provides `portuale` over ssh, because `bin/portageq-wrapper` execs
    `${PORTUALE_BIN:-portuale}`.
  - The client phase headers export `PORTAGE_PYTHON=/usr/bin/python`
    (`remote.rs:2520`, `:2941`).
  - Every client hook phase writes `environment.raw` (`remote.rs:2583`,
    `:2828`, `:2924`), so the filter runs at `phase-functions.sh:274` and
    again at `:1261` on **every** hook phase, not only for the regen.
  - The scripts also run `cd ""` at `phase-functions.sh:1145,1260`, because
    `PORTAGE_PYM_PATH` is unset there.
  - D5 settles all of this in S8.
- **Remote bundles ship the overlay.** When a checkout exists, `bin_dir()`
  returns an overlay of **absolute** symlinks (`build_bin_overlay`,
  `ebuild_phases.rs:932-945`). `remote_bundle.rs:437-446` copies it with
  `cp -a`, so a client on another host gets dangling links. l31 hides this,
  because its client is the same container with the repo mounted at the
  same path.
- **In-process tests.** `PORTUALE_BIN` is `current_exe()`
  (`ebuild_phases.rs:3115-3119`), which is the libtest harness under
  `cargo test`. A shim that execs it prints `running 0 tests … ok` and exits
  0, and that banner would silently become the saved environment.
- **`main.rs:170`** collects `std::env::args()`. It panics on a non-UTF-8
  argument, which helpers receive as raw filenames.
- **gpkg cannot be reproduced byte for byte, even by real Portage.**
  `gpkg.compress` stamps `datetime.now()` on each container member
  (`gpkg.py:1019,1039,1298,1321,1570,1614`). Further traits matter, listed in
  D3. Comparison is therefore structural. xpak recompose is deterministic.
- **External programs are fine.** Compressors come from `BINPKG_COMPRESS`
  through `gpkg._get_binary_cmd` (`:1883-1885`, which also reads `MAKEOPTS`
  for `{JOBS}`). Signing comes from `BINPKG_GPG_SIGNING_COMMAND`
  (`_add_signature`, `:1603`). A native writer runs the same commands.
- **Workspace crates already present:** `tar` 0.4, `sha1`, `sha2`, `blake2`,
  `md-5`, `flate2`, `regex`, `libc` (`rust/portuale/Cargo.toml`).
- **The signed-gpkg test keyring** used today lives in the checkout
  (`3rdparty/portage/lib/portage/tests/.gnupg`; `emerge_getbinpkg.rs:1807`,
  `binpkg.rs:3405`).
- **`sys-libs/glibc` needs Python to build** (`python-any-r1`,
  `glibc-2.44-r3.ebuild:39,115,1007`). So the glibc+bash gate cannot be built
  from source on a Python-free host (Z handles this).

### 0.4 What `lu-zero/portage-cli` offers, and why we only read it

Checked at `5e1098d` (2026-10-04), MIT licence.

- `em` runs phases as Rust brush builtins
  (`portage-repo/src/build/commands/install.rs`, 1721 lines: `doins`,
  `dosym`, `fperms`, `newins`, …), not the real `bin/*.sh`.
- Its `portage-binpkg::write_gpkg` shells out to `tar` + `zstd`, only knows
  zstd, and writes `metadata/` without directory members. That is not the
  shape `gpkg.py` produces.
- Its `gpg.rs` signs with `rpgp` rather than `BINPKG_GPG_SIGNING_COMMAND`.
- Its crates `portage-repo` and `portage-vdb` have the same names as ours.

**Decision (owner, 2026-10-08): reference only; Portage stays the primary
reference.** Each step names the portage-cli file worth reading next to the
real Portage source it ports. Nothing is imported, and nothing is copied
without first being checked against Portage.

### 0.5 Decisions (re-open any of these, do not silently change them)

- **D1 — one dispatcher, call sites untouched, a shrinking fallback.**
  - The vendored `bin/` keeps upstream's call sites byte for byte.
    `PORTAGE_PYTHON` points at a new shim, `bin/portuale-python`, which execs
    `"$PORTUALE_BIN" __helper python "$@"`.
  - The dispatcher picks the helper from the script basename (the first
    argument), or, for `-c`, from the exact `90config-impl-decl` program
    string.
  - **Transition table.** A script with no native port yet is re-executed
    with the real interpreter, with the original argv: `/usr/bin/python`, or
    `$PORTUALE_REAL_PYTHON`. Each of S3–S7 deletes its own row. The last
    of them asserts the table is empty.
  - **A transition row needs an installed Portage (Q7).** Only
    `filter-bash-environment.py` is vendored, and it is the only
    self-contained one. `doins.py`, `gpkg-helper.py`, `xpak-helper.py`,
    `xattr-helper.py`, `install.py` and `dohtml.py` are not in the embedded
    runtime, and all of them import the `portage` library (P0,
    `docs/evidence/2026-10-08-326-p0-inventory.md`). A row therefore
    resolves the script from the Portage that is present: the checkout's
    `bin/` (with its `lib/` on `PYTHONPATH`), else the system's
    `/usr/lib/portage/python*/`. With neither, the row exits 127 with
    `portuale: no native helper for: python <argv>`, the same as an unknown
    name. On [noportage] and [nopy], a helper works only once its own slice
    has ported it.
  - From then on, **anything unknown exits 127** with
    `portuale: no native helper for: python <argv>`, so an upstream re-sync
    that adds a Python call fails loudly.
  - `chmod-lite` and `ebuild-ipc` get their own shims under the upstream
    names. `ecompress-file` is vendored verbatim. All portuale-owned `bin/`
    files are listed in `bin/README.md`, so a re-sync does not overwrite
    them.
  - Why a shim rather than editing the call sites: the `bin/` re-sync stays
    a plain copy, and one table lists every Python entry point.
- **D2 — the oracle stays runnable.**
  - `PORTUALE_PYTHON_HELPERS=real` brings back today's behaviour:
    `PORTAGE_PYTHON=/usr/bin/python`, the checkout overlay, and the upstream
    `chmod-lite`. The `chmod-lite` shim honours it by exec'ing
    `<checkout>/bin/chmod-lite`.
  - Unset, or `native`, is the default. In `native` mode `bin_dir()` builds
    no overlay at all.
  - This switch is the A/B handle that every differential test uses.
  - `real` therefore needs an installed Portage too (Q7): the host, or a
    bed image with a checkout. It is never expected to work on
    [noportage] or [nopy].
- **D3 — what "equal to real" means, per helper.**
  - **Byte-identical output:** `filter-bash-environment`, `xpak recompose`,
    and the modes `chmod-lite` leaves.
  - **`has_utf8_ctype`:** the same answer as real for the locale the phase
    bash actually runs in (see S2.4).
  - **`gpkg compress`, field by field (fields, not raw header bytes):**
    - the same container members in the same order;
    - the same tar format per member: the container is USTAR, or GNU when
      `len(basename) >= 154` (`:1007-1008`); the metadata tar is always
      USTAR (`:1311,1316`); the image tar is USTAR or GNU per
      `_get_tar_format_from_stats` (`:1948-1986`) over
      `_check_pre_image_files` (`:1988-`), never PAX;
    - every tarinfo field equal except `mtime`;
    - the image tar as `TarFile.add(root_dir, "image", recursive=True)`
      builds it (`:1052`): `uname`/`gname` from `/etc/passwd` and
      `/etc/group` (empty when the lookup fails), hardlinks found through an
      inode table, children in sorted `listdir` order, directory names with
      a trailing `/`;
    - metadata members in raw `os.walk` order (`_generate_metadata_from_dir`,
      `:1844-1862`; this order depends on the filesystem, so the native
      writer uses raw `read_dir` order, never a sort);
    - every archive padded to a 10240-byte record, as Python's `close()`
      does;
    - identical decompressed payloads;
    - the Manifest identical except the `DATA` lines whose bytes depend on
      `mtime`, or on the compressor version and `MAKEOPTS`.
  - **`doins` / `install`:** identical resulting trees: paths, types, modes,
    owners, symlink targets, contents, mtimes when `-p` is given, and xattrs
    where the filesystem supports them.
- **D4 — expected values come from running the real helper.**
  - On the dev host with `3rdparty/portage`, a generator runs the real
    helper on each input. It writes the result as a pmtest fixture:
    `fixtures/helpers/<helper>/<case>/{args,in…,out…,README}`.
  - Rust unit tests read the fixtures through the `fixtures` symlink, so they
    run without the checkout.
  - Each case's `README` records everything the bytes depend on:
    - the Portage pin and the Python version;
    - the compressor binaries and their versions;
    - `MAKEOPTS` and `BINPKG_COMPRESS_FLAGS*`;
    - the `/etc/passwd`/`group` entries used;
    - `locale -a`.
  - The native side runs with the same values.
  - Filter patterns are **captured** from instrumented real runs (source and
    binary merges, EAPI 7 and 8), not rebuilt by hand.
- **D5 — remote clients run the server's own binary (owner, 2026-10-08).**
  - **Match.** The client must have a `portuale` with **the same SHA-256 as
    the binary the server ships**. That is `current_exe()` by default, or
    `--remote-portuale-binary=<path>` on the server (for example the static
    musl build, when the server itself runs a dynamic dev build).
  - **Name (owner, 2026-10-08, Q5).** `<hash>` is the first 16 hex digits of
    the SHA-256. Whatever file is found, the full digest is always what gets
    compared.
  - **Search.** In `/opt/bin`, then `/usr/local/bin`, check `portuale` and
    `portuale-<hash>`. The first file whose full digest matches is used. A
    plain `portuale` whose digest differs is **never touched**: it may be an
    operator's own install.
  - **Install.** If nothing matches, install as **`portuale-<hash>`** (never
    as plain `portuale`). The server streams the binary over the existing ssh
    connection into `mktemp <dir>/.portuale.XXXXXX`, runs `chmod 0755`,
    re-checks the digest, and `mv`s it to `<dir>/portuale-<hash>`. This is a
    rename, never an in-place write. A `portuale-<hash>` whose content does
    not match its name (corrupted) is replaced the same way. Different server
    builds get different names, so they never overwrite each other.
  - **Target directory:** the first of `/opt/bin`, `/usr/local/bin` that
    exists and is writable. World-writable directories without the sticky
    bit are refused.
  - **When.** The install is a client mutation, so it follows §5.5: it runs
    after the read-only stages, only when at least one unit will ship, and
    never under `--pretend` or with an empty plan.
  - **Absolute path everywhere.** From then on every client call uses that
    absolute path. Every generated script exports `PORTUALE_BIN=<abs>`, and
    no shim falls back to `PATH`; this includes `portageq-wrapper`.
  - **Local transport:** keeps `PORTUALE_BIN=current_exe()`
    (`local_client_bash`) and installs nothing.
- **D6 — no IPC daemon.** `PORTAGE_IPC_DAEMON` is dropped explicitly at both
  phase spawn sites (`ebuild_phases.rs:3808-3813`, `:4415-4417`, the same
  way `LC_ALL` is dropped there), and in the remote headers. The `ebuild-ipc`
  shim exits **127** with `portuale: ebuild-ipc is not supported (no IPC
  daemon)`. An exit code of 1 would make `has_version` silently answer "not
  installed" (`phase-helpers.sh:916-922`); 127 makes it die with
  `unexpected ebuild-ipc exit code`.
- **D7 — the helper entry has no side effects.**
  - `portuale __helper …` is dispatched first in `main()`, from
    `std::env::args_os()` (never `args()`, see 0.3).
  - It runs before anything else. It never calls `bin_dir()` (no extraction,
    no atexit), loads no config, and writes only its own outputs.
  - Known difference: a static binary is not intercepted by libsandbox's
    `LD_PRELOAD`, while the Python helpers were. Native `doins` therefore
    asserts that every write lands under `${D}`, or under its `--dest`
    argument.
- **D8 — `PORTUALE_BIN` is never a test harness.** Under `cfg(test)`,
  `portuale_bin_value()` resolves to the real `portuale` binary next to
  `deps/` (the pattern at `ebuild_phases.rs:5575-5580`). The test build makes
  sure it exists. A test runs `$PORTUALE_BIN __helper ping` and expects a
  fixed token.

### 0.6 Owner answers (all questions answered 2026-10-08)

- **Q1 (S8) Client login: root normally, non-root through
  `--remote-portuale-dir`.** `mrg` cannot escalate. The usual client login
  is root, otherwise it could not install packages into `/`, so `/opt/bin`
  and `/usr/local/bin` are writable.
  - A non-root login that owns its target ROOT is supported today
    (`remote-merge.md` §1; backlog #169's non-root client, uid 1000). It
    stays supported, but only through `--remote-portuale-dir=<abs dir>`
    pointing at a directory it can write.
  - The same two names are searched in that directory, and an install goes
    there. Tests use the option too.
  - If neither default directory is writable and no `--remote-portuale-dir`
    is given, preflight fails. The message names the option and says that
    the alternative is a root login.
- **Q2 (S8) Client tool floor: yes, both.**
  - Add `sha256sum`, `mv`, `uname` and `mktemp` to the preflight floor
    (`remote.rs:1020`, `:1075-1077`).
  - Reconcile §6's six-tool list with the 14 tools the code actually checks.
- **Q3 (S8) Architecture: the shipped binary must be built for the
  client's architecture.**
  - It is chosen with `--remote-portuale-binary=<path>`, defaulting to
    `current_exe()`.
  - Preflight compares its ELF `e_machine` with the client's `uname -m`, and
    after the install runs `<abs> __helper ping`.
  - A mismatch or a failure fails preflight, and the error names
    `--remote-portuale-binary`.
  - No cross-arch shipping in this plan.
- **Q4 (S4) Signed gpkg: gpg, as real does.** S4 runs
  `BINPKG_GPG_SIGNING_COMMAND`. A native rpgp signer is postponed, and not
  part of this plan.
- **Q5 (S8) The file name: `portuale-<hash>`.**
  - The search checks both `portuale` and `portuale-<hash>`, and an existing
    `portuale` whose digest matches is reused. See D5.
  - A plain `portuale` that does not match is left alone.
  - Old `portuale-<hash>` files from earlier builds accumulate. This plan
    does not clean them up; file a residue if it matters.
- **Q6 (S8) Placement vs ROOT: leave it unowned.** On a client with
  `ROOT=/`, the installed binary sits inside the managed system and no vdb
  entry owns it. S8.4 documents this.
- **Q7 (D1/D2, raised by P0) Where transition rows find the real scripts:
  from an installed Portage.** Vendoring only the `.py` files would not
  work, because they import `portage`, and vendoring `lib/portage` too
  would bring Portage back. Rows resolve from the checkout or the system
  Portage, and exit 127 without one. See D1.
- **Q8 (P0) P0 closes with four 0.3 rows NOT OBSERVED.** These are
  `xpak-helper.py`, `xattr-helper.py`, `install.py` and the locale probe.
  Every bare build dies at the first missing helper, so they cannot be
  reached yet. The slice that ports each one observes it (S5, S7, S7, S2).
