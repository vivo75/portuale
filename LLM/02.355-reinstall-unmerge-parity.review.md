## D — defects (in the plan's design)

**D1 (high; likely, from source) — S4 ships R3 without R2/R4/R4b, so the tree between S4 and S5 can unlink `/bin`, `/lib`, `/lib64` on `emerge -C`.**
- *Where:* plan S4 step 7. A `dir` entry that is a live symlink takes the sym branch and is unlinked. R4 (`!empty`), R2 (libdir ignore) and R4b come only in S5 ("then R4 (S5)").
- *Portage:*
  - `/lib`, `/usr/lib` and `/usr/local/lib` are exempt (`vartree.py:3042-3045`).
  - Every other `dir`+islink (on merged-usr: `/bin`, `/sbin`, `/lib64`, `/usr/sbin`) reaches the sym branch, where `!empty` (`:3131-3183`) protects it: `/usr/bin` holds children this package does not own. `_unmerge_protected_symlinks` (`:3324`) then finds the many packages that record `dir /bin` and keeps it.
- *Shape:* a merged-usr ROOT (`/bin -> usr/bin`) and `emerge -C` of a package whose `CONTENTS` has `dir /bin` (bash, coreutils, …).
  - Portage: `--- !empty dir /bin`, kept.
  - portuale today: `remove_dir` fails, kept.
  - portuale at S4 HEAD: `/bin` unlinked.

  The replace loop is protected by `is_owned`, so the glibc/bash reinstall gate cannot see this. Only `emerge -C` (and `ebuild … unmerge`) can. If the owner gives Q9's per-slice commit grant, S4 becomes a committed, dangerous state.
- *Fix direction:* move R3 into S5, in the same commit as R2, R4 and R4b. In S4, keep a `dir` entry that is a live symlink on today's path (kept). Alternatively, implement R2 and R4 inside S4. Also add the merged-usr `-C` cell described in G7.

**D2 (medium; likely) — Q3's `UNINSTALL_IGNORE` fallback ("unless a layer assigns it") breaks the usual `make.conf` append form, and U1 is written in exactly that form.**
- *Portage:* `UNINSTALL_IGNORE` is not in `INCREMENTALS` (`const.py:125-138`). A user adds patterns with `UNINSTALL_IGNORE="${UNINSTALL_IGNORE} /x/*"`, which expands against `make.globals`' `/lib/modules/*`.
- *portuale with Q3 as written:* in a hermetic root there is no globals layer, so `${UNINSTALL_IGNORE}` expands to empty. `make.conf` assigns the key, so the fallback is skipped and `/lib/modules/*` is lost. S0 U1 ("`UNINSTALL_IGNORE="/usr/share/t355/ign/*"` plus the default") then diverges because of the harness, not the code. A pmtest pin built the same way would ratify the wrong value.
- *The same weakness for `FEATURES`:* "unless a layer removes it" needs the "was this token removed" query that §3 risk 1 worries about.
- *Fix direction:* when `make.globals` was not read, seed a synthetic base layer **under** the stack, before `make.conf` expansion: `UNINSTALL_IGNORE="/lib/modules/*"`, and the token `unmerge-orphans` at the bottom of the `FEATURES` fold. For `FEATURES`, prepending the token is harmless even when the real `make.globals` was read, because it already carries it. This reproduces `-*`, `-unmerge-orphans` and the append form with no new `Config` query, and removes S4's stop condition. In S0, write U1's `make.conf` both ways, literal and `${UNINSTALL_IGNORE} …`, so the fallback is pinned.

**D3 (low-medium; proven by source and documented in code-notes) — S4's `MergeOptions::from_env` copies the non-incremental `ebuild.rs` rule.**
- *Where:* plan S4: "`from_env` sets it true unless `FEATURES` is set and lacks the token, the current `ebuild.rs` rule".
- *Portage:* `FEATURES` is incremental (`const.py:130`). The calling env is one more layer, so `FEATURES="buildpkg"` in the env keeps `make.globals`' `unmerge-orphans`.
- *portuale:* `FEATURES=buildpkg ebuild x.ebuild unmerge` turns the orphan arm **off**. `code-notes/portuale/ebuild_unmerge.md:39` already admits this. The `emerge` paths are saved only because `set_resolved_features` runs after `from_env`.
- *Fix direction:* in `from_env`, fold the env tokens over the `make.globals` default with the same `fold_token_layers` (`-tok` removes it, `-*` clears it). Alternatively, Q11's default of routing `ebuild` through the resolved helper should apply whenever a config root resolves, and the fallback should be the fold, not the literal test.

**D4 (low; likely) — R4's child-ownership check is specified as an exact `CONTENTS` match, but Portage's `isowner` matches through the parent's inode, and the plan cuts that.**
- *Where:* S5: "`contents_text_owns` on its own text". §0.2/§1 cut `_match_contents` inode matching.
- *Portage:* `self.isowner(child)` → `_match_contents` (`vartree.py:3527-3600`) stats the child's parent, following symlinks, and compares it against the inodes of recorded parent dirs. So `z-link/f` is owned when the package recorded `a-real/f`.
- *Shape:* A records `obj /usr/share/t355/a-real/f` and `sym /usr/share/t355/z-link -> a-real`; then `emerge -C A`.
  - Portage: `z-link` sorts first, every child is owned → unlinked, no elog.
  - portuale per plan: child not owned → `!empty` → R4b elog ("may need protection…", "safe to remove…") → unlinked. The file outcome is the same, but the output differs (Q2 ports the elog).
- *Fix direction:* for R4 only, compare `canonicalize(parent(child))` with the canonicalised parents of the package's recorded paths. Or file it explicitly with the inode-matching residue and say E3 is expected to diverge in output.

## G — gaps

- **G1 — T1/T2 setup does not restore the mtime, so the expected labels are wrong.**
  - T1: a directory replacing a recorded `obj` has a new mtime. Portage skips the orphan arm (`S_ISDIR`) and stops at `--- !mtime` (`:3114-3119`), not `!obj`. Only with the directory's mtime set to the recorded value does `!obj` (`:3200-3202`) show.
  - portuale under default `FEATURES` fails earlier: in the orphan arm (`ebuild_unmerge.rs:163-166`), not `:183-186`. So the divergence (portuale exits 1) holds, but the cell needs two variants: mtime new / mtime restored.
  - T2 (`-unmerge-orphans`, a `sym` replaced by a file) is **not discriminating** unless the file's mtime is restored: with a new mtime both sides keep it via `!mtime`.
- **G2 — E3 as described never reaches the `all_owned` loop.** `mykeys` is reverse-sorted (`:2918-2920`). With `real` > `link`, A's files under `real/` are unlinked before `link` is examined, `os.listdir` returns empty, and the link is unlinked directly. To exercise R4's "all owned" half (and D4), the link name must sort **after** the target (`z-link -> a-real`).
- **G3 — the `mrg` remote merge script is a fourth unmerge implementation, and the plan neither scopes it nor cuts it.**
  - `crates/portuale/src/remote/merge_flow.sh:31-34` builds the ownership lists with `awk '{print $2}'` (#357 shape).
  - `:177-200` removes the old instance on mtime only: no orphan arm, no protect, no `!md5`, no type guards, no `UNINSTALL_IGNORE`; `fif`/`dev` are "unmerge-skip".
  - Either add it to §0.3/§1, or record it as a named cut with its own residue number.
- **G4 — S1's pre-#354 bed run has no stated mechanism.** The bed takes the PM from `managers/managers.yaml` (`portuale.repo: ../portuale`, binary `../portuale/target/release/portuale`) via `PMTEST_PM`. Running a `8772601e^` worktree needs a temporary registry entry, for example `portuale-pre354` with `repo:` pointing at the worktree. That is a pmtest edit, and the plan should name it and say it is reverted or kept. The worktree's first release build is long, so budget for it.
- **G5 — Q4 overlooks the existing index rebuild and the read-only open.**
  - `WriteTxn::rebuild_index` already re-derives `owner` / `dep_atom` / `needed` in one transaction for sqlite (`sqlite/write.rs:520-535`) and redb (`redb_db/write.rs:447-460`), exposed as `portuale vdb rebuild-index` (`vdb_cmd.rs:179`). The `contents_parser` re-derive should call it rather than add a second path. This also settles risk 4 (atomic, idempotent).
  - The plan does not say what happens on `SqliteDb::open_readonly` (`sqlite.rs:267`) or a redb `ReadOnlyDatabase`, for example a non-root `emerge -p` on a root-owned DB. Specify: do not write; derive the answer at query time, or warn and use the stale rows.
- **G6 — R4b's owner search is exact-path, while Portage's `get_owners` also sees implicit parent dirs** (`getcontents` `:2286-2300`).
  - A package that recorded `obj /x/link/f` without `dir /x/link` owns `link` in Portage but not in portuale's `owners` (`files.rs:303-325`, and the sqlite/redb `owner` rows).
  - This is the destructive direction (portuale would unlink the symlink). Make R4b count a package as owner when any of its recorded paths has the symlink path as a proper prefix component, and test it.
- **G7 — no cell covers the `emerge -C` safety of system symlinks.** Add a hermetic S0 cell and a pin.
  - Setup: ROOT with `bin -> usr/bin` and `lib64 -> usr/lib64` holding untracked files; package A records `dir /bin` and `obj /bin/t355`; then `emerge -C A`.
  - Expected: Portage `!empty` plus the R4b owners search; whether `/bin` survives depends on other owners. This is the cell that would have caught D1. The glibc/bash gate exercises only the replace loop.
- **G8 — S3's "` -> ` inside a target" unit test must pin Portage's mis-split.** For `sym /p -> x -> y 123`, the greedy regex yields path `/p -> x` and target `y`. The plan states the rule but not that the expected value is this wrong-looking split. Make it explicit so the executor does not "fix" it.
- **G9 — an unfiled divergence turned up during the audit (likely).**
  - portuale's preserve-libs path has no `FEATURES` gate: `find_preserve_paths_for_merge` (`after_install.rs:184-199`); `plib_merge.rs` and `plib_unmerge.rs` contain no `features` reference.
  - Portage gates it on `preserve-libs` (`_find_libs_to_preserve`), and #354 matrix row `f0` captured `FEATURES=-preserve-libs` removing `libt354b.so.1`.
  - Not in this plan's scope. It needs a backlog number (see P2).
