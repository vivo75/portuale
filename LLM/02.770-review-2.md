## D — defects (in the plan)

### N1. Option A turns the stale-pin arm OFF for walked consumers when `--update` is absent; the plan says it turns it on. Severity: medium. **Proven** (source); effect on output **likely**.

- `rebuild_scan.rs:244-250`: `in_scope = reachable ∋ cp || walked_installed ∋ cp`;
  `stale_scope = if update { in_scope || !walked ∋ cp } else { !in_scope }`.
- With option A, a walked `p569virt` gets `in_scope = true`. Under `--update` → `stale_scope` true (the plan's
  claim holds). Without `--update` (`-DN`, `-D`) → `stale_scope = false`: the stale-pin arm, which is the arm
  that schedules `rR p569virt-1` on pubgrub today under `-DN` (§0 item 2, first-round D6), stops running for it.
- Scheduling under `-DN` then depends on the same-slot arm (`same_slot_scope` becomes true because
  `new_slot` holds `p569prov`). That arm very likely fires (the default solver passes the same
  `walked_installed` and prints `rR` under `-DN`), but it files differently: it pushes the provider into
  `scheduled` via `provider_joins` (`rebuild_scan.rs:362-363`) and emits the pair from the same-slot branch.
  The `-DN`/`-D` output may move in the pair text, and any refusal line the stale-pin arm prints today for a
  walked consumer under no-`--update` disappears.
- Plan text: Q1 A "Option A switches on both `same_slot_scope` and `in_scope`, so the stale-pin arm also
  becomes live for walked consumers"; S2.3 "check every new refusal or NOTE line".

**Fix direction:** correct the Q1 A sentence ("live under `--update`; under no `--update` it is turned off for
walked consumers and the same-slot arm takes over, as on the default solver"). In S2.3 name `-DN @world` and
`-D @world` on pubgrub as must-still-print-`rR` probes, and check vanished refusal lines as well as new ones.
Add an `update = false` variant to S1.3's Rust tests (walked consumer still `Reinstall`).

### N2. S2.1 cannot compute the walked set where it says. Severity: low. **Proven** (source).

- S2.1: "compute the bridge's walked-installed set (Q1 A) next to `slot_op_reachable` in
  `bridge_slot_operator_rebuilds`". That function takes `(req, entries, lazy)` only
  (`solver_bridge.rs:1570-1574`); the solution's `parents` map is a parameter of `graph_result_from_order`
  (`:879`), which calls it at `:908`.
- `parents` is keyed by the child `cpn-ver` with parent `(cat, pkg)` values, no parent version
  (`solver_bridge.rs:5579-5596`). A downward transitive walk from merge-bound entries needs the inverse map;
  `solution_taken_edges` / the inverter at `:2637-2644` exist for that.
- So the change is two signature changes (`bridge_slot_operator_rebuilds` gains `parents`, the args struct gains
  `walked_installed`), not "one new argument, about 15 lines".

**Fix direction:** say so in Q1 A / S2.1, and name the existing inverter to reuse, so the executor does not
write a second one.
