## 1. Cross-cutting rules and gotchas (apply to every section)

1. **Layout convention (owner to pick one).** The repo already uses both
   `helpers/mod.rs` and `vdb_rw.rs` + `vdb_rw/ops.rs`. rust-skills
   `proj-mod-rs-dir` suggests directory modules; I write `foo/mod.rs` below.
   `git mv foo.rs foo/mod.rs` keeps blame. If the owner prefers `foo.rs` +
   `foo/`, nothing else in the map changes.
2. **Stable paths.** `portuale` is a binary crate: every `mod x;` is in
   `main.rs`, so external callers use `crate::pretend::load_repos_and_config`
   etc. Each `foo/mod.rs` re-exports exactly the items that other modules use today
   (counts, from `grep`):
   - `pretend`: `run`, `load_repos_and_config`, `config_features_string`,
     `config_install_mask`, `config_bzip`, `load_config_quiet`.
   - `ebuild_merge`: `XattrPolicy`(19 uses), `MergeOptions`(9), `run_merge`(4),
     `write_cfgfiledict`, `read_cfgfiledict`, `preserved_lib_paths`,
     `apply_install_mask`.
   - `ebuild_phases`: `bin_dir`(6), `ShellBackend`(4), `require_phase_runtime`(3),
     `run_phase_from_saved_env`, `resolve_entry_portage_tmpdir`, `repo_root_for`,
     `package_sets_conf`, `BIN_DIR_VAR`, `run_commands`, `portage_checkout`,
     `match_package_env_vars`, `match_package_env_incremental_raw`,
     `fold_package_env_incremental`.
   - `remote`: `ConfigPlacement`(7), `check_remote`, `take_remote_exec`,
     `run_remote_plan`, `run_remote_cli`, `check_binary_plan`, `RemoteTransport`,
     `ClientBinPlan`.
   - `emerge_build`: `StatusDisplay`(10), `StatusMode`, `run_wide_phase_env`,
     `resolved_features`, `progress_color`, `entry_buildpkg_wanted`,
     `build_log_path`, `system_loadavg_1min`, `scheduler_status_mode`,
     `run_merge_loop`, `reloaded_config_protect`, `merge_progress_map`,
     `merge_one_source_entry`, `installing_line`, `entry_counts_toward_progress`,
     `emerging_line`, `completed_line`.
   - `binpkg`: `GpgVerify`(25), `read_gpkg_metadata`(8), `populate_local_pkgdir`(7),
     `read_xpak_metadata`, `extract_binpkg`, `verify_gpkg_manifest`,
     `DEFAULT_GPG_VERIFY_BASE_COMMAND`, `read_outer_members`,
     `verify_binpkg_against_index`, `read_xpak_segment`, `parse_xpak_members`,
     `digest_failure_block`, `checksum_failure_rename`.
   - `portage-repo` is a library: every `pub` item of `lib.rs` is public API for
     `portuale`, `portage-*` and `mrg-director`. Re-export with explicit
     `pub use module::{...}` lists (not `*`) so a stray `pub` does not leak, and
     keep `pub mod md5_dict;` and the existing `pub use merge_order::{...}` in
     `lib.rs`.
   Recompute these lists with `grep` right before each step; they will have grown.
3. **`pub(crate)` narrowing (`proj-pub-crate-internal`).** Inside a library
   crate, a private fn that used to be shared by two regions of `lib.rs`
   becomes `pub(crate)` (or `pub(super)` inside a module tree) when it crosses a
   new module boundary. Expect this to touch hundreds of fns in `portage-repo`
   (section 2.4). Do not widen anything to `pub`.
4. **`no_hand_built_vdb_paths.rs` lint (the real gotcha).** The lint
   (`crates/portage-vdb/tests/no_hand_built_vdb_paths.rs`) walks every `.rs` file
   under `crates/`, skips path components named `tests`, `target`, `portage-vdb`,
   and skips lines inside a `#[cfg(test)]` span found **in the same file**. A
   moved `foo/tests.rs` contains no `#[cfg(test)]` attribute (it sits on
   `#[cfg(test)] mod tests;` in the parent), is not in a directory called
   `tests`, so every `var/db/pkg`, `"world"`, `VDB_DIR` literal in it would be a
   violation. Plan 6.1 already says "first teach the lint to skip `tests.rs`";
   do that **before the first test move**. Alternative with no lint change: put
   the files in a directory named `tests/` (`foo/tests/mod.rs`, `foo/tests/ask.rs`).
   The lint's allowlist matches on substrings, not line numbers, so moving
   production lines does not break it; `#[cfg(test)]`-only helper fns in
   production files (e.g. `installed_cp_sources_with`, `lib.rs:835`) stay
   exempt as long as they carry their own attribute.
5. **Relative paths / `include_str!` / `#[path]`.** The nine target files use
   only `env!("CARGO_MANIFEST_DIR").join("../../fixtures...")`, which is
   compile-time absolute and survives any move. No `include_str!`, `#[path]`,
   `file!()` in them. The only relative includes are in `vdb_rw.rs:1425-1564`
   (`#[path = "vdb_rw/ops.rs"]`, `include_str!("vdb_rw/testdata/...")`), which is
   **not** a target here; if `vdb_rw.rs` ever moves its tests, those four paths
   change (plan D12). `embedded_runtime.rs` `include!(concat!(env!("OUT_DIR"),...))`
   is untouched.
6. **Test identity changes.** Test names become `pretend::tests::foo` ->
   `pretend::prompt::tests::foo`. `verify-pass` compares by test NAME, so each
   move step needs an old->new name map (a `cargo test -- --list` before and
   after, diffed after stripping module prefixes) and the harness/doc references
   to module-qualified test names (`grep -rn "tests::" LLM docs ../pmtest`)
   must be checked. Doc references of the form `file.rs:123` go stale with any
   move; `graft build` after each step.
7. **Test helpers.** Large test modules share helpers
   (`fixtures_root`, `test_config`, `resolve`, `tmp_vdb`, ...). Put the shared
   ones in a `#[cfg(test)] pub(crate) mod test_support;` per crate (portage-repo,
   portuale) and import them from each `tests.rs`. The `tests_16x` modules in
   `portage-repo` deliberately duplicate their own helpers ("self-contained so
   rebases stay mechanical"); keep them separate files and do not dedupe
   during the move.
8. **Cycles to avoid.** Within each crate, the dependency direction should be
   leaf utilities -> domain modules -> orchestration (`run`, `backtracking_resolve`).
   Concretely: `portage-repo` modules below `resolve/` must not call into
   `resolve/pass.rs`/`driver.rs`; they only take data structures from
   `resolve/state.rs`. Where today a leaf fn takes `&ResolveCtx` (defined at
   `lib.rs:27088`) the struct moves to `resolve/ctx.rs`, a leaf both sides import.
9. **Pure moves.** No renames, no signature changes, no reordering of `impl`
   blocks, no change in `static`/`thread_local!` identity (they move with their
   functions; there is one definition each). `#[allow(...)]` attributes stay on
   the item. Keep `//` header comments of a file in the parent `mod.rs`.
