## 0. Owner ruling (read first — this inverts nothing, it builds on #749)

#749 deleted the illegal machinery (the positional duplicate, `built_twice`, the
checker excuse) and rewrote charter 2a to the literal rule: a build dependency
must be installed before the build, a runtime dependency need only be present by
the end, and a cycle no order satisfies is reported, never papered over. The one
rebuild the project recognises is the bootstrap (charter 2a, last paragraph).

Owner's shape, verbatim: *"`pkgnew` depends on `usefoo? ( otherpkg[useblah] )`;
`otherpkg` depends on `useboh? ( pkgnew[use3] )`. If otherpkg has useboh and
pkgnew has usefoo the cycle exists. It can be serialized: 1) build
`USE="-useboh" otherpkg` (temporary), 2) build `pkgnew`, 3) build `otherpkg`
with the declared USE (definitive)."* (Step 2 is `pkgnew`.) The owner fixed
the *invariants*: at most **3 rebuilds**, the **last build must be the files
a normal build would have produced** (declared USE/version), earlier builds
are bootstrap only, and the user must be told they happened (property 5).
The owner left the *selection rule* (which package, which USE) to the
implementation — which is why §1's reduction rule is a [default sicuro],
not a question for the owner.

Grounding: charter property 2a (the bootstrap paragraph) and property 5 (the
user is told); PMS dependency semantics (USE-conditional dependencies — the
conditional arms are what the reduction removes). Portage does not implement
this — no Portage capture is owed or claimed, and no test docstring cites one.
The #749 report line (`plan-world: build cycle with no serial order: …`,
`build_time_cycles` in `crates/portage-world/src/order.rs`) and the checker's
`build-order` cycle failure are the starting point: today the genuine cycle
fails; after this plan it succeeds **only** in the owner's 3-step shape.

One writer in the tree at a time; no `../pmtest` suite while a bed run is
active. Do not file backlog numbers (report proposed residues to the owner
instead); do not commit or push.

## Decisions taken by this plan (all [default sicuro]; no open [BLOCCA])

- **[default sicuro] Which package and which USE to reduce.** The smallest
  deterministic reduction that breaks the cycle: take the reported
  build-time cycles in reported order (cycles in `cycles.sort()` sorted
  order; members within one cycle in walk order — the review-corrected
  reading of `order.rs:330-392`); within
  each cycle, walk its members in member order and collect the USE flags
  guarding each member's outgoing cyclic conditional edges, sorted by flag
  name; take the first flag whose removal drops that outgoing edge.
  Tie-breaks, in order: prefer a flag that breaks more than one reported
  cycle in the same pass; if several flags qualify for one edge, the
  lexicographically first. Only one flag is ever reduced (the "smallest
  reduction" is one flag, never a set). On the owner's pair this yields
  `otherpkg` with `-useboh` (the `useboh` arm guards the
  `otherpkg -> pkgnew` edge; removing it breaks the cycle; sorted order
  meets `otherpkg` first). If no single flag on a cycle's edges breaks it, take
  the next cycle; if no cycle has one, the reduction is `None` — the cycle
  is reported as today, never enumerated as flag combinations.
  The rule lives in the leaf `crates/portage-use-reduce` (both
  `portage-repo` and `portage-world` already depend on it; the rule is a
  pure function of cycles + guard flags needing no resolver state), so both
  callers share one implementation and agree by construction — the reverse
  direction is impossible (`portage-world` depends on `portage-repo`, never
  the reverse, so the selection cannot live in `portage-world/src/order.rs`).
  Rationale (recorded, not an owner answer): this is the smallest
  deterministic reduction, it reproduces the owner's own `otherpkg`
  `-useboh` choice for the exemplar shape, and it needs no search.
- **[default sicuro] Boot-build representation.** A boot build is never a
  second identical row (that is what #749 removed). A boot row carries an
  explicit marker: `--json` `entries` objects gain `"bootstrap": true` plus
  `"reduced_use": ["-useboh"]` (the flags removed relative to declared USE)
  on boot rows only; the final row of the same slot carries the declared USE
  and no marker. Text output prints the boot row with a
  `(bootstrap: USE="-useboh" temporary — will be rebuilt with the declared
  USE)` suffix. No existing pin moves: acyclic plans emit no `bootstrap`
  key and no suffix (byte-identical by construction, proved by the S1.3 unit pin and confirmed by the S3 suite run).
- **[default sicuro] Survivor invariant.** The last row per slot must equal
  the declared build: same version, same USE (the reduced flags restored),
  same recorded bindings (slot-operator/sub-slot targets as the resolver
  records them for a normal build). The S1 test proves it by building the
  same slot once normally (flags off / cycle absent) and comparing the
  recorded fields of the final bootstrap row against that reference.
  Bootstrap artifacts are gone after the survivor by construction: the boot
  row's files are overwritten by the definitive merge of the same slot
  (same `cat/pn` reinstall path, not a second slot), so there is nothing for
  the checker to "excuse" — a bootstrap row that is *not* last is a failure,
  not a note (S2).
- **[default sicuro] Resolver vs fast plan.** The resolver
  (`crates/portage-repo` plan builder — the real merge path) is the source;
  the fast plan (`crates/portuale/src/plan_world.rs`) follows. The selection
  itself is the shared leaf implementation in `crates/portage-use-reduce`
  (see above): both callers feed it the same cycles + guard map and emit
  the same `(slot, flag)`, so they agree by construction — no duplicated
  rule, no cross-crate agreement test needed. The merge list shows all three
  builds in order
  (`otherpkg[boot] -> pkgnew -> otherpkg`), with the boot row marked as
  above; `--pretend` shows the same three rows (the user is told before
  anything merges — property 5).
- **STOP rules (not negotiable, S0/S1 enforce):** (0) the guard-flag seam
  is not recoverable through the existing `World`/config seam → STOP with
  `NEEDS_CONTEXT`: no invented unconditional stand-in, no harness change
  to force it (S0.2 probes this first); (1) no single-flag reduction
  breaks any reported cycle → report the cycles as today (the #749 failure
  stands), do not enumerate multi-flag sets; (2) the reduced boot build
  itself still needs the other package at build time — decided by the S1.1
  `boot_closure_reaches_member` DFS on the reduced build-kind edges (no
  second resolve): if it still reaches the other cycle member, stop; (3) more
  than 3 builds would be needed (longer loops get one boot build each only if
  the total stays ≤ 3 rows for the affected slots, else report).
