# crates/portage-repo/src/slot_operator/rebuild_scan.rs
Rebuilds triggered by slot-operator dependencies.

## fn slot_operator_rebuild_scan
- Portage `_slot_operator_trigger_reinstalls` (`_emerge/depgraph.py:3089-3132`): the post-walk scan for consumers needing a slot-operator rebuild, with a same-slot arm (bound sub-slot moved under a replacing provider) and a new-slot arm (bound slot abandoned for a fresh one).
- `new_slot`: cp -> (new version, new slot, new sub-slot) for every entry that replaces an installed version in that slot. `new_slot_fresh`: the same for every entry merged into a fresh slot (no installed instance there) -- Portage's `_get_installed_best` empty-`myinslotlist` case, rendered `[ebuild N]`. A provider that moves slot only ever arrives via `new_slot_fresh`; the update probe's new-child-slot arm (`:3121-3126`) prefers these, falling back to `Upgrade`/`Downgrade`/`Reinstall` entries in a slot the consumer is not bound to (same Portage candidate loop).
- Portage only rebuilds consumers of a package this run actually leaves at a new slot.
- Backlog #303: under `--update`, a non-requested provider the pass *downgraded* was held back by an installed consumer's built `:=` pin (the pass picked the older sub-slot the consumer is bound to). Portage's first pass does the same, then `_slot_operator_update_probe` (`depgraph.py:3131`) finds the installed instance as the missed update and backtracks to replace the consumer.
- `installed_by_cp`: the update probe's superseded child (`dep.child`) is the installed instance in the consumer's bound slot, looked up per built atom.
- #65 S2: every cp this pass actually walked (any outcome, installed nodes included). Portage only registers a slot-operator dep for a *built* parent's `DEPEND`/`BDEPEND` when the walk reaches it non-optionally (`_add_pkg_deps`' `optional=pkg.built`, `depgraph.py:4277/4287` combined with `dep.want_update`, `:3802-3806`), so a consumer that complete mode merely *reaches* (`slot_op_reachable`) never rebuilds through a build-time key. The world shape still qualifies: there the consumers are walked nodes (complete-mode seeds), not reachability-only. `RDEPEND`/`PDEPEND`/`IDEPEND` keep the wider `reachable` gate.
- #24 S5 scoping: the post-walk vdb scan stays behind the `reachable` gate (complete mode) for the same-slot arm. The #211 new-slot arm additionally accepts walked consumers: Portage registers slot-operator deps for every walked parent (`_add_pkg_deps`), and the update probe's own gate is `want_update`, not reachability -- an empty world (the conflict-mass shape) leaves `reachable` empty while the installed consumers sit in the graph as walked nodes. The `_slot_change_probe` half is *not* complete-mode gated in Portage (its first trigger arm runs for any merge-bound parent, 3103-3107).
- #211 R2: the update-probe refusal parents (Portage `_slot_operator_check_reverse_dependencies`, `depgraph.py:2472`). Collected once per scan; the per-edge verdict reads the replace set as it grows (see `probe_refused` in abi_probe).
- #288: Portage records the arguments as parents too (`_add_parent_atom`), so an argument pin vetoes a provider candidate it does not match.
- #268 cut (a): the requested cps Portage's `--update` greedy expansion actually pins (`greedy_pinned_cps`). Collected once per scan; the #252 gate reads it per edge.
- #268 cut (b): per-(provider, bound-slot) memo for the revision check (tree metadata + effective-USE walks, so not recomputed per consumer edge).
- #65 S1/S2 dep keys: Portage empties a built package's DEPEND/BDEPEND when bdeps is not y/auto, and only the consumers the walk reached non-optionally can fire through them.
- #269 display rule: only the same-slot arm contributes display pairs.
- #211 R2: Portage `_slot_operator_check_reverse_dependencies` (`depgraph.py:2472-2573`, gates `:2622`/`:2738`) refuses the whole replacement when the fresh candidate violates another parent's atom -- on both arms alike.
- #24 S5 tail: the slot-move-without-revbump arm (bug 456208). The #212 binary arm rides the same call and reports stale binaries into `masked` for `collect_feedback`'s `slot_operator_mask_built` records.
- #72 B3: a removal installs nothing, so it is not "in graph" for the slot-operator rebuild scan (Portage only rebuilds consumers of a package this run actually leaves at a new slot).
- #269: Portage's probe ranges over every *available* package (`_iter_similar_available`, `depgraph.py:3015-3057`), not just the scheduled entries: a provider upgrade nobody pulled in (the `mmcons` shape) still rebuilds the consumer. Ebuilds only: a binary candidate has no ebuild-visibility verdict at this layer (cut, same direction as the old miss). Visible ones only (Portage's `_pkg_visibility_check`), highest first like the walk's own selection; versions already installed are not updates (Portage's `pkg.installed` skip).
- #24 S5: Portage `_slot_change_probe` (`depgraph.py:2317-2359`), the slot-move-without-revbump arm (bug 456208). Runs even when the vdb scan above is gated off (Portage's first trigger arm is not complete-mode gated) -- see the helper's own doc comment. The #212 binary arm rides the same call and reports stale binaries into `masked` for `collect_feedback`'s `slot_operator_mask_built` records.

## fn slot_op_edge_for_atom
- #269: Portage's update probe ranges over every *available* package (`_iter_similar_available`, `depgraph.py:3015`), not just the scheduled entries, so the new-slot arm can fire with both maps empty (the `mmcons` shape: no pass schedules the provider, yet the probe finds it among the available packages). The arm itself still needs `want_update` (the per-candidate gate), which is exactly `update || provider requested`.
- Same-slot arm scope (frozen): complete-mode reachability only. New-slot arm scope (#211): reachability or walked this pass. Merge-bound consumers stay skipped by the `in_graph` rule -- their live `:=` re-binds through their own walk and their vdb is rewritten at merge, so no reinstall is needed (Portage's not-installed-parent disjunct would probe them; the refusal half of that probe is v2 `#24b` remainder either way). Unlike the same-slot arm the new-slot arm needs no scheduled entry -- the outer `want_probe` gate already covers that.
- #211 (v2 `#24b`): Portage `_slot_operator_update_probe` with `new_child_slot=True` (`depgraph.py:3121-3126`, bug 486580): an installed consumer whose built `:S/SS=` dep is bound to a slot the provider no longer occupies rebuilds against the fresh slot. Candidates are the fresh (`New`) entries first, then `Upgrade`/`Downgrade`/`Reinstall` entries in a slot the consumer is not bound to -- but only while no greedy request-argument pin covers the bound slot (the #252 gate): Portage's candidate loop (`_iter_similar_available`, `:2660-2695`) ranges over every available package, yet the reverse-deps gate refuses each off-slot candidate against the `P:S` arg, so a bound-slot mismatch on a requested provider's upgrade probes nothing (entries at the bound slot stay with the same-slot arm above). First acceptable candidate wins, gates and R2 refusal per candidate.
- #252: Portage's greedy request-argument pin. Under `--update` Portage expands a directly-requested cp into per-slot arg atoms (`_select_files`, `depgraph.py:5380`, via `_greedy_slots`, `:5896`): every installed slot below the highest visible slot gains a `cat/pkg:S` arg recorded on the installed instance in S (`_add_parent_atom`, `:4136`). The update probe's reverse-deps gate (`_slot_operator_check_reverse_dependencies`, `:2472-2538`) checks the fresh candidate against those too, and a non-`Package` parent goes straight to the atom match (`:2487-2541`) -- so every candidate in another slot is refused, the probe returns None, and the replace set stays empty.
- #252 evidence: probed on Portage 3.0.82.2 (host staged-fixture probe 2026-09-29, plus a vendored-`ResolverPlayground` spy run): on the `mmprov` shape (`mmprov` requested, consumer bound `0/1=`, upgrade `1/1 -> 1/2`) both `new_child_slot` forms return None -- the `mmprov:0` arg kills the slot-1 candidates -- and only `mmprov-3` merges. Without the pin (provider not requested, bound to the highest slot, or no `--update`) the arm fires as before.
- The pin is recorded per installed instance, but the edge already carries its bound slot (`a_slot`), and every candidate this arm keeps sits in another slot -- so a pin on `a_slot` refuses the whole edge.
- #268: both cuts are now modelled. (a) The pin only exists when the request atom spans slots (`greedy_cps` -- Portage `_greedy_slots`' own single-slot emptiness): an explicit slot or exact-version request pins nothing, so the arm fires. (b) The pin must survive the greedy revision with blocker lookahead (`greedy_pin_survives_revision`): a discarded pin refuses nothing, so the arm fires and the old slot is uninstalled instead of updated. Still cut: the pairwise lower-version discard among two or more greedy packages (needs three installed slots).
- #288 detail: an installed provider instance in another slot that an argument names is a graph package (Portage selects it for the argument), hence a probe candidate the argument itself accepts: with `=mmprov-2` the rebuild proceeds against it, while `=mmprov-1` (the bound slot's own instance) leaves no other-slot candidate the argument accepts.
- #269 detail: the `mmcons` shape (a provider upgrade nobody pulled in still rebuilds the consumer). A binary candidate has no ebuild-visibility verdict at this layer (cut, same direction as the old miss).
- The superseded child: Portage `pkg < dep.child` skips downgrades; equal versions -- a slot move without a revbump -- probe.
- `want_update` stand-in (Portage `:3805-3809`): `--update`, or the provider itself is directly requested (Portage's arg-chain disjunct). The registration-time complete-mode/depth nuance is not modelled.
- A `replacement_parent` must exist: with no visible tree candidate the forced reinstall would dead-end (Portage finds no replacement and does nothing).
- #304: a replacement parent whose own atom accepts the new slot must exist (`replacement_parent_accepts`).
- #269 backtrack shape: Portage's `_slot_operator_update_backtrack` (`depgraph.py:2442`) files the child (provider) reinstall only when `new_child_slot is None` -- the new-slot arm records the consumer alone, so only the same-slot arm contributes `(provider, consumer)` display pairs (Portage's `_forced_rebuilds`, what renders the provider `r` and the `causing rebuilds` block). The consumer itself is scheduled on both arms alike.

## type SlotOpRebuildScan
- The consumer `(cat, pkg)` replace set is Portage `_slot_operator_replace_installed`; the display pairs are Portage `_forced_rebuilds` (what `_show_abi_rebuild_info` renders); the stale-binary triples feed `collect_feedback`'s `slot_operator_mask_built` records (Portage `_slot_change_backtrack`, backlog #212 v2 `#24c`).
