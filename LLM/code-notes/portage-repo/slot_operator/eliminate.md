# crates/portage-repo/src/slot_operator/eliminate.rs
Eliminating unnecessary slot-operator rebuilds.

## fn slot_operator_eliminate_rebuilds
- Backlog #24 S4: Portage `_eliminate_rebuilds` (`depgraph.py:3859-4000`), the undo path. Rules, with Portage's line refs: 1. installed instance at the same cpv (a Portage upgrade is never undone); 2. `--newuse`/`--changed-use` wins (`pkg in _reinstall_nodes`); 3. `--changed-slot` (3898-3899): keep the rebuild when the tree ebuild at the same cpv moved `(slot, sub_slot)` vs the installed instance -- landed in S5; for an ebuild consumer rule 6 already keeps every such rebuild (the entry's own slot *is* the tree ebuild's), so the line is behaviour-neutral until the binary halves land (v2 `#24c`), kept in Portage's position so that half drops in without moving rules; 4. every parent atom matches the installed instance; 5. non-`selective` only: no user-asked parent; 6. installed and new `(slot, sub_slot)` equal; 7. built `provides`/`requires` equal -- not reachable in v1: the binary halves are v2 `#24c`, so a binary entry keeps its rebuild; 8. the dep comparison: `flat_dep_atoms` (use-reduced against the *new* node's enabled USE) of `bind_slot_operator_deps`'s bound tree string vs the vdb string, both through `strip_libc_atoms`.
- The rules come from the plan's §1.2, applied in Portage's order. The caller drops demoted cps from the set and latches them in `slot_operator_undone`.
- Portage `match(root, atom, installed=False)` only ever sees a *non-installed* graph pkg; the S3 flip is the only thing that constructs `slot_operator_rebuild: true`, and an ordinary Upgrade/Reinstall-for-USE entry keeps its rebuild like Portage's `installed_instance.cpv != pkg.cpv` / `_reinstall_nodes` arms.
- Rule 7 hoisted above rule 1 (Portage checks `pkg.built` between rule 6 and 8): the pre-filter can only *keep* a rebuild, and rules 1-6/8 are all keep-on-mismatch, so the only decision it can change is the all-rules-pass demotion that IS rule 7's domain -- no ordering counter-example exists.
- Portage `installed_instance = match_pkgs(pkg.slot_atom)[0]`: the installed instance in the *entry's* own main slot.
- Rule 3 detail (Portage 3898-3899, S5): `--changed-slot` keeps a rebuild whose tree ebuild at the same cpv moved (slot, sub_slot) vs the installed instance (Portage `_changed_slot(installed_instance)`). Portage also checks `_changed_slot(pkg)`, always false for a merge-bound ebuild entry -- its slot *is* the tree ebuild's -- and rule 6 is the ebuild equivalent, so this is behaviour-neutral until the binary halves land (v2 `#24c`).
- Rule 8 detail: Portage `except InvalidDependString: continue` keeps the rebuild on an unparsable *installed* string; treating either side's parse failure as "not equal" keeps it too.
- Skipped entirely under `--emptytree` (Portage `"empty" in myparams`) and under any live slot conflict (`entries` cannot see the pass; the caller checks, Portage bug 922038).

## fn slot_operator_rebuild_entries
- #24 S3 legacy path, for the `--solver=pubgrub` / `--solver=resolvo` bridges only (`solver_bridge.rs`). Those engines have no `Backtracker`, so they cannot re-drive a pass with the consumer seeded as a walked node the way the default resolver now does; they keep the pre-S3 post-pass synthesiser: run `slot_operator_rebuild_scan`, build one `Reinstall { slot_operator_rebuild: true }` entry per scheduled consumer, and iterate until the set stops growing (the cascade the scan itself no longer walks -- a rebuild lands at its *tree* ebuild's sub-slot, which when it differs from the vdb's is itself a slot shift the next round chases).
- Same cuts as the v1 synthesiser it is: empty `deps` / `required_by`, so a synthesised rebuild falls back to array position in `topological_merge_order`, and its own `RDEPEND` is never re-walked. The default `--solver=portage` path has none of that -- see `BacktrackParams::slot_operator_replace_installed`.
- #212 cut: the scan's stale-binary triples are dropped here. The bridge resolves in one shot with no `Backtracker`, so there is no re-pass a `slot_operator_mask_built` record could steer (Portage enforces the mask through the backtrack-config restart, `depgraph.py:5703-5712`); recording one would be dead state. The bridge keeps its pre-#212 answers on stale-binary shapes.
- #211 I1: the `--solver=` bridge threads the same `update`/`top_level` context the default path passes, so both solvers agree on the new-slot arm (the request carries both -- the "no context at this layer" cut that kept this fixpoint same-slot-only is gone).
- The rebuild lands at the tree ebuild's SLOT, not the vdb's (Portage re-reads `SLOT` at merge time).
- The installed repo is `__unknown__` when the vdb records none (Portage `portage.versions._unknown_repo`) -- the same value `resolve_pretend`'s own oldbest assembly compares (backlog #247).
- Portage `output.py::_get_installed_best` (721-731): the rebuilt cpv is already installed (`replace = True`), so the `[oldver]` bracket shows when the rebuild lands at a different slot/sub-slot than the installed instance (the sub-slot bump driving the cascade) *or* when the repo differs and repo display is not quieted (the third disjunct -- #247 ported it to `resolve_pretend`, #274 ports it to this synthesiser assembly; `--quiet-repo-display` stays an unimplemented option exiting 2, so every successful run has it off and the disjunct reduces to the repo comparison).
- The entry is the tree package being merged (Portage `pkg.repo`), not the installed instance -- the two agree unless the repo drifted, in which case the row keeps `::tree` and the bracket names the installed repo.

## fn rebuild_if_entries
- Portage `_emerge/depgraph.py`'s `_rebuild_config` covers an already-installed package whose own build-time dependency (`DEPEND`/`BDEPEND` in its vdb, resolved against its *built* `USE`) is satisfied by a package this run is merging. `_needs_rebuild(dep_pkg)` -- for portuale every merge is from source (`dep_pkg.built` is always false), so: `unbuilt` triggers always (a source build invalidates any binary parent); `new_rev` triggers unless the merged `cat/pkg-version` (revision included) is already one of the installed versions of that cp; `new_ver` is the same but with the `-r<n>` revision stripped from both sides.
- The caller resolves the Portage precedence (`unbuilt` > `new_rev` > `new_ver`; `=n` disables) so at most one of the three is set here.
- `--rebuild-exclude ATOMS` matches the *parent* (skip rebuilding it); `--rebuild-ignore ATOMS` matches the *dep* (it never triggers a rebuild) -- both the same two-tier `matches_config_entry` matcher `excluded` uses. Structurally a sibling of `slot_operator_rebuild_entries` above (same `all_installed_packages` scan, same `Reinstall` rebuild-entry shape) -- `--rebuild-if-new-slot` stays that function's job.
- #72 B3: a removal merges nothing.

## fn rebuild_if_entries (S2 graph-membership gate, #362)
- Portage `_rebuild_config.add` (`depgraph.py:424-442`) records a rebuild edge only for a parent already in the graph (an installed node with a buildtime edge to the dep); `trigger_rebuilds` (`:531-573`) walks that graph alone, bottom-up, consulting `_needs_rebuild` per child. A package nothing in the run reaches is therefore never rebuilt, even when its vdb build-dep names a merged package. Oracle: S0 `s0-b-rebuild-*` (`U rebuildtrigger-2.0` alone) and the fresh host capture `s2-fresh-ub.txt` (`R rebuildnochange-1.0` alone), both in `LLM/evidence/2026-10-16-359-exec/` (S0 dir for the former).
- A reached installed parent keeps the outcome the walk gave it: flipping it post-walk would skip walking its own deps, while Portage restarts the whole walk (`_need_restart`). That re-walk is backlog #394, implemented as `rebuild_if_restart_parents` (above) plus the driver restart step (`resolve/feedback/rebuild_if_restart.rs`); either way this synthesis currently adds nothing.

## fn rebuild_if_restart_parents
- Backlog #394: Portage `_rebuild_config.add` (`depgraph.py:424-442`) records a dep→parent edge only for a built parent with buildtime priority; `trigger_rebuilds` (`:531-573`) walks that graph bottom-up and `_needs_rebuild` (`:444-471`) fires for an unbuilt (source-merged) dep, a merged cpv no installed instance matches (new-rev), or a merged norev no installed norev matches (new-ver). The scan reads the *walked* edges (`entry.deps` with `priority.buildtime`, i.e. `DEPEND`/`BDEPEND` -- `key_priority` in `merge_order/priority.rs`), not the vdb snapshot, so it agrees with the edges the restart will re-walk. `RDEPEND`/`PDEPEND` never qualify.
- Only kept-installed (`AlreadyInstalled`) parents qualify: Portage records no edge for a merging parent (not built), and a binary-source merge is `built` (`built=(type_name != "ebuild")`, `:8868`) so it never triggers the plain path (the `--usepkg` reinstall-list arm is unported -- no pin).
- `already` is Portage's `rebuild_list` membership check in `_trigger_rebuild`: a seeded parent never re-fires, so the feedback loop terminates. `--rebuild-exclude` matches the parent cpv, `--rebuild-ignore` the merged dep cpv (same matcher as `rebuild_if_entries`).
