# crates/portage-repo/src/slot_operator/force_scan.rs
Slot-operator update-force and slot-change probes.

## fn slot_operator_update_force_scan
- #236 A: the forcing half of Portage's slot-operator update probe (`_slot_operator_trigger_reinstalls` -> `_slot_operator_update_probe` -> `_slot_operator_update_backtrack`, `_emerge/depgraph.py:3089-3132`, `:2576-2800`, `:2400-2452`) for the case `slot_operator_rebuild_scan` cannot see: the walk bound a built consumer's `:S/SS=` dep to the *installed* child and put no update of that child in the graph at all (the `_minimize_children` collapse makes this the normal shape -- the live `cat/pkg:=` and the appended built atom both bind the installed instance).
- Portage's probe then looks for a visible candidate of the child in the same slot with a different sub-slot and a higher version (downgrades need `_downgrade_probe`, not modelled), which the consumer's replacement ebuild's own atoms on that cp accept (`_iter_similar_available(dep.child, atom)` intersected over the atoms, highest wins), and which every other parent of the child accepts (`_slot_operator_check_reverse_dependencies`, the #211 R2 `probe_refused` helper). A hit writes both halves of Portage's backtrack: the consumer into the replace set, the child's candidate into `slot_operator_forced_upgrade`, and the restart selects them.
- Gates, as the scan's #211 arms: the consumer is a walked installed node (Portage registers `_slot_operator_deps` for walked parents only) that is not merge-bound, neither end is `--exclude`d (`:2589-2603`), `want_update` is stood in for by `--update` or the child being directly requested, the child's graph node is the installed instance the atom is bound to, and a visible replacement ebuild exists. The `_select_atoms_probe` check (`||` choices) and `_too_deep` are not modelled; the consumer's atoms are flattened like the scan's.

## fn slot_operator_slot_change_probe
- Backlog #24 S5: Portage `_slot_change_probe` (`depgraph.py:2317-2359`), the first arm of `_slot_operator_trigger_reinstalls` (`3103-3107`). Covers an *unbuilt* slot-operator dep -- `:=` or `:S=`, Portage's `not (atom.soname or atom.slot_operator_built)`, i.e. anything but the built `:S/SS=` form. A slot move without a revbump (bug 456208; `test_slot_change_without_revbump.py`, `test_regular_slot_change_without_revbump.py`).
- Portage finds the dep through `_slot_operator_deps` (registered when the parent's dep was walked); portuale re-reads the parent entry's own tree metadata and use-reduces it against the node's enabled USE (`flat_dep_atoms`) so only deps this run would walk are seen -- `||` arms are flattened (the same over-approximation the vdb side of the scan makes; the S4 undo and the probe's own rule-6 keep are the correction for a false hit). `slot_changed` is the probe's tree-ebuild-at-cpv lookup. A hit joins `scheduled`, exactly Portage's `_slot_change_backtrack` (`2361-2399`) writing `slot_operator_replace_installed` + `_need_restart`.
- Portage's `runtime_pkg_mask` / excluded-package checks on the tree ebuild (2341/2343) have no portuale counterpart on the installed arm: `slot_changed` is the same tolerant metadata re-lookup the standalone `--changed-slot` trigger uses. The binary arm below carries Portage's visibility gate (`_pkg_visibility_check` 2347, #243).
- The binary arm (`dep.child` a binary package scheduled for merge) is v2 `#24c`.
- Portage's `not dep.parent.built`: only an ebuild scheduled for merge is a probing parent.
- Portage's `dep.child.built`: the graph must have resolved this dep to that installed instance. A merge-bound entry means the walk chose a different candidate (typically a Portage upgrade) -- the probe does not fire. A merge-bound *binary* is the #212 arm, which runs independently -- Portage files the two backtracks from independent deps.
- #212 binary arm (Portage `_slot_change_backtrack`, `depgraph.py:2381-2398`, v2 `#24c`): the graph resolved this dep to a merge-bound *binary* (`dep.child.built` and not installed), and the tree ebuild at the binary's own cpv (`=cpv`, Portage `_slot_change_probe`'s `self._pkg(dep.child.cpv, "ebuild", ...)` then `_iter_match_pkgs(..., "ebuild", ...)` fallback) carries a different `(slot, sub_slot)` -- the same slot move without a revbump, but the stale side is a binary, not the vdb. Portage masks it (`slot_operator_mask_built`) so the backtrack-config restart resolves the dep to the tree ebuild instead.
- Portuale's one-instance-per-cp model makes entry existence equivalent to dep resolution: whatever atom pulled this cp sees the binary entry's version.
- Gates, mirroring Portage (`_slot_change_probe` `2317-2359`): the tree ebuild at the binary's cpv must exist (a `replacement_parent` -- else masking dead-ends the re-pass, the same gate the #211 arms carry), must not be `--exclude`d (Portage `:2343`, the same `matches_config_entry` idiom as the C4 grouping and `collect_probe_parents`), and must be visible (`_pkg_visibility_check`, `:2347`, #243). A binary entry does not imply a visible same-version ebuild, and masking a binary whose ebuild is hidden dead-ends the re-pass.
- Portage's `runtime_pkg_mask` check on the tree ebuild (`:2341`) has no counterpart (standing cut, same as the installed arm above).
- Portage compares package objects that always have a slot; without a resolved slot there is nothing to compare against the tree.
- The replacement gate and the slot compare read one tree lookup: the highest-priority repo's candidate at the binary's own version (the same tolerant metadata `slot_changed` trusts).
- Backlog #243: Portage masks the binary only when the same-version ebuild passes `_pkg_visibility_check` (`depgraph.py:2347`); an ebuild a keyword or package mask hides leaves the binary alone (the live bed run keeps `[binary]` on `--usepkg` there).
