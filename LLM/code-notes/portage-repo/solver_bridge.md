# crates/portage-repo/src/solver_bridge.rs
Alternate `--solver=` backends: PubGrub and resolvo over the same repo facts.

## module
- Portuale-only (Portage's `emerge` has no `--solver`). Both backends drive lu-zero's `portage-atom-pubgrub` / `portage-atom-resolvo` bridges; see `docs/history/solver-backends-analysis.md` and the `3rdparty/portage-cli` checkout.
- The feeding direction is the bridges' documented boundary ("a solver over facts"): portuale computes all policy (per-version resolved USE via [`super::effective_use_flags`], target atoms, installed set) and hands it in, target atoms, installed set in; the engines only pick versions.
- Performance shape (measured: the engines take ~20ms; the adapter must not dominate): md5 reads, dep-string parses and (dominant, ~1ms each) `effective_use_flags` runs scale with the request's closure, not the tree, the same complexity shape as the backtracking walk's own BFS. The closure over-approximates (both sides of every `flag?()` conditional followed, USE unevaluated), so reachability never drops a selectable package; `all_packages` exposes exactly the closure, keeping dropped-dependency filtering sound. The PubGrub provider uses `new_for_targets` (reachable conversion, not whole-tree); the resolvo pool is populated from closure records only (its construction is inherently whole-input).
- Deliberate v1 cuts (each its own slice): no autounmask relaxation levels (the pool is visibility-filtered with the walk's own `is_visible`, so an invisible version is never offered -- but unlike the walk, a candidate that would need a `--autounmask*` flip (a `~arch` keyword, a license, a `package.mask`) simply fails to resolve rather than producing the flip suggestion); notices wired where the bridge result admits them (blockers via the walk's `resolve_blockers` (H.15c), ABI rebuilds via `slot_operator_rebuild_entries` (H.15), circular deps via `find_hard_cycles` (J), USE display with Portage's forced/masked `( )` markers (J)); merge order is the walk's `topological_merge_order` over Portage's `deps` edges rebuilt from raw dep strings plus resolved USE (H.15b).
- USE-dep / `::repo` / slot-operator target forms resolve the way the bridges resolve them, which may differ from the walk.
- `oldbest` carries the resolved candidate's own sub-slot/repo (an approximation of the installed one's); new-slot `New` entries list installed versions with empty sub-slot/repo.

## struct LazyRepo
- `Clone` shares nothing but copies the memoized maps (cheap: the closure is fully loaded at `build` time): the provider takes one copy while the `Plan -> GraphResult` mapping keeps the other, so USE computed during the solve stays cached provider-side and only the selected versions re-resolve mapping-side.

## impl LazyRepo::build
- Installed CPNs load for favored-version registration and upgrade comparison, but their dep cones are not expanded; nothing explores them unless the target cone reaches them, in which case the target expansion loads them anyway. Loads are md5 read + parse, no USE, per visited `cat/pkg`.
- #34 S2: new `seeds_first` parameter. Queued last, the expanding seeds (and their transitively pushed refs) all pop before any shallow installed entry (LIFO), so a CPN that is both a seed and installed expands instead of loading shallow. Before, an installed target never expanded and its deps stayed outside `closure` (D-closure: `pg-closure dev-libs/pg34-arg shallow` with no `expanded` line, so `pg34-new` never entered the slot map). Pubgrub passes true; resolvo passes false so its pool — and its output — does not move (measured identical on pg34-arg/pg34-app before/after). Expanding installed cones under deep stays S3's (S2's only deep mode is `-e`, whose rebuild set already covers every installed cpv).
- #34 S3: `vdb_expand` (`seeds_first && deep`, so resolvo and non-deep pubgrub keep the old order): shallow installed CPNs additionally expand from their vdb deps (`installed_dep_strings`, both conditional branches), and referenced repo-backed CPNs queue expanding. Without it an installed-only dep's own dep (pg34-gone → pg34-gextra) never enters `closure`, so the unslotted dep misses the slot map and the crate's stub stays a leaf. Portage: the `_too_deep`-gated walk reaches the same cone (`depgraph.py:7359-7375`).

## fn graph_result_from_order
- Shared `Plan -> GraphResult` mapping: ordered `(cp, version)` selections plus `(to_cpv -> [(from_cat, from_pkg)])` parent edges become entries; each entry's `deps` come from its raw dep strings plus resolved USE (H.15b) and the whole list is re-sorted through the walk's own `topological_merge_order`. USE display resolves on demand through `repo` (memoized).
- USE display (`refresh_entry_use_display`): the bridge passed an empty set, so Portage `pkg_use_display`'s `( )` wraps never rendered. Same call, same `cat/pkg-ver:slot/sub::repo` candidate spelling.
- Blocker reporting (H.15c): every collected blocker atom is matched against the installed db plus this plan's own resolved entries via the shared walk-path `resolve_blockers` (same USE-aware `[use]` gating, same `match_from_list` semantics), and each conflict is filed on its owner entry, mirroring the walk, which resolves blockers after the graph settles and before the merge-order sort.
- ABI rebuilds: an installed consumer whose built `cat/pkg:S/SS=` dep no longer matches how this plan leaves that slot is scheduled for a reinstall, via the walk's own `slot_operator_rebuild_entries` fixpoint; entries are extended before the merge-order sort so rebuilds land dependency-first like every other entry.
- `outcome` is always `Complete`: a solved engine plan admits no same-slot divergence and no relaxation loop ran, so it cannot abort either (no `_create_graph` 0-return, no `_serialize_tasks` give-up, no backtrack loop to exhaust). See `ResolveOutcome`'s doc comment.
- #34 S2: new `kept: Option<&KeptInstalled>` parameter. A same-slot same-version pick in `kept.rebuild` is a bare, reasonless `Reinstall` (all six empty/false, precedent `resolve/pretend.rs:170-179`); anything else keeps `AlreadyInstalled`. Resolvo passes `None` and its output does not move. Portage: the walk's `is_top_level && !selective` arm (`resolve/pretend.rs:1289-1298`; `selective` there is already `selective && !empty`, `:407-412`, so `-e` reinstalls).
- `autounmask_no_clean_tail` stays false: no relaxation loop ran whose flips a "terminated early" gate could hinge on (backlog #217: no changes, so `autounmask_backtrack_disabled()` is False regardless).
- The empty virtual-cycle field (backlog #193): the engine backends have no `_virt_deps_visible` probe walk, and the bridge outcome is always `Complete` by design -- a virtual cycle is one more abort shape the bridges do not do, like slot conflicts.
- Merge-order fidelity (H.15b): the walk path builds every entry's `deps` (Portage `_add_pkg_dep_string` order/priorities) and sorts the whole list through `topological_merge_order` (Portage `_serialize_tasks`); bridge entries used to carry no edges at all, so engine install order leaked straight into the display. Same helper over the raw dep strings (`raw_deps`: DEPEND, RDEPEND, BDEPEND, PDEPEND, IDEPEND) plus this version's resolved USE.
- Blocker atoms met in plan entries' dep strings are resolved after the loop by the shared walk-path helper.
- #34 S5 G7: the pubgrub path passes the walk-identical required-set closure (`blocker_retry_seed_atoms` + request atoms + `system_packages` over installed deps, `required_set_reachable_cps`) instead of an empty set — same formula as `ResolveCtx` (`resolve/ctx.rs:161-167`); resolvo keeps the empty set so its output does not move. Plus `unsolvable_with_installed_parent`: a satisfied-by-uninstall conflict whose removal target is installed, unmerged, and still depended on by an installed package the request expansion reached flips to unresolved (`satisfied_by = None`). Portage's `_validate_blockers` never unmerges a blocked package pulled into the digraph with parents (`depgraph.py`, the digraph-contains-and-parents veto on uninstall scheduling); the bridge entries only hold solution members, so an installed parent past the kept leaves (installed systemd behind leaf-kept util-linux, installed pg34-smid behind leaf-kept pg34-shold) is invisible to the shared `graph_has_parent`. The parent edge is read from the vdb (`RDEPEND`/`PDEPEND`/`DEPEND`/`BDEPEND`, USE-evaluated with the built flags, blockers excluded, version/slot-matched against the blocked instance via `match_from_list` like `graph_has_parent`) and the parent must sit in `LazyRepo`'s `expanded` cone (seeds plus expansion-reached cps — shallow installed loads excluded, so an uninstall Portage schedules for a truly parentless package like `dev-libs/samepkg` under `dev-libs/blockerpkg` still stands). On the fixture the system/world closure is `{systempkg}` (misses the chain), so the installed-parent arm carries it; on the real tree the system set reaches systemd, so both arms agree with Portage. Approximation note: expansion is USE-unevaluated, so a parent behind an untaken conditional would keep a block Portage satisfies — no corpus row hits that. The walk has the same latent gap on the fixture (its closure misses the chain too, hence the default `-pv` satisfied rendering); fixing the walk is out of scope.
- Tests: `pg34_snew_pubgrub_pv_keeps_soft_block_unresolved` (`N snew`, no `Uninstall`, one unsatisfied conflict; fails pre-fix on the uninstall) and the `-pvuD` non-regression pin (deep already parents via the solution).
- Missing records cannot happen (the order came from the plan over these same facts) — except #34 S3's installed-only picks, which have no repo record and map from the vdb (`installed_record`, gated on a deep bridge so the old skip stands without deep and on the resolvo path). Their entries render `AlreadyInstalled`, hidden like any other kept package.
- Bridge plans are ebuild (source) candidates, hence the ebuild key list and `built = false`, exactly the walk's own call.
- #143 S1: `raw_deps` is key-ordered (DEPEND/RDEPEND/BDEPEND/PDEPEND/IDEPEND), recovering Portage's `blocker.priority.buildtime` provenance.
- The bridge path never runs under `--buildpkgonly` (`ResolveRequest` carries no such flag; the parked engines are not the `--buildpkgonly` CLI path). No scan-collected owners of its own; orphans still arise from walk-pending owners without entries.
- ABI rebuilds (H.15, last slice): the walk's own gate (`rebuild_if_new_slot`, not `ignore_built_slot_operator_deps`) and complete-mode reachability (empty outside complete mode suppresses the scan, like a plain non-complete walk). The `(provider, consumer)` pairs feed `_show_abi_rebuild_info`.

- Same merge-order sort the walk path applies (Portage's `mylist` is dependency-first): `serialize_merge_order` re-sorts over the `deps` edges plus the `required_by` fallback, with the same top-level atoms, profile config, root, and `--implicit-system-deps` bias.
- The bridge engines pick `||` branches natively (PubGrub/resolvo unit propagation, not `dep_zapdeps` bins); an empty map keeps the suppression's re-derivation exactly as before (backlog #221).
- Circular-dep notice (J): a build-time edge no installed package satisfies is hard (`best_installed_for_atom`, the walk's own gate), anything else soft; blockers never reach the map on either side. `find_hard_cycles` also reads the entries' own `deps` for the #228 slot-operator arm, so the bridge inherits it with no extra map state.
- `slot_conflicts` and the `autounmask_*` lists stay empty on purpose (a candidate needing a flip fails instead; the remaining cut). A bridge failure is one `Error::Detail` line (engine-native text), not a Portage `depgraph.py` notice.
- The abort path is a property of the BFS walk + backtrack loop in `lib.rs`, not the bridge; see `ResolveOutcome`'s doc comment.
- Backlog #221 is a walk-path rule (cycle map). Backlog #217: no changes, so `autounmask_backtrack_disabled()` is False regardless. Backlog #193: a virtual cycle is one more abort shape the bridges do not do, like slot conflicts.

## struct OrChoiceOverrides
- #34 S5 G5/G6: per-solve `||` facts for the pubgrub bridge. `OrGroupKey` = member cpv + dep class index (DEPEND..IDEPEND = 0-4, the `version_row` order) + the group's pre-order index among the class's `||` nodes (structural: branch reorder/drops inside the node never move it; counter restarts per class in the traversal `apply_or_overrides_to_classes`, shared by facts and analysis so indices line up). `OrGroupOrder` = full desired branch-key sequence (a live branch missing from it is dropped) plus the sorted branch keys it was computed from (the fingerprint: a group whose content does not contain it is a different node — a nested `||` inside a dropped branch moved the index — and is skipped). `signature()` (fingerprint and order) drives the fixpoint's oscillation history. `or_branch_key`: atom identity (cp, slot pin, version floor + glob, sorted USE deps) for `Atom` branches (same-cp different-slot branches key differently), nested content otherwise. `or_subtree_has_blocker`: groups carrying blockers anywhere in the subtree are never touched. Apply rebuilds `AnyOf` children in stored order (unknown stored keys ignored, live extras dropped); `^^`/`??` nodes are traversed but never reordered. No ported code (rule restated bridge-side), no comment.
- Tests: the `pg34_svt_*`/`pg34_stt_*` integration pins (fail pre-fix, pass post-fix); the `pg34-xapp`/`pg34-ztop` pins guard the no-desired case (no reorder, no drop: the engine and Portage already agree on the installed branch there).

## fn or_member_view
- #34 S5 G5/G6: the engine's view of one solution member's dep classes for the post-solve analysis — same class source as `versions_for` (repo md5-cache, or the vdb reader for a deep installed member including versions gone from the repo), same G3 strip (same slot source), then the current overrides via the shared traversal, plus the member's effective USE from the same source `desired_use` answers (vdb flags for a deep kept member, config USE of the repo record otherwise, empty for an installed-only version). `None` for a kept leaf (engine sees empty deps) or a member with no record.

## fn or_branch_standing
- #34 S5 G5/G6: whether one `||` branch is the branch Portage would take. `qualifies` = every named package independently selected (in the plan *and* edged from another parent or a root target — a package merged only through this group, e.g. gnome-keyring via the virtual, is not), every atom matching the planned version (`matches_cpv` with the plan version's record slot: a pin naming another slot is a different choice), and every USE dep holding under the member's effective USE (`use_deps_satisfied` with the plan version's record iuse/USE: a branch Portage would autounmask-gate is not the faithful pick). `installed_blocking` = a direct atom branch an installed instance satisfies (`installed_satisfies_self`, the G3 helper) while not the desired pick: the engine's installed-preference (`provider/solve.rs:140-258`) takes it regardless of branch order, so reordering alone cannot fix the group. Group (non-atom) branches reorder only, never drop. Portage: `depgraph.py:778-793` graph_db preference, `dep_check.py` `dep_zapdeps` bins (in-graph and installed share the first bin, with the in-graph promotion) and the USE/mask bins after it.

## fn visit_or_groups
- #34 S5 G5/G6: pre-order `||` visitation over one dep class for the analysis (same node order as the apply traversal): `AnyOf` nodes collected with `(index, children snapshot, active under the member USE)`; `AllOf`/conditionals transparent (activity conjoins the gate), `^^`/`??` traversed but never collected.

## fn compute_or_overrides
- #34 S5 G5/G6: the desired `||` facts for the next solve, from the solved plan. For every active, blocker-free `||` group in every selected member's engine-view deps: the first-listed independently-selected (`or_branch_standing`) branch moves first (the engine's final fallback is first-listed via n-i numbering, `convert.rs` `convert_choice_group`), and an installed-satisfying direct branch that is not that pick is dropped — but only when such a pick exists (without one the engine and Portage already agree on the installed branch; dropping it would force the untaken alternative, the `pg34-xapp` regression caught mid-slice). Groups with no qualifying branch keep their facts verbatim (emitted as-is, so the fixpoint comparison sees stability). Every active group emits its full order each pass (even unchanged), so map equality means convergence. Skipped wholesale under `--nodeps` (deps never expand). Trace: `pg-or-group <cpv> [class:index] -> keys` and `pg-or-drop ... <key>`.
- Sensitivity: the `pg34_svt` pin fails if the independence check is dropped (any in-plan branch, including the group's own pick, would count); the `pg34_stt -pve` pin fails if the drop arm is removed (reorder alone cannot move the engine's installed-preference); the `pg34-xapp`/`pg34-ztop` pins fail if drops fire without a desired pick (the mid-slice regression).

## fn resolve_pubgrub
- `new` converts every CPN; `new_for_targets` converts the seeds' closure with the same `with_bdeps = false` the default path uses, so behaviour is unchanged, only the converted set shrinks. The copy is O(closure), no recompute.
- Same expansion the bridge's own `Solver` impl uses (`to_portage_targets`): an unslotted target node carries no versions when every version is slotted.
- #34 S5 G2 round 2: solve runs inside a fixpoint loop (extracted `pubgrub_targets`, so the per-round target build is shared): each round solves, inverts the round's `parents` map into taken edges, runs `KeptInstalled::apply_parent_use_reinstalls`, and re-solves while `rebuild` grows.
- #34 S5 G5/G6: the `||` reorder/drop pass rides the same loop. Each round solves with the current overrides (root-target cps parsed once from the request atoms: an alternative naming the probe target is in-graph trivially), runs the G2 pass, then `compute_or_overrides`; the round ends when `rebuild` stops growing *and* the override map stops changing. Overrides are not monotonic, so a repeating override signature (`OR_FIXPOINT_MAX_PASSES = 8`) or the round cap (`PUBGRUB_FIXPOINT_MAX_ROUNDS = 32`, G2 growth stays unbounded as before) falls back to the previous plan (`pg-or-oscillate` / `pg-or-round-cap` trace); a solve broken by an override pass falls back the same way (first pass reports the engine error). `SolvedRound` names the round's `(order, parents)` pair. Pubgrub-only: `pubgrub_provider` takes the overrides (like `kept`); resolvo never sees them.
- #34 S2: `KeptInstalled::of` runs before `new_for_targets` (deps convert inside the constructor); installed cpvs in `kept.rebuild` register `InstalledPolicy::Rebuild` instead of `Favor` (extracted `pubgrub_provider`, so tests can assert `installed_policy`), and `set_rebuild_tree(req.empty)` is set (moved here from S4: without it `-pve` keeps old installed versions where Portage shows `U`). Portage-cli has no leaf rule and renders named-argument `R` as a post-solve display filter (`round.rs:578-620`) keeping `Favor`; S2 registers `Rebuild` instead, so the reinstalled target expands DEPEND/BDEPEND as Portage's ebuild node does. No ported code, no comment.
- #34 S4: `pubgrub_provider` sets the engine switches ported from portage-cli `portage-cli/src/query/depgraph/round.rs` at commit `41f4132a` (MIT, Luca Barbato), lines 254-264 verbatim:
  `provider.set_nodeps(nodeps);` (:254), `provider.set_rebuild_tree(emptytree_native);` (:255, already set since S2 as `set_rebuild_tree(req.empty)`),
  `provider.set_prefer_newest_slot(deep || emptytree_native);` (:257),
  `provider.set_prefer_update(update && deep && !emptytree_native);` (:261),
  `provider.set_selective_no_update(selective && !update);` (:264).
  The bridge spells the portage-cli locals in request terms: `deep = !matches!(req.deep, Deep::NotRequested)` (`--deep=N` counts as deep, the S0-recorded cut), `selective = req.selective && !req.empty` (the walk clears selective for `-e`, `resolve/pretend.rs:407-408`), `emptytree_native = req.empty`.
  What each setter gates in the crate (`portage-atom-pubgrub-0.8.0`): `prefer_update` disables the Favor early-return for non-root packages (`provider/solve.rs:89-110`: `-pvuD` in-slot upgrades, e.g. `U pg34-dlib-2` under `N pg34-dtop`; without deep it stays off so `-pvu` leaves the installed dep alone); `selective_no_update` keeps a satisfied root target at its installed version when `--update` is off (`solve.rs:89-110`: `-pvN` keeps `pg34-ulib-1`); `prefer_newest_slot` bumps `:*` any-slot deps to the newest slot (`solve.rs:131-135`, scoped to `SlotChoice`); `nodeps` reports no deps for real packages (`solve.rs:304-310`, `-pvO` target only).
  `set_with_bdeps` is deliberately NOT called: it only gates the cross-host branch (`solve.rs:378`); native build deps of kept packages are dropped by the installed-and-kept branch (`solve.rs:311-341`), which is why S3's planned BDEPEND fold stays cut. Crate-gap note (§0.4): no crate change needed for this corpus.
  Deltas from the model (bridge-side, not crate-side): portage-cli compares VDB USE/IUSE against the planned fold per iteration (`package_needs_use_reinstall`) and registers `Rebuild` per installed package; the bridge computes the same decision once, up front, in `KeptInstalled::of` (USE-drift arm, `--newuse`/`--changed-use` only) because deps convert inside `new_for_targets`. `--changed-deps`, `--changed-slot` and `--newrepo` reinstall triggers are out of scope (no corpus mode sets them).

## fn resolve_resolvo
- USE resolved per version (memoized, so each runs once). Per-version USE rides in each `PackageMetadata::use_flags`; the provider-level config stays default (no globally-forced flags).
- The explicit copy of the closure ids stands: `iter()` is `slice::Iter` (items are `&SolvableId`), so `to_vec` would collect references.
- Engine-native failure text (the H.15a half of the solver V1 depth cuts): resolvo's `Conflict::display_user_friendly` ("The following packages are incompatible" plus conflict chains, named through the portage provider's solvable display) instead of the raw `UnsolvableOrCancelled` debug dump (`Unsolvable(Conflict { clauses: ... })`), which names no package at all. Mirrors the pubgrub backend, whose `format_solve_error` renders its `NoSolution` derivation tree. A cancelled solve (not reachable through this synchronous call path) stays a plain message.

## fn pg_trace
- S0 Step 5 (#34): gated pubgrub-bridge trace for the §0.2 chain walk. Gate is `PORTUALE_PG_TRACE=1` (env, not the `resolver_debug` global, so unit tests can drive it without the CLI); `pg_trace(out, args)` writes one line, stderr in production, `Vec<u8>` in tests. Unset: every call site no-ops (the `versions_for` fan-out and `desired_use` flag sort sit behind an extra `pg_trace_enabled` check, so not even the formatting work runs).
- Lines: `pg-target <cp> slot=<s>` (`s` = named slot, `*` = whole slotted-node fan-out, `-` = unslotted fallback); `pg-use <cpv> source=config|vdb <flags>` (`vdb` = a kept installed cpv under deep, the USE it was built with; `config` otherwise — S3 fixed the installed case); `pg-edge <parent-cpv> -> <child-cp> (<CLASS>)` (per referenced CPN per dep class in `versions_for`, over the vdb classes for installed cpvs under deep); `pg-installed <cpv> slot=<s> policy=Favor|Rebuild` (S2's kept/rebuild set: `Rebuild` for every installed cpv under `-e`, and for the installed best accepted version of a non-selective root target); `pg-closure <cp> expanded|shallow` (`LazyRepo::build`, one line per first insert); `pg-plan <cpv>` (S1 prep: one line per package the solution installs, so `pg-edge` lines of candidate versions outside the plan can be dropped by `pg-buckets.py`).
- `LazyRepo::build` is shared with resolvo, so a resolvo run with the env var set also emits `pg-closure` lines; the resolvo resolve path itself (`resolve_resolvo`, `versions_for`-equivalent pool fill) is untouched, and with the var unset both paths behave exactly as before.

## fn target_slots
- #34 S1: a bare target atom used to become a root target in every slot (`packages_for_cpn`). Portage selects the slot of the best visible match (`depgraph.py` `_select_pkg_highest_available`) and, only under `--update`, adds the installed slots (`_greedy_slots`, `depgraph.py:5385-5427`, `:5896-5930`) whose best match is lower than the overall best; it never adds non-installed sibling slots. `target_slots` computes that set from `LazyRepo::load_versions` (already visibility-filtered) and the atom's version restriction; an empty result falls back to the old fan-out, so an all-masked target keeps its error path.
- Recorded cut: `_greedy_slots` also drops a slot when a blocker lookahead excludes it (`blocker_lookahead`); not ported. Tie on the best version between slots picks the lower slot string (Portage picks the first in its own order).
- Trace: `pg-target <cp> slot=<s1,s2>` now lists the chosen slots, not `*`.
