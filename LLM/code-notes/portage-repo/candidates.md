# crates/portage-repo/src/candidates.rs
Ebuild candidates for a package.

## enum CandidateSource
- Portage's own `pkg.type_name` (`lib/_emerge/RootConfig.py`'s `pkg_tree_map`, exactly the strings `"ebuild"`/`"binary"` used here): an ebuild candidate's own USE gets computed dynamically (see `effective_use_flags`), while a binary candidate's USE was already baked in at build time (`Candidate::binary_use`) -- Portage `--pretend` also prints a different bracket word for each (`"[ebuild"` vs `"[binary"`). See `GraphEntry::source` for the `--pretend` bracket words.

## struct Candidate
- `sub_slot`: the sub-slot half of this candidate's own `SLOT` metadata (Portage `SLOT="main/sub"`), read via `split_slot` alongside `slot` -- defaults to `slot` itself when the ebuild's own `SLOT` carries no `/` at all, matching Portage `_pkg_str`'s own slot-parsing fallback. Folded into every candidate string for `portage_dep::match_from_list` as a `slot/sub_slot` suffix (see `portage_dep::Candidate`'s regex, which already parses this shape). Closed a previously-silent gap: any dependency atom restricted on sub-slot (`dev-libs/foo:0/2`, PMS 8.3.3) could never match anything, since every candidate string omitted the sub-slot half no matter what the real `SLOT` metadata said.
- `repo_location`/`repo_priority`: which repo this candidate's ebuild/metadata actually lives in -- needed once there's more than one repo (see `list_candidates`), both to re-read this exact package's own DEPEND/RDEPEND later (`resolve_pretend_graph`) and to break a same-version tie between two repos toward the higher-priority one (`resolve_pretend`). `repos` iteration order comes from `find_repos`'s ascending `(priority, name)` sort.
- `repo_name`: the repo's own `repos.conf` section name (`RepoConfig::name`), e.g. "gentoo" -- appended as a `::name` suffix to every candidate string this crate builds for `portage_dep::match_from_list` (except the two paths noted in the module doc comment's `::reponame` bullet), so a `::repo`-constrained atom actually filters. Portage cross-checks this against each repo's own `profiles/repo_name` file too; portuale reuses the already-read `repos.conf` name as-is rather than reading a second file.
- `license`: empty matches Portage `use_reduce("")`'s empty result; see `is_visible`'s license-masking check.
- `iuse`: most packages' LICENSE has no conditional, so most candidates never need this field.
- `properties`/`restrict`: see `properties_accepted`'s doc comment.
- `source`: ebuild (a repo's own `metadata/md5-cache`) or binary (a `PKGDIR/Packages` index entry) -- see `CandidateSource`'s doc comment.
- `binary_use`: the USE flags this specific build was compiled with, already fully resolved (Portage `Packages` index's own `USE` field -- bare flag names, presence means enabled, no `+`/`-` markers needed since nothing is "still deciding" the way a fresh ebuild build's own IUSE defaults are) -- `None` for an ebuild candidate, whose USE gets computed dynamically instead (`effective_use_flags`). The only consumer of `list_binary_candidates`' output is `resolve_pretend`'s `--binpkg-respect-use` check, comparing this against what would currently be selected over the candidate's own `iuse` flags.
- `remote`: a `--getbinpkg` binary candidate from a *remote* binhost's own `Packages` index (`list_remote_binary_candidates`), not yet present in the local `$PKGDIR` -- Portage `bintree.isremote`. Flows to `GraphEntry::remote_binary` -> the `g` bracket column (`PkgAttrDisplay.remote_binary`, `output_helpers.py:627-633`). Always `false` for ebuilds and local `$PKGDIR` binaries.
- `build_id`: the `BUILD_ID` field from this binary's own `Packages` index entry (Portage binpkg-multi-instance / binhost `_pkg_str.build_id`) -- `Some("4")` for a binary, `None` for an ebuild or a `Packages` entry with no `BUILD_ID`. Portage `output.py::_append_build_id` appends `-{build_id}` to the displayed version of a `type_name == "binary"` package (before the `:slot` / `::repo` decoration).
- `binary_deps`: this binary instance's own recorded `*DEPEND` strings (its `Packages` entry's `DEPEND`/`RDEPEND`/`BDEPEND`/`PDEPEND`/`IDEPEND` -- absent keys omitted), kept so `--binpkg-changed-deps` compares the *exact* instance's deps rather than re-looking-up the cpv (a binpkg-multi-instance cpv has one dep set per build). Empty for an ebuild candidate.
- `build_time`: from Portage `_pkg_str.build_time`. Portage `dbapi._cmp_cpv` sorts same-version instances by `build_time`, and `_iter_match_pkgs` reverses that and `break`s on the first acceptable one -- so the highest `BUILD_TIME` passing the checks wins (`dedup_binary_instances`).

## fn strip_version_prefix
- Same disambiguation principle as the PMS package-name grammar ported in portage-dep's atom parser.

## fn split_pf
- Splits `package-version` (`PF` without category) into `(PN, PVR)` the way Portage `_pkgsplit` does: the version is the longest trailing `-`-separated suffix that `ververify` accepts, so a package name may itself contain digit-led words. Since #127 the single copy: the former `portuale::remote_bundle::split_pf` and this crate's private `split_installed_dir` were deleted for it. Needed by the md5-cache validator to find an entry's ebuild (`<repo>/<cat>/<pn>/<pf>.ebuild`); e.g. `foo-1bar-2.0` -> `foo-1bar`. Portage `lib/portage/versions.py`: a `-r<digits>` revision belongs to the version only when the rest still verifies (else `foo-r1-2.0` would mis-split).

## fn list_candidates
- Mirrors Portage `portdbapi.cp_list`, gathering from every configured repo, not just the first one with the package. V1 doesn't distinguish "stale cache" from "doesn't exist" -- both mean "not visible". The resolver calls this per cp per graph-walk visit (visibility, keyword, slot-operator, changed-deps and parent-scan checks all re-list the same cp); each build is a `read_dir` plus a dozen owned strings per version. Sound because nothing here ever writes an `.ebuild` (`--regen` only touches `metadata/md5-cache`, in a separate process) -- same reasoning as `read_md5_cache`. Keyed by a hash of the repo locations + `cp`.
