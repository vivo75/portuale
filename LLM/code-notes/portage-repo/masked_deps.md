# crates/portage-repo/src/masked_deps.rs
Masked-dependency reports.

## fn resolve_pretend (design notes; the doc block lived above `atom_currently_satisfiable`)
- The single-atom v1 `emerge --pretend` decision: find the best visible candidate matching `atom_str` across all of `repos` (the main repo and any overlays -- see `find_repos`), compare it against what's installed. `atom_str` may be a full atom (operator, slot -- anything portage-dep's v1 grammar supports), not just a bare category/package: this lets dependency atoms extracted from DEPEND/RDEPEND (see `resolve_pretend_graph`) reuse the exact same resolution logic as the top-level CLI atom. `newuse`/`changed_use` each enable their own reinstall check (see `reinstall_flags_for_use_change`) for an already-installed match, `newuse` winning if both are set; `false` for both reproduces the pre-`--newuse`/`--changed-use` behavior exactly.
- `update` (`--update`/`-u`) gates Portage's `_wrapped_select_pkg_highest_available_imp` `avoid_update`/`dont_miss_updates` behavior (`lib/_emerge/depgraph.py`, lines 7814 and 8448): `"--update" not in myopts` is Portage's *default*, and when it holds, an already-installed version that itself still satisfies the atom is returned immediately, without ever searching for a newer one -- Portage's `emerge` does NOT offer an upgrade just because `emerge cat/pkg` was run with no other flags; that's what `--update`/`-u` is for. Ported as an early return before the "always resolve to the single best visible candidate" logic: if `!update` and some installed version both matches `atom_str` and still has a visible candidate in `visible` (mask/keyword-filtered), the highest such version is used as-is, exactly like the pre-existing "installed version equals best" branch, `newuse`/`changed_use` included. Requiring a *visible* candidate (not just checking the vdb directly) is deliberate: it lets an installed version that's since become masked fall through to the ordinary best-visible-candidate path unchanged, matching Portage's own "enable upgrade or downgrade to a version with visible KEYWORDS when the installed version is masked" comment right above its own `avoid_update` check. When `update` is true, or no installed version qualifies, behavior is exactly as before the parameter existed.
- `selective`/`is_top_level`: a previously-undiscovered gap the `update` handling didn't capture, found by comparing portuale's output against the installed system `emerge` on a package (`sys-apps/portage`) and tracing Portage's decision live. Portage's `avoid_update` shortcut (`!update`) is NOT sufficient on its own for a **directly-requested (top-level) atom**: Portage's `_wrapped_select_pkg_highest_available_imp` per-candidate loop (`lib/_emerge/depgraph.py`) computes `want_reinstall = reinstall or empty or (found_available_arg and not selective)`, and `if want_reinstall and matched_packages: continue` -- for a "found via an atom on the command line" (`found_available_arg`, `_iter_atoms_for_pkg`) candidate, this SKIPS ever re-adding the already-installed `Package` object as a further candidate whenever `selective` is absent, so the later `if avoid_update: ... return pkg` shortcut (`lib/_emerge/depgraph.py` line ~8447) finds nothing installed to return and falls through to picking the best *available* (ebuild) candidate instead -- even when its version is identical to what's installed. Net effect: a bare `emerge <atom>` with no other flags, on an atom named directly (not via a dependency string), always resolves against the best *available* version (searching for a newer one exactly as `--update` would), and even when nothing newer exists, still reports a bare reinstall (`[ebuild R] cat/pkg-ver`, no parenthetical reason) rather than treating the identical installed version as satisfying -- confirmed live: `--noreplace`/`--selective` (both setting Portage's `myparams["selective"]`) restore the "nothing to do" result. `selective` mirrors Portage's `create_depgraph_params.py` `myparams["selective"] = True` condition, computed from whichever of its trigger flags portuale implements: `update`, `newuse`, `changed_use` (Portage's `--changed-use`/`-U` rewrites to `--reinstall=changed-use` before `create_depgraph_params` runs, `lib/_emerge/main.py`, and `--reinstall` is constrained to that one literal choice in Portage -- so `changed_use` alone covers portuale's whole share, no separate `--reinstall` flag needed), `changed_deps` (any non-`"n"` value), `changed_slot`, plus the two flags whose *entire* effect is exactly this (see `pretend.rs`'s CLI parsing): `--noreplace`/`-n` and `--selective[=y|n]` (`n` explicitly cancels `selective` even if another condition set it, matching `create_depgraph_params.py`'s `if myopts.get("--selective") == "n"`: pop unconditionally). Portage's `--newrepo` (forces reinstall on an installed-vs-current repo mismatch, and separately contributes to `selective`) is a documented, narrower scope cut, deliberately not modeled: portuale has no vdb `REPOSITORY` reader (confirmed absent during the investigation -- the vdb file is even lowercase `repository`, unlike every other metadata key), the same "no vdb-metadata reader" simplification documented elsewhere (e.g. `enqueue_dependencies`'s doc).
- `is_top_level` is portuale's "argument" equivalent -- `resolve_pretend_graph`'s `depth == 0`, the same equivalence established for `--with-test-deps`'s `pkg.depth == 0 and self._is_argument(pkg)` gating -- since every depth-0 atom already came from `atoms` itself or a `@world`/`@system` expansion of it, both of which Portage's `_iter_atoms_for_pkg` also counts as an "argument" for this purpose. A dependency atom (`is_top_level = false`) is NEVER affected by `selective`: Portage's `found_available_arg` is only ever set for an argument-derived candidate, so a dependency atom's already-installed, still-satisfying version keeps its pre-existing `AlreadyInstalled` treatment, unconditionally, matching Portage's `_want_installed_pkg` `return not arg` fallback (empty `arg` for a non-argument package).
- Applied at both places an installed version can otherwise satisfy the atom "as is": the `!update` shortcut (skipped entirely -- not just its outcome adjusted -- whenever `is_top_level && !selective`, so version selection falls through to the ordinary "best across everything visible" comparison, reproducing Portage's "searches for a newer version even without `--update`" effect) and the final "best visible candidate happens to already be installed" comparison (where instead the outcome is forced to `Reinstall` -- with whatever `changed_flags`/`deps_changed`/`slot_changed` were independently computed, all three possibly still empty/false, exactly matching Portage's bare, reasonless `[ebuild R]`).
- `excluded` (`--exclude`/`-X`) is a list of raw atom/wildcard-atom strings (Portage's `WildcardPackageSet`, ported as the same "try `match_from_list`, fall back to `parse_wildcard_atom`" two-tier matcher `matches_config_entry` uses for `package.mask`/`.unmask` -- both are Portage atom-set matchers with the identical "plain atom or `*`-wildcard" grammar). Checked in two places, mirroring depgraph.py's scattered `excluded_pkgs.findAtomForPackage` call sites: (1) if an installed version matches both `atom_str` and an exclude atom, it's returned as `AlreadyInstalled` immediately, before `update`/`newuse`/`changed_use` get a say -- ported from `_want_update_pkg`'s and `_replace_installed_atom`'s excluded-check-first pattern (Portage: "the user has not explicitly requested for this package to be replaced", so excluding it means never touching it, full stop); (2) an excluded candidate is never eligible as the New/Upgrade "best visible candidate" either, mirroring the `excluded_pkgs`-gated candidate-selection loops elsewhere in depgraph.py (e.g. around lines 2331 and 5544) -- if every remaining candidate is excluded and none is installed, this resolves to `NoVisibleCandidate`, the same outcome as no eligible candidate for any other reason. Deliberately NOT replicated: depgraph.py's ~18 `excluded_pkgs` call sites cover many more interaction points (autounmask, binpkg selection, `--complete-graph`, ...) portuale doesn't implement -- the two checks cover the dominant use ("pin an installed package so `--update`/`--deep` never touch it") and the New/Upgrade selection case, not every edge case.

## fn atom_currently_satisfiable
- Whether every atom in `atoms` currently has a satisfying candidate -- one input to the `AltPreference` rank `use_reduce_flat_disjunctive` uses to pick a `"||"` group's alternative (the `Available` half; `atom_cp_installed` is the installed-vs-not half). A blocker atom (`!foo/bar`/`!!foo/bar`) is always satisfiable here, vacuously -- it isn't a dependency to *resolve* at all, just a conflict to report (`enqueue_flat_deps` handles that separately, unaffected by which `"||"` alternative was chosen), so it never disqualifies an otherwise-fine alternative.
- Deliberately the *early* half of `resolve_pretend`'s logic only (`list_candidates` -> filter `is_visible` -> `match_from_list` -> USE-dep post-filter) -- not a call to `resolve_pretend` itself, which also applies `--update`/`--newuse`/`--exclude`/reinstall refinements that only matter once an alternative has been chosen and is actually being resolved, not for this "is it even possible" probe. A minor, deliberate duplication rather than a shared refactor -- the same "duplicate a small, stable chunk rather than force two different call sites through one function" precedent `keyword_masked_only` set against `is_visible` itself.
- `extra_constraints` is the `'backtrack` loop's accumulated per-`cat/pkg` constraints for this atom's package -- Portage backtracking's `runtime_pkg_mask` seen by `dep_zapdeps` (`dep_check.py:449` `all_available`). A `!`-prefixed entry is a negative (candidate must NOT match it); a bare entry is positive. Empty `&[]` at every non-disjunctive call site -- a strict no-op, exactly the pre-`||`-backtrack behaviour.
- Applies the accumulated `runtime_pkg_mask` negatives/positives the same way `resolve_pretend` filters its own `matched` list (lib.rs ~7437) -- an alternative whose every satisfying candidate is masked out counts as unsatisfiable, so the next `||` alternative wins on the retry.
- #212/#276: a per-instance negative (`[binary]` `slot_operator_mask_built`, `[installed]` missing-dependency) hides no tree candidate (see `is_instance_only_mask`).

## fn atom_all_use_unmasked
- Portage's `atom.violated_conditionals(pkg_use_enabled(avail_pkg), avail_pkg.iuse.is_valid_flag)` -- the `all_use_unmasked` boolean of `dep_zapdeps`'s choice classification (`dep_check.py` soft 406-414, 497-523). For an atom whose `[use]` deps NO candidate satisfies (`avail_pkg_use` empty, the `if not avail_pkg_use:` branch at soft 494), Portage computes which flags would have to change, then checks those violated flags against the best candidate's (`avail_pkg = mydbapi_match_pkgs(atom.without_use)[-1]`, see `atom_all_use_unmasked`) own `use.mask` / `use.force`: an enabled-required flag that isn't enabled needs unmasking if in `use.mask` (global or package, `resolved_use_mask_or_force`); a disabled-required flag that is enabled needs unforcing if in `use.force` and NOT also in `use.mask` (one masked/forced violation makes the whole choice fall to `other`, never selectable). Evaluated per single use-dep via `portage_dep::use_deps_satisfied` so default-marker/missing-IUSE semantics match exactly (`(+)`-defaulted missing flags are "as if enabled", `(-)`-defaulted missing flags "as if disabled", no-default missing flags fail outright -- the same classification Portage's `violated_conditionals` derives from `is_valid_flag` + `missing_enabled`/`missing_disabled`).
- No visible candidate at all: `all_available` already sent the whole choice to `Unsatisfiable`; returns `true` (nothing to evaluate).
- Single-dep evaluation = "would *this* flag have to change", per Portage's `violated_conditionals` per-token classification. The four conditional forms impose no candidate constraint in portuale's matching (see the `use_deps_satisfied` doc), so they can never be "violated" here either.

## type CandidateUseProbe
- Portage's `avail_pkg = mydbapi_match_pkgs(atom.without_use)[-1]` (`dep_check.py` soft 469-474): the single highest-sorted visible candidate matching an atom's `[...]`-stripped form, plus candidate string, IUSE, effective enabled-use set and slot -- the seeds of the `use.mask`/`use.force` probe, the `violated_conditionals` argument of `atom_all_use_unmasked`, and the slot `atom_installed_in_slot_of` checks against the vdb.

## fn highest_available_candidate_ignoring_use
- `extra_constraints` is the same `'backtrack`-loop `runtime_pkg_mask` filter `atom_currently_satisfiable` applies -- Portage's `mydbapi` in `dep_zapdeps` is `_dep_check_composite_db`, which honours it too, so once backtracking masks the highest version this probes the highest *unmasked* one instead. Empty `&[]` at every non-disjunctive call site, a strict no-op.
- Portage's `match_pkgs` returns matches ascending by version and takes `[-1]`; `candidate_strs` is in repo/readdir order, so the highest-VERSIONED match is picked explicitly. Same `runtime_pkg_mask` filter as `atom_currently_satisfiable`.
- #212/#276 per-instance negatives hide no tree candidate (see `is_instance_only_mask`).

## fn candidate_masking_reasons
- Reason order mirrors Portage: `package.mask`, `LICENSE`, `PROPERTIES`, `RESTRICT`, `KEYWORDS`, then `invalid` (Portage appends the invalid reasons after `_getmaskingstatus` in `_get_masking_status`). `package.mask` and the `KEYWORDS` string (`"~<arch> keyword"` / `"-<arch> keyword"` / `"missing keyword"`) and the `LICENSE` string (`"<names> license(s)"`) match Portage verbatim; `PROPERTIES`/`RESTRICT` are the bare key name (Portage names the specific tokens -- portuale has no missing-token list for those two, and neither the L0 comparator nor the contract suite checks this line against Portage anyway; the two `!!!` header lines are what matter).
- Backlog #153: Portage appends the `invalid` reasons after `_getmaskingstatus` in `_get_masking_status` -- same position here.
- S9 (#341): the `package.mask`/`unmask` check passes the candidate's binary build-id, so an `=`+build-id line reasons `package.mask` only for the equal instance.

## struct MaskedDepReport
- Portage's `_show_unsatisfied_dep` "All ebuilds that could satisfy … have been masked" block for a *dependency* (the Tier 2.20 half of finding S's top-level report). The resolver attaches these to the pass result; the caller (`pretend.rs`) renders each in place of the bare `!!! no visible ebuild for dependency` line, followed by the `(dependency required by …)` chain, then the docs footer -- Portage's `depgraph.py:6992-7030` shape for a non-`AtomArg` parent.
- `(cpv::repo, reasons)` descending version, cpv-deduped -- exactly the `- <cpv> (masked by: …)` lines the renderer prints.
- `chain` is Portage's `_get_dep_chain` for this disclosure: `(node, type)` pairs, innermost parent first, up to the top-level argument(s) -- e.g. `("dev-libs/n1-1.0::probe", "ebuild")` then `("dev-libs/n1", "argument")`. An installed intermediate renders its vdb repo (`__unknown__` fallback, like Portage) with type `"installed"`; a binary parent renders `"binary"`. Computed post-loop out of the final entries (see `masked_dep_chain`); one chain per direct parent (Portage shows only its DFS-first abandon -- portuale never abandons, so all failing branches disclose, convergence with #19 parked).

## struct UseUnsatDepReport
- Portage's `_show_unsatisfied_dep` separate "no ebuilds built with USE flags to satisfy" disclosure (backlog #20) for a *dependency*'s `[use]`-unsatisfied atom: among the ebuilds an atom names by version (USE ignored), the visible ones whose own IUSE is missing a required flag (`Missing IUSE: …`) or whose effective USE cannot satisfy the atom's unconditional use-deps (`Change USE: +… -…`). Rendered instead of the bare `!!! no visible ebuild for dependency` line.
- `atom` is the requesting atom as queued, unevaluated (Portage's `atom.unevaluated_atom`), so a `[flag]` dep shows as written.
- `rows`: the `- <cpv>::<repo> (<reason>)` rows in Portage's display order: the latest `Change USE:`-adjustable candidate only (Portage's `unmasked_use_reasons`'s "Only show the latest version"), else every `Missing IUSE:` candidate in descending-version order. Never empty (the report exists only when a row does). `chain` is Portage's `_get_dep_chain`, walked post-pass exactly like `MaskedDepReport::chain`.

## struct PlainMissDepReport
- Portage's `_show_unsatisfied_dep` plain-miss disclosure — the `emerge: there are no ebuilds to satisfy "<unevaluated atom>"` block plus the `(dependency required by …)` chain — for a dependency `NoVisibleCandidate` that is neither masked-only nor `[use]`-unsatisfied (nothing matches the atom by version at all, or every version-matching candidate is unusable for a reason no `Change USE:`/`Missing IUSE:` row can name, e.g. a profile-forced flag). Rendered instead of the bare `!!! no visible ebuild for dependency "<cp>"` line (#135 (d); oracle bed `l0-fx-20260922T192350Z` arm D / `libcnoisepkg`). The staging `for <root>.` suffix Portage appends when the target root is not `/` stays absent, matching the top-level miss and the two sibling arms (the `fixture-miss-message-unsuffixed` class).
- `atom`/`chain`: same unevaluated-atom and `_get_dep_chain` conventions as the sibling reports.

## fn masked_candidates_for_atom
- Portage's `_show_unsatisfied_dep` version match: the candidates an atom names by version, visibility and USE ignored (Portage's `db.match(atom.without_use)`). `None` when the atom matches no ebuild at all by version (Portage's plain "there are no ebuilds to satisfy" case) or when some matching ebuild is actually `is_visible` (e.g. only a `[use]`-dep mismatch -- Portage's separate "no ebuilds built with USE flags" path, left to the autounmask-use machinery here).
- Portage's `cpv_list.reverse()` -> descending version.

## fn all_binary_masked_report
- S4 (#341): binary-only twin of `all_masked_report` for `--usepkgonly`, where ebuilds are ineligible rather than masked. When every version-matching binary is masked the block lists the binary rows (Portage's `_show_unsatisfied_dep` over the binary pool; S0 cell `F-binary-rewritten` shows the binary row under the same "All ebuilds" header). `None` when no binary matches or some match is visible. Wired only at the top-level unsatisfied step; `--usepkg` (ebuild fallback alive) keeps the ebuild-side report. Remote-binrepo rows are not included (no S0 cell).
- #402: now a no-gate convenience over `all_binary_masked_report_with_respect_use` (inactive gate: byte-identical rows); kept because the `masked_deps` tests pin the no-gate shape directly.

## fn all_binary_masked_report_with_respect_use
- #402: a version-matching binary that is `is_visible` but rejected by the gate reports `use flag configuration mismatch` instead of vanishing into the plain miss (S0 `b03-use-bid2-respect`, re-run live on host 3.0.82.2 2026-10-19: one cpv-deduped row for both builds, rc 1). Portage models the mismatch as a mask, not a miss: built pkgs whose `ignored_binaries` carry `respect_use` get exactly that reason, and only when no other mask fires (`depgraph.py:6658-6663`, the `elif ... not mreasons` chain in `_show_unsatisfied_dep`; rows deduped by cpv in `show_masked_packages`, `depgraph.py:12453`). A selectable match (visible and gate-ok) still silences the report, and a non-visible binary keeps its own `candidate_masking_reasons` row — the mismatch row never overrides another mask. The installable set is unchanged (the `retain` sites are untouched); only the masked builder sees the dropped binaries. The ebuild pool (`masked_candidates_for_atom`) is unaffected — `all_masked_report` still delegates with no gate.
