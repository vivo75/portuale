# crates/portage-repo/src/resolve/root_deps.rs
`--root-deps` build entries for the running root.

## fn root_deps_satisfied_atoms
- Portage `--root-deps`'s own `DEPEND`/`BDEPEND`-vs-`ESYSROOT` distinction (see `running_root_satisfies_atom` for the full Portage grounding), factored out so both Portage dep-walk sites in this file (the main New/Upgrade/Reinstall flatten and `enqueue_dependencies`'s own AlreadyInstalled-recursion path) share one implementation rather than drifting apart. Reads `metadata`'s own `dep_keys` (Portage `["DEPEND", "BDEPEND", "IDEPEND"]` at both ordinary dep-walk sites -- `DEPEND`/`BDEPEND` are the classic `ESYSROOT` build deps, and `IDEPEND` *always* targets the running root for every package, not just recursed build entries -- `depgraph.py:4247-4252`), flattened the exact same way the caller already flattened its own combined dep string with, *except* for one deliberate branch-selection difference: the disjunctive (`||`) closure accepts a branch when every atom in it is either ordinarily satisfiable (`atom_currently_satisfiable`, tree-visibility) *or* running-root-satisfied (`running_root_satisfies_atom`) -- so a `DEPEND`/`BDEPEND` `||` group with no branch visible in the fixture tree at all still flattens correctly here as long as some branch is already installed on the running root, matching Portage's own effective behavior (a build-time tool that's already present on the host never needs a *visible* ebuild candidate to satisfy a Portage `--root-deps` build).
- The returned tokens are evaluated against `use_flags` (#133: Portage evaluates at every producer), so callers compare evaluated forms. Callers drop these from their own already-flattened `flat_deps` before queueing (Portage "no separate graph node needed for an already-satisfied dep"). Degrades to an empty set on any flatten failure -- never a false negative that could silently drop a dep portuale actually needed to walk.
- The `||` closure: `--root-deps` only needs the satisfiable-or-not split here (there's no "prefer the installed branch" question for a build-time `||` group resolved against the running root). The `tie_break` is trivially first-tied-wins: Available-vs-Unsatisfiable never ties on more than one selectable alternative in a way this call site's logic distinguishes.
- #133: Portage evaluates every token's conditional use-deps at the producer itself (`use_reduce(..., token_class=Atom)`'s own per-token `token.evaluate_conditionals(uselist)` step, before any branch selection or split) -- without this the raw `[flip=]` form reached the satisfied check below, where a conditional form imposes no state constraint at all, and every conditional build dep was vacuously running-root-satisfied. Unparseable tokens pass through as-is (today's tolerance, the same pass-through both dep-walk loops' own post-passes use).

## fn unsatisfied_root_deps_atoms
- The complement of `root_deps_satisfied_atoms`: Portage `DEPEND`/`BDEPEND` atoms (or, for the recursive walk into a package that is *itself* being built against the running root, `RDEPEND` + `IDEPEND` too) that flatten out of `metadata` but are *not* already satisfied by `running_root`'s own vdb -- the set Portage would need to recursively resolve (and potentially build) against the running root itself, rather than the target `ROOT`. `dep_keys` is `["DEPEND", "BDEPEND", "IDEPEND"]` at the two ordinary dep-walk sites (Portage `DEPEND`/`BDEPEND`-vs-`ESYSROOT`, plus `IDEPEND` which always targets the running root for every package), and `["DEPEND", "BDEPEND", "RDEPEND", "IDEPEND"]` when recursing into an already-`targets_running_root` entry (Portage `_add_pkg_deps`'s own `deps` tuple: a package whose own `pkg.root` is the running root has its `RDEPEND` resolved there too, and `IDEPEND` *always* targets the running root regardless -- `depgraph.py:4247-4252`).
- A blocker atom (`!foo/bar`) is never a real build target, so it's excluded here the same way `enqueue_flat_deps`/`enqueue_dependencies` already exclude one from their own ordinary queueing.
- Computed as its own separate flatten (duplicating `root_deps_satisfied_atoms`'s own work) rather than refactoring that already-shipped, already-tested function to return both halves at once -- deliberately additive/isolated, minimizing risk to it.
- #133: same producer-side evaluation as `root_deps_satisfied_atoms` -- Portage evaluates at every producer, so the complement set is evaluated-keyed too.

## fn resolved_version_meta_and_use
- The same re-lookup `slot_changed`/`deps_changed` already use; theoretically imprecise if the highest-priority provider of that version is masked while a lower-priority visible one exists, an accepted edge case those two functions share. `None` is the same tolerant "can't tell, don't crash" fallback. Cold path (`--root-deps` only); the shared `Rc` isn't worth threading through `unsatisfied_root_deps_atoms`'s `&HashMap`.

## struct ResolveRootDepsBuildEntriesArgs
- `local_binpkg`: threaded through to `resolve_pretend` (backlog #123); unconsulted here since `usepkg`/`usepkgonly` are both `false` below.

## fn resolve_root_deps_build_entries
- Portage "recursively pull in and build new packages against the running root" (`--root-deps`, `depgraph.py:4207-4271`'s own `depend_root` selection + `_add_pkg_deps`'s per-key `dep_root` tuple). Resolves `atom_str` against `running_root` the same way any dependency atom is resolved -- reusing `resolve_pretend` wholesale, `is_top_level: false`/`selective: true`, `usepkg`/`usepkgonly` both `false` (a build-time tool needed to actually perform a build is never satisfied by a `--usepkg` binary, and portuale's `--root-deps` scope has never touched binary packages).
- Still not walked: this entry's own `PDEPEND` (Portage keeps it a target-`ROOT` concern) -- a documented cut, not an oversight.
- `seen` (the shared `root_deps_build_seen` set, threaded through the whole graph resolution) is both the cross-package dedup key *and* the cycle guard: a `(category, package)` is inserted *before* its own dependencies are walked, so two build tools whose `BDEPEND`s point at each other (an unremarkable bootstrap pattern) terminate cleanly -- the second edge back into an in-progress package just yields no further entry. One `required_by` edge is therefore lost at whichever point a cycle is cut (Portage's own bidirectional digraph keeps both); a bounded, documented imprecision, the same best-effort `required_by` tracking already has elsewhere.
- `NoVisibleCandidate` gains an entry too, so an unbuildable, not-installed build dependency is surfaced by the renderer's own `!!! no visible ebuild for dependency` note exactly as it is without `--root-deps` (before this slice, `--root-deps` silently swallowed it). `AlreadyInstalled` yields nothing: the running root already has it (`unsatisfied_root_deps_atoms` and `resolve_pretend` disagreeing in some USE-dep edge the former's narrower check misses).
- Since #141 the display fields (`use_flags_display` / `use_expand_display` / `use_expand_display_p`) and the slot/repo identity are **populated** through the same `refresh_entry_use_display` seam the main walk uses, so a running-root rebuild row prints Portage's `USE="-flip*"` column instead of skipping the display -- Portage's row is `[ebuild   R    ] … to <root> USE="-flip*"` (bed `l0-fx-20260922T192350Z`). `oldbest` stays empty: Portage's `[oldver]` bracket is an Upgrade-row concern and S0's capture shows none on this shape (`findings/l0.md` "## #141/#135/#138/#134/#136 S0").
- Non-interactions: `--emptytree` deliberately does not reach `--root-deps` running-root build entries (this resolver is its own path, and `-e --root-deps` is an exotic combination); likewise `--getbinpkg` (a `--root-deps` build entry is always an ebuild built against the running root); `--autounmask` keyword / USE resolution is a target-`ROOT` concern (`resolve_pretend_graph`).
- #72 B3: a removal is never walked (it has no deps). `usepkg`/`usepkgonly` are both `false` above, so the outcome can only ever have come from an ebuild candidate (Portage `dbs` never grows a binary entry in that case).
- #141: the slot/repo identity and the USE-display fields the renderer's `USE="…"` column reads. `refresh_entry_use_display` diffs the tree candidate's effective USE against the *running* root's vdb record (the root `resolve_pretend` just resolved against), so a Reinstall whose flag flipped renders Portage's `-flag*` marker exactly like the non-`--root-deps` rebuild row.
