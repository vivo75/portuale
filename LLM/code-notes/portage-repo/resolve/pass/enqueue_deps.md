# crates/portage-repo/src/resolve/pass/enqueue_deps.rs
Folds the entry's dependency keys and queues the atoms they name.

## fn select_dep_tokens
- Portage `depgraph.py:4195-4247` (`_add_pkg_dep_string`): for a *built* package (`pkg.built` -- true for a binary, not for a fresh ebuild) with `myparams["bdeps"]` not in `("y","auto")` (i.e. `--usepkg`/`--getbinpkg`, which leaves `bdeps` unset per `create_depgraph_params.py:100`), `DEPEND` and `BDEPEND` are both emptied before the walk. `with_bdeps` (built from that same rule in `pretend.rs`) carries the bit. A binary's recorded `BDEPEND` (e.g. libgweather's `|| ( ( python:3.14 pygobject[...] ) ... )`) must not drive a merge.
- Backlog #143 S1: Portage `depgraph.py:4176-4183` (`_add_pkg_dep_string`) blanks `RDEPEND`/`PDEPEND`/`IDEPEND` for a *non-built* package under `--buildpkgonly` without `--deep` -- runtime blockers never enter the graph (upstream pg1 E/F). A binary or installed candidate is `pkg.built` and keeps its keys. The same runtime-key blanking applies to the `deps` list: runtime edges must not reach the merge-order digraph either under `--buildpkgonly`.
- Backlog #194: Portage `depgraph.py:4186-4193` (`_add_pkg_deps`) blanks an `--onlydeps` root's (`pkg.onlydeps` -- the arg-selected package, i.e. this walk's `depth == 0`) `RDEPEND` and `PDEPEND` when `--onlydeps-with-rdeps=n`, and its `IDEPEND` too unless `--onlydeps-with-ideps` is `y` or `True` (`man emerge.1`: rdeps enabled by default so only an explicit `=n` blanks; ideps disabled by default so only an explicit `=y`/bare flag keeps). Build-time keys (`DEPEND`/`BDEPEND`) always stay (`man emerge.1`: "When this is disabled only build time dependencies are included"). Without `--onlydeps` both flags are inert (no `pkg.onlydeps` node exists to blank). The same blanked keys stay out of the merge-order digraph (Portage never walks them, so they contribute no edge), and a blanked runtime key classifies nothing: an atom that only survives via a build-time key is `buildtime_hard`, not runtime. A *walked* `IDEPEND` still classifies (rdeps=n + ideps=y on EAPI 8), so the selection mirrors `onlydeps_walk_dep_key`, not just the rdeps blank. The filter only ever removes keys, so when nothing is blanked the static slices are used as-is (no per-package alloc on the hot path). An EAPI-7 root with `--onlydeps-with-rdeps=y` merges `[B, C, D]`, never `E` (oracle cell).
- Portage `bin/ebuild.sh`'s own `depend` phase (`if ! ___eapi_has_IDEPEND; then unset IDEPEND; fi`) + Portage `portage/eapi.py:135` (`eapi_has_idepend`): below EAPI 8 `IDEPEND` never reaches saved metadata, so `portdb.aux_get` serves `""` for it, for ebuild and binary candidates alike (Portage `porttree.py:644-648` defaults a missing `EAPI` to `"0"`, same as `bintree`). #194's EAPI-7 oracle cell needs this.

## fn record_merge_order_deps
- Discovery order differs from inclusion order: Portage walks `RDEPEND`, `IDEPEND`, `PDEPEND`, `DEPEND`, `BDEPEND` (`depgraph.py:4253-4289` deps tuple). `use_reduce_flat` drops `||`/`(`/`)` markers and lists every branch's atoms in written order; the unchosen branches are never an entry, so they contribute no edge once the digraph looks them up. See `GraphEntry::deps`.
- Track X Slice B fix (#242): a running-root build entry's own `deps` preserve Portage's insertion order -- `BDEPEND` before `RDEPEND` (`rdrtooldep` before `rdrlib`), like the old sidecar `["DEPEND", "BDEPEND", "RDEPEND", "IDEPEND"]` walk did -- instead of the target-root `RDEPEND`-first `deps` tuple. The old sidecar walk used `["DEPEND", "BDEPEND", "RDEPEND", "IDEPEND"]`, so `rdrtooldep` precedes `rdrlib`. The `cyc0z-3`/`cyc0y` cross-root `DEPEND` cycle (the #207 flip) carries a single key either way.
- Running BDEPEND cut: the `rdrcycb -> rdrcyca` bootstrap closing edge drops like the old sidecar `seen` guard dropped its second `required_by` edge (and like the `required_by` cut drops it for `find_hard_cycles`); `rdrtooldep`/`rdrlib` stay since first-visit. `DepEdge::key` numbering is `0=R,1=I,2=P,3=D,4=B`; bare and versioned atom texts alike collapse to cp.
- Self-edge exemption, Track X Slice C (#242): Portage `_add_pkg` drops a direct self-edge "unless it is an unsatisfied build-time dependency" (`depgraph.py:3765-3770`) -- and `_serialize_tasks` dead-ends on exactly that kept edge (`depgraph.py:10262`, the g216 running-root self cycle). The owner's own cp is trivially "visited" (its own pulling atom resolved to it), so without the exemption the cycle cut deletes the true self-loop along with the bootstrap-ring closing edges it exists for (`rdrcycb -> rdrcyca`) and the pass-1 abort never fires. Satisfied self-edges drop via `build_digraph`'s self-edge rule and `owner_self_loop`'s installed gate.

## fn classify_dep_atoms
- Classification uses a plain (non-disjunctive) `use_reduce_flat`: only the originating key matters, and a `||` group's branch choice matches the main flatten in every case without one. Groups never span keys, so the `||` branch choice matches across the buildtime/runtime/bdepend flattens.
- Without blanking, the runtime set is the long-standing unconditional three-key set.
- Backlog #133: `buildtime_atoms`/`runtime_atoms` are raw-keyed flattens and `enqueue_flat_deps` runs its own post-pass over whatever survives.

## fn prepare_disjunction_scope
- Cross-root runs: each queued atom carries its group root (`QueueItem::targets_running_root`); candidates select against that root's installed db, and only same-root entries satisfy the in-graph preference. Siblings share one owner and one cp, so the group root is homogeneous in practice. Mixed-key same text falls target (the queue tag's target-wins rule).
- Backlog #221: `disjunction_preference` takes `slot_constraints` itself (not a lookup closure); it holds this pass's recorded cycle edges -- empty on the first attempt, populated on the restart after a stranded walk (see `collect_feedback`). Backlog #249: Portage expands a new-style virtual's deps inline, inside the dep_check of the package that pulled it, and its `dep_zapdeps` chains `circular_dependency.get(parent)` and `.get(virt_parent)` (`portage/dep/dep_check.py:673-678`, with `virt_parent` set at `:236-252`). Portuale walks the virtual as its own node, so `self_cp` is already Portage's `virt_parent` key; the `parent` half is the virtual's puller(s), whose recorded cycle children join the lookup here. (Portage runs the expansion once per pulling edge; the union over this pass's pullers is the one-node approximation.)

## fn flatten_dep_string
- Portage `dep_zapdeps` re-chooses a `||` alternative once backtracking has masked the preferred one: an atom whose only satisfying candidates are excluded by the negatives this loop accumulated for its `cat/pkg` (`slot_constraints`, = `runtime_pkg_mask`) counts as unsatisfiable, so the next alternative wins on the retry.
- Backlog #216: `dev-lang/go`'s BDEPEND `|| ( >=dev-lang/go-<min> dev-lang/go-bootstrap-<min> )` with in-graph `go` ranks the first branch `preferred_in_graph` (bin 0), so the cycle forms and the `circular_dependency` map re-resolves it (`BacktrackParams::circular_dependency`); only a self atom matching nothing in-graph (and nothing installed) refuses; see `disjunction_preference`'s circular-self-dep check.
- Review 2026-09-11 F1/F2: the `dep_zapdeps` choice-bin classification used to be two hand-maintained copies (this closure and `enqueue_dependencies`'s); only this one got the fine `unsat_use_*` bins, so they were unified into `disjunction_preference`.

## fn filter_root_deps
- `--root-deps` limitation (documented in `LLM/agent-context.md`'s `--root-deps` backlog entry, the "recursive second-root graph" gap): portuale's single-unified-graph architecture merges the five dep keys into one string before flattening, so the closure can't tell which key an atom came from while Portage applies `--root-deps` only to `DEPEND`/`BDEPEND`.
