# crates/portage-repo/src/resolve/pass/unresolved_dep.rs
Handles a dependency with no version to merge: backtracking feedback and its unsatisfied entry.

## fn maybe_missing_dep_backtrack
- Portage `_feedback_missing_dep`: this dependency atom has no matching package. If backtracking is live and its parent is a merge-bound entry not yet tried, remember to mask `!=parent-cpv` and retry, so a `||` group whose chosen alternative has an unsatisfiable subtree yields to the next alternative; a top-level-selected version whose dependency is unmaskable yields to the next older version. Backlog #198: `akk0a-2` masked, `akk0a-1` picked; Portage `depgraph.py:3493-3503` + `backtracking.py:197-207` carry no top-level exemption (the mask names one cpv, never the requested package itself). Only the first such trigger per pass is acted on (like Portage, one backtrack node at a time); the NVC entry is still built so an un-fixable dep is reported unchanged.
- Portage (`depgraph.py:3473-3483`) does NOT missing-dep backtrack when only a USE change would satisfy the dep (`_select_package(dep.atom.without_use)` still finds a package); that path is the autounmask machinery's, and an unfixable `[flag]` dep reports as a plain NVC.
- C3: Portage's "no matching package" is mask-aware (a masked candidate matches nothing), so the probe consults the negatives, not the bare tree: a dependency unsatisfiable only because backtracking masked its candidates masks its parent and retries (`btconsumer-2.0` under a masked `bttarget-2.0` falls back to `btconsumer-1.0` on retry, the same downgrade the old puller pre-masking produced). Positives stay out (Portage selection has no enforcement counterpart); a USE-only failure satisfies the probe and stays out, as before.
- Backlog #276: Portage `_add_dep` (`depgraph.py:3456-3470`) maps to `runtime_pkg_mask` "missing dependency". See `is_installed_only_mask`; the next pass walks the same-version ebuild like Portage's second backtracking try masking the ebuild.

## fn record_installed_slot_collision
- Backlog #57, direction 1: this atom settled on an *installed* instance, and the same `(cat, pkg, slot)` may already hold a merge-bound one that this atom rejects -- Portage's `_package_tracker` sees both nodes and calls that a slot collision (`othermod`'s `<paired-2.0` landing on installed 1.0 while `needer`'s `>=paired-2.0` already graphed 2.0). Recorded before the `other_outcomes` dedup, since a repeat visit of this `cat/pkg` under a different atom text is exactly how the second, conflicting constraint arrives. Deliberately no `continue`: Portage keeps the installed node and still merges the other instance, and the solvable/unsolvable split (Portage `_solve_non_slot_operator_slot_conflicts`) is the backtracker's -- `collect_feedback`'s `slot_want` solvability check reconciles a jointly-satisfiable slot on the retry and this record disappears with it; only a slot no single version can satisfy survives to be reported. The instance lives in this atom's own resolving root (Track X Slice B, #242).
- The vdb `SLOT` read is reused by the slot-conflict record and the `other_outcomes` dedup key; `installed_refs` would re-list every version and read each `repository` too, and this runs for every `AlreadyInstalled` outcome in the walk (thousands on a `-puD @world`).
- Direction-1 forgiveness (#270): the "this is a rebuild trigger, not a conflict" forgiveness presumes the slot-operator rebuild scan will schedule the consumer, and that scan only runs with a backtrack budget (`backtrack_max > 0`, like its own call site). At `--backtrack=0` nothing schedules the rebuild, so Portage's in-pass solver sees the conflict and withholds the provider update instead of merging it alone (Portage 3.0.82.2: `[sct, oldc, newc]` only); Portage `_solve_non_slot_operator_slot_conflicts` (`depgraph.py:1774-2115`).

## fn dedup_repeat_visit
- Backlog #74 S2a: AlreadyInstalled repeats are keyed by the installed instance's own slot (Portage's `pkg.slot_atom` node identity): a *second* installed instance of the same cp in another slot is a distinct node whose deps must still be walked. NoVisibleCandidate has no instance to key by: `None` keeps the old cp-scoped repeat dedup. The old cp key let the first slot processed shadow the rest, dropping `llvm-core/clang:23`'s own build deps.
- Backlog #57 (`suppressed_nvc`): a deduped `NoVisibleCandidate` never gets its own entry, so under an active `runtime_pkg_mask` the `has_nvc` scan must still treat the pass as a dead end (Portage's `_create_graph` returns 0 on an unsatisfiable dep and the attempt is abandoned in favour of `get_best_run`); gated on an active mask so no unmasked pass changes behaviour. The argv order `othermod needer` used to settle on the masked try otherwise.
- Backlog #286: the repeat edge carries the atom the first edge lacked, and Portage's fail-fast walk would have hit it first. Both row builders read the new atom only; the cheap gate runs them only when the recorded atom is a supersedeable built one.

## fn enqueue_installed_deps
- `--deep`: an AlreadyInstalled package's own further dependencies are walked too, once `deep` allows recursion at this package's own depth (see `Deep::recurses_at`'s own doc comment) -- never for NoVisibleCandidate (no version to look anything up by), and never when `nodeps` disables the dependency walk entirely. Portage's own `_add_pkg` gate is the same: an installed package whose deps aren't recursed into gets pushed onto `_ignored_deps`, never `.order`, so `GraphEntry::deps` for an AlreadyInstalled entry is likewise only ever computed under this identical condition.
- The installed entry's `deps` display list uses the installed recorded USE, not effective profile USE (see `enqueue_dependencies`); a `flag?`-gated dep it shows must match what the recursion actually queued. An installed package is `pkg.built`, so Portage marks its build-time deps `optional`.
- Installed `deps`: live ebuild deps plus the vdb's own built `:=` atoms by default, the vdb snapshot under `--dynamic-deps=n` (backlogs #25 S1b display/recursion agreement, #26 A2 same-view construction, #86 recorded-repo view, never a priority search). The recursion walks `atom_root` (Portage `pkg.root`, Track X Slice B #242); `--debug`'s `Depstring` line and `--tree`'s edges can no longer contradict the child the walk actually queued; see `enqueue_dependencies`.

## fn compute_nvc_suggestions
- `--autounmask`'s own keyword-suggestion sub-feature, extended here to a *dependency's* own `NoVisibleCandidate` -- see `GraphEntry::keyword_suggestion`. `--autounmask-use`'s own suggestion sub-feature -- see `GraphEntry::use_suggestion`; `atom.use_deps` is the dependency atom's own use-dep spec (already conditional-evaluated by `enqueue_flat_deps` before this atom was ever queued, so only plain `flag`/`-flag` forms survive to be checked here). Its second, architecturally distinct sub-feature (see `suggested_parent_use_candidate`) is only attempted when this atom actually had a conditional use-dep evaluated away (`unevaluated_atom.is_some()`) and has a real parent to flip a flag on (`owner.is_some()`, always true here: a top-level atom's own `NoVisibleCandidate` already aborted the whole call via the fatal check above).

## fn record_miss_disclosure
- Masked disclosure (Portage `_show_unsatisfied_dep`'s "All ebuilds that could satisfy … have been masked" block for a *dependency*) is the Tier 2.20 half of finding S's top-level report: a dependency `NoVisibleCandidate` whose atom still matches ebuilds by version, every one of which is masked, is recorded here (one per `cat/pkg`, like the entry itself) instead of rendering the bare `!!! no visible ebuild` line. The display atom is the unevaluated form as queued. Computed every pass; only the final pass's reports are rendered.
- #420: the masked rows come from `masked_rows_for_dep` — the ebuild pool merged with every binary pool selection consulted (local under `--usepkg`/`--usepkgonly`, remote under `--getbinpkg`), so a USE-mismatched (cell A) or deps-stale (cell C) binary discloses instead of falling through to the plain miss. The `dedup_repeat_visit` refresh below reads the same merged rows. Chain rendering is untouched (`finalize_dep_reports` walks every `masked_deps` entry).
- #420: the disclosure atom is the unevaluated form, so a slot-operator dep prints whole (`"dev-libs/t341-dep:0/1="`, s10x cell A) and version-matches through `parse_match_atom` unchanged.
- USE-unsatisfied disclosure (backlog #20, Portage `_show_unsatisfied_dep`'s separate "no ebuilds built with USE flags to satisfy" path): a dependency `NoVisibleCandidate` whose atom names version-matching ebuilds that are *visible* but cannot satisfy the atom's own `[use]` deps. Portage's precedence puts this block before the masked one (`show_missing_use` wins), and the caller renders it first.
- Parent-flip suppression: a dep the `'parent_flip` off-arm collected into a parent USE flip records no disclosure at all: Portage drops the collected item from `_unsatisfied_deps_for_display` (`depgraph.py:5820` `remaining_items`), so neither the masked block, nor the use-unsat block, nor the plain-miss block prints for it -- the change block is its whole output. (`nvc_dep_atoms` above is kept: `abort_outcome` still needs the atom for the abort reason.)
- Plain-miss shape (backlog #135 (d)): when neither sibling block claimed the miss -- nothing matches by version at all, or no candidate's failure is a `Change USE:`/`Missing IUSE:` one (e.g. a profile-forced flag) -- Portage's `emerge: there are no ebuilds to satisfy "<atom>"` block applies.
