# crates/portage-repo/src/resolve/pass/top_level_unsatisfied.rs
Drops or aborts a top-level atom with no visible candidate, Portage's argument handling.

## fn step_top_level_unsatisfied
- S7 (#341): `--exclude`d top-level arguments resolve to nothing silently (`Total: 0`, exit 0) instead of aborting with "there are no ebuilds" — `top_level_atom_entirely_excluded` drops an explicitly requested atom with at least one matching package (ebuild, local binary or installed instance) when every match is `--exclude`d, before the set-member/masked/USE/miss reports. Portage (`depgraph.py`, the `if excluded: continue` in the argument loop) skips when *any* match is excluded; the all-excluded rule is its safe half — a surviving non-excluded match means the walk would have selected a package, so this probe is never reached then. Remaining corner (a masked, non-excluded match beside an excluded one: Portage skips, portuale reports the mask) is documented, not pinned. Set members never take this path (their miss lands in `missing_args`, like Portage's `SetArg` handling, which never consults the excluded set).
- Backlog #286: Portage `depgraph.py:5577-5605` (`_resolve`): explicit arguments fail the run, set members land in `_missing_args`. The missing parent is an installed one with no merge-bound replacement (the #276 shape: both instances masked by now), so the healed rest of the graph settles and the display layer reports the skipped update plus the world-file problem.
- Backlog #210: see `complete_mode_withheld_version`. `slot_op_reachable` is populated on the CLI's complete pass and its `--deep` re-run alike, empty otherwise.
- A top-level atom (as opposed to a dependency reached while recursing) with no visible candidate aborts the whole call, matching Portage's own depgraph.py behavior for an unsatisfiable target, not the "report and keep going" treatment a dependency's own NoVisibleCandidate gets. Top-level atoms are always dequeued in argv order, before any dependency, so the *first* bad top-level atom is the one that aborts.
- Portage `_show_unsatisfied_dep`: an atom that matches ebuilds which all turned out masked reports the "All ebuilds that could satisfy … have been masked" block (+ each masked candidate and why), not the "there are no ebuilds to satisfy" one.
- USE-miss block (backlog #265(b), with #273): a top-level atom's own USE miss aborts with Portage `_show_unsatisfied_dep`'s "no ebuilds built with USE flags to satisfy" block, not the bare miss -- the `(Change USE: …)` / `(Missing IUSE: …)` rows. Ordered after the masked block like Portage's own `show_missing_use`-before-`masked_packages` precedence. Portage `depgraph.py:6969-6994`, with `AtomArg` parents getting no `(dependency required by …)` lines (`:7080-7090`). Portage's staging `for <root>.` suffix stays absent (the long-standing `fixture-miss-message-unsuffixed` class); backlogs #265(b), #273. The dependency arm renders the same way.
- `--autounmask`'s own keyword-suggestion sub-feature is only attempted when enabled, and only finds something to suggest when a real candidate exists that is masked by KEYWORDS alone; a candidate masked by package.mask/license/etc. too gets no suggestion, matching Portage's "only suggest a fix that would actually work" spirit.
- `--autounmask-use`'s own suggestion sub-feature: same gating/"only suggest a fix that would actually work" spirit. Message format mirrors Portage `package.use` suggestion syntax (`=category/package-version flag -flag`).
- `--autounmask-license` suggestion: same "only suggest a fix that would actually work" gating. `--autounmask-keep-masks=n` has its own suggestion sub-feature.
- Keyword suggestion: see `keyword_masked_only`; portuale does not yet combine multiple simultaneous suggestion kinds the way Portage can. The on/off default-resolution logic lives in this function's caller config.
