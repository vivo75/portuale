# crates/portage-repo/src/resolve/cycles.rs
Circular dependencies: hard-cycle detection, restart triggers, virtual cycles and USE-fix suggestions.

## fn cycle_restartable
- Finds the shortest **unbreakable** dependency cycle among the merge-bound `entries` -- Portage `circular_dependency_handler`'s `_find_cycles` + `shortest_cycle`, restricted to *hard* edges. Those are the only edges Portage `_serialize_tasks`' `_ignore_runtime` scan can't drop, so a cycle made entirely of them is exactly the case Portage reports with `* Error: circular dependencies:`.
- A hard edge is an unsatisfied build-time dep with no run-time alternative, `edge_kind_map[(dep cp, owner cp)] == (true, false)` -- or, since backlog #228, an unsatisfied non-optional slot-operator edge (`DEPEND`/`RDEPEND` `:=`, Portage `DepPriority` `buildtime_slot_op`/`runtime_slot_op`, which no `ignore_priority` rung of either `DepPriority*Range` relaxes -- Portage `_emerge/DepPriorityNormalRange.py` / `_emerge/DepPrioritySatisfiedRange.py`, grounded by the n228 probe: Portage 3.0.81.3 aborts `dev-libs/slopcyca -RDEPEND:=-> dev-libs/slopcycb -DEPEND-> dev-libs/slopcyca` with `(runtime_slot_op)` / `(buildtime)`). A plain unsatisfied run-time edge stays soft on purpose: both serializers merge a run-time cycle as a group (`find_smallest_cycle`/`gather_deps`), so it never forces an abort. The slot-op arm reads the owner's own `deps` edges (the merge-order graph input, which carries Portage's per-key `DepPriority` including the `:=` promotion) with Portage's own installed gate (`dep_edge_satisfied_by_installed`, so a satisfied slot-op edge stays breakable exactly like Portage's `satisfied` rung -- and, for a slot-operator edge, only an installed instance in the child's own slot/sub-slot satisfies, Portage `_add_pkg_dep_string`'s `inst_pkgs` same-slot filter in `depgraph.py`); `DepEdge` `priority.satisfied` itself is never consulted -- it is always false on an entry (`build_digraph` only sets it on a local copy).
- The hard-edge digraph has an edge `owner -> dep` for every such `edge_kind_map` entry whose both endpoints are merge-bound `entries` (plus every slot-op deps edge between two merge-bound entries, even one the walk never recorded -- provided it sits on the `||` branch the walk selected: Portage's digraph holds the resolved edge only, so a suppressed alternative's `:=` edge never hardens, Portage `dep_check.py::dep_zapdeps`). Branch selection reuses `merge_order::kept_alt_branches`, the same set `build_digraph` collapses to, so the two cannot disagree. Returns the shortest directed cycle as an ordered CPV list where each element depends on the next (the last wrapping to the first), starting where Portage's `shortest_cycle[0]` starts (backlog #278 -- `discovery` order stands in for Portage's digraph insertion order); empty when the hard-edge graph is acyclic (every ordinary resolve).
- Full elementary-cycle enumeration lives separately (`merge_order::elementary_cycles`, Portage `digraph.get_cycles` over the `medium_soft` rung) and feeds only `large_cycle_count` and the cycle-only re-display -- this stays the short hard ring the message and the suggestions render.
- Backlog #216: a same-cp edge is a cycle only when it targets the owner's own instance. `owner_self_loop` is that test: one of the owner's kept `deps` edges (inline, or on the `||` branch the walk selected -- a suppressed alternative's edge is not in Portage's digraph) names the owner's own `cat/pkg` and its atom matches the owner's merge-bound cpv. `>=dev-lang/go-X` against in-graph `go-X` loops; `=foo-2` against `foo-1` (a same-cp cross-slot edge, ordinary in Portage's package-keyed digraph) does not.
- Scope gate for the serialize-dead-end retry in `collect_feedback` (`cycle_restartable`): only a fresh single-node self-loop closed by a kept `||` self-branch retries. That is exactly the `||` pick this slice ports (Portage's pass-1 `preferred_in_graph` self choice, `dep_check.py`); everything else keeps today's report-no-retry path: multi-node rings are backlog #221's general branch-switching scope (G18, EAPI-gated), whose display-side (`kept_alt_branches`) re-derivation and merge-vs-installed bookkeeping this slice does not re-model; an inline (branch-less) self-dep has no alternative branch a retry could switch to; an installed instance of the owner cp means the demoted branch lands on installed subgraphs (slot_want unification, display re-derivation), same scope cut.
- `kept` is `kept_alt_branches` over the same entries.

## fn owner_self_loop
- Scope: self-loops touching an installed instance stay invisible (like before this slice). Portage deadlocks on them too, but only ever as a transient: its `circular_dependency` retry re-resolves past them, which needs the merge-vs-installed bookkeeping (slot_want unification, display re-derivation) backlog #221's general branch-switching scope (G18, EAPI-gated) owns. Reporting one here would flip an outcome-correct resolve (the invisible self-edge never constrained order or display) into a spurious circular abort, so the retry gate (`cycle_restartable`) never sees them either -- fresh self-loops only, both sides consistent.

## fn find_hard_cycles
- Merge-bound entries only, lowest index per cp (the merge list is already in dependency order, so the first is the one to start a rendered cycle at).
- Track X Slice C (#242): the per-(root, cp) resolution view (Portage's package-keyed digraph). Single-root graphs resolve every endpoint through the cp fallback, exactly as before.
- Backlog #228 slot-op arm: owner index -> dep indices with an unsatisfied non-optional slot-operator `deps` edge between two merge-bound entries. Only the `||` branch the walk selected counts (`kept_alt_branches`, Portage `dep_zapdeps`' choice -- the same set `build_digraph` collapses to): Portage's digraph holds the resolved edge only, never a suppressed alternative's. The installed gate is `dep_edge_satisfied_by_installed`, so a `:=` edge is satisfied only by an installed instance in the dep entry's own slot/sub-slot (Portage `_add_pkg_dep_string`'s `inst_pkgs` same-slot filter in `depgraph.py`).
- The walk's `(true, false)` arm, or the slot-op deps arm (an `RDEPEND` `:=` edge is never `buildtime_hard`, so the map alone can never see it).
- Backlog #216: a same-cp edge is a cycle only when it targets the owner's own instance (Portage's digraph keys by package, so `foo:1 → foo:2` is an ordinary edge while `go → go` deadlocks `_serialize_tasks`). The kept branch's atom decides, matched against the owner's merge-bound cpv.
- A slot-op deps edge the walk never recorded has no map entry at all -- it still counts when it sits on the branch the walk selected (Portage's digraph holds that resolved edge); a suppressed `||` alternative's edge is skipped.
- Track X Slice C (#242): the child's resolving-root instance (Portage resolves each atom against its group's root); the cp fallback is the pre-slice behaviour. Same true-self-loop gate as the map arm.
- The iteration order analogue of Portage `digraph`'s node insertion order: DFS pre-order from the request targets over declaration-order deps (Portage's `_add_dep` recurses synchronously). Seeds are the parsed `top_level_atoms` in order (target-root instance first when both roots hold the cp); with `onlydeps` the targets are not inserted up front, so the seeds are their resolved direct deps instead (backlog #518). Units with no usable targets fall back to entry order. Stable sort everywhere; insertion order, not array position.
- Shortest directed cycle, chosen the way Portage `circular_dependency_handler` chooses what to print (backlog #278): Portage `digraph.get_cycles` (`portage/util/digraph.py:387`) walks nodes in insertion order and, per node, closes a cycle through each child with the shortest child-`>`node path; Portage `_find_cycles` (`resolver/circular_dependency.py:48`) keeps the first strictly-shortest one, and `_prepare_circular_dep_message` (`:76`) prints from its `[0]`. The child order follows declaration order (deterministic; Portage's BFS set order is hash-seeded, but only same-length ties can differ, and per node only the first of those can win the strict-shortest race). Only the display's start node changes: the winning length is the same global minimum the per-start BFS found before, so the cycle set (and, for two-node rings, the members) is untouched, and empty stays empty (a start reaches itself iff one of its children reaches it). Portage `shortest_path(node, node)`: `bfs` yields the start first, so the one-member path wins immediately.

## fn find_restart_cycles
- Backlog #221: the restart-trigger half of Portage `_serialize_tasks`' no-leaf handling (`_emerge/depgraph.py:10264-10296`). Portage records `backtrack_infos["config"]["circular_dependency"]` and restarts whenever its leaf selection strands -- i.e. whenever the digraph filtered by `DepPrioritySatisfiedRange.ignore_medium_soft` still holds a cycle. That rung (`_ignore_satisfied_buildtime_slot_op`, `DepPrioritySatisfiedRange.py:79-86`) keeps exactly the non-optional edges Portage cannot satisfy without merging: unsatisfied `buildtime` AND unsatisfied `runtime` alike (`return not priority.buildtime and not priority.runtime` -- only an edge with neither flag, or a satisfied or optional one, is ignored). A pure-runtime cycle never reaches the recorder: `find_smallest_cycle` group-merges it first (no restart, no error). So the trigger is a directed cycle over those kept edges that contains at least one buildtime edge -- the shape a group merge can never absorb, since a buildtime edge is unignorable at every rung.
- Edge sources mirror `find_hard_cycles`: the walk's `edge_kind_map` hard arm (precomputed unsatisfied-buildtime, cp-level) plus the selected `||`-branch `deps` walk (`kept_alt_branches`, Portage's digraph holding the resolved edge only), widened from buildtime-only to buildtime-or-runtime with Portage's own installed gate (`dep_edge_satisfied_by_installed`, so an installed-provided dep stays breakable exactly like Portage's `satisfied` rung). `PDEPEND`-only (`runtime_post` without `runtime`) edges stay out -- Portage's rung ignores those too.
- Returns one index cycle per hard edge that closes a loop (each element depends on the next, the last wrapping to the first, the `find_hard_cycles` convention, so the recorder below can reuse Portage's `circular_child = cycle[index - 1]` rotation). One cycle per hard edge rather than full elementary enumeration: disjoint co-cycles converge over successive restarts (each retry strictly grows the recorded map -- see the `unsolved_cycle` gate at the call site), while enumeration would blow up on big graphs. Empty when no hard edge closes a loop (every ordinary resolve, and every pure-runtime cycle).
- Track X Slice C (#242): the per-(root, cp) resolution view (see `find_hard_cycles`). Trigger adjacency: owner index -> (dep index, hard). `hard` is an unsatisfied buildtime edge; any entry is an unsatisfied non-optional buildtime-or-runtime edge (Portage's kept set).

## fn find_virtual_cycles
- Backlog #193: Portage `depgraph._virt_deps_visible`'s virtual-cycle rule (`lib/_emerge/depgraph.py:6208-6222` in 3rdparty/portage 3.0.82.2). While resolving a `virtual/` atom, Portage recursively probes the selected provider's own `RDEPEND` closure (`_virt_deps_visible_imp`, `:6224-6256`, reached through `dep_check` → `_dep_check_composite_db.match_pkgs`, `:11833` → `_visible`, `:11921` → `_virt_deps_visible`, `:11945`), and re-entering a virtual already on the probe stack (`_virt_deps_visible_recursion`, `:873`) raises `_virtual_cycle_error` (class `:11685`, `:6215-6216`). `select_files` (`:5002-5013`) catches it into `_virtual_cycle`, prints `\n\n!!! virtual cycle detected:\n\n` plus one `  {cpv}::{repo}` line per stack member (sorted) plus `\n` (`writemsg`, stderr), and fails the resolve (`_skip_restart`, no merge list, exit 1). Upstream `test_virtual_cycle.py` (bug 965570): `virtual/gzip-1` whose `RDEPEND` is itself, and the `virtual/A-1 → B-1 → C-1 → A-1` ring, both fail (the playground surfaces the members as `virtual_cycle`, `ResolverPlayground.py:1241-1242`). Grounded live by the g193 probe (`podman run localhost/test-portuale:latest`, portage 3.0.81.3 -- same message shape in 3.0.82.2 by source read -- `emerge -p --color=n app-misc/{bar,foo}` on the staged #50 fixtures, rc 1 both, members `virtual/gzip-1` / `virtual/A-1,B-1,C-1` each with `::testrepo`).
- Ported as a settled-graph check over the provider selection the walk already made: DFS from every merge-bound `virtual/` entry along kept-branch `RDEPEND` (`DepEdge.key == 0`, the only key Portage's imp expands) edges to merge-bound `virtual/` targets; revisiting an on-stack entry reports the whole stack -- Portage reports the full recursion set, so a lollipop (a virtual pulling a self-looping virtual) reports every virtual on the path, not just the loop. Members return as `cpv::repo` lines in Portage's sorted order (cp, then `vercmp` version, then repo). A `virtual/ → non-virtual → virtual/` ring is NOT one (Portage's stack holds virtuals only, so that shape probes clean) and stays an ordinary merge.
- Documented cuts: a dep target that is not merge-bound (`AlreadyInstalled`, unresolvable) is not expanded -- Portage probes the installed/available package's own recorded `RDEPEND` there too, but no fixture shapes an installed virtual with a cyclic recorded `RDEPEND` that nothing merges; and a suppressed `||` alternative is never probed -- Portage's `dep_check` may probe a non-selected branch first and fail where this succeeds (no fixture shapes that either). A virtual the walk considered but did not select is likewise never a start node (Portage may probe such a candidate mid-search; single-provider fixtures cannot tell).
- Branch selection reuses `kept_alt_branches`, the same set `build_digraph` collapses to (Portage's digraph holds the resolved edge only) -- computed lazily so resolves without a `||` edge on any merge-bound virtual never touch the digraph prelude. The empty map is backlog #193's own settled behaviour (this check predates the circular backtrack map; its pins must stay byte-identical): branch switching from a later backtrack pass is already reflected in the walk's own selection, which is what this re-derives.
- The revisit check is the `_virt_deps_visible_recursion` membership test (`:6215`): the reported members are the whole stack, like Portage's `list(recursion_set)`. Portage `sorted()` on `Package` (`Package.py:830`: cp, then `vercmp` version); the `::repo` suffix plays no part there.

## fn cycle_edge_labels
- Backlog #228: one label per edge of a `find_hard_cycles` cycle -- Portage `_prepare_circular_dep_message` (`resolver/circular_dependency.py`, the `({pkg} ({priorities[-1]}))` on every line after `depends on`). `labels[i]` is the edge `cycle[i] -> cycle[(i + 1) % len]`: the `DepPriority.__str__` (`_emerge/DepPriority.py`) of the hardest `deps` priority the owner's entry carries toward the dep's cp. Portage keeps the per-edge priorities sorted by hardness (`digraph.add`'s `bisect.insort`), so `[-1]` is the max -- taken here with `max_by_key(dep_priority_rank)`, the ordering `resolver_trace::max_priority` implements, rendered with the same `dep_priority_str` the `--debug` digraph dump already prints per edge. `satisfied` never affects a label (Portage ranks by hardness only); a `||` group contributes every branch's priority (Portage's digraph holds only the resolved branch -- an approximation, immaterial whenever the branches share a key, which they do by construction). `"buildtime"` when the owner carries no `deps` edge there at all (a map-only edge from a `deps`-less synthetic entry; every resolver-built cycle edge has its atom queued, so the fallback never fires on a Portage resolve).

## fn split_cpv
- Splits a `category/package-version` string into its three parts (the last `-`-separated boundary whose right half `ververify`s).

## fn required_use_flag_names
- Every USE flag name referenced anywhere in a `REQUIRED_USE` string -- Portage `portage.dep.get_required_use_flags`, as a plain token scan (strip a trailing `?`, a leading `!`, skip the grouping operators).

## struct CircularSuggestion
- One entry of Portage `circular_dependency_handler.suggestions`: a specific `Change USE:` fix that would break the cycle at one edge. `followup`: Portage `followup_change`: a grandparent's atom conditionally constrains one of these flags, so the fix may cascade upward.

## fn circular_dep_solutions
- Backlog #506: a wrapper over `circular_dep_search` with the default limit of 10; `circular_dep_search` takes `PORTAGE_CIRCULAR_MAX_USE_FLAGS` (`circular_max_use_flags`) in both of Portage 3.0.83's places (the REQUIRED_USE widening bound and the give-up) and returns the given-up parents as `search_truncated` (Portage `self.search_truncated.add(parent)`), which the report lists. The search still reads `DEPEND BDEPEND` only; Portage 3.0.83 also searches `RDEPEND` for a runtime edge (residue #517).
- Port of `circular_dependency_handler._find_suggestions` (`lib/_emerge/resolver/circular_dependency.py:114`): for each edge of the shortest cycle, the minimal `package.use` changes on the *depending* package that would drop the offending atom from its build-time deps without violating its own `REQUIRED_USE`. Returns them deduped and sorted (Portage iterates a `set()`, order undefined -- this crate sorts for a deterministic render, the same choice made everywhere else portuale diverges from a Portage non-determinism).
- Simplifications vs Portage, all documented in `docs/history/find-suggestions-plan.md`: `_pkg_use_enabled` is `effective_use_flags` with the autounmask-USE overlay applied (Portage `_emerge/depgraph.py:7669` returns the `_needed_use_config_changes` set, autounmask included); autounmask-*changed* flags are still honoured as untouchable (Portage `resolver/circular_dependency.py:104-114`); the grandparent-atom set is re-derived by scanning each puller entry's raw `DEPEND`/`BDEPEND`/`RDEPEND`/`PDEPEND` for atoms on `parent`'s `cat/pkg` rather than Portage's exact recorded `_parent_atoms`.
- Portage `_pkg_use_enabled` (`_emerge/depgraph.py:7669`) returns the `_needed_use_config_changes` set when the parent carries one -- the autounmask-USE overlay applied on top of the configured USE. The changed flags themselves stay untouchable (Portage `_get_autounmask_changes`, `circular_dependency.py:104`).
- `parent_atom`: the (unevaluated) token in `dep` that pulls the child -- Portage `all_parent_atoms[pkg]` filtered to this parent, `.unevaluated_atom`.
- untouchable = use.mask ∪ use.force ∪ autounmask-changed. REQUIRED_USE entanglement (bug #374397 -- bounded): when an affecting flag is REQUIRED_USE-entangled, widen to the referenced flags bounded by MAX_AFFECTING_USE. bug #555698: drop irrelevant not-currently-enabled flags when over the cap.
- Every enable/disable assignment of the affecting flags whose reduced `dep` no longer contains `parent_atom` and still satisfies `REQUIRED_USE`, recorded as a minimal diff. Drop a solution that's a strict superset of another.

## fn grandparent_use_conflict
- Portage `_find_suggestions` step 9: does a grandparent's own atom on `parent`'s `cat/pkg` constrain a flag in `solution`? A hard `[flag]` / `[-flag]` clash disqualifies the solution; a conditional (`flag?`/`flag=`) clash only flags `followup_change`. Grandparents are re-derived by scanning each puller entry's raw dep strings (see `circular_dep_solutions`).
