# crates/portage-repo/src/resolve/or_preference.rs
Which alternative of an `||` group to prefer: Portage `dep_zapdeps`'s choice bins and in-bin ordering.

## fn alternative_downgrade_demoted
- Portage `dep_zapdeps`'s two bug-531656 guards (`dep_check.py` soft 476-490 `conflict_downgrade`, 531-541 `installed_downgrade`): an otherwise available `||` alternative is demoted to the `other` bin when one of its atoms would pull in a *lower* version of a package whose slot the live graph already holds at a higher version, unless that downgrade is desirable (`downgrade_probe`). This is what makes `|| ( dev-ml/labltk:= <dev-lang/ocaml-4.02 )` take `labltk` once the `ocaml-4.02.1` update is in the graph (upstream `test_or_choices.py::testConflictMissedUpdate`) instead of the `<ocaml-4.02` arm that forces the update back out.
- Portage's `graph_db` is the depgraph's live package set; portuale's is the resolver's in-progress `entries` (both `||` call sites pass `state.entries`/`entries` as they stand at that instant), which is the same set Portage consults at the same moment.
- Port notes, each a deliberate narrowing:
  - `avail_pkg` is the highest visible tree match of the atom without its `[use]` block (Portage then re-selects with USE when that succeeds; the version compared below can only differ when a USE-satisfying lower version exists, not a shape this guard targets).
  - `highest_in_slot` counts only as "in graph" when an entry for that `cat/pkg` slot exists (merge-bound, or an `AlreadyInstalled` node). Portage's `_select_package` would also return a bare installed instance that is not yet a graph node when `--update` is off; that variant needs the update mode threaded to this depth and is left out.
  - `replacing` (`will_replace_child`): an atom of the entry's own `cat/pkg` (`self_cp`) is never demoted.
- Backlog #90 (S1): Portage selects every world/argv atom inline and forward before walking anything, so by the time a `||` alternative is judged the pending update is already a graph node. Portuale walks last-declared-first and judges eagerly: a queued atom on the same cp stands in for the not-yet-graphed selection. The hypothetical is what that selection would pick -- tree-best under `--update` (the update Portage already graphed), installed-best otherwise (Portage selected the installed instance) -- evaluated against the queued atom's own text, with that cp's hard constraints.
- Graph nodes in `cat/pkg:avail_slot`: merge-bound versions, and the installed version when an `AlreadyInstalled` node holds the slot.
- #72 B3: a removal installs nothing into the slot.

## struct DisjunctionPreferenceArgs
- Track X Slice C (#242): the whole-graph views for the circular-self-dep gate below. `entries`/`queued` above are the group's own root scope (Portage's group-rooted `graph_db` match); the gate asks whether the owner's cp is in play *at all* (Portage has no self-exclusion -- the package is already graphed when its own `||` group pops, whichever root it sits in), so it reads these unscoped views instead. Same slices as `entries`/`queued` on every same-root call -- a strict no-op there.

## fn disjunction_preference
- The single probe closure `use_reduce_flat_disjunctive` calls for every `||` alternative -- Portage `dep_zapdeps`'s whole choice-bin classification (`dep_check.py` soft 449-523, 599-618) collapsed into one `AltPreference` rank. Shared by both of portuale's `||`-resolution call sites (the main New/Upgrade/Reinstall walk in `backtracking_resolve`, and the `--deep` AlreadyInstalled recursion in `enqueue_dependencies`) so a fix to one can never silently miss the other again (2026-09-11 review finding F1/F2: `enqueue_dependencies` had kept its own, unfixed copy of this closure after the fine `unsat_use_*` bins shipped).
- `constraints` is the `'backtrack`-loop's accumulated per-`cat/pkg` `runtime_pkg_mask` (empty at every non-disjunctive call site, a strict no-op) -- kept as the raw map rather than a `constraints_for(atom)` closure parameter (as first drafted): a `&dyn Fn(&str) -> &[String]` trait object needs the elided-lifetime signature `for<'a> Fn(&'a str) -> &'a [String]`, which a closure whose return actually borrows a captured map (not the input `&str`) can't satisfy without the borrow checker extending the map's borrow for the trait object's whole lifetime -- exactly the `slot_constraints` "does not live long enough" / "also borrowed as mutable" conflict this hit against the backtrack loop's later `slot_constraints.entry(...)` mutations.
- `self_cp` is the entry currently being resolved, for the circular-self-dep check; `circular_dependency` is the backtrack loop's map (owner `cat/pkg` -> circular-child records; empty on the first pass, a strict no-op) -- Portage `dep_zapdeps`' `circular_atom` demotion (`dep_check.py:673-691`), backlogs #216/#221. `root_deps_running_root` is the `--root-deps` feed-in (`None` = strict no-op). See `atom_currently_satisfiable`'s, `atom_all_use_unmasked`'s, `atom_cp_installed`'s and `atom_installed_in_slot_of`'s own notes for the per-predicate grounding; this function only sequences them the way Portage `dep_zapdeps`'s per-atom loop does.
- `circular_dependency` is backlog #221's `backtrack_infos["config"] ["circular_dependency"]` for this pass (empty on the first attempt): the previous attempt's cycle edges, parent `cat/pkg` to in-cycle children. An alternative with an atom matching one of `self_cp`'s recorded children -- Portage's `circular_atom` (`lib/portage/dep/dep_check.py:673-691`) -- ranks `other`, so the re-walk takes the branch that breaks the cycle (bugs 703440, 705986). The installed-walk call sites (`collect_unwalked_installed_blockers`, `enqueue_dependencies`) pass an empty map: Portage keys exact package nodes (`Package.__hash__ = Task.__hash__`, no `__eq__` override), so an installed parent -- never a merge-bound cycle node -- can never hit. The argument is node-identity keying, not cp-disjointness: portuale's cp-keying would over-demote on an installed-v1/merging-v2 cp collision Portage never exhibits (the blocker scan skips walked cps, but `enqueue_dependencies` parents are `AlreadyInstalled` entries whose cp may coincide with a merging cp).
- Portage's per-atom loop probes each atom's availability once and short-circuits (`if not avail_pkg: ... break`, soft 469): review finding F3 -- for an atom with no `[use]` block (the overwhelming majority), `atom.without_use` and `atom` are the same string, so Portage's separate `all_available`/`all_use_satisfied` probes would do byte-identical candidate-listing work twice. This loop computes each atom's availability once and reuses it for both facts when there is no `[use]` block to strip.
- Backlog #216: narrowed to Portage's actual pass-1 rule. Portage has no self-exclusion at all -- `_create_graph` adds the package to the digraph before walking its deps (`_add_pkg` at select time), so by the time the owner's own `||` group pops off `_dep_disjunctive_stack` the self-naming atom matches an in-graph node and the alternative ranks `preferred_in_graph` (bin 0): the cycle forms, then `_serialize_tasks` dead-ends and the `circular_dependency` map re-resolves it (see `BacktrackParams::circular_dependency`). Only a self atom matching nothing in-graph (and nothing installed) stays `Unsatisfiable` -- selecting it even as a last resort would let a package self-satisfy its own not-yet-resolved atom.
- Backlog #90 (S1)'s drain-state approximation (see `atoms_all_in_graph`), built lazily: only a self-naming atom needs it, and most alternatives have none.
- `all_available`'s per-atom probe: `mydbapi_match_pkgs(atom.without_use)` -- USE settings never affect `||` preference evaluation at this stage (dep_check.py soft 469).
- No `[use]` block: Portage's `if atom.use:` is false, so this atom trivially satisfies its own (nonexistent) use-deps -- reuse `avail` (`== true`) instead of re-probing the identical candidate list a second time (F3).
- #74 S1 (T10): Portage's `mydbapi_match_pkgs(atom)` in `dep_zapdeps` is `_dep_check_composite_db` over the graph/installed/ebuild dbs, and a *built* package's `[use]` deps are matched against its recorded vdb USE (`dbapi._match_use`'s `not self._use_mutable` branch, `portage/dbapi/__init__.py:298-327`) -- not against the tree candidate's profile-derived USE. Without this disjunct an alternative satisfied by an installed instance whose flag the current profile does not enable (`dev-lang/rust:1.94.1[llvm_slot_21]`, `dev-libs/altprov:1.1[flip]`) failed `all_use_satisfied`, was demoted to `unsat_use_*`, and lost bin 0 to the *uninstalled* slot's cp-level `Installed` -- Portage keeps the installed alternative (fixture `altprov`/`altconsumer` and the #74 host probe).
- Portage's bug-515584 probe: only evaluated for an atom whose own USE-match actually failed (dep_check.py soft 493-523).
- Portage's `other_installed`/`other_installed_some`/`other_installed_any_slot`/`other` classification (dep_check.py soft 715-724): reached when some atom has no tree candidate at all, even ignoring USE. Blockers are excluded from the fold entirely (Portage's own `if not atom.blocker:` guard), not merely vacuously satisfied.
- Portage's own fuzzy cp-level fallback (soft 720-724, bug 522652) -- plain `vardb.match(Atom(atom.cp))`, deliberately NOT `atom_cp_installed` (that helper's `virtual/` zero-cost exemption doesn't apply to this specific Portage code path).
- Portage demotes an otherwise-`all_available` choice straight to `other` (skipping bin 0/1 entirely) when `conflict_downgrade` or `installed_downgrade` fires (dep_check.py soft 634, bug 531656) -- backlog #35, see `alternative_downgrade_demoted`. `entries` is the resolver's live in-progress set at both call sites.
- Backlog #221: Portage's `circular_atom` demotion (`lib/portage/dep/dep_check.py:673-691`, bugs 703440, 705986): on a backtrack restart after a stranded merge-order walk, an alternative with an atom matching one of the resolving parent's recorded in-cycle children ranks `other`, so the re-walk takes the branch that breaks the cycle. Before the USE binning below because Portage demotes regardless of USE-satisfaction (`if circular_atom is not None: other.append(this_choice)` ahead of the `all_use_satisfied` split). Two exemptions straight from Portage: blocker atoms never match, and an atom satisfied by an installed version is not a circular dep (`if vardb.match(atom): continue`). The `parent.onlydeps` half of the `circular_atom` site (soft 649-671) stays a documented cut: `--onlydeps` is not threaded to this call depth, and its demotion (avoiding the direct self-cycle for `--onlydeps` arguments) is independent of this backtracking one.
- Choice bin 0 -- the single list `preferred_in_graph` / `preferred_installed` / `preferred_any_slot` all alias to when `graph_db` is present. An alternative every non-blocker atom of which is either already installed (`all_installed`, cp-level -- makes `virtual/wine`'s `|| ( wine-vanilla wine-staging … )` pick the installed `wine-staging`) OR already a merge-bound node this run (`all_in_graph`, `[use]`-checked -- makes `virtual/secret-service` pick the KDE-stack-pulled `kwallet-runtime[keyring]` over the first-listed `gnome-keyring`) ranks above one that would need a fresh merge.
- `!all_use_satisfied`: Portage's `unsat_use_*` bins -- the alternative exists but can only be merged with USE changes. First the bug-515584 gate (soft 705): if the flags that would have to change sit in `use.mask` / `use.force`, the choice is demoted to plain `other` (dep_check.py soft 705-706 -- no installed-variant sub-classification, unlike the `!all_available` branch above); otherwise it keeps the fine-bin ordering `unsat_use_in_graph` > `unsat_use_installed` > `unsat_use_non_installed`.
- Portage `unsat_use_installed`'s `all_installed_slots` (dep_check.py soft 599-607): cp-level installed is not enough -- the *slot* the best USE-ignoring candidate would pull in must also be installed (F4). A cp installed only in a different slot than this alternative targets still counts as `unsat_use_non_installed`.

## fn candidate_version
- Portage `mydbapi_match_pkgs(atom.without_use)[-1]`'s `version` field, parsed back out of a `highest_available_candidate_ignoring_use` candidate string (`"{cp}-{version}:{slot}/{sub_slot}::{repo}"`) -- the per-atom seed of a `||` alternative's own `cp_map` (`promote_tied_alternative`'s slice-2 in-bin ordering).

## fn promote_tied_alternative
- Portage `dep_zapdeps`'s in-bin upgrade-preference ordering pass (`dep_check.py` soft 738-802), plugged in as `use_reduce_flat_disjunctive`'s `tie_break` -- called only when 2+ alternatives tie at the best selectable `AltPreference` rank (`disjunction_preference`'s own return). Portage processes `choices[1:]` (by object identity, in original left-to-right order) against the CURRENT, being-mutated bin list, promoting `choice_1` in front of the first `choice_2` it beats and stopping the moment it would reach its own current position unpromoted; ported as a literal remove+insert over an `id`-tagged `Vec` (not simplified to a stable sort -- the promotion isn't transitive/associative in general, which is the whole point of Portage's own "sorting is done separately for each bin, so as not to interfere with the ordering ... specified in the ebuild" comment) so this matches Portage byte-for-byte rather than an approximation of it. Returns the WINNING alternative's original index into `alts` (`tie_break`'s own contract).
- Two of Portage's per-choice facts are deliberate, documented cuts (§2 of the design brief, `docs/history/022-agent-task-22-zapdeps.fable.md`): `minimize_slots` (only applies after `_overlap_dnf`'s DNF rewrite, which portuale doesn't do -- skipped entirely, matching the brief's own "cut it and document" fallback for slice 2) and `want_update` (`graph_interface.want_update_pkg`, needing the `--update`/`--newuse` "wanted" set threaded down to this call depth, which portuale doesn't do) -- pinned to Portage's own default (`False`), which only ever WIDENS when the `all_installed_slots` promotion applies (a true `want_update` on `choice_2` would SUPPRESS it): never picks a DIFFERENT winner than Portage would for a fixture where `want_update` is genuinely false, only potentially a fixture Portage would need `want_update` to decide -- none of which are targeted here.
- Also deliberately simplified vs `dep_check.py`'s own `cp_map` construction (soft 552-568, "bug 600346"): when an alternative's OWN atoms name the SAME `cp` more than once, Portage re-checks whether the higher-version candidate still satisfies every atom that already matched the previous one before overwriting `cp_map[cp]` (internal consistency); this always just keeps the higher version. A narrow cut -- it only differs from Portage when a single `||` alternative contains two atoms on the identical package where the higher version satisfies one atom but not the other, which the brief's own slice-2 fixtures don't exercise -- documented in `scope-backlog.md`.
- Portage `for choice_1 in choices[1:]:` -- a snapshot of every choice BUT the first, by identity, taken before any mutation.
- Reached choice_1's own current position without a promotion firing -- Portage's `if choice_1 is choice_2: break`.
- `pos2 < pos1` always (the scan breaks the moment it would reach `pos1`), so removing `pos1` first never shifts `pos2`.

## view threading (#580 10b)
- `DisjunctionPreferenceArgs`, `PromoteTiedAlternativeArgs` and `AlternativeDowngradeDemotedArgs` carry a **required** `view: OrView` (see `or_view.md`). Every probe of the choice bins goes through it: `Normal` calls the functions that were there before (`atom_currently_satisfiable`, `atom_matches_installed`, `atom_cp_installed`, `installed_candidates`, `atoms_all_in_graph`, `atom_installed_in_slot_of`, `highest_available_candidate_ignoring_use`) in the same order, so the forward walk is byte-identical; all seven walker sites and `tests_162.rs` pass `OrView::Normal`. `PostMerge` reads the package set after the merge (`PostMergeSet`).
- `alternative_downgrade_demoted` in `PostMerge`: `avail_pkg` is the highest set member that matches the atom and `highest_in_slot` the highest set member in its slot (DC:480-490, DC:531-541; `t9/views.md` item 6). An arm that only a replaced installed version satisfies is not in the set, so it leaves at DC:475 before either guard. The `queued` stand-in for a pending update is `Normal`-only: the scan has no queue.
- `[use]` deps in `PostMerge` (`OrView::use_satisfiable`): a graph node carries no USE state in the set, so the tree and the vdb stand in for it (same test as `Normal`). Approximation, reached only by an atom with a `[use]` block.

## struct OrSplit / fn split_or_groups
- #580 10b: a dependency string split into plain atoms and `||` groups (`split_tokens`, the walker's own splitter), USE already applied. `arms_outside(chosen)` is the arm texts a pick leaves out, minus any text that is also a plain atom (a plain atom is always a parent atom). Texts are the tokens of the string, which are the atoms `flat_dep_atoms` and the walker's `chosen` hold, so the comparison is exact.

## fn installed_consumer_or_selection
- #580 10b: the atoms `dep_zapdeps` selects from each `||` group of an installed consumer's dependency string, judged against the given view. The same `use_reduce_flat_disjunctive` call `resolve_installed_group` makes, with `promote_tied_alternative` as the tie-break and `disjunction_preference` as the rank; nothing is queued (`queued` empty), no `runtime_pkg_mask` constraints apply, the circular map is empty (an installed parent is never a merge-bound cycle node). A group that fails to flatten selects every arm (the conservative direction). Returns the **selected** arm texts, not the unselected set the plan sketched; `OrSplit::arms_outside` derives the unselected set.
- Used by the reverse-dependency scan (`rev_dep_or.rs`) with `PostMerge` only. A consumer the walk recursed into keeps the walker's recorded pick (`PassState::installed_walked`) and never reaches this function. Portage decides that pick at pop time against the graph as it stood then; the final `entries` differ.

## gate threading (#571)
- `AlternativeDowngradeDemotedArgs`, `DisjunctionPreferenceArgs` and `PromoteTiedAlternativeArgs` carry the gate; the `||`-preference tree lookups gate with it.
