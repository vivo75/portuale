# crates/portage-repo/src/resolve/rev_dep_or.rs
Which `||` arms of an installed consumer become parent atoms (#580 10b).

## struct OrScan
- The per-pass facts of `||` evaluation: whether Portage entered complete mode (`ResolveCtx::portage_complete`), the installed packages the walk recursed into with their picks (`PassState::installed_walked`), and the post-merge set (`PostMergeSet`).

## fn consumer_or_arms
- Portage evaluates an installed consumer's `||` once per dependency key, in the `_create_graph` call that pops it (`t9/views.md`). Three cases: the walk recursed into it (`Deep::recurses_at`, D:3834): the **walker's recorded pick**, whatever the complete-mode signal says (Portage chose it in `_filtered_trees` at pop time; the scan never recomputes it). Not recursed and Portage entered complete mode: `PostMerge` selection (`installed_consumer_or_selection`). Neither: `None`, the `||` is never evaluated and adds no parent atom.
- Edge: with `--ignore-world` the `--deep` re-walk has no seeds, but `portage_complete` does not depend on them (it is `req.complete` or the auto-detection over the pass's entries), so the edge noted in `t10b/mapping.md` section 2 does not arise.

## fn consumer_or_demotions
- The arm texts of one consumer's dependency string that are no parent atoms: the arms `dep_zapdeps` did not select, every arm when the `||` is not evaluated, and, for a `PostMerge` consumer, a selected arm that matches no installed package. Portage files such a dependency as initially unsatisfied (`_complete_graph`, D:8803-8809: `vardb.match_pkgs(dep.atom)` is empty) and never adds a pin; the site is the vdb test, not "matches nothing in the post-merge set" (T3's `=5.42*` matches the vdb and keeps its pin; T1's `=5.40*` does not). The plan named D:3438-3453, which is the narrower `_create_graph` site. A walker-recursed consumer's pick is not dropped: Portage's walk pulled it in.
- An arm that a sibling virtual leaked (see `sibling_virtual_leaks`) stays a parent atom, and goes through the same vdb test.
- Not done: a plain (non-`||`) atom that matches no installed package follows the same Portage rule and still pins here. Backlog item filed by 10b.

- #606 (2026-11-07): the vdb test above runs only for a selected arm the **graph** leaves unsatisfied (`!scan.post_merge.matches(atom)` first). Portage's `_complete_graph` pops only `_unsatisfied_deps` (D:8799-8809); a dependency a graph node satisfies is an ordinary parent atom. On Q19 the installed `virtual/p590vva` chooses `=5.44*` (the merge node) and this test used to demote it because no installed package matches, which dropped a conflict parent and gave 2/20 instead of 6/20.

## fn sibling_virtual_leaks
- Quirk Q19 (`LLM/portage-quirks.md`). `_expand_new_virtuals` runs one `dep_check` per virtual (DC:195-260); `_select_atoms_highest_available` then keeps a virtual's child atoms whose `id()` is in `chosen_atom_ids`, the ids of every atom chosen in the parent's call (D:6122-6133, D:6164-6167). Since atoms are interned (PD:100-130) equal atoms are one object, so a virtual keeps every atom of its own dependency string that equals an atom chosen by its parent or by a sibling virtual, whatever its own `||` picked. On the bed's `dev-perl/XML-Parser` cell nine installed perl virtuals that list `=5.44*` first still carry `=5.42*` through this.
- The pre-pass runs per evaluated parent (walked, or in scope under complete mode) and per dependency key: chosen = the parent's own `||` picks (until #604 also its plain atoms), plus, for each installed virtual it names, that virtual's plain atoms and picks (recorded when the virtual was walked, `PostMerge` otherwise; a virtual nothing evaluates chooses nothing). The leak of a virtual is its atoms that are in that set.
- Intern key (PD:1577-1595): atom text, EAPI, repo, USE and the unevaluated form. Until #604 only the text was compared and the parent's plain atoms counted; see `fn leak_one_parent (#604)` below for the corrected model.
- Fixture family `p590v*` (pmtest): `p590vpar-1` (installed, in world) expands `virtual/p590vva` (`=5.44*`, `=5.42*`) and `virtual/p590vvb` (`=5.42*`, `=5.38*`). Portage 3.0.83 lists both virtuals' `=5.42*` in the skip block (`t10b/captures/q19-order-portage.txt`). The test passes on HEAD too, by the installed-arm heuristic that this slice removes; it is the guard for the pre-pass.

## built-atom conflict (fix round)
- In `constraints_from_atom`: a built slot-operator atom of a PostMerge consumer (not walked, Portage complete mode) that the post-merge set cannot satisfy but an installed instance matches is a pin, verbatim with its sub-slot, so the 10a consumer-pin conflict forms (`_complete_graph`, D:8803-8834; T2). It applies only when the stripped constraint is not already broken by the merge (that case keeps its old pin text; `test_oracle_209`).
- Exception, D:8816-8832: when backtracking is allowed and `_want_installed_pkg(pkg)` is false, Portage tries `_slot_operator_update_probe` (a rebuild of the parent) instead of adding the instance, so no pin. `OrScan::want_installed_pkg` is D:7308-7330: true if `--exclude` matches the installed instance; true if `selective` is set (`--update`, `--newuse`, `--reinstall`, `--noreplace`, `--changed-deps`, `--changed-slot`, `--selective`, minus `--emptytree`: `create_depgraph_params.py:145-155`, `:175-180`, `:213-217`); otherwise true unless an argument atom matches the instance. Argument atoms are real atom matches against the installed instance's `cat/pkg-ver:slot/sub::repo`. The `force_reinstall` argument flag is not modelled (portuale has no such argument kind). `selective` is `ctx.selective && !ctx.empty` (`resolve_plan.rs` computes it from Portage's trigger flags). So with `--update` the pin forms: `--update dev-libs/p589bpull` is 4/20 like Portage.

## fn leak_one_parent (#604, 2026-11-07)
- The chosen set is keyed like Portage's atom intern key (PD:1577-1595), narrowed to text + EAPI: the parent's atoms carry its own EAPI (D:4367-4374, `eapi=pkg.eapi` even when installed; vdb `EAPI` for an installed parent, the ebuild's for a merge-bound one), an installed virtual's atoms none (DC:866-871, `eapi=None` for an installed `virt_parent`), a merge-bound virtual's its own. Repo, USE and the unevaluated form are not compared.
- Only `||` groups and virtual atoms share the disjunctive dep_check (`_queue_disjunctive_deps`, D:4872-4904), so the parent contributes only its `||` picks; its plain non-virtual atoms are dropped (the first version added them: on e604 the installed virtual got the parent's `=5.42*` and a residual pin printed a second conflict block).
- Consequence: installed virtuals leak only into each other; a merge-bound virtual takes the parent's `||` pick and its merge-bound siblings' atoms of the same EAPI.
- A virtual atom resolves to a merge-bound entry first (the composite db returns the graph's instance), then to the best installed match.
- Probes (Portage 3.0.83, `LLM/evidence/2026-11-06-sweep/604/`): shapes A-D of the `w604*` fixtures; scratch originals e604/e604b/e604c/e604d in `clusterB.md`.

## fn select_expansion_arms
- Backlog #572: Portage's choice bins for one new-style virtual `||` group, narrowed to the expansion question. Availability is per leg (tree-visible or installed-matched); the bug-531656 downgrade guard (`alternative_downgrade_demoted`, judged against the pass's entries) demotes an arm the graph already holds newer. Of the survivors an installed arm wins outright (it stays a parent atom/pin -- the Q19 shape); otherwise the first survivor in ebuild order is the fall-through arm to seed. dep_zapdeps' fuller ladder (USE bins, upgrade promotion) is deliberately not reproduced: an arm needing USE changes stays unseeded. A nested disjunction bails the whole group (`group_arms` returns `None`, still a documented cut). With `keep_demoted` the guard never fires and installed arms stay in the running: the first available arm returns even when demoted, the shape of Portage's *inner* `dep_zapdeps` return over an expanded virtual's own `||` (backlog #643; the outer choice demotes the conjunction as a unit instead).
- The walk's own `disjunction_preference` is deliberately NOT reused here: its bin-0 test (`cp_installed || all_in_graph`, fuzzy at cp level) ties an installed-matching arm with a tree-only arm and the upgrade-preferring tie-break then picks the tree arm -- which inverts Q19 (the installed `=5.42*` must win over tree-only `=5.44*`). The narrow rule keeps Portage's installed preference exact.
- Backlog #650: a demotion whose higher-in-slot node the pass's open slot conflict may yet skip commits no seed. The `conflicts` arg carries the committing pass's surviving `slot_conflicts`; a demoted arm whose demoter's `(cat, pkg, slot)` matches one is withheld (falls through to the installed/survivor logic, so an installed arm holds instead of seeding), and the feed re-commits on a later pass iff the verdict lands with the demoter surviving. Shape (b) of the plan, verdict-free: contest-at-commit stands in for skip-verdict (observationally equivalent -- a keep-verdict re-commits through the normal feed, a skip-verdict never re-demotes), so no provenance field and no queue/feed contract change. Portage ground: the withheld demotion is the transient filing (`dep_check.py:531-544`, filed `:634-635`); the installed hold is the post-skip bins' counterpart (`=perl-5.42*` `preferred_in_graph` `:636-655`, `~perl-core/*` `preferred_non_installed` `:599-616`). Returns `ExpansionArms` (`chosen` + per-arm `demoters`); the `PORTUALE_BT_TRACE=1` `SEED decline/commit` lines log demoter identity + verdict per seed. The commit-line `via` names the veto-level demoters only (demoted installed-matching arms, without which no seed would commit); per-arm identity for a withheld demotion lives on the decline line. Known limitation at #650 time (no oracle, not filed): a conflict that first appears on a later pass than the seed commit still merges from the queue -- closed by #651 (below): the committing pass's `conflicts` is empty there by construction (commit-before-conflict), so the withhold cannot fire and the fix moved to the consumer.
- Backlog #651: the committed seed carries its demotion input with it (`ExpansionSeed.demoters`, the `via` triples), and the consumer (`seed_queue`) skips a seed whose every recorded demoter is masked in the pass's backtrack state. Chose the consumer hook over a filing-time re-check because the settle pass already re-derives no seeds (the guard self-corrects against the post-skip entries) -- the stale commitment persists in `grown` and only the queue step can stop the merge. Latch stays owner+atom (first commit wins, demoters frozen); the skip verdict needs no new walk (exact `!=cpv` hit in `runtime_pkg_mask`, the `check_runtime_pkg_mask` precedent). Ruling-4 proxy stands: the open-conflict withhold above is untouched.

## fn virtual_expansion_seeds
- Backlog #572: Portage `dep_check.py:_expand_new_virtuals` without the inline splice. For each installed new-style virtual the walk pulled but did not walk (AlreadyInstalled entry with requirers): single visible tree ebuild at the installed version (multi-version choice stays a documented cut, backlog #644), tree RDEPEND read live with the tree effective USE, pure-`||` gate (a plain atom beside the group suppresses Portage's expansion -- S0 `probe572_mixed.py`; note the gate is conservative: valid-syntax mixed shapes show shape-dependent Portage behavior per `probe572_mixed_exact.py`, where a same-cp plain pin expands-with-failure and a different-cp plain pin suppresses-with-failure, so the gate skips all mixed virtuals), then `select_expansion_arms` against the pass's entries with `OrView::Normal` (the walk pop's view). Chosen arms matching an installed instance stay pins (never queued -- that inversion is what the S0 candidates 3/4 hit); chosen arms matching no installed package but a visible tree candidate, and not already merge-bound, become `((vcat, vpkg, vver), atom)` seeds for the RevDep feed. Latched in `grown.virtual_expansion_seeds`, so the feed terminates; gated on `!ctx.nodeps` like the walk's own dep-following, and on `!ctx.onlydeps` (the playground oracle merges nothing on the p02 shape under `--onlydeps`; a build-dep-pulled virtual needing its fall-through arm merged stays a documented cut).
- Backlog #651: the seed is an `ExpansionSeed` (`owner`, `atom`, `demoters` -- the `via` triples, i.e. the veto-level higher-in-slot nodes that demoted the installed arm). Latched by owner+atom (first commit wins, so a re-derived seed with different demoters is the same commitment and the feed still terminates). - Backlog #647: the single-version gate is gone; only the installed version's tree ebuild drives the feed (sibling tree versions never seed). ## fn virtual_expansion_seeds (seed hold, backlog #652 leg B)
- A seed with demoters is withheld (never committed, so nothing latches) when every demoter is walk-selected (not `demoter_request_pinned`) and an `independent_keeper` exists: `SEED hold ... keeper=... demoters=... walk-selected`. The pin arm then never rides even though the demoter survives and merges. Disjoint from #651 (demoter-masked skip, which needs committed seeds) and from M6b/M5 (versioned-request demoters stay pinned, seeds fire) and #646 (no demoter, no demotion).
- Backlog #656 leg (b) (Task 2): the hold above binds only for a requested keeper (`keeper_requested` — a walk-selected keeper is post-demoter by construction, so it never keeps and the fresh leg falls through; undecidable request text counts as requesting, fail closed). The feed returns an `ExpansionFeed` (seeds + hold add/drop delta), applied by `collect_feedback`; the queue contract is untouched (holds never ride).

## fn replacing_posture_holds
