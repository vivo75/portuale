# crates/portage-repo/src/resolve/feedback/mod.rs
Feedback hub: one pass's problems packaged into the next pass's backtrack input.

## enum MaskReason
- Phase C1 (023): why one `cat/pkg` version is masked on retry, mirroring Portage `backtracking.py`'s `runtime_pkg_mask[pkg][reason]` dict shape (one entry per masked version, reason-annotated). C1 only splits the storage -- readers still see the union (see `BacktrackParams::union_constraints`); C2's `Backtracker` consumes the reasons.
- `SlotConflict`: Portage `mask_info["slot conflict"]`: the masked version collided in its slot. `parents` are the pulling `((cat, pkg, ver), atom)` triples whose atom does NOT match the masked version (Portage's `conflict_atoms`, used by the bug-375573 discard check, which tests versioned parent packages -- hence the stored `ver`). Parent downgrades are `MissingDependency` masks on a later node, never empty-parent slot masks (C3 removed puller pre-masking).
- `MissingDependency`: Portage `mask_info["missing dependency"]`: the masked parent's subtree contained an unsatisfiable dep; `atom` is that dep's text (Portage also records the root; portuale resolves a single root).
- `SlotOperatorBuilt`: Portage `mask_info["slot_operator_mask_built"]` (backlog #212, v2 `#24c`): a non-installed binary whose built slot-operator dep cannot be satisfied the way it was built, recorded by `_slot_change_backtrack` (`depgraph.py:2383`), `_slot_operator_update_backtrack` (`:2427-2431`) and `_slot_operator_unsatisfied_backtrack` (`:2901-2903`) and enforced through the backtrack-config restart (`:5703-5712`, `resolver/backtracking.py::_feedback_config:237-242`, which files the mask under *both* `slot_operator_mask_built` *and* `runtime_pkg_mask`). Portage keys by package object, so the mask hides only the binary instance -- the same-version ebuild stays visible. Portuale's string readers match binary and ebuild at one `cpv:slot::repo` key, so the rendered `neg` carries a `[binary]` marker (`!=cat/pkg-ver[binary]`): every string-constraint reader skips marked entries (see `is_binary_only_mask` -- `match_from_list` ignores USE-deps, so the marker would otherwise match the ebuild too), and only the binary-candidate pool filter honours them (via `slot_operator_binary_masked_version`). Only the slot-change arm is ported (see `slot_operator_slot_change_probe`'s own notes); the update-probe and unsatisfied-probe arms have no portuale-visible diverging shape (both steer a parent the graph already replaces or fails on, so same-version binary-vs-ebuild steering is vacuous there).

## struct MaskEntry
- `neg` renders exactly as the string used to live in `slot_constraints`, so every reader that matches on it behaves identically. The masked version is recoverable without parsing: strip the `!=cat/pkg-` prefix formed from the bucket key (C2 does this when it needs per-cpv granularity).

## fn file_unsat_probe_results
- Files one `_slot_operator_unsatisfied_probe` result: replace-set seeds grow `slot_operator_replace_installed` (Portage `backtrack_infos["config"]["slot_operator_replace_installed"]`), binary parents become `[binary]`-marked `SlotOperatorBuilt` negatives (Portage `:2896-2903`). Returns true when anything grew -- the caller restarts with the same budget-free Config feedback the #211 scan returns. Single filing point for both probe sites (the missing-dep trigger arm, which Portage runs first per failing edge, and the no-trigger dead-end fallback); the replace set therefore expands in exactly one place here, and neither arm keeps restart bookkeeping of its own. Under `--usepkgonly` the binary result is discarded (Portage's `_iter_similar_available` yields binaries only, so no ebuild replacement exists -- see the trigger site).

## fn collect_feedback
- One pass's outcome in Portage `_backtrack_depgraph` terms. C2: the A3 overlay union lands in a working copy, not the live search state -- the driver applies the packaged effect through `Backtracker::feedback`. A3: fold this pass's overlay into the cross-pass accumulators before deciding. The old code wrote `bp` directly during the walk, so at this point `bp` already held everything; the union below reproduces that state exactly (idempotent per-flag insert with the same `bucket.get(f) != Some(want)` rule, `(atom, token)`-deduped record append, `|=` latch for the contradiction). Placed before the chain rather than in step 5: an earlier step (solvable growth, mask trial, breakage) may fire on the same pass that folded flips, and the retry must see them -- as it always did.
- #57 S1: the *dropped* half of the reverse-dependency scan (#54, documented at its enforcement site further down) is not feedback at all -- it is the input `assemble_result` renders the residual installed-instance block from. A pass that ends in slot-conflict mask feedback returns long before the scan's own site, so those pins never reached `grown` and a later `get_best_run` re-pass reported the collision without its installed consumers (the keeper-reachable triangle lost keeper's `=dev-libs/paired-1.0` parent line the moment the walk started recording that collision itself). Collected here for exactly that case -- a pass that found a slot conflict -- so the ordinary settle path pays for one scan, as it always did, not two.

## fn collect_feedback_inner (chain order)
- Scan once at the top (`scan_reverse_dependencies`); then: built-parent probe, circular dead end, ABI step, solvable conflicts, `file_consumer_pin_conflicts` (a contradicted installed-consumer pin joins the conflicts after the walker's, the ABI step runs again when one was filed), the slot-conflict backtrack (first conflict only, B:180-185), autounmask, missing dependency, the pin step (enforcement only), dead end, and the rest. Portage's order inside `_process_slot_conflicts` is solvable, ABI, backtrack (D:2131, D:2208-2218); portuale's walker order is unchanged.

## fn collect_feedback_inner (walk_stopped gate, #592)
- Portage's walk stops at an unsatisfied dependency (masked, USE-only, plain miss): `_add_dep` returns 0 (D:3535), `_create_graph` returns at once (D:3276-3280), `_resolve` returns before `altlist` (D:5691-5696), so `_process_slot_conflicts` (D:2123) never runs and no slot-conflict backtrack info is filed (D:2276-2279). `walk_stopped` = `pass_has_unsatisfied_dep(pass)` outside the `_complete_graph` re-walk (`allow_unsatisfied`, D:3419-3421); it skips the ABI, solvable-conflict and backtrack steps. A USE-only miss files no trigger (D:3488-3497), so with autounmask off the run ends with 0 tries and the miss reported. Evidence: `LLM/evidence/2026-10-26-575-residues/r1/s0.md`.
- Escapes not modelled (no known fixture needs them): optional or ignored build-time dep (D:3411-3413), installed parent past depth (D:3438-3453), healed built slot-op dep (D:3463-3470), installed parent already in `runtime_pkg_mask` (D:3478-3486). `step_built_parent_update_probe` is left ahead of the gate: no RED needed it. `file_consumer_pin_conflicts` keeps its own site rule (10a, P3) through the shared `pass_has_unsatisfied_dep`; it also needs the autounmask and pin-state terms, so it was not dropped.
- Known residues: #609 (conflicts Portage never sees past the stop point), #610 (empty repo name on a failed conflicted graph).

## fn fill_use_change_chains
- Phase A2 (023): the settle tail of `backtracking_resolve` -- rebuild passes, trace dump, merge-order sort, autounmask coalesce, residual conflicts, masked chains, `abort_outcome`, and the `GraphResult`. Residual conflicts (`slot_conflicts` extension) live here, not in `PassResult`: no `continue` follows them, so they cannot influence a retry.
- Backlog #205: USE changes start their chain at the forcing parent, not the first requirer. Portage `_get_dep_chain(pkg, unsatisfied_dependency=True)` (`depgraph.py:6257`) picks the parent whose atom the package still does not satisfy (`best_match_to_list`); when every parent is satisfied post-change -- the ordinary flip shape, the change fixed them all -- it walks the digraph parents preferring the last merge parent (bug #354747), i.e. the deepest forcing edge, then the argument. The flip site records its forcing owner in `AutounmaskChange::trigger`; the fill starts there when it is still a requirer, else the legacy first-requirer start stands (stale triggers after a masking retry, parent-flip rescues). (Keyword/license/mask changes keep the legacy start: Portage renders those without the unsatisfied filter -- see `fill_non_use_change_chains`.) The ascent above that start is unchanged (single-branch, first-requirer hops).
- Backlog #248: no requirer at all means the change sits on a start node (an argument package) -- Portage `_get_dep_chain` never prints the start node, so the fill passes `None` and `autounmask_dep_chain` renders just the `(argument)` line. (The old `.or(Some(own))` fallback started the walk at the change's own package, printing its `# required by <cpv>::<repo>` row first.)

## fn fill_non_use_change_chains
- Backlog #248: keyword/license/mask twin of `fill_use_change_chains`. Re-derive from the change's own atom: its left-hand `=<cpv>` / `>=<cpv>` names the package the change is on, whose requirer chain is what Portage `_get_dep_chain_as_comment` prints (Portage renders those without the unsatisfied filter, so no `trigger` narrowing here). Same no-start-node rule: a change on an argument package (no requirers) passes `None`, yielding just the `(argument)` line.
