# crates/portage-repo/src/use_flags.rs
Effective USE and USE mask/force resolution.

## fn effective_use_flags
- Portage `config.py::regenerate()` over the reversed `uvlist`; `USE_ORDER` default `env:pkg:conf:defaults:pkginternal:features:repo:env.d`.
- The "Config depth" slice (SCOPE_BACKLOG Part 2.C) split the earlier flat model ("IUSE seed, then `use_tokens`, then one flat `package.use` list") so each `package.use` source sits at its own Portage position.
- `repo` layer: `Config::repo_make_defaults_use` is Portage `_repo_make_defaults`: the main repo's applies to every package, an overlay's only to a candidate from that overlay.
- `iuse` defaults: found by comparing portuale's output against the installed system `emerge` on a Portage package (`media-video/ffmpeg`) -- REQUIRED_USE reported violated for a USE combination fully satisfied once IUSE's own `+`/`-` markers are honored (`ffmpeg`'s IUSE declares `+gpl`/`+dav1d`/`+drm`/etc., all silently defaulted to disabled before). Portage `config.py::_setup_pkg_iuse` (`lib/portage/package/ebuild/config.py`, ~line 1878) builds exactly this: `+flag` contributes a bare `flag` token, `-flag` contributes itself unchanged, a markerless `flag` contributes nothing -- stored under `self.configdict["pkginternal"]["USE"]`, a named `USE_ORDER` component (`lib/_emerge/actions.py`'s default). Confirmed by reading `config.py`'s `uvlist` construction (`for x in self["USE_ORDER"].split(":"): ...; self.uvlist.reverse()`): `pkginternal` (position 5 of 8) applies after `repo` but before `defaults`, `conf`, and `pkg` -- every one of those three can override an IUSE default; only `env`/`env.d` sit even lower/higher than portuale models.
- History: an earlier portuale unioned a flattened `base` here, which could only ever add a flag, never cancel an IUSE `+default` the way Portage `defaults`/`conf` genuinely can (Portage runs one continuous incremental walk, so a `-flag` in `defaults`/`conf` cancels an earlier `pkginternal` `+flag`). Replaying the ordered raw tokens closes that gap. `resolve_config` exposes both `use_flags` (flattened, still used for `--newuse` comparisons) and the per-layer token lists -- see `Config::use_tokens`'s doc. The dominant case (an IUSE default nothing else mentions) was already correct either way.
- `.stable.` variants: `Config::use_stable_force`/`use_stable_mask`/`package_use_stable_force`/`package_use_stable_mask` (`keywords`/`candidate_str` decide via `is_stable`) are ported from Portage `getUseMask`/`getUseForce`'s per-package (`pkg is not None`) branch, which appends the stable variant alongside the ordinary one at each step, but only when `stable` (see `is_stable`'s "would masking every keyword make this invisible" definition). Grouped here as force-then-mask, ordinary then stable, within each tier -- not Portage's per-profile-level interleaving, which the flat global accumulation already doesn't replicate either (see portage-profile's `package.use.mask`/`.force` doc for that established simplification, extended here).
- `Config::autounmask_use` is the top tier (after `env`, before force/mask) so the backtracking loop's in-progress `--autounmask-use` changes flow through (see that field's doc).
- Memo: a deep `emerge -pu` calls this ~20k times for a few hundred distinct candidates -- once in `is_visible`, then again for `keywords_accepted`, `is_stable`, `binpkg_respect_use_ok`, `use_flags_if_conditional`, the slot-op and changed-deps scans -- each rebuilding a ~200-entry set from scratch (the largest remaining cost after the `parse_atom` / config-bucket / move-chain / md5-cache fixes). `config` is captured by `use_context_fingerprint` (frozen digest plus live `autounmask_use`).
- Backlog #103: the per-call `HashSet` clone was ~14 M `String` clones on a deep `emerge -pu`; callers share the `Rc` and clone only where ownership is genuinely needed.

## fn use_context_fingerprint
- Backlog #105: the immutable part is frozen by `resolve_config` into `Config::use_context_base`, so production hashes that `u64` plus the live `autounmask_use` -- the one field the backtracking loop mutates (each tier / `flag_is_settable` probe adds an entry), hashed in full. ## fn effective_use_flags_uncached
- `repo` walk: Portage `regenerate()` walks `configdict["repo"]["USE"]` (make.defaults) ahead of that tier's package-scoped USE, stacking the candidate's repo's masters chain then the repo itself. Here an empty repo name means the main repo (which masters every overlay).
- `features` walk: Portage `configdict["features"]["USE"]` (`config.py` ~2043). `FEATURES=test` there is the make.conf/env equivalent of `--with-test-deps` (which only pulls the deps, for top-level atoms, without enabling the flag). Only `test` is modelled (Portage `feature_use` never holds anything else); `config.features_use` is `["test"]` or empty, derived from portuale's last-wins `FEATURES` scalar.
- `pkginternal` walk: matches Portage `config.py`'s own `if x.startswith("+"): ... elif x.startswith("-"): ...` (no `else` branch at all).
- `pkg` walk: Portage `_grab_pkg_env` fills `pkg_configdict`, then `config.py:2042-2048` appends `self.puse` after -- so user `package.use` wins over `package.env`.
- `env` walk: the process-environment `USE="..."` -- `USE="-X" emerge foo` overrides even user `package.use`. Tokens keep their `+`/`-` syntax.
- `autounmask_use` walk: Portage `_dynamic_config._needed_use_config_changes`, fed back into the backtracking loop by `_feedback_config`. A package under an autounmask flip is walked with the flipped flag so its `flag?`-gated deps appear.
- `_*` expansion: Portage `config.py` `setcpv` ~2242, with the `x not in usemask` guard. Deliberately not guarded on `k` being a `USE_EXPAND` name (Portage's `use_expand_split` check): a `_*`-suffixed token in portuale's USE set only ever originates from `USE_EXPAND` folding or `package.use`'s `USE_EXPAND` shorthand.
- Force/mask step: Portage `regenerate()`'s final two lines, `myflags.update(useforce)` then `myflags.difference_update(usemask)`, where `setcpv()` set `self.useforce`/`self.usemask` to the per-package `getUseForce(pkg)`/`getUseMask(pkg)`. A global `use.mask` `-flag` at a later profile level cancels an earlier level's `package.use.mask` entry, which the old flat `config.use_mask` union `package_use_mask` application could not.
- `_*` stripping: Portage strips every `_*`-suffixed token from `PORTAGE_USE` (`config.py` ~2260).

## fn specificity_ordered_flags
- Mirrors Portage `stack_lists(incremental=True)` over `[src0, src1, ...]` (`getUseMask`/`getUseForce`/`getPKeywords`).
- Portage `stack_lists` runs `ordered_by_atom_specificity` within each source before stacking, so same-file specific-before-general entries would reorder. Portuale takes plain file order (the same shortcut `apply_matching`/`package.use` takes) -- correct for every Portage profile, which lists general-before-specific by convention, and crucially for the `targets/*` pattern (a broad `cat/pkg -flag` in a child target un-masking a narrow `>=cat/pkg-N flag` from `base`), which a global specificity sort gets backwards.
- `seed` is empty for every `package.use.mask`/`.force` caller; `keywords_accepted` seeds it with `ACCEPT_KEYWORDS` (Portage `KeywordsManager.getMissingKeywords`'s `pgroups`).

## fn resolved_use_mask_or_force
- The `dev-libs/glib sysprof` / `arch/amd64 -sysprof` case: the flat `Config::use_mask` union `package_use_mask` union structurally cannot express the cancellation.
- Memo soundness: `use_mask_force_levels` is built once at config resolution and the backtracking loop mutates only `autounmask_use`, which this function never reads -- the fingerprint is included for defence in depth. 29,774 calls on the reference workload.
- Backlog #122: `category`/`package` are key components in their own right, not merely implied by `candidate_str` -- every current caller builds that string from these same two values, but the coupling was conventional rather than structural.

## fn forced_or_masked_flags_unfiltered
- Portage `depgraph.py:8264`/:8268-8270 passes `chain(myeb.use.force, myeb.use.mask)` / `chain(pkgsettings.useforce, pkgsettings.usemask)` to `_reinstall_for_flags` verbatim (`config.setcpv`'s `getUseForce(cpv_slot)`/`getUseMask(cpv_slot)`, `portage/package/ebuild/config.py:1973-1980`, never filters by the package's IUSE), and `:3151`'s `flags -= forced_flags` must forgive a profile-masked flag the new ebuild's IUSE has dropped (audit D1, `LLM/02.68-74-review-through-B5.md`; probed live against 3.0.82.2). The `forced_or_masked_flags` IUSE filter stays for the display paths that render `( … )` over a package's own IUSE.

## fn atom_specificity
- Portage's code has three extended-syntax tiers (`0` for a wildcard combined with `=*`, `-1` for one combined with a slot, `-2` for a bare one with neither); portuale's wildcard grammar has no slot or glob concept, so every wildcard entry falls into that third, lowest tier. Matches `portage-dep`'s v1 grammar scope.
