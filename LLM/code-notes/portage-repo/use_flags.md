# crates/portage-repo/src/use_flags.rs
Effective USE and USE mask/force resolution.

## fn effective_use_flags
- Portage `config.py::regenerate()` over the reversed `uvlist`; `USE_ORDER` default `env:pkg:conf:defaults:pkginternal:features:repo:env.d`.
- The "Config depth" slice (SCOPE_BACKLOG Part 2.C) split the earlier flat model ("IUSE seed, then `use_tokens`, then one flat `package.use` list") so each `package.use` source sits at its own Portage position.
- The walk, weakest layer first (original doc list):
  - `repo` -- each repo's `profiles/make.defaults` USE (`Config::repo_make_defaults_use`, Portage `_repo_make_defaults`: the main repo's applies to every package, an overlay's only to a candidate from that overlay), then every configured repo's own `profiles/package.use` (`Config::package_use_repo`) -- all *before* the IUSE defaults. The weakest layer portuale models.
  - `pkginternal` -- `iuse`'s own `+flag`/`-flag` default markers (see the `iuse` bullet below for the grounding).
  - `defaults` -- walked one profile chain level at a time (`Config::profile_use_layers`): that level's `make.defaults` USE, then that level's own `package.use`, before the next level (so a child profile's `make.defaults` can cancel a parent's `package.use`). Falls back to the flat `Config::use_tokens` + `Config::package_use` for a hand-built `Config`.
  - `conf` -- `make.conf` USE, then the `USE_EXPAND` folded values (`Config::conf_use_tokens`).
  - `pkg` -- `package.env`'s own `USE=` (`Config::package_env_use`), then the user-level `/etc/portage/package.use` (`Config::package_use_user`) on top. The strongest layer before the final `use.force`/`use.mask` step.
- Every layer is replayed via `apply_use_incremental` directly -- not a pre-flattened set unioned on top. The rest of the `env` layer (`$USE`, `package.env` non-USE vars) and `features`/`env.d` are documented cuts. Unlike `is_visible`'s mask/keywords checks (which only ever add to an accepted set), this can both add and remove flags, and does so per package -- a `package.use` entry never affects any other package's own resolution.
- `iuse` defaults: found by comparing portuale's output against the installed system `emerge` on a Portage package (`media-video/ffmpeg`) -- REQUIRED_USE reported violated for a USE combination fully satisfied once IUSE's own `+`/`-` markers are honored (`ffmpeg`'s IUSE declares `+gpl`/`+dav1d`/`+drm`/etc., all silently defaulted to disabled before). Portage `config.py::_setup_pkg_iuse` (`lib/portage/package/ebuild/config.py`, ~line 1878) builds exactly this: `+flag` contributes a bare `flag` token, `-flag` contributes itself unchanged, a markerless `flag` contributes nothing -- stored under `self.configdict["pkginternal"]["USE"]`, a named `USE_ORDER` component (`lib/_emerge/actions.py`'s default). Confirmed by reading `config.py`'s `uvlist` construction (`for x in self["USE_ORDER"].split(":"): ...; self.uvlist.reverse()`): `pkginternal` (position 5 of 8) applies after `repo` but before `defaults`, `conf`, and `pkg` -- every one of those three can override an IUSE default; only `env`/`env.d` sit even lower/higher than portuale models.
- History: an earlier portuale unioned a flattened `base` here, which could only ever add a flag, never cancel an IUSE `+default` the way Portage `defaults`/`conf` genuinely can (Portage runs one continuous incremental walk, so a `-flag` in `defaults`/`conf` cancels an earlier `pkginternal` `+flag`). Replaying the ordered raw tokens (rather than the flattened set) closes that gap: `portage_profile::resolve_config` exposes both `use_flags` (flattened, still used for `--newuse` comparisons) and the per-layer token lists -- see `Config::use_tokens`'s doc. The dominant case (an IUSE default nothing else mentions) was already correct either way.
- `.stable.` variants: `Config::use_stable_force`/`use_stable_mask`/`package_use_stable_force`/`package_use_stable_mask` (`keywords`/`candidate_str` decide via `is_stable`) are the `.stable.` variants of the global/per-package force/mask sources already applied above -- ported from Portage `getUseMask`/`getUseForce`'s per-package (`pkg is not None`) branch, which appends the stable variant alongside the ordinary one at each step, but only when `stable` (see `is_stable`'s "would masking every keyword make this invisible" definition). Grouped here as force-then-mask, ordinary then stable, within each tier -- not Portage's per-profile-level interleaving, which the flat global accumulation already doesn't replicate either (see portage-profile's `package.use.mask`/`.force` doc for that established simplification, extended here).
- Every layer above comes from `config`; only the candidate's own identity -- `iuse`, `keywords` (its raw `KEYWORDS`), `candidate_str` (`cat/pkg-ver:slot/sub::repo`), `category`, `package` -- is passed separately. `Config::autounmask_use` is applied as the top tier (after `env`, before `use.force`/`use.mask`) so the `'backtrack` loop's in-progress `--autounmask-use` changes flow through (see that field's doc).
- Memo: a deep `emerge -pu` calls this ~20k times for a few hundred distinct candidates -- once in `is_visible`, then again for `keywords_accepted`, `is_stable`, `binpkg_respect_use_ok`, `use_flags_if_conditional`, the slot-op and changed-deps scans -- each rebuilding a ~200-entry set from scratch (the largest remaining cost after the `parse_atom` / config-bucket / move-chain / md5-cache fixes). `config` is captured by `use_context_fingerprint` (frozen digest plus live `autounmask_use`).
- Backlog #103: the per-call `HashSet` clone was ~14 M `String` clones on a deep `emerge -pu`; callers share the `Rc` and clone only where ownership is genuinely needed.

## fn use_context_fingerprint
- Backlog #105: the immutable part is frozen by `resolve_config` into `Config::use_context_base`, so production hashes that `u64` plus the live `autounmask_use` -- the one field the backtracking loop mutates (each tier / `flag_is_settable` probe adds an entry), hashed in full, so a single added entry always changes the key. The production path hashes [`portage_profile::Config::use_context_base`]. A hand-built `Config` (tests, `Config::default()`) has no base and falls back to `portage_profile::use_context_base_fingerprint`, so an in-place edit of any context field is still seen.

## fn effective_use_flags_uncached
- `env.d` walk: Portage `configdict["env.d"]["USE"]`, from `/etc/profile.env`: the lowest `USE_ORDER` tier -- everything below overrides it. Practically always empty. See `Config::envd_use_tokens`.
- `repo` walk (Portage `configdict["repo"]`): each repo's own `profiles/make.defaults` USE (Portage `_repo_make_defaults`) first, then every configured repo's own `profiles/package.use` -- all *before* the ebuild's own IUSE defaults, the weakest layer portuale models. Portage `regenerate()` walks `configdict["repo"]["USE"]` (make.defaults) ahead of that tier's package-scoped USE, stacking the candidate's repo's masters chain then the repo itself. Here an entry with an empty repo name applies to every package (the main repo, which masters every overlay); a named entry applies only to a candidate from that repo. `candidate_str`'s `::<repo>` suffix names the candidate's repo.
- `features` walk: Portage `configdict["features"]["USE"]` (`config.py` ~2043). `FEATURES=test` appends `test` to this tier, so a package that declares `test` in IUSE builds with it enabled and its `test?( )` deps resolve -- the make.conf/env equivalent of `--with-test-deps` (which only pulls the deps, for top-level atoms, without enabling the flag). Sits between `repo` and `pkginternal` in `USE_ORDER`. Only `test` is modelled (Portage `feature_use` never holds anything else); `config.features_use` is `["test"]` or empty, derived from portuale's last-wins `FEATURES` scalar. A use-masked `test` is still dropped by the `use.mask` step below, exactly as Portage's own `regenerate()` filtering intends.
- `pkginternal` walk: matches Portage `config.py`'s own `if x.startswith("+"): ... elif x.startswith("-"): ...` (no `else` branch at all).
- `defaults` walk (Portage `configdict["defaults"]`): Portage `regenerate()` walks this tier one profile at a time -- that level's `make.defaults` USE, then that level's own `package.use`, before the next level -- so a child profile's `make.defaults USE="-foo"` can cancel a parent's `package.use foo`. `config.profile_use_layers` carries that per-level structure; the flat `config.use_tokens` + `config.package_use` are the fallback for a hand-built `Config` (a test helper) that never populated the layers.
- `conf` walk (Portage `configdict["conf"]`): `make.conf` USE, then the `USE_EXPAND`/`USE_EXPAND_UNPREFIXED` folded values.
- `pkg` walk (Portage `configdict["pkg"]`): `package.env`'s own `USE=` first, then the user-level `/etc/portage/package.use` on top. Portage `_grab_pkg_env` fills `pkg_configdict`, then `config.py:2042-2048` appends `self.puse` after -- so user `package.use` wins over `package.env`.
- `env` walk (Portage `configdict["env"]`, the highest `USE_ORDER` tier): the process-environment `USE="..."` -- `USE="-X" emerge foo` overrides even user `package.use`. Tokens keep their `+`/`-` incremental syntax. This is the strongest layer before the final `use.force`/`use.mask` step.
- `autounmask_use` walk: Portage `_dynamic_config._needed_use_config_changes`, fed back into the `'backtrack` loop by `_feedback_config`: a USE change the resolver has already decided is needed to make the graph resolve. Applied after `env`, before `use.force`/`use.mask`, as the top USE tier, so a package under an autounmask flip is walked with the flipped flag and its `flag?`-gated deps appear. Normally empty; see `Config::autounmask_use`.
- `_*` expansion: Portage `config.py` `setcpv` ~2242: once `package.use` has been applied, a `k_*` flag still in the set (from `USE="linguas_*"`, `LINGUAS="*"` folding, or a `package.use` `LINGUAS: *` shorthand) means "enable every `k_<x>` flag declared in THIS candidate's own `IUSE`" -- the per-package expansion the IUSE-blind global config layer can't do. Any masked `k_<x>` is dropped again by the `use.mask` steps below, exactly as Portage's `x not in usemask` guard intends. Deliberately NOT guarded on `k` actually being a `USE_EXPAND` variable name (Portage's `use_expand_split` check): a `_*`-suffixed token in portuale's USE set only ever originates from `USE_EXPAND` folding or `package.use`'s own `USE_EXPAND` shorthand.
- Force/mask step: Portage `regenerate()`'s final two lines, `myflags.update(useforce)` then `myflags.difference_update(usemask)`, where `setcpv()` set `self.useforce`/`self.usemask` to the per-package `getUseForce(pkg)`/`getUseMask(pkg)`. A global `use.mask` `-flag` at a later profile level cancels an earlier level's `package.use.mask` entry, which the old flat `config.use_mask` union `package_use_mask` application could not.
- `_*` stripping: the `k_*` pseudo-flags themselves are not real USE flags -- Portage strips every `_*`-suffixed token from `PORTAGE_USE` (`config.py` ~2260) once they've done their expansion job above.

## fn specificity_ordered_flags
- Computes the final per-candidate flag set from `entries` (raw `package.use.mask`/`.force`/`package.accept_keywords` `(atom, tokens)` pairs, already in profile-chain / source order): filters to entries whose atom matches `candidate_str`, then applies each match's own tokens in **source order** via the same incremental `-flag`/`flag`/`+flag` semantics `package.use` itself uses (`apply_incremental`), onto `seed` -- so a `-flag` in a *later* (child) profile cancels a `flag` mask/force from an *earlier* (parent) one.
- Mirrors Portage `stack_lists(incremental=True)` over `[src0, src1, ...]` (`getUseMask`/`getUseForce`/`getPKeywords`).
- Portage `stack_lists` runs `ordered_by_atom_specificity` within each source before stacking, so same-file specific-before-general entries would reorder. Portuale takes plain file order (the same shortcut `apply_matching`/`package.use` takes) -- correct for every Portage profile, which lists general-before-specific by convention, and crucially for the `targets/*` pattern (a broad `cat/pkg -flag` in a child target un-masking a narrow `>=cat/pkg-N flag` from `base`), which a global specificity sort gets backwards.
- `seed` is empty for every `package.use.mask`/`.force` caller; `keywords_accepted` seeds it with `ACCEPT_KEYWORDS` (Portage `KeywordsManager.getMissingKeywords`'s `pgroups`).

## fn resolved_use_mask_or_force
- Portage `UseManager.getUseMask(pkg)` / `getUseForce(pkg)`: the four (or, for a non-stable candidate, two) sources stacked **interleaved per profile level** and then collapsed with one incremental `stack_lists` -- so a global `use.mask` `-flag` line at a later profile level cancels an earlier level's `package.use.mask` entry. Per level, in Portage's own order: global `use.mask`, global `use.stable.mask` (stable only), `package.use.mask` (atom-specificity ordered within the level via `specificity_ordered_flags`), `package.use.stable.mask` (stable only).
- The `dev-libs/glib sysprof` / `arch/amd64 -sysprof` case: the flat `Config::use_mask` union `package_use_mask` union structurally cannot express the cancellation.
- Memo soundness: `use_mask_force_levels` is built once at config resolution and the backtracking loop mutates only `autounmask_use`, which this function never reads -- the fingerprint is included for defence in depth. 29,774 calls on the reference workload.
- Backlog #122: `category`/`package` are key components in their own right, not merely implied by `candidate_str` -- every current caller builds that string from these same two values, but the coupling was conventional rather than structural.

## fn forced_or_masked_flags
- Portage `_display_use`'s own `self.forced_flags = pkg.use.force | pkg.use.mask` (fed to `map_to_use_expand(..., forced_flags=True)`), restricted to `iuse`'s own declared flags: the set of this candidate's IUSE flags that `emerge --pretend -v` wraps in `( … )` because they're force-enabled or mask-disabled and so not actually under the user's control. Built from the exact same `use.force`/`use.mask` + `package.use.force`/`.mask` (+ the stable variants when the candidate is stable) layering `effective_use_flags` already applies -- reusing `specificity_ordered_flags` so a more-specific `-flag` cancels a less-specific force/mask identically.

## fn forced_or_masked_flags_unfiltered
- Portage `depgraph.py:8264`/:8268-8270 passes `chain(myeb.use.force, myeb.use.mask)` / `chain(pkgsettings.useforce, pkgsettings.usemask)` to `_reinstall_for_flags` verbatim (`config.setcpv`'s `getUseForce(cpv_slot)`/`getUseMask(cpv_slot)`, `portage/package/ebuild/config.py:1973-1980`, never filters by the package's IUSE), and `:3151`'s `flags -= forced_flags` must forgive a profile-masked flag the new ebuild's IUSE has dropped (audit D1, `LLM/02.68-74-review-through-B5.md`; probed live against 3.0.82.2). The `forced_or_masked_flags` IUSE filter stays for the display paths that render `( … )` over a package's own IUSE.

## fn atom_specificity
- Full port of Portage `best_match_to_list`'s specificity ranking (dep:2796-2884): full operators as before; extended atoms rank below everything (`=*` 0, slotted −1, plain −2 — the code values, which differ from the docstring). Anything unparseable is −2. S3 parses entries with `allow_wildcard: true, allow_repo: Some(true)` so the extended tiers apply; before that every wildcard fell into −2 via the default `parse_atom` rejection.
