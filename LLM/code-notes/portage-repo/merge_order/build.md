# crates/portage-repo/src/merge_order/build.rs
Building the digraph and biasing it toward Portage's order.

## fn build_digraph
- Nodes are the entries themselves (portuale's own graph is already one node per resolved `cat/pkg` slot); edges come from `GraphEntry::deps`, which carries Portage's own per-key `DepPriority`. `required_by` supplies a fallback edge for any owner relationship the forward `deps` walk didn't record (a diamond dependency's second owner, a synthetic rebuild entry, an entry whose metadata was unreadable) so the new scheduler is never less constrained than the `required_by`-only one it replaces.
- `satisfied`: Portage's `mypriority.satisfied`: an installed package matching the atom, via the shared `edge_satisfied_with` rule.
- `edge_matches`: the per-entry candidate strings `edge_matches` narrows atoms against -- see `digraph_prelude` for the full Portage grounding.
- Ports Portage's `dep_zapdeps` (`dep_check.py`): a `|| ( … )` group resolves to one alternative, not all. The derivation lives in `suppressed_alt_edges` so the public `kept_alt_branches` used by the #76 wait predicate cannot drift from this internal use.
- Ports Portage's `_create_graph`: an explicit LIFO `dep_stack` seeded from the top-level atoms. A node is recorded into `.order` the moment its parent's dep string first names it (forward, before any recursion), then the last-pushed node is expanded first -- so each node's own direct children land as one contiguous forward-order run, but the deepest-declared sibling's subtree is numbered before its earlier siblings'.
- Ports Portage's `_create_graph`'s own two-stack outer loop (`depgraph.py:3254-3269`): the ordinary `_dep_stack` is drained completely, and only then is the last-queued disjunctive bundle popped off `_dep_disjunctive_stack` and expanded -- which pushes fresh nodes back onto `_dep_stack`, so the whole thing repeats. Each bundle is one dep key's worth of `|| ( … )` / `virtual/*` atoms (`_queue_disjunctive_deps` queues at most one per key, before that key's inline atoms are added).
- An entry this walk never reaches -- a synthetic slot-operator / `--rebuild-if-*` entry (no `deps` of its own), or an `--nodeps` run -- keeps its original array position, appended after every genuinely-discovered node.
- Edges: forward first, so `children` keeps Portage's own dep-key/atom order (which `asap_nodes` and the cycle harvester both read).
- The single package the atom resolves to -- shared with `pretend.rs::print_tree` through `resolved_dep_targets` (#82), so the ranking cannot drift between the scheduling graph and the tree display. `merge_bound_only = false`: Portage's scheduler digraph edges to nomerge nodes too.
- Ports Portage's `_add_pkg`: a direct self-edge is dropped unless it is an unsatisfied build-time dependency, "since otherwise it can skew the merge order calculation in an unwanted way" (`depgraph.py:3765-3770`).
- Fallback edges from `required_by` for owner relationships the forward walk has no `deps` entry for.
- #72 B3: a `Uninstall` removal's `required_by` names the blocker owner it removes for, which Portage orders the removal after (u1/u3: the owner's row, then `[uninstall]`). The generic fallback would add owner -> removal (removal first), so the dedicated pass below adds the reversed edge instead and this loop skips the removal. `add_edge(j, i)`: the owner is the removal's child, so the owner is selected first (Portage's `_serialize_tasks` defers every uninstall node until it is scheduled, `get_nodes` `depgraph.py:9539-9549`).
- `required_by` is keyed by `cat/pkg` only, so a multi-slot dependency hands every scheduled slot the same owner set. If the forward dep walk already gave this owner a real edge to another slot of `j`'s `cat/pkg`, that atom was slot-qualified and resolved elsewhere -- don't synthesize a fallback edge to this slot too (Portage resolves each atom to one package).
- Track X Slice C (#242): `required_by` is cp-keyed and root-blind, so one puller's cp fans out to every scheduled instance -- including a same-cp sibling in the other root that never pulled `j`. When the forward walk already edged `j` back to this owner, synthesising `i -> j` closes a two-node ring the walk never recorded (the g216 target `g216comp` edges to the running one; the fallback would edge the running one back, stranding the whole chain behind a phantom cycle). The forward direction is authoritative: a genuine relationship the forward walk missed has no edge either way. Never synthesise a two-cycle.

## fn prune_nomerge_roots
- Removes rootless *synthetic* installed nodes (indices `>= from`, `from = real_n`) to a fixpoint, then drops them from `order`. Portage's own prune runs before `_merge_order_bias` (`depgraph.py:9540-9548`); portuale keeps its displayed `AlreadyInstalled` resolver entries in the graph (its `--tree` / "already installed" rendering wants them after the dependencies they pull in), so only the synthetic closure nodes are removed here.

## fn post_prune_parent_count
- The bias key. Simulates Portage's nomerge-root prune on the alive flags (an installed node with zero surviving parents is removed, decrementing its children's counts, to a fixpoint) and returns the surviving parent counts. Portage calls `_merge_order_bias` on the pruned graph (`depgraph.py:9540-9548`, then `:9317-9350`), so this is the count its comparator sees.
- #601: before this, portuale counted every alive parent. `sys-kernel/linux-headers` kept its 7-parent set (including the rootless installed `sys-apps/iproute2` / `net-firewall/iptables`), outranking `app-arch/zstd` (7 post-prune, 5 raw); the `ignore_optional` pick then unblocked `sys-libs/libseccomp` one iteration before `net-libs/nghttp3`, swapping them at #10 of `-puvD @world`. Keeping the displayed entries in the graph is not fidelity-free: their parent counts are the bias input.
- Limitation: models only the `installed` branch of Portage's prune condition (`depgraph.py:9542`). Portage also drops non-`Package` and `node.onlydeps` roots; portuale's graph has neither today (no `DependencyArg` nodes, no `onlydeps` entries), so those branches have nothing to act on.

## fn deep_system_deps
- Ports Portage's `_emerge/_find_deep_system_runtime_deps.py`: every `@system`-set member in the graph, plus everything reachable from one by following only runtime-priority edges (`RDEPEND`/`IDEPEND`/`PDEPEND`; `DEPEND`/`BDEPEND` are dropped). Feeds `merge_order_bias`'s own "system deps first" tier -- Portage: "promote deep system runtime deps... for optimal leaf node selection".
- Known difference: this runs on the unpruned graph (it still sees the displayed installed roots), while Portage calls `_find_deep_system_runtime_deps(mygraph)` after the nomerge-root prune (`depgraph.py:9328`). Not observable in the #601 cell (the extra rows are portuale-only and outside the comparator's ordered set); if a future cell makes it matter, seed the walk from the post-prune alive set instead.

## fn merge_order_bias
- Ports Portage's `depgraph._merge_order_bias` (`depgraph.py:9317-9350`): re-sorts `mygraph.order` in place so that, among simultaneously-eligible leaves, `@system`-deep runtime deps come first and the rest go from highest to lowest post-nomerge-prune parent count ([`post_prune_parent_count`]). Portage's own uninstalls-last rule has nothing to apply to here (a `--pretend` merge graph has no uninstall nodes).
- `implicit_system_deps` is Portage's `myparams["implicit_system_deps"]` (`create_depgraph_params.py:120`, default on): `false` (Portage's `--implicit-system-deps=n`) takes Portage's own early return (`depgraph.py:9322`) and leaves discovery order alone.
- Stable sort, so a tie keeps discovery order -- Portage's own `cmp_sort_key` comparator returns 0 for a tie and `list.sort` is stable too.

## fn seed_toolchain_asap
- Ports Portage's `_serialize_tasks`' own libc / os-headers `asap_nodes` seeding (`depgraph.py:9608-9638`, bug #303567 / #328317): merge libc as early as possible -- almost every ebuild has an implicit build-time dependency on it that Portage strips (`strip_libc_deps`) and re-expresses as this ordering preference -- and pull an `os-headers` upgrade in first when there is one.
- Portage walks `_expand_virt_from_graph(root, virtual/libc)` -> the graphed `virtual/libc`'s own `RDEPEND` provider atoms -> `_package_tracker.match` -> the provider package, keeping only `pkg.operation == "merge"` (not already installed at that cpv). Portuale's equivalent: find the graphed `virtual/libc` / `virtual/os-headers` entry, take its `RDEPEND` (`key == 0`) provider `cat/pkg`s, and return the merge-bound entries with those `cp`s. `os-headers` providers first (bug #328317), then libc.
- Portage: `pkg.operation == "merge" and not vardb.cpv_exists(pkg.cpv)` -- a genuine new-version/upgrade merge, NOT a bare `[ebuild R]` reinstall at a cpv already in the vdb. A `@world` re-emerge where `virtual/libc` / `virtual/os-headers` just reinstall must not seed `asap`, or they front-load past dep-free `@system` leaves like `sys-devel/gnuconfig`.
- The virtual itself, if it is a genuine merge (Portage's `_package_tracker.match` returns it too).

## fn gather_deps
- Ports Portage's `_serialize_tasks`' `gather_deps`: the closure of `node` under `ig`, or `None` when it escapes `mergeable`. "Recursively gather a group of nodes that RDEPEND on eachother. This ensures that they are merged as a group and get their RDEPENDs satisfied as soon as possible."
