# crates/portage-repo/src/merge_order/select_nodes.rs
Choosing the next nodes to merge (Portage `_serialize_tasks`).

## fn select_nodes
- Ports Portage's `_serialize_tasks` selection loop over the biased graph; returns the merge order.
- The incremental leaf frontier (see `SerializeFrontier`): built once from the biased order, kept in sync at the one removal site below. `None` when `PORTAGE_SERIALIZE_FRONTIER_DISABLE` falls back to the plain scans.
- #142 S2 F4b: Portage's uninstall-scheduling dance (`depgraph.py`, `_validate_blockers` through `_serialize_tasks`): every uninstall task is ordered after its blocker owner (the validation edge — the owner is not a leaf while its removal is unscheduled), an empty selection round admits removals (edges reversed: the removal then waits on its owner), and a round mixing merges and admitted uninstalls takes the uninstalls first (`good_uninstalls`). Portuale files removals only for solved blockers (Portage's schedulable uninstalls) with the execution edge already in the graph, so the dance is virtualized as two leaf-selection rules instead of graph surgery (the frontier never sees an edge change): an owner of a live unadmitted removal waits (filtered out of every leaf set), and the first stuck round admits removals. No removal present: both rules are vacuous and selection is byte-identical to before.
- Waiting fires only for the merging arm — the anchor entry carrying the `Uninstall` row naming this removal. A nomerge-arm anchor (B0b/#77 A1: the blocked merge instance) never waits, exactly like Portage, whose validation edge runs owner-side.
- Static (removal, merging-arm owner) pairs; liveness is checked per round below.
- B1: one `MO_NODES` snapshot of the post-prune graph, so the aligner can name a membership difference (gtk:4 is alive=398 vs 395 at iteration 1) instead of only reporting the count.
- F4b: owners waiting on their unadmitted removal (the validation edge, virtualized). Recomputed per round: admission below lifts entries out of this set.
- #131 S1: an admitted removal waits on its owner in tree mode. Portage reverses the validation edge on admission (the removal then waits on its owner, `depgraph.py:9998-10020`); portuale's virtualization only had the owner-waits half above, which sufficed while tree-mode selection fed verdicts alone. The display order consumes the selection sequence, and without this half an admitted removal (u1's `samepkg` uninstall) schedules ahead of its owner where Portage schedules the owner first. An owner outside the graph (pruned) or already scheduled lifts the wait -- there is nothing to wait on. Tree-mode only: the flat caller keeps its standing batch behavior, pinned everywhere; porting the reversal flat is reorder work outside this phase. Termination is safe: the roots last-resort and the final fallback below ignore this set.
- Cycle search must not see waiting owners either (Portage's validation edge keeps them out of its leaf set), nor a removal that was never admitted (defensive: one is only a leaf once its owner is gone, which admission precedes).
- F4b: waiting owners never compete (Portage's validation edge keeps them out of the leaf set), and an unadmitted removal is only a leaf once its owner is gone — which admission below always precedes, so filter defensively all the same. #131 S1: an admitted removal waiting on its owner (see `admitted_waiting` above) never competes either.
- Portage: "Greedily pop all of these nodes since no relationship has been ignored." Portage additionally gates this on `not tree_mode`, because the batch "destroys --tree output" (`depgraph.py:9764-9777`). The flat caller (`tree == None`) keeps portuale's standing batch behavior; the #81 tree simulation passes `Some` and takes Portage's gate, popping one non-root node per round so the stuck branch below can fire -- and #131's `tree_display_order` consumes that one-at-a-time sequence as the `--tree` display list, exactly like Portage's `_ordered_tree_display` consumes the reversed tree-mode retlist.
- #142 S2 F4: "If there is a mixture of merges and uninstalls, do the uninstalls first" (`depgraph.py`, same selection-round block). Every removal reaching this filter is admitted (F4b admission runs before any owner it waits on can schedule), i.e. one of Portage's `scheduled_uninstalls` — bed blk0 cells schedule `[X-1, uninstall, blocks, ...]`; the blockerorderpkg T7 pin already expects post-owner placement.
- "For optimal merge order: only pop one node; removing a root node (node without a parent) will not produce a leaf node, so avoid it." Portage first prefers a node whose parent is itself an asap node.
- "We failed to find any asap nodes to merge, so ignore them for the next iteration."
- "Try to merge neglected medium_post deps as soon as possible if they're not satisfied by installed packages." -- Portage's `PDEPEND`-asap promotion, bug #180045.
- Backlog #81: the stuck branch (`depgraph.py:9998`), tree-mode only. When no leaf is selectable and replacement rows are still pending, Portage schedules an uninstall for the blocked package (`scheduled_uninstalls`, `:10190`) and reverses its edges so the blocked package merges on top of it; the solved blocker is appended when the blocked package is later selected (`:10351-10358`). It sits here -- after the cycle harvest and the PDEPEND promotion, before the roots-last-resort -- exactly like Portage's. The flat caller never takes it (`tree == None`).
- #142 S2 F4b admission: Portage's uninstall-scheduling round (`depgraph.py:9998-10020`, "An Uninstall task needs to be executed in order to avoid conflict if possible"). No merge node is selectable anywhere on the ladder or the cycle paths above, and a live unadmitted removal exists: admit the first in graph order (Portage admits one uninstall per stuck round — its min-parent_deps choice approximated here by graph order; single-removal runs are exact), reset the round state like Portage, and re-select. The admitted removal's owner stops waiting (the validation edge reversed); the execution edge already in the graph still orders the removal after it. Sits after the cycle harvest and before the roots last-resort, exactly like Portage's: a waiting owner must not be picked as a last-resort root while its removal is still unadmitted.
- Ports Portage's `_serialize_tasks` (`depgraph.py:10230-10231`): "Only select root nodes as a last resort. This case should only trigger when the graph is nearly empty and the only remaining nodes are isolated (no parents or children)." -- but it also catches parentless plain leaves the one-node-at-a-time scan above skipped (it only ever picks a node with parents, and once `asap` is non-empty its rung-`NONE` batch is disabled). Portage runs this before escalating to `drop_satisfied`, so a stub whose only dep is a satisfied-runtime edge is not freed early via `s_ignore_satisfied_runtime`.
- Same set the order scan collected (alive `None`-leaves), via the level-0 heap instead.
- Portage leaves `ignore_priority` at `None` here, so the `medium_post` PDEPEND-asap promotion above (gated on `ignore_priority is not None`) does not apply -- and it has already run for this iteration regardless.
- #131 S1: Portage selects `get_nodes()` here -- its `leaf_nodes()` order, i.e. graph order, not heap order (`depgraph.py:10230-10231`; p2b's round-2 batch is `[newpkg, p2bowner]` in graph order). The heap only collects the set; the sequence follows `g.order`.
- Portage raises `_unknown_internal_error` here (an unresolved blocker, or a cycle none of the `ignore_priority` rungs could break). Portuale reports a genuinely unbreakable cycle separately via `find_hard_cycles` and still has to produce a list either way, so it keeps going instead: prefer a node whose every remaining dependency is one the widest filter (`DepPrioritySatisfiedRange.ignore_medium`, i.e. everything except an unsatisfied build-time dep) would drop -- the same "break the cycle at a run-time edge" preference the pre-digraph implementation used -- and only fall back to plain bias order when even that finds nothing.
- Keep the frontier in sync at the loop's one removal site (Portage's `_FrontierDigraph.remove`); counts/edges are read off the adjacency as it stands.
- Backlog #81: selecting the blocked package while its uninstall is scheduled solves the blocker (Portage's `:10351-10358` appends it to the retlist here); selecting the synthetic uninstall itself discards it the same way (`myblocker_uninstalls.remove`). Either way the row's verdict is recorded once.
- `emerge --pretend --debug`: Portage's `depgraph.py:9917-9930`'s `\nruntime cycle digraph (<n> nodes):\n\n` + `debug_print()` of the induced subgraph, then `runtime cycle leaf: <pkg>` -- to stderr, once per relaxed cycle.
- "NOTE: This case should only be triggered when prefer_asap is True... select only one node here, so that merge order accounts for as many dependencies as possible."
