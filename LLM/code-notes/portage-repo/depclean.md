# crates/portage-repo/src/depclean.rs
depclean, prune and clean selection.

## struct DepcleanResult
- Portage `emerge --depclean`'s own removal list (`_calc_depclean` + `create_cleanlist`, no `args_set`).
- The graph edges: a package that is *only* a build-time dependency of a kept package is itself kept -- `emerge --depclean` will not remove something the tree still needs to rebuild what stays installed. Build-time keys are followed because Portage's "remove" mode sets `bdeps="auto"` (`create_depgraph_params(myopts, "remove")`, `create_depgraph_params.py:100-103`; `depgraph.py:4208-4213` discards them only with `--with-bdeps=n`). Removal walks resolve build deps against the root being cleaned (`depend_root = myroot`, `depgraph.py:4218-4219`), i.e. the same vdb, so portuale reads them from the same `<root>` vdb as the runtime keys.
- No-`args` roots: the installed packages `world_atoms` ∪ `system_atoms` match. **`args` given** (`emerge --depclean <atoms>`): Portage `_calc_depclean` plus `_complete_graph` in "remove" mode drop the world "selected" plain atoms entirely (the default `--deselect` behavior -- the named packages get removed *and* deselected) and make every installed package NOT matching an `args` atom a protected root. So here roots = `system_atoms` ∪ `{=cpv | installed, unmatched by args}`, and the cleanlist is just the `args`-matched packages none of those reach.
- `lib_protected_providers` path: Portage computes the tentative cleanlist, then (`actions.py:1356-1573`) runs a soname-linkage scan over `NEEDED.ELF.2` and, for any cleanlist package solely providing a library still needed by a *surviving* consumer, re-adds that provider (and its own dependencies -- Portage `_calc_depclean` re-adds it via `resolver._add_pkg` then `_complete_graph`). The caller owns the `NEEDED.ELF.2` linkage map (see `portuale`'s `needed_elf`): first call with `lib_protected_providers = &[]`, scan, then call again passing the packages found. Cleanlist, `required_count`, `kept_parents` and removal order are all recomputed consistently.
- Narrowings: a lib-protected provider is kept but, unlike Portage (which labels its reverse-dep entry with the link-level consumer), contributes no `--verbose` `kept_parents` line unless an ordinary dependency also reaches it.
- Result fields: already in Portage `_calc_depclean`'s own unmerge order (see `topological_removal_order`); `required_count` is Portage `req_pkg_count` (the `Required packages:` stat); `ordered` mirrors Portage `_unmerge_display`'s own `if not ordered:` regroup branch, `unmerge.py:459-474`; the caller is `run_depclean_pretend` / `run_prune_pretend`.
- `kept_parents`: Portage `create_cleanlist`'s `elif "--verbose": show_parents(pkg)` (`actions.py:1324`/`1331`). No-args covers all kept packages; args covers only the `args`-matched ones. Each `(package, parent_lines)` -- `parent_lines` already rendered and sorted the way `show_parents` emits them (`<parent> requires <atom>, <atom>` per line, lines sorted ascending, atoms within a line sorted by atom package-name descending). A kept package whose only parent is the internal protected-set (Portage `protected_set_name` filter) contributes no entry.

## fn topological_removal_order
- Portage `_calc_depclean`'s own unmerge-order pass (`actions.py:1591-1731`): build a digraph over the cleanlist where an edge `depender -> dep` exists whenever one cleanlist member satisfies another's `DEPEND` / `RDEPEND` / `BDEPEND` / `PDEPEND` / `IDEPEND` (flattened against the depender's own vdb `USE`), then topologically sort it so each package is unmerged *before* the packages it depends on.
- `deps[i]` = indices `j` such that `cleanlist[i]` depends on `cleanlist[j]`, i.e. `i` must be unmerged before `j`. `edge_prio[(i, j)]` = the highest `UnmergeDepPriority` seen for it.
- Returns `(ordered, cleanlist)`. With no edges at all (`len(graph.order) == len(graph.root_nodes())` in Portage), `ordered` is `false` and the input order (the `cat`/`pn`/version sort `depclean_cleanlist` already applied) is kept -- Portage `_unmerge_display` then does its own `cat/pn` grouping. With edges the order is Portage's `nodes.sort(reverse=True)` repeated pop. Rationale quoted from Portage: "to avoid breaking things that may need to run during pkg_prerm or pkg_postrm".
- Priority table (Portage `actions.py:1608-1622` + `UnmergeDepPriority.__int__`): `IDEPEND` 0, `RDEPEND` -2 (bumped to -1 for `slot_operator_built` -- `foo/bar:2/2=`, Portage `runtime_slot_op`), `PDEPEND` -3, `DEPEND`/`BDEPEND` -4 (a `DEPEND`/`BDEPEND` slot-op edge stays -4; `__int__` never bumps `buildtime_slot_op`). When one `(i, j)` edge comes from several keys, the highest wins (Portage `digraph`'s sorted `priorities[-1]`).
- The pop mirrors Portage `actions.py:1713-1727`: while any package still has an un-removed depender, emit all current true roots at once, cpv-descending; only with none (a genuine cycle) use the `ignore_priority_range` scan (`[-4, -3, -2, -1, 0]`), finding the packages whose every remaining incoming edge is `<= ignore_priority` and popping just the cpv-max node so the fewest ordering edges break. `ignore_priority == 0` always yields a node, so the loop terminates. Portage's `node_refcounts` pre-sort has no observable effect (every batch is re-sorted by cpv anyway), so it isn't reproduced.
- Still narrower than Portage `actions.py` in one spot: `flat_dep_atoms` keeps every `||` branch (Portage `_select_atoms` resolves to one), so a disjunctive dep can add a few extra ordering edges -- the conservative direction.

## fn render_show_parents
- Portage `show_parents`'s own per-package rendering (`actions.py:1274-1291`): group a kept package's recorded `(parent descriptor, atom)` edges by parent, render one `"<parent> requires <atom>, <atom>"` line each with the atoms sorted by atom package-name descending (`sorted(atoms, reverse=True, key=attrgetter("package"))`), then sort the lines. Dedupes identical `(parent, atom)` edges before rendering. Shared by `depclean_cleanlist` and `prune_cleanlist`.

## fn pprovided_matches
- `package.provided` (`pkgsettings.pprovideddict`): true when `atom_str`'s `cat/pkg` is listed and its constraint matches one of that cp's provided CPVs (Portage `portage.match_from_list(atom, pprovided)`, e.g. `depgraph.py:5497-5503` for a top-level target, `dep_check.py:1052` area for a dependency -- the same check the main resolver's own `pprovided_refs` logic performs).

## fn unresolved_runtime_deps
- Portage `_calc_depclean`'s `unresolved_deps()` (`actions.py:1137-1248` on the result field, `actions.py:1137-1245` on the narrowed check): `(atom, parent_cpv)` for every *kept* installed package's hard runtime dependency (`RDEPEND`/`PDEPEND`) that no installed package satisfies. Non-empty means Portage depclean/prune prints the `* Dependencies could not be completely resolved ...` block and exits 1 without removing anything -- the caller (`run_depclean_pretend` / `run_prune_pretend`) does exactly that. Sorted, deduped. See `unresolved_runtime_deps` for the narrowings.
- Portage `DEPEND`/`BDEPEND` are `buildtime` = SOFT and never trip the halt (only `runtime`/`runtime_post` do). The any-of resolution for a whole `||` group is out of scope. Portage relies on libc genuinely being installed (`find_libc_deps` -- what an installed `virtual/libc` pulls in; `actions.py:1196`); `strip_libc_deps`' premise is that implicit libc deps are noise, so a config/fixture without an installed libc must not spuriously halt.

## struct DepcleanCleanlistArgs
- `world_seeds` labels: `@selected` for a `world` file line, `@<name>` for a `world_sets` nested set.
- `deselect`: Portage `action_depclean`'s `deselect = myopts.get("--deselect") != "n"` (default `true`): in `args` mode, `if deselect:` empties the `@selected`/`world` set (`actions.py:1037`) so a named package that is *also* in `world` still gets removed. `--depclean <atoms> --deselect=n` keeps `world` as a protection root instead, so a world member named as an arg is kept. No effect without `args` (the `world` seeds are always used then).

## fn depclean_cleanlist
- `matches_atom`/`matched_by_args` shape: candidate strings per installed package, `parse_atom` + `match_from_list` filtered to the same cp.
- Portage `_dynamic_config._parent_atoms`: child key -> [(parent descriptor, atom)], where the parent descriptor is a cpv (a `Package` parent) or an `@set` label (a `SetArg` parent). Every dep that resolves to an installed package records an edge, whether or not it was the one that first pulled that package in.
- `package.provided`: a `@world`/`@system` seed atom this covers is intercepted before it ever becomes a graph root (Portage `_resolve`'s per-arg loop, `depgraph.py:5497-5503` -- `pprovided and match_from_list(atom, pprovided): ... continue`, *before* `_add_pkg`/`_select_package` ever run). It therefore never becomes a depclean protection root here either, even if an installed package of the same cpv happens to exist -- that's the Portage `-pc` advisory's "will be removed by depclean even if in world" case. See `pprovided_matches`.
- Kept/`kept_parents`/`unresolved` coverage: `show_parents` over kept packages cpv-sorted; `unresolved_deps()` over *every* kept package (Portage `_complete_graph`'s full required set); `required_count = reachable.len()`.

## fn prune_cleanlist
- Portage `emerge --prune`'s removal list (`_calc_depclean` with `action="prune"` -- `actions.py:1059-1110` plus `create_cleanlist`'s own prune branch, `:1334-1340`). `--prune` removes *superseded* installed versions: for every cp with more than one version installed, the non-highest versions, kept only if something still needs that exact old version.
- **Deliberately out** (matching `depclean_cleanlist`'s own cuts): `--prune --nodeps` (the obscure `_unmerge_display` prune branch that skips the closure entirely), the `--deselect` world-file rewrite (`--pretend` never writes it), and slot-operator rebuild edges.
- Portage seeds its `protected_set` with every installed cp as a bare `cp` atom (resolving to just the *highest* installed version), then additionally protects the highest version of every cp and every non-highest version an argument atom does not match. With no `args`, `args_set` auto-fills with every multi-version cp (`actions.py:1071-1075`); `emerge --prune <atom>` uses those atoms as `args_set` instead.
- `lib_protected_providers` and `package.provided` params mirror `depclean_cleanlist`'s.

## fn prune_nodeps_selection
- Portage `emerge --prune --nodeps`'s own selection (`unmerge.py:245-272`, the `_unmerge_display` prune branch that `--nodeps` routes to *instead of* `_calc_depclean` -- `actions.py:2684`). No dependency check at all: for every cp with more than one version matched, protect the "best" version and select every other for removal.
- **`args` given**: each atom's `vardb.match` set; the best/rest split is over *that* set (so `--prune --nodeps '<cat/pkg-3'` keeps `pkg-2` even if `pkg-3` is also installed). A cp matched by several atoms appears once -- the `selected` sets unioned, `best` taken over the union (Portage `_unmerge_display`'s own `if not ordered:` regroup).

## fn clean_selection
- Portage `emerge --clean`'s own selection (`unmerge.py:274-293`, the `unmerge_action == "clean"` branch): like `--prune --nodeps` but **per slot** -- for every `(cp, slot)`, keep only the highest version, select every older one for removal. `args` given: the best/rest split is over the union of the matched sets, grouped by `(cp, slot)`; `args` empty (`emerge --clean` alone): every installed `(cp, slot)` (Portage `vardb.cp_all()` -> `cp_list`). Collapse back to one entry per cp (Portage `_unmerge_display` regroups the `pkgmap` by `mykey` = cp), unioning the per-slot removal sets. Same `COUNTER`-tiebreak narrowing as `prune_nodeps_selection` (portuale's single-instance-per-slot fixtures never hit it), and no `sys-apps/portage` self-skip (Portage `unmerge.py:368`: the self-skip is explicitly *not* applied for `--clean`).

## fn strip_slot_operator_one
- Guards: a plain `:=` (no slot), a `:2` / `:2/3` (no operator), or a `:2*` is left untouched, matching Portage `strip_slots`'s `x.slot_operator == "=" and x.slot is not None` guard (`lib/portage/dep/_slot_operator.py:11`). `::repo` uses `::` and use-deps live inside `[...]`, so a single leftmost replacement is safe.

## struct CycleSuggestion
- Portage `show_cycle_suggestion` (`_emerge/actions.py`, `_calc_depclean`, commit `96c320967`, bug 346351, backlog #508): one notice per kept, `args`-matched package whose strongly connected component has at least two members and no member is recorded as a parent from outside the component. `members` holds the package and the rest of its component.
- `DepcleanResult.cycle_suggestions` is empty without `args` and for `--prune` (Portage only calls `show_cycle_suggestion` in the `action == "depclean"` branch with `args_set`).

## fn cycle_suggestions
- Portage `show_cycle_suggestion` (`actions.py`, `_calc_depclean`, `96c320967`). Graph = the reachable installed packages; edges = one per recorded parent (`parent_atoms`), `parent -> child`, for package parents only. Portage's digraph has the same edges for resolved deps.
- Outside-parent rule: a member with any recorded parent edge whose label is not a member suppresses the notice. Portage's check skips only the protected set (`____depclean_protected_set____`), and portuale records no edge from the protected roots, so the rule reduces to "any parent outside the component". Parents that do count: a protected package outside the cycle (oracle `07-pair-protected-parent`) and the `@system` set (oracle `12-system-cycle`: `_parent_atoms` holds `('system', ...)`).
- `@selected` / `world` parents do not count, because portuale drops world seeds in `args` mode (`deselect` default), matching Portage, where `_parent_atoms` never holds the `world` set in `args` mode. Oracles `06-pair-world-parent`, `10-pair-world-member-b`. Portage quirk: LLM/portage-quirks.md Q7.
- Self-loops are not members (`len(members) < 2`), oracle-free but matches `show_cycle_suggestion`'s early return.

## fn print_cycle_suggestion (portuale)
- Portage `show_cycle_suggestion`'s text (`96c320967`): the two-line sentence, then `emerge --depclean` with every member as `=cpv`, sorted as strings (`sorted("=" + member.cpv ...)`), then a blank line. Written to stdout (Portage `writemsg_stdout`), no colour.
