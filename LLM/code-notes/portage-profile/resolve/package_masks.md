# crates/portage-profile/src/resolve/package_masks.rs
`package.mask`/`package.unmask` and `package.accept_keywords`.

## fn fold_package_masks_and_keywords
- Repo-level scoping: Portage `append_repo` scopes EVERY repo's own repo-level package.mask/.unmask, including the main repo's -- confirmed by reading MaskManager.py's `repo_pkgmasklines`/`repo_pkgunmasklines` loop (`for repo in repositories.repos_with_profiles()`, unconditional). Portuale previously left the main repo's entries unscoped, a genuine documented gap: an identically-named package.mask atom from main would incorrectly also mask a same-named-but-different overlay package no mask file mentions. The profile-chain (`for level in &chain`) and user-level entries are NOT the same thing: Portage's `profile_pkgmasklines`/`user_pkgmasklines` never get `append_repo`'d, only repo-level ones do.
- Masters: `repo_masters` comes from Portage `repos.conf`'s `masters = name1 name2 ...` key (`portage_repo::find_repos`'s `RepoConfig::masters` doc comment has the full grounding, `config.py:1229-1260`). An overlay's package.mask stacks on top of every declared master's mask in declared order before `::reponame` scoping. No `repo_masters` entry (every pre-existing test call site) falls back to the "main repo alone" default, so nothing already tested changes. Simplified from Portage `MaskManager.py`'s per-master `stack_lists` (which stacks each master separately then concatenates, so a `-atom` removal's unmatched-master warning attributes correctly) to one flat `stack_mask_lines` call -- identical final masked-atom set for the common case; no fixture exercises the exotic two-masters-removal case.
- package.unmask deliberately gets NO masters treatment -- confirmed reading both MaskManager.py loops side by side: the mask loop stacks each master's lines first, the unmask loop only ever stacks a repo's own lines (`stack_lists([repo_lines], incremental=1, ...)`, no masters iteration). A Portage asymmetry, not a portuale simplification.
- package.accept_keywords: profile-chain in chain order, then user-level -- Portage `KeywordsManager.getPKeywords` iterates per-profile-level dicts first, then the user one, extending the same accumulating "extra accepted keywords" list each time. No `-atom` removal exists for this file (unlike package.mask), so flat concatenation-then-parse equals parsing each source separately. No repo-level source exists in Portage at all (unlike package.mask's repo-level file) -- confirmed by reading `KeywordsManager.__init__`, which never reads a repo-location path for package.accept_keywords or its package.keywords alias.
- Bare-atom defaults: Portage `accept_keywords_defaults`'s implicit meaning (`~` plus every plain non-`~`/`-`-prefixed token in the final global ACCEPT_KEYWORDS), computed against `config.accept_keywords` as fully resolved by that point -- matching what Portage computes it from at both call sites (`KeywordsManager.__init__`'s `global_accept_keywords` parameter, `getPKeywords`'s `pgroups`, both already-resolved global ACCEPT_KEYWORDS by then). Every profile-level/make.conf ACCEPT_KEYWORDS contribution above already folded in, exactly matching what Portage computes it from. Sorted only for deterministic test assertions; downstream `specificity_ordered_flags` folds into a `HashSet`, so fold order was never semantically significant.
