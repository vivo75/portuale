# crates/portage-profile/src/lib.rs
Profile-chain + make.conf + package.* resolution for USE, ACCEPT_KEYWORDS and visibility.

## module
- Origin: the depgraph/config-resolution follow-up work (see `LLM/agent-context.md`; full scope writeup in `LLM/what-this-proves.md`). Replaced the base `emerge --pretend` slice's hardcoded `ACCEPT_KEYWORDS="amd64"`/`USE=""` with the inherited-chain + `make.conf` + per-package-override mechanism.
- Cross-repo `parent` references resolve via `expand_parent_colon`/`repo_containing`, gated on the current profile node's own repo declaring `profile-formats = portage-2` in `metadata/layout.conf` (Portage `_config/LocationsManager.py:47`/`259`'s `_allow_parent_colon` frozenset). `resolve_config` reads each repo's `layout.conf` directly (`repo_profile_formats`) rather than threading a param through every call site. Portage's EAPI-conditional `profile-formats` default when the key is absent (`portage-1`/`portage-1-compat`) is not modeled; absent means "no `portage-2`".
- ARCH-based KEYWORDS-format validation is out of scope. Wildcard `_*` IUSE-aware expansion (e.g. `linguas_*`) lives in `portage_repo::effective_use_flags` (it needs a specific candidate's own IUSE, which this global config layer doesn't have). History: `USE_EXPAND` itself and `package.use`'s `USE_EXPAND`-prefix shorthand used to be listed as cuts here too; follow-ups closed both (see the `USE_EXPAND` notes under `Config::use_expand`).
- Portage `USE_ORDER` is `env:pkg:conf:defaults:pkginternal:features:repo:env.d`; every tier is modeled (see the `Config` field notes for which field carries which tier).
- `package.mask`/`.unmask`: an overlay's own `package.mask` (only `package.mask`; Portage never consults masters for `package.unmask`) stacks with its implicit `masters` default (the main repo alone, since portuale doesn't parse an explicit `masters =` repos.conf key). Still out of scope: eclass inheritance via `masters`, and an explicit `masters =` override/multi-master chain.
- `package.accept_keywords`: mirrors Portage `KeywordsManager.getPKeywords` exactly; confirmed by reading it that no repo-level source exists at all (unlike `package.mask`). No `-atom` removal exists either, so every matching source's keyword tokens are just unioned (see `is_visible` in `portage-repo`).
- `package.use`: the "Config depth" slice (SCOPE_BACKLOG Part 2.C) replaced the earlier flat "one incremental list regardless of source" model with one `Config` field per source at its own Portage `USE_ORDER` position. Still applied per package, not globally: a matching entry's tokens layer on with the same incremental semantics as `USE` itself, scoped to the package being resolved (see `effective_use_flags` for the full walk and `resolve_pretend_graph` for where it is driven; it needs the candidate's SLOT for slotted entries, which exists only at that later layer).
- `use.mask`/`use.force`: confirmed by reading `UseManager.getUseMask`/`getUseForce`'s `pkg=None` case (the one Portage `config.py`'s `regenerate()` calls for the global `USE` value) that it returns `stack_lists(self._usemask_list/self._useforce_list, incremental=True)` directly, never touching a repo-level or per-package source there; those exist only on the per-package path (`pkg` not `None`). An earlier portuale version folded these into `use_flags`, which was wrong.
- The stable-vs-`~arch` KEYWORDS distinction named as a cut when the `package.use.mask`/`.force` notes were written is now stale: closed by the `use.stable.mask`/`.force` follow-up (see `Config::use_stable_force`).
- USE quirk, deliberately preserved from `lib/portage/package/ebuild/config.py` (see the comment above its `expand_map.pop("USE", None)`): in the flat single-set consumption model portuale uses (no package.use interaction, unlike the Portage bug this quirk guards against), the scenario usually doesn't change the final set of enabled flags; ported anyway for fidelity with the Portage algorithm since it is cheap.
- Profile-chain + make.conf + package.mask/.unmask/.accept_keywords resolution for Portage USE/ACCEPT_KEYWORDS/visibility (see LLM/agent-context.md's depgraph/config-resolution follow-up work, and LLM/what-this-proves.md for the full scope writeup). Replaces the base `emerge --pretend` slice's hardcoded `ACCEPT_KEYWORDS="amd64"`/`USE=""` with Portage's mechanism: a profile inheritance chain (`make.profile` -> `parent` files) plus `/etc/portage/make.conf`, each level's `make.defaults` contributing incremental USE/ACCEPT_KEYWORDS tokens, plus per-package overrides from `/etc/portage/package.mask`, `package.unmask`, and `package.accept_keywords`.

  - `package.use` is stacked from all four Portage sources (repo-level, every profile level, the user profile at `eapi=None` with wildcards, user-level -- #341 S6 added the user-profile source and validates every user-side line), and -- as of the "Config depth" slice (SCOPE_BACKLOG Part 2.C) -- each source now lands in its own `Config` field at its own Portage `USE_ORDER` position, instead of the earlier flat "one incremental list regardless of source" model:
  * repo-level (`<repo>/profiles/package.use`, every configured repo, overlays `::repo`-scoped via `scope_repo_package_use_lines`) -> `Config::package_use_repo`, Portage `configdict["repo"]` -- applied *before* the ebuild's own IUSE `+`/`-` defaults, the weakest USE layer portuale models.
  * every profile level's own `package.use` (chain order) -> `Config::profile_use_layers`, Portage `configdict["defaults"]` -- the `defaults` tier is walked one profile at a time, each level's `make.defaults` USE then that level's own `package.use`, before the next level (Portage `regenerate()`), so a child profile's `make.defaults` can cancel a parent's `package.use`. Applied after the `repo` tier, *before* `make.conf`. (`Config::package_use` still holds the flat all-levels-as-one-group list, kept only as the fallback for a hand-built `Config`.)
  * `package.env`'s own `USE=` (`Config::package_env_use`, from `/etc/portage/package.env` -> `/etc/portage/env/<name>` files) -> Portage `configdict["pkg"]` via `_grab_pkg_env`, applied first in the `pkg` layer.
  * user-level (`/etc/portage/package.use`) -> `Config::package_use_user`, Portage `configdict["pkg"]` -- applied after `make.conf` and after `package.env` (Portage appends `self.puse` on top of the `_grab_pkg_env` result), the strongest USE layer before the final `use.force`/`use.mask` step. Each repo's top-level `profiles/make.defaults` USE (Portage `_repo_make_defaults`) is folded into the `repo` layer too, ahead of repo `package.use` (`Config::repo_make_defaults_use`) -- the main repo's applies to every package, an overlay's only to a candidate from that overlay. The `env.d` layer (`Config::envd_use_tokens`, from `/etc/profile.env`) is folded in below everything, as the lowest tier. Each source is still purely additive within itself (no `-atom` removal exists for this file -- see `parse_package_use_lines`), and still applied per package (not globally): a matching entry's tokens are layered on with the same incremental semantics as `USE` itself (see `apply_incremental`), scoped to the one package being resolved -- see `portage-repo::effective_use_flags` for the full per-package `USE_ORDER` walk and `resolve_pretend_graph` for where it is driven (it needs the candidate's SLOT to match slotted entries, which only exists at that later, repo-aware layer).
  - `packages` (`@system`'s Portage source -- `PackagesSystemSet` in `lib/portage/_sets/profiles.py`) IS now read: every profile level's own `<level>/packages` file, in chain order, stacked with the identical `stack_lists(incremental=1)` semantics `package.mask` already ports (see `stack_mask_lines`) -- confirmed by reading `PackagesSystemSet.load`, which calls the exact same Portage `stack_lists` function `MaskManager` does, on the *raw* lines (`*foo` and plain `foo` alike -- `-foo` only ever removes an earlier exact-text `foo`, never a `*foo`, same plain string equality `stack_mask_lines` already uses). Only *after* stacking does Portage keep the subset starting with `*` (stripping the `*`) as the actual `@system` atom list -- every other stacked line is a "this package is known to the profile but not part of the base system" hint with no `@system`-set meaning of its own, so `system_packages` applies that same post-stack filter. **Partly stale since #341 S6**: the user profile's `packages` stacks last too (Portage's last profile node, `eapi=None`, no wildcards, config.py:655-666); what remains true is that no *repo-level* source exists for this file (only profile nodes, never `config_root`), unlike `package.mask`'s repo-level `profiles/package.mask`. Every user-side line now validates with Portage's per-file flags (`--- Invalid atom` warnings via `atom_lines`).
  - `use.mask`/`use.force` (global USE forcing) ARE now read: every profile level's own `<level>/use.mask`/`use.force` file, in chain order, stacked with the identical `stack_lists(incremental=True)` semantics `package.mask`/`packages` already port (see `stack_mask_lines`) -- confirmed by reading `UseManager. getUseMask`/`getUseForce`'s own `pkg=None` case, the one Portage `config.py`'s `regenerate()` actually calls to build the *global* `USE` value portuale's flat model corresponds to: it returns `stack_lists(self._usemask_list/self._useforce_list, incremental=True)` directly, never touching a repo-level or per-package source at all here -- those only exist on the *per-package* path (`pkg` not `None`), see the `package.use.mask`/`.force` bullet further below for that follow-up. Deliberately NOT folded into `use_flags` here at all (an earlier version of portuale did, which was wrong): Portage `regenerate()` applies `self.useforce`/`self.usemask` (which `setcpv()` sets to the *per-package* `getUseForce(pkg)`/`getUseMask(pkg)` -- global `use.force`/`use.mask` combined with the atom-scoped `package.use.force`/`.force`) as the literal *last* step of its own incremental USE walk (`myflags.update(useforce)` followed by `myflags.difference_update(usemask)`), strictly *after* the `pkg` (`package.use`) tier -- so `portage-repo`'s own `effective_use_flags` applies `use_force`/`use_mask` at that same relative position instead, alongside the atom-scoped `package_use_force`/`package_use_mask` it already positions correctly (force-add first, THEN force-remove, so a flag listed in both ends up masked, not forced). Exposed on `Config` directly either way, since Portage's own `forced_flags` (consumed by `--newuse`'s `reinstall_flags_for_newuse` in `portage-repo`, previously always empty -- see that function's own doc comment) is `use.force ∪ use.mask`, not either alone.

Stored flat, same as `package_use`; `portage-repo`'s own `effective_use_flags` decides which entries actually apply to a given candidate and in what order -- see that crate's doc comment for the atom-specificity algorithm this needed (Portage `ordered_by_atom_specificity`, ported) and a deliberate simplification made along the way: comparison- operator atoms lose Portage `best_match_to_list`'s "closest version wins a tie" refinement, since Portage-world `package.use.mask`/ `.force` files essentially never use `>`/`<`/`>=`/`<=` atoms in practice.   - `use.stable.mask`/`.force`/`package.use.stable.mask`/`.force` (PMS 5+, always recognized here per portuale's own "no EAPI parametrization" precedent) ARE now read too, closing the stable-vs-`~arch` cut named above: ported as `portage-repo`'s own `is_stable`, grounded against Portage `KeywordsManager.isStable` -- genuinely more subtle than a raw "no `~` prefix" check (a candidate counts as stable if replacing *every* one of its own KEYWORDS with its `~`-prefixed unstable form would make it invisible under the current `ACCEPT_KEYWORDS`/ `package.accept_keywords`). `use_stable_force`/`use_stable_mask` stay separate `Config` fields rather than folding into `use_flags` like `use_force`/`use_mask` do, since Portage `getUseMask`/`getUseForce`'s own global (`pkg=None`) branch never even looks at the stable variant at all -- "stable" is inherently a per-candidate property with no meaningful global value, so `portage-repo`'s own `effective_use_flags` applies these conditionally instead, once it knows a specific candidate's own stability. `use.stable.mask`/`.force` read from the profile chain only (matching portuale's own already-established profile-only sourcing for the non-stable global files, not Portage per-package `getUseMask`/`getUseForce`'s own additional repo-level source for them, which portuale's global mechanism never had either); `package.use.stable.mask`/`.force` read repo-level (every repo, `::repo`-scoped) plus profile-chain plus the user profile's own pair (#341 S6), mirroring `package.use.mask`/`.force`'s own sourcing exactly, no user-level source (same `UseManager.__init__` file/variable table confirmation).
- One Portage, deliberately-preserved quirk from lib/portage/package/ebuild/ config.py (see the comment above its `expand_map.pop("USE", None)`): `${VAR}` substitution persists across profile levels for every variable *except* USE, which is reset before each level's make.defaults is parsed. This stops a parent profile's accumulated USE from leaking into a child's own `USE="${USE} flag"` self-append. In the flat, single-set consumption model portuale uses (no package.use interaction, unlike Portage's bug this quirk guards against), that particular scenario usually doesn't change the final *set* of enabled flags -- it's ported anyway for fidelity with Portage's algorithm, since it's cheap to do and it's what Portage actually does.
