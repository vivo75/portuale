# crates/portage-profile/src/package_files.rs
Line readers for `package.mask`/`.unmask`, `package.accept_keywords`, `package.license`/`.properties`/`.accept_restrict`, `package.use`, and `license_groups`.

## fn read_config_lines
- Portage's `_recursive_file_list` semantics: arbitrary depth, one ascending sort per directory over files and subdirectories together with each subdirectory expanded in place, skipping `VCS_DIRS` directories, dot-prefixed names and `~`-suffixed backups at every level including the root path itself, following symlinks (via `portage_util::recursive_config_files`).
- Unreadable paths report; missing paths stay empty.

## fn scope_repo_mask_lines
- Portage `append_repo`'s "atoms without an explicit repo part get one; atoms that already have one are left alone" rule, applied to an overlay's own repo-level entries so they can never silently mask/unmask a same-named package in a different repo.
- A removal atom is scoped exactly like an addition one, so it can only ever cancel a same-repo-scoped entry.
- Scopes each of `lines` (raw `package.mask`/`.unmask` entries, a leading `-` meaning removal) to `repo_name` by appending a `::name` suffix to the atom portion -- Portage `append_repo`'s own "atoms without an explicit repo part get one; atoms that already have one are left alone" rule (`lib/portage/util/__init__.py`), applied here to an overlay's own repo-level entries so they can never silently mask/unmask a same-named package in a *different* repo. A leading `-` (removal) is preserved ahead of the atom, not swallowed into it -- `-cat/pkg` scopes to `-cat/pkg::name`, matching Portage's own behavior of scoping a removal atom exactly like an addition one, so it can only ever cancel a same-repo-scoped entry.

## fn scope_repo_package_use_lines
- Unlike `package.mask`/`.unmask`, none of these files has `-atom` whole-entry removal syntax: Portage only ever `.extend()`s these, and a leading `-` inside the flag list masks/forces a single flag off, not an atom. So there is no leading-`-` case to preserve here.
- Same Portage "add `::repo` to every atom without one" rule as `scope_repo_mask_lines`, applied to the `package.use`/`.mask`/`.force`/ `.stable.mask`/`.stable.force` line shape instead (`<atom> <flag> <flag> ...`, see `parse_package_use_lines`): only the leading atom token gets scoped, the flag tokens after it are passed through untouched. Unlike `package.mask`/`.unmask`, none of these files has `-atom` whole-entry removal syntax (confirmed by `parse_package_use_lines`'s own doc comment: Portage only ever `.extend()`s these, and a leading `-` inside the flag list masks/ forces a single flag off, not an atom) -- so there's no leading-`-` case to preserve here, unlike `scope_repo_mask_lines`.

## fn stack_mask_lines
- Ports Portage `stack_lists`'s `ignore_repo=True` behavior, the flag Portage `MaskManager.__init__` always passes for its final `[repo_pkgmasklines, profile_pkgmasklines, user_pkgmasklines]` combination, confirmed by reading it directly: "let `-cat/pkg` remove `cat/pkg::repo`". An unscoped removal token (all a profile-level or user-level `-atom` can ever be, since only repo-level entries get `::repo`-scoped) strips `::repo` off every existing entry before comparing; a `::repo`-scoped removal token (rare, only hand-written) keeps exact-match semantics, matching Portage's own `"::" not in token` guard exactly.
- Previously portuale's user-level-only `package.unmask` handling treated a leading `-` as meaningless; meaningful once more than one source contributes.
- Without the unscoped-removal rule, a profile's `-dev-libs/foo` could never cancel the main repo's now-`::reponame`-scoped mask entry: a regression the main-repo-scoping follow-up would otherwise have introduced.

## fn parse_package_accept_keywords_lines
- A bare atom gets Portage `accept_keywords_defaults`' implicit `~arch` meaning at both levels, confirmed by reading `KeywordsManager.__init__` (user-level: a bare `pkgdict` entry's value is replaced with `accept_keywords_defaults` before storage in `self.pkeywordsdict`) and `getPKeywords` (profile-level: the identical substitution at read time per matching entry). Same formula either way: `"~" + keyword` for each plain (non-`~`/`-`-prefixed) token in the current global `ACCEPT_KEYWORDS`. Contrary to portuale's earlier assumption, the user-level source gets the identical substitution too.
- This function only preserves the bare atom so that substitution has something to act on; `parse_package_license_lines` filters bare atoms back out immediately after, since no other file gets this treatment.
- `package.accept_keywords`: each line is `<atom-or-wildcard> <keyword...>`. A line with no keyword tokens after the atom is kept here with an *empty* token list, not dropped -- Portage gives a bare atom an implicit `~arch` meaning at *both* levels, confirmed by reading `KeywordsManager.__init__` (the user-level source: a bare `pkgdict` entry's value is replaced with `accept_keywords_defaults` right there, before it's ever stored in `self.pkeywordsdict`) and `getPKeywords` (the profile-level source: the identical substitution happens at read time instead, per matching entry) -- the same `accept_keywords_defaults` formula either way: `"~" + keyword` for each *plain* (non-`~`/`-`-prefixed) token in the *current* global `ACCEPT_KEYWORDS`. `resolve_config` fills in the actual defaults once `config.accept_keywords` is final (see its own call site) -- this function only preserves the bare atom itself so that substitution has something to act on; every other caller of this shape (`parse_package_license_lines` below) filters bare atoms back out immediately after, since no other file gets this treatment.

## fn parse_package_license_lines
- Same shape as `package.accept_keywords`, reused directly for all three files (unlike `parse_package_use_lines`'s deliberate separateness, which exists only because of `package.use`'s `USE_EXPAND`-shorthand parameter).

## fn parse_license_groups_lines
- `grabdict` format: no `-atom`/removal semantics. Matches Portage `self._license_groups.setdefault(k, []).extend(v)` exactly.
- `license_groups` (Portage `LicenseManager._read_license_groups`): each non-comment, non-blank line is `<group-name> <license or @group ...>` (`grabdict` format -- no `-atom`/removal semantics at all, unlike `package.mask`'s own file format). Later sources *extend* (never replace or stack-remove) whatever the same group name already has, matching Portage `self._license_groups.setdefault(k, []).extend(v)` exactly.

## fn expand_license_token
- `-@EULA` with `EULA = "Eula1 Eula2"` expands to `-Eula1 -Eula2`, matching Portage's tail `if negate: rValue = ["-" + token for token in rValue]`.
- Portage: "Skipping invalid element %s in license group '%s'": a group's member list is never itself allowed to contain a `-`-negated entry.
- Both circular references and undefined group names are deliberately silent here (no stderr warning), unlike Portage's own `writemsg`: portuale has no precedent for emitting warnings to stderr from deep inside config resolution (every other Portage warning-only path is silently skipped the same way).
- Expands a single `ACCEPT_LICENSE`/`package.license` token against `groups`: a plain license name (or `*`/`-*`, Portage's own symbolic wildcard tokens) passes through unchanged; an `@group-name` token (optionally `-`-negated) expands to every one of that group's own members, each recursively expanded the same way (a member that's itself a nested `@group` reference, Portage's own `_expandLicenseToken` "elif license_group:" recursion) -- negation applies to every expanded member, not just the group reference itself (`-@EULA` with `EULA = "Eula1 Eula2"` expands to `-Eula1 -Eula2`, matching Portage's own tail `if negate: rValue = ["-" + token for token in rValue]`). `traversed` guards against a circular group reference (matching Portage's own cycle guard): a group already being expanded higher up this same call stack is left as its own literal `@group-name` text instead of recursing infinitely, same for a genuinely undefined group name (never declared in any `license_groups` file at all) -- both deliberately silent here (no stderr warning), unlike Portage's own `writemsg`, since this portuale has no precedent for emitting warnings to stderr from deep inside config resolution (every other Portage warning-only path in portuale is silently skipped the same way).

## fn parse_package_use_lines
- Matches `parse_package_accept_keywords_lines` on bare atoms (documented no-op).
- Portage consumption (`config.py`'s `regenerate`) only ever `.extend()`s a growing token list per source, never removes a previous entry.
- The shorthand resets at the start of every line, confirmed by reading Portage `grabdict_package`'s `newlines=1` marker handling (a fresh `"\n"` token between every physical line; the loop resets its prefix on each one). Only the user-level source (`_parse_user_files_to_extatomdict`) ever applies it; `_parse_repository_files_to_dict_of_dicts`/`_parse_profile_files_to_tuple_of_dicts` go through `_parse_file_to_dict`, which never passes `newlines=1` and has no expansion step, so a `VIDEO_CARDS:` token there is just a literal, almost-certainly-invalid USE token. Genuine Portage behavior, not a portuale-invented restriction; see `resolve_config`'s call sites.
- `package.use`: each line is `<atom-or-wildcard> <use-token...>`. A line with no tokens after the atom is a documented no-op, matching `parse_package_accept_keywords_lines`. Purely additive across sources, like `package.accept_keywords` and unlike `package.mask`/`.unmask`: Portage's own `package.use` consumption (`config.py`'s `regenerate` -- see the module doc comment on `USE_ORDER`) only ever `.extend()`s a growing token list per source, never removes a previous entry, so there's no `-atom` semantics to port here at all.
- `use_expand_shorthand`, when true, ports Portage `UseManager._parse_user_files_to_extatomdict`'s own `VIDEO_CARDS: nvidia intel` syntax: a token ending in `:` sets a `lowercase(name) + "_"` prefix applied to every following token on *that same line* (a leading `-` stays outside the new prefix, e.g. `-flag` becomes `-video_cards_flag`, not `video_cards_-flag`) -- reset back to none at the start of every line, confirmed by reading Portage `grabdict_package`'s own `newlines=1` marker handling (a fresh `"\n"` token is inserted between every physical line for the same atom, and Portage's code's own loop resets its prefix on each one). Callers pass `false` for repo-level/profile-level lines: confirmed by reading `UseManager.__init__`, only the *user*-level source (`_parse_user_files_to_extatomdict`) ever applies this shorthand at all -- `_parse_repository_files_to_dict_of_dicts`/ `_parse_profile_files_to_tuple_of_dicts` both go through `_parse_file_to_dict` instead, which never passes `newlines=1` and has no such expansion step, so a `VIDEO_CARDS:` token in a repo-level or profile-level `package.use` file is (in Portage) just a literal, almost-certainly-invalid USE token, not shorthand at all. This is genuine Portage behavior, not a portuale-invented restriction -- see `resolve_config`'s own call sites.
