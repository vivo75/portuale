# crates/portuale/src/global_updates/config_files.rs
The world and `package.*` half of the `_do_global_updates` port (backlog #576): `update_dbentry` over the world list and every `package.*` file.

## fn update_world
- Ports the world loop (`_global_updates.py:182-214`): per repo (skipping `DEFAULT` and empty lists), per command, per entry, `update_dbentry(update_cmd, atom)`; a change applies only under `_world_repo_match` (`:166-180`, via `RepoMatch::matches`); then `world_list.sort()` and the `"".join(f"{x}\n")` write (`:208-210`). Returns `world_modified` (`:141` gate feeds the record/commit in a later piece).
- The list comes from `InstalledDb::world()` and goes back through a write transaction's `set_world` (sorted first -- the caller sorts, per the `set_world` contract), never through the `var/lib/portage/world` file directly: on a database backend that file is not the store. `World.atoms` holds the non-`@` atoms (`@set` names live in the separate `world_sets` store); `read_world` also trims lines and drops inline-`#` tails where `grabfile` would collapse them. A world file carrying `@` lines or odd spacing would therefore round-trip differently than Portage's raw `grabfile` loop -- the fixture has neither, so the files-backend bytes stay identical to the capture.
- `update_dbentry` itself is `portage_repo::{apply_move_to_token, apply_slotmove_to_token}` (made `pub` for this piece; the versioned-slotmove no-op is the known #583 gap, not fixed here). The `portdb.match` hit only feeds `world_warnings`, which Portage discards (`pass`, `:214`), so there is no portdb side here.
- `_world_repo_match` needs `vardb.match` + `best`: `match_keys` builds `cat/pf[:slot]` candidates (stored `SLOT` appended, like the strings `vardb.match` compares) and filters with `portage_dep::match_from_list`; `best_key` takes the `vercmp` maximum. An unparseable atom matches nothing (Portage would raise out of the match; untested either way).
- The write only happens when modified, so an untouched world keeps its exact bytes (a database backend's `set_world` would rewrite the store regardless once called -- not reached without a change).

## fn update_config_files
- Ports `update_config_files` (`update.py:241-415`): the same `myxfiles` + `profile/` lists, directory expansion skipping hidden/`VCS_DIRS` entries and hidden files, `errors="replace"` reads with missing files skipped, the per-command/per-file/per-line loop with the `-`/`*` atom strip, the `isvalidatom` gate, `update_dbentry` on the bare atom, the `# <cmd>` comment + `line.replace(atom, new, 1)` splice with the next-line skip, and the `isprotected` → `new_protect_filename` → `write_atomic` write-back (the local `write_config_file_atomic` is that `write_atomic` port, used only for these `package.*`/`._cfg` writes).
- Reuses `crate::ebuild_merge::{is_protected, new_protect_filename}` (md5 over the rewritten bytes, like Portage's `newmd5`) and the same token rewrites as the world piece. Per-file write failures warn (`!!! …`, `:409-414`) and continue; the function still returns `Ok`.
- Order note: files iterate in sorted order (BTreeMap), while Portage's `os.walk` expansion order is filesystem-arbitrary; only the `p` progress-letter order could differ, and progress output is a later piece's (no printing here yet).
- `case_insensitive` lowercases the protect/mask strings and the compared path before delegating to `is_protected`, which has no such parameter; on Linux the lowered directory probe fails and non-directories fall back to exact match, degrading the same way Portage's `stat`-based `_dirs` probe does. No fixture covers it.
- `::repo`/`[usedeps]` slotmove targets are left unchanged by the shared helper (its own documented cut); Portage's `str(atom.with_slot(...))` would rewrite them.

## struct UpdateConfigFilesArgs
- `on_progress` fires once per rewritten line, at the site Portage writes `'p'` (`update.py:396-397`, unconditional `sys.stdout.write` plus flush). The hook carries no count: Portage writes one character per line, so the driver maps each call to a single `'p'`.
