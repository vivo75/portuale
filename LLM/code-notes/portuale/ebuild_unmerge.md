# crates/portuale/src/ebuild_unmerge.rs
Package removal: `ebuild <file> unmerge`. Context moved out of the code comments (#336 Phase 7); the code keeps only the short why.

## module
- Task #55's complement: `ebuild <file> unmerge` mirrors Portage's `dblink.unmerge()` plus the top-level `unmerge()` function's success-gated `dblink.delete()` call (lib/portage/dbapi/vartree.py): runs `pkg_prerm`, deletes every file/dir/symlink the vdb entry's `CONTENTS` lists from `${ROOT}` (in Portage's `_unmerge_pkgfiles()` reverse-sorted order -- deepest paths first, so a directory always empties out before its own removal is attempted -- `mykeys.sort(); mykeys.reverse()`), runs `pkg_postrm`, and -- only if every step above succeeded -- removes the vdb entry itself (Portage's `dblink.delete()`: `shutil.rmtree(self.dbdir)` plus an `rmdir` of the parent `<category>` directory if it's now empty). `pkg_prerm`/`pkg_postrm` run via `ebuild_phases::run_single_phase`, the same way `ebuild_merge::run_merge`'s `pkg_preinst`/`pkg_postinst` do -- Portage's `unmerge()` invokes them directly (`EbuildPhase(phase="prerm"/"postrm")`), not through `doebuild()`'s `actionmap_deps` chain.
- Without this, `merge` alone can never be exercised through an install/reinstall/removal cycle -- every merge would just accumulate vdb entries and files forever.
- Locally-modified files are protected on removal too, Portage's `_unmerge_pkgfiles()` mechanism for it: an `obj`/`sym` entry whose live, on-disk mtime no longer matches what `CONTENTS` recorded at merge time is left in place instead of deleted (Portage's `!mtime` skip -- broader than `CONFIG_PROTECT` alone, since it applies to every unmerge regardless of path, and it's what actually protects a CONFIG_PROTECT'd file on removal too: Portage's `dblink._protect()` diverts a changed write to a `._cfgNNNN_` sibling while `CONTENTS` still records the original file's now-stale mtime, so the `/etc/foo.conf` a user edited never matches and is never touched).
- `others_in_slot` reverse-dependency checking: Portage's `_unmerge_pkgfiles()` `is_owned` check (lib/portage/dbapi/vartree.py:2893-2916, via `dblink.isowner()` == `bool(self._match_contents(filename))`) -- before a `CONTENTS` entry is even considered for the mtime check, every other installed version of the same `category/PN` in the same `SLOT` (excluding self) is asked whether its own `CONTENTS` also claims that exact path; if so, the entry is left alone entirely (Portage's `"replaced"` skip) regardless of node type. This is what makes an in-place upgrade not delete files the new version also owns -- without it, `merge`-then-`merge` (a reinstall/upgrade) followed by `unmerge`ing the old vdb entry would have deleted files the new installation still depends on. Reuses `ebuild_merge::owns_path_pf` (already built for blocker exclusion's `CONTENTS`-ownership check) and `ebuild_merge::read_installed_slot`, both promoted to `pub(crate)` for this. Portage's `isowner` path-ambiguity-via-symlinked-directories inode-cache mechanism isn't reproduced -- portuale's `owns_path_pf` is a plain string scan, matching the same simplification `find_owners`/blocker exclusion already made.
- The "symlink orphan" refinement (bug #326685): when a live symlink-to-directory this package's `CONTENTS` recorded as `sym` or `dir` is `is_owned` by another same-slot instance that itself now records that exact path as a literal `dir` entry (the directory the symlink pointed to got "promoted" to a real directory across the upgrade), the symlink is genuinely orphaned: neither this package's removal pass nor the survivor's files still need it as a symlink. Portage's `_unmerge_pkgfiles()` (lib/portage/dbapi/vartree.py:2895-2926) detects this and defers the decision -- `protected_symlinks`, keyed by the symlink's target directory's `(dev, ino)` -- to a second pass over this package's literal `dir` entries (Portage's `_unmerge_dirs()`, lib/portage/dbapi/vartree.py:3209-3332, `remove_dirs`): when that target directory is later actually removed (because nothing else needs it as a real directory either), the now-truly-orphaned symlink is deleted too, and its newly-emptied parent directories are recursively revisited (bug #640058) in case removing the symlink itself finally empties them. Portage's `_unmerge_protected_symlinks()` (lib/portage/dbapi/vartree.py:3276-3368, called on whatever `protected_symlinks` entries don't get resolved by `_unmerge_dirs()`) is ported as `unmerge_protected_symlinks` (#356 S5; the earlier "unreachable dead code" reading was stale once R4 existed -- R4 adds unowned paths that no `others_in_slot` check ever saw, so the early `return` no longer always fires). The early return re-checks the same-slot owners with the full per-package ownership (exact path, or rebuilt under a same-inode recorded parent); otherwise every installed package is searched for owners of the symlink path via `read_file_all("CONTENTS")` -- a recorded path counts when it equals the symlink path or holds it as a proper prefix component, which is Portage's implicit-parent-`dir` mechanism (`getcontents`, vartree.py:2286-2300) without materialising the entries. When nobody owns the leftovers they are unlinked and `remove_dirs` re-runs over their ancestors (vartree.py:3335-3366); whatever stays gets the trailing preserved notice. The three elog wordings (vartree.py:3246-3264, :3300-3319, :3334-3339) go through portuale's elog (`emit_unmerge_elog`: ` * ` echo lines plus the summary log), because that text is what tells the user why a symlink survived.
- `FEATURES=unmerge-orphans` (lib/portage/dbapi/vartree.py:2934-2950): despite the name, not untracked-orphan scanning -- for a non-`CONFIG_PROTECT`'d `obj`/`sym` entry (excluding a symlink whose live target itself resolves to a directory, Portage's comment: "Don't unlink symlinks to directories here since that can remove /lib and /usr/lib symlinks"), it bypasses the ordinary `!mtime` staleness check entirely and deletes the entry unconditionally, even if locally modified. Reuses `ebuild_merge::is_protected` (promoted to `pub(crate)` for this), the exact same `ConfigProtect.isprotected()` check `ebuild_merge`'s `CONFIG_PROTECT` handling already established -- `UnmergeOptions`' `config_protect`/`config_protect_mask` fields mirror `MergeOptions`' exactly, same env-var-sourced defaults.
- `INFOPATH` cleanup (lib/portage/dbapi/vartree.py:3226-3251, inside `_unmerge_dirs()`/`remove_dirs`): a directory literally named `"info"` (Portage's comment: "since it might have been in INFOPATH previously even though it may not be there now") whose only remaining content is a subset of `{"dir", "dir.old"}` (Portage's `_infodir_cleanup`, GNU `install-info`'s auto-generated index files) has those removed first, before the ordinary `rmdir` attempt -- without this, a stray leftover index file would keep such a directory from ever emptying out and being removed at all. The other trigger for this same cleanup, `inode_key in infodirs_inodes` (an `INFOPATH`/`INFODIR` env-var-driven inode set, covering an info directory that isn't literally named `"info"`) is threaded through too now: `env_update::info_dirs_inodes` collates `INFOPATH`/`INFODIR` values from `/etc/env.d/*` the same way `env_update::run_env_update` collates every other `COLON_SEPARATED` key, and `run_unmerge` computes that set once and threads it down through `remove_contents`/`remove_dirs` into `cleanup_info_dir`.
- `stale_confmem` cleanup (lib/portage/dbapi/vartree.py:2747/2931-2932/3106-3109): `cfgfiledict`, the `_conf_mem_file` "already offered this MD5" memory `ebuild_merge` writes on merge (`ebuild_merge::read_cfgfiledict`/`write_cfgfiledict`, promoted `pub(crate)` for this), is read once up front by `run_unmerge`; any path `remove_contents` actually removes -- not `is_owned` by another same-slot instance -- that `cfgfiledict` still remembers is collected into `stale_confmem` and dropped from the persisted memory afterward, matching Portage's ordering exactly (the elif is off the same `is_owned` check as the "replaced" skip).
- Known, documented gaps (v1 scope, matching `ebuild_merge`'s "narrow v1, document the cut" pattern): no `bsd_chflags` handling -- confirmed dead code on Linux, not a gap: `lib/portage/__init__.py:311` sets `bsd_chflags = None` unconditionally on non-BSD, and portuale's hard goal is Linux-only/musl-static. Failure handling is coarser: Portage's `_unmerge_pkgfiles()` counts per-file failures and keeps going regardless (overall success is governed by the `prerm`/`postrm` phase exit codes, not by individual file-removal failures); portuale's removal loop tolerates "already gone" (`NotFound`, matching Portage's `_ignored_unlink_errnos`/`_ignored_rmdir_errnos`) and "directory not empty" (matching Portage's `!empty` tolerance) but treats any other I/O error as a hard failure. `${T}`/`${D}`/etc. are recomputed fresh via `ebuild_phases::compute_environment` for every `unmerge` call, the same as `merge` -- Portage's `unmerge()` reuses whatever `PORTAGE_BUILDDIR` a prior merge left behind when present; portuale doesn't attempt that distinction.

## struct ContentsEntry (field mtime)
- `mtime` is Portage's `ebuild_merge::format_contents_line` trailing field, present for `obj`/`sym` lines. `None` for `dir`/`dev`/`fif`, which have no trailing field. Since #357 the line is split by `portage_vdb::contents::parse_line` (Portage's `_contents_re`, see `portage-vdb/contents.md`), not by whitespace, so paths with spaces survive.

## type ProtectedSymlinks
- Portage's `protected_symlinks`: the live target directory's `(dev, ino)` an orphaned symlink (bug #326685) points to -> every such symlink's `abs_path`. Grouped by target inode (not by symlink path) because that's how `remove_dirs` looks entries up -- Portage's `_unmerge_dirs()` `protected_symlinks.pop(inode_key)`.

## fn remove_contents
- Deletes every `CONTENTS`-listed entry from `root`, deepest paths first, in Portage's arm order (`_unmerge_pkgfiles()`, lib/portage/dbapi/vartree.py:3013-3230): a missing lstat skips (`--- !found`, which also covers a path under a replaced directory reporting ENOTDIR, not only ENOENT); the `is_owned`/`"replaced"` skip with the bug-#326685 symlink-orphan deferral; the orphan arm for any non-directory that is not a symlink-to-directory and not protected, whatever the recorded kind (`obj`/`sym`, but also `fif`/`dev` nodes and a `dir` entry that is live a regular file); the `!mtime` skip for kinds other than `dir`/`fif`/`dev`; then the `!dir`/`!sym`/`!obj` type guards, the `!md5` content check for a surviving `obj`, and the `!fif` guard (`dev` is always kept). The `UNINSTALL_IGNORE` + libdir-symlink ignores (R1/R2) run before `is_owned`, like Portage's `cfgpro` arm; a `dir` entry that is a live symlink takes the sym branch (R3, same commit as R2/R4/R4b so no commit could unlink `/bin` on a merged-usr `emerge -C`); a symlink to a non-empty directory whose children are not all owned regular files waits in `protected_symlinks` (R4, `!empty`) for the owners search. Returns the R4b elog lines. (Cell C1a is the failing-first pin for the merged-usr shape; C1b pins nothing -- with no other recorder Portage removes `/bin`.) The v1 failure-tolerance simplification: see the module gaps. The `is_owned`/`"replaced"` skip: see the module notes. The `!mtime` skip (which is also what protects a CONFIG_PROTECT'd file on removal): see the module notes. `unmerge_orphans` bypasses that `!mtime` check entirely for a non-`CONFIG_PROTECT`'d `obj`/`sym` entry (a symlink whose live target is itself a directory excluded, Portage's comment: "Don't unlink symlinks to directories here since that can remove /lib and /usr/lib symlinks"). This package's literal `dir` entries are deferred to a second pass (`remove_dirs`, Portage's `_unmerge_dirs()`) instead of removed inline here (Portage's `mydirs`) -- see the module notes on bug #326685 for why the deferral matters. `cfgfiledict`/`stale_confmem`: Portage's `_unmerge_pkgfiles()` `stale_confmem` cleanup (lib/portage/dbapi/vartree.py:2931-2932) -- a removed, not-`is_owned` entry that `cfgfiledict` (the `_conf_mem_file` "already offered this MD5" memory `ebuild_merge` writes on merge) still remembers has its path collected into `stale_confmem`, so `run_unmerge` can drop it from the persisted memory afterward -- otherwise a future merge could wrongly treat a long-gone package's previously-offered update as "already offered" for a path nothing installs anymore. `preserved_paths`: Portage's "remove the preserved files from our contents so that they won't be unmerged" (lib/portage/dbapi/vartree.py:2293-2294, see `ebuild_merge::preserve_libs_on_unmerge` for the preserve-libs registration this mirrors) -- filtered out of `entries` immediately, the same point Portage itself strips them from the CONTENTS dict, before the per-file removal loop ever sees them at all.
- Bug-detection step: Portage's bug #326685 detection (lib/portage/dbapi/vartree.py:2898-2926) -- a live symlink-to-directory this package's `CONTENTS` recorded as `sym` or `dir`, whose exact path another same-slot instance now claims as a literal `dir` entry (not `sym`). The `"replaced"` skip is checked before the mtime check, matching Portage's `_unmerge_pkgfiles()` ordering (an in-place upgrade sharing files with the version being unmerged is the common case). `stale_confmem` (lib/portage/dbapi/vartree.py:2931-2932): the path is actually going away and nothing else owns it, so its `_conf_mem_file` memory entry is now stale too. `FEATURES=unmerge-orphans` (lib/portage/dbapi/vartree.py:2934-2950): deletes a non-`CONFIG_PROTECT`'d `obj`/`sym` entry unconditionally, bypassing the `!mtime` staleness check -- even a locally-modified file is deleted; a symlink whose live target resolves to a directory falls through to the ordinary mtime-checked removal instead; checked before the mtime check, matching Portage's ordering exactly.
- `fif`/`dev` branches: Portage's `_unmerge_pkgfiles()` orphan arm (`lib/portage/dbapi/vartree.py:3098-3112`) unlinks any non-directory that is not a symlink-to-a-directory and not protected, whatever the recorded kind -- so a `fif`/`dev` node (or a `dir` entry that is live a regular file) is unlinked under default `FEATURES`, and only kept under `-unmerge-orphans` by the `fif` (`:3224-3227`, `--- !fif` unless a live fifo) and `dev` (`:3229-3230`, always `---`) arms. An earlier revision of this note claimed both "just report, never unlink, matching Portage exactly": that was wrong under the default FEATURES (S0 cells F1a/F1b plus the F2 source verdict established it; #356 S4 ports the orphan arm). (see `ebuild_merge::merge_tree`'s `fif`/`dev` branch for the merge-time counterpart that creates these nodes).
- Trailing `if protected_symlinks:` elog warning (lib/portage/dbapi/vartree.py:3085-3103) for whatever entries `remove_dirs` didn't resolve is deliberately not reproduced -- no message-printing output anywhere else in this module either. The behavioral effect -- those symlinks are left in place -- already holds: `remove_dirs` only ever deletes a `protected_symlinks` entry's symlinks when it actually removes their target directory.

## fn remove_dirs
- Ports Portage's `_unmerge_dirs()` (lib/portage/dbapi/vartree.py:3209-3332): removes this package's literal `dir` entries (`dirs`, Portage's `mydirs`), tolerating "already gone" and "not empty" the same way the main per-entry loop does for everything else. When removing one of these directories actually succeeds, and its `(dev, ino)` matches a `protected_symlinks` entry (a bug-#326685 orphaned symlink pointing at exactly this directory), that symlink is now safe to delete too -- deleted here, with its newly-emptied parent directories recursively re-queued for another removal attempt (bug #640058), since a directory that failed to rmdir earlier only because this exact symlink still occupied it deserves a second chance. Uses `dirs` as a LIFO stack, mirroring Portage's `_unmerge_dirs()` `dirs.pop()`/`dirs.append()` usage of a plain Python list -- removal order itself has no semantic meaning, but the stack shape (a directory can be pushed back after being popped) is load-bearing for the bug-#640058 revisit to work at all.
- `dirs = sorted(dirs)`: Portage's `mydirs` is built as a Python set during the caller's traversal (order not guaranteed), so Portage always re-sorts ascending before relying on `pop()` (removes-from-the-end) to visit deepest paths first -- sorted ascending, a path is always lexicographically greater than its own ancestor (`/usr` < `/usr/share`), so the last element is always the deepest.
- Bug #640058 revisit: walk each newly-emptied symlink's ancestor chain while each successive ancestor is itself a directory that previously failed to rmdir (`revisit`), re-queuing all of them for another removal attempt now that the symlink is gone. Already gone needs no revisit (Portage: `errno == ENOENT` is excluded from revisit tracking); any other tolerated rmdir failure (chiefly "not empty") is tracked for a possible later revisit.

## field unmerge_orphans

The value travels three ways, all default-on: `MergeOptions::from_env` folds the calling env over the default token with the incremental semantics (`-tok` removes, `-*` clears; `FEATURES` is incremental, const.py:130); `MergeOptions::set_resolved_features` re-derives it from the resolved list (which carries the synthetic base layer seeded when `make.globals` was not read, so `-unmerge-orphans` in any layer still turns it off); the replace loop (`unmerge_one_installed`) and `emerge -C` (which already passes the resolved `MergeOptions`) inherit it, and `ebuild <f> unmerge` reads the resolved chain when one is available (`resolve_unmerge_config`) with the same env fold as fallback. The old literal "set and lacks the token" env test (which read `FEATURES=buildpkg` as off) is gone.

## fn unmerge_pkgfiles
- File-removal core of Portage's `dblink.unmerge()` -- everything Portage's `_unmerge_pkgfiles()` does (delete every `CONTENTS` entry deepest-path-first, honoring the same-slot "replaced" skip, the `!mtime` CONFIG_PROTECT skip, `FEATURES=unmerge-orphans`, bug #326685's orphaned-symlink handling, `stale_confmem` pruning and preserve-libs) -- but not the `prerm`/`postrm` phase hooks and not the final vdb-directory removal (`delete_vdb_dir`). Split out of `run_unmerge` (which brackets it with the two phase calls) so `ebuild_merge::merge_binpkg`'s replace-an-installed-version path can reuse it: a binpkg carries no ebuild to source a phase from, so its replace runs the file removal phase-free (a documented v1 cut -- see `merge_binpkg`'s doc). `also_keep`, when non-empty, is folded into Portage's `others_in_slot` set so a path the replacing version now owns is left in place exactly as a path owned by a genuine other same-slot instance would be. `is_replacement` is Portage's `unmerge_with_replacement`: `treewalk()`'s replace loop sets it (the preserved set was computed merge-side and injected into the replacing package's `CONTENTS`, so the files survive through ownership and no old-cpv registration happens -- see `ebuild_merge::preserve_libs_on_unmerge`); a standalone `emerge -C` clears it. `replacement_preserved` is Portage's `preserve_paths` (owner -> paths just preserved merge-side, not yet registered): non-empty only on the replace-loop path, where the merge caller threads its own set through `unmerge_replaced_same_slot` and `unmerge_one_installed`; empty everywhere else. `replacement_needed` is Portage's `include_file` (the replacing package's own `NEEDED.ELF.2` lines -- see `ebuild_merge::unmerge_replaced_same_slot`): same threading, same empty-on-standalone rule.

## fn unmerge_pkgfiles_into
- `unmerge_pkgfiles` with the D4 writes (preserved-libs registry, config memory, W4 rewrites of other entries) collected into `retire` instead of committed one by one (feat#157 S4.2); the caller commits them with `retire_entry`. `None` is the S1.5 behaviour, call for call.
- Through the root's installed-database backend. `read_to_string` errors keep their text: the io error for a read that failed, `ENOENT` for a missing entry or file, the std UTF-8 text for a `CONTENTS` that is not UTF-8.
- `others_in_slot`: every other installed version of this same category/PN in the same SLOT, excluding self. `infodirs`/`infodirs_inodes` (lib/portage/dbapi/vartree.py:2830-2846): Portage's `INFOPATH`/`INFODIR`, collated from `/etc/env.d/*` the same way `env_update::run_env_update` collates every other `COLON_SEPARATED` key -- see `env_update::info_dirs_inodes` for why this is a separate, narrower computation rather than a refactor of that already-tested function. `cfgfiledict`/`stale_confmem` (lib/portage/dbapi/vartree.py:2747/2931-2932/3106-3109): the `_conf_mem_file` memory `ebuild_merge` writes on merge, read once up front the same way Portage's `_unmerge_pkgfiles()` does, then pruned of every path this unmerge actually removes and rewritten -- see `remove_contents`.
- `_prune_plib_registry(unmerge=True, ...)` (confirmed by reading the Portage call site, not just the method itself -- see `ebuild_merge::preserve_libs_on_unmerge` for the full grounding). `own_slot` defaults to `"0"` the same way `parse_slot`'s fallback already does, matching Portage's `_pkg_str` `settings["SLOT"]` fallback for a package with no recorded slot at all.
- `_prune_plib_registry`'s tail, which runs on unmerge too, not only on merge: a preserved library whose last surviving consumer is the package now being removed is orphaned -- delete it and drop it from the registry. Portage's `unmerge_no_replacement = unmerge and not unmerge_with_replacement`: in replacement mode a consumer owned by the old instance still counts (it survives through the replacing package), the old instance's own linkmap data is excluded, the merge-side just-preserved set is scanned in, and the replacing package's own `NEEDED` lines are fed explicitly (Portage's `include_file` -- the new entry is still `-MERGING-`; see `ebuild_merge::find_unused_preserved_libs`). `exclude_pkgs`: the unmerged instance itself, plus (database backends, #310) the same-slot instances this replace loop already unmerged -- their entries stay installed until the publishing commit, where `files` has already removed their directories, so they must not feed the linkage map of the later instances' prune.
- A replaced instance (`is_replacement`, i.e. the merge's replace loop) with no `CONTENTS` file walks an empty file list instead of failing, like Portage's `getcontents()` returning `{}` on `ENOENT` (vartree.py, `dblink.getcontents`; #348 S6 M1: resolve-fixture seeds carry no `CONTENTS`, and the same-`pf` reinstall must still unmerge them). Scoped to missing files only (other io errors still fail); a standalone unmerge keeps the "not installed" error `emerge -C` relies on.

## fn delete_vdb_dir
- `WriteTxn::delete_entry` is the old body, unchanged: `remove_dir_all` of the entry, then the best-effort category `rmdir` (Portage's `dblink.delete()`: a best-effort `os.rmdir` of its now-maybe-empty parent category directory, ignored on failure -- another installed package in the same category is the common case). Split out of `run_unmerge` so `ebuild_merge::merge_binpkg`'s replace path can drop an old version's vdb entry without going through the phase machinery (N14).

## fn retire_entry
- `retire` is `Some` on a database backend (feat#157 S4.2), and one transaction then holds the row's deletion together with the D4 writes the unmerge collected (registry, config memory, W4 rewrites); `None` is `delete_vdb_dir`, the S1.5 call.

## fn entry_path_for_message
- The directory of the installed entry `category/pf` as the old messages printed it (`<root>/var/db/pkg/<category>/<pf>`); on a backend with no such directory, the bare `category/pf`.

## fn run_unmerge
- `exists()` of old: one `stat` that follows symlinks, any error is "not there". Standalone `emerge -C`: no replacing package, so no include feed (backlog #224).

## tests: is_owned
- The "shared.txt" skip can only be explained by the `is_owned` check itself, not incidentally by an `!mtime` mismatch (matching mtimes for both files).

## tests: stale_confmem
- A removed, not-`is_owned` path that `cfgfiledict` (the `_conf_mem_file` "already offered this MD5" memory) still remembers is collected so the caller can drop it from that persisted memory afterward. Ordering (lib/portage/dbapi/vartree.py:2928-2932): `stale_confmem` is an `elif` off the same `is_owned` check as the "replaced" skip -- a path another same-slot instance still owns is never considered stale, since the memory is still meaningful for that surviving instance.

## tests: orphaned symlinks (bugs #326685, #640058)
- First shape: the orphaned symlink's target directory is never part of this package's own `dir` entries at all (owned/populated by something else entirely), so `remove_dirs` never gets a chance to resolve it either: the symlink and its target must both survive untouched (the ordinary `is_owned` skip already protects the symlink from direct deletion). The assert message pins the revisit shape: "the parent, blocked only by the now-deleted symlink, is revisited and removed too (bug #640058)".
- Second shape: the symlink's target directory is one of this package's own `dir` entries -- once it's actually removed (nothing else needs it as a real directory), the now-truly-orphaned symlink is deleted too, and its parent directory (which could only fail to rmdir because the symlink was still occupying it) gets a revisit and is removed as well.

## const INFODIR_CLEANUP
- Portage's `_infodir_cleanup` (vartree.py:1794): the only filenames GNU `install-info`'s auto-generated index is ever known to leave behind.

## fn cleanup_info_dir
- Portage's `_unmerge_dirs()` INFOPATH cleanup (vartree.py:3226-3251): `inode_key in infodirs_inodes or os.path.basename(obj) == "info"`. If the directory's only remaining content is a non-empty subset of `INFODIR_CLEANUP` (Portage's `remaining and len(remaining) <= len(infodir_cleanup) and not set(remaining).difference(infodir_cleanup)`), those files are deleted -- regular-file-only (Portage's `stat.S_ISREG`), so a same-named symlink or subdirectory is left alone -- clearing the way for the caller's subsequent `rmdir` to succeed.

## tests: info-dir cleanup
- The `automake.info` probe file carries genuine content. Condition: cleanup only fires when the entire remaining content is a subset of `{"dir","dir.old"}` -- any other file present means the directory genuinely still has content, so nothing is removed at all (not even "dir" itself). Second trigger half (lib/portage/dbapi/vartree.py ~3226): `inode_key in infodirs_inodes` fires independently of the literal `basename == "info"` check -- an `INFOPATH`/`INFODIR` entry can name any directory at all. Without the cleanup, `usr/share/info` would never empty out at all -- `dir` isn't one of this package's own CONTENTS entries (Portage's `install-info` writes it outside any package's tracked content), so it would otherwise sit there forever, blocking the directory's removal.
- The `INFOPATH`-via-env.d test asserts the live env.d entry resolves ("the env.d entry must resolve") and that an env.d-sourced `INFOPATH` directory is cleaned up even though it isn't named info.

## tests: end-to-end config memory and upgrades
- End-to-end proof that `ebuild_merge::read_cfgfiledict`/`write_cfgfiledict` and `remove_contents`'s `stale_confmem` collection actually connect through `run_unmerge` (lib/portage/dbapi/vartree.py:2747/2931-2932/3106-3109). The scratch `_conf_mem_file` has one entry for a path this package actually owns and is about to remove, one entry for a wholly unrelated path nothing touches.
- End-to-end `others_in_slot` proof: `ebuild <file> merge` othersinslotpkg-1.0, then -2.0 (same SLOT, both writing the same shared path). Merging 2.0 is an in-place upgrade -- `merge_after_install`'s replace loop (`unmerge_replaced_same_slot`, Portage's `dblink.treewalk()`) removes 1.0 automatically: the shared file survives (2.0 owns it), the 1.0-only file goes, 1.0's vdb entry is dropped. Then unmerging 2.0 -- now the sole owner -- finally removes the shared file. The category dir is empty too at the end.

## fn unmerge_protected_symlinks
- Ports Portage's `_unmerge_protected_symlinks()` (lib/portage/dbapi/vartree.py:3276-3368): the early return, the search elog, the unlink-when-unowned with ancestor re-`rmdir`, all in one place. The whole-vdb search reads every live entry's `CONTENTS` through `InstalledDb::read_file_all`, so it is backend-independent (files, sqlite, redb); the unmerged instance itself is excluded by `(category, pf)`, like Portage dropping `self.mycpv`. It runs rarely (only with leftover protected symlinks), so the full scan costs nothing in the common case. The inode-translation part of `isowner` is deliberately not in the search: the query is the symlink path itself (never a through-symlink child), so exact-or-prefix is the whole rule; the translation lives only in `contents_isowner` for R4's child loop and the early return. Narrow-shape residue: #381 (`_match_contents` full inode matching, implicit parent entries).

## fn emit_unmerge_elog
- The R4b wordings reach the user two ways, mirroring Portage's elog `echo` + `save_summary` modules: ` * `-prefixed stdout lines (gated on `echo_enabled`) and an append to `<logdir>/elog/summary.log` (gated on the `save_summary` module), both best-effort. Called from `unmerge_one_installed` (the replace loop and `emerge -C`) and `run_unmerge` (`ebuild <f> unmerge`), so every entry point reports alike. Portage re-displays the summary block at the end of the run (`Messages for package ...`); portuale has no such display pass (02.346's 351-LIST family), so only the inline echo is asserted by the S5 pins.

## fn shlex_split
- Minimal POSIX-shell word splitter for `UNINSTALL_IGNORE` (Portage calls `shlex.split` at vartree.py:2933): single/double quotes group, backslash escapes the next char. There is no shared helper (`portage-profile`'s `shlex_token` tokenises one `KEY=VALUE` right-hand side; `doins`' is byte-oriented and private), and the value space is tiny, so a local implementation with unit tests is the whole cost.

## field uninstall_ignore
- `MergeOptions::uninstall_ignore` is the resolved `UNINSTALL_IGNORE` scalar: `from_env` reads the calling env over the `make.globals` default (`/lib/modules/*`, cnf/make.globals:93); `apply_uninstall_ignore` replaces it from the resolved config next to `apply_config_protect` (both the `emerge -C` and merge/replace-loop setups call it); `set_resolved_features` folds the packdebug tarball dir over whatever base resulted, idempotently. `UnmergeOptions::uninstall_ignore` is built from it in `unmerge_one_installed`, and separately in `ebuild.rs` from the resolved-or-env chain (Q11's routing, same helper). `remove_contents` splits the raw string once per call.
