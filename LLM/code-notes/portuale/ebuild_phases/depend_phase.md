# crates/portuale/src/ebuild_phases/depend_phase.rs
The `depend` phase and its metadata cache (run + depcachedir rung).

## fn run_depend_phase
- `bin/ebuild.sh`'s `depend` branch writes the full key list (`DEPEND RDEPEND SLOT SRC_URI RESTRICT HOMEPAGE LICENSE DESCRIPTION KEYWORDS INHERITED IUSE REQUIRED_USE PDEPEND BDEPEND EAPI PROPERTIES DEFINED_PHASES IDEPEND INHERIT`) to `${PORTAGE_PIPE_FD}` (Portage's `_metadata_fd`), so incidental stdout/stderr cannot corrupt the metadata. The wrapper is a tiny `exec 9>` shell prefix (no `unsafe`, no extra crate).
- `EbuildMetadataPhase` reports every outcome as a `returncode` (`os.EX_OK` / 1 for expected failures like invalid metadata / anything else unexpected); `MetadataRegen._task_exit` keys `cp_retry` off it (`returncode != 1` retries). Hence the `DependError` struct.
- Sandbox-log rewrite to 2 does not apply: `depend` is outside `_doebuild_spawn`'s `SANDBOXED_SRC_PHASES`.
- Exit 0 with no metadata is Portage's `metadata_valid == False` arm (returncode 1, never retried).
- Portage `EbuildMetadataPhase` reads the metadata from a private pipe, so concurrent `emerge` processes never share it. The builddir is shared (`${PORTAGE_TMPDIR}/portage/<cat>/<pf>`), so the file that stands in for the pipe is per-process: a fixed name let two concurrent cache-miss resolutions delete each other's metadata and report the package as having no ebuilds.
- Portage `EbuildMetadataPhase._async_start`: `doebuild` failing before it even spawns surfaces as an int retval (in practice 1) -- an "expected" failure, never retried by `metadata_regen_retry`'s `cp_retry` (which only re-runs a cp whose phase died with an *unexpected* returncode).

## fn depend_phase_metadata
- Registered via `portage_repo::register_aux_metadata_provider`; Portage's ebuild fallback when `metadata/md5-cache` has no entry (`_pull_valid_cache` miss -> `doebuild(mydo="depend")`).
- The depcachedir rung sits exactly where Portage's `_pull_valid_cache` has it: consult after the repo pregen cache, before `EbuildMetadataPhase`; write after success via `portdb._write_cache`. Flat layout `<depcachedir>/<repo path without leading '/'>/<cat>/<pf>` (e.g. `/var/cache/edb/dep/var/db/repos/porttest/porttest/docs-1.0`). An unwritable dir is Portage's `secpass < 1` read-only branch (volatile `_ro_auxdb`); here the in-memory memo.
- The writable depcachedir is `mtime_md5_database`: its `_eclasses_` carries eclass dir paths (`name\tpath\tmd5`, `store_eclass_paths = True`).
- Unsupported EAPI: Portage skips the phase and the package is EAPI-masked (`masked by: EAPI 9999`); portuale returns a failure instead (documented narrowing: the cp drops from candidates rather than rendering as an EAPI mask). Default head EAPI is `"0"`.
- `PORTAGE_TMPDIR` comes from `portage_tmpdir_from_env`, same CLI-boundary default as the rest.
- C2's registered cache-miss provider (see `portage_repo::register_aux_metadata_provider`): regenerate one ebuild's aux metadata by running its Portage `depend` phase -- Portage `porttree.py`'s ebuild fallback when `metadata/md5-cache` has no entry (`_pull_valid_cache` miss -> `doebuild(mydo="depend")`, C0's oracle). The result is the same `HashMap` shape `read_md5_cache` returns, so the resolver cannot tell the difference. C3 adds the **depcachedir rung** around that phase run, exactly where Portage `_pull_valid_cache` has it (`porttree.py:603-651`): before running the phase, a depcachedir entry whose `_md5_` still matches the ebuild is used as-is; after a successful run, the result is written to the depcachedir (Portage `EbuildMetadataPhase` -> `portdb._write_cache`, `porttree.py:578-596`) in Portage's flat layout (`<depcachedir>/<repo path without the leading '/'>/<cat>/<pf>`, `cache/flat_hash.py:20-22`). When that write cannot happen -- an unwritable depcachedir, Portage's `secpass < 1` read-only branch -- the result still lives for the process in `repo_aux_metadata`'s own memo (C2). The write is best-effort; render/write live in `regen.rs` because `--regen` writes the identical `flat_hash` format into the repo's `metadata/md5-cache`, and the shared validator lives in `portage_repo::md5_dict` (#46 S2). Layering: this lives in `portuale` (the binary that owns real phase execution) and is registered once from `main`; `portage-repo` only holds the `fn`-pointer slot. `root`/`config_root`/`PORTAGE_TMPDIR` come from the process environment, the same CLI-boundary defaults `root_from_env`/`config_root_from_env`/`portage_tmpdir_from_env` already establish. `depend` is never sandboxed, so this is a plain `bash bin/ebuild.sh depend` (see `run_depend_phase`).
- Portage `_pull_valid_cache`: the depcachedir auxdb is consulted after the repo's pregen `metadata/md5-cache` (C1's `read_md5_cache`) and before `EbuildMetadataPhase` runs. Same validator as the repo cache (Portage `template.validate_entry`), but the writable depcachedir is `mtime_md5_database`: its `_eclasses_` carries the eclass dir (`name\tpath\tmd5`, `store_eclass_paths = True`, S0 cell (a)).
- Portage `EbuildMetadataPhase._async_start` (`:61-75`): the ebuild head's EAPI is parsed before anything runs, and an unsupported one skips the phase entirely -- the package is then masked by EAPI visibility (S0 cell (e): `masked by: EAPI 9999`). Portuale returns a failure instead of Portage's synthesized `{"EAPI": ...}` map (a documented narrowing): the cp is dropped from candidates rather than rendered as an EAPI mask.
- Portage `_write_cache`: `metadata["_md5_"] = ebuild_hash.md5` then `cache[cpv] = metadata` -- the md5-dict/`flat_hash` writer. Best-effort: a read-only depcachedir keeps the result in memory (C2's memo) exactly like Portage's volatile `_ro_auxdb` branch.

## fn parse_aux_entry
- Portage's cache reader (`_parse_data`) raises `CacheCorruption` for lines without `=`; the phase pipe is written by `bin/ebuild.sh` and never emits one, so skipping is safe.

## fn depcachedir
- Not relative to `ROOT` (Portage rebases under `eroot` only in the unprivileged non-`/` target-root fallback, which never applies here).
- Narrowing: Portage resolves the setting through the full config stack (a `make.conf` assignment wins over the environment); portuale reads the process env only, the same CLI-boundary default the phase env whitelist already carries.
- Portage `settings.depcachedir` (`config.py:1114-1128`): the `PORTAGE_DEPCACHEDIR` setting when present, else `portage.const.DEPCACHE_PATH` = `/var/cache/edb/dep`. Not relative to `ROOT` (real rebases it under `eroot` only in the unprivileged non-`/` target-root fallback, which portuale's root runs never take). Narrowing: real resolves the setting through the full config stack (so a `make.conf` assignment wins over the environment); portuale reads the process environment only, the same CLI-boundary default the phase env's own whitelist (`ENVIRON_WHITELIST`) already carries.

## struct DependError
- Run one ebuild's `depend` phase (Portage `EbuildMetadataPhase` / `doebuild(mydo="depend")`) and return the raw metadata keys it emits. Portage `bin/ebuild.sh`'s `depend` branch (`ebuild.sh:781-804`) writes `KEY=value` lines (`DEPEND RDEPEND SLOT SRC_URI RESTRICT HOMEPAGE LICENSE DESCRIPTION KEYWORDS INHERITED IUSE REQUIRED_USE PDEPEND BDEPEND EAPI PROPERTIES DEFINED_PHASES IDEPEND INHERIT`) to `${PORTAGE_PIPE_FD}` -- Portage's `_metadata_fd` -- so incidental stdout/stderr can't corrupt the metadata. Portuale wires that fd to a `${T}` temp file via a tiny `exec 9>` shell wrapper (no `unsafe`, no extra crate), then parses it back. `depend` is never sandboxed (Portage `_doebuild_spawn`'s `SANDBOXED_SRC_PHASES` excludes it), so this is a plain `bash bin/ebuild.sh depend` -- no `sandbox`/`unshare` wrapper. Only the `Bash` backend is used (the metadata pipe is a raw fd the in-process `Brush` interpreter can't be handed). An exit-code-carrying `run_depend_phase` failure. Portage `EbuildMetadataPhase` reports every outcome as a `returncode` (`os.EX_OK` / 1 for an expected failure like invalid metadata / anything else for an unexpected one), and `MetadataRegen._task_exit` keys its `cp_retry` decision off exactly that (`returncode != 1` is retried). Threading the code through -- instead of a bare message -- is what lets `regen.rs` replay that decision.

## fn depcache_entry_path
- Portage `flat_hash.FsBased.__init__` (`cache/flat_hash.py:20-22`) with the `md5_database`/`md5-dict` label: `os.path.join(depcachedir, repo_path.lstrip('/').rstrip('/'))/<category>/<pf>` -- a flat tree keyed by the repo's absolute path minus the leading separator (C0's oracle: `/var/cache/edb/dep/var/db/repos/porttest/porttest/docs-1.0`).
