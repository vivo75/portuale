# crates/portuale/src/ebuild_phases/scheduler_registry.rs
Child processes registered for the build scheduler to kill.

## module
- Portage's `_terminate_tasks` sends kill signals and returns without waiting for exit status, once `_keep_scheduling` sees a package fail without `--keep-going`.
- A whole process group, not one pid: the descendant tree (`unshare` -> `sandbox` -> bash -> e.g. a compiler) inherits the group unless one starts its own session (none do), so `kill(-pgid, …)` reaches the whole tree. The child enters via `process_group(0)` (`setpgid` before `exec`), so its pid becomes the group id.
- `run_build_scheduler` creates one fresh registry and shares it with its `std::thread::scope` workers (`scope_scheduler_registry` guard at the top of each closure). Not a threaded-through parameter, to avoid a signature change across `run_commands_logged`/`run_one_phase`/….
- A single global registry would be unsafe: an unrelated `cargo test` thread's subprocess could be killed by a different test's scheduler-failure path.
- Portage `Scheduler._terminate_tasks`'s own "send kill signals... send kill signals and return without waiting for exit status" (`PollScheduler.py:106-118`, called once `_keep_scheduling` sees any package fail without `--keep-going`): every scheduled build's own top-level real subprocess (a phase's `unshare [sandbox] bash bin/ebuild.sh <phase>`, or `bin/misc-functions.sh`'s own equivalent) is spawned into a fresh process group (`process_group(0)`, `setpgid` before `exec`, so the child's own pid becomes the group id) via `spawn_trackable`, registered in `registry` for as long as the process runs. A whole process GROUP, not just the one pid: Portage's own descendant tree here -- `unshare` -> `sandbox` -> Portage `bash` -> whatever the ebuild itself spawns, e.g. a real compiler -- all inherit the same group unless one of them starts a session of its own (none of these do), so a single group-directed signal (`kill(-pgid, …)`) reaches the whole tree, not just its outermost process. `registry` is per-`run_build_scheduler`-*call*, not a single process-wide singleton: `emerge_build::run_build_scheduler` creates one fresh (`new_scheduler_registry`) and shares it with its own worker threads only (`scope_scheduler_registry`'s own RAII guard, set at the very top of each `std::thread::scope`-spawned closure). A thread-local pointer to it -- not a parameter threaded through every intervening call (`run_commands_logged`/`run_one_phase`/…) -- keeps this from being a signature change touching that whole chain; safe specifically because none of this module's own async phase bodies ever `tokio::spawn` an inner task (confirmed by grep), so `runtime.block_on(fut)` always drives the whole future to completion on the *calling* OS thread -- the same one the scheduler's own `scope.spawn` closure set the guard on, with no tokio-internal worker-thread migration to break the thread-local's visibility. Any other thread (a concurrent, unrelated test in the same process, a standalone `ebuild <file> <phase>` run, a single-job non-scheduler build) simply never sets the guard, so its own spawns are never registered anywhere and `kill_registered_children` can never reach them -- this is what makes a single global registry unsafe (an unrelated `cargo test` thread's subprocess could get killed by a completely different test's own scheduler-failure path) and why this is scoped per-call instead.

## fn kill_registered_children
- `SIGTERM`s every process group currently registered in `registry`. Best-effort: a group that already exited between the snapshot and the signal simply yields `ESRCH`, silently ignored, matching Portage's own "typically... return without waiting for exit status" non- blocking semantics.

## enum PhasePlacement (#408)

Backlog #408: phases used to be spawned with `process_group(0)` while the terminal's foreground group stayed portuale's. Any `bash -i` inside a phase (`app-shells/bash`'s `make check`) then did `kill(0, SIGTTIN)` and stopped the whole group for good. Stdin was irrelevant: `bash -i` opens `/dev/tty` or uses stderr (probe, `LLM/evidence/2026-10-18-408-s0/` and `LLM/2026-10-18-batch-plan.review.md`, cases A/C/J/K). Portage never makes a process group: pid-sandbox phases run under `bin/pid-ns-init:96` (`os.setsid()`), and `_global_pid_phases = {config, preinst, prerm, postinst, postrm}` (`doebuild.py:141`) stay in emerge's foreground group. portuale: `NewSession` (`setsid` in `pre_exec`, pgid == pid, so `kill(-pgid)` still reaches the tree) for every phase script except those five, which are `ParentGroup` and are killed by pid only (`pids` set). Known deltas, both deliberate: a build phase gets a session even when `pid-sandbox` is off (Portage leaves it in emerge's group; kept so the registry's group kill still reaches `make`'s children), and Ctrl-C reaches only portuale (backlog #411: no signal forwarding, as before the change).
