# crates/portuale/src/ebuild_phases/mod.rs
Real ebuild phase execution: module root, helpers, phase-command routing.

## module
- Origin: the "Real ebuild phase execution" slice. First scope proved real phase functions run and real files land under `${D}`, without touching the vdb/CONTENTS/merge machinery (`dblink.merge()`/`treewalk()`/`mergeme()`, ~6500 lines).
- The sourced bash is never reimplemented: `bin/ebuild.sh` plus `bin/phase-functions.sh`/`bin/phase-helpers.sh`/`bin/isolated-functions.sh`/`bin/bashrc-functions.sh`/`bin/save-ebuild-env.sh`. EAPI-default-phase dispatch (`default_src_install` etc.) comes along for free as real bash in `phase-functions.sh`.
- `EBUILD_SH_ARGS` is deliberately never set: `bin/ebuild.sh`'s trailing `if [[ -n ${EBUILD_SH_ARGS} ]]` block ends in a bare `exit $?`, which would kill the hosting Rust process. Hence brush's "source, then separately `invoke_function`" two-step instead of `__ebuild_main`.
- `bin/ebuild.sh` sources the ebuild file itself unconditionally (`source "${EBUILD}" || die`, not gated on `EBUILD_SH_ARGS`): an earlier version sourced it a second time and failed ("cannot mutate readonly variable") against vars the first pass had made `readonly`. `run_one_phase` sources `bin/ebuild.sh` alone, never the ebuild directly.
- `__check_bash_version` runs unconditionally at `ebuild.sh`'s top level; brush reports a version high enough for every EAPI portuale recognizes (confirmed empirically, not from brush's version-reporting code).
- Fresh shell per phase mirrors `spawnebuild()`; resume markers (`.pretended`/`.setuped`/`.unpacked`/...) make re-running done prerequisites cheap, exactly as Portage relies on across its separate spawns.
- One process-wide tokio runtime (`shared_runtime`), not one per phase: Portage's Scheduler runs a whole invocation on one asyncio loop; per-phase runtimes paid thread-pool setup/teardown per phase per package (see `misc_functions.rs` notes).
- Isolation model: `_doebuild_spawn` sandboxes every phase not in `_unsandboxed_phases` and unshares every phase not in `_ipc_phases`; for the phases run here both come out to the six `src_*` phases (`SANDBOXED_SRC_PHASES`). Any isolation forces `Bash`: neither `unshare(2)` nor LD_PRELOAD `libsandbox.so` can confine the in-process brush interpreter. Wrappers compose: `unshare <flags> --map-root-user -- sh -c '<config>; exec "$@"' _ [sandbox] bash bin/ebuild.sh <phase>`.
- `FEATURES=sandbox`/`usersandbox` is `sandbox bash ...` (Portage's `spawn_sandbox`) when `/usr/bin/sandbox` exists (`sandbox_capable`); `SANDBOX_LOG=${T}/sandbox.log` and `SANDBOX_DISABLED=0` let `bin/ebuild.sh` do its `SANDBOX_ON=1` + `addread /` + `addwrite "${PORTAGE_TMPDIR}/portage"` setup. `misc-functions.sh` calls get `sandbox-misc.log` (`MiscFunctionsProcess._spawn`). Missing binary degrades unsandboxed with a one-shot warning (Portage's silent `free = True`).
- Namespaces: `network-sandbox` -> `unshare --net` + loopback setup with the `10.0.0.1/8` + `fd::1/8` `AI_ADDRCONFIG`-workaround addresses (bug #690758; `_configure_loopback_interface`); `ipc-sandbox` -> `--ipc`; `mount-sandbox` -> `--mount` + `mount --make-rslave /` (`_exec2`); `pid-sandbox` -> `--pid --fork --mount-proc` (`CLONE_NEWPID` + `pid-ns-init`, `--fork` for the init).
- Exemptions (real, in `phase_isolation`): `RESTRICT=network-sandbox`, `PROPERTIES=live` for unpack, `PROPERTIES=test_network` for test. The phase env carries USE-reduced `PORTAGE_RESTRICT`/`PORTAGE_PROPERTIES` for bash's direct consumption (`RESTRICT=test`/`nostrip`/`strip` skips). `_ipc_phases` needs no check: all outside `SANDBOXED_SRC_PHASES`.
- Cuts: SELinux sandbox (kernel LSM, no meaningful degrade, only a `libselinux`/policy dependency); `userpriv`/`fakeroot` (drop privileges from an already-root process; builds never run as root, so nothing to drop — the merge side reproduces the `os.lchown`/`os.chown` calls itself). Unlike Portage (unshares only when `uid == 0`), `--map-root-user` always, so it works non-root; an unavailable namespace degrades with a warning ("Unable to unshare").
- `PORTAGE_PYM_PATH` is always set (`<checkout>/lib` with a checkout, else `/` for `__dyn_clean`'s unconditional `cd`). History: originally unset so `bin/ebuild.sh`'s "safe cwd" logic took the `${PORTAGE_BUILDDIR}/empty` branch (it still does — `create_directories` pre-creates it); but upstream's `ebuild-pyhelper` (`import portage`, reached in `real` oracle mode) `cd`s `"${PORTAGE_PYM_PATH}" || exit 1` unconditionally, so unset broke every eclass `has_version`/`best_version`.
- `__source_all_bashrcs` (`/etc/portage/bashrc` hooks) unimplemented: surfaces as a non-fatal "command not found" warning, not a phase failure. No profile/make.conf-driven bashrc concept exists.
- Cosmetic: from the third phase of a `run_commands` call, sourcing `bin/ebuild.sh` prints six "cannot mutate readonly variable" warnings (its `readonly SANDBOX_*` declaration). Not root-caused (fresh `Shell` each phase, so not the shared-shell issue; plausibly brush env inheritance across `Shell` instances, unconfirmed). Exit statuses unaffected.
- `EAPI` is read from the ebuild text (not `read_md5_cache`) because `ebuild <file>` operates on arbitrary standalone files; mirrors `_parse_eapi_ebuild_head`.
- `PORTAGE_TMPDIR` defaults to `/var/tmp` (`make.globals`), overridable via env (no make.conf-reading path into `ebuild.rs`; same simplification as `ROOT`/`PORTAGE_CONFIGROOT`).
- Stale claim removed from the old module doc: "`FILESDIR` is created here empty and never populated". Untrue since the `files` symlink work (`environment.rs`): `${PORTAGE_BUILDDIR}/files` is always a symlink to the repo `files/`.

## fn parse_eapi
- Matches `doebuild.py`'s `"eapi = None"` fallback. PMS rationale for first-line-only: the EAPI must be knowable without evaluating bash.
- Portage PMS 7.3.1: the ebuild's own EAPI is the value of an `EAPI=...` assignment (optionally single- or double-quoted, an optional trailing comment) on the first non-blank, non-comment line -- and *only* that line; an `EAPI=` assignment anywhere else in the file is not the ebuild's own EAPI at all (PMS's own rationale: the EAPI must be knowable without evaluating any bash). No match at all (including an ebuild whose first real line isn't an EAPI assignment) means EAPI "0", matching Portage `doebuild.py`'s own "eapi = None" fallback. Mirrors Portage `lib/portage/__init__.py`'s own `_parse_eapi_ebuild_head`/ `_pms_eapi_re` exactly.

## struct PackageSplit
- `portage-versions` has no name/version splitter (only `ververify`/`vercmp`), so this reuses `portage-repo`'s `strip_version_prefix` shortcut: `PN` is the parent dir name (Portage's `<category>/<package>/<package>-<version>.ebuild` convention, which `doebuild_environment`'s own assertion checks rather than derives). `PR` is the trailing `-r<digits>` of the remainder after stripping `PN-`.
- Portage `doebuild.py`'s own `_pkgsplit`-derived `P`/`PN`/`PV`/`PR`/`PVR`. Portage `_pkgsplit` derives `PN` from the version-shaped *suffix* of a bare `PF` string with no other information -- portuale's own `portage-versions` crate doesn't port that algorithm (it only has `ververify`/`vercmp`, not a name/version splitter), so this reuses the same shortcut `portage-repo`'s own `strip_version_prefix` already relies on instead: `PN` is simply the ebuild's own *parent directory* name (real convention -- `<category>/<package>/<package>-<version>. ebuild` -- that `doebuild_environment`'s own `os.path.basename(pkg_dir) in (mysplit[0], mypv)` assertion actually checks holds, rather than derives from scratch). `PR` is the trailing `-r<digits>` suffix of what's left after stripping `PN-` (default `"r0"`, Portage's own "no explicit revision" default) with `PV` being everything before it.
- Portage `PVR`: `PV` alone when `PR` is `"r0"`, otherwise `PV-PR` -- Portage's own "omit r0 from display" convention.

## fn is_standalone_phase_command
- Portage's branch is `mydo in ("config", "help", "info", "postinst", "preinst", "pretend", "postrm", "prerm")`, "running them out of the sandbox -- and stop now", narrowed to the four an admin invokes directly.
- `preinst`/`postinst` are ordering-tied to `merge`'s file copy (`dblink.treewalk()` invokes them around it: `preinst` before anything merges, `postinst` only after), so no standalone invocation could reproduce them; they stay merge-internal. `prerm`/`postrm` have no such tie to `unmerge`, so standalone and internal (`run_unmerge`) use are two independent ways to reach the same function (e.g. testing `pkg_prerm` without removing the package).
- Pure CLI-routing addition: `phase-functions.sh`'s `__ebuild_main` already accepts all four as literal phase args.
- Whether `command` is a real, standalone single-phase `ebuild` command with no `actionmap_deps` prerequisite chain at all -- Portage `doebuild()`'s own `mydo in ("config", "help", "info", "postinst", "preinst", "pretend", "postrm", "prerm")` early-return branch (`lib/portage/package/ebuild/doebuild.py:1326-1351`, "running them out of the sandbox -- and stop now"), narrowed to the four of those a real admin/user actually invokes directly by name: `config`/`info`/`prerm`/`postrm` -- `preinst`/`postinst` are real too, but only ever reached internally, as part of `merge` (see `ebuild_merge::run_merge`'s own doc comment: Portage `dblink. treewalk()` invokes them directly around the actual file-copy step, a real ordering constraint no standalone top-level invocation could reproduce -- `preinst` must run *before* anything is merged, `postinst` only *after*), so they stay internal-only; `pretend` is already part of the `actionmap_deps` chain above; `help` this portuale's own CLI already handles separately (`wants_help`). `prerm`/`postrm` have no equivalent ordering constraint tying them to `unmerge`'s own file-removal step the way `preinst`/`postinst` do to `merge`'s -- Portage itself allows invoking them completely standalone (e.g. to test a `pkg_prerm`/`pkg_postrm` function without actually removing the package), so `unmerge`'s own internal use (`ebuild_unmerge::run_unmerge`'s own doc comment) and this new standalone path are simply two independent, real ways to reach the same real phase function. `run_single_phase` (already used internally for exactly this reason) is a direct fit for all four: Portage `bin/phase-functions.sh`'s own `__ebuild_main` already accepts them as literal phase arguments (`run_single_phase`'s own doc comment), so no new phase-execution machinery is needed at all -- this is purely a CLI-routing addition.

## fn phase_prerequisites
- Portage `doebuild.py:874-884`'s own `actionmap_deps`: the prerequisite chain for `mydo`, run in order before `mydo` itself -- ported here as the Rust-side driver loop (see this module's own doc comment for why everything else stays real bash). Only the phase-only subset is covered (see this module's own "KNOWN, DOCUMENTED GAPS"); an unrecognized `mydo` returns just itself, letting the caller decide whether that's valid for its own purposes.
