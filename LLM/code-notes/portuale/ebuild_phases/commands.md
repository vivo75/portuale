# crates/portuale/src/ebuild_phases/commands.rs
Runs a phase command list (with logging): fetch once, then each command's phase chain.

## fn run_commands_async
- Origin: the `emerge <atom>` build/merge path passes the resolved `USE` flags in `build_env` because `bin/ebuild.sh`'s `use()` reads the `USE` var, which `phase_env_vars` otherwise leaves `""`. A standalone `ebuild <file> <phase>` passes `&[]` (no resolved graph entry).
- Each phase runs in its own fresh shell, not one shared shell: `bin/ebuild.sh`'s tail makes `EBUILD_PHASE` (among others) `readonly`, so a second phase in the same shell cannot re-export it. This mirrors Portage's `doebuild()`, which spawns a fresh `bin/ebuild.sh` process per phase via `spawnebuild()`. Resume markers (`.pretended`/`.setuped`/`.unpacked`/...) make re-running an already-done prerequisite cheap.
- Fetch ordering matches Portage: `pkg_pretend` runs before fetching (PMS's point for that phase is a fast sanity check needing no network); `setup` likewise precedes it. `A`/`AA` are exported into every phase, matching Portage's environment.
- `DISTDIR` is always exported: Portage's `unpack` (a `bin/ebuild-helpers/` script) resolves `${A}` relative to `${DISTDIR}`, not from anything Rust passes it. Found empirically: a fetched-and-verified distfile still made `unpack` report `"either does not exist or is not a regular file"` before the export was added.
- DISTDIR remap: `doins` passes the real dir as `--distdir`, so absolute symlinks under `doins -r` stay symlinks; the fake is `${PORTAGE_BUILDDIR}/distdir`, filled by `prepare_fake_distdir`.
- `AA` is never exported: Portage's `config.environ()` pops `AA` for EAPI 4+ and the floor here is EAPI 5+.
- Fake-distdir rule mirrors `doebuild.py`'s `mydo` test: prepare when the requested command is not `setup` (unless `FEATURES=noauto`), or the chain contains `install`/`unpack`. Portuale's `noauto` still runs prerequisites and `unpack` needs `${DISTDIR}/<A>`.
- After `install`: `_post_phase_cmds["install"]` is unconditional `bin/misc-functions.sh install_qa_check install_symlink_html_docs install_hooks`, never part of `phase_prerequisites` (unlike `ebuild <file> package`'s separate `__dyn_package` call), so this is the one place it runs. `EBUILD_PHASE` is popped for the spawn (`drop_ebuild_phase`, Portage's `MiscFunctionsProcess._spawn`): a misc spawn is not a real phase, so `use()`'s `IUSE`-membership gate stays off there (backlog #516). `MISC_FUNCTIONS_ARGS="$@"` with an unquoted `for x in ${MISC_FUNCTIONS_ARGS}` re-splits on whitespace, so one space-joined string equals three argv entries.
- Ordering is load-bearing for `SIZE`: `_post_src_install_write_metadata` and `_post_src_install_uid_fix` run before the QA sequence, so `SIZE` is the pre-transform image (`ecompress`/`estrip` run later). Observed values for `porttest/docs`: 807 bytes pre-transform vs 372 compressed.
- Drives `commands` against `ebuild_path` for real: computes the environment once, then for each of `commands` in order, runs its own `phase_prerequisites` chain, each phase in its own fresh embedded brush shell (see `run_one_phase`'s own doc comment for why a fresh shell per phase, not one shared across the whole invocation, is the real, not simplified, model here) sourcing Portage `bin/ebuild.sh` (see this module's own doc comment) and the ebuild file itself. Portage `doebuild()`'s own `SRC_URI`-vs-`DISTDIR` fetch check (see `fetch_sources`'s own doc comment) runs exactly once here, before the phase loop, whenever the combined prerequisite chain includes `unpack` -- matching Portage's own ordering (Portage `pkg_pretend` explicitly runs *before* fetching, PMS's whole point for that phase being a fast sanity check that shouldn't need network access at all; `setup` likewise precedes it). The resulting `A`/`AA` are exported into *every* phase this call runs, not just `unpack` itself, matching Portage's own environment (every phase sees the same `A`/`AA`, whether or not it happens to reference them). `DISTDIR` itself is always exported too (regardless of whether `unpack` is in the chain at all), matching Portage's own unconditional environment -- Portage `unpack` (a `bin/ebuild-helpers/` script, not reimplemented) resolves `${A}`'s own files relative to `${DISTDIR}` itself, not anything this Rust code passes it directly, so omitting the export here would silently break real unpacking even after a real, successful fetch (caught empirically: a real fetched-and-verified distfile still made `unpack` report `"either does not exist or is not a regular file"` before this was added).
- The real distdir goes in as `DISTDIR`; `phase_env_vars` remaps it the way Portage `config.environ()` does (`config.py:3403-3409`): the real directory becomes `PORTAGE_ACTUAL_DISTDIR` (`doins` passes it as `--distdir`, so absolute symlinks under `doins -r` stay symlinks) and `DISTDIR` the per-package fake `${PORTAGE_BUILDDIR}/distdir`, filled by `prepare_fake_distdir` below (#330).
- Portage `config.environ()` exports `A` but pops `AA` for every EAPI >= 4 (`config.py:3331-3333`, `eapi_exports_AA`); the EAPI floor here is 5+, so `AA` is never exported (S0 finding `l2-env-aa-exported`).
- Portage `doebuild.py:1463-1469`: the fake distdir is prepared when the requested `mydo` is not `setup` (unless `FEATURES=noauto`), or is `install`/`unpack`. The first test is over the *command*, not the chain: `setup`'s own prerequisite chain starts with `pretend`. The second looks at the whole chain, because portuale's `noauto` still runs the prerequisites and `unpack` needs `${DISTDIR}/<A>`.
- Portage `_post_phase_cmds["install"]` (`EbuildPhase.py:424`/ `442-461`): real, unconditional `bin/misc-functions.sh install_qa_check install_symlink_html_docs install_hooks`, run once right after a successful Portage `install` phase -- not gated on any `FEATURES` flag, and (unlike `ebuild <file> package`'s own separate `__dyn_package` misc- functions call) never itself part of `phase_prerequisites`' own chain, so this is the one place it can run. A `doebuild()` `ebuild <file> install` reaches the same `_PostPhaseCommands` through its synchronous `EbuildPhase` (`_spawn_phase`), so the direct path QA-checks exactly like a merge (verified: host `ebuild ... install` strips an empty `dodir` via `95empty-dirs`). `EBUILD_PHASE` is popped for the spawn (`MiscFunctionsProcess._spawn` pops it from `settings`), so `use()`'s strict branch stays off -- a repo-local check like `60noop-testsuites`' `use test` reads `USE`, never dies on a missing `IUSE` flag (backlog #516). Portage `bin/misc-functions.sh`'s own `MISC_FUNCTIONS_ARGS="$@"` then unquoted `for x in ${MISC_FUNCTIONS_ARGS}` re-splits on whitespace regardless of how many real argv entries this arrived as, so passing all three names as one space-joined string here is exactly equivalent to Portage's own three separate positional args.
- Portage `EbuildPhase._ebuild_exit_unlocked` order (`EbuildPhase.py:424-438`): `_post_src_install_write_ metadata` and `_post_src_install_uid_fix` run right after `bin/ebuild.sh install` returns and **before** the `install_qa_check` post-phase commands below. That ordering is load-bearing for `SIZE`: it is the *pre-transform* image (`ecompress`/`estrip` run later), Portage's own 807 bytes for `porttest/docs` against the 372 the compressed image would give.
- Portage `EbuildPhase._commands_exit` runs `_post_src_install_soname_symlinks` immediately after that same misc-function sequence (see its own doc comment): the 6-field `NEEDED.ELF.2` (from the post-`estrip` image), generated `PROVIDES`/ `REQUIRES`, and `_inject_libc_dep`'s own implicit libc dependency (#39).

## fn run_commands
- Synchronous entry point for `ebuild.rs` (which is not itself async -- `emerge`'s own dispatch never needs an async runtime at all, so this portuale doesn't pay for one there; only this one code path does). Spins up a tokio runtime for the duration of the call -- MUST be multi-threaded (`new_multi_thread`, not `new_current_thread`): confirmed empirically (a single-threaded runtime deadlocks partway through a real multi-phase run -- brush-core's own `Cargo.toml` requires tokio's `rt-multi-thread` feature under unix, not just `rt`, which is the same thing portuale rediscovered the hard way). `PORTAGE_TMPDIR` (Portage's own `make.globals` default: `/var/tmp`; the builddir adds `portage/<cat>/<pf>` on top) is read by the caller, not internally here -- deliberately, so tests can pass a distinct value directly rather than mutating process-global environment state (`std::env::set_var` is unsound to call from parallel test threads), the same "env var read once at the CLI boundary" shape `emerge`'s own `pretend.rs` already uses for `ROOT`/`PORTAGE_CONFIGROOT` via `root_from_env`/ `config_root_from_env`.

## fn run_commands_logged
- `PORTAGE_LOG_FILE` default is `${T}/build.log`. `run_build_scheduler` passes it for parallel `--jobs` builds; the scheduler dumps the file on failure. `.gz`-suffixed paths come from `emerge_build::build_log_path` (`FEATURES=compress-build-logs`).

## fn open_log_file
- Mirrors `EbuildPhase._open_log`: the file is opened `ab`, wrapped per call in `gzip.GzipFile(mode="ab")` when the name ends `.gz`; readers (failure tail, QA scan) wrap it back in `mode="rb"`. The pump thread is that wrapper: the phase writes plain bytes into two pipes, the thread gzip-encodes them into the file. Portage defers its header to the first write too.
- Lifetime contract: declare the sink early and drop the writer holder explicitly; see the call sites (`run_one_phase_bash`, `run_misc_functions_bash`, `run_one_phase_brush`).

## fn pump_one_pipe
- Both pipes' pumps share one `GzEncoder` under a mutex; stdout/stderr chunk interleaving was never deterministic.

## fn open_log_file (pipe branch)
- `O_CLOEXEC` on the pump's read ends is hygiene only: EOF keys off the write ends.

## struct LogSink
- Opens `log_file` for append (creating it and its parent dir), returning the two write ends a phase's stdout+stderr go to plus the gzip pump guard when the path ends in `.gz` (`FEATURES=compress-build-logs`, whose `.gz`-suffixed paths `emerge_build::build_log_path` produces). Portage `EbuildPhase._open_log` (`_emerge/EbuildPhase.py`): the log file is opened `ab` and, when its name ends `.gz`, wrapped in a `gzip.GzipFile(mode="ab")` -- every phase appends one gzip member to the same file, and the failure-tail / QA readers wrap it in `gzip.GzipFile(mode="rb")` back. The pump thread below is that wrapper: the phase (a real bash child, or the embedded brush shell writing its fd table) writes plain bytes into two pipes, and the thread gzip-encodes them into the `.gz` file -- one member per `open_log_file` call, exactly like Portage's one `GzipFile` per `_open_log` call. A phase that writes nothing appends no member at all (Portage's header is deferred to the first write too). Lifetime: the guard MUST drop after the phase's write ends close (child waited + parent `Command` dropped, or brush `Shell` dropped), otherwise its join hangs waiting for EOF. Declare the sink early and `drop` the writer holder explicitly -- see the call sites. Joining first also guarantees the `.gz` member is finished before any reader (failure tail, next phase's append, QA scan) touches the file.

## fn can_skip_source_phases (#456)
- Portage `_emerge/EbuildExecuter.py::_can_skip_source_phases` (3.0.82.2, verified identical in host site-packages and `pmtest/3rdparty/portage`): skip `unpack`/`prepare`/`configure`/`compile`/`test` when `noauto` not in FEATURES, `live` not in `settings["PROPERTIES"]`, `configdict["pkg"]["A"]` empty, `DEFINED_PHASES` misses every skippable phase, and no `.src_patches` stamp. `src_install` always runs. The skip is flag-independent (fires on default, `--quiet-build=n`, `--verbose` alike); the `--quiet-build=y`/`-q`/`-jN` hiding is the separate background-capture path (`merge_run.rs` `capture_log`, already shipped).
- Oracle `LLM/evidence/2026-10-21-b456/` (setup.sh/cells.sh, host `emerge` 3.0.82.2 on the long-clean-multi `schedparent` root): default/`=n` cells print only `>>> Emerging`, `>>> Install ... into`, `>>> Completed installing ...`, `Final size`, `>>> Installing`/`>>> Completed`; `=y`/`-j2` background cells never showed phases anyway; the earlier plan draft's `PORTAGE_QUIET`-threading predicate was flag-only and could not reproduce this (a `=n` run of a sourceless package still skips; a default run of a defining package like `dev-util/good` still prints -- b437 evidence) -- content-based skip is the only faithful shape.
- Gate inputs: `noauto` via `feature_token_present` on the run's resolved FEATURES; `live` via `restrict_and_properties` (USE-reduced `PORTAGE_PROPERTIES` semantics, matching `doebuild.py:243`'s own live-unpack gate; Portage's `EbuildExecuter` reads `settings["PROPERTIES"]` whose reduction path differs in a USE-conditional corner nobody ships -- noted, not chased); `A` is the just-fetched list (`a_is_empty`, computed before the fake-distdir block moves `a`); `DEFINED_PHASES` via `repo_aux_metadata` (md5-cache, eclass stack included; missing metadata is conservative `false`); `.src_patches` via `setup`'s recording in `bin/phase-functions.sh` (evaluated lazily at the first skippable phase, after `setup` ran).
- Plumbing: `skip_noop_src_phases` on all three `RunCommands*Args` structs, `true` only at the two merge-path call sites (`ebuild_merge::run_merge_with_hook`, `emerge_build::scheduler` parallel leg); direct `ebuild`, `run_package` (also serving `--buildpkgonly`, mirroring `doebuild()`), and all unit-test literals pass `false`. EAPI floor note: old-EAPI `prepare`/`configure` absence never matters here -- skipping runs only `install` regardless. (#458 amends the `run_package` half: it grew its own `skip_noop_src_phases` field, `false` for direct `ebuild <file> package`, `true` on the scheduler-driven `--buildpkgonly` path; see below.)

## fn spawn_bash_script (demoted pre_exec namespace block, #630)
- The `droppriv: Some(..)` path builds the command with `direct_command`/`phase_argv` (the `unshare(1)` shim would demote the wrapper process instead of the phase, and carries `--map-root-user`), then does namespace setup in the child's own `pre_exec` while still root: `clone_flags_for(&iso)` → `libc::unshare` (loud `Err`; post-validation failure is TOCTOU-only, a deliberate divergence from Portage's warn-and-run-unisolated), `mount --make-rslave /` when `mount || pid` (result ignored, Portage warns at `process.py:1215-1225` and `pre_exec` cannot print), `sethostname("localhost")` when `net` (result ignored, `:1246-1261`; the `CString` is parent-built and moved into the closure), then the unchanged `setgid → setgroups → setuid → umask`.
- Nothing allocates, spawns or prints in the child, and the whole block is `#[cfg(target_os = "linux")]`-gated. The `pid` case continues into the fork dance below (#635), which mounts the namespace's own `/proc`.

## fn configure_loopback_netlink (#636)
- Raw `AF_NETLINK` syscalls on stack buffers — no subprocess can run in `pre_exec`. Sequence mirrors Portage `_configure_loopback_interface` (`process.py:838-871`): `RTM_GETLINK` for the name `lo` → parse `ifinfomsg.ifi_index` from the reply → link-up (`IFF_UP` change+flags) → `10.0.0.1/8` → `fd::1/8` iff the caller's `has_ipv6` is true; one ACK/`NLMSG_ERROR` drained per request. Builders live in `sandbox.rs` (`lo_nl` consts, `repr(C)` structs, `lo_*_msg`), byte-identical to `netlink.py` `Struct.pack` (`:30-34, :94-114`); the unit test pins header fields and address bytes, the two root-gated spawn tests pin a real TCP round-trip (S0 ruling: `lo` flags `0x9` in both states and a succeeding `bind` are NOT discriminators — only `connect` is).
- No bind/connect on the netlink socket: the kernel autobinds on first send and plain `send`/`recv` is enough for one `lo`, so Portage's `(0, 0)` bind+connect (`netlink.py:64-72`) is skipped. The reply parse is fixed-offset (`nlmsg_type` at 4, `ifi_index` at 20) and any other reply — short read, `NLMSG_ERROR` — means "no `lo`"; Portage's `parse_message` raises there instead.
- Divergence as shipped by #636, superseded by #638: the ACK/`NLMSG_ERROR` code was ignored, so a failed request was silent and the later steps still ran, where Portage raises on a nonzero code (`netlink.py:52-56`) and `_configure_loopback_interface` prints `Unable to configure loopback interface: <errno>` and abandons the rest (`process.py:867-871`); #638 now reports the first failure and stops (see its entries below). The same silence still covers the `mount`/`sethostname` failures #630 records. The reply buffer is 512 B (Portage peeks then re-reads 8 kB): truncation keeps the head the fixed offsets read, enough for one `lo` `RTM_NEWLINK`.

## fn loopback_fail_at_env (#638)
- Parent-side `PORTUALE_TEST_LOOPBACK_FAIL` → `fail_at`: `""`/unset/garbage → `0`, `getlink` → 1, `linkup` → 2, `v4` → 3, `v6` → 4. The child cannot read the environment (no allocation in `pre_exec`), so the `u8` is computed before the spawn and moved into the closure. Test-only hook; the injected-failure test is serialized by `LOOPBACK_HOOK_LOCK` because the variable is process-global.

## fn loopback_warn_table (#639)
- Portage's warning text verbatim (`process.py, _configure_loopback_interface (:867-871)`): `Unable to configure loopback interface: {strerror}\n`, one line per errno `1..=135` at index `errno - 1`; the failed step is deliberately unnamed, as in Portage. Parent-built once per spawn (`spawn_bash_script`, beside `hostname`/`has_ipv6`/`fail_at`, moved into the closure by reference) because the child cannot allocate. Bodies come from XSI `strerror_r` into a caller-owned 256-byte stack buffer (`CStr::from_bytes_until_nul`), not `libc::strerror`'s shared static buffer and not `io::Error`'s Display, which would append ` (os error N)`; a nonzero rc yields `Unknown error N`. Pinned by `loopback_warn_table_matches_portage_text` (len 135, prefix, one trailing newline, no `(os error` suffix); the body is the C library's, i.e. `os.strerror`'s text by construction, not by an oracle run (hence only the stable prefix/newline are asserted).

## fn loopback_warn_line (#639)
- The child's lookup, shared by the `pre_exec` site and the unit test: `errno.checked_sub(1).and_then(|i| table.get(i as usize)).map(Vec::as_slice).unwrap_or(LOOPBACK_WARN_FALLBACK)` — no allocation, no indexing panic. `errno` rides as a `u8` (real Linux errnos stay below 134). Pinned by `loopback_warn_lookup_falls_back_out_of_range` (errno 0 and 200 → the fallback, `ENOENT` → its table line).

## const LOOPBACK_WARN_FALLBACK (#639)
- `b"Unable to configure loopback interface: Unknown error\n"` — a `const` so the child can borrow it; deliberately elides the errno number and `strerror` body because building either would allocate in `pre_exec` and the arm is unreachable in practice. Same Portage prefix, so a reader still greps one shape.

## fn configure_loopback_netlink (#638 first-failure report)
- Signature `(has_ipv6, fail_at) -> (u8, u8)`: step `0` ok, `1` GETLINK, `2` link-up, `3` v4, `4` v6; the first failure returns immediately and later requests never run — Portage's warn-and-abandon (`process.py:867-871`). `errno` is truncated to a byte so it can index `loopback_warn_table` in the child (#639 deleted the pipe that used to carry it); real Linux errnos stay below 134, so no bits are lost.
- Per-ACK nonzero `NLMSG_ERROR` is that step's failure (Portage `parse_message`, `lib/portage/util/netlink.py:52-56`); GETLINK failures carry the kernel's errno: socket/send/recv error, `EINTR` included (safe direction: warning plus no-`lo`), short reply, wrong type, or zero ifindex. A malformed non-error reply is `EPROTO`; an `NLMSG_ERROR` reply names its own errno.
- `fail_at` short-circuits the named step before its syscall (the test hook); it can only be set from the parent (`loopback_fail_at_env`). The caller reports the pair with one child-side `write(2)`: `errno` is a `u8` table index for `loopback_warn_line`, not a pipe payload (#639 replaced the pipe). The `(step, errno)` shape and every earlier refusal/errno mapping are unchanged by #639.

## fn spawn_bash_script (loopback report via child-side write(2), #639/#640)
- Demoted + `net` only, `step != 0` after `configure_loopback_netlink`: one `libc::write(2, line.as_ptr(), line.len())` of `loopback_warn_line(&table, errno)` pre-fork and pre-`execve`, destination fd 2, result ignored (`let _`: a report failure never fails the spawn). This is the sole reporting exception to the no-print rule — no `println!`/`print!`, stdio, allocation or subprocess runs in the child, and `mount`/`sethostname` failures stay silent.
- Why the child can report at all: inside `pre_exec` fd 2 is the `Command`-configured stderr (`dup2` runs before hooks on rustc 1.99.0; S0 `LLM/evidence/2026-11-01-639-loopback-report/s0-fd2-preexec.log` probed a `stderr(File)` command), so one write reaches the right place per placement — `Capture` the build-log pipe (one gzip member under `compress-build-logs`), `Tee` the shared tee pipe (our stdout + log, in order, because the warning precedes all phase output), `Inherit`/`Foreground` the terminal. Only the `File` destination is proven; `Tee`'s pipe and `Inherit`'s untouched fd 2 follow from the same `dup2` ordering by extrapolation (low risk, not probed). A toolchain that reorders `dup2` after hooks degrades to the parent stderr: visible, never lost.
- The #638 pipe is deleted, not kept beside this: `pipe2(O_CLOEXEC)` pair, the closure's write `File` (its 2-byte `[step, errno]` payload gone), the post-wait 2-byte read with its EOF/`EINTR` reasoning, and the parent `OpenOptions::append`/`eprint!` split are all gone, so no path can bypass the gzip pump or land after the phase output. The only new failure mode #638 introduced (pipe creation) went with it; the spawn now has none.
- Pins: root-gated `demoted_loopback_failure_warns_and_continues` (injected `linkup`: rc 0, no `10.0.0.1` fib_trie route, warning is `lines().next()` — head, pre-exec; clean control: route + `LOOPBACK=1` + no warning) and `demoted_loopback_warning_survives_gzip_log` (same injection through `Capture` to `build.log.gz`; `MultiGzDecoder` reads the member to end carrying the warning and `PHASE_RAN=1`). Serialized by `LOOPBACK_HOOK_LOCK` (the hook is process-global); both SKIP without root.

## fn spawn_bash_script (demoted netns loopback via netlink, #636)

## fn spawn_bash_script (demoted pid fork dance, #635)
- Portage re-execs the phase through `bin/pid-ns-init` (`process.py:1111-1145`); this is the same init shape without a helper binary. After the raw unshare the demoted child blocks `SIGINT`/`SIGTERM`/`SIGHUP`/`SIGTSTP`/`SIGCONT` with `pthread_sigmask` **before** `fork` (nothing can land between fork and the loop; stack-local `sigset_t`, so parallel `JOBS>1` spawns cannot cross-forward), then forks. The grandchild is pid 1 by fork order: `mount --make-slave /proc` then a fresh `proc` mount (`process.py:1228/1226-1245`, either failure is `Err` like Portage), unblock the inherited mask (`execve` never resets it), fall through to demotion, exec. The middle: own `setsid` (Portage `pid-ns-init:96`), `close_range(3, ..)` after the fallible `setsid` so `spawn()` gets the error-pipe EOF and the scheduler can still kill mid-phase (pre-5.9 `ENOSYS` degrades to the late return, still correct), then a zero-timeout `sigtimedwait` forward loop plus `waitpid(WNOHANG)` polling and a 10 ms `nanosleep`: normal exit re-`_exit`s with the child's code, a signalled child gets `SIG_DFL` + unblock + self-`kill` (Portage `pid-ns-init:140-144`, not the unreachable trailing return), `_exit(127)` fallback. The middle never returns from `pre_exec`; a `setsid` failure kills the grandchild before `Err` so no detached phase is left.
- Parity dispositions: the utf8 re-exec (`pid-ns-init:9-14`) has no analogue (no Python on this path); the autogroup-nice restore (`:93-107`) is moot (portuale never calls `nice`/`setpriority`); `TIOCSCTTY` (`:107-116`) is not mirrored and cannot diverge — every demoted phase's stdout is a `Tee`/`Capture` pipe, never a tty, and on an inherited tty after `setsid` the ioctl answers `EPERM`, the case `pid-ns-init` swallows.

## fn spawn_bash_script (placement override, #635)
- A demoted+pid spawn takes `PhasePlacement::ParentGroup` instead of `for_phase(argv_word)`, Linux-gated as `cfg!(target_os = "linux") && droppriv.is_some() && iso.pid`. `spawn_trackable` chains `pre_exec` hooks in registration order, so a `NewSession` `setsid` hook would run in the grandchild and split it out of the middle's process group, making a group-kill miss the phase. `ParentGroup` adds no second hook, and its kill is by pid (`scheduler_registry.rs:157-160`), so the recorded middle (session leader) is the target.

## fn spawn_bash_script
- The `droppriv: Some(..)` `pre_exec` ends with `libc::umask(0o22)` after the `setuid` block (#631), mirroring `_exec`'s `setgid → setgroups → setuid → umask` (Portage `process.py:1265-1274`; keyword from `doebuild.py:2178`); it sets the demoted child's own mask, whereas `UmaskGuard` (`run_phase.rs`) only restores the parent process umask around an in-process brush phase.
