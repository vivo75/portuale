# crates/portuale/src/ebuild_phases/package_env.rs
`package.env` matching and its incremental variables.

## const PACKAGE_ENV_INCREMENTALS
- Full Portage list (`const.py`).
- Portage `const.INCREMENTALS` (`3rdparty/portage/lib/portage/const.py:125`): a key in this list is appended to the container's current value by `_grab_pkg_env`, then folded onto the lower layers by `regenerate()` (`config.py:2778-2825`: `-*` clears the set, `-tok` removes, sorted union). Kept complete even though the acceptance gate below drops most of them, so a future gate change cannot silently lose the semantics.

## fn package_env_key_allowed
- Portage `_grab_pkg_env`'s per-key acceptance gate (`config.py:2269-2300`), minus the keys portuale's own phase pipeline owns: * `USE` is Portage's special case (popped before the call, re-appended after `package.use`); portuale folds it via `Config::package_env_use`, so it must not also appear here. * `ENV_BLACKLIST` is Portage's `env_blacklist` (it already covers `PKGUSE`, the only `protected_pkg_keys` member). * `ENVIRON_FILTER` keys Portage accepts into the config but never exports to a phase (`config.environ()`, `config.py:3263-3350`); portuale's `package_env_vars` layer only exists in the phase env, so they are dropped. * `PORTUALE_COMPUTED` keys portuale's own phase runner computes and must always win (`FEATURES` and `PORTAGE_TMPDIR` are filed residues #98/#99; `PATH`, `DISTDIR`, `D`, … are owned by design). * `profile_only_variables` is the profile's dynamic `PROFILE_ONLY_VARIABLES` (`config.py:724-733`; `ARCH`, `ELIBC`, `IUSE_IMPLICIT`, `USE_EXPAND*`, …). Everything else is accepted, including empty values (Portage blanks a variable with `VAR=""`) and `__`-prefixed names (Portage does not strip them here).
- Portage `_grab_pkg_env` (backlog #95) rejects `protected_keys` ∪ `non_user_variables` (PROFILE_ONLY ∪ env_blacklist ∪ CONFIG_PROTECT); portuale additionally rejects its `ENVIRON_FILTER` export-filter list here -- a deliberate conservative narrowing, except for the compression family below. Portage honors a per-package `BINPKG_COMPRESS` (and its FLAGS sisters: `doebuild.py:697-750` reads all three from the package's own `mysettings`, and none is in Portage's `non_user_variables` -- S0 B-xpak proves gzip magic), so backlog #147 S2 exempts exactly that family; every other `ENVIRON_FILTER` key stays rejected. `PORTAGE_BZIP2_COMMAND` is listed for symmetry only: it is not on Portage's `environ_filter`, so accepting it here exempts nothing.

## fn fold_package_env_incremental
- A package.env `-tok` cannot prune a calling-env token (verified: calling-env `-tok` prunes a package.env addition). `base_lower` is `""` when the run-wide env lacks the key.
- Portage `regenerate()`'s incremental fold (`config.py:2735`, `:2778-2825`) for one key, in Portage's layer order `[base-lower, pkg, calling-env]`: the already-folded lower layers' tokens, then the package.env value's tokens in order, then the calling environment's tokens in order (`-*` clears, `-tok` removes), sorted and space-joined. The calling env folds **last**, so a `-tok` there prunes a token a package.env file added (backlog #101, S0 cell B), while a package.env `-tok` cannot prune a calling-env token. Re-applying the calling-env tokens after a base that already folded them in is idempotent (set add/remove), so `base_lower` may be the caller's own already-folded value for the key (`""` when the run-wide env doesn't carry it).

## fn match_package_env_vars
- Atom-match `package_env_vars` (Portage `_grab_pkg_env` folding a matching `/etc/portage/package.env` entry's env file into `configdict["pkg"]`) against one `cat/pkg-ver:slot/sub` string. The container follows Portage exactly: files of one entry in order, matching entries in list order (portuale keeps parse order; Portage applies `ordered_by_atom_specificity`, a pre-existing narrowing), an incremental appends, a scalar replaces, an empty value blanks. Incrementals are then folded in Portage's layer order `[base-lower, pkg, calling-env]` (`regenerate()`), and a package.env **scalar is dropped when the calling environment carries the same key**: Portage's `USE_ORDER` puts the `env` layer above `pkg` (`config.py:1031-1035`), so the process value wins (backlog #101, S0 cell A). `calling_env` is the same source `phase_environ`'s step 2 uses (`portage_profile::config_env_all()`), compared by key presence — *not* `base_env` as a whole, which also contains config scalars a package.env value legitimately outranks. Shared by the merge path (`emerge_build::entry_package_env_vars`, matching a resolved graph entry and passing `options.build_env`) and the standalone path below (matching the ebuild's own md5-cache identity and passing the narrow base -- no resolved graph needed). Both paths thread the real calling environment, so the precedence rule holds on both: the S0 capture shows the standalone path is inverted today too, the same bug in this shared function (S2's base replacement is a separate change and is untouched here).

## fn match_package_env_scalar_raw / incremental_raw
- The gated phase-env path (`match_package_env_vars`) keeps its own loop; per-key recomputes where a flat pair would corrupt — `PORTAGE_TMPDIR` and `FEATURES` (both `PORTUALE_COMPUTED`) — match raw and re-derive instead.

## fn standalone_package_env_lookup
- Shared by the standalone `PORTAGE_TMPDIR` and resolved-`FEATURES` lookups so path-parsing happens once. Uses `resolve_standalone_config` (the `package_env_vars` table) and `standalone_cpv_slot` (md5-cache `SLOT`).
- The resolved `Config` and `cat/pkg-ver:slot/sub` identity Portage `_grab_pkg_env` would match, for an ebuild with no resolved graph entry (standalone `ebuild <file>`/`qmerge`): the ebuild's own path gives the `category`/`pf`, [`resolve_standalone_config`] the `package_env_vars` table, [`standalone_cpv_slot`] the md5-cache `SLOT`. `None` outside a repo checkout or on an unparsable path -- shared by [`resolve_standalone_portage_tmpdir`] (#99) and [`resolve_standalone_resolved_features`] (#130) so the path-parsing only happens once.

## fn match_package_env_scalar_raw
- Atom-match a single `package.env` key against `cpv_slot` and return the container value with Portage `_grab_pkg_env`'s append semantics but WITHOUT the acceptance gate and WITHOUT folding: matching entries in list order, files of one entry in order. Two flavours, mirroring Portage's container behaviour exactly: scalars replace (last matching file wins; `None` when nothing matched), incrementals append (`container[k] += " " + v`). The caller owns the key choice and the fold: `match_package_env_vars` (the gated, phase-env export path) keeps its own loop, while per-key recomputes a flat pair would corrupt — `PORTAGE_TMPDIR` (#99) and `FEATURES` (#98), both `PORTUALE_COMPUTED` — match raw and re-derive instead.
