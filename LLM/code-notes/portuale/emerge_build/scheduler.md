# crates/portuale/src/emerge_build/scheduler.rs
The parallel build scheduler (`--jobs`): concurrent `install` builds, serialized vdb merges.

## fn build_one_source_entry
- Ports Portage's `_emerge/EbuildBuild` (+ `EbuildBinpkg`): the `install` phase chain and any `--buildpkg` binpkg for one source entry, WITHOUT the vdb merge. Returns the located ebuild path for `merge_one_built_entry` to reuse. Safe to run from a scheduler worker thread: every build gets its own `${PORTAGE_BUILDDIR}` (`<tmpdir>/portage/<cat>/<pkg>-<ver>`) and `run_commands` passes the environment explicitly (no `std::env::set_var`). The log tail goes to `${T}/build.log` (Portage's `PORTAGE_LOG_FILE`).
- The build half prints Portage's `MergeListItem._start` per-package line (backlog #177) when the build starts, exactly where Portage starts the `EbuildBuild` chain.
- Per-package `PORTAGE_TMPDIR` (backlog #99): log, pre-clean and phase chain all live under the matched value.
- `prepare_build_dirs` truncates a stale build.log; see `logs.rs` for why truncation (not deletion) matters with `PORTAGE_LOGDIR`.
- A captured parallel build runs through Portage's `bash` (not the embedded `brush`): Portage uses bash for builds regardless of portuale's default backend, and its stdout+stderr redirect to `build.log` cleanly at the OS level.
- Pre-clean ports Portage's `_emerge/EbuildBuild._start_pre_clean`: the `clean` phase runs before every build unconditionally (`noclean` only skips the post-merge clean). Backlog #42; see `merge_one_source_entry` for the full grounding.
- The binpkg `USE` field is Portage's `Package.use.enabled` as `_pkgindex_entry` writes it: not the ebuild's default, but the `use_flags_display`-derived `USE` env var `entry_build_env` already resolved for the phase, reused verbatim rather than re-derived.
- Per-package `FEATURES` (backlog #130): the shared run-wide `PackageOptions` does not see the entry's `package.env` `FEATURES` fold, so clone it and re-derive the binpkg-affecting tokens (`binpkg-multi-instance`/`buildpkg-live`/`binpkg-signing`) from the same per-entry folded list `entry_resolved_features` computes for the phase env.
- `BUILD_ID` gate ports Portage's `EbuildBinpkg._start` (backlog #147 S1 ruling (i)): the binpkg layout is run-wide-only (Portage's bintree binds its allocator once), while the `BUILD_ID` export follows the entry's own token (Portage `EbuildBinpkg.py:47-48`).

## fn merge_one_built_entry
- Ports Portage's `_emerge/EbuildMerge` (always serialized; only the build runs in parallel). Checks the same `${PORTAGE_BUILDDIR}/.installed` marker `install` leaves behind; same-slot replace via `merge_after_install`.
- The `>>> Jobs:` `maxval` lives on the run's `StatusDisplay`, computed by the caller (backlog #197) -- see `run_source_merge`.
- Per-package `FEATURES` (backlog #98): the merge half's gates (`feature_enabled`, the vdb-environment regeneration) read the per-entry folded list; `set_resolved_features` re-derives the merge-time tokens from it.
- Prints Portage's `PackageMerge._start` per-package line (backlog #177) right before the serialized vdb merge, exactly where Portage starts `EbuildMerge`.
- Reusing the captured `install` log path (`MergeOptions::log_file`) is what keeps `pkg_preinst`/`pkg_postinst` output appended after `install`'s in one continuous per-package log; previously it leaked straight to the terminal under `-jN`/`--quiet-build`.
- Post-merge clean ports Portage's `dblink.merge()` tail (`dbapi/vartree.py:6183-6198`): the `clean` phase runs after a successful merge unless `FEATURES=noclean` (the postinst-failure gate collapses into `status != 0`). `run_qmerge` itself deliberately does not clean, because Portage's `doebuild qmerge` implies noclean. Backlog #42.
- Prints Portage's `PackageMerge._install_exit` `Completed (N of M) cpv::repo` line (backlog #177) where portuale used to print its own `merged.` line.
- A postinst failure (#444) prints `Completed` anyway and returns the `postinst failed` marker (see `merge_one_source_entry`); the world record and the post-merge clean below are both skipped for it. Post-merge clean ports Portage's `dblink.merge()` tail (`dbapi/vartree.py:6183-6198`) -- which also never cleans after a postinst failure (bug #704866 rule) -- so the clean gate reads `outcome.status == 0`, not the marker.

## fn run_build_scheduler, fn system_loadavg_1min
- Ports Portage's `_emerge/Scheduler.py` core. Portage merges one package at a time to avoid `collision-protect` / `CONTENTS` races. Bare `--jobs`/`-j` maps to `usize::MAX` (Portage's `max_jobs is True`).
- The load gate is shared with `regen.rs`'s `--jobs` dispatch (Portage's `PollScheduler._can_add_job` gates `MetadataRegen` the same way). A non-Linux host or sandboxed `/proc` yields `0.0`.
- `RunBuildSchedulerArgs.policy` is the director's `SchedulerPolicy` trait: a capped (`LoadAwarePolicy`) or uncapped (`UnlimitedPolicy`) scheduler is one caller-side value, never a loop change here.
- Known, documented cuts (same "narrow v1" pattern as the rest of this module), current as of the capture/kill slices (the old paragraph predates them and is superseded on these two points): builds used to inherit phase output straight to the terminal and interleave under `-j` > 1 (Portage captures per-package build logs); a non-`--keep-going` failure used to return immediately but wait for already-running builds via `thread::scope` join instead of killing them. (The old paragraph also said each `run_commands` call spins up its own tokio runtime; `run_commands_logged` now goes through a shared runtime.)
- `deps` reconstruction: `d`'s `required_by` lists the cps that depend on `d`, so the edge is `d -> r` for every `r` in `d.required_by`.
- The per-call (not process-wide) scheduler registry exists so an unrelated `cargo test` thread's subprocess is never reachable here; see `ebuild_phases::SCHEDULER_REGISTRY`.
- Per-run `Scheduler._pkg_count` (backlog #177): every build/merge half prints its entry's own snapshot. The worker closure is `move` and cannot borrow the map, so the snapshot is copied.
- Dispatch asks the policy's two halves in trait-contract order (`max_jobs`, then `should_start`); Portage's `Scheduler._run` never gates the first build, so the DAG cannot deadlock. Identical decisions to the old inline `in_flight < jobs` + load-average gate for `LoadAwarePolicy`.
- Display event order ports Portage's `_schedule_tasks_imp` (`running = self._jobs` -- the `>>> Jobs: 0 of N complete, R running` line): the `>>> Jobs:` line prints at dispatch, before the worker's `>>> Emerging` line. On the build-ok path the `running` drop (`_build_exit` tail) fires before the serialized merge; on the merge-failure path only `failed` rises (`_merge_exit` / `_do_merge_exit`, `Scheduler.py:1543-1561`; no `running` event fires there because the build slot is already free from the tail above, and the `Some` arm fires none either, so each failure prints exactly Portage's lines); on the build-failure path `failed` rises before the `running` drop (`_build_exit` failure arm, `Scheduler.py:1641-1658`). Portage also prints a `>>> Failed to emerge ...` tail between the two on build failure; portuale's source-build failure rendering is unchanged by that slice.
- The kill path ports Portage's `_keep_scheduling`/`_terminate_tasks` (`PollScheduler.py:106-126`): once any package fails without `--keep-going`, Portage stops scheduling new work and sends kill signals to what is already running rather than letting it finish. `return Err(e)` does the first half (the outer loop never starts another build); `kill_registered_children` does the second, since `std::thread::scope`'s implicit join would otherwise wait for every in-flight build to run to completion, wasted work whose result is discarded regardless.
- Resume-list shrink on success ports Portage's serial-loop behavior (`Scheduler.py:1595-1602`): order-free removal by value, so parallel completion order is fine. `_merge_exit`'s `curval += 1` becomes `display.merge_finished()`.
- A postinst failure (#444) ends the pass (`halted`, Portage's `_keep_scheduling` gate) without dropping dependents: the merge landed, so they stay dispatchable -- the failed entry joins `merged` for dispatch purposes (like `Scheduler._task_complete`) but the saved resume list keeps it (like `vartree`, which removes it only on a clean return). What never ran re-plans in a resumed pass (`ledger.resuming`, `display.reset_for_resume`, progress remap, `resave_resume_list`); the dropped-notice epilogue skips its own `resuming` banner when a resume pass already printed one.

## fn worker_panic_message (#376)
- The scheduler keeps its own `tx` clone alive for the whole loop, so `rx.recv()` never reports a closed channel. A worker thread that panicked therefore sent nothing and the run waited forever (seen 2026-10-17: five scheduler tests parked in `recv` with no worker thread alive, at 0 CPU; the panic text was hidden by the test harness's output capture). The worker closure now runs under `catch_unwind` and sends `Err("<cat>/<pkg>: build thread panicked: <payload>")`.
- Known trigger: the stale-binary guard in `self_exe.rs` panics inside a worker when `target/release/portuale` is older than the sources. A `/tmp` at 98% inode use (leaked `portuale-gpkg-build*` and `portuale-vdbview*` directories) is the other likely trigger: `tempdir` creation panics.

## fn land_built_entry, fn note_landed (#512)

The up-front pretend pass itself moved to `pretend_pass.md` (#577):
the shared generic runner over `SourcePretendEntry`, each entry's
`run_pretend` composing its `${T}` log from a clean-proof staging
capture. What stays here is the `stdout`-lock replay sink and the single
`finish_failed_pretend` call. The `>>> Running pre-merge checks for
<cpv>` line ports Portage's `_status_msg("Running pre-merge checks for
...")` (`Scheduler.py:1085`); the pass's `max_jobs` clamp is
`pretend_max_jobs` now.
- Pre-#577 shape (superseded by `pretend_pass.md`, kept for provenance).
  Ports Portage's up-front `_run_pkg_pretend` (commit `1c8b75d73`): every build-bound entry runs `clean` + the `pretend` chain (up to `max_jobs` threads, each captured to `pretend-<pid>-<idx>.log` under the run tmpdir), then the captures replay to the sink in merge-list order and are deleted — Portage's buffered-then-replayed shape, including unlinking. A failure aborts before any build starts (Portage returns `FAILURE` before `_add_packages`, regardless of `--keep-going`). The replay sink is `stdout` on a non-pretend run (`pkg_pretend` output bypasses `--quiet`/`--jobs`, like Portage) and an injectable `&mut dyn Write` otherwise, so the order pin does not need process-stdout capture. The build then starts at `setup` (`skip_pretend`, see `ebuild_phases/commands.md`); the serial merge loop keeps the whole chain (pre-3.0.83 serial divergence, out of scope). Binary entries never reach this scheduler (the mixed dispatcher routes them to `merge_binpkg`, whose own pretend stays as-is).
- `land_built_entry` is the old recv-arm merge extracted verbatim (slot-free `build_finished`, serialized `merge_one_built_entry`, `job_failed` only on merge failure). `note_landed` is the old success/failure bookkeeping extracted verbatim, plus clearing the merge-wait queue on a stopping failure: terminated runs never drain it (Portage `8ac550470`, bug 961044). SIGINT itself needs no queue handling — `ExitOnSignalGuard` exits the process, so no further merge can start; oracle shape `13-sigint`.
- Merge-wait wiring in `run_build_scheduler`: the wait set comes from `merge_wait_set` over the resolved `@system` set plus `features_hold_all_merges` for default `FEATURES`; a finished gated build always queues (no in-flight condition, `Scheduler.py:1833-1836`) and the queue drains whole, FIFO, per idle episode, before any dispatch (`Scheduler.py:2245-2280` plus the `_merge_wait_scheduled` build gate at `:2471`). Portage's breaks before/after a system package only serialize queue-to-queue moves and are no-ops under portuale's always-serial merges. `StatusDisplay::set_merge_wait` feeds the `N merge wait` arm of `>>> Jobs:` (the pure `jobs_line` already rendered it; the display hardcoded `0` before). Dispatch reads `blocking_deps`, so only cyclic post-merge edges differ from the old `deps`.
- `_unsatisfied_system_deps` gating (`Scheduler.py:1686-1730`, `:2472`) is a deliberate cut: it only blocks new builds while other jobs run with unmerged runtime deps of a started system merge, a shape no scheduler test has (fixture runs start from an empty vdb; the wait-set members under test have no dependencies). Next free backlog number at filing time: #581 (verify with grep; #575-#580 are this plan's). The discriminating shape for the follow-up is a wait-set member with an unmerged runtime dep plus an unrelated build under `--jobs 2`. Evidence `LLM/evidence/2026-10-25-review/t2/S0.md` §4.

## display slot on queue (#512)
- A queued build frees its `running` slot at build exit (`build_finished` in the recv arm, before the gate), not at merge time: Portage's `_build_exit` tail drops `running` unconditionally, and the `>>> Jobs:` line would otherwise claim two builders while one builds. `land_built_entry` therefore never touches `running`; the drain path lands without it (already freed at queue time).
