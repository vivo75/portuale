# crates/portuale/src/binpkg/metadata.rs
Reading gpkg and xpak metadata for the `$PKGDIR` scan.

## fn read_gpkg_metadata
- Ports Portage's `portage.gpkg.gpkg.get_metadata()` / `unpack_metadata(want=None)` (`lib/portage/gpkg.py:838-870`), narrowed to the local metadata read: a `.gpkg.tar` is a plain (uncompressed) tar whose members are `<basename>/{gpkg-1, metadata.tar[.<comp>], image.tar[.<comp>], Manifest}` (+ optional `.sig` files). Returns the `metadata/<KEY>` -> value map (Portage `_strip_metadata_prefix` over the inner `metadata.tar`'s own members), each value UTF-8 with surrounding whitespace trimmed; a member whose bytes aren't valid UTF-8 (`environment.bz2`) is skipped, not an error. Values have the same shape as a vdb aux file / `read_md5_cache` entry.
- This reader is the "populate the pool" path (Portage `bintree._populate_local` / `get_metadata`); it trusts the container the same way the `Packages`-index reader "trusts the index outright" (Portage `FEATURES=pkgdir-index-trusted`). The merge path (`extract_binpkg`) runs the Portage `Manifest` digest check first -- see `verify_gpkg_manifest`.
- Still required here: the `gpkg-1` version marker's presence (Portage `_get_inner_tarinfo`'s own `InvalidBinaryPackageFormat` guard) and, since `#56`, that every trusted member name is a regular member (`read_outer_members`, since `#58` S5 from the tar header instead of an extracted `symlink_metadata`): a symlinked marker/metadata/`Manifest` member is an error naming the member and its type, never a follow (see `TEST/findings/l2.md` "## #56 S0" -- before this, this path listed the host `/etc` through a symlinked prefix and read a host file through a symlinked `Manifest`).
- Since `#58`, the inner `metadata.tar` is read in process with the `tar` crate (`read_inner_metadata`) (see `TEST/findings/l2.md` "## #58 S0").
- Step 1 (`#58` K7/S5): the outer container is read in process -- the `gpkg-1` validity marker, the one-level structure and `#56`'s regular-member check all come from the tar headers, before anything is written or decompressed. Step 2 (`#58` S1/K0): the member's stream goes straight into the `tar` crate (through the decompressor where needed) and every entry is resolved exactly like Portage `tarfile.extractfile`; nothing is written to disk before it is accepted.
- Symlink discipline history: the outer member check comes from the tar header (not an extracted `symlink_metadata`), and the inner `metadata.tar` is read in process with the `tar` crate, porting Portage's `tarfile.extractfile` (symlink/hardlink resolves inside the archive or errors; directory/FIFO/device members and names outside `metadata/` error). Before this, the extracted tree was walked with `Path::is_file`/`fs::read`, so a symlinked prefix listed the host `/etc`, a symlinked `Manifest` read a host file, and an inner `metadata/DESCRIPTION -> /etc/hostname` symlink returned the host file's bytes (see `TEST/findings/l2.md`).
- Deliberate cut: NO GPG `.sig` check on this populate path; the merge (`extract_binpkg` -> `verify_gpkg_manifest`) enforces the Portage `request_signature` / `verify_signature` policy via the system `gpg` (see `GpgVerify`). A container that carries `.sig` members still has its cleartext `DATA` digests verified at merge time (what an unverified read amounts to is Portage's own `binpkg-ignore-signature` behaviour); Portage's `unpack_metadata`/`get_metadata` verify (`_verify_binpkg(metadata_only=True)` still checks the metadata `.sig` + Manifest), so a corrupt-or-foreign-signed binpkg resolves in portuale's pool but fails at merge. The resolve side stays deterministic and `gpg`-free on purpose.

## fn read_xpak_metadata
- Ports Portage's `portage.xpak` `.tbz2` reader (`tbz2.scan` + `getindex_mem`/`searchindex`, `lib/portage/xpak.py:395-460` / `234-266`). Values carry a trailing newline like a vdb aux file. Codec-agnostic: the trailer is raw, whatever compressor produced the tarball.

- Layout: `"XPAKPACK"  be32(indexsize)  be32(datasize)  <index>  <data>  "XPAKSTOP"  be32(infosize)  "STOP"`, where `infosize` is the length of the `XPAKPACK`…`XPAKSTOP` segment and `<index>` is a flat run of `be32(namelen) name be32(datapos) be32(datalen)` records into `<data>`. Every metadata key (`DEPEND`, `SLOT`, …) is one record. Each value is UTF-8 (lossy-decoded, then trimmed). `CONTENTS` is never present in a binary package's own xpak (Portage `xpak()` skips it -- it's generated at merge time).
- Only the bounded `infosize + 8` tail of the file is read; the image tarball itself is never touched.

## fn read_xpak_segment
- Ports Portage's `tbz2.scan`. Every xpak read error is `Fatal`: Portage's `tbz2.scan()` swallows the failure and returns falsy, `get_data()` then returns `None`, and the caller raises `AttributeError` on `None.get`.

## fn parse_xpak_members
- Walk an xpak segment's index (Portage `getindex_mem`/`searchindex`: `"XPAKPACK" be32(indexsize) be32(datasize) <index> <data>`, then `while startpos + 8 < len` over `be32(namelen) name be32(datapos) be32(datalen)` records into `<data>`). Returns every member as `(name, &data bytes)`, borrowing from `seg`.
