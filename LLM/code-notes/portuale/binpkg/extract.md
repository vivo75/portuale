# crates/portuale/src/binpkg/extract.rs
Extracting a binary package's image and metadata at merge time.

## fn extract_binpkg
- `#500`: for a gpkg both halves are validated before either is written: `load_gpkg_metadata` (regular members, no duplicate or nested keys), then the image scan inside `extract_gpkg_member`, then the metadata files. A refused metadata member leaves the image directory empty and the other way round.
- Ports Portage's binary-package unpack (`portage.xpak.tbz2.decompose` / `portage.gpkg.gpkg.decompress` + `_generate_metadata_from_dir` in reverse); scalar metadata has the `build-info` shape.
- The scalar metadata is `read_{xpak,gpkg}_metadata`'s own map; the two non-scalar members (`environment.bz2` -- the package's saved build-time bash environment -- and `<pf>.ebuild`) are written back verbatim as raw bytes, not through the lossy scalar path.
- xpak image: the leading `file_len - (infosize + 8)` bytes. Ports `bintree.dbapi.unpack_metadata` -> `tbz2.unpackinfo` (`xpak.py:486-524`): every XPAK member written verbatim. The verbatim write fixed two bugs: an empty `DEBUGBUILD` became `"\n"`, and the trailing space Portage keeps on the last `NEEDED` line was trimmed (the gpkg branch had the same bug class). Found by the L2 xpak control (#326 S5): every XPAK member is written VERBATIM, not as a scalar parse plus reserialize, the same bug the gpkg branch fixed.
- The merge runs `pkg_preinst`/`pkg_postinst` by `bunzip2`'ing `environment.bz2` into `${T}/environment` (Portage's `BinpkgEnvExtractor` -> `bin/ebuild.sh`'s saved-env source path); Portage keeps both non-scalar members in the vdb.

## fn xpak_member_dest
- Portage `unpackinfo`'s target path for one member: the name with leading `/` stripped, joined under `dest` and normalized. A name whose `..` components climb out of `dest` is skipped (`None`), as Portage's `if not filename.startswith(mydest): continue` does.

## fn extract_gpkg_metadata
- `#58` K2: the metadata half of `extract_gpkg_member` -- Portage `bintree.dbapi.unpack_metadata` -> `gpkg().unpack_metadata(dest_dir)` extracts every inner `metadata/` member into build-info. Portuale writes each member as a regular file with its header mode (masked to `0o7777`, setuid/setgid stripped). Since `#500` the reader refuses every non-regular member, so no link ever reaches this function.
- `OpenOptions::mode` passes through the process umask; Portage's `tarfile.extract` chmods the header mode on afterwards, so the mode is set explicitly for a umask-independent result.
- Ports `bintree.dbapi.unpack_metadata` -> `gpkg().unpack_metadata(dest_dir)`. Portage would extract an in-archive symlink as a symlink, which every later build-info reader (`populate_vdb_tmp`, `BINPKGMD5`, the saved-`environment.bz2` extractor, the `pkg_*` phases) would then follow; Portage's writer never emits one. Nested keys would need directory creation Portage's writer never necessitates.

## fn scan_image_tar
- `#58` K2 / S4, redone by `#500` (plan 02.442 S1) and `#514` (plan `plan-residui-514-555.md` Task 1): Portage `gpkg.tar_safe_extract._check_member` (3.0.83-r1, `gpkg.py:702-732`), applied to the already-decompressed scratch `image.tar` before GNU `tar` unpacks it, so nothing reaches the filesystem until the whole member list is accepted. Python's check order is kept: duplicate (also as `./<name>`), absolute, any `..` component (`name.split("/")`, so `a/..` and a bare `..` too), device/FIFO (`isdev()`), hard link whose target is not an earlier member, then `_check_symlink_path` on the parent, on the member and, for a hard link, on its source and on the relocated target of a symlink source (`_check_hardlink`). Messages copy Portage's `Danger: <what> detected: <path>`; the path is the one Portage was checking (parent, member, link source or relocated target), not always the member.
- `#514`: the model root is the staging directory (Portage's temporary directory, `gpkg.py:741`), one level above `image/`: names keep their `image/` prefix and only a climb *above* the root escapes. The old root (the unpack directory) refused a symlink climbing exactly to the temp root and named an earlier path (`image/opt/link` for Portage's `image/../../marker`); the `Danger` lines are now Portage's own (`LLM/evidence/2026-10-23-500-501/514-oracle-matrix.txt`). The final `_check_symlink_path(temp_dir, prefix)` (`gpkg.py:761`) runs over the finished model.
- Portage checks resolved paths against what it has already extracted. Here that tree is modelled (`ImageLinks`): every symlink member, and every hard link to a symlink (CPython's `os.link` links the symlink itself, so it is a symlink at the new place), keyed by its resolved location under the staging root. `realpath` is re-implemented over the model: a `..` above the root, an absolute target (it leaves the staging directory) or a chain of more than 40 links is an escape. A file under a symlink parent that stays inside the image is accepted, as upstream `test_contained_symlink_parent` demands.
- One deliberate boundary stays. A member under a symlink whose target contains `..` passes the checks (it resolves inside the temp root) but GNU tar 1.35 defers `..`-target symlinks and stops after a partial unpack (rc 2); Portage's `tarfile` extracts it (rc 0). The scan cannot see the extractor's limits, so portuale reports tar's failure (rc 1, staging discarded, `dest` empty). Pinned by `extract_binpkg_reports_the_gnu_tar_truncation_for_a_dotdot_hardlink_shape` and the with-member half of `extract_binpkg_accepts_a_symlink_climbing_to_the_temp_root_like_portage`.
- Portage `tar_safe_extract.file_list`: one entry per accepted member, trailing `/` trimmed the way `tarfile` trims it.
- Evidence and the 23-shape oracle table: `LLM/evidence/2026-10-23-500-501/README.md`; pmtest pins `test_usepkgonly_refuses_hostile_gpkg_archives_like_portage`, `test_usepkgonly_matches_portage_on_temp-root_and_dotdot_hardlink_shapes`; bed L5 cell `differential-test-bed/run/l5-hostile-fault.sh`.
## fn xpak_xattr_tar_options
- Portage `BinpkgExtractorAsync._xpak_start` (`BinpkgExtractorAsync.py:39-50`, #334): under `FEATURES=xattr`, when the tar knows `--xattrs`, extract with `--xattrs --xattrs-include='*'` plus one `--xattrs-exclude=<pat>` per `PORTAGE_XATTR_EXCLUDE` pattern.
- Under `FEATURES=xattr` the xpak itself was packed with `gtar --xattrs` under the same feature (`misc-functions.sh:587-590`). Portage builds a shell string, so its quoted `'*'` reaches tar as the plain word `*`; this argv is what that shell hands tar.

## fn extract_gpkg_member
- The inner tarball's layout: the members all live under a single `<want>/` top-level directory (Portage's `gpkg._add_data`: `image_tar.add(root_dir, "image", recursive=True)`); Portage extracts to a temp dir and moves `<want>/*` into `dest`. `#514` ports that split: GNU `tar` unpacks into a staging directory inside `dest` (same filesystem, so the move is a rename) and `<stage>/image/*` is then moved into `dest`. `--strip-components=1` can not express this (the old `-xpf --strip-components=1` is gone): a symlink the scan accepts may still defeat GNU `tar`, and its partial unpack must not reach `dest` (the staging guard removes it however the unpack goes, leaving `dest` empty).
- Shares the outer unpack, the `#56` trusted-name regular-file walk and the `gpkg-1` validity guard with `read_gpkg_metadata`.
- The `image` half keeps GNU `tar` (`-xpf`) for its ownership/permission/xattr/sparse semantics, with Portage `tar_safe_extract`'s rules applied by a pre-scan first (`#58` K2, S4). The `metadata` half is resolved in process (`#58` S3, `extract_gpkg_metadata`).
- `#58` S5: the outer container is read in process -- the `#56` trusted-name regular-member check, the one-level structure and the `gpkg-1` marker all come from the tar headers before any bytes are streamed.
- `#58` K2/S3: the inner metadata tar is resolved in process and written as regular files only (no scratch copy, no `tar -xpf`).
- Portage `gpkg.decompress` validates the image stream with `tar_safe_extract` as it extracts (`gpkg.py:1094-1096`); portuale validates the whole scratch `image.tar` first (`#58` S4, `scan_image_tar`) so a rejected member never reaches the filesystem, then lets GNU `tar` do the actual unpack.
- Portage `gpkg.tar_safe_extract.extractall(dest)`: the format guarantees the one prefix component, so the moved entries become `usr/...` / `environment.bz2` directly. Without the move every path in the merged package's vdb `CONTENTS` would be recorded as `/image/...`, which breaks unmerge (portuale's and Portage's).

## fn load_gpkg_metadata
- `#500`: reads and validates the inner `metadata.tar` in process without writing. Portage `gpkg._check_metadata_files` runs over `metadata.getmembers()` before anything is extracted (`gpkg.py:856-862`, called at `:891` and `:1002`) and raises `InvalidBinaryPackageFormat` for any member that is not `isreg()`.

## fn check_gpkg_metadata
- `#58` K2/S3, moved out of `extract_gpkg_metadata` by `#500` so the checks (duplicates, nested keys) run before any file of the package is written.

## fn locate_gpkg_member
- The outer-container checks and the member lookup shared by the metadata and image halves of `extract_gpkg_member` (was inline there).
