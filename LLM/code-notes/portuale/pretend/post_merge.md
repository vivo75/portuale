- Ports Portage's `post_emerge()` (`post_emerge.py:126-130`): the vdb-changed gate is structural here -- every merge failure returned early above, `--pretend` never reaches this branch, `buildpkgonly` merges nothing, and an empty mergelist changed nothing either.
- Backlog #196: ports Portage's `post_emerge()` (`post_emerge.py:155`), which prints the GLEP 42 count notice a second time once the merge changed the vdb (after the preserved-libs notice and the config-file check, both mirrored above) -- same FEATURES-plus-nonzero-count gates, no `--quiet` gate. `--buildpkgonly` builds but never merges (Portage's `_pkgs_changed` stays false, so its `post_emerge` early-returns with no notice). A merge failure prints the notice too when the vdb changed (Portage prints regardless of retval, `post_emerge.py:104-108,155`).
- Ports Portage's `post_emerge()` (`post_emerge.py:141-152`): once the merge changed the vdb, warn about any library the merge/unmerge just preserved and point the user at `emerge @preserved-rebuild`.

## fn run_autoclean_after_merge
- Backlog #404 (02.346 S11): ports Portage's post-merge auto-clean (`_emerge/actions.py`, `action_build` `:694-704`: `>>> Auto-cleaning packages...` then `unmerge(root_config, myopts, "clean", [], ldpath_mtimes, autoclean=1)`), gated on the resolved `AUTOCLEAN == "yes"` (`autoclean_enabled`, make.globals default `no`, `:103`), called from `run_after_display` after `record_world_after_merge` and before `show_post_merge_notices` (Portage records world before the merge and updates the info index after the clean). The unmerge's exit code is discarded there too -- a clean that finds nothing exits 1 while the merge already succeeded.
- Only the user-set case is modelled: the forced-yes after applied global updates (`actions.py:3944-3964`) and after depclean (`:809-813`) are out of scope with the updates/depclean-forces they belong to; every oracle cell runs with `--package-moves=n`. `--pretend`/`--buildpkgonly`/failed merges never reach the hook (fetchonly is unimplemented); `--oneshot` does not suppress it (S404 cl01/cl01c/cl02/cl05).
- The `>>> Using system located in ROOT tree <root>/` line (Portage `_unmerge_display`, only for non-`/` ROOT, trailing slash included) comes from the shared clean path's display header (`print_unmerge_display_header`), exactly once, as in Portage -- the wrapper prints only `>>> Auto-cleaning packages...` (Portage `actions.py:935` prints the opener, then `unmerge()` renders the header). Backlog #560 fix round: the wrapper used to print the header too, doubling the line under `AUTOCLEAN=yes` (pin `autoclean_tail_prints_the_using_system_header_exactly_once`); the manual `--clean`/`-C` output is byte-identical to before either way since the header is shared. Same for the trailing-blank-line delta: Portage ends the slated/protected pair with `\n\n` (blank before the first `>>> Unmerging`), portuale ends it with one `\n` on every removal path already -- changing it would move the `--pretend` pins, so the auto-clean block carries the same delta (S404 matrix).
- Backlog #560 true cause (fix round S0, `task-3-report.md`): on the `14-merge-match`/`16-merge-mismatch` probe shapes AUTOCLEAN is set nowhere (probe make.conf, calling env, make.globals default `no`) yet Portage prints the tail -- its run applies Global Updates on the fresh ROOT, which forces `settings["AUTOCLEAN"] = "yes"` (`actions.py:3944-3964`, bug #792195; `_global_updates` returns True iff a changed updates file yielded >=1 valid directive, `_global_updates.py:139`, error files applied but unrecorded `:131-135`). Proven by the controls: Portage with `--package-moves=n` prints no tail, and a second merge into the same ROOT (recorded `mtimedb["updates"]`) is silent. Portuale has no updates run and no `mtimedb["updates"]` section (moves apply at metadata-read time; #551 keeps the updates re-read cut), so the force signal is a separate slice -- the unconditional tail was ruled out (it would regress both proven silences).
- Evidence: `LLM/evidence/2026-10-18-404/` (`l/` captures, `matrix.md`, `PROVENANCE.md`); pmtest pins `test_autoclean_*` in `test_portuale.py`; Rust pins `pretend::tests::autoclean`.
- Backlog #562: the gate is now `!buildpkgonly && (autoclean_enabled(config) || updates_force)`, where `updates_force` is the target root's applied-updates force computed pre-resolve in `run()` and threaded through `FinishRunArgs`/`RunAfterDisplayArgs` (see `pretend/global_updates.md`). The force sets no config value (the #551 re-read cut stays -- no config reload); it only ORs the gate, which is exactly what Portage's forced `AUTOCLEAN=yes` amounts to at the tail. A running-root-only force never reaches the gate (the tail reads the target settings). `--pretend`/`--buildpkgonly`/failed merges still never print the tail (structural: the hook sits past all three returns), but they do commit the `updates` record -- the #179/`ask_declined` pins were narrowed accordingly (resume section identical, `updates` added).
