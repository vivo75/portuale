# crates/portuale/src/pretend/mod.rs
`emerge --pretend`: resolve and display, never build.

## module
- The v1 slice; see crates/portage-repo/src/lib.rs for the full scope writeup. The recursion's own scope cuts (see `resolve_pretend_graph`): DEPEND+RDEPEND only, `||` resolves every alternative, cycle/dup-safe.
- `--update`/`-u` ports Portage's `avoid_update` (see `resolve_pretend` in portage-repo): without it, an already-installed version that still satisfies the requested atom is kept as-is -- Portage's own default, not something portuale invented.
- `--deep`/`-D` ports Portage's `Deep` and depth-cutoff semantics (see `resolve_pretend_graph` in portage-repo): only New/Upgrade/Reinstall packages recurse unconditionally either way. Like `--verbose`/`-v`, it is Portage `argument_options` with an optional value, not a plain boolean: a standalone `--deep`/`-D` peeks at the next token, consuming it only if it parses as a non-negative integer (matching Portage `insert_optional_args`'s `valid_integers` check); `--deep=N` (argparse's native `=`-form) is a separate mechanism where a non-numeric or negative value is an immediate parse error (exit 2), matching Portage `parser.error("Invalid --deep parameter")`. A bundled `-D` (e.g. `-pvD`) never consumes anything (same "no ambiguity with another bundled flag character" reasoning as bundled `-v`). `N==0` (either form) is indistinguishable from `--deep` never given, matching Portage `create_depgraph_params.py`'s `!= 0` check.
- `--exclude`/`-X` ports Portage's `excluded_pkgs` / `WildcardPackageSet` (see `resolve_pretend` in portage-repo; a documented scope cut relative to depgraph.py's ~18 call sites). Portage `main.py` declares it `"action": "append"` -- repeatable, each occurrence's own value itself a space-separated atom list ("A space separated list of package names or slot atoms"). The value is required: a missing value is an immediate usage error (exit 2). A bundled `-X` (e.g. `-pX`) is deliberately not supported -- no sensible default exists -- and gets its own "requires an argument, can't be bundled" message.
- `--deselect`/`-W`: Portage `main.py` turns a bare `--deselect` into its own standalone ACTION (`if myaction is None and myoptions.deselect is True: myaction = "deselect"`, the same shape as `--depclean`/`--sync`), dispatched to `run_deselect` before any resolve machinery. Without `--pretend` it really rewrites the `world` / `world_sets` files (the world files are user config portuale does edit -- like `-C`/`--depclean`/`--prune`). It reports which world-file atoms each target would cause Portage `action_deselect` (lib/_emerge/actions.py) to discard: every target is expanded against the vdb (a bare package name -- no `/` -- via Portage's own "null category" mechanism, scanning the world file for a same-named atom to borrow its category from, then `vardb.match`-equivalent lookup either way -- see `portage_repo::installed_candidates`), and each expanded, actually-installed `category/package:slot` is matched against every world-file atom. Documented scope cut versus Portage `Atom.intersects()`: only a narrower category/package(+slot) equality check, not the full version-range/USE-dep algebra -- sufficient for the dominant plain-atom case. A `@set`-prefixed world entry is never matched, consistent with the pre-existing `read_world_atoms` cut for `@world` itself (not a new one). Portage `--deselect` is `true_y_or_n` choices (`_emerge/main.py:446-449`, `in true_y` at `:869-870`): a bare `--deselect`/`-W` or `--deselect y`/`--deselect True` enables it, `--deselect n` disables it (falling through to ordinary resolution); a bundled `-W` never consumes a value. `--ask` confirmation and `--json` output are both out of scope for deselect mode -- the former falls through to the existing "not yet implemented" rejection, the latter simply is not offered.
- `--json` is not a Portage emerge option at all. Built as a portuale-specific convenience, requested directly by name (not routed through emerge_options.rs's CLI-surface tables). Dumps the whole resolved graph as one line of JSON instead of the plain-text lines -- see `print_json` for the exact shape. The contract suite and `tests/output_invariants.py` read this output; the byte shape is pinned by the harvested corpus (`tests/corpus/`).
- A top-level atom may carry an operator/version/slot (e.g. `>=cat/pkg-1.2`, `cat/pkg:0`) -- `resolve_pretend`'s atom-vs-candidate matching (see portage-repo/src/lib.rs) already handles this with zero extra code (the same `match_from_list` path every DEPEND/RDEPEND atom uses). Only a blocker (`!`/`!!`) top-level atom is rejected -- Portage does not accept a bare blocker as an emerge target either; prior to that slice the CLI's bare-atom check did not test for it, so `emerge --pretend '!!cat/pkg'` silently no-op'd (accepted by the CLI, then dropped by `resolve_pretend_graph`'s blocker skip) instead of being rejected. Dependency atoms from DEPEND/RDEPEND keep the full grammar.
- Multiple top-level atoms (`emerge --pretend foo bar`) seed the same BFS/dedup/slot-conflict machinery together (see `resolve_pretend_graph`), so a shared dependency dedupes like a diamond and a slot conflict between two targets is detected too. A top-level atom with no visible candidate aborts the whole run immediately in argv order (matching Portage depgraph.py's "there are no ebuilds to satisfy") -- confirmed with the user before implementing, over reporting it and resolving the rest.
- CLI surface: every Portage emerge option/action from lib/_emerge/main.py (see emerge_options.rs) is recognized by name, so real-world invocations carrying unimplemented options (e.g. from EMERGE_DEFAULT_OPTS or a script) fail with an accurate message. See emerge_options.rs for the (deliberately unfaithful) value-consumption scope cut for every option other than `--verbose`/`-v`.
- `--verbose`/`-v`: Portage registers it in main.py's `argument_options` with `choices=("True", "y", "n")`, and `insert_optional_args` inserts "True" when given with no explicit value (verified by tracing `insert_optional_args` by hand). A standalone `--verbose`/`-v` peeks at the next argv token: exactly "y" or "n" is consumed, anything else (including nothing) leaves verbose enabled without consuming. `--verbose=y`/`--verbose=n` (argparse's native `=`-form) are handled the same way. A bundled `-v` (e.g. `-pv`) never consumes anything -- Portage's own `short_arg_opts_n` / "Don't make things like '-kn' expand to '-k n'" reasoning. See the `--verbose`/`-v` handling and the bundle-handling comment in `run`.
- Short-flag bundling (`-pv`, `-pd`, ...): unlike Portage's own `insert_optional_args` (which scans for a value-taking short option anywhere in the bundle and extracts it first via an internal recycling stack, regardless of position), portuale processes strictly left to right and reports the first unimplemented/unrecognized character, exiting immediately -- the same two outcomes (and messages) a standalone occurrence would produce. An intentional simplification of the processing order, not the outcome: since portuale exits at the first out-of-scope input either way, the algorithm is unobservable except for two different unimplemented flags bundled together, where portuale always reports the leftmost one.
- `--help`/`-h`: Portage `main.py`'s `parse_opts` maps `-h`/`--help` to the "help" action, which `main()` special-cases (`if myaction == "help": emerge_help(); return os.EX_OK` -- checked once, after the whole line parsed, so it wins regardless of position or accompanying unimplemented flags). Portuale's scan is a documented simplification: it checks every token (including each bundle character) unconditionally, rather than first confirming the rest of the line parses -- so `emerge --help --this-is-not-a-real-flag-at-all` prints help here where Portage reports a parse error. The help text itself is not a port of Portage's `_emerge/help.py` (157 lines of colorized usage for its ~130-flag surface, most unimplemented here -- reproducing it would mislead); a short portuale-specific summary pointing at README.md and LLM/agent-context.md.
- `emerge --pretend <category/package>`: the v1 slice (see crates/portage-repo/src/lib.rs for the full scope writeup -- candidates come from every repos.conf repo, main + overlays).
- `N==0` (either form) is indistinguishable from `--deep` never being given at all, matching Portage `create_depgraph_params.py`'s own `!= 0` check.  --exclude/-X is real and implemented too (see portage-repo's `resolve_pretend`'s own doc comment for the Portage `excluded_pkgs`/ `WildcardPackageSet` behavior it ports, and the documented scope cut relative to Portage depgraph.py's own ~18 call sites): an installed package matching an exclude atom is left exactly as-is, regardless of `--update`/`--newuse`/`--changed-use`, and a not-yet-installed package matching one is never offered as a New/Upgrade candidate either. Portage `main.py` declares it `"action": "append"` -- repeatable, each occurrence's own value itself a *space-separated* atom list (Portage help text: "A space separated list of package names or slot atoms"), so both accumulate here too: `--exclude foo --exclude "bar baz"` excludes all three. - It previews under `--pretend`, and without it really rewrites the `world` / `world_sets` files (same "never merges" invariant, but the world files themselves are user config portuale does edit -- like `-C`/`--depclean`/`--prune`).
- Portage `--deselect` is `true_y_or_n` choices (`_emerge/main.py:446-449`, `in true_y` at `:869-870`), the same optional-value shape `--verbose`/`-v` already has: a bare `--deselect`/`-W` or `--deselect y`/`--deselect True` enables it, `--deselect n` explicitly disables it (falling through to ordinary resolution instead); a bundled `-W` (e.g. `-pW`) never consumes a value, always enabling, the same "no ambiguity with another bundled flag character" reasoning as bundled `-v`/`-D`.
