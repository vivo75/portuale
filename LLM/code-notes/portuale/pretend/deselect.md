# crates/portuale/src/pretend/deselect.rs
`emerge --deselect`. Context moved out of the code comments (#336 Phase 7); the code keeps only the short why.

## fn run_deselect
- Ports Portage's `action_deselect` (`lib/_emerge/actions.py`). Needs no repo/config resolution -- only the world files and the vdb -- so unlike every other portuale feature it never calls `find_repos`/`resolve_config`.
- Bare name: expanded via Portage's own "null category" mechanism -- scan the world file's own atoms for one sharing that package name, and substitute in its category (Portage `Atom(..., category="null")` handling; portuale's atom parser has no equivalent, so this is a dedicated lookup instead), added to the candidate set directly, unconditionally, with no installed check at all. Confirmed by reading `action_deselect`'s null-category-substitution loop, which adds the substituted atom to `expanded_atoms` before ever touching the vardb. Portage's `action_deselect` *does* separately call `vardb.match(atom)` for the same original (still-null-category) atom, but that call can never match a vardb entry -- no package is ever catalogued under category "null" -- so it is dead code for this branch and correctly contributes nothing here.
- Explicit-category target: added directly with no installed check -- confirmed by reading Portage's call chain feeding `action_deselect`'s `atoms` parameter: `action_uninstall`'s `dep_expand(x, mydb=vardb, ...)` (`lib/portage/dbapi/dep_expand.py`) returns an explicit-category atom unchanged (`if mydep.category != "virtual": return mydep`), *before* it ever reaches `cpv_expand` (the vardb-dependent part, only reached for a bare name); `action_deselect` then seeds `expanded_atoms = set(atoms)` with that atom unconditionally. So `--deselect cat/pkg` genuinely discards a matching world entry even if never installed -- an earlier portuale doc comment (and test) claimed installation was always required, an incorrect generalization. Portage's vardb-derived narrowing (`vardb.match`) is a *separate, additional* contribution on top of the unconditional candidate, for BOTH cases -- not a gate on it. For an explicit-category target it adds a further bare `category/package:slot` candidate (Portage `Atom(f"{pkg.cp}:{pkg.slot}")`, no version/operator) for whatever is actually installed; for a bare name it is correctly omitted, per the dead-code reasoning above.
- Comparison is Portage's `Atom.intersects()` (`portage_dep::atom_intersects`) plus `action_deselect`'s own repo check (`not (arg_atom.repo and not atom.repo)`), replacing portuale's previous narrower category/package(+slot)-only equality check.
- `--deselect @some-set`: Portage's combined `world_set` (`WorldSelectedSet`) iterates BOTH `world`'s plain atoms AND `world_sets`'s literal `@name` reference *strings* -- confirmed by reading `WorldSelectedSet.load`'s `self._setAtoms(chain(self._pkgset, self._setset))`: a `@name` string fails Portage `Atom(...)` parsing and lands in `_nonatoms`, so it is carried through *unexpanded*, never resolved into member atoms. A `@`-prefixed CLI target can only discard a `@`-prefixed `world_set` entry via exact string equality (`arg_atom == atom`). So despite `resolve_custom_set`'s working nested-set expansion (built for -- and still only used by -- `@world`'s dependency-resolution walk, a genuinely different mechanism, `SetConfig.getSetAtoms`), it has no role here: the equivalent is a membership check against `read_world_sets`. Each discarded entry is reported against its source file (`"world"` vs `"world_sets"`, matching Portage's `filename = "world_sets" if str(atom).startswith(SETPREFIX) else "world"`), sorted together into one combined list, mirroring Portage's `sorted(discard_atoms, key=str)`.
- Portage's `action_deselect` always returns `os.EX_OK` on every reachable path (matches, no matches, no targets at all).
- Rewrite shape: Portage's `world_set.replace(remaining)` -> `WorldSelectedSet.write`, exactly `WorldSelectedPackagesSet.write` / `WorldSelectedSetsSet.write`. One transaction (S1.6): `var/lib/portage` created once, then `world`, then `world_sets`.
- `--ask` prompts once, after the `>>> Removing ...` lines, before either file is rewritten; `No` aborts with `128 + SIGINT`. `--pretend` never rewrites, so the prompt only matters for a non-pretend run (Portage's `main.py` drops `--ask` under `-p` entirely).
- `emerge --deselect <atom-or-bare-name> [...]`: Portage `action_deselect` (`lib/_emerge/actions.py`). Under `--pretend` this previews (`Would remove ...`); **without** it, after the same preview (`Removing ...`), `run_deselect` rewrites both `var/lib/portage/world` and `var/lib/portage/world_sets` with the discarded entries dropped, each file sorted + one entry per line + comments dropped -- Portage `world_set.replace(remaining)` -> `WorldSelectedSet.write`. Needs no repo/config resolution at all -- only the world files and the vdb -- so this doesn't call `find_repos`/`resolve_config` either, unlike every other Portage feature in portuale. For each target in `targets`: a bare package name (no `/` at all) is expanded via Portage portage's own "null category" mechanism -- scan the world file's own atoms for one sharing that package name, and substitute in its category (Portage `Atom(..., category="null")` handling; portuale's own atom parser has no equivalent, so this is a dedicated lookup instead), added to the candidate set directly, **unconditionally, no installed check at all**: confirmed by reading `action_deselect`'s own null-category-substitution loop, which adds the substituted atom to `expanded_atoms` before ever touching the vardb. Portage `action_deselect` *does* separately call `vardb.match(atom)` for this same original (still-null-category) atom, but that call can never match a Portage vardb entry -- no package is ever catalogued under category "null" -- so it's dead code for this branch specifically, and correctly contributes nothing here. An *explicit*-category target (already has a `/`) is likewise added to the candidate set directly, with **no installed check at all** -- confirmed by reading Portage portage's own call chain feeding `action_deselect`'s own `atoms` parameter: `action_uninstall`'s own `dep_expand(x, mydb=vardb, ...)` (`lib/portage/dbapi/dep_expand.py`) returns an explicit-category atom completely unchanged, `if mydep.category != "virtual": return mydep`, *before* it ever reaches `cpv_expand` (the vardb-dependent part, only reached for a bare name); `action_deselect` itself then seeds `expanded_atoms = set(atoms)` with that same atom, unconditionally. For an explicit-category target specifically, that separate vardb contribution (`portage_repo::installed_candidates`, portuale's own vdb scan, via `match_from_list`) still runs and adds a further bare `category/package:slot` candidate (Portage `Atom(f"{pkg.cp}:{pkg.slot}")`, no version/operator at all) for whatever version(s) are actually installed; for a bare name it's correctly omitted, per the dead-code reasoning above. Every candidate atom collected this way -- installed-derived (bare `category/package:slot`) or the literal target/substituted atom (version/operator intact, if given) -- is compared against every world-file entry via Portage `Atom.intersects()` (`portage_dep:: atom_intersects`, see its own doc comment) plus Portage `action_deselect`'s own separate repo check (`not (arg_atom.repo and not atom.repo)`), replacing portuale's own previous narrower category/package(+slot)-only equality check. `--deselect @some-set`: Portage `action_deselect`'s own combined `world_set` (`WorldSelectedSet`) iterates BOTH `world`'s own plain atoms AND `world_sets`'s own literal `@name` reference *strings* -- confirmed by reading `WorldSelectedSet.load`'s own `self._setAtoms( chain(self._pkgset, self._setset))`: a `@name` string fails Portage `Atom(...)` parsing and lands in `_nonatoms`, so it's carried through *unexpanded*, never resolved into its own member atoms at all. `action_deselect`'s own matching loop confirms this: a `@`-prefixed CLI target can only ever discard a `@`-prefixed `world_set` entry via *exact string equality* (`arg_atom == atom`) -- there is no installed-candidate matching, no member-atom expansion, for either side. So despite `resolve_custom_set`'s own Portage, working nested-set expansion (built for -- and still only used by -- `@world`'s own dependency-resolution walk, a genuinely different Portage mechanism, `SetConfig.getSetAtoms`), it has no role here at all: portuale's own equivalent is a plain membership check against `read_world_sets` (`@name` stripped of its own leading `@` for the comparison), nothing more.
