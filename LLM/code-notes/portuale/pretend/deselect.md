# crates/portuale/src/pretend/deselect.rs
`emerge --deselect`. Context moved out of the code comments (#336 Phase 7); the code keeps only the short why.

## fn run_deselect
- Ports Portage's `action_deselect` (`lib/_emerge/actions.py`) for `emerge --deselect <atom-or-bare-name> [...]`. Under `--pretend` this previews (`Would remove ...`); **without** it, after the same preview (`Removing ...`), `run_deselect` rewrites both `var/lib/portage/world` and `var/lib/portage/world_sets` with the discarded entries dropped, each file sorted + one entry per line + comments dropped. Needs no repo/config resolution -- only the world files and the vdb -- so unlike every other portuale feature it never calls `find_repos`/`resolve_config`.
- For each target in `targets`: a bare package name (no `/` at all) is expanded via Portage's own "null category" mechanism -- scan the world file's own atoms for one sharing that package name, and substitute in its category (Portage `Atom(..., category="null")` handling; portuale's atom parser has no equivalent, so this is a dedicated lookup instead), added to the candidate set directly, unconditionally, with no installed check at all. Confirmed by reading `action_deselect`'s null-category-substitution loop, which adds the substituted atom to `expanded_atoms` before ever touching the vardb. Portage's `action_deselect` *does* separately call `vardb.match(atom)` for the same original (still-null-category) atom, but that call can never match a vardb entry -- no package is ever catalogued under category "null" -- so it is dead code for this branch and correctly contributes nothing here.
- Explicit-category target: added directly with no installed check -- confirmed by reading Portage's call chain feeding `action_deselect`'s `atoms` parameter: `action_uninstall`'s `dep_expand(x, mydb=vardb, ...)` (`lib/portage/dbapi/dep_expand.py`) returns an explicit-category atom unchanged (`if mydep.category != "virtual": return mydep`), *before* it ever reaches `cpv_expand` (the vardb-dependent part, only reached for a bare name); `action_deselect` then seeds `expanded_atoms = set(atoms)` with that same atom, unconditionally. So `--deselect cat/pkg` (or a bare `pkg` resolvable via the world file) genuinely discards a matching world entry even if never installed -- an earlier portuale doc comment (and test) claimed installation was always required, an incorrect generalization. Portage's vardb-derived narrowing (`vardb.match`) is a *separate, additional* contribution on top of the unconditional candidate, for BOTH cases -- not a gate on it. For an explicit-category target specifically, that separate vardb contribution (`portage_repo::installed_candidates`, portuale's own vdb scan, via `match_from_list`) still runs and adds a further bare `category/package:slot` candidate (Portage `Atom(f"{pkg.cp}:{pkg.slot}")`, no version/operator) for whatever is actually installed; for a bare name it is correctly omitted, per the dead-code reasoning above.
- Comparison is Portage's `Atom.intersects()` (`portage_dep::atom_intersects`, see its own doc comment) plus `action_deselect`'s own repo check (`not (arg_atom.repo and not atom.repo)`), replacing portuale's previous narrower category/package(+slot)-only equality check.
- `--deselect @some-set`: Portage's combined `world_set` (`WorldSelectedSet`) iterates BOTH `world`'s plain atoms AND `world_sets`'s literal `@name` reference *strings* -- confirmed by reading `WorldSelectedSet.load`'s `self._setAtoms(chain(self._pkgset, self._setset))`: a `@name` string fails Portage `Atom(...)` parsing and lands in `_nonatoms`, so it is carried through *unexpanded*, never resolved into member atoms. A `@`-prefixed CLI target can only discard a `@`-prefixed `world_set` entry via exact string equality (`arg_atom == atom`). So despite `resolve_custom_set`'s working nested-set expansion (built for -- and still only used by -- `@world`'s dependency-resolution walk, a genuinely different mechanism, `SetConfig.getSetAtoms`), it has no role here: the equivalent is a membership check against `read_world_sets`. Each discarded entry is reported against its source file (`"world"` vs `"world_sets"`, matching Portage's `filename = "world_sets" if str(atom).startswith(SETPREFIX) else "world"`), sorted together into one combined list, mirroring Portage's `sorted(discard_atoms, key=str)`.
- Portage's `action_deselect` always returns `os.EX_OK` on every reachable path (matches, no matches, no targets at all). -- ported the same way, unconditionally `ExitCode::SUCCESS`.
- Rewrite shape: Portage's `world_set.replace(remaining)` -> `WorldSelectedSet.write`, exactly `WorldSelectedPackagesSet.write` / `WorldSelectedSetsSet.write`. One transaction (S1.6): `var/lib/portage` created once, then `world`, then `world_sets`.
- `--ask` prompts once, after the `>>> Removing ...` lines, before either file is rewritten; `No` aborts with `128 + SIGINT`. `--pretend` never rewrites, so the prompt only matters for a non-pretend run (Portage's `main.py` drops `--ask` under `-p` entirely).
