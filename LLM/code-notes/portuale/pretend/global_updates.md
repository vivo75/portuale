# crates/portuale/src/pretend/global_updates.rs
The applied-updates AUTOCLEAN force (backlog #562, full port under backlog #576): Portage's `_global_updates` over the target root, then the running root when different, before the resolve. An applied target run reloads the config so the rest of the run sees the moved state.

## fn global_updates_force
- Ports Portage's pre-resolve `_global_updates` call (`lib/_emerge/actions.py:3941-3964`): runs for every action except `help`/`info`/`sync`/`version` (`--help` returns before any config load, so only the other three are gated here) and unless `--package-moves=n`. Computed in `run()` before the option validation -- Portage's `run_action` calls `_global_updates` first, before every validation and action dispatch -- so the early actions (`--deselect`, `--list-sets`, `--regen`, `--metadata`, which return from `validate_and_early_actions`) run it in Portage's order; then before the colour gate (the updates block is never coloured) and before the resolve. Returns the *target* root's force for the merge gate; the running root is handled inside `updates_force_for_roots`.
- Which root's AUTOCLEAN the tail reads: `action_build` unpacks `settings` from `emerge_config`, i.e. the *target* config's settings (`_emerge_config.__iter__` yields `target_config.settings`), while the force sets `AUTOCLEAN` on whichever `root_config`'s updates fired (`actions.py:3958-3962`). So a running-root-only force stays silent on the tail -- mirrored by returning only the target force.
- An unreadable updates file is skipped rather than propagating (Portage's `grab_updates` has no such guard, an unhandled corner there).

## fn updates_force_for_roots
- The two-root core behind `global_updates_force`: the target root first, then the running root when it differs (same repo list, each root's own settings and record -- Portage passes the same `trees` with each `root_config`'s own `mtimedb` and `mysettings`). Only the target force is reported; both records are maintained. A failed pass is reported on stderr and reads as no force. Split out so tests need no process-global env.
- `secpass` is global (target-root based, `data.py` unprivileged mode), so privilege is computed once from the target and passed to both driver calls.
- An applied target run reloads the whole config from scratch (`resolve_config_for_root`, mirroring `load_emerge_config` at `actions.py:3957`): world, `package.*`, vdb and binpkg reads after this point see the moved state. A failed reload is reported and the old config is kept.

## tests
- `pretend::tests::global_updates`: `--package-moves=n` and `info`/`sync`/`version` skip without touching the disk; directiveless files print the notice but commit nothing. The Task 1 pins now run end to end (fresh root fires + records; repeat run silent; error file fires but stays unrecorded; running-root-only force never reads as target force while its record is still maintained; unwritable record still forces). `applied_updates_check_leaves_a_portage_written_mtimedb_untouched` pins the converse: a record that already matches the files means nothing is applied and the file stays byte-identical, foreign keys included. The merge-gate OR itself is pinned at pmtest level (`test_applied_updates_force_*`).

## moved helpers
- `file_mtime` (whole-second `st_mtime`, `None` when unreadable; Portage `lib/portage/update.py`, `grab_updates` via `mystat[stat.ST_MTIME]`), the `updpath_map` shared-directory dedup (`lib/portage/_global_updates.py`, `_do_global_updates`), the `int(record.get(path, -1)) != st_mtime` changed-file gate, the `errors="replace"` lossy read with unreadable files skipped, and the `check_root_updates`/`updates_force_for_roots` two-root core over `profiles/updates/` (same repo list, each root's own record, no process-global `PORTAGE_RUNNING_ROOT` in tests) all live in `global_updates::{updates_file_mtime, scan_updates, run_global_updates}` now; this module is only the call site.
