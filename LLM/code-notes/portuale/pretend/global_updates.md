# crates/portuale/src/pretend/global_updates.rs
The applied-updates AUTOCLEAN force (backlog #562), reverted to read-only pending backlog #576 (backlog #575 Task 1): the scan still parses changed `profiles/updates/` files, but nothing is recorded and no force is ever reported, because portuale never performs the moves on disk -- recording would make Portage's `grab_updates` (`_global_updates.py:91`) skip those files as applied and never move the installed entries.

## fn global_updates_force
- Ports Portage's pre-resolve `_global_updates` call (`lib/_emerge/actions.py:3941-3964`): runs for every action except `help`/`info`/`sync`/`version` (`--help` returns before any config load, so only the other three are gated here) and unless `--package-moves=n`. Computed in `run()` before the resolve. Read-only interim: always returns false; the `--pretend`/failed-merge record commit is gone with the record itself (Portage commits at `actions.py:3954`, pre-merge -- restored with the full port). Returns the *target* root's force for the merge gate; the running root is handled inside `updates_force_for_roots`.
- Which root's AUTOCLEAN the tail reads: `action_build` unpacks `settings` from `emerge_config`, i.e. the *target* config's settings (`_emerge_config.__iter__` yields `target_config.settings`), while the force sets `AUTOCLEAN` on whichever `root_config`'s updates fired (`actions.py:3958-3962`). So a running-root-only force stays silent on the tail -- mirrored by returning only the target force. The #551 re-read cut stays: no config reload, only the force signal + record are mirrored (the world/vdb/binpkg/config-file moves stay read-time, and the `Performing Global Updates` progress block stays cut -- the suite blesses "modulo Global Updates").
- Deliberate cuts (documented, not mirrored): the `secpass<2`/`SANDBOX_ACTIVE`/vdb-lock early-False gates (`_global_updates.py:39-56`) -- portuale runs unprivileged in the suite, where those gates would pin the feature off; an unreadable updates file is skipped rather than propagating (Portage's `grab_updates` has no such guard, an unhandled corner there).

## fn updates_force_for_roots
- The two-root core behind `global_updates_force`: both roots are scanned (same repo list, each root's own record -- Portage passes the same `trees` with each `root_config`'s own `mtimedb`), but the interim always reports no force. Split out so tests need no process-global env.

## fn check_root_updates
- Ports `_do_global_updates`' return (`retupd`, `_global_updates.py:139`) without its side effects: true iff a *changed* updates file yields >=1 valid directive, measured against the `updates` mtime record in `<EROOT>/var/cache/edb/mtimedb`. Per-repo `profiles/updates/` scan skipping dotfiles and non-files; repos sharing one updates directory scan it once (`updpath_map`); only files whose whole-second `st_mtime` differs from the record are parsed (`grab_updates`); the record is consulted but never extended. Since backlog #576 Task 6 the count comes from the shared `portage-repo` parser (`parse_updates_content`) instead of the deleted local `parse_updates_file` -- with one inherited divergence (see `parse_updates_file`): a versioned `slotmove` atom no longer counts as valid. Unobservable while the force stays hardcoded false; the error-aware record rebuild must count it valid again. The discarded `write_updates_mtimes` call also swallowed its error (`lib/portage/util/mtimedb.py`, `MtimeDB.__write_to_disk`'s `except OSError`); a non-writable root still never fails the run, now because nothing is written. Record keys are the scanned path strings (`myfile.path`). The caller (`updates_force_for_roots`) ignores the return until the full port restores the force.

## fn parse_updates_file
- Deleted (backlog #576 Task 6): counting moved to the shared `portage-repo` parser (`parse_updates_content`). Ported `lib/portage/update.py::parse_updates` as a silent `(valid directives, error-free)` split: blank lines skipped; `move` needs exactly 2 bare-`cat/pkg` atoms; `slotmove` needs exactly 3 fields with a parseable non-blocker package atom and valid slot names; anything else marks the file errored. Silent by design -- a malformed updates file never fails a merge (and the #551 "no `ERROR:` line at all" rule stays: Portage's `ERROR:` stderr lines are not mirrored). One deliberate looseness, matching Portage exactly: a `slotmove` package may carry a version (Portage only rejects blockers there -- `parse_updates` has no `atom != atom.cp` check for `slotmove`, unlike `move`); `bare_cp` matches Portage's `atom != atom.cp` check for `move` atoms. DIVERGENCE, inherited by the shared parser and now by the check: `portage-repo`'s `parse_updates_content` requires a bare `cat/pkg` for `slotmove` too, so a versioned `slotmove` atom (valid to Portage) counts as nothing there. The read-path metadata remap shares the narrow reading; the full port's driver must use error-aware parsing that counts it valid.

## fn bare_cp
- Deleted (backlog #576 Task 6): was a duplicate of `portage-repo`'s updates-application `bare_cp` (`parse_updates_content`'s own copy). Kept local only because that helper was `pub(crate)` to `portage-repo`; the reuse made it `pub`. A bare `cat/pkg`, else `None`.

## fn update_atom
- Deleted with `parse_updates_file` (backlog #576 Task 6): the `slotmove`-package half of `parse_updates` -- parseable and not a blocker. Versioned atoms pass (see `parse_updates_file`).

## fn valid_slot_name
- Deleted (backlog #576 Task 6): was a duplicate of `portage-repo`'s `valid_slot_name`. `[A-Za-z0-9_][A-Za-z0-9+_.-]*`, i.e. Portage `_slot` (`versions.py`, `slot_re`) with no `/` alternative -- the EAPI-5 `/subslot` form is rejected by the same regex here, where Portage rejects it with a separate `/` check (`update.py`).

## fn file_mtime
- Whole-second `st_mtime` (`grab_updates` compares `mystat[stat.ST_MTIME]` ints); `None` when unreadable.
