# crates/portuale/src/pretend/expand_targets.rs
Expanding the command-line arguments (sets, package moves, bare names) into the atoms to resolve.

## fn expand_targets
- S7 (#341): every non-set argument is validated with `is_valid_package_atom` before set expansion (Portage `run_action`, `_emerge/actions.py:4244-4262`), so a bad atom beats an unknown `@set` the way Portage reports it before the depgraph runs. Filesystem paths skip the check (Portage's `os.sep`-prefix / `os.lstat` skips); `@sets` validate on their own path (S8).
- S8 (#341): a direct `@name` arg resolves through `resolve_custom_set` and keeps its `errors` in `ExpandTargetsOut::set_validation_errors`, printed after the merge list and its USE-change prompt (even when the USE changes already fail the run); `@world`/`@selected` members come from `expand_selected`, which already dropped its bad lines silently.
- `--autounmask-continue` + `--autounmask=n` prints the `has been disabled by` WARNING on the merge/build path before the depgraph (`actions.py:3772`). Portuale's only observable effect for `--autounmask-continue` -- its write-and-continue path is Portage-gated on `"--pretend" not in myopts` (`depgraph.py:5796`), inert here.
- Built-in sets: `@world`/`@selected` via `expand_selected` (world file atoms + `world_sets` nested sets); `@installed` via `installed_set_atoms`. Other `@name` tokens expand recursively via `resolve_custom_set` (Portage `StaticFileSet` / `SetConfig.getSetAtoms`), the same machinery the `--unmerge`/`--depclean`/`--deselect` paths use; a `@name` with no matching set file is a fatal "set 'name' not found".
- Backlog #286: `expanded_from_set` tracks which atoms rode a `@world`/`@selected` argument (Portage `SetArg` named `"world"`/`"selected"`, `depgraph.py:5577-5605`). Parallel to `expanded_atoms` through the moves rewrite and dedup (both index-preserving); `dep_expand_token` mutates atoms in place, so the flag rides renames too.
- `@world` is `@profile ∪ @selected ∪ @system` (`_sets/__init__.py:97-98`), not just the world file; the world set lists its nested sets as `@profile @selected @system`. `emerge @world` / `-uD @world` re-emerges / updates every `@profile`/`@system` member too; on an empty world it is still non-empty. `@selected` alone stays the world file. Each `SetArg`'s list is processed `sorted(arg.pset.getAtoms(), key=str)` (`depgraph.py:5500`).
- Dedup explicit-wins: Portage holds both a `SetArg` and an `AtomArg` for an atom given both ways -- the set member drops but the explicit argument still fails the run. `@world` folding `@system` in overlaps the world file for anyone who ran `emerge --noreplace @system`.
- Bare-name expansion ports `dep_expand()` / `cpv_expand()` (`lib/portage/dbapi/`). The ambiguous multi-match shape ports the `ambiguous_package_name` block's `--quiet` form -- Portage's default form runs a full `search`, a documented cut. A `@set`-expanded atom is already `cat/pkg`, so only a genuine command-line bare name reaches this.
- A top-level blocker atom is rejected with Portage's `run_action` text (S7, #341: two `!!!` lines, exit 1 — the same gate as any other bad package atom, `is_valid_package_atom` with `allow_blockers=False`); dependency atoms from DEPEND/RDEPEND keep the full grammar.
- Recorded in `world_sets` after a successful non-`--pretend` merge (Portage `depgraph.saveNomergeFavorites`).
- Portage `_resolve` (`depgraph.py:5500`) processes each `SetArg`'s atom list `sorted(arg.pset.getAtoms(), key=str)`; the nested `@system` set is one such arg, and the world set lists its nested sets as `@profile @selected @system`.
- The `@profile` set on its own (Portage `ProfilePackageSet.load`); same sorted-arg shape as `@system` above.
- A `>=`-prefixed atom sorts before every plain one (`>` is 0x3E), which is exactly why Portage's `-pe @system` pre-bias order starts `>=sys-apps/baselayout-2`, `>=sys-apps/findutils-4.4`, `>=sys-devel/patch-2.7`, `app-admin/eselect`, `app-alternatives/awk`, … (F-B3's probe). Portuale used the profile's raw `packages` order, so the resolver walk -- and therefore the pre-bias order the scheduler's stable `_merge_order_bias` preserves -- diverged from index 1.
- Portage `profiles/updates/` package moves (SCOPE_BACKLOG Part 2 Section H item 2): a `move sys-libs/foo sys-libs/bar` / `slotmove` directive rewrites a command-line, `@world`/`@system` or `@<set>`-expanded atom before it's resolved *or* used as a display "requested" key (Portage global-updates rewrites the world file and the vdb; portuale applies the moves in memory on read -- see `portage_repo::apply_updates_to_atom`).
- Portage `dep_expand()` / `cpv_expand()` (`lib/portage/dbapi/`): a command-line target with no category (`emerge eix`, `emerge eix-1.2`, `emerge eix:0`) is qualified against the repo tree -- scan every `<repo>/<cat>/<pkg>/` for a package matching the bare name.

## fn expand_targets (allow-list, #571)
- Takes the run-shared `Categories`: short-name expansion (`dep_expand_token` over `all_cp(repos, &categories.set)`) and the `--update-if-installed` cp set see listed categories only. The similar-names block takes the same set (Portage suggestions never name an unlisted cp). Atom *validation* (`is_valid_package_atom`'s `cat` splice) is untouched — Portage validates against a dummy category too.
