## fn plan_resolve
- `--with-bdeps` (#361 S1): Portage's `create_depgraph_params.py:97-103` precedence -- an explicit `--with-bdeps` always wins; absent it, `bdeps` is "auto" only when `--with-bdeps-auto != n` AND the `--usepkg` key is absent from `myopts`. Absence is key presence, not value: `_emerge/main.py:1109-1121` stores `--usepkg=n` as `False`, so an explicit `=n` (command line or `EMERGE_DEFAULT_OPTS`, which prepends to argv) turns bdeps-auto off exactly like bare `--usepkg`. The key is also inserted `True` by the `_emerge/actions.py:3709-3723` implications -- `FEATURES=getbinpkg` folds to `--getbinpkg` (unless the command line said `--getbinpkg=n`), and `--getbinpkg`/`--getbinpkgonly`/`--usepkgonly` equal to `True` chain into `--usepkg`. Ported as `plan_with_bdeps` (`usepkg_given`/`getbinpkg_given` beside the values; the `FEATURES` fold is local to the rule, so `opts.getbinpkg` still means "remote loading on" elsewhere). When `bdeps` is left unset (the --usepkg case), `depgraph.py:4196` treats it as "not in (y, auto)", so `_add_pkg_dep_string` drops DEPEND/BDEPEND for every *built* (binary or installed) package. `with_bdeps` carries exactly that "keep build-time deps of a built package" bit through the resolver. NOT part of the rule: `--usepkgonly=n` stores `False`, implies nothing, and leaves bdeps-auto on -- Portage's `Total: 0` there comes from the ebuild-db drop (`depgraph.py:809`, `"--usepkgonly" not in myopts`), unmodelled (S0 STOP-2, no #396: the cell does not discriminate).
- `selective`: Portage's `create_depgraph_params.py` condition, computed from whichever of its trigger flags portuale implements -- see `resolve_pretend`'s doc comment (portage-repo) for the full grounding, including why `--changed-use` alone covers portuale's whole share of Portage's `--reinstall` contribution. `--newrepo` is one of Portage's listed triggers too (confirmed by reading it, line ~147: `"--newrepo" in myopts`). An explicit `--selective=n` unconditionally cancels it regardless of what the other flags computed, matching Portage's unconditional `if myopts.get("--selective") == "n": pop`, checked last, after every other trigger.
- --autounmask/--autounmask-keep-keywords/--autounmask-use/-license: Portage's `create_depgraph_params.py` default-resolution logic, simplified for portuale's v1 scope (`--autounmask-keep-masks` still isn't read, matching every fixture/user who never touches it getting the exact same outcome this simplification produces). Portage logic: `autounmask` itself defaults to enabled (only `--autounmask=n` turns the whole feature off -- with `--autounmask-use`/`-license` now read, the "is autounmask_use/license itself what makes autounmask default true" branch takes the "yes" arm whenever `--autounmask-use` isn't explicitly "n", which portuale's `autounmask_enabled` still simplifies to the same "only `--autounmask=n` turns it off" shortcut -- a narrow gap only when `--autounmask-use=n` is given *without* `--autounmask` itself, which Portage would still leave `autounmask` enabled for but is close enough in practice to be the same pre-existing simplification, not a new one). `autounmask_keep_keywords` (Portage: "suppress keyword suggestions") defaults to suppressed (true) when `--autounmask` itself was NOT explicitly given at all, but to *not* suppressed (false) once `--autounmask` itself WAS explicitly given (any value) -- Portage's own "explicitly asking for autounmask implies wanting its keyword suggestions too, but the ambient always-on default doesn't" asymmetry, ported exactly. `autounmask_use` (Portage: "allow autounmask to change package.use") has no such asymmetry -- Portage's `myparams["autounmask_keep_use"] = True if autounmask_use == "n" else False`, unconditionally on whenever `--autounmask-use` isn't explicitly "n".
- Known gap: Portage's `autounmask_use` is also forced to `"n"` whenever `myparams["binpkg_respect_use"] == "y"` (an explicit, literal `--binpkg-respect-use=y`, not the "auto" default) -- portuale's `binpkg_respect_use` is already a resolved bool by the time it's available, with no way to distinguish "explicitly y" from "auto-resolved to true". A narrow corner case: giving both `--binpkg-respect-use=y` and relying on `--autounmask-use`'s own default at once.
- `autounmask_license` defaults to `"y"` only when `--autounmask` itself is explicitly True, else `"n"`; `myparams["autounmask_keep_license"] = autounmask_license != "y"`.
- `autounmask_keep_masks`: `myparams["autounmask_keep_masks"] = autounmask_keep_masks not in (None, "n")`.
- Backtracking keeps going after autounmask changes only with `--autounmask-backtrack=y` -- Portage's `_backtrack_depgraph` (`depgraph.py:11736`) -- or `--autounmask-continue` (which implies it), unless `--autounmask-backtrack=n` is explicit. Carried into the resolver on `Config` (see `Config::autounmask_backtrack`).
