# crates/portuale/src/ebuild_merge/mod.rs
The merge driver: `merge`/`qmerge` entry points, shared helpers, submodules.

## module
- Task #55 (see `LLM/agent-context.md` "Real merge/install/filesystem mutation"): after the task-#54 `install` phase chain (`ebuild_phases`), runs `pkg_preinst`, copies `${D}`'s regular files, directories and symlinks into `${ROOT}`, writes a vdb entry (`CONTENTS` in the exact `obj`/`dir`/`sym` line format of Portage's `dblink._format_contents_line`, plus `CATEGORY`/`SLOT`/`repository`), then runs `pkg_postinst`. Mirrors Portage's `dblink.merge()`/`treewalk()`/`mergeme()` (`lib/portage/dbapi/vartree.py`, ~6500 lines) at a deliberately narrow v1 scope, the same "narrow v1, document the cut" pattern `ebuild_phases` established. `pkg_preinst`/`pkg_postinst` run via `ebuild_phases::run_single_phase`, not `run_commands`: Portage's `treewalk()` invokes them directly (`EbuildPhase(phase="preinst"/"postinst")`), not through `doebuild()`'s `actionmap_deps` chain.
- CONFIG_PROTECT for `obj` and `sym`: Portage's `ConfigProtect.isprotected()` path matching (`is_protected`), the MD5-comparison rename-instead-of-overwrite decision (Portage's `dblink._protect()`, into the next `._cfgNNNN_<name>` sibling -- Portage's `new_protect_filename()`, including reusing the last `._cfgNNNN_` file when its content/target already matches), and Portage's `vardbapi._conf_mem_file` persistence (`read_cfgfiledict`/`write_cfgfiledict`) so a repeat merge of an offered update doesn't spawn a fresh file every time -- unless `NOCONFMEM` is set (Portage's `--noconfmem`: an `emerge`-only CLI flag, `lib/_emerge/actions.py:2790`, landing as `settings["NOCONFMEM"]`, `vartree.py:4949`'s `cfgfiledict["IGNORE"]`; Portage's `bin/ebuild` has no such flag, so portuale reads the env var directly, the same "env var, not full config resolution" shortcut `CONFIG_PROTECT` uses). Options ride the `ebuild.rs` CLI boundary bundled into `MergeOptions` (deliberately a struct, not positional parameters -- portuale relearned the "positional-parameter pain" lesson once, in `--newrepo`'s bulk-fix saga), defaulting to Portage's `make.globals` `CONFIG_PROTECT="/etc"` / `CONFIG_PROTECT_MASK="/etc/env.d"` (`NOCONFMEM` unset). The MD5 decision is Portage's type-independent one (`vartree.py:5434-5480`/`5831-5901`, `protect_decision`, shared by both branches): `dest_md5`/`dest_link` always come from the live destination's lstat'd on-disk type, so a symlink replacing a regular file (or vice versa) is protected too. For symlinks the compared MD5 is the target string's, not file content (Portage bug #485598).
- `config-protect-if-modified` (Portage `vartree.py:4409-4418`/`5849-5866`): `installed_instance_pf` picks the max-`COUNTER` same-slot instance being upgraded (reusing the per-package `COUNTER` portuale writes on every merge), and `protect_decision` consults its `CONTENTS` (`owned_node_value_pf`): a path it recorded that is now missing on disk (admin deleted it) always force-diverts (Portage bug #523684); only when the feature is on (a Portage `make.globals` default), a live destination still matching exactly what that instance installed is overwritten directly, distinguishing "default content changed between versions" from "admin hand-edited it".
- `FEATURES=collision-protect`: Portage's `dblink._collision_protect` (`vartree.py:3836`), narrowed -- runs before `pkg_preinst` (matching Portage's `merge()` ordering: the abort precedes the `EbuildPhase(phase="preinst")` block), walks `${D}` like `merge_tree` but read-only, checking file/symlink entries only (never directories: Portage only checks `file_list`/`symlink_list`, built with `os.walk`, where a directory-target symlink lands in `dirs` and is never checked). PMS 13.4's symlink-over-directory ban covers only the checked symlinks (file-target/dangling) and is unconditional; a directory-target symlink over a directory is ignored by the check and lands at the first `dest.backup.NNNN` at merge time (Portage's `mergeme()` branch), keeping the directory (e.g. linux-firmware's `nvidia/ad10x` symlinks merge with exit 0 under plain `protect-owned`). An ordinary collision (destination exists, unowned by an older same-slot instance of this package, not `CONFIG_PROTECT`'d) aborts only when the feature is set; `find_owners` (Portage's `vardbapi._owners.get_owners()`, narrowed to a fresh per-abort scan of every installed `CONTENTS` rather than a persistent reverse index) names the owning packages for the message.
- `preserve-libs` collision exclusion, consult-and-exclude half only: Portage's `plib_inodes`/`plib_collisions` handling (`vartree.py:3860-3985`); a colliding path whose on-disk `(st_dev, st_ino)` matches a registry path is excluded unconditionally (Portage's `_plib_registry` is constructed unconditionally in `vardbapi.__init__`, not gated by the feature -- the flag only gates registration), since the just-merged package legitimately takes over that file. Post-merge mirrors Portage's `:5095-5159`: `unregister_preserved_libs` drops taken-over paths from the registry (removing the owning `cp:slot` entry once empty) and from the previous owner's vdb `CONTENTS` (Portage's `removeFromContents`), skipped when the previous owner is the just-merged package (`if cpv != self.mycpv`). The registry is a fixed-shape JSON document (`{"cp:slot": [cpv, counter, [paths...]]}`, Portage's `PreservedLibsRegistry.store()` `json.dumps(indent="\t", sort_keys=True)`) read/written with a hand-rolled parser/writer rather than a new `serde_json` dependency, matching portuale's "small, format-specific parser" precedent (`--json` output, `SRC_URI` grammar, `grabdict` `thirdpartymirrors`).
- `FEATURES=protect-owned`: Portage's separate abort condition alongside `collision-protect` (`vartree.py:4770-4838`; Python precedence makes it `collision_protect or (protect_owned and owners)`). `protect_owned` alone aborts only when `find_owners` identified an owner for at least one collision; Portage's "None of the installed packages claim the file(s)" case (stray unowned file) does not abort under it alone.
- Blocker exclusion: Portage's `mypkglist = others_in_slot + blockers`. Portage's `dblink._blockers` is never computed by `dblink` itself but injected by the depgraph resolver; portuale's standalone `ebuild <file> merge` has no depgraph, so `blocked_installed_packages` is new self-contained machinery (repos.conf/profile/USE resolution via `portage_repo::find_repos` + `portage_profile::resolve_config`, effective USE via `portage_repo::effective_use_flags`, flattening via `portage_use_reduce::use_reduce_flat` over all five `*DEPEND` keys, blocker-atom matching via `portage_dep::match_from_list`). Degrades to an empty set on any resolution failure; see `MergeOptions::config_root` for the safety issue this surfaced (portuale's dev/test machine has a populated `/etc/portage/repos.conf`, so an ambient env-var default would have made every pre-existing test read host config).
- `pkg_preinst`/`pkg_postinst` run via `ebuild_phases::run_single_phase`, not `run_commands`, since Portage's `treewalk()` invokes them directly (`EbuildPhase(phase="preinst"/"postinst")`), not through `doebuild()`'s own `actionmap_deps` chain the way `pretend`..`install` are.
- Portage's `_installed_instance`/`FEATURES=config-protect-if-modified` is implemented (`vartree.py:4409-4418`/`5849-5866`): `installed_instance_pf` picks the max-`COUNTER` same-slot instance this merge is upgrading over.
- `FEATURES=collision-protect`: Portage's `dblink._collision_protect` (`lib/portage/dbapi/vartree.py:3836`), narrowed; the abort happens before `pkg_preinst` ever runs, matching `merge()`'s own ordering exactly: the Portage abort happens before the Portage `EbuildPhase(phase="preinst")` block, not after.
- Preserve-libs collision exclusion: a colliding path whose on-disk `(st_dev, st_ino)` matches a path the Portage `preserved_libs_registry` JSON already lists for some other package is excluded from ordinary collision reporting unconditionally (Portage's `_plib_registry` is constructed unconditionally in `vardbapi.__init__`, not gated by `FEATURES=preserve-libs` at all -- that flag only gates the registration side). The registry is read/written with a small hand-rolled parser/writer (`read_plib_registry`/`write_plib_registry`) rather than a new `serde_json` dependency.
- `FEATURES=protect-owned`: Portage's `dblink.merge()` separate abort condition alongside `collision-protect` (`lib/portage/dbapi/vartree.py:4770-4838`; Python operator precedence makes the Portage check `collision_protect or (protect_owned and owners)`).
- Blocker exclusion: portuale's own `ebuild <file> merge` has no depgraph at all (a standalone, single-ebuild real-execution path, unlike `emerge --pretend`), so `blocked_installed_packages` is new, self-contained machinery: effective-USE computation (`portage_repo::effective_use_flags`, made `pub` for this), dependency-string flattening (`portage_use_reduce::use_reduce_flat`) against `DEPEND`+`RDEPEND`+`BDEPEND`+`PDEPEND`+`IDEPEND`, and blocker-atom matching against every installed package (`portage_dep::match_from_list`).

## known gaps (v1 scope)
- The one non-`NEEDED.ELF.2`-driven branch inside Portage's `LinkageMap.rebuild()` is still not ported: live `scanelf` for orphaned preserved libs (`LinkageMapELF.py:233-324`) -- the one spot a raw ELF header read would matter. Every other preserve-libs registration/detection computation (`needed_elf.rs`: `NeededEntry`, `read_all_needed_entries`, `rebuild`, `getlibpaths`, `find_consumers`, `find_libs_to_preserve`) and the control-flow wiring into merge (`unregister_preserved_libs`) and unmerge (`preserve_libs_on_unmerge`) are ported; see `LLM/what-this-proves.md`'s "`preserve-libs`" sections for each slice's grounding.
- `merge_tree`'s file/symlink writes mirror Portage's `movefile()` atomic replacement: materialize at a temporary sibling (`.{name}._portage_merge_.{pid}`) and `rename(2)` over the destination, so the existing inode is never written to. Load-bearing, not cosmetic (backlog #96): an in-place `std::fs::copy` truncates the live inode; the kernel refuses to open a running executable for write (`ETXTBSY`, which used to abort a `/bin/bash` merge mid-copy) but an mmap'd shared library opens fine, so every process mapping it would execute rewritten pages. Portage is safe the same way (`os.rename` same-device, `movefile.py:231`; copy-to-`#new`-then-rename cross-device, `:346`; see `replace_file_atomic`/`replace_symlink_atomic`). Attribute parity is Portage's explicit `os.chmod`/`os.chown`, reproduced with `std::fs::set_permissions` on the temp file before the rename (on top of the mode bits `std::fs::copy` already carries over). Shipped 2026-09-05: Portage's `os.lchown`/`os.chown` (symlink, regular file) and `mergeme()`'s directory `os.chown`/`os.chmod` (newly created directories only; existing ones left alone) are reproduced via `lchown_or_chown` (`libc::lchown`/`libc::chown`); root/non-root behaviour is unconditional like Portage (fails with `EPERM` like Portage when privileged-but-not-root). No privilege-dropping anywhere (Portage userpriv/fakeroot's reason for existing); see `LLM/scope-backlog.md` "sandbox / build isolation" for that separate non-goal.
- Directory merge order is sorted by filename for determinism (portuale's test-reproducibility need) rather than Portage's arbitrary `os.listdir()` order -- a deliberate choice, not a gap: `CONTENTS` order has no meaning Portage relies on (unmerge re-sorts, `qmerge`/`qlist` sort on read).
- `SLOT` is read the way Portage's `dblink.treewalk()` reads it (`vartree.py:4455-4498`): from `build-info/SLOT`, which the install phase's `__dyn_install` filled with the evaluated `${SLOT}`, so a bash-computed `SLOT="$(ver_cut 1)"` is already evaluated. The full fallback chain (build-info value, then `settings["SLOT"]` write-back, then `!!! SLOT is undefined` abort, plus the `_eqawarn` QA Notice on divergence) lives in `merge_after_install`.
- `repository` is resolved by walking up from the ebuild's package directory for a `profiles/repo_name` file (Portage's own mechanism), defaulting to the `"__unknown__"` sentinel `portage_repo::new_repo_changed` already uses.
- The `LinkageMap.rebuild()` gap, verbatim: the one non-`NEEDED.ELF.2`-driven branch inside Portage's `LinkageMap.rebuild()` itself is still not ported: live `scanelf` for orphaned preserved libs (`LinkageMapELF.py:233-324`).

## fn feature_enabled
- The merge's resolved incremental list (`MergeOptions::features`, the `emerge` paths, #37 S2) when set, else the raw `$FEATURES` process env (the standalone `ebuild <file>` fallback `MergeOptions::from_env` documents). Mirrors `emerge_build::resolved_features`' precedence.

## fn process_merge_elog
- Ports Portage's `dblink.merge()` `self._elog_process()` call between the success/die hooks and the post-merge `clean` (`dbapi/vartree.py:6160-6198`). Running it there keeps the messages alive now that backlog #42's clean removes `${T}`: Portage's `elog_process` is per-package, before the clean, and so is this. `--buildpkgonly` keeps its "no elog" behaviour (Portage processes it in `_buildpkgonly_success_hook_exit`; portuale does not yet). The `split_elog` argument is the merge's resolved list when set (#37 S2/S3); the standalone fallback is the raw env.

## fn run_merge / fn run_merge_with_hook
- `run_merge`'s first step is always the `install` phase chain already completed (`actionmap_deps["merge"] == ["install"]`), run here directly like `ebuild_phases::run_commands` chains prerequisites; Portage's `PORTAGE_BUILDDIR`-relative resume markers make re-running a done `install` cheap, so calling after an `install` in the same command list (see `ebuild.rs`'s dispatch loop) is safe.
- `buildpkg` is `Some` for a source `emerge <atom>` under `FEATURES=buildpkg`/`--buildpkg` (Portage's `_emerge/EbuildBinpkg`): a binpkg of the fresh `${D}` is written into `$PKGDIR` before the vdb merge, matching Portage's `EbuildBuild` -> `EbuildBinpkg` -> `EbuildMerge` task order (a build failure merges nothing). `ebuild <file> merge` passes `None`: `buildpkg` is an `emerge`-flow concept with no Portage `bin/ebuild` equivalent.
- The hook is what Portage's `Scheduler._build_exit` fires between the halves: it wraps the finished `EbuildBuild` in a `PackageMerge` (`Scheduler.py:1615-1621`) whose `_start` prints `Installing (cur of max)` (`PackageMerge.py:32-54`). A failed build never reaches the hook (Portage queues no merge for it).
- Inside the `buildpkg` arm: the `USE` field is Portage's `Package.use.enabled` (the resolved flag set `install` just ran with). Per-package `FEATURES` (backlog #130): `options.features` is already this call's fully resolved value (per-entry fold when matched, run-wide otherwise), so the binpkg-affecting `PackageOptions` fields re-derive from it. Per-package `BUILD_ID` gate (backlog #147 S1 ruling (i)): the export follows the resolved features while the layout stays run-wide.
- The hook point is Portage's `PackageMerge._start`: build halves succeeded, vdb merge not started -- where Portage prints `Installing (cur of max)`.
- The tail is Portage's `dblink.merge()` (`dbapi/vartree.py:6183-6198`): after success hooks and `env_update`, `clean` removes the builddir unless `FEATURES=noclean`, never after a postinst failure (bug #704866, i.e. non-zero `merge_status`). Backlog #42's post-merge half; the `emerge` scheduler's build+merge split gets the same call from `emerge_build::merge_one_built_entry`.
- Portage's `Scheduler.py:1615-1621` wraps the finished `EbuildBuild` in a `PackageMerge`, whose `_start` prints `Installing (cur of max)` (`PackageMerge.py:32-54`) before `create_install_task()` starts the `EbuildMerge` vdb merge -- i.e. after the build phases (and the `EbuildBinpkg` packaging) succeed, before the vdb merge begins.
- Per-package `FEATURES` (backlog #130): `options.features` is the caller's per-entry fold when one matched (`entry_resolved_features` + `MergeOptions::set_resolved_features`), the run-wide value otherwise; re-deriving the binpkg-affecting `PackageOptions` fields from it keeps `binpkg-multi-instance`/`buildpkg-live`/`binpkg-signing` in step with the same `FEATURES` the `install` phase just saw, instead of the caller's single shared, run-wide `PackageOptions`. Portage's `EbuildBinpkg._start` per-package `BUILD_ID` gate (backlog #147 S1 ruling (i)) follows the same value.

## fn run_qmerge
- Ports Portage's `doebuild()` `mydo == "qmerge"` branch (`doebuild.py:1562-1591`): skips `install`, assuming a prior one populated `${D}`, gated on the same `${PORTAGE_BUILDDIR}/.installed` marker Portage checks (see `Environment::installed_marker` for why portuale doesn't write it itself). Portage doesn't treat a missing marker as a hard failure (`writemsg(...); return 1`, not an exception); portuale's `Err` through `ebuild.rs`'s `Err` -> `eprintln!` path produces the same exit code 1 (see `ebuild.rs`'s `Ok(_) => ExitCode::from(1)` fallback), and matches this module's other "not in the expected state" checks (e.g. `run_unmerge`'s "not installed") rather than a second message-printing path.
- No post-merge `clean`: Portage's `qmerge` branch adds `noclean` to `settings.features` before `merge()` (`doebuild.py:1573-1575`: "qmerge is a special phase that implies noclean"). The `emerge` scheduler path reaches `run_qmerge` but does post-clean like Portage's `dblink.merge()`; that call lives in `emerge_build::merge_one_built_entry` right after this returns 0, keeping `ebuild <file> qmerge`'s builddir the way Portage keeps it (backlog #42).
- Portage's `doebuild()` `mydo == "qmerge"` branch (`lib/portage/package/ebuild/doebuild.py:1562-1591`): skips the `install` phase entirely. A missing marker is a hard failure in Portage (`writemsg(...); return 1`, not a raised exception); the `Err` -> `eprintln!("ebuild: {e}")` path still produces the same exit code (1) either way.

## fn source_distfiles
- Ports Portage's `configdict["pkg"]["A"]` (`doebuild.py:585-594`): the use-reduced, unique distfile basenames of `SRC_URI`, reduced against the resolved `USE` the hook env carries. Portage's `config.environ()` exports it into every phase, so the postinst vdb-env regeneration (see `merge_after_install`'s `PORTAGE_UPDATE_ENV` comment) sees it; the filtered `${T}/environment` drops `A`, so the merge path re-supplies it. `None` outside a repo checkout, with no `SRC_URI`, or on an unparsable `SRC_URI` -- the same "can't tell, so don't set it" degrade `flat_field_on` uses. Portage sets `A` unconditionally (`" ".join(uri_map)` is `""` for an SRC_URI-less package like `virtual/pkgconfig`), so missing/empty yields `Some("")`: the vdb env must carry `declare -x A=""` the way Portage's does.
