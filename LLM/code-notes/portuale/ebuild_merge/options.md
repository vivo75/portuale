# crates/portuale/src/ebuild_merge/options.rs
Env-var-sourced merge options for `run_merge` plus the `movefile` xattr policy.

## struct MergeOptions
- Bundled into a struct rather than more positional parameters: portuale already relearned the "positional-parameter pain" lesson once, in `--newrepo`'s bulk-fix saga.
- `config_protect`/`config_protect_mask` are env-var-sourced at the `ebuild.rs` CLI boundary, the same "env var, not full config resolution" shortcut `PORTAGE_TMPDIR`/`ROOT` already use.
- `collision_protect`: Portage `"collision-protect" in self.settings.features`. `FEATURES` itself is never in `FEATURES` by default (Portage's `make.globals` never sets it), so `Default = false` matches.
- `protect_owned`: Portage `"protect-owned" in self.settings.features` (lib/portage/dbapi/vartree.py:4718); a separate abort condition from `collision_protect` (see `run_merge`'s doc for the exact Portage logic). Unlike `collision_protect`, it IS one of Portage's `make.globals` default `FEATURES` tokens (cnf/make.globals:77-84), confirmed by reading it directly -- a previously-undiscovered mismatch: this field's `Default` used to be `false` with a doc comment incorrectly claiming the same "not in FEATURES by default" reasoning. `Default` is now `true`, matching Portage's actual out-of-the-box behavior. The env-var read only checks whether the literal `FEATURES` value (when set at all) contains `"protect-owned"`; it doesn't *accumulate* onto the default set the way Portage's own `+`/`-`-prefixed `make.conf` `FEATURES` merging does, so `FEATURES=<other>` reads `false` here while Portage would keep it enabled unless `-protect-owned` was given -- a pre-existing simplification.
- `noconfmem`: Portage `--noconfmem`/`settings["NOCONFMEM"]` (lib/_emerge/actions.py:2790, vartree.py:4949 `cfgfiledict["IGNORE"]`); an `emerge`-only CLI flag with no `bin/ebuild` equivalent, so portuale reads the `NOCONFMEM` env var directly (presence-based, matching `"NOCONFMEM" in self.settings`) rather than adding a CLI flag Portage's `ebuild` doesn't have. `Default = false` matches Portage's default (unset).
- `protect_if_modified`: Portage `"config-protect-if-modified" in self.settings.features` (vartree.py:5376-5379); gates `_protect()`'s `protect_if_modified` behavior (see `protect_decision`). It IS one of Portage's `make.globals` default `FEATURES` tokens (cnf/make.globals:79), confirmed by reading it directly -- the same category of previously-undiscovered default-`FEATURES` mismatch as `protect_owned`. Same env-var-not-full-config-resolution shortcut (and the same non-accumulation simplification).
- `config_root`: Portage `PORTAGE_CONFIGROOT` (`portage_repo::config_root_from_env`'s default: `/` when unset); consulted only by `blocked_installed_packages`' `repos.conf`/profile/USE resolution. Deliberately an explicit field, not an ambient env read inside library code -- the same "explicit parameter, not ambient env read" reasoning `portage_fetch::FetchOptions::gentoo_mirrors` established. Load-bearing here for a different reason: portuale's dev/test machine is a real Gentoo system with a populated `/etc/portage/repos.conf`, so silently defaulting to `/` the way `ebuild.rs`'s CLI boundary does would make every test that doesn't override this field read real host config. `Default` is a deliberately impossible path (`/dev/null/...`: `/dev/null` is a real character device, never a directory, so joining anything under it can never exist on any real filesystem, guaranteeing `find_repos` always fails cleanly), so `blocked_installed_packages` degrades to an empty blocked set unless a test opts in explicitly.
- `build_env`: `install` runs via `run_merge`, `pkg_preinst`/`pkg_postinst` via `merge_after_install`. The `emerge <atom>` source path sets `[("USE", "<resolved enabled IUSE flags>")]`, computed per entry by `merge_one_source_entry`, so `bin/ebuild.sh`'s `use()` sees the flags instead of the `""` `phase_env_vars` leaves. Empty (`Default`) for standalone `ebuild <file> merge`/`qmerge` and tests. See `ebuild_phases::run_commands_async`.
- `resolved_config`: in scope for `emerge <atom>` and friends (#37 S2); `None` for standalone merges (keeps the curated base env). `emerge_build::entry_build_env` uses it to compute each entry's resolved `USE` (`portage_profile::portage_use` over `portage_repo::candidate_effective_use_flags`) and the per-package rows of Portage's `config.environ()` (`phase_environ_pkg`), instead of the enabled-IUSE-only `USE` this field used to carry. An `Arc` so the per-entry `options.clone()` is a pointer copy.
- `package_env_vars`: `/etc/portage/package.env`'s non-`USE` scalar half (`Config::package_env_vars`), `(atom, [(KEY, value)])` pairs. `emerge_build::entry_build_env` matches a build-bound entry's cpv against each atom and layers matches over `build_env` (scalars lose to the calling environment, incrementals fold in `[base, pkg, calling-env]` order) -- Portage `_grab_pkg_env` into `configdict["pkg"]`. Empty (`Default`) everywhere else.
- `log_file`: Portage `Scheduler._background_mode`'s `PORTAGE_LOG_FILE` redirection, extended to this merge's `pkg_preinst`/`pkg_postinst`/`pkg_prerm`/`pkg_postrm` hooks. Previously only the `install` phase chain (`emerge_build.rs` `build_one_source_entry`/`run_build_scheduler`) had a log path, so every hook printed straight to the terminal even under `-jN`/`--quiet-build`, interleaving with or outliving the per-job build log Portage keeps separate. `Some` only when the caller already derived a `build.log` path for this package's `install` phase (`emerge_build.rs` `build_log_path`); `run_one_phase`'s log file opens in append mode, so hook output lands after that phase's in the same file, exactly the way Portage's single `PORTAGE_LOG_FILE` spans a whole package's build-then-merge lifecycle. `None` (`Default`) for standalone `ebuild <file> merge`/`qmerge`/`unmerge`, `emerge -C` and tests, matching Portage's foreground run.
- `install_mask`: Portage `INSTALL_MASK` as `preinst_mask()` (bin/misc-functions.sh) resolves it: configured `INSTALL_MASK` (`make.conf`/profile/bashrc) with the `no{man,info,doc}` `FEATURES` tokens folded in (each appends `/usr/share/<man|info|doc>`). Portage `dblink.treewalk()` applies it to the staged image -- deleting every matched path -- *before* `CONTENTS` is recorded and before collision-protect, so a masked file never lands in `${ROOT}` nor in the vdb `CONTENTS`. Written verbatim into the vdb entry's `INSTALL_MASK` file too (Portage copies `build-info/INSTALL_MASK` wholesale). Empty (`Default`) means nothing masked, no `INSTALL_MASK` file written.
- `install_mask_prunes_usr_share`: with `nodoc`/`noman`/`noinfo` in `FEATURES`, Portage `dblink.treewalk()` also `rmdir`s a now-empty `ED/usr/share` after applying the mask; `false` leaves an emptied `usr/share` in place, exactly as Portage does when the mask emptied it for some other reason.
- `gpg_verify`: Portage `gpkg._verify_binpkg`'s GPG layer (see `crate::binpkg::GpgVerify`); enforced by `merge_binpkg` (via `extract_binpkg`) before anything is unpacked. `from_env` resolves it from `FEATURES`/`BINPKG_GPG_VERIFY_*`; `Default` is the same resolution (env reads either way -- the struct carries no other state).
- `features`: the resolved merge-time `FEATURES` incremental list (space-joined) for `merge_binpkg`'s `PORTAGE_UPDATE_ENV` vdb-environment regeneration -- Portage's stored vdb env carries the fully-resolved list, not the binpkg's build-time one. The `emerge` production paths set this from `Config::resolved_incremental("FEATURES")`; `from_env`/`Default` fall back to the raw `$FEATURES` string (all `ebuild <file> merge` has).
- `process_tmpdir`: Portage's `env` layer outranks the `pkg` layer, so a per-package `package.env` `PORTAGE_TMPDIR` only re-derives the build directory when this is `None` (backlog #99, resolved per entry by `ebuild_phases::resolve_entry_portage_tmpdir`).
- `protect_owned` env read: any *other* token still reads as `protect_owned: false` here, unlike Portage (which would keep it enabled unless `-protect-owned` was explicitly given).
- `noconfmem`: forces every already-offered, unmodified-since CONFIG_PROTECT update to be re-protected into a fresh `._cfgNNNN_` file instead of silently reused/applied.
- `config_root`: Deliberately an explicit field, not an ambient env read inside this module -- the same "explicit parameter, not an ambient env read inside library code" reasoning `portage_fetch::FetchOptions::gentoo_mirrors` already established.
- `log_file`: the same-slot-replace/binary-merge `prerm`/`postrm`/`setup` hooks are reached through `unmerge_one_installed`/`run_binary_merge`'s own `run_hook` closures; they printed straight to the terminal even under `-jN`/`--quiet-build`.

## impl MergeOptions::from_env
- Portage's `settings`-derived merge configuration via the shortcut every real-execution CLI boundary in portuale takes (`PORTAGE_TMPDIR`/`PKGDIR`/..., no full profile+`make.conf` resolution): `CONFIG_PROTECT`/`CONFIG_PROTECT_MASK`, `DISTDIR`, the `FEATURES` tokens, `NOCONFMEM` presence, `PORTAGE_CONFIGROOT` (default `"/"`). Shared by `ebuild <file> merge`/`qmerge` (`ebuild.rs`) and `emerge <atom>` (`emerge_build::run_source_merge`).
- `install_mask`/`install_mask_prunes_usr_share`: the `emerge <atom>` production path overrides both fields from the resolved `Config` (`make.conf` `INSTALL_MASK`/`FEATURES`) right after this; the env read is the `ebuild <file> merge`/`qmerge` fallback, matching every other var here.
- `features`: the `emerge` paths overwrite the raw `$FEATURES` fallback with the resolved incremental list right after, as with `install_mask`.
- `process_tmpdir`: the `emerge` paths keep `from_env`'s value like every other var here.

## impl MergeOptions::set_resolved_features
- Applies the resolved `FEATURES` list (Portage's `settings.features` from `config.environ()`). This is what makes a `make.conf` `FEATURES=collision-protect` (or `-protect-owned`) take effect on the `emerge` paths -- Portage reads `settings.features`, never the calling env, for all three.

## impl MergeOptions::apply_config_protect
- Backlog #333. Portage `dblink._get_protect_obj` (vartree.py:2063-2072) and quickpkg's `include_config` filter (vartree.py:2340-2350) read `settings["CONFIG_PROTECT"]`: the incremental fold of env.d, `make.globals`, the profile chain, `make.conf` and the calling env (config.py:2735-2736), which `Config::resolved_incremental` already computes (`emerge --info` prints it byte-identical to Portage). `from_env` read only the process env, so a merge started without the login shell's exported `CONFIG_PROTECT` protected `/etc` alone.

## struct XattrPolicy
- #329. Portage renames the image file into place when both sides share a device (movefile.py:326-330), so every xattr survives whatever `FEATURES` says. Across devices it copies, then `_copyxattr`s (movefile.py:351-358) only under `FEATURES=xattr`, skipping `PORTAGE_XATTR_EXCLUDE` patterns. `_needs_move` (vartree.py:6376-6379) also compares xattrs (`_cmpxattr`) under `FEATURES=xattr`.
- What Portage `movefile()` does with a merged file's extended attributes. portuale always copies (see [`replace_file_atomic`]), so it reproduces both outcomes explicitly.
- `enabled`: `"xattr" in settings.features`. `exclude`: `settings.get("PORTAGE_XATTR_EXCLUDE", "")`.

## impl XattrPolicy::from_options
- Uses the merge's resolved `FEATURES` when the options carry a non-empty list, else the raw `$FEATURES` (as everywhere else in this module). Uses the resolved config's `PORTAGE_XATTR_EXCLUDE` (`make.globals` sets it), else the process env's.

## MergeOptions.direct (#403)
- The direct-`ebuild`-applet gate for the per-file listing printer
  (`listing.rs`): `ebuild.rs` sets it for `merge`/`qmerge`/`unmerge`; the
  `emerge`-scheduler paths never do (their listing would go to the build
  log, which portuale does not reproduce). Portage discriminator:
  `dblink._display_merge`'s foreground scheduler vs background task.
