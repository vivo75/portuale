# crates/portuale/src/ebuild_merge/after_install.rs
The post-install merge driver and same-slot unmerge.

## fn merge_after_install
- `instprep` runs first (Portage's `dblink.treewalk()` starts with it; see `ebuild_phases::run_instprep`).
- SLOT read (Portage's `treewalk()` `_installed_instance` slot read, `vartree.py:4455-4498`): the evaluated slot comes from `build-info/SLOT` (the install phase's `__dyn_install` wrote the live `${SLOT}`, so a computed `SLOT="$(ver_cut 1)"` is already evaluated and Portage only `_eqawarn`s a divergence), not from parsing the raw ebuild text (which would hand back the literal `$(ver_cut 1)` -- the #149 symptom). The full chain: read `build-info/SLOT`'s first line (empty/whitespace counts as a read error; Portage tolerates a missing file as empty); empty falls back to the resolved `settings["SLOT"]` (`options.build_env`'s `SLOT`, the emerge path's resolved metadata value) written back into the inforoot via `write_atomic`; still empty aborts with `!!! SLOT is undefined`; source builds only (`is_binpkg` is always false here; the binary path reads `meta_get("SLOT")` instead) warn with a `_eqawarn` QA Notice on a known settings value differing from the inforoot value. Guarded on a non-empty settings value because Portage always carries a resolved `settings["SLOT"]` on a merge (`depend` has run) while portuale's fixture path can hand an empty `build_env`, where an `Expected SLOT='', got '1'` notice would be noise.
- The installed instance (Portage's `self._installed_instance`, `vartree.py:4409-4418`) is computed before the vdb write touches this category/pf's `CONTENTS`.
- Slot comparisons use the main slot (`"0"` for a real `"0/6"`): `installed_instance_pf`/`find_collisions`/`blocked_installed_packages` all compare against `read_installed_slot` (the installed vdb `SLOT` file's main slot), while the vdb write records the ebuild's full `slot/sub_slot`. Passing the full slot made every sub-slotted package (ncurses, glibc, ...) look like it owned none of its files, so reinstall merges aborted under `FEATURES=protect-owned` (L3 smoke finding).
- `REPLACING_VERSIONS` is set right before `pkg_preinst` (`vartree.py:4768-4771`), and Portage's general `doebuild_environment` setter runs it for `postinst` too (`doebuild.py:1317-1322`); see `replacing_versions`.
- The `preinst_mask` + `install_mask_dir` step runs before `_collision_protect` and before any copy; see `apply_install_mask`.
- Collision ordering is Portage's `merge()`: the `_collision_protect` abort precedes the `EbuildPhase(phase="preinst")` block (confirmed by reading it; the Portage `EbuildPhase(phase="preinst")` block sits strictly after the Portage `if abort: return 1` check). The preserve-libs registry is consulted unconditionally (Portage's `_plib_registry` is never `None` in practice), regardless of `FEATURES=collision-protect`. `mypkglist = others_in_slot + blockers`; standalone `ebuild <file> merge` has no depgraph and never resolved config/USE before, so the blocker half is new machinery (see `blocked_installed_packages`).
- Abort condition is Portage's `dblink.merge()` (`vartree.py:4830-4838`; Python operator precedence: `collision_protect or (protect_owned and owners)`). A checked symlink-over-directory violation (file-target/dangling over a directory; directory-target symlinks never reach `symlink_collisions`, see `find_collisions`) always aborts; `collision_protect` alone aborts on any collision, `protect_owned` alone only when an owner was identified (Portage's "None of the installed packages claim the file(s)" case does not abort under `protect_owned` alone). `find_owners` is computed a second time here (alongside `collision_message`'s own call) only when `protect_owned` might need it, matching Portage's `get_owners()` running only when `collision_protect or protect_owned or symlink_collisions`.
- Vdb temporary ordering is Portage's `treewalk()`: the `-MERGING-<pf>` entry is created before `pkg_preinst` (wiping a stale one a killed merge left), populated after it, renamed into place only after every replaced same-slot version is unmerged; `pkg_postinst` runs last and sees the live entry (see `create_vdb_tmp`/`populate_vdb_tmp`/`publish_vdb_tmp`). `run_single_phase` (not `run_commands`) since neither hook is in the `install` chain's own `actionmap_deps` (Portage's `treewalk()` invokes them directly, not through `doebuild()`).
- Pre-replace-loop preserve-libs (Portage's `treewalk` block): the replaced instance's still-needed libraries are selected now -- the new entry sits in its `-MERGING-<pf>` temporary (written by `populate_vdb_tmp`), so enumeration skips it and it reaches the linkage map only through the explicit include feed inside `find_preserve_paths_for_merge` (Portage's `include_file=needed`) -- and their entries are carried into the new package's `CONTENTS` (`_add_preserve_libs_to_contents`). The record lands after the replace loop (`register_merge_preserved_libs`).
- Replace loop is Portage's `treewalk()` (`vartree.py:5187-5219`): after the file copy, before the rename into place and `pkg_postinst`/`env_update`. A same-cpv reinstall finds nothing to unmerge (its live entry is untouched until publish), matching the pre-replace-loop behaviour. The merge-side just-preserved set travels with the loop (Portage's `preserve_paths` into `dblink.unmerge`) so the post-unmerge prune sees files no `NEEDED.ELF.2` indexes yet (see `linkage_owner_entries`).
- Post-replace-loop registration (Portage `vartree.py:5266-5272`; backlog #178): the one `cp:slot` record is replaced by the merging package's `(cpv, counter, paths)`, so a second consecutive soname bump cannot keep a stale path list. After the rename into place, like Portage (backlog #183: the counter is read back from the published entry). On a database backend the publish, deletion of replaced entries and registration are one commit (see `publish_merged_entry`).
- Postinst ordering is Portage's `merge()`: its exit never gates what follows ("It's stupid to bail out here, so keep going regardless of phase return code"); Portage's `env_update()` always runs next as long as anything was installed (`if contents:`) or a replaced version was removed. `PORTAGE_UPDATE_ENV=<dbpkgdir>/environment.bz2` is set before the postinst of every merge, source included (Portage's `treewalk()`, `vartree.py:5334-5337`), so `bin/phase-functions.sh:1072-1082` rewrites the vdb environment from the live environment through the filtered save -- which drops the install-time `build-info/environment` save's stray globals (`f`, `x`) Portage never records (#45 P2a finding). The filtered `${T}/environment` drops `A`, re-supplied here exactly as Portage's `doebuild_environment`/`config.environ()` exports it (`doebuild.py:585-594`: the use-reduced, unique distfile names). The path is the live entry's own file (`InstalledDb::entry_path`, feat#157 N9; on `files` `<root>/var/db/pkg/<cat>/<pf>`); a database backend uses a scratch copy in the build dir, stored back after the phase (`update_env_target` / `absorb_update_env`, S4.1).
- `env_update` then prunes preserved libs orphaned by the merge: Portage's `treewalk()` "For gcc upgrades, preserved libs have to be removed after the library path has been updated" via Portage's `_prune_plib_registry()`. No include feed: the new entry is already renamed into place, so its own lines are enumerated (backlog #224).
- Portage's `dblink.merge()` `self._elog_process()` runs after the merge body and before the clean (which every caller runs once this returns). Backlog #42: the post-merge clean removes `${T}`, so this must not be deferred to a batch after the whole `emerge` returns -- and Portage never deferred it either.

## fn unmerge_replaced_same_slot
- Ports Portage's `treewalk()` replace loop (`vartree.py:5187-5219`). Merge-then-unmerge matches `<package>-<digit...>` vdb-dir names, the same shape `blocked_installed_packages` and `installed_instance_pf` match; the just-merged entry is excluded. A `-MERGING-<pf>` temporary can never match the shape (Portage package names never start with `-`) but is skipped explicitly anyway: readers never see in-progress entries, not even here.
- `dblink.unmerge(needed=...)` (backlog #224): the replacing package's `NEEDED.ELF.2` lines travel with the replace loop into `_prune_plib_registry`'s `_linkmap_rebuild(include_file=...)`, because the new entry still sits in its temporary and enumeration skips it. Read once here (the temporary is live for the whole loop).
- Feat#157 S4.1: on a database backend the replaced entries are deleted by the publishing commit (`publish_merged_entry`), not here, so the old instance stays installed until the new one is; later iterations still treat already-unmerged instances as gone (`others_in_slot`), as on `files` where their directories are removed in this loop.
- Elog is Portage's `dblink.unmerge()` `self._elog_process(phasefilter=("prerm", "postrm"))`: the superseded versions' `pkg_prerm`/`pkg_postrm` `elog`/`ewarn`/`eerror` output reaches the `echo`/`save`/`save_summary` modules, exactly as `emerge -C` does through `execute_unmerge`. Each old PF's `${T}` is `unmerge_one_installed`'s `run_phase_from_saved_env` builddir (`<PORTAGE_TMPDIR>/portage/<cat>/<pf>/temp`), which here only holds `prerm`/`postrm` logs. Colour resolves the way every non-graph path does (`NO_COLOR` / not-a-tty aware). The `split_elog` argument is the merge path's resolved list when set (#37 S3); the standalone fallback is the raw env.

## fn unmerge_one_installed
- A replace-loop phase failure is logged, never fatal: Portage's `treewalk()` replace loop is a literal `# TODO: Check status and abort if necessary` that doesn't, and Portage's `emerge -C` loop only aborts on the file-removal core failing, not on a phase.
- `backup` is `Some` only for standalone removals with `FEATURES=unmerge-backup` (Portage's `dblink._pre_unmerge_backup`, at the very top of `dblink.unmerge()` before `pkg_prerm` and before a single file is touched): a `quickpkg` of the still-installed package into `$PKGDIR` (`ebuild_package::quickpkg_from_vdb`). A quickpkg failure aborts the unmerge, Portage's `if retval != os.EX_OK: ... return retval`. The replace loop passes `None`: its `_pre_merge_backup`/`downgrade-backup` path is a documented cut.
- Feat#157 S4.2: a standalone unmerge on a database backend collects its D4 writes and commits them with the row's deletion.

## fn run_vdb_saved_env_phase
- Unlike `unmerge_one_installed`'s internal hook runner this does not gate on `DEFINED_PHASES`: the caller decides (Portage's `emerge --config` runs `pkg_config` unconditionally, Portage's `doebuild(ebuildpath, "config", ...)`).
- Both files go to bash / a copier by path (N9): the entry's own directory on `files`; on a database backend a scratch copy of the two files under `scratch_dir` (feat#157 S4.1; nothing is stored back, the phase gets no `PORTAGE_UPDATE_ENV`).
- Each unmerge seeds its own (old version's) builddir once. An unmerge's `prerm`/`postrm` never rewrites a vdb env (the entry is on its way out). Portage does not give an unmerge hook `REPLACING_VERSIONS`.

## struct UnmergeReplacedSameSlotArgs
- Every already-installed same-slot version of the same cp is removed -- `dblink.unmerge()` (`pkg_prerm` -> delete its files -> `pkg_postrm`) then `dblink.delete()` (drop its vdb entry) -- once the new entry is a temporary (it is renamed into place only after this returns). Each `pkg_prerm`/`pkg_postrm` runs from that version's own vdb-stored `environment.bz2` + `<pf>.ebuild` (`ebuild_phases::run_phase_from_saved_env`, gated on its recorded `DEFINED_PHASES`); a version merged before portuale kept those files, or via a bare `ebuild <file> merge` of an older build, has neither and its rm hooks are skipped (documented degrade). Only the files the new version does not itself own are deleted (`also_keep = [new_pf]`, folded into Portage's `others_in_slot`). A different-slot version is left untouched.
- `scratch_dir` is where the extracted-from-vdb ebuild is laid out for its phase run (`<scratch_dir>/<cat>/<pn>/<old_pf>.ebuild`, so `compute_environment`'s own `<cat>/<pn>/<pf>.ebuild` path parse works). `unmerge_replaced_same_slot` returns every replaced `PF` (empty when there was nothing to replace) so the caller can fold it into its own `env_update` gate. Shared by `merge_after_install` (source `emerge <atom>` / `ebuild <file> merge`) and `merge_binpkg`.

## struct UnmergeOneInstalledArgs
- `is_replacement` is Portage's `unmerge_with_replacement` (see `preserve_libs_on_unmerge`): set by `unmerge_replaced_same_slot`, cleared by `pretend.rs`'s `emerge -C`. `scratch_dir` holds the ebuild extracted from the vdb for its phase run (`<scratch_dir>/<cat>/<pn>/<pf>.ebuild`, so `compute_environment`'s path parse works). Shared by `unmerge_replaced_same_slot` and `pretend.rs`'s `emerge -C`.

## struct RunVdbSavedEnvPhaseArgs
- The phase runs from the entry's own vdb-stored `environment.bz2` + `<pf>.ebuild`, copied into `scratch_dir` as `<cat>/<pn>/<pf>.ebuild` so `compute_environment`'s `<cat>/<pn>/<pf>.ebuild` path parse works (the vdb layout is `<cat>/<pf>/<pf>.ebuild`). Errors if the vdb entry carries no saved environment or ebuild (a package installed before portuale started keeping them).
