# crates/portuale/src/ebuild_merge/plib_merge.rs
Merge-side preserved-library handling: collision takeover, CONTENTS/NEEDED stripping, preserve-libs computation and registration.

## module
- Ports Portage's `dblink.merge()` post-copy step, `vardbapi.removeFromContents`, `PreservedLibsRegistry.register`/`.unregister`, `LinkageMap.rebuild()`'s preserved-libs branch, `dblink.treewalk()`'s pre-replace-loop preserve computation, `dblink._add_preserve_libs_to_contents` and the post-replace-loop registration.

## fn unregister_preserved_libs
- Ports `dblink.merge()`'s post-copy step (lib/portage/dbapi/vartree.py:5095-5159): any path this merge's `find_collisions` matched against a currently-registered preserved lib is now owned by the just-merged package, so the taken-over paths drop from the registry (removing the owning `cp:slot` entry once its path list empties) and from the previous owner's vdb `CONTENTS` (Portage's `removeFromContents`).
- Skipped when the previous owner *is* the just-merged package (Portage's `if cpv != self.mycpv`): re-merging the exact same cpv already replaces its own vdb entry wholesale, so there is nothing stale to strip.

## fn remove_from_contents
- Ports `vardbapi.removeFromContents` (vartree.py:1244-1310). A missing vdb entry for `cpv` (already unmerged some other way) is silently a no-op, matching Portage's tolerance of a stale registry entry.
- `NEEDED`-line stripping (Portage's "Also remove corresponding NEEDED lines, so that they do no corrupt LinkageMap data for preserve-libs", vartree.py:1279-1310) is ported too, closing a gap this module's old doc comment recorded as moot ("without the registration side above ever writing NEEDED data in the first place") -- moot no longer, since `NEEDED.ELF.2` generation and the full `LinkageMap`/preserve-libs computation are both ported (see `needed_elf.rs`).
- Portage's `removed` (whether any `CONTENTS` line was dropped) gates the whole thing, matching `if removed:` exactly: when this package's own `NEEDED.ELF.2` doesn't exist at all (Portage's `except OSError: ... new_needed` stays `None`), nothing is written, matching `if new_needed is not None:` in `writeContentsToContentsFile`.
- When it does exist, every entry whose own `filename` (already `ROOT`-relative, portuale's `CONTENTS`/`NEEDED.ELF.2` convention -- no `os.path.join(root, ...)` needed the way Portage's Python does, since both sides already agree on the same convention) still appears among the *surviving* `CONTENTS` paths is kept; every other entry (now pointing at a file this package no longer owns) is dropped -- stale linkage data that would otherwise corrupt a *later* `LinkageMap.rebuild()`'s preserve-libs decision for some *other* package's future unmerge.

## fn remove_from_contents_into
- The `retire` variant (feat#157 S4.2): collects the rewrites instead of committing each at once.
- W4 backend note: `read_entry_text` is today's `read_to_string(..) else return Ok(())` (missing, unreadable or non-UTF-8 all stop here); `replace_file` covers the two in-place `std::fs::write`s.

## fn register_preserved_libs
- Ports `PreservedLibsRegistry.register`/`.unregister` (lib/portage/util/_dyn_libs/PreservedLibsRegistry.py:142-176): Portage's `unregister(cpv, slot, counter) = register(cpv, slot, counter, [])`, so one function covers both calls, matching `register` exactly.
- Portage's `cps = cpv_getkey(cpv) + ":" + slot` (registry key `category/package:slot`, no version); `category`/`pn` arrive already split rather than re-derived from a version string the way `cpv_getkey` does, since every caller here already has them split (`ebuild_phases::Environment::split`).
- Empty `paths` (Portage's `unregister`): removes the `cps` entry only if it records the *same* `cpv` and `counter`, never blindly erasing a different package's entry sharing the slot key. Non-empty `paths`: unconditional overwrite; Portage's `_normalize_counter` is just a whitespace-trim, not integer parsing, so a plain trimmed-string comparison matches Portage exactly.

## fn linkage_owner_entries
- Shared input of the preserve-libs computations (`find_preserve_paths_for_merge`, `preserve_libs_on_unmerge`, and the post-unmerge prune `find_unused_preserved_libs`): `read_all_needed_entries` plus `LinkageMap.rebuild()`'s preserved-libs branch (`needed_elf::scan_preserved_lib_entries`).
- Scanned entries join their owner's already-present group when one exists (Portage groups everything by owner for the bundled-library runpath inference), else form a new one; vdb entries come first, so on a same-inode conflict the vdb data wins (Portage indexes the `scanelf` line first instead -- the two describe the same live file, so they agree in practice).
- Skipped entirely when there is nothing to scan (backlog #178's second bump is the first merge that ever has anything to scan).
- `exclude_cpvs` is `LinkageMap.rebuild()`'s `exclude_pkgs` (a package being unmerged contributes neither `NEEDED.ELF.2` lines nor registry orphans -- its data "would only serve to corrupt the `LinkageMap`"): the unmerged instance in replacement mode plus, on a database backend, the earlier-unmerged same-slot instances (#310); empty everywhere else.
- `replacement_preserved` is Portage's `preserve_paths` (the merge-side just-preserved set, owner -> paths, not yet registered at prune time so passed explicitly): scanned under the replacing cpv, where Portage indexes it with owner `None` (and skips the bundled-library runpath inference for `None`); grouping it under the replacing cpv is the closest this `String`-keyed input gets, and the owner only feeds that inference, never the keep/drop verdict.
- `replacement_needed` is `LinkageMap.rebuild()`'s `include_file` (backlog #224): the replacing package's `NEEDED.ELF.2` lines, fed explicitly because its vdb entry still sits in its `-MERGING-<pf>` temporary at prune time and enumeration (`read_all_needed_entries`, Portage's `cpv_all()`) skips it -- without the feed a preserved library whose only remaining consumer is the replacing package looks orphaned and is pruned. Portage indexes those lines with owner `None` (`LinkageMapELF.rebuild` processes the include file first); grouped here under the replacing cpv for the same `String`-keyed reason, with the same verdict-neutrality (the owner only feeds the same-owner bundled-library runpath inference, never the keep/drop verdict -- and these lines genuinely share one owner, so the inference is, if anything, more faithful). Empty on every path but the replace-loop prune and the merge-side preserve computation (`find_preserve_paths_for_merge`, backlog #229): standalone `emerge -C` has no replacing package, and the merge-end prune runs after the rename into place, when the new entry's own lines are already enumerated.
- Backlog #355 (S2): the `exclude_cpvs` removal applies to the registry map in `preserved_scan_input` *before* the `replacement_preserved` feed merges in. Portage's `LinkageMapELF.rebuild` (`LinkageMapELF.py:180`) adds `preserve_paths` unconditionally and applies `exclude_pkgs` only to registry entries; the old order (merge, then remove) dropped the just-preserved paths on a same-version reinstall, where the feed key and the excluded cpv are the same string, so a registry-preserved lib whose only consumer was the just-preserved lib was wrongly pruned. Oracle: Portage 3.0.82.2 S0 cell P1 (`libt355base.so.1` kept, both registry records held).

## fn preserved_scan_input
- Pure constructor for the registry-orphan scan input `linkage_owner_entries` scans (backlog #355, S2): clones `preserved`, drops `exclude_cpvs` keys, then merges `replacement_preserved` untouched. Split out so the exclusion order is unit-testable without ELF files; the only behaviour change vs the old inline order is the #355 case (feed key equal to an excluded cpv survives).

## fn owner_entries_with_preserved_orphans
- Thin forwarder used by the unmerge path: `linkage_owner_entries` with empty `exclude_cpvs` and empty replacement feeds.

## fn replacement_needed_entries
- Ports `dblink.treewalk()`'s `needed = os.path.join(inforoot, LinkageMap._needed_aux_key)` (backlogs #224/#229): the replacing package's `NEEDED.ELF.2` lines, read from its `-MERGING-<new_pf>` temporary vdb entry holding the build-info copy from `populate_vdb_tmp` (every build-info file is copied there, the `scanelf` QA step's `NEEDED.ELF.2` included). Portage's replace loop passes that path as `dblink.unmerge(needed=...)` into `_prune_plib_registry`, whose `_linkmap_rebuild(include_file=needed, ...)` indexes the lines explicitly -- because the entry is still `-MERGING-`, `cpv_all()` (portuale's `read_all_needed_entries`, which skips `-MERGING-` names) never yields them. Grouped under the replacing cpv (see `linkage_owner_entries` for why that owner choice is verdict-neutral).
- Empty when the temporary entry carries no `NEEDED.ELF.2` at all (a package with no ELF content -- Portage's `grabfile` on a missing file degrades the same way), so callers on paths with no replacing package simply never call this. Unreadable or non-UTF-8 likewise means "no lines".
- In-function fact: reads the pending entry's file (`-MERGING-<new_pf>/NEEDED.ELF.2`, one `open`).
- Portage `LinkageMap.rebuild(include_file=needed)` (backlog #229) is what indexes these lines.

## fn find_preserve_paths_for_merge
- Ports `dblink.treewalk`'s pre-replace-loop preserve-libs computation (the `_linkmap_rebuild(include_file=needed)` + `_find_libs_to_preserve()` block): rebuilds the system-wide `LinkageMap` and selects the installed same-slot instance's still-needed libraries (`_find_libs_to_preserve()`, `unmerge=False`).
- `new_image_paths` is the just-merged image's path set (parsed from `merge_tree`'s `CONTENTS` text) -- Portage's `self.isowner(f)` on the merging instance, whose `CONTENTS` is already written at this point, so a library the new version itself ships is never preserved.
- Old instance located via `installed_instance_pf`; a first-ever install (`None`) preserves nothing, as does an installed instance owning no files (Portage's `installed_instance.getcontents()` falsy skips the rebuild). Returns the preserve set plus the old instance's raw `CONTENTS` text for entry injection below.
- Must run after `merge_tree` (files on disk for `lstat`) and after `populate_vdb_tmp` (backlog #183: the new vdb entry *is* written by then, into its `-MERGING-<pf>` temporary -- the old doc said it was not). Enumeration still skips `-MERGING-` names, so the new package reaches the linkage map only through the explicit include feed (Portage's `include_file=needed`, backlog #229): without it a library owned by the replaced instance whose only consumer is the replacing package would not be preserved. Runs before `write_vdb_tmp_contents`.
- In-function facts: the registry's own preserved libs join the linkage input too (`_linkmap_rebuild` loads them via the orphan `scanelf` branch) -- without them a previously-preserved library the replaced instance no longer ships in its own `NEEDED.ELF.2` is invisible here, and a second consecutive soname bump would preserve nothing (backlog #178). The replacing package's `-MERGING-<new_pf>/NEEDED.ELF.2` lines join first, owner verdict-neutral (see `linkage_owner_entries`).

## fn inject_preserved_libs_into_contents
- Ports `dblink._add_preserve_libs_to_contents` (vartree.py:3775-3826): copies the preserved paths' entries from the replaced instance's `CONTENTS` into the merging package's (digest/mtime carried over verbatim -- the files are *not* reinstalled), printing Portage's `>>> needed    {obj|sym} <path>` per path in `sorted()` order.
- `new_image_paths` is the just-merged image's path set: a preserved path already there keeps its own fresh entry (Portage assigns into a dict, so re-adding is a no-op, never a duplicate line).
- Returns the `CONTENTS` lines to append plus the surviving preserve set: a path with no entry in the old `CONTENTS` cannot be preserved (Portage's `!!! File ... will not be preserved due to missing contents entry`) and is dropped, exactly like Portage dropping it from `preserve_paths`.

## fn register_merge_preserved_libs
- Ports `dblink.treewalk()`'s post-replace-loop registration (vartree.py:5266-5272): `register(self.mycpv, slot, counter, sorted(preserve_paths))` -- the one `cp:slot` record is **replaced** by the merging package's `(cpv, counter, paths)`, never merged with or re-attributed from the old entry (Portage's `register()` unconditional overwrite, PreservedLibsRegistry.py:165-169). Reads the counter back from the just-written new vdb entry (Portage's `counter_tick()` value, the same one `COUNTER` carries).
- No-op when nothing was preserved (Portage's `if preserve_paths:`), leaving the replace loop's unregistration of the old record as the final state. Keeps #167's serialisation and write-only-on-change rules intact via `register_preserved_libs` + `write_plib_registry`.

## fn merge_plib_registration
- The registry `register_merge_preserved_libs` stores, with the counter given: the freshly loaded (and pruned) registry plus the merging package's `register(...)`. Split out so a database backend can store it in the publishing transaction (feat#157 S4.1), reading the counter from the still-pending entry.

## fn preserve_libs_for_merge (#383)

`dblink._preserve_libs` for a merge (`vartree.py:2053`, `:4541-4545`, `:4560-4564`): `FEATURES` has `preserve-libs`, and no replaced same-slot instance restricts it. `treewalk` reads `PORTAGE_RESTRICT` of the replaced installed instances only (`setcpv(cur_cpv, mydb=vardb)`, so the vdb RESTRICT reduced with that instance's own recorded USE), never the new package's, and one restricted instance restricts all of them. The unmerge arm (`vartree.py:2622-2626`, `:3667`) uses the unmerged package's own vdb RESTRICT and the same FEATURES token; a replace-loop unmerge never selects libraries itself (the merge side did). Hermetic roots used to preserve unconditionally because the synthetic base carried no `preserve-libs`; since the embedded make.globals (#384) every root has the token, so the gate is live everywhere. `installed_restricts_preserve_libs` and `installed_same_slot_pfs` live in `ebuild_merge/preserve_gate.rs`.
