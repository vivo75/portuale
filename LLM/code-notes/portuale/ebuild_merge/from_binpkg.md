# crates/portuale/src/ebuild_merge/from_binpkg.rs
Merging a binary package.

## fn merge_binpkg
- Ports Portage's `_emerge/Binpkg` task, narrowed. `pkg_setup`/`pkg_preinst`/`pkg_postinst` run from the extracted `<pf>.ebuild` plus the `bunzip2`'d `environment.bz2` (see `ebuild_phases::run_phase_from_saved_env`), gated on `DEFINED_PHASES` (Portage's `_defined_phases`) so a binpkg defining neither -- the common case -- spawns no shell. A binpkg without a saved env (older, or built before portuale kept them) gets no hooks and no `instprep`: a documented degrade, not a fallback to re-sourcing the ebuild.
- `always` (run even when the ebuild does not define the phase): Portage's `postinst` `EbuildPhase` always starts (`pkg_postinst` defined or not) so its post-hook `PORTAGE_UPDATE_ENV` block can run.
- The `${T}/environment` comes from Portage's `_emerge/BinpkgEnvExtractor`, extracted once per package with every hook evolving that one file. Seed on the first hook that runs, `false` afterwards: a per-hook re-seed would wipe `pkg_setup`'s variable mutations before `pkg_preinst`/`pkg_postinst` (and the vdb env regeneration) see them (#30 finding `l3-binpkg-hook-env-reseed`).
- `pkg_pretend`: Portage's `Scheduler._run_pkg_pretend` runs it for every package in the merge list, binary included (only the `SRC_URI` fetch inside is guarded by `if not x.built`; the status line switches colour to `PKG_BINARY_MERGE` for the built case). It skips EAPI 0-3 (where `pkg_pretend` cannot exist, so the `phase_defined` gate already covers that) and anything not defining the phase. Portage runs this as an up-front pass over the whole list; portuale folds it into the per-package flow, exactly as the source path runs `pretend` inline before each build.
- `pkg_setup` order is Portage's `_emerge/Binpkg`: an `EbuildPhase` right after metadata extraction, before `unpack_contents`/the merge. `instprep` is Portage's `EbuildMerge` -> `dblink.treewalk()` first step, on the extracted image from the saved env (see `ebuild_phases::run_instprep`); `seeded` is false when no earlier hook ran (a binpkg defining neither `pkg_pretend` nor `pkg_setup`), so seed there for `__dyn_instprep` to run from the archive's env, else reuse the evolved env (see `run_instprep`'s `seed` doc).
- Calling-env filter is Portage's `config.environ()` `filter_calling_env` (`config.py:3275-3310`): once `${T}/environment` exists (every binary-merge hook has it, seeded from the archive), the calling environment narrows to `environ_whitelist` (bug #189417: a variable the ebuild unsets must not leak back in), so harness/portuale-only vars (`PORTAGE_RUNNING_ROOT`, `L1_SKIP_PORTAGE_UPGRADE`, synthesized `GNUMAKEFLAGS`) never reach the regenerated vdb env. Per-phase keys (`EMERGE_FROM`, `MERGE_TYPE`, `PORTAGE_UPDATE_ENV`, the `*_EXCLUDE` reads) are added separately by `run_phase_from_saved_env` and are unaffected. L3 finding: the L2 real-set control leg carries exactly those three vars without this filter.
- Metadata peek: Portage knows the cpv (and so `${PORTAGE_BUILDDIR}`) before extracting anything, so the image lands straight in `${PORTAGE_BUILDDIR}/image`, the exact `${D}` a `pkg_preinst`/`pkg_postinst` expects (`${PORTAGE_BUILDDIR}` = `${PORTAGE_TMPDIR}/portage/<cat>/<pf>`, which `compute_environment` derives from the extracted ebuild).
- `PF` -> `PN` is Portage's `catpkgsplit` (`portage_dep::parse_candidate`'s regex, the canonical PMS `<pkg>-<version>[-r<rev>]` split). The earlier hand-rolled `rsplit_once('-')` only recognised a version-final `PF` (`foo-1.2`) or cases where the split landed a digit last; it fell through to `package = pf` for `libgcrypt-1.12.3-r1` (last token `r1`), which made the extracted-ebuild dir `ebuild-src/<cat>/libgcrypt-1.12.3-r1/` and `split_package` reject the ebuild ("filename doesn't start with the parent directory's own name").
- `BINPKGMD5` is Portage's `_emerge/Binpkg._start_task` "Store the md5sum in the vdb": it prefers the `MD5` field from the package index, else `perform_md5(pkg_path)`. Neither xpak nor gpkg carries `BINPKGMD5` inside itself -- it is the digest of the whole binpkg file, recorded so a later `emerge -k` / index rebuild can tell a still-current instance from a rebuilt one.
- `REPLACING_VERSIONS` mirrors Portage's `self._installed_instance` (`vartree.py:4409-4418`) computed before `treewalk()`'s `pkg_preinst`, set from it right before that hook (`:4768-4771`).
- Collision/abort/preserve-libs/replace/publish/postinst/elog steps are Portage's `dblink.treewalk()`/`merge()` ordering, identical to `merge_after_install` (see that function's notes): collision check before `pkg_preinst` with `blockers_from_flat_deps` reading the already-USE-reduced `*DEPEND` build-info files (a binpkg has no ebuild/repo path for config/USE resolution); abort condition `collision_protect or (protect_owned and owners)`; `-MERGING-<pf>` temporary ordering; pre-replace preserve-libs into `CONTENTS`; takeover from the registry; merge-then-unmerge with `preserve_paths` travelling into `dblink.unmerge`; publish plus post-replace registration (`vartree.py:5266-5272`, one commit on a database backend, see `publish_merged_entry`).
- Postinst is Portage's `treewalk()` order with Portage's `_postinst_failure` semantics ("It's stupid to bail out here"): non-zero exit is logged, never fatal. `PORTAGE_UPDATE_ENV` points at the vdb entry's own `environment.bz2` (just written, verbatim from the binpkg); `phase-functions.sh` regenerates it from the live merge-time environment (Portage `vartree.py:5334`), so the vdb env carries the resolved merge-time `FEATURES` and drops stale build-host locals (see `ebuild_phases::run_phase_from_saved_env`). The live entry's own path is `InstalledDb::entry_path` (N9), or a scratch copy on a database backend (see `merge_after_install`).
- Prune is Portage's `treewalk()` orphan prune, identical to `merge_after_install` (no include feed since the new entry is renamed into place, backlog #224).
- Elog is Portage's `dblink.merge()` `_elog_process()`, before the builddir removal: the binary merge's hook output lives in this builddir's `${T}/logging`, and the unconditional `remove_dir_all` would take it with it (the same #42 ordering as `merge_after_install`). Empty (and silent) for a binpkg with no saved env.
