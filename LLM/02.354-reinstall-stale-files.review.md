## What was checked and holds

1. **The §0 diagnosis is correct** (proven by a discriminating source read on both sides).
   - Portage: `treewalk` sets `self.dbdir = self.dbtmpdir` (`vartree.py:5027`), clears the contents caches of `self` and of every other instance in the slot (`:5125-5130`), appends `self` to `others_in_slot` (`:5190`), then calls `dblnk.unmerge(others_in_slot=…)` for each replaced instance (`:5191-5210`) and `dblnk.delete()` (`:5216-5221`). Only after that does it reset `self.dbdir = self.dbpkgdir` and move the temporary into place (`:5234-5238`). Both `getcontents()` (`:2202-2210`, which reads `self.dbdir/CONTENTS`) and `isowner`/`_match_contents` (`:3495-3560`) on `self` therefore read the **new** list. `slot_matches` includes the live same cpv (`:4525-4529`), so a same-version reinstall unmerges the old copy with `others_in_slot == [self]`.
   - portuale: `unmerge_replaced_same_slot` passes `also_keep=[new_pf]` (`crates/portuale/src/ebuild_merge/after_install.rs:405,425`). `unmerge_pkgfiles_into` removes `pf` itself from the live list and then adds `also_keep` back (`crates/portuale/src/ebuild_unmerge.rs:442-459`). `remove_contents` asks `owns_path_pf` for each name (`ebuild_unmerge.rs:96-98`). `owns_path_pf` calls `read_contents_pf` (`crates/portuale/src/ebuild_merge/installed_instance.rs:155-164`), which reads the live entry first and the pending one only when the live one is missing (`:120-129`). On a same-`pf` reinstall the live entry is the old copy, so every old path counts as owned and nothing is deleted. The doc comment states this (`after_install.rs:355-357`).
2. **Ordering premise.** The new image is merged and its pending `CONTENTS` written before the replace loop, on both paths:
   - source merge: `merge_tree` → `write_vdb_tmp_contents` → `unmerge_replaced_same_slot` (`after_install.rs:161,198,216`);
   - binary merge: `write_vdb_tmp_contents` → `unmerge_replaced_same_slot` (`from_binpkg.rs:476,497`).

   `write_vdb_tmp_contents` always writes `CONTENTS`, even an empty one (`ebuild_merge/vdb_entry.rs:78-94`). So in the loop a pending `CONTENTS` always exists, and an empty one correctly means "owns nothing".
3. **`read_pending_file` exists and reads the right place on all three backends.**
   - `files`: `<cat>/-MERGING-<pf>/<name>` (`crates/portage-vdb/src/files.rs:543`, `files_write.rs:70-77`).
   - `redb`: the `PENDING` table (`redb_db.rs:969-974`).
   - `sqlite`: rows with `state='merging'` (`sqlite.rs:785-790`).

   `seal_entry` does not change the pending state, so the pending entry stays readable through the loop.
4. **Scoping the change to `also_keep` is right; a global switch to pending-first would be wrong.** The other callers of the `*_pf` readers need the **old** list on a same-`pf` reinstall, or run before any pending `CONTENTS` exists:
   - `protect.rs:298` (`protect_if_modified` compares against the previous instance);
   - `plib_merge.rs:270` (`old_owner_is_owner`, runs before `write_vdb_tmp_contents`);
   - `plib_unmerge.rs:92` (runs only when `!is_replacement`);
   - `collisions.rs:262` (blockers, a different `pf`).

   The plan's "everything else live-first as today" therefore keeps them correct.
5. **Rules for protected and modified files** (source read). In `_unmerge_pkgfiles` only the `unmerge-orphans` branch skips CONFIG_PROTECT (`vartree.py:3096-3112`). Without that branch, removal is gated on mtime alone (`:3114-3119`). `unmerge-orphans` is on by default (`make.globals:83`). portuale's `remove_contents` mirrors this (`ebuild_unmerge.rs:137-172`). The plan's cell (d) wording ("removes an unmodified protected file, keeps a modified one") agrees with the source, where "modified" means a different mtime.
6. **Database bookkeeping for the replacing `pf`.**
   - `already_unmerged` (`after_install.rs:534`, `ebuild_unmerge.rs:446`) cannot hide the replacing `pf`, because the `also_keep` loop (`ebuild_unmerge.rs:455-459`) adds it back after the filter.
   - In the replace loop, `retire` is `None` (`after_install.rs:586-588`) and on a database backend the delete is deferred (`:605`), so the old row stays live until `publish_merged_entry`. Pending-first resolution is exactly what makes `also_keep` mean the new copy there.
   - On `files`, the old same-`pf` directory is already deleted after its unmerge (`after_install.rs:605-606` → `delete_vdb_dir`), so later lookups already fall back to pending today.
7. **`replacement_needed`** is read from the pending entry (`plib_merge.rs:203-224`) and is appended **after** the `exclude_cpvs` filter (`plib_merge.rs:158-169`), so a same-`pf` reinstall keeps the new `NEEDED.ELF.2` lines. Portage does the same with `include_file` (`vartree.py:5160`, `LinkageMapELF.py:212-216`). Registry ordering also matches: the replace-loop unmerge unregisters the cpv (`plib_unmerge.rs` `register_preserved_libs(paths: &[])`; Portage `vartree.py:2441`), and the new registration happens after the loop in both (`publish_merged_entry`; Portage `:5245-5275`).

## D — defects

### D1 — the plan's S1 resolution replaces the live owner instead of adding to it (low, likely)

**Where.** Plan §2 S1: "resolves its ownership **pending-first** (`read_pending_file`, then live)". Code: `ebuild_unmerge.rs:455-459` merges `also_keep` into the live list by name.

**Portage.** `others_in_slot` holds two separate dblinks when another same-slot instance is unmerged before the old same-cpv copy: the old same-cpv dblink reading `dbpkgdir`, and `self` reading `dbtmpdir` (`vartree.py:4531-4555`, `:5190-5197`). Ownership is the union of the two lists.

**Divergence.**
- Inputs: two same-slot instances of one package are installed, `a-10` and `a-2` (a broken or slot-move state; Portage handles it at `:4525-4529`), and `a-2` is reinstalled. `category_entries` lists by name (`portage-vdb/src/files.rs:428-440`), so `a-10` can be unmerged first.
- Portage unmerges `a-10` with `others_in_slot = [old a-2, self]`: a path that the old `a-2` and `a-10` own, but the new `a-2` does not, is skipped as `replaced`. It is judged later, during the old `a-2` unmerge, against `a-2`'s own recorded mtime.
- In portuale, the name `a-2` is already in the live list (`ebuild_unmerge.rs:443-452`), so the dedupe at `:456` drops the `also_keep` copy. Under the plan the single name `a-2` would then resolve pending-only. The path counts as unowned while `a-10` is unmerged and is removed under `a-10`'s rules: unconditionally with `unmerge-orphans` (`:137-152`), or by `a-10`'s mtime.

**Impact.** The end state differs only when the two instances recorded different mtimes, or for CONFIG_PROTECT paths. The case is rare but reachable.

**Fix direction.** Keep two owner sources and do not dedupe across them: `others_in_slot` (live reads, as today) and `replacing` (pending-only reads). `is_owned = live.any(..) || replacing.any(..)`. The same applies to the `owned_node_type_pf` lookup (see G3).

### D2 — on a same-version reinstall the just-preserved libraries are dropped from the linkage map (medium, likely; pre-existing)

**Context.** Plan §3 bullet 4 asks to "confirm `replacement_preserved` and `replacement_needed` are unaffected when `pf` is equal". `replacement_needed` is unaffected (holds item 7). `replacement_preserved` **is** affected.

**Where.** `crates/portuale/src/ebuild_merge/plib_merge.rs:171-179`. `linkage_owner_entries` merges `replacement_preserved` (keyed by `"<cat>/<new_pf>"`, built at `after_install.rs:211-214` and `from_binpkg.rs:489-495`) into `scan_input`, then removes every `exclude_cpvs` key from it. The replace-loop prune passes `exclude_cpvs = ["<cat>/<pf>", …]` (`ebuild_unmerge.rs:523-531`). On a same-`pf` reinstall the two keys are the same string, so the just-preserved paths are removed again.

**Portage.** `LinkageMapELF.rebuild` adds `preserve_paths` unconditionally (`LinkageMapELF.py:235-237`) and applies `exclude_pkgs` only to registry entries (`:238-247`; the comment says preserved libs "are already represented via the preserve_paths parameter").

**Divergence.**
- Inputs: a same-version reinstall that drops a soname still used by another package (plan cell f), with `FEATURES=preserve-libs`.
- Portage's replace-loop `_prune_plib_registry` linkmap contains the just-preserved library's own `NEEDED` lines.
- portuale's does not. A preserved library from the registry (another cpv) whose only consumer is the just-preserved library is then judged unneeded and pruned (`plib_unmerge.rs` `find_unused_preserved_libs_in`).

**Impact.** This exists today, independent of S1. S0 cell (f) should be built to show it.

**Fix direction.** In `linkage_owner_entries`, apply the `exclude_cpvs` removal to the registry map (`preserved`) **before** merging `replacement_preserved`, mirroring `rebuild`'s split. Give it its own backlog number, or fold it into #354 as a named slice, since the plan already raised it.

### D3 — the reinstall now reaches `remove_contents` rules that Portage has and portuale lacks (medium, proven by source read; pre-existing, exposure widened by S1)

**Where.** `crates/portuale/src/ebuild_unmerge.rs:95-182`. The missing Portage behaviours:

| Portage behaviour | Portage source | portuale |
|---|---|---|
| `UNINSTALL_IGNORE` patterns (plus `PACKDEBUG_PATH` under `packdebug`) are never removed | `vartree.py:2925-2932`, `:3036-3040` | no reference to `UNINSTALL_IGNORE` anywhere in `crates/` except the phase-env allow-list (`portage-profile/src/phase_environ.rs:105`) |
| Libdir symlinks `/lib`, `/usr/lib`, `/usr/local/lib` are never removed (bug 423127) | `:3042-3045` | not modelled |
| A recorded `sym` that points to a directory is kept (`!empty`) unless every child is a regular file this package owns (bug 326685) | `:3130-3181` | `:155-172` removes it after the mtime check |
| A `dir` entry that is live a symlink takes the `sym` branch | `:3125` (`file_type == "dir" and islink`) | `:173-177` pushes it to `remove_dirs`, where `rmdir` fails and the symlink is left |

**Divergence.** Before S1 a same-version reinstall deleted nothing, so none of these could fire on a reinstall. After S1, every path a reinstalled image drops goes through them.
- Example input: the old image had `dosym ../share/x /usr/foo` and another package installed files through `/usr/foo/`; the new image of the same version drops the symlink.
- Portage keeps `/usr/foo` (`!empty`).
- portuale removes it, which breaks the other package's paths.

**Fix direction.** Either port the three guards into `remove_contents` as an S1 prerequisite (they also affect `emerge -C` and ordinary upgrades), or record them in the plan's cuts with a real backlog number and add an S0 cell that shows each one.

### D4 — whitespace in a `CONTENTS` path (low, likely; pre-existing, same functions S1 touches)

**Where.**
- `parse_contents` takes `split(' ')` field 1 as the path (`ebuild_unmerge.rs:32-46`).
- `owns_path_pf`, `owned_node_type_pf` and `owned_node_value_pf` compare the second whitespace token (`installed_instance.rs:159-163`, `:177-185`, `:199-215`).

**Portage.** `_contents_re` parses `obj (.+) (\S+) (\d+)` and `sym (.+) -> (.+) (\d+)` (`vartree.py:1951-1958`), so paths with spaces are supported.

**Divergence.**
- Inputs: an old entry with `obj /usr/share/p/a b.txt <md5> <mtime>` that the new image drops.
- Portage removes `/usr/share/p/a b.txt`.
- portuale looks at `/usr/share/p/a`: the real file is leaked, and if a file `/usr/share/p/a` exists it is checked, and under `unmerge-orphans` deleted, in its place.

**Fix direction.** Add a shared `CONTENTS` line parser with Portage's field rules. File it separately; it is not specific to #354, but S1 should not add another split-based reader.

- **Decide what an absent pending entry means for `also_keep`.** Is it a hard error (an invariant broken mid-merge) or the silent live fallback the plan proposes? The fallback errs on the safe side (no deletion), but it would hide a future regression; write the choice down.

### G4 — the merge-path gate cannot see this bug class

`l1-merge-from-binpkg.sh` with `L1_CONSUME_REINSTALL=1` snapshots only the paths in the **post-merge** `CONTENTS` of the merged packages (`../pmtest/differential-test-bed/layers/l1/consume.sh:224-242`). A file that one PM removes and the other keeps is in neither post-merge `CONTENTS`, so it is never compared. That is why the #348 S6 gate passed with 0 hard / 0 unexplained while this bug was live (`LLM/what-this-proves.md:19499`). Same-image glibc/bash reinstalls also drop nothing, so they never exercise the new deletion path.

**Closes with:**
- an S2 change to `consume.sh` that adds the replaced instances' **pre-merge** `CONTENTS` paths (saved before the merge) to `paths.txt`;
- a reinstall cell whose rebuilt image differs, e.g. built with a different `INSTALL_MASK` or `nodoc` from the installed one;
- making S2's "if the L1 harness can express it" unconditional;
- stating in S3 that the glibc/bash gate is the `L1_CONSUME_REINSTALL=1` cell (the live-system reinstall), now the riskiest shape because it deletes for real.
