## D — defects in the plan

**D1 — blocking for S0.5's classes and S2.1's `w772c`. Proven by reading. The plan's C2 premise is false in plan
mode.**
- What the plan says:
  - §0.1: "An atom without a slot aims at every slot of its package (`lib.rs:509-511`), so `dev-lang/python`
    (unslotted) gives an edge to each python slot".
  - §0.3 C2 builds on that: "python:3.14 and :3.15 are both host members".
- What the code does:
  - `lib.rs:509-511` is a doc comment on `World::reached`, and it is stale.
  - The code narrows a slotless atom in `process_atom` → `narrow_slotless` (`lib.rs:831-839`, `:861-889`).
  - `plan_world.rs:35` sets `opts.rebuilds = true`, which becomes `Memos::newest_slot` (`lib.rs:142`, `:593`,
    `:623`). Under that flag, `narrow_slotless` keeps **the best slot alone** (`keep` is empty →
    `retain(top)`). Only a check (`newest_slot = false`) keeps the installed visible slots.
- So in `--plan-world`, an unslotted atom gives exactly one edge.
- The two python members come from slotted atoms (`dev-lang/python:3.14`, …), which the eclass emits per target
  or as `||` arms. The host plan has python:3.15 `new` at #7 and python:3.14 `upgrade` at #26.
- The shape that does exist is the reverse of the plan's: an unslotted atom narrowed to the **newest** slot, which
  is not installed, while an **older** installed slot already meets the atom (candidates: binutils:2.47, gcc:16 on
  the bed).
- Fix direction:
  - Restate C2 as "the edge goes to the newest slot chosen by `narrow_slotless`, and an installed other slot meets
    the atom".
  - S0.5's census already asks "whether another slot of the atom's package is installed and matches", so it can
    stay.
  - `w772c` must have the newer slot visible and not installed and the older slot installed. "two slots, one
    installed" is ambiguous: with the newest slot installed, nothing is shown.
  - Correct the `reached` doc at `lib.rs:509-511` (comment-only, in whichever slice touches `lib.rs`).

**D2 — blocking for S2. Proven by reading. Each Q2/Q3 option contradicts S2.2's "must stay green unchanged".**
- `plan_world.rs:762-765` asserts the whole line: `plan-world: build cycle with no serial order:
  dev-libs/w749otherpkg:0 -> dev-libs/w749pkgnew:0 -> dev-libs/w749otherpkg:0 (no order satisfies it; disable a
  USE flag …; bootstrap with USE="-useboh" … temporary — will be rebuilt with the declared USE)`. Each option
  breaks it:
  - (b) rewords it;
  - Q3 changes ` -> ` to `members:`;
  - (c) "drops the SCC line". The bootstrap suffix is appended to that very line (`plan_world.rs:77-82`), so under
    (c) the bootstrap has nowhere to be announced.
  - (c) also leaves open whether `late_build_needs` runs on `ordered()` rows, before the boot row is inserted
    (then the w749 pair reports a late need that the boot row actually fixes), or after it.
- `docs/world-check-and-plan.md:123` quotes the same text.
- Fix direction:
  - S2.2 should say "the pinned pair keeps its rows and its boot row; the line's text changes only as Q2/Q3 decide,
    and the new text is pinned in the same test".
  - Under (c), say where the bootstrap announcement goes, and compute late needs on the final rows, boot row
    included.
  - Under (c), a genuine all-build cycle with nothing installed must still print at least one line (charter 2a).
    The `w772b` control covers that; say so explicitly.

**D3 — high. Likely (source reading plus a raw, unreduced scan; no census yet). "Met by an installed version"
(C1) is not harmless for slot-operator atoms whose provider the plan replaces later.**
- The literal checker accepts a build atom met by the installed version even when the plan upgrades that package
  afterwards. For `:=` / `:slot/sub=` atoms, building the consumer against the old provider and then replacing the
  provider with a new sub-slot leaves a stale binding (property 1).
- The literal checker cannot see this: the 02.764 review B2 calls such rows a "checker limitation".
- A raw scan of the build atoms in plan-entry text that point at a later-merged SCC member is unreduced (USE and
  `||` not evaluated), so these are only candidates. It finds `:=` edges going backwards:
  - bed: `dev-libs/elfutils#46 -DEPEND-> >=app-arch/libarchive-3.1.2:=` (#82, upgrade);
    `net-libs/nghttp2#42 -> >=dev-libs/libxml2-2.7.7:2=` (#81, upgrade); `sys-devel/gcc:16#48 -> dev-libs/libxml2:=`;
  - host: `app-crypt/tpm2-tss#14 -> sys-apps/util-linux:=` (#25, upgrade);
    `sys-libs/pam#6 -> >=sys-apps/systemd-254:=` (#24, reinstall).
- Under Q2(a), these edges become "preferred cuts", which would **create** such orders. Under (c) they are not
  reported. Either way property 1 can break silently.
- Fix direction:
  - In S0.5, record for every edge the atom's slot operator and whether the plan changes the target's sub-slot
    (old sub-slot from the VDB `SLOT`, new from the plan row).
  - Split C1 into C1a (met, with no binding or a binding that does not move) and C1b (met only by a version whose
    `:=` binding the plan then moves). Only C1a may be skipped or cut.
  - Add a `w772d` fixture: a 2-cycle with `:=` and a sub-slot bump; the line or a need must stay.

**D4 — medium. Proven by logic and reading. One STOP-0 condition is vacuous, and the class list misroutes a
likely case.**
- The vacuous STOP:
  - C4 is defined as "target merged earlier". A cycle cannot consist of C4 edges only: in a linear order, at least
    one edge of every cycle points at a later target.
  - So "any reported SCC keeps a build cycle made of C4 edges only on a plan where the literal checker is clean"
    can never fire.
  - When the checker is clean, every cycle has at least one later-target edge that the checker accepts, so that
    edge is C1, C2 or a modelling difference.
  - The condition the plan means is "a cycle whose later-target edges are all ones the checker would fail". That
    should be impossible on a clean plan. If it happens, the checker and `edge_kinds` disagree.
- The missing class:
  - `dependency_atoms` (`lib.rs:345-399`) resolves each `||` to **one** branch (`branch_preference`; plan mode
    prefers the newest-matching branch, `lib.rs:112-116`). The checker's `_satisfied` (`health_checker.py:413-420`)
    accepts **any** satisfied arm.
  - An edge to the chosen arm (e.g. python:3.15, `new` on the host) whose `||` an installed other arm meets is not
    C1 (the chosen atom is not met), not C2 (it is not a slotless atom), and not an over-approximation of
    `edge_kinds`. Yet C3 "→ STOP, the fix is in `edge_kinds`" would catch it.
  - Its fix, if any, lies in the arm choice, not in `edge_kinds`.
- Fix direction: replace the C4 STOP with "a later-target edge that the checker would fail on this plan (checker
  and `edge_kinds` disagree): STOP". Add **C5: an `||` arm chosen by `branch_preference` while another arm is
  installed and meets the group**. The census needs the `||` group the atom came from: carry the unreduced text,
  or mark `||`-derived atoms.
