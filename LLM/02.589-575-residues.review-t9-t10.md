## Issues

### Critical (must fix)

#### 1. P1 has one `||` view, but Portage uses two, and the R4 keeper needs the other one

**Plan:** `:904-908`, `:916`, `:924`, `:956-959`; `t8/design.md` "The port", P1.
**Status:** **proven** for T1 (discriminating source read); **likely** for R4.

Portage chooses an installed consumer's `||` against two different tree sets:
- **Complete mode** uses `_graph_trees` (D:8705 → D:6009-6016). There
  `porttree` = `vartree` = `graph_db` = the package-tracker wrapper (D:764-768).
  "Available" means a graph node, or an installed package that is not replaced
  (PT:230-252, `_replaced_by` PT:137-143). "Installed" in the bins also means
  "present after the merge", because DC:603-616 and DC:713-736 call `vardb`,
  which is the same wrapper here.
- **Normal walk** uses `_filtered_trees`. `porttree` is the composite tree and
  binary db (D:775-777), and `vartree` is the real vdb (D:798-800). So a tree
  ebuild is available, and a replaced installed package still counts as
  installed.

The plan defines one view (`:924`): merge-bound entries, plus installed
packages no same-slot merge-bound entry replaces. That is the complete-mode
view. It then makes the `view` field optional, "only if S0 shows it is needed"
(`:916`). Both halves are wrong:
- **T1 needs the field.** `disjunction_preference` today probes availability
  with `atom_currently_satisfiable` against the tree (`or_preference.rs:236`)
  and "installed" with the real vdb (`atom_cp_installed`, `:217`). On T1,
  `=p569prov-5.42*` is available (the 5.42 ebuild exists) and installed. It
  goes to the preferred bin and is chosen, which is the arm Portage does *not*
  choose. With the function unchanged, T1 stays red.
- **R4 needs the other view.** In `r4-orchoice` the consumer is walked in the
  normal walk (`-uD @world`; `captures/r4-orchoice.trim.txt` file lines 13-15,
  raw dump :112-:115). `dev-libs/mllabltk:=` is available there from the tree.
  Under the plan's view, if mllabltk is not yet merge-bound, both arms are
  unavailable. `<dev-libs/mlocaml-4.02` then lands in `other_installed_any_slot`
  (mlocaml-4.02.1 is in the wrapper, DC:733-734), ahead of mllabltk in `other`,
  and wins. That is the opposite of Portage, and the #35 R4 keeper
  (`test_or_choice_avoids_downgrade_into_the_graphed_update`) is at risk.
- **The R4 RED cites a guard the defined view never reaches.**
  `consumer_or_downgrade_guard_prefers_the_graphed_update` (`:956-959`) cites
  DC:531-541. Under the plan's view, `<mlocaml-4.02` has no `avail_pkg`, so the
  loop breaks at DC:475-478 before the guard runs.

Also, the plan says the downgrade guards apply "in the normal walk" (`:907`).
`_graph_trees` also carries `graph_db`, `graph` and `downgrade_probe`
(D:767-770), so the guards apply in both modes.

**Fix to the plan:**
- Make the view a required input:
  `InstalledConsumerOrSelectionArgs { view: OrView::{Normal, PostMerge}, … }`.
  - `PostMerge`: availability = merge-bound entries + `AlreadyInstalled` nodes
    + vdb instances not replaced by same-slot *or same-cpv* merge-bound entries.
    The `vardb` probes of the bins and the unavailable-bin sort use the same set.
  - `Normal`: today's `disjunction_preference` behaviour, byte-identical.
- Add a Task 9 S0 trace that settles oracle §E: when is an installed consumer's
  `||` popped in the normal walk, and when in `_complete_graph`? The candidate
  rule is the parent's depth against `requested_depth` (D:3438-3453;
  `--deep` in R4, no `--deep` in T1). The rule must be written into the task
  with its Portage line before code.
- Split the R4 RED into its normal-walk form (mllabltk tree-available, guard
  cited) and assert that the T1 RED uses `PostMerge`.

#### 2. T2 cannot reach its Portage outcome through P1: the built slot-operator atom never forms a pin by itself

**Plan:** `:962-963` (T2 RED), `t8/targets.md` row T2.
**Status:** **likely** (source read; not run).

After P1, T2's consumer selects `=p569prov-5.40*`, and `=5.42*` is
deselected. The only remaining atom the 5.44 merge contradicts is the built
`dev-libs/p569prov:0/5.42=`. portuale strips a built slot-operator atom to its
bare `cat/pkg` before testing it (`reverse_dep_constraint_atom`,
`rev_dep.rs:35-41`). The bare atom matches 5.44, so `failing` is empty and no
pin forms (`rev_dep.rs:683-699`). The built text only rides in `built_seen` /
`built_render` (`rev_dep.rs:657-670`, `:449-457`). It gets attached to the
`=5.40*` pin, and `residual_conflict_for_pin` discards that pin because it
matches no installed version (`slot_conflict.rs`, "None (already broken before
this run) means no instance").

So no residual record forms, nothing heals, and portuale merges
`U p569prov-5.44` + `N p569pull-2`. Portage heals to `N p569pull-1` with 4/20,
and its only conflict parent is the built atom
(`captures/portage-c-swap-slotop.nodebug.txt`). In Portage the built atom is a
parent atom on the installed node. It fails to match 5.44 by sub-slot
(D:2189-2196), `_slot_conflict_backtrack_abi` (D:2205-2213, D:2296-2329) tries
a rebuild of the parent first, and `_slot_confict_backtrack` follows.

Result: the Task 9 RED `t2_swap_slotop_skip_block_has_only_the_built_atom`
stays red after the fix, and a target cell moves away from Portage (a stop
condition).

**Fix to the plan:** either
- (a) take T2 out of Task 9's targets, record its expected portuale outcome
  after P1 (`U`+`N`, a known divergence), and file a §R residue: "a built
  `:S/SS=` atom of a reachable installed consumer is a conflict parent when the
  ABI rebuild probe fails", with its own S0 trace of
  `_slot_conflict_backtrack_abi` on T2; or
- (b) add that mechanism to Task 10b, with the trace, and move the T2 RED
  there.

Either way, T2 must not be a Task 9 RED.

#### 3. P2 cannot reuse `slot_conflict_mask_choices` "as it is": the consumer pins never become conflict atoms

**Plan:** `:1013-1016`; `t8/design.md` P2.
**Status:** **proven** (discriminating source read against the trace).

`slot_conflict_mask_choices` builds its conflict atoms (`all_parents`) only
from `pass.slot_pullers` (`backtrack_params.rs:66-78`). It does not read
`sc.instances[*].parents`. A P2 record puts the consumer pins only on the
installed instance's `parents`, as `build_residual_slot_conflicts` does
(`slot_conflict.rs:563-600`). Portage's `all_parents` is `slot_parent_atoms`,
the union over every slot node, and it includes the installed consumer's atoms
(D:2160-2165, D:2238-2245). The trace shows them:
`p563-heal.trim.txt:58`, "parents: ((p563con-1 installed, '=…5.42*'), …,
(p563pull-2, '=…5.44*'))".

With the function unchanged on the p563 shape:
- masking 5.44 has 0 conflict atoms (the puller's `=5.44*` matches it);
- masking the installed 5.42 has 1.

After the ascending sort (`:163-165`), the DFS pops the installed-5.42 choice
first. Portage masks `p563prov-5.44` first (`p563-heal.trim.txt:56`). The node
parents (`MaskReason::SlotConflict.parents`) would also lack the consumer
pins, and the skip-block renderer prints those parents.

**Fix to the plan:** state that P2 widens the conflict-atom input. Either
`SlotConflictMaskChoicesArgs` gains the record's installed-side parents, or the
function reads `sc.instances[*].parents` in addition to `slot_pullers`, with
duplicates removed. Add a unit RED on the p563 shape: "first choice masks 5.44,
opposed by the three consumer atoms, in Portage's order"
(`p563-heal.trim.txt:54-58`). Also note that a puller-only change to
`slot_pullers` would leak into `has_merge_bound_puller` and the conflict
renderer.

must first be limited to the pins of the current pass, with a RED that
replays an R4-like two-pass sequence.

#### 6. P2's scan trigger is circular, and its order against enforced pins is not given

**Plan:** `:1005-1008`; `t8/design.md` P2 "Open point". **Status:** **proven**
(the trigger); **likely** (the order).

- "Widened to run when `dropped_pins` is non-empty" cannot be checked before
  the scan runs. `dropped_pins` *is* the scan's output, and the early block
  runs only when `pass.slot_conflicts` is non-empty (`mod.rs:283`). Its comment
  (`:277-281`) promises one scan per settling pass. A scan on every pass doubles
  that cost unless `step_reverse_dep_pins` (`:464-479`) reuses the result.
- Today `step_reverse_dep_pins` restarts on newly enforced pins first, through
  `RevDep` (budget-free), and masks over dropped pins only when `!added`
  (`:573-585`). A P2 record formed at the top of the chain and fed back at
  `:325` jumps ahead of that enforced-pin restart. Portage first runs
  `_solve_non_slot_operator_slot_conflicts` (D:2131) and only then
  `_process_slot_conflict` on what is left (D:2143-2144). The plan says
  nothing about this order, and it affects the counts the T3, k3 and igw
  targets assert.

**Fix to the plan:** run the reverse-dependency scan once per pass at the top
of `collect_feedback_inner` (when `upgrading` or `use_breaks` is non-empty) and
pass its `(enforced, dropped)` to `step_reverse_dep_pins` instead of scanning
again. State that the P2 record is formed only when this pass adds no new
enforced pin (the current `!added` rule), citing D:2131 → D:2143.

#### 7. The P2 record goes through four other steps whose behaviour the plan does not state
