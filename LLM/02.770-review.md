  The same holds for `-D dev-libs/p569pull` on the shared tree.

**Impact on the plan:**

- S2.3 requires output "equal to the default".
- S2.3 sends "any other difference" to STOP-1.

After a correct fix A, all three still fail on the provider row.

**Fix direction (proposal):**
- Add a Q (owner, or `[default sicuro]` if the owner agrees). Either (a) scope #770 to the consumer:
  - the `rR` row;
  - the "causes rebuilds for:" pair;
  - the `--json` reinstall set (which is what `_PINS_766` compares).

### D2. The #598 shape fails on pubgrub in a different way, which fix A cannot heal. Severity: high for the plan. **Proven** (behaviour); cause **likely** (source).

**Divergence** (shared fixture tree, `-pv -uD --getbinpkg=n dev-libs/p569pull`, rc 0 on both solvers):
- **Default:** `r U` p569prov-5.44, `N` p569core-1.0, `rR` p569virt-1, `N` p569pull-2, and the pair. This is
  `_598_expect`.
- **pubgrub:** a single row, `[ebuild  N     ] dev-libs/p569pull-1`, and then:

  ```
  NOTE: One or more updates were not merged because an installed package cannot follow them:
  dev-libs/p569prov:0 for <ROOT>/
    installed: 5.42
    not merged: 5.44 (dev-libs/p569virt-1 needs =dev-libs/p569prov-5.38*)
    No visible version of dev-libs/p569virt accepts dev-libs/p569prov-5.44.
  ```

- The same happens on root `pull` with `-pv -u @world` (no `--deep`): pubgrub holds back to `p569pull-1` with the
  same NOTE, while the default rebuilds.
- `-uD dev-libs/p589bpull` behaves the same way.

**The NOTE is false:**
- `p569virt-1`'s tree `RDEPEND` (md5-cache) is
  `|| ( =…5.42* =…5.40* =…5.38* ~dev-libs/p569core-1.0 ) dev-libs/p569prov:=`. It accepts 5.44 through the `~p569core`
  arm, which is exactly what the default solver does.
- "needs =…5.38*" names one arm of a four-arm `||`.

This is a pubgrub property-5 defect (a misleading message) and a property-3 defect (held back for no reason).

**Likely cause:**
- Without world seeds, `holder_fix` seeds from `merge_bound_dep_atoms(entries)`, which names `dev-libs/p569virt`
  (`solver_bridge.rs` near `:5690`).
- Its route test then rejects the `||` because no arm on the provider's cp accepts 5.44. The alternative
  non-provider arm is ignored.

**Impact on the plan:**
- §0 item 4 predicts "the #598 shape may already heal on pubgrub". That is false, and false in the opposite
  direction.
- H5 frames `holder_fix` as a missing healer. On these shapes it is the cause of a wrong plan.
- Q1 option B (widen `holder_fix`'s seeds to the plan's own atoms when world seeds exist) would very likely push
  root `pull` into the same held-back plan and false NOTE.
- S1.2 adds the #598-shape pubgrub parameter and a CASES row "only if S0 shows pubgrub misses it there too". It does
  miss it, so the plan would add a red test that fix A cannot turn green.
- S1.3's Rust test is "modelled on `pg765_…`", which builds the request with `fixture_request(&[atom])` and no
  `complete_seed_atoms`. A root-`pull` model built that way takes the `merge_bound_dep_atoms` seed path and most
  likely reproduces this withhold, not the missing rebuild (likely).

**Fix direction (proposal):**
- Delete option B.
- Restrict the pubgrub red to root `pull` with `@world` (both `-uDN` and `-uD`).
- Make S1.3 set `req.config.complete_seed_atoms` to the world atoms, so the test isolates the bridge scan.
- Add the #598 shape and `-u @world` to S0 as "recorded, different cause". Give this false refusal its own backlog
  number at close-out. It is next to 02.768's placeholder N1 (`holder_has_route` "visible"), but it is a different
  hole: an alternative arm on another cp.
