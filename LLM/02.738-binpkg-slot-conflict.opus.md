**The duplicate is real, not a rendering artifact.** `portuale-fail.txt:366-374` shows both ffmpeg instances "scheduled for merge" with distinct parents (9.0.2 from `dragon` + 8 more; 8.1.3 from `opencv` + `pipewire`). Merge-bound pushes always set `slot: Some(...)` (`resolve/pass/graph_entry.rs`), and `S=true` implies the outcome is `New` (L199-200), so the 8.1.3 entry is a `New` entry coexisting with the 9.0.2 `Upgrade`; `resolved_slots` (`pass_state.rs:94-100`) guards only walk-resolved `New`/`Upgrade`, while `Reinstall`/`AlreadyInstalled` use `other_outcomes` keyed `(cp, Option<slot>)` (L106-118) and post-walk `extend`s in `assemble_result` (`assemble.rs:103-112`) bypass both. The `rS` pair is therefore *possible mechanically* (`r` is cp-level, `S` entry-level), so §2.2 must assert the invariant, not assume it.

**Which probe reads recorded pins, and which is gated off.** `slot_operator_slot_change_probe` (`force_scan.rs:256-404`) does **not** read a binary's recorded `:=`; it is a slot-moved-without-revbump probe over ebuilds (L288-335) plus a mask for a merge-bound *binary* whose **own** slot moved (L345-400). The mechanism that reads a consumer's recorded pin is `built_parent_update_probe` / `child_has_slot_update`, and on this shape it returns false at **`built_parent_update_probe.rs:219-221`**: `if graph_child.is_some() && !from_graph_child { return false; }`. `dev-libs/openssl-4.1.0` **is** merge-bound in the failing plan, so every binary consumer's probe is skipped. The third path (`slot_operator_unsatisfied_probe_full`) needs a `NoVisibleCandidate` entry (`unsat_probe.rs:116`, `slot_operator_probe.rs:18`) that this plan does not have. So the question is not "which new rule to add" but "why is the pin not honoured when the provider is merge-bound"; S0 confirms the arming condition.

Two message defects stand on their own: the `openssl:0` conflict block renders **no parent atom** (`fail.txt:360-363`: `pulled in by`, then a blank line), and the merge list calls `ffmpeg-9.0.2` a binary (`fail.txt:128`) while the conflict block calls it an **ebuild** (`fail.txt:366`). ## 2. The rule

1. **A binary package must not be the reason a plan is inconsistent.** When a binary consumer's recorded `:=` forbids the provider version the plan chooses (or when the plan contains two entries for one slot), the plan must either rebuild that consumer from its ebuild (property 3) or decline the provider move as a skipped update naming the consumer and the atom (properties 1 and 5). The fix site is the gate that currently suppresses the rebuild (`built_parent_update_probe.rs:219-221`), not a new masking mechanism.
2. **One slot, one entry — as an invariant, not an assumption.** *At most one merge-bound entry per `(cat, pkg, slot, resolving root)` in the final entry vector.* The plan must find the second push path in S0 (walk `resolved_slots` vs `other_outcomes` vs a post-walk `extend` vs a different root) and guard there; it must not assume a `cat/pkg:slot` key exists.
3. **A conflict names its cause.** Every `slot_conflicts` entry has at least one parent atom naming the atom and the package that pulls it (property 5), and a package's `binary`/`ebuild` label must be the same in the merge list and in the conflict block.

Grounding: charter properties 1, 3, 5; the #697 precedent. Portage's skip block is the shape of the outcome, not the decision procedure.
