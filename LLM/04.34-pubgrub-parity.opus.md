**Goal:** for every L0 corpus target and every mode in §0.3, `portuale emerge
--solver=pubgrub` plans the same `cat/pkg-version` set with the same
`N`/`S`/`U`/`D`/`R` action letters as Portage's `emerge`, or the difference
is allowlisted with a backlog number.

**Architecture:** the over-merge is not the "reachability closure fed as the
graph" the backlog guessed. It comes from four things the bridge tells the
engine (§0.2): every slot of a bare target is a root target; every
installed package is expanded as if `--deep` were on, with the current
config's USE; installed packages' build deps never enter; and no
reinstall (`R`) can be displayed. The fixes live in `solver_bridge.rs`: the
target list, a kept/rebuild set computed **before** the provider is
constructed, the facts `versions_for`/`desired_use` give for installed
packages, the engine switches, and `graph_result_from_order`'s
`AlreadyInstalled`/`Reinstall` mapping. Acceptance is a new L0 bed mode
that runs Portage against `--solver=pubgrub` and counts only set/action
findings.

**Tech Stack:** Rust (`crates/portage-repo/src/solver_bridge.rs`), external
crates `portage-atom-pubgrub` 0.8.0 / `portage-solver` 0.3.0 (source under
`~/.cargo/registry/src/index.crates.io-*/`), pmtest L0 bed
(`differential-test-bed/layers/l0/in-container.sh`,
`compare/resolve-compare.py`).

**Spec:** backlog #34, `scope-backlog.md` §J, and §0 below.

### 0.2 Diagnosis (S0's trace confirms each)

- **D-target-all-slots.** A target without `:slot` is pushed as a root target in **every** slot (`solver_bridge.rs:883-893`; `packages_for_cpn` returns every slotted node, crate `provider/mod.rs:905-916`). Portage selects the slot of the highest visible match, and only under `--update` adds *installed* slots older than it (`_greedy_slots`, `depgraph.py:5385-5427`, `:5896-5930`); it never adds non-installed sibling slots. Multi-slot targets (gcc, llvm, python, rust) all hit this.
- **D-installed-expanded.** For an installed package at its installed version with policy ≠ `Rebuild`, the crate reports `RDEPEND + PDEPEND + IDEPEND` always (`provider/solve.rs:311-341`) — the engine walks installed packages as if `--deep` were on. Portage without `--deep` puts an installed node's deps into `_ignored_deps` (`depgraph.py:3815-3824` with `_too_deep` `:7359-7375`); complete mode only selects among graph/installed packages, never adds new ones.
- **D-installed-config-USE.** Those deps were converted once, at construction (`provider/mod.rs:443-503`), with `repo.desired_use(cpv)`, which the bridge answers with the current config (`solver_bridge.rs:216-233`, `:810-822`). Portage with `--deep` expands an installed node with `_pkg_use_enabled(pkg)` = the vdb USE (e.g. `dev-libs/libxml2` installed `-icu`, profile now `icu` → Portage `-D` keeps it, `-DN` shows `R libxml2 USE="icu*"` + `N icu`).
- **D-installed-bdeps.** Kept installed packages never contribute DEPEND/BDEPEND (`solve.rs:311-341`), and `set_with_bdeps` is read only on the cross-host branch (`solve.rs:378`; its doc at `provider/mod.rs:884-888` contradicts `solve.rs:382-387`). Portage with the default `--with-bdeps` auto (`create_depgraph_params.py:97-103`) traverses a built/installed package's DEPEND/BDEPEND as optional priority under `--deep` (`depgraph.py:4196-4206`, `:4274-4289`; `_add_dep` skips an optional dep only when nothing can be selected, `:3395-3398`). Affects `-pvuD`, `-pvuDN`.
- **D-closure.** `LazyRepo::build` queues `seeds(expand) ++ installed(shallow)` and drains with `Vec::pop` (`solver_bridge.rs:121-128`): installed cps enter `closure` unexpanded before any seed, so an installed **target** is never expanded and its deps stay outside `closure` → outside the crate's slot map (`all_packages()` `:750-752` → `provider/mod.rs:365-387`) → an unslotted dep on them converts to `PortagePackage::unslotted` (`convert.rs:417-426`) and never matches the slotted versions (`solver_bridge.rs:767-771`). Likely; S0's trace (`pg-closure`) confirms.
- **D-no-R.** `graph_result_from_order` maps every same-slot same-version pick to `AlreadyInstalled` (`solver_bridge.rs:358-365`), which the display hides (`crates/portuale/src/pretend/display/entry_line.rs:421-425`); it takes no policy input. So no `R` row can appear: named arguments (`-pv`), `-pve`, `-pvuDN` USE drift. Portage reinstalls a non-selective named argument; `req.selective` already folds `--update`/`--noreplace`/`-N`/`-U`/`--changed-*`/`--newrepo` (`crates/portuale/src/pretend/resolve_plan.rs:106-111`), but is **not** cleared by `--emptytree` at the request level (the walk clears it, `resolve/pretend.rs:407-408`).
- **D-installed-only.** Installed versions no longer in the repo are never offered by `versions_for` (`load_versions` lists repo candidates, `solver_bridge.rs:154-208`); the crate inserts an empty-deps stub (`provider/mod.rs:742-753`), so under `--deep` they stay leaves, where Portage expands them from the vdb with moves applied (`resolve/installed_meta.rs:126-130`).
- **Switches.** The bridge sets none of `set_prefer_update`, `set_selective_no_update`, `set_rebuild_tree`, `set_prefer_newest_slot`, `set_nodeps` (fields `provider/mod.rs:258-305`, setters `:815-889`). The crate's Favor keeps an installed version only if `!prefer_update && (selective_no_update || !root_targets.contains(pkg))` (`solve.rs:89-110`): under `-u` root targets are updated with `prefer_update` off, matching Portage's `-u` without `-D` (`dep.want_update = (arg_atoms or update) and not _too_deep(depth)`, `depgraph.py:3803-3807`). Muse C2 is therefore invalid (review §2).
- `--deep=N` (`Deep::Bounded`) is not a corpus mode: this plan treats it as `Unlimited` in the bridge and records the cut (Portage expands an installed node at depth d only if d+1 ≤ n; portuale's own rule is `Deep::recurses_at`, `resolve/queue.rs:20-31`).
