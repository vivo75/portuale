> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** done 2026-10-30 (Tasks 0-7, slices #627+#628+#629, branch `batch/2026-10-29-626-hyperfine`)

**Goal:** Run `src_unpack`, `src_prepare`, `src_configure`, `src_compile` and `src_test` as `portage:portage` when the `userpriv` gate holds, so foreign-owned tarballs unpack instead of dying EINVAL — closing #626.

**Architecture:** A pure gate predicate (`sandbox.rs`) decides demotion per phase; the bash spawn (`commands.rs`) applies `setgroups→setgid→setuid` in the child via `pre_exec` and drops the `unshare` wrapper when demoted (a demoted `--map-root-user` ns would re-root the child and reintroduce EINVAL); post-phase perms mirror `_post_phase_userpriv_perms`. Each task is independently testable; no task moves any merge list or pretend output.

**Tech Stack:** Rust 2024 (`crates/portuale`, `crates/portage-repo`), Portage 3.0.83 (`3rdparty/portage`, host), pmtest contract suite (`../pmtest`).

**Spec:** `LLM/backlog-tasks.md` #627, argued from `LLM/evidence/2026-10-29-626/` (Portage `250:250` work tree vs portuale root failure, `unshare --map-root-user tar` repro) and Portage `lib/portage/package/ebuild/doebuild.py:56,260,1780-1795,1817-1870,2200-2246,2485-2498`, `lib/portage/process.py:1061,1267-1272`, `lib/portage/data.py:92-106,169`, `lib/portage/util/__init__.py:1266-1340` (`apply_recursive_permissions`).

## Global Constraints

- **Expected behaviour comes from Portage, never a second portuale run.** Cite `3rdparty/portage` `file:line` in every code note.
- **Demote exactly Portage's phases:** `unpack`, `prepare`, `configure`, `compile`, `test` get `droppriv` (`doebuild.py:1817-1861`); `install` (`:1862-1870`, `droppriv: 0`), `setup` (`:1813`, `droppriv: 0`) and every other phase never demote.
- **Demote exactly under Portage's gate** (`:1795`, `:2200-2203`): `userpriv ∈ FEATURES`, `userpriv ∉ RESTRICT`, `nouserpriv ∉ RESTRICT`, `euid == 0` (secpass 2 ⟺ uid 0, `data.py:92-106`). No other condition demotes.
- **`fakeroot` stays out** (Part 3 non-goal stands; #627 lifts `userpriv` for phases only). `PORTAGE_BUILD_USER/GROUP` stay `mysettings`-internal — Portage's saved phase env carries neither (0 hits in `phase-env-portage.txt`), so they are not exported.
- **Never demote inside `--map-root-user`.** A single-id ns maps one uid only; a demoted child is unmapped (`setuid` fails) or, mapped as root, reintroduces the #626 EINVAL. Demotion and `unshare` are mutually exclusive.
- **Same branch pair, no rebase** (`batch/2026-10-29-626-hyperfine`, per `AGENTS.md`; pmtest commits first). `ebuild_phases/` is not in `pair_check.sh` `MERGE_PATH`, so no glibc/bash gate file is required — but Task 4's hyperfine source-merge acceptance covers a real source build anyway.
- **Corpus untouched** (no pretend-output change). New backlog numbers start at **628**.
- **Root-gated tests run via `sudo <test-binary> <filter>`** (image rebuild is an owner step); every root test skips cleanly when `euid != 0` or the `portage` user is unresolvable.

## Review Focus

- A demoted phase writing outside the builddir (e.g. a hardcoded `/tmp` path in an ebuild) now fails `EACCES` where root succeeded — Portage behaves the same (DAC as `portage` user); the e2e test pins the builddir-contained shape only, and any new failure gets its Portage-vs-portuale control run before any code change.
- Demoted phases lose the net/ipc/pid namespaces (cut, filed as residue in Task 5): with `network-sandbox` in FEATURES a demoted `src_unpack` keeps network access Portage would deny; libsandbox still applies when `usersandbox` is set, and DAC confinement as `portage:portage` always applies.
- `homedir` must exist and be portage-owned before a demoted phase starts (cargo/rustc write `$HOME`); Task 3 creates it.
- Log pumps and tee threads stay in the root parent — only the phase child demotes, so no log ownership changes.
- `SANDBOX_ACTIVE` in the parent env keeps the existing free path; the demotion decision never overrides an already-sandboxed ancestor.

- [ ] **Step 3: Implement the predicate and identity resolution**

```rust
/// Portage `_spawn_actionmap` droppriv gate + per-phase actionmap table.
// Portage: doebuild.py, _spawn_actionmap (:1780-1795) and actionmap (:1813-1870)
pub(crate) fn phase_droppriv(phase: &str, features: &str, restrict: &str, is_root: bool) -> bool {
    matches!(phase, "unpack" | "prepare" | "configure" | "compile" | "test")
        && feature_token_present(features, "userpriv")
        && !flat_field_has_token(restrict, &["userpriv", "nouserpriv"])
        && is_root
}
```
