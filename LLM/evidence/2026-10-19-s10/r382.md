## Decisions made

1. **One call does prerm + files + postrm + vdb delete** (subsuming the
   top prerm block too, not just the removal loop). Grounding: Portage
   `treewalk` merges the new files first, then runs the old
   `dblink.unmerge()` incl. prerm (`3rdparty/portage/.../vartree.py`
   docstring + `:5203-5225`). So the prerm-before-copy order is gone as
   part of the deleted shell copy; this also matches Portage better.
   Consequence: `MERGE_PRERM=`/`MERGE_POSTRM=` lines no longer emitted
   (subsumed by `MERGE_REMOVE=`); server collection is optional-per-name.
2. **Unmerge failure warns and continues** (files + entry kept), matching
   the driver's standing teardown policy and Portage's non-fatal replace
   unmerge (`vartree.py:5214-5218`). No `mfail`: a failed old-instance
   teardown must not fail an otherwise good merge.
3. **`FEATURES` not threaded to the child.** The no-config fallbacks equal
   the `make.globals` defaults (`unmerge-orphans`, `preserve-libs` on),
   so behavior matches a default client. Threading resolved FEATURES
   through `merge_script` args would be a bigger interface change.
4. **`ship_old_hook_envs` (server) and `run_old_hook` (helpers) left in
   place.** Dead for the driver now, but covered by their own passing
   tests; removal would touch `binpkg_flow.rs`/`stages.rs` + 3 tests for
   no behavioral gain. Same for `docs/remote-merge.md` slice-4 wording
   ("old hooks warn-and-skip…") — mildly stale, left for the owner.
5. **Entry point is `ebuild <copy> unmerge`, not a new subcommand.**
   `run_unmerge` computes `others_in_slot` from the live vdb, so the
   already-merged new instance (same full slot) protects shared files as
   replaced — verified by the passing test's `--- replaced dir` line.
