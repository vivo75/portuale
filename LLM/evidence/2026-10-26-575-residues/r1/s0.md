## The rule (Portage)

An unsatisfied dependency of a Package parent makes `_add_dep` return 0 (D:3535). `_create_graph`
then returns 0 at once (D:3276-3280), so the walk stops there. `_resolve` returns
`0, myfavorites` (D:5691-5693) before `altlist()` (D:5696 → D:9352-9354 → `_resolve_conflicts`
D:9473-9485 → `_process_slot_conflicts` D:2123). So the slot conflicts in that pass are never
processed: no `"slot conflict"` backtrack info is filed (D:2276-2279), and no ABI or solvable-conflict
handling runs. The `if "slot conflict"` / `elif "missing dependency"` order in `B:276-279` never
matters, because the two infos cannot come from the same pass.

This holds whether or not the dep files `"missing dependency"`:
- a plain miss or a masked dep with backtracking on files it (D:3517-3518) and restarts, masking the
  parent (B:203-213);
- a USE-only miss ("Do not backtrack if only USE have to be changed", D:3488-3497, `_select_package`
  on `atom.without_use` finds a package) files nothing. Under `--autounmask=n`, `need_restart()` is
  then false, so `_backtrack_depgraph` stops with 0 backtracks (D:12407-12418), the conflict is
  never backtracked over, and the run fails;
- the bug-693836 arm (D:3498-3515) sets `_skip_restart` and returns 0: also no conflict processing.

Escapes, where the walk does **not** stop and the conflicts are still processed:
- `allow_unsatisfied` (the `_complete_graph` re-walk): D:3419-3421, return 1;
- an optional or ignored build-time dep: D:3411-3413, return 1;
- an installed parent past the requested depth that was initially unsatisfied: D:3438-3453,
  return 1;
- a built slot-operator dep that the unsatisfied probe heals: D:3463-3470, return 1 (config
  feedback);
- an installed parent already in `runtime_pkg_mask` with no match at all: D:3478-3486, return 1;
- `--backtrack=0` (`_allow_backtracking` false): the walk still stops at D:3535, but nothing is
  filed and the run fails at once.

Also: a conflict pulled in **after** the stop point never exists in Portage's graph. A `--backtrack=0`
or final-failure display therefore shows only the conflicts added before the dep that failed (shape
A below).

portuale: `collect_feedback_inner` (`crates/portage-repo/src/resolve/feedback/mod.rs:301-337`) runs
`step_slot_conflict_abi`, `step_solvable_slot_conflicts`, `file_consumer_pin_conflicts` and
`step_slot_conflict_backtrack` before `step_missing_dep` (:340). `step_missing_dep` only acts on
`pass.missing_dep_trigger`, and `maybe_missing_dep_backtrack`
(`resolve/pass/unresolved_dep.rs:71-76`) never sets that trigger for a USE-only miss, which is
correct. Only 10a's `consumer_pin_conflict_may_feed_back` (`feedback/reverse_dep_pins.rs:86-103`)
already applies the "no unsatisfied dep in this pass" gate (`masked_deps`, `use_unsat_deps`,
`plain_miss_deps`, `missing_dep_trigger`). The walker's own conflicts do not.

## §P verdict

The premise holds in Portage, and it is a **resolver** item (phase 2, Claude). It goes wider than
the task text says, though. "Move `step_missing_dep` ahead" is **not enough**:
- the gate has to fire on any unsatisfied dep that stops Portage's walk, USE-only misses included
  (RED 4/5), and those set no `missing_dep_trigger`. The predicate 10a already uses
  (`masked_deps`/`use_unsat_deps`/`plain_miss_deps`/`missing_dep_trigger`,
  `reverse_dep_pins.rs:96-100`) is the natural general gate, minus Portage's escapes listed above;
- in such a pass the gate must suppress **all** of `_process_slot_conflicts`'s products
  (`step_slot_conflict_abi`, `step_solvable_slot_conflicts`, `step_slot_conflict_backtrack`),
  plus, unverified, the post-`altlist` producers (`step_built_parent_update_probe`, which is
  D:5707 `_rebuild.trigger_rebuilds` / the slot-operator trigger after the conflict exit at
  D:5700-5705).
So the task text needs amending per §P before the RED, and the plan routes that through an external
re-review.
