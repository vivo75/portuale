## The rule

For an installed consumer that the forward walk recurses into (`--deep`, the `Normal` view,
D:3834-3842), Portage registers its built `:S/SS=` atom as a slot-operator dep and pulls the
installed child the atom names. The child then sits in a slot conflict with the merge-bound new
sub-slot. At the end of the pass, two producers each file the same `slot_operator_replace_installed`
set, `{consumer:slot, child:slot}`:
- the slot-conflict ABI backtrack, `_process_slot_conflict` → `_slot_conflict_backtrack_abi`
  (D:2149-2218, D:2297-2330), which needs no `--update`;
- the trigger, `_slot_operator_trigger_reinstalls` → `_slot_operator_update_probe` →
  `_slot_operator_update_backtrack` (D:3104-3147, D:2591-2830, D:2415-2466), which needs
  `want_update`.

The next try turns the set into `@__auto_slot_operator_replace_installed__` force-reinstall
arguments (D:5473-5498). That gives `r U` on the provider, `rR` on the consumer, and the
"causes rebuilds for:" block. portuale schedules the same rebuild only when the consumer is in
`ctx.slot_op_reachable`, the installed closure of the complete-mode seeds (`@world`, `@selected`,
`@system`, profile packages, the request atoms). A consumer that only the request's forward walk
reaches is outside that closure, so the rebuild is dropped. The walk had already forgiven the
conflict, assuming this scan would schedule the rebuild.

## 2. Why `p589apull` and `p589cpull` do not trigger it

Their installed `virt` has no built slot-operator atom (vdb RDEPEND is the `||` only). So:
- dynamic deps append nothing (FV:180-195);
- the Normal-view walk never pulls the installed `prov-5.42`;
- no slot conflict appears and `_slot_operator_deps` stays empty, so neither producer has anything
  to probe.

The `||` picks `~core-1.0` in both fixtures, whatever the arm order. The 5.42 arm is an
`installed_downgrade` against the in-graph 5.44 (DC:530-541, 634-635), and the 5.40 and 5.38 arms
are unavailable (`puD-p589{a,c}pull-portage-debug.trim.txt`, lines 52-67). So the trigger is the
**built `:=` atom**, not the arm order: `p569pull` (5.42 first) and `p589bpull` (5.40 first)
behave identically.

## 3. Mapping onto portuale (source read, plus the probes above)

portuale's walk is the same up to the rebuild:
- dynamic deps match;
- the walk recurses into `virt-1` (debug `Parent: (dev-libs/p589bvirt-1…, installed) Depstring: …`);
- the `||` picks `core`;
- it graphs the installed `prov-5.42` beside the merge-bound `prov-5.44` (debug digraph).

Then, on both phase passes, the trace prints `BT try=N kind=Settle replace-in 0`. The stops, in
order:

1. **The walk forgives the conflict.** `existing_slot_unsatisfied`
   (`crates/portage-repo/src/resolve/pass/existing_slot.rs:150-201`, the forgiveness at 164-185)
   does not record the conflict Portage records (D:3734-3745). It skips it when:
   - `backtrack_max > 0`;
   - an installed instance accepts the atom;
   - `built_slot_operator_rebuild_trigger` holds (`resolve/rev_dep.rs:71-80`).

   The comment says the rebuild scan schedules the rebuild instead (backlog #290). So
   `step_slot_conflict_abi` (`resolve/feedback/slot_conflict_abi.rs:17`), the port of
   `_slot_conflict_backtrack_abi`, never sees this conflict. `--backtrack=0` turns the forgiveness
   off, and then both sides print the same conflict (`uD-bt0-*`).
2. **The scan does not reach the consumer. This is the condition that differs from Portage.**
   - `step_unsatisfied_dead_end` (`resolve/feedback/unsatisfied_dead_end.rs:22-104`) is the
     clean-pass port of `_slot_operator_trigger_reinstalls`.
   - It calls `slot_operator_rebuild_scan` with `scope = ctx.scan_reachable(entries)`
     (`unsatisfied_dead_end.rs:41-47`).
   - With no set argument, `ctx.rs:206-213` + `scan_scope` (`ctx.rs:398-411`) return
     `ctx.slot_op_reachable`, the installed closure of the complete-mode seeds plus the request
     atoms (`ctx.rs:271-283`). It is filled only on the seeded phase-2 re-run:
     `crates/portuale/src/pretend/resolve_phases.rs:185-197, 509-528`.
   - The request `p569pull` is not installed, so it seeds nothing, and `virt` is not in `@world`.
     So **`virt` ∉ scope**, and the same-slot arm skips it:
     `same_slot_scope = !new_slot.is_empty() && scope.unwrap_or(reachable).contains(&cp)`
     (`slot_operator/rebuild_scan.rs:157-158`, commented "(frozen): complete-mode reachability
     only").
   - The new-slot arm accepts walked consumers (`:162`), but 5.44 is in the same slot 0, so it has
     no edge.
   - Portage instead ranges over `_slot_operator_deps`, which every walked edge registers
     (D:3826-3832), including the forward walk of a recursed installed consumer.
   - Discriminating probe: put `p569virt` in `@world` (so it is in `slot_op_reachable`) and
     portuale schedules `{p569prov, p569virt}` on phase 2. The result matches Portage byte for byte
     on the rows (`W-uD-p569pull-virtinworld-*`, BT `try=2 kind=Feedback:Config`, then
     `replace-in 2 ["dev-libs/p569prov","dev-libs/p569virt"]`).
3. **The update probe refuses a merge-bound child.** `step_installed_parent_update_probe`
   (`resolve/feedback/slot_operator_probe.rs:103-157`, last in `collect_feedback_inner`,
   `feedback/mod.rs:356-364`) reaches `installed_parent_update_probe`
   (`slot_operator/installed_parent_update_probe.rs:43-195`) for `virt`. Then
   `child_has_slot_update` returns false at once (`slot_operator/built_parent_update_probe.rs:205-211`,
   "A child the graph already merges is left alone"), because `prov` has the merge-bound entry 5.44.
   Portage's `_slot_operator_update_probe` has no such refusal: its `dep.child` is the installed 5.42
   node (D:2591-2830). This probe is also `--update`-gated (`slot_operator_probe.rs:112`,
   `installed_parent_update_probe.rs:61-63`).

   Even without the refusal, `child_has_slot_update` would still refuse. It requires *every*
   replacement atom on the child cp, `||` arms included, to accept the candidate
   (`built_parent_update_probe.rs:241-263, 289-290`), so `=prov-5.42*` vetoes 5.44. Portage drops
   unselected arms through `atom_not_selected` (D:2744-2768). `replacement_accepts` in the rebuild
   scan strips `||` groups instead (`slot_operator/force_scan.rs:418-454, 458`), so it would accept.
4. The reverse-dependency built-atom conflict (10b) does not apply to a walked consumer. It is
   PostMerge only: `post_merge = portage_complete && !installed_walked.contains(consumer)`
   (`resolve/rev_dep.rs:640-646`), which is the port of D:8803-8834.

**The function and the condition.** `slot_operator_rebuild_scan`'s same-slot scope
(`rebuild_scan.rs:157-158`) leaves out installed consumers that the walk recursed into
(`PassResult::installed_walked`, `resolve/pass_state.rs:54-60, 236-241`, filled by
`Deep::recurses_at` = D:3834) when they are outside `ctx.slot_op_reachable`. Portage's equivalent
(D:3104-3147 over D:3826-3832, and D:2297-2330 over the conflict that D:3734 records) covers
exactly those consumers. `--deep=1` (consumer deps deferred) and no `--deep` keep the consumer out
of `installed_walked`, which matches Portage's PostMerge behaviour there.
