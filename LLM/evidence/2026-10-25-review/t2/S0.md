# Task 2 S0: Portage's merge-wait queue and drain order

Method: host-free oracle. The order below is derived from the reference
Portage 3.0.83 source in `3rdparty/portage`
(`lib/_emerge/Scheduler.py`), exact lines cited. No bed run: the drain
rule is fully determined by the cited code paths, and the walk in §3
pins the observable order for the three-package shape the plan asks
for. All line numbers are against `3rdparty/portage` at tag
`portage-3.0.83`.

## 1. A gated merge is always queued — no in-flight condition

`Scheduler._build_exit` (`Scheduler.py:1809-1865`). The gating test is
at :1833-1836:

```python
if not build.build_opts.buildpkgonly and (
    "merge-wait" in build.settings.features or merge.is_system_pkg
):
    self._merge_wait_queue.append(merge)
```

There is no test on the number of running jobs anywhere in `_build_exit`:
a finished gated build is appended to `_merge_wait_queue` whether other
builds still run or not. The `else` arm (:1839-1842) sends only ungated
merges straight to `_task_queues.merge`. System members additionally get
`_system_merge_started` as a start listener (:1837-1838; see §4).

Two related paths, for completeness:

- `_extract_exit` (:1867-1868) delegates to `_build_exit`, so already
  built (binary) packages gate the same way. portuale's scheduler under
  test handles source entries only; the binary path lives in
  `emerge_getbinpkg.rs` and is out of scope for this slice.
- Under `--buildpkgonly` Portage never queues (:1833, first condition).
  portuale's `--buildpkgonly` path (`buildpkgonly.rs::run_buildpkgonly`)
  performs no vdb merges at all, so there is nothing to queue and no
  divergence on that arm.

## 2. The drain moves the whole queue in one pass, FIFO

`Scheduler._schedule_tasks` (`Scheduler.py:2232-2282`). The drain entry
condition is at :2245-2248: the wait queue is non-empty and (no build
jobs and no merges running, or a manual flush). Inside, :2255-2280 is a
`while self._merge_wait_queue:` loop that moves entries to
`_task_queues.merge` in popleft (FIFO = build-finish) order.

The two system-package breaks inside that loop govern queue-to-queue
moves only and do not reorder anything observable with serial merges:

- Break *before* a system package (:2262-2266) applies only when the
  merge queue is already non-empty (a previous pass moved something, or
  a manual flush). The TODO at :2259-2261 says promoting non-system
  packages past it would change merge order away from build-finish
  order — i.e. Portage deliberately preserves FIFO here.
- Break *after* a system package (:2279-2280): one system install per
  drain pass. The comment at :2274-2278 gives the rationale — serialize
  system installs because of fragile states (bug 256616) — which only
  matters with `parallel-install`, when the merge queue runs several
  installs at once. portuale's merges are always serial, so the whole
  moved batch installs back-to-back in the same order either way.

While any moved merge is still installing, no new build starts:
`_merge_wait_scheduled` is appended at :2269, removed in
`_merge_wait_exit_handler` (:1732-1734), and `_schedule_tasks_imp`
returns early while it is non-empty (:2469-2472).

## 3. Schedule walk for the plan's three-package shape (`--jobs 2`)

Entries: A and B gated (`merge-wait`), A finishes first, B finishes
with no other build running; W depends on A's merge.

1. A finishes → `_build_exit` appends A (`:1836`). One job still runs:
   no drain (`:2245` needs `not self._jobs`).
2. B finishes → appended behind A. Now no jobs and no merges run.
3. `_schedule_tasks`: the drain moves **both** A and B to the merge
   queue in one pass (:2255-2280), `state_change` set, so
   `_schedule_tasks_imp` is still gated (`:2471`) — W cannot start.
4. A installs, then B installs (serial merge queue), each exit removing
   it from `_merge_wait_scheduled` (`:1732-1734`).
5. Only now is W dispatchable, and it starts.

Answers for the plan: (a) land order is build-finish order, A then B —
the last finisher never jumps the queue; (b) the dependent W does **not**
build before the next queued merge lands — it starts only after the
whole moved batch has installed.

## 4. `_unsatisfied_system_deps` — checked, not ported (cut)

`_system_merge_started` (`:1686-1730`) records, at each system merge's
start, the scheduled-but-unmerged runtime/post deps; `_schedule_tasks_imp`
(:2472) refuses new builds while jobs run and that set is non-empty
(fragile-system protection, bug 259954). It only bites while other jobs
still run and only for merges in the deep-system set with unmerged
runtime deps. No test in the suite has that shape (scheduler fixture
runs start from an empty vdb, and the wait-set members in the scheduler
tests have no dependencies), so porting it changes no test's order. Cut:
port `_unsatisfied_system_deps` gating as its own backlog item (next free
number at plan time: #581 — verify with grep at filing); the
discriminating shape is a wait-set member with an unmerged runtime dep
plus an unrelated build under `--jobs 2`.

## 5. Note on the plan's defect 2 wording

The plan says portuale "lands ONE queued merge and then reschedules".
The current code does not: `scheduler.rs:828` is a
`while in_flight == 0 && !wait_queue.is_empty()` loop that pops the
whole queue before any dispatch (landing is synchronous, so nothing can
refill it mid-drain). The observable defect is only the `in_flight > 0`
condition at `scheduler.rs:946` (defect 1): the last-finishing gated
merge lands ahead of earlier-queued ones. The fix therefore touches only
the queueing condition plus the drain comment that describes it as
one-at-a-time; the loop itself already implements §2's whole-queue FIFO.
