# S0: which digests Portage 3.0.83 verifies for a binpkg (Task 4, #578)

Probe: `s0_probe.py` + `s0_output.txt` in this directory
(`PYTHONPATH=3rdparty/portage/lib python3 .../s0_probe.py`).
Sources: `lib/_emerge/BinpkgVerifier.py:25-110`,
`lib/portage/dbapi/bintree.py:2831-2873` (`_get_digests`),
`lib/portage/checksum.py:343` (`_apply_hash_filter`), `:378` (`verify_all`),
`lib/portage/util/_async/FileDigester.py`.

## Verified set

- `_get_digests` collects every `get_valid_checksum_keys()` entry with a
  non-empty value, plus `size` iff `int(metadata["SIZE"])` parses
  (`ValueError` -> size silently dropped, with a `!!! Malformed SIZE`
  warning). On the reference host the valid keys are `BLAKE2B BLAKE2S MD5
  RMD160 SHA1 SHA256 SHA3_256 SHA3_512 SHA512 WHIRLPOOL size`
  (`RMD160/SHA3_*` via hashlib; `WHIRLPOOL` via the bundled pure-Python
  fallback, hence "unaccelerated").
- `BinpkgVerifier._start`: remote record without both `size` and another
  key -> `_missing_digests_exception` (no rename). No `size` at all ->
  local packages return OK without checking anything. Otherwise size is
  compared first (`st_size != digests["size"]` -> `_digest_exception`
  with name `size`), then every remaining key is hashed over the file
  (`FileDigester`) and compared one by one.
- Order: `_digester_exit` iterates `hash_names` in `digests` insertion
  order, which follows frozenset iteration -> **nondeterministic** in
  Portage itself. (`verify_all`, used by the Manifest path, iterates
  `sorted()` instead: ASCII `BLAKE2B BLAKE2S MD5 RMD160 SHA1 ...`.)
- Unsupported keys (not in `hashfunc_keys`) can never be in `digests`,
  so nothing is ever "skipped" at verify time; a record carrying only
  unknown keys behaves like a record with no digests at all
  (`verify_all` -> `Insufficient data for checksum verification`).

## `int(SIZE)` semantics (probed)

`" 4618"`/`"4618 "`/`" 4618 "` -> 4618; `"-1"` -> -1 (kept! then the
size comparison fails, `_digest_exception("size", actual, -1)`);
`"+5"` -> 5; `"007"` -> 7; `"x"`/`""`/`"0x10"` -> ValueError (size
dropped); `"46_18"` -> 4618 (Python `int()` underscore quirk, recorded
in `LLM/portage-quirks.md`, not copied). `"4618\n"` -> 4618.

## Filter

`_filter_unaccelarated_hashes` drops `WHIRLPOOL` when other verifiable
hashes exist (it is `bundled-py` here); a lone `WHIRLPOOL` is kept.
`_hash_filter("")`/`"*"` is transparent (no filtering); anything else
filters, and `_apply_hash_filter` always keeps at least one hash (plus
`size`, which is never filtered). The filter runs *after* the remote
missing-digests guard (`BinpkgVerifier.py:41-44`).

Probed subtleties (`s0_output.txt` tail):

- A trailing `"*"` clears the whole filter (`"* -MD5"` filters, but
  `"-MD5 *"` is transparent). The exclusion idiom is `"* -HASH"`.
- A filter with no positive token (e.g. `"-SHA512"`) rejects *every*
  present hash, and `_apply_hash_filter` then keeps exactly one — chosen
  by frozenset order, i.e. **nondeterministically**: 12 fresh processes
  split 6/6 between keeping `MD5` and keeping `SHA512`. A deterministic
  implementation keeps one of Portage's two possible outcomes.

## Failure text (byte shapes, from source)

- Missing (remote): `\n!!! Digest verification failed:\n!!! {path}\n!!!
  Reason: binhost's Packages index lacks size and checksum\n!!! for this
  package\n` (no rename).
- Mismatch: `\n!!! Digest verification failed:\n!!! {path}\n!!! Reason:
  Failed on {name} verification\n!!! Got: {value}\n!!! Expected:
  {expected}\nFile renamed to '{temp}'\n`, and the file is renamed
  (not removed) via `_checksum_failure_temp_file`.
