### 0.2 Cause (read)

- `stale_pin_for_consumer` (`crates/portage-repo/src/slot_operator/rebuild_scan.rs:694-773`,
  `held_back` called at `:754`)
  reduces each recorded key with `selected_parent_atoms` (`:719-725`;
  `slot_operator/abi_probe.rs:157-197`: per `||` group, the arm matching a graph entry, else the arm
  matching an installed instance). No arm matches the graph (`p569prov-5.44` is not `=5.42*`,
  `p569core` is not in the graph), so the installed arm `=dev-libs/p569prov-5.42*` is chosen, even
  though the plan replaces that installed version.
- `StalePinCtx::held_back` (`:513-546`) then refuses: the final 5.44 does not match `=…5.42*`.
  Refusals feed the NOTE (`pretend/problem_reports.rs`) and `--json` `stale-bindings` on both solvers.
- The tree side already has the rule this needs: `tree_route_atoms`
  (`crates/portage-repo/src/resolve/feedback/co_upgrade.rs:308-357`, `pub(crate)`) keeps, per `||`
  group, the provider atoms only when **every** arm names the provider; a group with an arm on
  another package "constrains nothing" (#781; unit tests `or_group_with_an_arm_off_the_provider_constrains_nothing`,
  `or_group_naming_only_the_provider_stays_a_menu`, `:459-476`). It and `selected_parent_atoms`
  both reduce through `cycle_report::reduced_dep_tree` over the same tokens and USE, so a selected
  token and a returned token are byte-identical strings when they are the same atom.
- **pubgrub after M1 (read, not measured):** pubgrub's scan runs with `tree_pin_refuses: true`
  (`slot_operator/eliminate.rs:275`). `tree_held_back` (`rebuild_scan.rs:551-600`) reads the
  consumer's **tree** `p569virt-1.ebuild`, which carries the same `||`; its chosen arm is again the
  installed `=dev-libs/p569prov-5.42*` (`p569core` not in the graph), so on pubgrub M1 most likely
  turns the recorded refusal into a `tree_pin: true` refusal, which `tree_refusal_fix`
  (`solver_bridge.rs:6018`, #808) answers by asking for the `~p569core-1.0` arm. Whether that
  second solve lands on "repaired" is what S0.2 measures; the NOTE text may change in between.
- The fast plan reads the same recorded text best-visible first (`reduced_recorded_atoms`,
  `crates/portage-world/src/rebuild.rs:91-115`), takes the `~p569core-1.0` arm and rebuilds (owner
  decision F1 (b), 2026-11-22).

### 0.3 The candidate change (M1) and what is not known

**M1:** `held_back` skips a selected recorded atom that `tree_route_atoms` over the same recorded
texts does not return for its provider, i.e. an atom from a recorded `||` group with an arm off the
provider. A plain recorded pin (`outpin`: `=…5.42* …:0/5.42=`) and a version-only menu
(`|| ( =…5.42* =…5.40* )`) still hold back, with today's atom text. The tree then decides, as it
does for a consumer without a recorded pin: `StalePinCtx::repairable` (`:604-644`), and the next pass
walks the rebuild (default solver) or the bridge's `tree_refusal_fix` (#808) asks for the arm
(pubgrub).

**Not known, measured in S0.2:** whether the walked rebuild then pulls `p569core-1.0` and keeps
`p569prov-5.44` (as on root `pull` today: `N p569core-1.0`, `rR p569virt-1`, pinned by
`test_770_*`, `test_811_*`), or whether the walk's own `||` choice keeps `=…5.42*` and the upgrade
is skipped instead (as on `a10`). The second outcome would trade property 3 for property 1 and is a
different answer for the owner (Q1 (C)). A third outcome is possible and is the worst one:
**silent** — the NOTE disappears, `p569prov` still goes to 5.44, and no `p569virt` row repairs the
binding (the scan schedules it, but the next pass drops it). That breaks property 1 *and* loses
the property-5 message the program prints today; it is never answer (A) (S0.3, STOP-0).
