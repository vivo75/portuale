## D — defects

### D1. The fast plan names a visible but unreached consumer as having "no visible ebuild", and so disagrees with the resolver on R1. Severity: high for this plan (it invalidates the core witness), medium for the product (property 5). **Proven.**

**Where:**
- `crates/portage-world/src/rebuild.rs:357-365`: the `chosen` lookup `world.slots…find(|s| s.node() == node)`
  runs *before* `held_back` at `:366`.
- `world.slots` holds only the slots the @world walk reached (`lib.rs:613-700`).
- `crates/portuale/src/plan_world.rs:274-278` and `:289` render a `None` provider as "no visible ebuild".

**Inputs:** R1 as the plan defines it. Fixtures `/var/tmp/765fx`, ROOT = a copy of its `var/` with `dev-libs/p569prov`
appended to the world. `p569virt-1` is installed with `|| ( =dev-libs/p569prov-5.42* … ) dev-libs/p569prov:0/5.42=`,
and its ebuild is visible: `KEYWORDS="amd64"`, `repo/dev-libs/p569virt/p569virt-1.ebuild`.

**What the resolver prints** (both solvers, identical): `"stale-bindings":[{"consumer":"dev-libs/p569virt-1","atom":"=dev-libs/p569prov-5.42*","provider":"dev-libs/p569prov-5.44"}]`, plus the #761 NOTE
`dev-libs/p569virt-1: its dependency =dev-libs/p569prov-5.42* is not satisfied by dev-libs/p569prov-5.44`.

**What the fast plan prints:** `"stale-bindings":[{"consumer":"dev-libs/p569virt","atom":"dev-libs/p569prov:0/5.42=","provider":null,"reason":"no visible ebuild"}]`,
with stderr `plan-world: 1 stale slot-operator binding(s) not rebuilt: dev-libs/p569virt (dev-libs/p569prov:0/5.42=, no visible ebuild)`.

**Consequences:**
- p569virt is not in @world's graph, so it has no slot, so it is refused with `provider: None` before the
  hold-back check runs. The reason given is false: a visible ebuild exists (charter property 5, "names the cause").
- The same refusal appears on R2, R4, R5, R6 and R7, because all of them inherit p569virt. In R6 it also
  swallows the case the root was built for (D2).
- The plan's §0.3(c) and row 8 describe the branch as "no chosen version in the consumer's own slot", which is
  true, but the plan never notes that every stale consumer outside the @world walk lands there. A1 ("refuse vs
  silent") does not fit: the resolver is *not* silent here.
- Row 8 needs a new class, and §0.1 / the gate table need a row "consumer reached by the plan's walk".
- `LLM/code-notes/portage-world/rebuild.md:8` also says "reachability plays no role in the scan anymore". That is
  false for the refusal branch.

**Likely (not probed):** a consumer reached only through `DEPEND`/`BDEPEND` gets the same refusal. `plan-world`
defaults to `with_bdeps = false` (`check_world.rs:100-102`), so the walk does not follow those edges. On a real
host that would cover build-only tools as well as orphans.

**Fix direction (proposal):**
- The plan must not run S0 against an R1 that expects agreement.
- Either (a) re-define the agreement key as the consumer cp alone and record the atom and provider difference as
  a classified difference, or (b) make R1's consumer reached: put it in the world or reach it from a world package.
  Re-probe before choosing. With `dev-libs/p569virt` in the world the resolver keeps p569prov at 5.42 while the
  fast plan upgrades it and reinstalls p569virt, which is a version-choice difference, not a stale-rule one (G3).
- For the product, file the misleading reason as a residue for the owner, inside #768 or as its own number.
  Possible fixes:
  - when the consumer has no slot in `world.slots`, look up its best visible ebuild (`Memos`/`list_candidates`)
    and continue to the hold-back check, which would make R1 agree;
  - or change the reason to name the real cause ("not in the @world graph").

  Either one changes user-visible text, so it is the owner's call, like Q7.
- Extend Q2's comment list accordingly. These docs repeat the inaccurate "no visible (tree) candidate":
  `rebuild.rs:57-61`, `:394-396`, `plan_world.rs:271-273`. Do not fix them comment-only while the rendered
  text stays wrong.

### D2. R6 cannot isolate A4 as designed. Severity: medium. **Proven.**

- R6 adds `dev-libs/p698rebuild-1` with only `DEPEND dev-libs/p569prov:0/5.42=`, not in the world.
- Fast plan: `dev-libs/p698rebuild (dev-libs/p569prov:0/5.42=, no visible ebuild)`, which is D1, not A4.
- Resolver: silent, and no reinstall.
- The resolver adds `DEPEND`/`BDEPEND` only for a *walked* consumer (`rebuild_scan.rs:650`). The fast plan
  refuses every *unwalked* consumer through D1. So with the consumer out of the world, the root shows D1. With it
  in the world, the resolver reads DEPEND too, and A4 only remains if bdeps are off, i.e. under `--usepkg` without
  `--with-bdeps`.

**Fix direction:** to witness A4, put the consumer in the world and run the resolver with `--usepkg`. Otherwise
drop R6 and keep A4 a source-only class.

### D3. Row 2's "fast plan always answers `-uDN @world`" is false. Severity: medium, because it breaks the Q4 reinstall-set comparison. **Proven.**

- `plan_world.rs:36` sets `opts.newuse = future.on("plan-world-newuse")`, which is off by default.
- Every probe's stderr says `not checked: blockers, REQUIRED_USE, slot conflicts, USE rebuilds; run 'mrg -puDN @world' for the full plan`.
- The fast plan answers `-uD` without USE rebuilds. `full_plan()` only *names* `-puDN` as the fuller plan.
- Any `--newuse` reinstall from the resolver therefore shows up as a "stale consumer only the resolver reinstalls"
  unless the comparison filters it out. On the real tree `crosscheck-nobin.txt` already has
  `1 resolver-only-reinstall` (`logs/l0-health-20261115T003208Z`).

**Fix direction:** in Q4, define "stale consumers each plan reinstalls" as reinstall rows whose installed VDB entry
has a stale `:=` binding, judged by `compare.py` from the VDB. The alternative is to pass
`--future-options=plan-world-newuse` to `mrg`. Correct row 2 and Q3 either way.

### G1. The agreement set has no non-empty member. Blocking. **Proven.**

The S2-red step 2 names "R0, R1, R2's `p569virt`" as agreement roots.

**To close:**

  consumer. A candidate is a w741-shaped consumer in the world: a recorded `=prov-1*` pin outside any `||`.
  `plan_world.rs:1233-1264` pins the fast side of that shape.

### G2. The normalisation key is inconsistent. Blocking.

- Q4 compares `(consumer cat/pkg, atom, provider)`.
- S1 step 1 and the crosscheck use `(consumer, atom)`.
- The fast `provider` can be `null` (rows 8 and 12), and D1 shows the *atom* differs systematically too.

**To close:** pick one key and use it in Q4, `compare.py`, the pmtest test and the crosscheck. The proposal is the
consumer cp plus a separately reported atom/provider match. State how a `null` provider compares.

### G3. Upstream version differences are not separated from stale-rule differences. Not blocking. **Proven.**

Staleness depends on the provider's final version. With `p569virt` in the world, the resolver keeps `p569prov-5.42`
and reinstalls nothing, while the fast plan upgrades to 5.44 and reinstalls `p569virt`.

**To close:** `compare.py` should first compare each stale provider's final version on the two sides, and classify
any mismatch as "upstream version choice" (already `world-version-differs` in the crosscheck) before judging the
stale rule.

### G4. The strict-xfail scheme is too coarse. Not blocking, but fix before S2-red.

- `xfail(strict=True)` on an equality assertion counts *any* failure as `xfailed`: a crash, `rc≠0`, unparseable
  JSON, or a *new* difference on the same root. A new divergence on R4 to R7 would be hidden behind the old one.
- Q5 also says expected values come "never from portuale's own output", but an accidental difference can only be
  pinned from output.

**To close:** for each confirmed accidental difference, assert the exact expected pair (fast set X, resolver set Y)
with the residue number in the docstring, as a characterisation pin. Failing that, use `xfail(strict=True,
raises=AssertionError)` *and* assert rc 0 and parsed JSON before the comparison. Reword Q5 so it says plainly that
difference pins record current behaviour.

### G5. "Agreement passes at once" needs a demonstrated red. Not blocking.

A characterisation test that is green immediately is acceptable here: there is no product change for it to be red
against, and the repo rule ("a test written after the code proves the code does what it does") is aimed at
tests-after-fixes. It needs a proof that it *can* fail.

**To close:** record in `after/red.txt` one run of the agreement assertion against a root known to disagree (R1 now
does), or against a mutated normaliser, and show it FAILs. The crosscheck unit tests (S2-red step 1) are genuinely
red-first and fine as written.
