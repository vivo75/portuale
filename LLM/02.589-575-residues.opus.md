- **Version scheme (#590)**: portuale uses exact SemVer derived from the
  Portage version it ports:
  - portuale MAJOR = Portage MAJOR × 100 + Portage MINOR;
  - portuale MINOR = Portage PATCH;
  - portuale PATCH = a sequence number. **0** means "porting of this
    Portage version has started; it may not yet match Portage". **1 and
    above** are releases we consider fit for installing packages onto a
    real file system.
  - Portage's fourth digit (fix releases like 3.0.82.2) is **ignored** by
    the scheme; moving to such a fix bumps portuale PATCH. The full Portage
    version we start from is recorded in Cargo metadata
    (`[workspace.metadata.portuale] portage-version`).
  - So today's version is **300.83.0**. Cargo ignores build metadata when it
    orders versions, which is why `3.0.83+0.0` and a five-digit
    `3.0.83.0.0` (rejected by Cargo: "unexpected character '.' after patch
    version number") were both dropped.
- #585's `"version"` value in `mtimedb` is **`portuale-<CARGO_PKG_VERSION>`**
  (today `portuale-300.83.0`), not Portage's `3.0.83`. Portage writes this key
  and never reads it back: `util/mtimedb.py:84` only fills a default,
  `:105` sets `str(portage.VERSION)` on every write, and nothing in
  `lib/` or `bin/` of 3.0.83 reads `mtimedb["version"]`. `commit` compares
  the state before it overwrites `version` (`:94-101`), so our string never
  causes a Portage write by itself, and Portage's next real write puts its
  own value back. Third-party readers (gentoolkit, eix) are out of scope
  (owner, 2026-10-26). Recorded as a deliberate, harmless difference in `LLM/portage-quirks.md`
  (Task 2).

## §R Residues found during the work (both phases)

Any new problem found while implementing a task (a Portage behaviour not
covered, a bug next to the change, a stale claim, a test gap) is handled
like this. **It is not left as a loose backlog entry.**

1. **File it** right away: take the next free number (scan all tiers) and
   add the entry `OPEN (filed <date>, residue of #589 Task N)` with the
   Portage source citation.
2. **Analyse it** (the phase manager does this itself, or uses a read-only
   worker): what Portage does (file:line), what portuale does, how big the
   fix is, whether it touches the merge path or the resolver, and which
   tests or bed cells would show it.
3. **Include it in this plan** by default. Append a task `R<n>` (`R1`,
   `R2`, …) under "Residue tasks" below, in the same format as the other
   tasks (defect, files, RED, fix, gate). Add a revision-log line, and put
   it in the phase whose area it belongs to:
   - opencode for merge, fetch, binpkg, mtimedb and scheduler work;
   - Claude for resolver work.

   A residue found in phase 1 that belongs to phase 2 waits for phase 2.
   Order: right after the task that found it, when the current task depends
   on it; otherwise at the end of its phase.
4. **Only exception: an owner gate.** A residue that would break a Global
   Constraint (contract-suite determinism, a new dependency, the merge-path
   gate, a Portage behaviour that cannot be settled from source) goes to
   `LLM/evidence/2026-10-26-575-residues/OWNER-QUESTION-R<n>.md`: analysis
   plus a crisp question with a recommended answer. That file is committed
   (docs only, standalone), and the manager **moves on**. It never
   implements on a guessed ruling.
5. The close-out lists every R-task (done, or held at a gate). The backlog
   entry of a done R-task becomes `DONE <date>` in the same commit as its
   fix.

## Execution Protocol — Phase 1 (opencode manager + workers)

The manager is the opencode session's top-level LLM. It does not write
product code; it briefs, reviews, verifies and commits.

**Brief.** Every worker brief starts with the block in
`LLM/tools/scope/brief-template.md`. Fill in: branch
`fix/2026-10-26-575-residues`, plan `LLM/02.589-575-residues.opus.md`,
Portage 3.0.83. Then add the task text verbatim, the files, the oracle, and
the exact RED/GREEN commands. The report goes to
`LLM/evidence/2026-10-26-575-residues/t<N>/report.md`.

**Dispatch.** Use opencode's own subagent mechanism, and check in the log
which model ran. If the manager shells out to `opencode run`, it passes
`--model` explicitly and wraps the call in `LLM/tools/scope/oc.sh`. Never
`pkill`. Space launches ≥60 s apart. Only read-only oracle or analysis
workers may run beside the one implementer. **Never two writers at
once**: they share `target/` and the pmtest corpus.

**Per slice, the manager:**
1. Waits until the worker exits **and** its files stop changing.
2. Reviews the diff itself against the task and the Global Constraints:
   - the oracle is cited in each test docstring;
   - every new ebuild fixture has a real-md5 cache entry;
   - comments are short and the details sit in code-notes;
   - there is no unrelated churn.

   Fix-ups go to a fresh worker.
3. Runs the full gate itself and compares failures by test name against the
   baseline. If order-dependent fixture pollution shows up, run
   `git clean -fdq fixtures/` in pmtest. Read corpus drift line by line
   before any `PORTUALE_CORPUS_BLESS=1`; unexplained drift blocks the
   commit.
4. Commits the pmtest half first, then the portuale half.
5. Updates the docs in the same commit:
   - the backlog entry becomes `DONE <date>` with branch and SHAs, or is
     narrowed;
   - one paragraph is appended to `LLM/what-this-proves.md` for every
     behaviour change, with a runnable, live-checked example.
6. Applies §R to anything new.

**Bed runs.** Freeze the binary first:
`cp -p target/release/portuale /var/tmp/bedbin/portuale`. Then run
`PMTEST_PM=portuale-bed PMTEST_NO_BUILD=1 differential-test-bed/run/<runner>.sh`
from `../pmtest`. Fetching runs need
`GENTOO_MIRRORS=http://$(ip -j -4 -o addr show eth0 | jq -r .[0].addr_info[0].local):8080`.
Never rebuild while a non-frozen bed run is going.

**Phase 1 end.** Write `LLM/evidence/2026-10-26-575-residues/phase1-report.md`:
tasks, commits, gates, open owner questions, and the phase-2 R-tasks filed
so far. Commit it (docs only). Then stop. The owner starts phase 2 in
Claude Code.

- the merge gate fails;

- corpus drift cannot be explained;
