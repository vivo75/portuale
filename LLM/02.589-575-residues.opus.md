  Portage version it ports:

  (owner, 2026-10-26). Recorded as a deliberate, harmless difference in `LLM/portage-quirks.md`

## §R Residues found during the work (all phases)

Any new problem found while implementing a task (a Portage behaviour not
covered, a bug next to the change, a stale claim, a test gap) is handled
like this. **It is not left as a loose backlog entry.**

1. **File it** right away: take the next free number (scan all tiers) and
   add the entry `OPEN (filed <date>, residue of #589 Task N)` with the
   Portage source citation.
2. **Analyse it** (the phase manager does this itself, or uses a read-only
   worker): what Portage does (file:line), what portuale does, how big the
   fix is, whether it touches the merge path or the resolver, and which
   tests or bed cells would show it.
3. **Include it in this plan** by default. Append a task `R<n>` (`R1`,
   `R2`, …) under "Residue tasks" below, in the same format as the other
   tasks (defect, files, RED, fix, gate). Add a revision-log line, and put
   it in the phase whose area it belongs to:
   - opencode for merge, fetch, binpkg, mtimedb and scheduler work;
   - Claude for resolver work.

   A residue found in phase 1 that belongs to phase 2 waits for phase 2.
   Order: right after the task that found it, when the current task depends
   on it; otherwise at the end of its phase.
4. **Only exception: an owner gate.** A residue that would break a Global
   Constraint (contract-suite determinism, a new dependency, the merge-path
   gate, a Portage behaviour that cannot be settled from source) goes to
   `LLM/evidence/2026-10-26-575-residues/OWNER-QUESTION-R<n>.md`: analysis
   plus a crisp question with a recommended answer. That file is committed
   (docs only, standalone), and the manager **moves on**. It never
   implements on a guessed ruling.
5. The close-out lists every R-task (done, or held at a gate). The backlog
   entry of a done R-task becomes `DONE <date>` in the same commit as its
   fix.

## §P An S0 that contradicts the task (all phases)

Every S0 (oracle read, host probe, bed capture) checks the premise of its
task. If the S0 result contradicts what the task says Portage does, the
worker **stops product work on that task** and reports it. The manager does
not let the worker adapt on the fly. Instead it:

1. writes the contradiction (Portage file:line, the probe output) to
   `t<N>/premise.md`;
2. amends the task text in this plan, with a revision-log line;
3. continues only if the amended task stays inside the owner rulings in §0
   and the Global Constraints. Otherwise it writes an
   `OWNER-QUESTION-t<N>.md` and moves on to the next task.

A change to the resolver tasks (8–10) always goes through an external
re-review before code.

### Task 2: write `mtimedb` in Portage's full shape (#585)

**Defect.** `MtimeDB._load` (`lib/portage/util/mtimedb.py:49-92`) does all
of this on every load:
- maps `old` → `updates` and drops `cur`;
- fills `starttime` (0), `version` (""), `info`, `ldpath` and `updates`
  ({});
- deletes every key outside `_MTIMEDBKEYS` (`:15-23`) with
  `Deleting invalid mtimedb key: <k>`.

`commit` (`:94-101`) writes only when the state changed. `__write_to_disk`
(`:103-117`) sets `version`, writes atomically with `ensure_ascii=False`,
`indent="\t"`, `sort_keys=True`, and sets mode 0644 with the portage gid.

`crates/portuale/src/mtimedb.rs` (`write_sections` :146,
`preserved_parts` :391) writes only the sections it manages and keeps every
other key, so a fresh file has different bytes and a stray key survives.

**When Portage loads it.** `load_emerge_config`
(`lib/_emerge/actions.py:3378-3391`) builds `MtimeDB` for the target root,
and a second one for the running root when the two differ. `emerge_main`
calls it (`lib/_emerge/main.py:1360`) for every action except the early
exits above it (`help`, `moo`, `status`, and `sync` failures,
`main.py:1288-1357`), so `--info`, `--version`, `--pretend` and merges all
load the file and print the unknown-key warning. portuale reads `mtimedb`
only in the paths that need it: `--info` never touches it
(`pretend/standalone_actions.rs:257-293`). Normalizing the read/write
helpers alone therefore cannot match Portage's output.

**Files:**
- Modify: `crates/portuale/src/mtimedb.rs` (the load and normalize step, the write)
- Modify: the emerge entry point that runs before the action dispatch (`crates/portuale/src/pretend/mod.rs` `run`, ahead of `validate_and_early_actions`, the place #584 moved the global-updates call to), and `pretend/standalone_actions.rs` if `--info` returns before that point
- Test: in-file tests in `mtimedb.rs`; pmtest pins in `test_emerge_pretend_contract.py` for `emerge -p <atom>`, `emerge --info` and `emerge --version` on a root whose `mtimedb` carries a stray key, plus one with target root ≠ running root (warning count from S0)
