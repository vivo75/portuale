## D — defects (new, introduced by or surviving the fold-in)

**N1 — blocking for S1 acceptance. Proven by reading. STOP-1's code-equality check cannot pass, and the tool
cannot be called as S1.4 describes.**
- S1.4 and §4 STOP-1 say: run `python3 LLM/tools/strip_comments_eq.py` "between the `v3fix` worktree's
  `order.rs` and S1's", and any difference is STOP-1.
- The tool's interface (`LLM/tools/strip_comments_eq.py:3-8`) is `strip_comments_eq.py [REV] [FILE...]`. It
  compares a git revision with the working tree, over the whole file. The `v3fix` worktree is "never committed"
  (S0.2), so there is no REV that holds it.
- Even with a REV, the result is fixed in advance. S1.1-S1.2 rename `w764_an_uncuttable_runtime_cycle_is_left_to_the_walk`
  and rewrite its assertions, and they change the first-cut assertion of
  `the_virtual_provider_edge_is_the_only_cuttable_edge`. Both tests live in `order.rs`'s own `mod tests`. The
  `v3fix` mutation (`after/red.txt` R3) changed only `cycle_cut`. So the stripped files always differ, and STOP-1
  fires on every correct execution.
- Fix direction: compare only the non-test code. One way: apply `before/v3fix.patch` to a scratch copy of
  HEAD's `order.rs`, cut both files at `#[cfg(test)]`, and compare the code parts with the tool's `strip()`
  function. Another way: commit `v3fix` on a throwaway local ref in the worktree and run
  `strip_comments_eq.py <ref> crates/portage-world/src/order.rs` with test-module changes listed as expected.
  Write the chosen procedure down.

**N2 — high for S2. Likely (spec reading; no capture, because host and bed are checker-clean). `late_build_needs`
counts "never provided" as "merged later", and its scope exceeds what S0.5 measures.**
- S2.3 defines a need as met when an installed version matches it or an earlier row provides it. Every other
  need gets a line, and each of the three wordings says "merged later".
- Two kinds of build atom are unmet without anything being merged later:
  - **An atom with no row target.** The walk records such atoms as `unmatched` (`lib.rs:637`, `:649-650`;
    `World.unmatched` `:503`), or gives them no slot (a masked best is filtered at `lib.rs:845`). Nothing
    installed matches them either. `plan_world.rs` never prints `unmatched` today.
  - **An atom whose target is an earlier row** whose planned USE lacks a required `[flag]`. The fast plan says
    it does not check this ("not checked: … USE rebuilds").
- For both, S2.3 prints "…, merged later; no build cycle joins them, so the order itself is wrong". That is a
  false line, and property 5 is exactly what #772 is fixing. The "no build path back" wording also claims to be
  "possible only if #771 stays pinned", which is false for both cases.
- Scope: S0.5's census covers only the edges of `build_time_cycles` SCCs. S2.3 checks every build atom of every
  row. So `772-verdict.txt` cannot predict a line outside an SCC: a C1b edge on a V3-like shape if #771 does
  not ship, or an `unmatched` atom. In either case STOP-4 fires without telling the operator why.
- Fix direction:
  - Define a late need positionally, as the census measures it: an atom whose resolved target (`atom_nodes`) is
    a row placed **after** the requesting row, and which neither an installed version (outside C1b) nor an
    earlier row meets.
  - Leave atoms with no row target, and USE mismatches on earlier rows, to the checker and the existing
    "not checked" line.
  - Extend S0.5's census to every late build edge of the produced order, not only SCC edges.

**N3 — medium. Proven by reading the PMS. The `w772d` fixture puts the `:=` binding in `BDEPEND`, where the PMS
gives it no binding meaning.**
- PMS `dependencies.tex:348-350`: the `=` operator, "for runtime dependencies", binds to "the best version
  installed as a build-time (`DEPEND`) dependency".
- `BDEPEND` is CBUILD tooling. A `:=` there records no binding that the runtime relies on, so "duser's binding
  would go stale" (S2.3's C1b wording) is not grounded for this fixture. The round-1 D3 candidates on the bed
  were `DEPEND` atoms (`elfutils DEPEND libarchive:=`).
- If the C1b rule is implemented "per slot operator" regardless of class, the fixture makes a tool-only `:=`
  produce a C1b line.
- Fix direction:
  - In `w772d`, set `w772duser-2` to `DEPEND="dev-libs/w772dprov:="` and `RDEPEND="dev-libs/w772dprov:="`, and
    keep `w772dprov-2 BDEPEND dev-libs/w772duser`. The derived order is unchanged (`duser, dprov`; the edge
    still carries a build bit).
  - Restrict C1a/C1b in the §0.3 table and in the S2.3 matcher to a `DEPEND` slot-operator atom (the binding the
    PMS defines). A `BDEPEND` `:=` is C1a.
  - The docstring should cite `:348-350` rather than only `:340`.

**N4 — medium. Likely. The census is not tied to the order S2 will check.**
- S0.5 applies `census.patch` "in the same worktree" as `v3fix`, but does not say whether the patch goes on top
  of the fallback.
- The S2.4 prediction depends on row positions, and the fallback is allowed to move **host** rows (Q1: listed,
  not a STOP).
- So a census made on the before order predicts the wrong lines whenever S1 ships with host moves. A census made
  on `v3fix` predicts the wrong lines whenever Q1 stops #771. Either way STOP-4 can fire on a correct S2.
- Fix direction: run the census on both orders (`census-{plan}-{before,v3fix}.txt`), and let S2.4 compare
  against the one that matches S1's outcome.

## G — gaps

**G-A. The bed run does not say where the checkers and the census run.**
- The bed VDB is visible only inside the container (`in-container.sh` header). Yet S0.4 runs
  `health_checker.py --vdb` and `strict_health_checker.py` "on both plans", and `bed-plan.sh` as specified runs
  `mrg` only.
- S0.5 runs the census binary on the bed, but S0.2 builds no `bin-census/` dir.
- To close: `bed-plan.sh` takes the bin dir as an argument. In the same container it mounts
  `../pmtest/pytests-contract-suite` (`PMTEST_CHECKERS`) and `LLM/evidence/02.764` read-only, as
  `LLM/evidence/02.764/bed-check.sh:10-11` does. S0.2 adds `/var/tmp/771/bin-census/`.

**G-B. The bootstrap line's "true path through the boot node" has no algorithm.**
- In a 2-cycle (w749) any path is the right one. In a larger SCC, a shortest cycle through the boot node can
  leave out the edge that `Bootstrap::drops` removes. The line "… broken by a bootstrap" would then name a
  cycle the reduction does not break.
- To close: specify "the shortest build cycle whose first edge is one `drops` removes (neighbours in name
  order)". Add a unit test on a 3-member SCC with one guarded edge.

**G-C. The S2.3 matcher treats installed versions as present after an earlier row has replaced them.**
- "Met when an installed version matches (any slot)" does not mirror the checker's `available_at`
  (`health_checker.py:524-527`: a replaced installed version counts only until the row that replaces it).
- Example: an atom `<foo-2`, with `foo-1` installed and `foo-2` merged earlier. The checker reports it; S2
  stays silent. That is no worse than today, but it is not the "check of the produced order" Q2 promises.
- To close: count an installed version as present only until the row that replaces its slot. Add a unit test.
