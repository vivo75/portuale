# Adversarial review of the runbooks and plans for backlog #768-#773

Reviewed 2026-11-22 at portuale `466b1a2e` (binary built 2026-11-16) / pmtest `d6c89e9`:
`LLM/02.768-773-runbook-common.md`, `LLM/02.768-769-runbook.md`, `LLM/02.770-runbook.md`,
`LLM/02.773-pubgrub-rebuild-against-tree-pin.opus.md`, `LLM/02.771-772-runbook.md`, and the

**Verdict: runbook 1 (#768-769) must not be launched as written.** Its central expectation is
false (F1), and the executor would write all of S1 before finding out. The others can run
after the fixes below. Runbook 3 (#773) needs one pin corrected.

## Defects

### F1 — after S1 the fast plan rebuilds `p569virt` where the resolver refuses it. Critical. Proven.

Runbook 1 (Task 4 pins, Task 5 Step 7) and plan 02.768-769 (§0.2, S1.5, S2.3, S3.3) expect
that once the fast plan stops refusing out-of-walk consumers early (D1), it gives the
resolver's row on every root where `p569virt` is stale outside the walk:
`(p569virt, =dev-libs/p569prov-5.42*, dev-libs/p569prov-5.44)`. It will not.

- The recorded text of `p569virt-1` in the shared VDB is
  `|| ( =dev-libs/p569prov-5.42* =dev-libs/p569prov-5.40* =dev-libs/p569prov-5.38* ~dev-libs/p569core-1.0 ) dev-libs/p569prov:0/5.42=`.
- `reduced_recorded_atoms` (`rebuild.rs:89-113`) reduces it with `Memos::branch_preference`.
  In plan mode, `newest_slot` is true: `analyse` builds the memos with `opts.rebuilds`, and
  `plan_world.rs:35` sets it. In that mode an arm whose atoms the best visible version
  matches ranks `BestVisibleAvailable`, which outranks `Installed`
  (`portage-use-reduce/src/lib.rs:824-862`). So the `~p569core-1.0` arm wins, and no
  hold-back atom on `p569prov` survives.
- With no hit, `judge` goes on to `tree_names_provider`, which is true. `p569virt` is then
  **rebuilt**, and seeding brings `N p569core-1.0`.
- Witness, already archived: roots `virtw`/`vw2` of #766, where `p569virt` is walked, so D1
  never applied. `LLM/evidence/02.766/before/compare.txt`: fast `reinstalls ['dev-libs/p569virt']`,
  refusals `[]`; resolver refusals `[]`, reinstalls `[]`. #766 classified it as a
  version-choice difference; it is a different reading of the recorded `||`. Live today,
  root `virtw`: `N p569core-1.0`, `U p569prov-5.44`, `R p569virt-1`.
- The resolver reduces the same text installed-first (`selected_parent_atoms`) and refuses on
  `=…5.42*`. Captured today on root `prov`: both solvers print the NOTE
  `dev-libs/p569virt-1: its dependency =dev-libs/p569prov-5.42* is not satisfied by dev-libs/p569prov-5.44`.

Roots whose pin is wrong: `prov`, `bdw`, `unred`, `outr`, `bdout`, `outpin`, `r698`, `gone`,
and `a10` (F3). The runbook's STOP-1 would fire at Task 5 Step 6. Nothing would be broken,
but a whole slice of work would be thrown away.

Which side is right is the owner's decision; it was not among the 2026-11-16 decisions. Two
facts bear on it:

- `p569virt-1`'s tree ebuild can follow the new provider through the `~p569core-1.0` arm
  (the default solver does exactly that on root `pull`: `N p569core-1.0` plus
  `rR p569virt-1`). So the fast plan's rebuild repairs the binding (charter property 1),
  while the resolver's out-of-walk refusal leaves it stale (only said, property 5).
- A recorded `||` was satisfied, at build time, by what was installed then. Reducing it in
  plan mode asks "which arm would I pick today", not "which arm was used".

Options to put to the owner before runbook 1 starts:

- **(a)** The fast plan reduces *recorded* text installed-first (`newest_slot = false` for
  `reduced_recorded_atoms` only). It then refuses like the resolver. This makes F2 live on
  `pull`, `virtw` and `vw2`, so F2 must be fixed in the same slice.
- **(b)** Keep the plan-mode reduction and let the fast plan rebuild. The agreement pins
  become difference pins, and the resolver's out-of-walk refusal is filed as a property-1
  residue.
- **(c)** Both sides ask the tree for a route before refusing an out-of-walk consumer. This
  reverses the Q-D posture and changes the resolver: a new plan.

Whichever is chosen, runbook 1's pins (Task 4 Step 4 (c)/(d), Task 6 Step 1, Task 7 Step 3)
and Task 5 Step 7's must-hold list are rewritten from a capture taken after a throwaway S1
build, not derived again by hand.

### F2 — the #769 waiver reads the tree with `provider_atoms`, which flattens `||`. High. Latent.

Plan Q-E and runbook 1 Task 6 Step 4 judge "does the tree accept the new provider" with
`provider_atoms` + `provider_atoms_accept`. `provider_atoms` uses `flat_dep_atoms`, which
returns the atoms of every `||` arm. For `p569virt-1`'s tree text, that gives the versioned
menu `=5.42* =5.40* =5.38*`, which rejects 5.44, although the `~p569core-1.0` arm accepts the
group. Plan 02.770 §0 item 4 names this exact reading as the cause of the pubgrub false NOTE
(#781). The fast plan would copy the defect into a second planner.

It is not witnessed on runbook 1's roots only because F1 removes the hold-back hit. Under
F1 option (a) it becomes witnessed on root `pull` (walked `p569virt`, hit `=5.42*`, route via
`~p569core`).

Fix: judge the tree with the arm selection the planner itself uses. That is the fast plan's
`reduced_recorded_atoms` over the tree text with the candidate's effective USE (as
`tree_names_provider` already does), then `provider_atoms_accept` on the reduced atoms. Make
`provider_atoms_accept` public only.

### F3 — #773's fast-plan pin is wrong, and so is runbook 1's `a10` expectation. Medium. Proven by derivation from F1.

`LLM/02.773-…` Task 2 pins the fast side on `a10` as `(set(), {"dev-libs/p573virt"})`.
Runbook 1 Task 5 Step 7 expects `R p573virt-1` and no `U p569prov`. Root `a10` also carries
the shared VDB's `p569virt-1`, stale outside the walk, so:

1. Iteration 1: by F1, both `p573virt` and `p569virt` are rebuilds.
2. Iteration 2: both are seeded. `p573virt`'s tree pins `=5.42*`, so the provider stays at
   5.42 and `p569virt`'s binding is no longer stale. But `rebuilds` never shrinks.

Expected fast outcome: `R p573virt-1`, `R p569virt-1`, `N p569core-1.0`, no `U p569prov`; the
reinstall set ∩ bound is `{p573virt, p569virt}`.

Fix: take the pin from a capture after runbook 1 lands, not from derivation. Also add to
residue #777: a seeded rebuild whose binding stops being stale in a later iteration is
still rebuilt (needless work, charter property 3). It is the same root cause as the
hold-back side #777 already names.

### F4 — #772's late-need rule is ambiguous when a node has two rows. Medium.

Runbook 4 Task 7 Step 3 decides "met by an earlier row" with "`to` is a row at index `< i`".
A bootstrap plan has two rows for the boot node: the boot row and the definitive row
(`bootstrap.rs:99-123`). For `w749`, row `pkgnew` (index 1) needs `otherpkg[useblah]`, whose
rows are at 0 (boot) and 2. An implementation that looks up "the" index of `otherpkg` gets 2,
calls the need late, finds nothing installed, and prints a false "merged later" line. The
pinned w749 test would catch it, but only after the code is written.

Fix: state the rule per need — met when **any** row before `i` provides a matching version
(for the boot row: the declared USE minus the reduced flag), and late only when the earliest
matching row is after `i`.

### F5 — #772 rule 4 (the `||` arm re-reduction) is underspecified for a Sonnet executor. Medium.

"Re-read the row's own metadata text … giving the preference closure the best rank to a
branch all of whose atoms are met at row `i`" leaves the closure, the tie-break and the USE
set to the executor. That rule is where classes C5 and U are told apart, and STOP-0 and
STOP-4 depend on it.

Fix: record the `||` origin at walk time instead. Keep, per node atom, the sibling arms of
its group (the plan's G7 already says `node_atoms` must keep the `||` origin). Rule 4 then
becomes "met when any sibling arm is met by rules 1-3". Specify that data shape in Task 3
Step 1, so the census and the product use the same one.

### F6 — runbook 4's bed STOP-3 hash predates runbooks 1-3. Low-medium.

`96bc81c1e57d5e49` is the `FAST_world.json` of `l0-health-20261116T113020Z`, taken at #764.
Runbook 4 now runs after runbook 1, which changes `portage-world`. Runbook 1 Task 8b
expected no stale-binding change on the bed, which makes a moved row unlikely, but it lists
moved FAST rows as a possibility. If it recorded any, runbook 4 Task 2 Step 4 stops falsely.

Fix: "the hash runbook 1 Task 8b recorded for its after-run, or `96bc81c1e57d5e49` if it
recorded no FAST row change".

### F7 — two of runbook 1's #769 table cases cannot be built as written. Low.

Cases 4 and 6 (Task 6 Step 1) put the old-provider pin in the tree's `RDEPEND` while another
world package asks `>=…-2`. The walk then holds both atoms on one slot, so the outcome
depends on `reorder`. The runbook allows dropping them, but case 6 is the only test of N5
("every hit is judged").

Buildable shape: put the tree pin in `DEPEND` only. The consumer is installed at its tree
version, so iteration 1 follows only `RUNTIME_KEYS` for it (`lib.rs:240-258`) and never sees
the pin, while the waiver reads all five keys for a walked consumer and refuses. That keeps
both cases deterministic.

### F8 — the check-world guard test proves nothing. Low.

Runbook 1 Task 5 Step 5: `--check-world` never seeds (`opts.rebuilds` is false there), so
"no requester line for the seeded consumer" holds before and after the change. The second
half (the `R` row in `--plan-world`) is the real assertion; rename the test after it, or drop
the first half.

### F9 — the seed atom can upgrade the consumer. Low, not witnessed.

The seed `cat/pkg:slot` lets the walk pick the newest visible version, so an out-of-walk
stale consumer with a newer ebuild becomes `U`, while the resolver rebuilds the installed
version (`rR`). The plan accepts it; the runbook should list it as an expected difference
class in Task 5 Step 7, so an executor does not STOP on it.

### F10 — #770's walked set ignores a bounded `--deep`. Low.

`bridge_walked_installed` (runbook 2 Task 5) walks without a depth limit whenever `deep`
is not `NotRequested`. The default solver fills `installed_walked` only where
`Deep::recurses_at` (`resolve/pass_state.rs:256-260`). Under `--deep=N`, pubgrub would
rebuild consumers the default does not reach. Pass the depth along, or record the gap in
the code note and as residue #783.

### F11 — #773 option (A) can name a route that exists. Low.

The tree check of `LLM/02.773-…` Task 5 selects `||` arms "in-graph first, then installed".
When the arm that would accept the new provider names a package the pubgrub plan does not
merge, the check refuses, although the default solver would pull that package in. On `pull`
the arm package `p569core` is in pubgrub's plan (captured today: `N p569core-1.0`), so the
witnesses are safe. Mention the case in the NOTE's code note and under #781.
